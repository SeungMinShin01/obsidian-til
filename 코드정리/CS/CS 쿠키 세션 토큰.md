# CS 쿠키 세션 토큰

> 상위: [[CS 네트워크 기초]]

HTTP는 기억을 못 한다 — 그런데 로그인은 유지된다. 그 장치들의 비교표다.

## 쿠키 — 브라우저가 자동으로 들고 다니는 메모

```
서버 응답:  Set-Cookie: sessionId=abc123; HttpOnly
이후 요청:  Cookie: sessionId=abc123     ← 브라우저가 자동 첨부
```

- 서버가 심으면 브라우저가 **같은 사이트의 모든 요청에 자동으로** 붙여 보낸다. localStorage와 달리 자동 전송이 핵심 차이다
- `HttpOnly`를 붙이면 JS에서 읽을 수 없다 — XSS로 탈취당하는 것을 막는 기본 옵션. `Secure`(HTTPS만), `SameSite`(다른 사이트발 요청 제한)까지가 보안 3종 세트다

## 세션 — 서버가 기억하는 방식

```
로그인 성공 → 서버가 세션 저장소에 {abc123: 회원3} 기록 → 쿠키로 abc123만 전달
다음 요청 → 쿠키의 abc123으로 저장소 조회 → "아, 회원3이구나"
```

- 사용자에겐 **열쇠(세션 ID)만** 주고 실제 정보는 서버가 들고 있다. 서버에서 세션을 지우면 즉시 강제 로그아웃 가능 — 통제권이 서버에 있다
- 약점: 서버가 기억해야 하므로 **서버가 여러 대면** 세션 공유 문제가 생긴다(같은 사용자가 다른 서버로 가면 모름) — Redis 같은 공용 저장소로 푼다

## 토큰(JWT) — 클라이언트가 들고 다니는 방식

```
로그인 성공 → 서버가 서명된 토큰 발급 (내용: 회원3, 만료시각 + 서명)
다음 요청 → Authorization: Bearer <토큰> → 서버는 서명만 검증 (저장소 조회 없음)
```

- 정보를 **토큰 안에** 넣고 서버는 위조 여부(서명)만 확인한다. 서버가 상태를 저장하지 않아(무상태) 서버 여러 대에서도 문제없다 — API 서버·모바일 앱에서 표준이 된 이유
- 약점: 발급한 토큰을 서버가 **회수할 수 없다**(만료 전까지 유효) — 그래서 수명을 짧게 하고 리프레시 토큰으로 갱신하는 구조를 쓴다
- JWT 내용(payload)은 암호화가 아니라 **인코딩**이다 — 누구나 열어볼 수 있으니 비밀번호 같은 걸 넣으면 안 된다. 서명은 "위조 방지"지 "비밀 유지"가 아니다

## 저장 위치와 보안

```
localStorage 저장   JS로 읽힘 → XSS에 취약 / 자동 전송 없음 → CSRF엔 강함
HttpOnly 쿠키 저장  JS로 못 읽음 → XSS에 강함 / 자동 전송 → CSRF 대비 필요(SameSite)
```

- "비밀번호를 평문으로 localStorage에 저장"이 왜 안 되는지의 정답 프레임: F12 열면 그대로 보이고, XSS 한 번이면 통째로 유출된다. 비밀번호는 서버에서 해시(bcrypt)로만 저장한다

- 세션과 JWT 각각의 장단점은? (통제권 vs 확장성 — 서버 여러 대 시나리오로)
- HTTP는 무상태인데 로그인은 어떻게 유지되나? (이 노트 전체가 답)
- JWT를 어디에 저장하겠는가? (정답 하나를 외우기보다 XSS/CSRF 트레이드오프를 아는지를 본다)

# CS 쓰레드와 동시성

> 상위: [[CS]]
> 세부: [[CS 동기화 문제]]

"동시에 두 명이 누르면 어떻게 되나"에 답하는 지식이다. 웹 서버는 기본이 동시 실행이라, 백엔드 면접의 단골 중 단골이다.

## 프로세스와 스레드

```
프로세스  실행 중인 프로그램 하나. 자기만의 메모리 공간 (다른 프로세스와 격리)
스레드    프로세스 안의 실행 흐름. 힙 메모리를 공유하고, 스택은 각자 가진다
```

- 지금까지의 콘솔 프로그램은 main **스레드 하나**로 위에서 아래로 돌았다
- "메모리 공유"가 스레드의 장점이자 모든 문제의 근원이다 — 같은 변수를 여럿이 동시에 만질 수 있다는 뜻이라서
- 스택은 각자라서 지역변수는 안전하고, **힙의 객체(멤버변수·static·컬렉션)가 위험 지대**다

## 자바에서 스레드 만들기

```java
Thread t = new Thread(() -> {
    for (int i = 0; i < 5; i++) {
        System.out.println(Thread.currentThread().getName() + ": " + i);
    }
});
t.start();

t.join();
```

- Runnable(추상메소드 1개 = 람다 가능)을 Thread에 담아 `start()`한다 — `run()`을 직접 부르면 새 스레드가 아니라 현재 스레드에서 그냥 실행된다(고전 함정)
- 실행 순서는 **보장되지 않는다.** 돌릴 때마다 출력이 섞이는 게 정상이고, 그게 동시성의 본질이다
- `join()`은 그 스레드가 끝날 때까지 기다리기다
- 실무는 스레드를 직접 만들기보다 풀에서 빌려 쓴다: `ExecutorService pool = Executors.newFixedThreadPool(10)` — 만들고 부수는 비용을 아끼고 개수를 제한한다

## 내 코드 어디에 이미 있나

- **웹 서버(스프링·톰캣)는 요청마다 스레드**를 배정한다 — DAO의 싱글톤 인스턴스 하나를 수백 스레드가 동시에 부른다는 뜻. "싱글톤 + 멤버변수에 상태 저장"이 위험한 이유가 여기서 나온다
- JS는 반대로 **싱글 스레드 + 이벤트 루프**다. setTimeout·fetch가 "나중에 실행"인 것이 그 구조다 — 대신 공유 메모리 경쟁이 없어 synchronized 같은 게 필요 없다
- 커넥션 풀, 스레드 풀, DB의 동시 접속 — 전부 이 개념 위의 장치들이다

## 면접 단골 질문

- 프로세스와 스레드의 차이는? (메모리 관점으로: 격리 vs 공유, 스택은 각자)
- 스레드를 만드는 두 가지 방법과 start()와 run()의 차이는?
- 멀티스레드 환경에서 싱글톤이 위험할 수 있는 이유는? (공유 상태 — 상태 없는 싱글톤은 안전)
- 스레드가 많을수록 무조건 빠른가? (컨텍스트 스위칭 비용·경쟁 — 코어 수와 작업 성격에 따라 역전)

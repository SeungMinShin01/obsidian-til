# CS 해시와 트리

> 상위: [[CS 자료구조]]

HashMap과 DB 인덱스의 속이다 — "왜 빠른가"에 답하는 노트.

## 해시 테이블 — HashMap의 원리

```
키 → hashCode() → 배열 칸 번호 계산 → 그 칸에 바로 간다   = O(1)
```

- 키를 숫자(해시)로 바꿔 **배열 인덱스처럼** 쓴다. "어디 있는지 계산으로 아는" 구조라 탐색이 필요 없다
- **충돌**: 다른 키가 같은 칸에 떨어지면 그 칸에 목록으로 매달고(체이닝), 한 칸이 너무 길어지면 자바는 트리로 바꾼다. 칸이 부족해지면 배열을 2배로 늘려 전부 재배치(리해싱)한다
- equals를 재정의하면 hashCode도 같이 해야 하는 이유가 여기 있다 — **hashCode로 칸을 찾고 equals로 확정**하는 2단계라, 한쪽만 고치면 같은 키를 다른 칸에서 찾는다
- 순서가 없는 이유도 구조에서 나온다: 칸 번호는 해시값이지 넣은 순서가 아니다(순서가 필요하면 LinkedHashMap)

## 트리 — 정렬을 유지하는 구조

```
이진 탐색 트리: 왼쪽 자식 < 부모 < 오른쪽 자식
찾기 = 대소 비교로 절반씩 버리며 내려감 = O(log n)
```

- 100만 건에서도 20번 비교면 도착한다(2^20 ≈ 100만). "절반씩 버린다"가 log의 정체다
- 한쪽으로만 자라면(1,2,3,... 순 삽입) 사실상 연결 리스트가 되어 O(n)으로 무너진다 — 그래서 실전 트리는 스스로 균형을 잡는다(레드블랙 트리 = TreeMap의 속)
- 해시 vs 트리 선택: 딱 하나 찾기만 하면 해시(O(1)), **정렬 순회·범위 검색**("8월 대여 전부")이 필요하면 트리(O(log n))

## DB 인덱스 = B-트리

- MySQL 인덱스는 B-트리(자식이 수백 개인 넓은 트리)다. 노드 하나가 디스크 블록 하나라 100만 건도 3~4번의 디스크 읽기로 도착한다
- `WHERE member_no = 3`이 인덱스로 빨라지는 것 = 트리 하강. `LIKE '%검색어%'`가 인덱스를 못 타는 것 = 시작점을 모르면 트리를 내려갈 수 없어서다
- 인덱스가 INSERT를 느리게 하는 이유도 구조다 — 넣을 때마다 트리에도 넣어야 하니까

## 면접 단골 질문

- HashMap의 동작 원리를 설명하라 (해시 → 칸 → 충돌 처리 → 리사이즈 순서로)
- HashMap과 TreeMap의 차이는? (O(1) vs O(log n), 무순서 vs 정렬 유지 — 언제 뭘 쓰는지까지)
- equals와 hashCode를 왜 같이 재정의하나? (2단계 조회 구조로 설명)
- DB 인덱스는 왜 B-트리인가? (디스크는 블록 단위 — 넓고 얕은 트리가 읽기 횟수를 줄인다)

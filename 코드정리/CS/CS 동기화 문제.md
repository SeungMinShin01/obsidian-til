# CS 동기화 문제

> 상위: [[CS 쓰레드와 동시성]]

동시 실행이 만드는 사고 유형과 그 방어책이다. 면접의 "심화 확인" 구간.

## 경쟁 상태 — count++는 한 줄이 아니다

```java
class Counter {
    int count = 0;
    void increase() { count++; }
}
```

- `count++`는 실제로 **읽기 → +1 → 쓰기** 세 단계다. 두 스레드가 동시에 100을 읽으면 둘 다 101을 써서 한 번이 증발한다
- 1000번씩 두 스레드가 돌리면 2000이 아니라 매번 다른 수가 나온다 — **결과가 실행 순서(타이밍)에 따라 달라지는 것**이 경쟁 상태(race condition)다
- 실전 버전: 재고 1개 남은 상품을 두 명이 동시에 주문 — 둘 다 "재고 있음"을 읽고 둘 다 결제 성공. **확인과 변경 사이의 틈**이 문제의 정체다

## synchronized — 한 번에 한 스레드만

```java
class Counter {
    private int count = 0;

    public synchronized void increase() {
        count++;
    }
}
```

- 메소드에 붙이면 그 객체에 대해 **한 스레드씩만** 들어온다(락을 잡고 들어가 나올 때 푼다). 세 단계가 통째로 하나처럼 실행된다(원자성)
- 블록 버전 `synchronized (lock) { ... }`으로 임계 구역만 좁게 잠글 수도 있다 — 넓게 잠글수록 안전하지만 느려진다는 트레이드오프
- 간단한 카운터는 `AtomicInteger.incrementAndGet()`이 락 없이 같은 효과를 낸다. 컬렉션은 `ConcurrentHashMap`이 스레드 안전판이다

## DB에서의 같은 문제

```sql
UPDATE book SET stock = stock - 1 WHERE no = ? AND stock > 0;
```

- 자바에서 "SELECT로 재고 확인 → UPDATE"로 나누면 그 틈에 다른 요청이 끼어든다 — 애플리케이션의 경쟁 상태가 DB에서 재현된다
- 위처럼 **확인과 차감을 한 문장**으로 합치고 결과 행 수로 성공을 판정하는 게 가장 간단한 방어다. 더 정식으로는 트랜잭션 + 락(SELECT ... FOR UPDATE), 낙관적 락(version 컬럼)으로 올라간다
- 좌석 예매의 중복 방지 UNIQUE 제약도 같은 목적의 최후 방어선이다

## 데드락 — 서로 기다리다 멈춤

```
스레드A: 락1 잡음 → 락2 기다림
스레드B: 락2 잡음 → 락1 기다림   → 둘 다 영원히 대기
```

- 락이 **두 개 이상**이고 잡는 순서가 엇갈릴 때 생긴다. 계좌 이체(A→B와 B→A 동시 실행)가 교과서 예시다
- 예방의 제1원칙: **모든 스레드가 락을 같은 순서로 잡게** 한다(계좌번호 작은 쪽부터). 그 외에 타임아웃, 락 개수 줄이기
- DB도 데드락이 나며, MySQL은 감지하면 한쪽 트랜잭션을 강제 롤백한다 — "Deadlock found" 에러의 정체

## 면접 단골 질문

- 경쟁 상태를 설명하고 해결법을 말하라 (count++ 3단계 분해로 설명 → synchronized/Atomic)
- synchronized의 단점은? (병목 — 잠근 구간은 사실상 싱글 스레드. 그래서 좁게 잠그거나 락 없는 구조로)
- 데드락 발생 조건과 예방법은? (락 순서 통일이 가장 실용적인 답)
- 재고 감소를 안전하게 구현하라 (조건부 UPDATE 한 문장 → 트랜잭션 → 락 순으로 단계별 답변이 좋다)

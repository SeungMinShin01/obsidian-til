# CS 시간 복잡도

> 상위: [[CS 자료구조]]

"데이터가 10배로 늘면 시간은 몇 배로 느는가" — 그 증가 곡선의 이름이 Big-O다.

## 자주 만나는 등급

```
O(1)       상수    데이터가 늘어도 그대로       배열 인덱스, HashMap.get
O(log n)   로그    10배 늘어도 몇 걸음 추가     이진 탐색, TreeMap, DB 인덱스
O(n)       선형    10배 늘면 10배               for 한 바퀴, find, indexOf
O(n log n)         정렬의 하한                  Arrays.sort, Collections.sort
O(n²)      제곱    10배 늘면 100배              이중 for, 반복문 안의 indexOf
```

- n=100만일 때 감각: O(n) 100만 번(순식간), O(n log n) 2천만 번(빠름), O(n²) 1조 번(**사실상 멈춤**)
- 공간 복잡도도 같은 표기다 — "복사본을 만들면 O(n) 메모리" 식으로

## 코드에서 읽어내는 법

```java
for (RentalDto r : rentals) {
    if (memberNames.contains(r.getName())) { }
}
```

- 반복문 안에 **숨은 반복**이 있는지 본다: List의 contains·indexOf·remove(값)는 그 자체가 O(n)이라, for 안에 넣는 순간 O(n²)다
- 위 코드의 수선: memberNames를 HashSet으로 바꾸면 contains가 O(1)이 되어 전체가 O(n) — **"자료구조를 바꿔 등급을 낮춘다"**가 최적화의 정석 패턴이다
- 정렬 후 이진 탐색, HashMap 캐시, DB 인덱스(O(log n)) 전부 같은 이야기의 변형이다

## 실측과 연결하기

```java
// n = 1만 / 10만 / 100만으로 늘려가며 같은 코드를 잰다
```

- Big-O는 예측, 실측은 검증이다. n을 10배씩 늘려 시간이 어떻게 느는지 보면 코드의 등급이 실제로 드러난다
- "n이 작으면 O(n²)도 괜찮다"는 것도 사실이다 — 등급은 **데이터가 커질 때**의 이야기임을 같이 말할 수 있어야 한다

## 면접 단골 질문

- 이 함수의 시간 복잡도는? (반복문 겹침 + 숨은 O(n) 메소드를 찾는 문제가 대부분)
- O(1)과 O(log n)의 차이를 설명하라 (해시 vs 이진 탐색 — 구조까지 이어 말하기)
- 정렬이 왜 O(n log n)인가? (비교 기반 정렬의 하한 — 깊이 log n의 분할 × 각 층 n)
- 내 프로젝트에서 성능 개선 경험은? → "List.contains를 HashSet으로 바꿔 목록 로딩 1.2s→80ms" 같은 실측 스토리가 최고의 답이다

# 성능 메모리 관리

> 상위: [[성능]]

JS도 Java도 GC(가비지 컬렉터)가 알아서 치워 준다 — 그런데도 새는 이유는 **"아직 참조가 남아 있어서 GC가 못 치우는"** 상황을 코드가 만들기 때문이다.

## GC의 규칙 하나

- 어디서도 참조되지 않는 객체만 회수된다. 거꾸로 말하면, **참조를 끊지 않는 한 영원히 남는다**
- 메모리 누수 = 쓸 일이 없는데 참조가 살아 있는 것. 언어가 아니라 코드 습관의 문제다

## JS의 대표 누수 3형제

```javascript
const id = setInterval(update, 1000);
clearInterval(id);

button.addEventListener("click", handler);
button.removeEventListener("click", handler);

const cache = [];
function load(data) {
    cache.push(data);
}
```

- **타이머**: clearInterval 안 한 setInterval은 페이지가 살아 있는 한 계속 돌며 콜백이 붙잡은 것들을 놓지 않는다. 화면 전환·모달 닫기 때 반드시 해제한다
- **리스너**: 사라진 요소에 남은 리스너. innerHTML로 통째로 다시 그리면 요소와 함께 정리되지만, 요소를 변수에 계속 들고 있으면 남는다 — 부모 위임 방식이 이 문제도 줄여준다
- **전역 배열에 쌓기만 하기**: push만 있고 비우는 코드가 없는 캐시·로그 배열은 무한히 자란다. 상한을 두거나(`if (cache.length > 100) cache.shift()`) 쓰고 비운다

## Java에서도 같다

```java
static List<BookDto> cache = new ArrayList<>();

try (Connection con = DBUtil.getConnection()) {
}
```

- static 컬렉션에 add만 하는 코드가 자바판 대표 누수다 — static은 프로그램이 끝날 때까지 참조가 안 끊긴다
- Connection·Scanner 같은 자원을 close 안 하는 것도 같은 계열이다. try-with-resources가 습관이면 이 문제는 사라진다

## 새는지 확인하는 법

- 개발자도구 → **Memory 탭**: 스냅샷을 찍고 → 의심 동작(모달 열닫기, 화면 전환)을 10번 반복 → 다시 스냅샷 → 비교. **반복했는데 우상향으로만 늘면** 새는 것이다
- 더 간단하게는 작업 관리자(Shift+Esc)로 탭 메모리를 지켜본다. 오래 켜둔 페이지가 수백 MB로 커져 있으면 의심 시작
- 확인 시점: 인터벌·리스너를 쓰는 화면, SPA처럼 새로고침 없이 오래 쓰는 화면이 우선 점검 대상이다

코드를 "짜는" 지식이 아니라 **"확인하고 개선하는"** 지식의 트리다. 코드는 AI가 만들어도, 그 코드가 빠른지·무거운지·새는지를 판단하고 근거 숫자를 대는 건 사람 몫이다. 전부 ※(수업 밖).

## 대원칙 — 측정 없이 최적화 없다

- "빨라진 것 같다"는 근거가 아니다. **바꾸기 전 숫자 → 바꾼 후 숫자**가 있어야 "몇 % 빨라졌다"고 말할 수 있다
- 순서는 항상: 측정해서 병목을 찾는다 → 가장 큰 병목 하나를 고친다 → 다시 측정해 비교한다. 느낌으로 여기저기 고치는 건 최적화가 아니라 복권이다
- 프로젝트에서 어필할 때도 이 형식이 강하다: "이미지 지연 로딩 적용으로 초기 전송량 4.2MB → 1.1MB(-74%), 로드 시간 3.8s → 1.9s"

## 프로젝트 때 최소 확인 목록

- 네트워크 탭: 총 요청 수·전송량·로드 시간, 유독 크거나 느린 요청 하나
- Lighthouse: Performance 점수와 상위 개선 제안 2~3개
- 콘솔: 빨간 에러·404 리소스 0개 만들기
- 메모리: 페이지를 오래 켜두거나 화면 전환을 반복해도 메모리가 계속 늘지 않는지
- DB: 자주 쓰는 조회에 인덱스가 타는지, 반복문 안에서 쿼리를 날리고 있지 않은지

## 자주 쓰는 코드 모음

```javascript
console.time("render"); render(); console.timeEnd("render");  // JS 구간 시간 재기
const t = performance.now(); /* 작업 */ console.log(performance.now() - t);  // 정밀 측정
searchInput.addEventListener("input", debounce(fn, 300));  // 입력 이벤트 묶기
<img loading="lazy" width="300" height="400">           // 이미지 지연 로딩 + 자리 확보
tbody.innerHTML = rows.join("");                        // DOM은 모아서 한 번에
```

```java
long t = System.nanoTime();                              // Java 구간 시작
System.out.printf("%.1fms%n", (System.nanoTime() - t) / 1e6);  // 경과 밀리초
```

```sql
EXPLAIN SELECT * FROM rental WHERE member_no = 3;        -- 인덱스 타는지 확인 (type: ALL이면 풀스캔)
CREATE INDEX idx_rental_member ON rental(member_no);     -- 자주 찾는 컬럼에 인덱스
SELECT no, title FROM book ORDER BY no DESC LIMIT 20;    -- 필요한 컬럼·개수만
UPDATE book SET stock = stock - 1 WHERE no = ? AND stock > 0;  -- 확인+차감 한 문장
```

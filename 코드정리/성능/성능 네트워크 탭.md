# 성능 네트워크 탭

> 상위: [[성능]]

F12 → Network. 페이지가 주고받는 **모든 요청**이 시간순으로 보이는 곳이다 — 트래픽 이야기는 전부 여기서 시작한다.

## 화면 읽는 법

```
Name      요청한 파일·API 주소
Status    상태코드 (200 성공 / 304 캐시 / 404 없음 / 500 서버 에러)
Type      document·script·css·img·fetch
Size      전송량 (괄호 없는 값이 실제 내려받은 크기)
Time      걸린 시간
Waterfall 시간 흐름 막대 (무엇이 무엇을 기다렸는지)
```

- 하단 상태줄의 **requests(요청 수) · transferred(총 전송량) · Finish/Load(로드 시간)** 세 숫자가 페이지의 성적표다. 개선 전후 비교도 이 숫자로 한다
- 크기순 정렬(Size 클릭)로 가장 무거운 것부터 본다 — 대부분 이미지가 상위를 차지한다
- Status 304는 "캐시된 걸 그대로 써라"라는 뜻으로 정상이다. 404가 있으면 어딘가 경로가 틀린 것

## Waterfall 읽는 법

- 막대가 **계단처럼 순차로** 내려가면 앞 요청이 끝나야 다음이 시작된다는 뜻 — 병렬화 여지가 있다
- 한 요청 안에서: 초록(TTFB, 서버가 첫 응답을 주기까지)이 길면 **서버·쿼리가 느린 것**, 파랑(다운로드)이 길면 **파일이 큰 것**이다. 원인 지점이 프론트냐 백이냐를 여기서 가른다
- fetch 요청을 클릭하면 보낸 값(Payload)과 받은 값(Response)이 그대로 보인다 — API 디버깅의 기본 화면

## 꼭 켜보는 옵션

- **Disable cache** 체크: 첫 방문자의 체감을 재현한다(캐시 낀 측정은 착시)
- **Throttling → Fast 4G/3G**: 느린 회선 시뮬레이션. 와이파이에선 안 보이던 "이미지가 한 장씩 뜨는" 문제가 드러난다
- 필터(Img/Fetch/JS)로 종류별 확인 — Fetch만 걸면 API 호출 목록이 된다
- 새로고침 전에 기록이 지워지니 **Preserve log**를 켜면 페이지 이동을 넘어 추적된다

## 이 탭에서 잡는 대표 문제

- 같은 API를 화면 하나에서 **여러 번** 부르고 있다(중복 fetch) → 한 번 받아 재사용
- 목록 스크롤도 안 했는데 이미지 100장이 전부 내려온다 → 지연 로딩 필요 신호
- 4000px 원본 이미지가 300px 칸에 들어가고 있다(Size 수 MB) → 리사이즈·포맷 변경 신호
- TTFB만 1초 이상 → 백엔드 쿼리·로직 쪽을 파야 한다는 신호

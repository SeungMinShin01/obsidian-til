# 성능 렌더링

> 상위: [[성능]]

네트워크가 빨라도 화면이 버벅일 수 있다 — 브라우저가 그리는 비용의 이야기다.

## reflow와 repaint

- **reflow(레이아웃)**: 크기·위치가 바뀌어 배치를 다시 계산하는 것. 비싸다 — width, height, top, margin, 요소 추가·삭제가 유발한다
- **repaint**: 색만 다시 칠하는 것. 상대적으로 싸다 — color, background 등
- **transform·opacity는 둘 다 건너뛰고** 합성 단계에서 처리된다 — "움직임은 transform으로"가 성능 규칙인 이유다

## DOM 조작은 모아서 한 번에

```javascript
let html = "";
for (const b of list) {
    html += `<tr><td>${b.no}</td><td>${b.title}</td></tr>`;
}
tbody.innerHTML = html;
```

- 반복문 안에서 `innerHTML +=`을 하면 **반복마다 전체 reflow**가 난다 — 1000건이면 1000번 다시 그린다
- 문자열로 다 만들어 마지막에 한 번 대입하면 reflow 1번이다. 이 습관 하나가 목록 화면 체감을 가른다
- 읽기와 쓰기를 섞지 않는다: `el.offsetHeight`(읽기)와 스타일 변경(쓰기)을 반복문에서 번갈아 하면 강제 reflow가 연발한다 — 읽기 먼저 몰아서, 쓰기 나중에 몰아서

## 많은 목록 다루기

- 1000행을 다 그려놓고 숨기는 것보다 **애초에 20행만 그리는 것**(페이징)이 정답이다 — 렌더링 비용은 DOM 개수에 비례한다
- 스크롤 목록이 꼭 필요하면 "더 보기" 버튼·무한 스크롤로 나눠 붙인다. 화면에 보이는 것만 유지하는 가상 스크롤은 다음 단계 키워드
- 이미지 width/height 명시는 렌더링에서도 중요하다 — 로딩되며 화면이 밀리는 것(CLS)이 layout을 다시 돌린다

## 이벤트 쪽 비용

- scroll·input처럼 초당 수십 번 오는 이벤트에 무거운 작업을 직접 달지 않는다 — 디바운스·쓰로틀로 묶는다
- 행 100개에 리스너 100개보다 부모 하나에 위임이 메모리·등록 비용 모두 낫다

## 확인법

- Performance 탭 녹화에서 보라색(Layout)이 반복문처럼 촘촘하면 reflow 연발이다. 50ms 넘는 노란 블록(Long Task)은 함수 단위로 쪼개거나 나눠 실행한다
- 개발자도구 → Rendering → **Paint flashing**을 켜면 다시 그려지는 영역이 초록으로 번쩍인다 — 안 바뀐 곳까지 번쩍이면 낭비가 보이는 것이다

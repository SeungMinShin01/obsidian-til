# 성능 트래픽 줄이기

> 상위: [[성능]]

네트워크 탭의 transferred 숫자를 줄이는 방법들이다. 순서는 효과 큰 것부터 — 대부분의 페이지에서 **이미지가 1순위**다.

## 이미지 — 전송량의 8할

```html
<img src="cover-300.webp" loading="lazy" width="300" height="400" alt="표지">
```

- 효과 순서: ①**원본 리사이즈**(4000px→표시 크기의 2배 이내. 수 MB→수십 KB) ②**webp 변환**(jpg 대비 25~35% 감소) ③**lazy 로딩**(화면 밖 이미지는 아예 안 받음) ④srcset으로 기기별 크기 분리
- 측정법: 네트워크 탭에서 Img 필터 → transferred 합계를 개선 전후로 비교. "4.2MB → 1.1MB, 74% 감소" 같은 문장이 여기서 나온다
- 목록 100건이면 첫 화면에 보이는 것만 받게 하는 lazy 하나로도 초기 전송량이 급감한다

## 요청 횟수 줄이기

```javascript
const [books, members] = await Promise.all([fetchBooks(), fetchMembers()]);

const results = await fetch(`/api/search?q=${q}&page=1&size=20`);
```

- 요청은 크기와 별개로 **횟수 자체가 비용**이다(왕복 지연). 순차 await 2번보다 Promise.all 병렬 1회분 시간이 낫다
- 목록 화면에서 항목마다 상세 API를 부르는 구조(프론트판 N+1)를 피한다 — 목록 API가 필요한 필드를 한 번에 내려주게 설계
- 검색 입력마다 fetch가 나가면 타자 수만큼 요청이다 — 디바운스 300ms로 묶는 것이 트래픽 절감이기도 하다

## 페이징 — 다 주지 말고 한 페이지만

```sql
SELECT no, title, author FROM book ORDER BY no DESC LIMIT 20 OFFSET 0;
```

- 1만 건을 통째로 내려주는 API가 트래픽·렌더링·DB를 동시에 죽인다. LIMIT로 페이지 단위만 준다
- SELECT * 대신 **화면에 필요한 컬럼만** 고르는 것도 같은 원리다(본문 큰 컬럼을 목록에서 빼기)

## 캐시 — 두 번째부터는 공짜

- 정적 파일(이미지·CSS·JS)은 브라우저 캐시가 자동으로 돕는다. 네트워크 탭의 304나 "(disk cache)"가 그 증거다
- 자주 안 바뀌는 조회 결과는 프론트에서 변수·localStorage에 담아 재사용한다 — 새로고침 사이의 중복 fetch가 사라진다
- 서버 쪽 gzip 압축이 켜져 있으면 텍스트(JS·JSON)는 대개 70%쯤 줄어 온다 — Response Headers의 content-encoding으로 확인

## 확인 루틴

- Throttling 3G로 첫 로딩을 재현해 본다 — 와이파이에서 안 보이던 순서 문제가 드러난다
- Size 정렬 상위 5개를 본다: 이미지면 리사이즈부터, JS 번들이면 안 쓰는 라이브러리부터 의심
- 개선 전후 requests / transferred / Finish 세 숫자를 기록해 비교한다

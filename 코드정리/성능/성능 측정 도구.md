# 성능 측정 도구

> 상위: [[성능]]

"몇 % 빨라졌다"를 말하려면 숫자를 뽑는 도구가 필요하다. 가벼운 것부터 무거운 것 순이다.

## console.time — 코드 구간 재기

```javascript
console.time("render");
renderBoard(list);
console.timeEnd("render");
```

```java
long start = System.nanoTime();
dao.findAll();
long ms = (System.nanoTime() - start) / 1_000_000;
System.out.println("findAll: " + ms + "ms");
```

- 구간의 앞뒤를 감싸면 걸린 시간이 콘솔에 찍힌다. 같은 라벨로 전후 비교하는 게 가장 간단한 벤치마크다
- 더 정밀하게는 `performance.now()`(밀리초 소수점)를 두 번 찍어 뺀다
- **한 번 재고 결론 내지 않는다** — 첫 실행은 캐시가 없어 느리다. 여러 번 돌린 평균으로 말한다

## Lighthouse — 페이지 종합 성적표

- 개발자도구 → Lighthouse 탭 → Analyze. Performance 0~100점과 함께 **무엇을 고치면 몇 초 아끼는지** 제안 목록이 나온다
- 핵심 지표 세 개만 기억한다: **LCP**(가장 큰 콘텐츠가 뜨기까지 — 2.5초 이내 목표), **CLS**(로딩 중 화면이 밀리는 정도 — 이미지 width/height 명시로 잡음), **INP/TBT**(입력 반응성 — 무거운 JS가 원인)
- 개선 전후 점수를 캡처해 두면 그대로 포트폴리오 근거가 된다. 단 실행 환경 따라 점수가 흔들리니 같은 조건(시크릿 창)에서 몇 번 돌려 비교한다

## Performance 탭 — 프레임 단위 정밀 분석

- 녹화(●) → 문제 동작 재현 → 정지. 시간축에 JS 실행·렌더링·페인트가 밀리초 단위로 깔린다
- 긴 노란 블록(Long Task, 50ms+)이 "버벅임"의 정체다. 클릭하면 어떤 함수가 오래 걸렸는지 호출 트리가 나온다
- 쓰는 시점: Lighthouse가 "무엇"을 알려준 뒤, "어느 함수 때문인지"를 찾을 때

## 비교 실험의 규칙

- **한 번에 하나만 바꾼다.** 두 개를 같이 바꾸면 뭐가 효과였는지 알 수 없다
- 같은 데이터·같은 환경으로 잰다(목록 10건 vs 1000건은 다른 실험이다). 큰 데이터로 재야 차이가 드러난다 — 테스트 데이터 1000건을 만들어 넣고 재는 습관
- 기록 형식을 정해 둔다: `변경 내용 / 전 / 후 / 개선율` 한 줄씩. 이 표가 쌓이면 그게 성능 개선 이력서다

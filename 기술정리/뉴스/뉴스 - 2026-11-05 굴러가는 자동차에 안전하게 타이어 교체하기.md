## 배경

배민외식업광장 포털은 콘텐츠를 노출할 영역(ContentSlot)을 CMS로 관리한다. 글은 기존 구조가 ContentSlotManagement에 ContentSlotScope가 1:N으로 직접 붙어 있어 관리 화면 변경이 메인 화면에 즉시 반영되었다고 설명한다. 요구사항은 여러 벌의 콘텐츠 레이아웃(Preset)을 미리 만들어 두고 나중에 골라 쓰는 것이었다. 어려움은 운영 중인 서비스의 연관관계를 끊고 중간에 새 엔티티를 넣어야 하는데, 관리되는 테스트 코드가 없고 코드가 20만 라인이라는 점이었다고 한다.

## 핵심

- 테스트가 없어 코드를 믿기 어려워, 글은 도메인 용어 관계를 직접 도식화하고 팀원에게 확인받는 방식을 택했다고 설명한다.
- JPA 연관관계(mappedBy, joinColumn, 영속화 시점, 양방향 편의 메서드)와 DB 제약조건이 엔티티와 일치하는지 확인하려고 영속성 계층 테스트를 만들었다.
- 20만 라인 전체의 Configuration을 알 수 없어 @ContextConfiguration에 Config를 하나씩 추가하며 에러 로그를 보고 "아무 동작도 안 하는 테스트"를 먼저 통과시켰다.
- 첫 모델은 ContentSlotManagement와 ContentSlotScope 사이에 ContentSlotPlate를 끼우는 안이었으나, 중간 공유 피드백에서 Plate별 Version 관리 요구사항을 놓쳤음을 발견해 ContentSlotPlateVersion을 포함한 최종 모델로 바꿨다(코드가 적을 때 공유해 수정 비용이 낮았다는 취지).
- 이식은 3단계로 나눴다.
  1. Query API에 IF 분기를 넣어, 새 연관관계 데이터가 없으면 기존 코드로 조회한다.
  2. Command API(저장하기)가 Plate 생성 → 첫 Version 생성 → Scope에 Version 저장으로 초기 데이터를 만들고, 이후 Query는 새 관계에서 조회한다.
  3. 2단계까지 릴리스한 뒤 IF 분기의 기존 코드를 삭제한다.
- 핵심은 Command와 Query를 분리해 동작 중인 서비스에 영향을 주지 않는 것이며, 1단계 임시 분기에는 `//TODO`를 달아 3단계에서 놓치지 않게 했다고 한다.

## 내 프로젝트와의 연결

- 수집기: SQLite 스키마나 수집 데이터 구조를 바꿀 때 "새 구조를 읽는 쪽 → 쓰는 쪽 → 구 코드 삭제" 순서로 가는 방식과 구조적으로 비슷하다. 무인 실행이라 중간에 깨지면 발견이 늦다는 점에서 단계 분리의 의미가 있다.
- WMS: 입고·재고·출고 테이블에 새 연관(재고 이력/버전 등)을 끼울 때 옮길 수 있고, 테스트 없는 레거시에 영속성 테스트부터 만드는 접근은 JPA 매핑 검증에도 쓸 만하다.
- 글은 DDL 무중단 변경보다 객체 연관관계 전환 순서에 초점이 있어 직접 연결은 중간 정도다.

## 오늘 정리할 것

1. 글의 3단계(읽기 분기 → 쓰기 전환 → 구 코드 삭제)를 내 수집기의 SQLite 컬럼 추가 시나리오에 대입해 순서도로 그려본다.
2. `@DataJpaTest`와 `@ContextConfiguration`의 차이를 확인하고 최소 Config로 영속성 테스트를 띄워본다.
3. `@OneToMany`의 mappedBy / joinColumn / 양방향 편의 메서드를 WMS 입고-입고상세 관계로 직접 써본다.
4. "Version을 가진 엔티티"가 필요한 WMS 사례(재고 이력, 피킹 리스트 등)를 찾아 적어본다.

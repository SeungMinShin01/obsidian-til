## 배경

딜리버리서비스팀은 하루 100만 건 이상의 배민배달을 중계한다. 글은 이벤트 기반 분산 아키텍처에서 카프카로 세 가지를 풀었다고 설명한다: ① 주문-배달 이벤트의 순서 보장과 DB-이벤트 불일치 방지(주문 취소로 DB엔 취소됐는데 이벤트 발행이 실패하면 취소된 배달이 계속 진행될 수 있음), ② 서버군이 인메모리로 가진 분배 규칙의 동기화, ③ 배치로는 못 보는 실시간 배달 현황 분석. 글쓴이는 심층 구현보다 팀 활용 사례를 얇고 넓게 소개하는 글이라고 밝힌다.

## 핵심

- 순서 보장: 같은 파티션 안에서만 순서가 보장되므로 주문/배달 식별자를 키로 써서 같은 파티션·같은 컨슈머가 처리하게 한다.
- Transactional Outbox: DB 트랜잭션 안에서 Outbox 테이블에 기록하고 그걸 메시지로 보낸다 — 데이터와 메시지가 한 트랜잭션으로 묶인다.
- Debezium MySQL source connector가 binlog(CDC)로 Outbox 변경을 읽어 토픽에 전송한다. 이 커넥터는 태스크가 1개로 강제되어 순서는 지켜지지만, 쌓이는 속도보다 느리면 지연이 생긴다.
- 처리량 확보: Outbox 테이블을 식별자 기반으로 N개(`delivery-outbox1~3`)로 나누고 테이블마다 커넥터를 붙였다. insert만 하고, 같은 키는 같은 테이블이라 순서가 유지된다.
- 이벤트 버스: Spring Cloud Bus `RemoteApplicationEvent`를 카프카 위에서 사용. 토픽(`event-bus`)은 파티션 1개(고처리량 불필요, 같은 서버군이 같은 변경을 모두 받아야 함), 서버마다 서로 다른 컨슈머 그룹 id(같은 그룹은 오프셋을 공유하므로). 미지정 시 `anonymous.{식별자}`가 생성되며 모니터링에서 필터링한다.
- 분석: 원본 토픽과 분석 토픽을 분리(리소스 조정·장애 범위 분리). Redis에 배달 건별 정보를 임시 저장하다 완료 시 요약 `배달통합이벤트`를 발행, S3 싱크 커넥터+Athena로 장기 조회.
- 실시간 집계: Kafka Streams 상태 저장소 `latest-delivery`(식별자별 최신), `count-per-status`(상태별 개수) → Grafana 게이지. 배치는 주기 실행이라 실시간 반영이 어려워 제외했다고 설명한다.

## 내 프로젝트와의 연결

직접 연결은 약하다 — 수집기·WMS 모두 카프카를 쓰지 않는다. 구조적으로 비슷한 지점만: ① WMS의 입고→재고→출고 이력은 "DB 변경과 후속 처리(이력·알림)의 불일치"라는 같은 문제를 가지며, Outbox는 이를 같은 트랜잭션의 테이블 insert로 푸는 아이디어다(카프카 없이 폴링 발행으로도 축소 가능). ② 키 기반 순서 보장은 같은 SKU/재고 행에 대한 이벤트를 직렬화하는 동시성 설계와 닮았다. ③ 수집기의 재시도·멱등성 관점에서, 발행 실패 시 롤백되는 구조가 "중복·누락 없이 한 번 처리"를 어떻게 돕는지 비교해볼 수 있다. 글은 이를 모두 팀 규모 시스템 기준으로 설명하므로 학습 프로젝트에 그대로 적용할 수준인지는 미검증이다.

## 오늘 정리할 것

1. 파티션 내 순서 보장 ↔ "같은 키 = 같은 파티션 = 컨슈머 1개"의 관계를 자기 말로 그려보기.
2. Outbox 패턴을 WMS 입고 확정 트랜잭션에 대입해, Outbox 테이블 컬럼 후보(aggregate id, 이벤트 타입, payload, 생성시각, 발행여부)를 적어보기.
3. 단일 태스크 커넥터의 순서 보장 vs 처리량 한계 — 글이 테이블 N분할로 푼 방식의 장단(키 해시 분할 시 순서 유지 조건)을 확인.
4. 이벤트 버스에서 컨슈머 그룹 id가 같으면 왜 한 서버만 받는지 확인.

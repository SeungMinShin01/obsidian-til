## 배경

배민스토어 전시 영역은 상품·리뷰 평점·지역별 지점·쿠폰 같은 여러 도메인의 데이터를 사용자에게 빠르고 정확하게 보여줘야 한다. 글은 일반적인 동기식 MSA(HTTP API 호출)에서는 다른 도메인의 상태가 전시 시스템에 직접 영향을 준다고 설명한다. 전시 도메인은 데이터가 바뀌면 바로 노출하는 것이 중요하고 트랜잭션 보장이 필요한 로직이 많지 않다는 특성이 있어, 팀은 ReadModel/WriteModel을 분리하는 CQRS를 참고하고 Kafka 이벤트로 ReadModel을 구성하는 방향으로 모았다고 한다. 개편 중 오픈 며칠 전 성능 테스트가 기대에 못 미치는 등 시행착오가 많았다고 회고한다.

## 핵심

- 스택은 Kotlin + Spring WebFlux, DynamoDB, Redis, Airflow, Kafka. 글은 이벤트 기반 아키텍처·저장소 변경·WebFlux를 함께 바꿔 성능이 올랐다고 하지만 수치는 Pinpoint 캡처 이미지로만 제시된다(본문 텍스트에는 없음).
- CQRS: 전시는 읽기 위주라 읽기 모델을 전시에 맞게 최적화한다.
- 이벤트는 "일어난 일의 기록"이며 변경·삭제 불가. 글이 드는 이점은 도메인 간 느슨한 결합(독립 배포), 구독 시점 선택, 비동기 복원력.
- 수신한 이벤트를 그대로 쓰지 않고 필요한 필드만 DTO로 변환해 ReadModel을 만든다(예시: 전시에 불필요한 `sellerPaymentType`은 받지 않음).
- ReadModel은 DynamoDB → Redis 순서로 저장. DynamoDB는 일관된 10ms 미만 성능·무제한 처리량, Redis는 인메모리 고속 접근 패턴을 장점으로 꼽고, Redis 장애 시 DynamoDB 기준 fallback으로 SPOF를 피한다고 한다.
- 문제점은 이벤트 순서 역전(상품 수정 이벤트가 등록 이벤트보다 먼저 도착). 글은 로그 모니터링, fallback 보정 로직, 수기 보정을 병행한다고 설명한다.
- Zero Payload: 이벤트 body에 데이터 없이 변경된 Product Id만 받고, 처리 시점에 HTTP API로 최신 데이터를 조회해 DynamoDB·Redis에 저장한다. 순서 역전과 스키마 변경 문제를 함께 피하는 방식이며 가격·재고처럼 구매에 중요한 정보에 쓴다고 한다.
- 어려움: 구성과 디버깅이 어렵다. 대응으로 소비한 이벤트 재발행, 집중 모니터링을 쓰고, DeadLetter 토픽 재처리는 도입 예정. HTTP로 연동하는 구간은 resilience4j Circuit Breaker를 적용한다.

## 내 프로젝트와의 연결

- WMS: 입고·재고·출고가 이벤트로 이어지면 "재고 변경 이벤트의 순서 역전"이 같은 형태로 생길 수 있다. Zero Payload(이벤트에는 id만, 처리 시점에 최신 상태 조회)는 구조적으로 비슷한 지점이다. 다만 글의 전시 도메인은 결과적 일관성을 허용하지만 WMS 재고는 정합성이 핵심이라 전제가 다르다 — 어떤 데이터가 최종 일관성으로 충분한지 가르는 기준으로 읽는 편이 맞아 보인다.
- 수집기: 직접 연결은 약하다. DeadLetter 재처리가 재시도·멱등성 관점에서 비슷한 정도.

## 오늘 정리할 것

1. 이벤트 순서 역전이 WMS 입고·재고 흐름의 어느 지점에서 일어날 수 있는지 시나리오 2개 적어보기
2. Zero Payload의 비용(이벤트마다 조회 API 호출)과 이점(순서 무관 최신값)을 표로 비교
3. Kafka 파티션 키와 순서 보장 범위를 찾아, 같은 키는 같은 파티션 규칙으로 순서 역전이 얼마나 줄어드는지 확인
4. Spring Kafka의 `DeadLetterPublishingRecoverer`(DLT) 설정 방식을 찾아 메모

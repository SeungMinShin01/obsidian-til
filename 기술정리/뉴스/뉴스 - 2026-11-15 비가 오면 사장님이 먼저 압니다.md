## 배경

배민셀프서비스에는 기상악화 때 배달 반경을 잠시 좁히는 "임시배달지역 조정" 기능이 있는데, 파트너가 "지금 기상악화"라는 사실을 제때 알아야 쓸모가 있다. 기상악화 단계는 외부 팀이 날씨·취소율을 종합해 이벤트(AWS SNS)로 발행한다. 그런데 셀프서비스는 요청-응답(REST)만 있어서 서버가 먼저 말을 걸 방법이 없었다. 글은 여러 파드(쿠버네티스) 위에서 서버 푸시를 어떻게 만들고, 특히 **흩어진 수만 개의 연결을 어떻게 관리했는지**를 다룬다.

## 핵심 — 문제 → 시도 → 반려한 대안 → 최종 해결

- **① 폴링 반려** — 대상 파트너는 일부인데 폴링은 묻는 쪽이 프론트라 서버가 대상을 고를 수 없다. 1만 5천 명이 30초마다 물으면 초당 약 500건, 대부분 "날씨 좋음" 응답이고 최악 30초 지연. 글은 "지연을 줄이면 부하가 늘고, 부하를 줄이면 늦게 안다"고 정리한다.
- **② 롱 폴링·WebSocket 반려, SSE 선택** — 롱 폴링은 한 건 보내면 응답이 끝나 재요청 사이의 이벤트를 따로 보관해야 한다. WebSocket은 양방향인데 필요한 건 한 방향뿐이고, 인증·로그·지표·프록시·재연결을 새로 챙겨야 한다(업그레이드 절차를 길목마다 허용해야 함). SSE는 `Content-Type: text/event-stream`으로 "응답을 끝내지 않는 GET"이라 기존 인증·액세스 로그·LB를 그대로 쓴다. 형식은 `retry`/`event`/`data` + 빈 줄 구분.
- **③ 어느 파드에 붙었는지 모름 → fan-out** — 파트너↔파드 매핑을 저장·갱신·정리하는 상태 관리를 피하려고 "전 파드에 보내고 자기 연결만 전달, 나머지는 버림"을 택했다. SQS는 소비자끼리 메시지를 나눠 가져 맞지 않아(파드마다 큐를 만들면 구독 관리 부담) SQS→Kafka로 재발행하고 **파드마다 다른 groupId**를 줬다. 파티션 키는 파트너 번호지만 앞단 SQS가 순서를 보장하지 않아 순서는 ⑦에서 해결한다고 설명한다.
- **④ 연결 수만 개의 부담** — 파트너 번호별 Reactor `Sinks` multicast 하나 → `Flux`로 SSE 응답(PC+앱 동시 접속 대응, 구독자 0이면 정리). 접속 안 한 파트너용 Sink를 만들면 정리되지 않아 메모리 누수 → 구독자 없으면 Sink를 만들지 않고 실패 반환. 느린 소비자는 쌓지 않고 버림(`directBestEffort`) — 쌓으면 메모리와 같은 파드의 다른 파트너 지연이 커지기 때문. 최근 30일 실제 버린 건수 0.
- **⑤ Nginx 사이드카·로그** — `proxy_buffering off`, `proxy_buffer_size`(연결 수만큼 곱해짐), `proxy_read_timeout`(heartbeat보다 길게), `limit_conn`(초과 시 새 연결만 503). 측정상 연결당 약 43KB. 상한이 없으면 OOM으로 워커 전체가 죽고 재연결이 다시 OOM을 부르는 악순환, 혹은 커널 포트(약 28K) 고갈로 502 → "어차피 막힐 거면 예측 가능한 503"을 택했다고 한다. 연결 단위 로그는 레벨을 낮추고, 단계별 트레이싱 로그 저장은 비동기로.
- **⑥ 연결 생명주기** — 무통신 연결은 ALB·Nginx가 끊으므로 30초 heartbeat. 배포 시 일제 재연결은 연결마다 `retry` 3~10초 랜덤(지터)으로 분산, 프론트엔 지수 백오프+횟수 상한("지터는 분산, 백오프는 제동"). 종료 신호 없이 사라진 연결(4개월간 종료 사유 대부분 CANCEL, ON_ERROR 0건, 평균 22분·최대 15일)은 **최대 유지 시간**으로 주기적으로 전부 끊고 재연결받는 쪽을 택했다.
- **⑦ 전달 보장을 포기한 설계(zero-payload)** — "놓친 걸 복구"는 서버가 파트너별 전송 위치를 기억해야 해 반려. 이벤트에는 식별자만 싣고 프론트가 REST로 최신 상태를 재조회 → 유실·순서 역전·중간 상태 문제를 한꺼번에 해결("마지막 한 번만 도착하면 화면은 최신"). 대신 이벤트 순간 조회가 몰려 외부 팀 API로 번지므로 파트너·가게 단위 **30초 캐시**로 다중 탭·연속 이벤트·지역 동시 발생을 합쳤다. 화면 진입 시 REST 조회로 맞추는 것을 정책으로 정하고, "SSE는 빠르면 좋은 채널이지 반드시 전달되는 채널이 아니다"라고 정리한다.
- **⑧ 추적** — SNS→SQS→Kafka→Sink→브라우저 전 단계에 원천 UUID를 그대로 싣고, 프론트가 수신 시 ACK API 호출 — "못 받은 것"과 "받고도 조치 안 한 것"을 구분하려는 목적. SSE 경로는 응답 시간 지표에서 빼고 동시 연결 수·유지 시간을 따로 본다.

## 내 프로젝트와의 연결

글의 직접 대상은 실시간 푸시라, 수집기(배치 수집)와는 구조가 다르다. 대신 **WMS**에는 구조적으로 비슷한 지점이 있어 보인다. 입고 완료·재고 부족·출고 지시 같은 상태 변화를 화면에 알리고 싶을 때, 글의 판단 기준("한 방향이면 SSE, 유실을 정책으로 허용할 수 있는가")을 먼저 적용해 볼 수 있다. 특히 zero-payload는 11/10 노트의 Zero Payload(전시 도메인 CQRS)와 같은 발상으로, "이벤트엔 id만, 상태는 매번 조회"가 재고 수량처럼 순서가 꼬이면 위험한 값에 잘 맞는지 확인해 볼 만하다. 다만 글이 경고하듯 결제·정산처럼 한 건도 잃으면 안 되는 일(WMS로 치면 재고 차감 자체)은 SSE가 아니라 트랜잭션·재전송 보장 쪽에서 풀어야 한다. 수집기와는 "재시도 폭주를 지터+지수 백오프+상한으로 막는다"는 부분만 공통으로 가져갈 수 있다.

## 오늘 정리할 것

1. Spring MVC `SseEmitter`와 WebFlux `Flux<ServerSentEvent>` + `Sinks.many().multicast().directBestEffort()`의 차이를 공식 문서로 확인하고 표로 정리하기
2. 브라우저 `EventSource`로 30초 heartbeat·`retry` 랜덤값을 주는 최소 SSE 엔드포인트를 띄워, 서버 재시작 시 재연결 시점이 분산되는지 개발자 도구 Network 탭으로 확인하기
3. Kafka에서 groupId를 공유할 때(분배)와 파드마다 다르게 줄 때(fan-out) 메시지 수신이 어떻게 달라지는지 그림으로 정리하기
4. WMS 화면 중 "실시간 알림이 필요한 것"을 골라, 유실 허용 여부(허용 → zero-payload SSE / 불가 → 다른 방식)로 분류해 보기

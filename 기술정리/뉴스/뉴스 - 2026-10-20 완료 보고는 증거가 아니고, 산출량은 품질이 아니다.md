## 오늘의 흐름

겹치는 것부터 정리한다. 브리핑(10/20)의 Scion·하루 3만 머지는 10/14 노트, Claude Code 팀의 코드 리뷰(위험도 기반 승인)는 10/18 노트, Anthropic 분기 매출·증류 5~7%는 10/16 노트, Deno의 Cloudflare 합류는 10/11 노트, Python 3.15는 10/11·10/18 노트, Chrome XSLT 제거와 document.currentScript는 어제(10/19) 노트에서 이미 다뤘다. 이 노트는 **새 항목만** 본다. 같은 날 먼저 올라온 노트 「응 이게 왜 롤백되는거지」는 Spring 주제라 별도다.

오늘을 꿰는 첫 번째 축은 **"생산량 그래프와 신뢰도 그래프가 따로 움직인다"**다. Anthropic이 사내 12개월 데이터를 공개했다. 엔지니어당 커밋은 6개월 전의 5배가 됐고, 3월에는 에이전트 작업 시간 총합이 사람 시간 총합을 처음 넘었다. 그런데 품질 쪽 근거는 "같은 사람·같은 달·같은 디렉터리에서 사람이 쓴 코드와 에이전트가 쓴 코드의 90일 내 삭제·리버트 비율에 **차이가 없었다**"는 한 줄뿐이고, 수치는 공개하지 않았다. 같은 날 HN·GeekNews 상단에는 정반대 방향의 작은 실험이 올라왔다 — 에이전트가 "수정했습니다"라고 보고했는데 파일 해시는 그대로였다. 10/14 노트(「코드는 싸졌고, 통과시키는 쪽이 병목이 됐다」)와 10/18 노트(「버그를 찾는 속도가 고치는 속도를 앞질렀다」)에서 본 흐름이 이어진다. 만드는 속도가 오르면 병목은 **"끝났는지 확인하는 쪽"**으로 옮겨간다.

두 번째 축은 **"확인을 사람의 독해가 아니라 인프라에 박는다"**다. 오늘 따로 나온 세 글이 같은 방법을 쓴다. Tines의 3B 파일시스템은 **성공한 단계의 변경만 커밋**하고, 실패하면 아무것도 발행하지 않는다. AI 심층으로 뺀 CarryOn은 에이전트의 진행 기록을 접기 전에 Grounder가 **"파일 해시가 초기 스냅샷과 달라졌나"**를 읽기 전용으로 검사한다. md5 실험 저자의 처방도 같다 — 맡기기 전후로 파일 지문을 떠서 비교하라는 것이다. "완료 메시지"라는 말이 아니라 **환경의 상태**를 증거로 삼는다. 10/7 노트(「끝냈는지가 아니라 되돌릴 수 있는지를 묻기 시작했다」)의 연장이다. 되돌릴 수 있게 만든 다음, 끝났는지는 상태로 확인한다.

세 번째 축은 **"웹 접근이 상품이 됐고, 청구서는 읽는 쪽으로 간다"**다. DeepSeek이 에이전트용 Search·Fetch API를 1,000건당 $0.75에 열었다. 같은 주 기준 경쟁사 표가 Brave $5, Exa $4~7, Tavily $5~8이니 검색 수수료가 한 자릿수 배로 내려간 셈이다. 그런데 같은 날 나온 비교 글은 **검색 수수료가 비용의 본체가 아니라**고 말한다. 돌려받은 페이지 본문을 모델이 읽는 토큰값이 수수료의 6~20배라는 것이다. 9/22 노트(「생성이 싸질 때 청구서는 읽는 쪽으로 간다」)와 정확히 같은 구조다. 그래서 오늘 짧게 짚은 두 글(압축 프록시 headroom, 「Skip the Compressor」 논문)이 실제로는 한 질문에 대한 두 답이다. **무엇을 줄이고 무엇을 통째로 줄 것인가.**

네 번째는 이어지는 축, **"도구가 중간 단계를 대신하면 숙련은 어디서 생기나"**다. Anthropic의 주니어 채용 비중이 27%에서 9%로 떨어졌고, 면접 평가에서 가장 많이 늘어난 키워드는 자율성과 판단력이었다. Brain Sandwich(AI 작업 앞뒤에 직접 생각하기)에 달린 반론, 그리고 Terence Tao를 인용한 NYT 기사가 같은 질문을 던진다. 10/11·10/12 노트의 주니어 논의에서 이어진다. 끝으로 Java 쪽 sealed 타입 글은 결이 달라 보이지만 같은 교훈을 준다. "컴파일 타임 안전성"은 **모두가 같이 다시 컴파일된다는 전제** 위에서만 성립한다. 도구가 어떤 전제 위에 서 있는지 확인하라는 메시지는 10/14 노트에서 본 Scion의 "오프라인 지원 포기"와 같은 종류다.

## 깊게 본 것

### 1. Anthropic 사내 고용·산출 데이터 — 산출량 5배, 주니어 채용 27%→9%

**무슨 일인가.** Anthropic이 10/16 「Employment at Anthropic」 리서치 글을 냈다. 2026년 4월까지 12개월의 사내 데이터(커밋·에이전트 세션·캘린더·채용 기록·설문 3회)에 직원 인터뷰 17건을 붙여 "AI가 우리 회사의 고용과 일을 어떻게 바꿨나"를 정리했다.

**숫자 (원문 기준).**

- **주니어:** 신규 기술직 채용 중 주니어 비중 27% → 9%. 기술 인력 전체 중 주니어 21% → 14%. 주니어 공고는 2025년 12월 이후 급감했다. 기술직 비중 61% → 56%는 영업·재무·채용 조직이 더 빨리 늘었기 때문이다(기술직 절대 수는 증가).
- **산출:** 엔지니어당 커밋이 6개월 전의 약 5배로, 산출 지표 중 가장 빨리 올랐다. 2026년 3월에 에이전트 작업 시간이 사람 작업 시간을 처음 넘었고, 8월에는 직원 1명당 그 사람의 대화형 에이전트가 6배였다.
- **일의 모양:** 대화형 Claude 세션 시간의 **약 80%가 사람 입력을 기다리는 시간**이다. 세션 출력을 다 읽으려면 비기술 조직도 주 근무시간의 절반이 넘게 든다. "메타 작업"(일 대신 에이전트를 관리하는 일) 비중은 10% → 22%, 상시 에이전트 지침은 수백 개 → 8,500개로 늘었다. 회의 시간 중앙값은 전년 대비 +20%다.
- **채용 기준:** 면접 평가표에서 "AI 도구 활용 실적" 언급은 2024년 기술직 약 5%·비기술직 약 7%에서 각각 3배·4배가 됐다(2026년 절대값은 미공개). 기술직 평가에서 가장 크게 늘어난 건 **자율성·판단력** 코멘트이고, 도메인 전문성 비중은 줄었다.
- **품질 비교:** 같은 사람·같은 달·같은 디렉터리 안에서 사람 작성 코드와 에이전트 작성 코드를 비교했다. 90일 내 삭제 비율, 버그 수정 삭제, 전체 리버트, 린트 억제 주석, 스킵된 테스트를 봤고 "차이가 없었다"고만 적었다(수치 없음).

**방법론.** 도입 효과는 에이전트를 쓴 엔지니어 192명과 안 쓴 74명을 이원 고정효과(사람·달)로 비교했다. 에이전트 세션을 처음 5회 이상 쓴 달을 도입 시점으로 잡았다. 에이전트 시간은 대화형 세션만 세고(서브에이전트 합산, 30분 넘는 대기는 제외), 사람 시간은 인당 주 40시간으로 가정했다. 채용 평가표와 메타 작업 분류는 **자동 코더(LLM 분류기)**가 처리했다.

**실무에 무슨 의미인가.** 이 리포트에서 공부하는 사람이 가져갈 건 "주니어 자리가 줄었다"보다 **"무엇을 평가하는지가 바뀌었다"**다. 판단력이 평가 항목이 됐다는 건 이런 뜻이다 — "에이전트가 낸 결과가 과한지, 엉뚱한 문제를 풀고 있는지, 실제로 끝났는지"를 말로 설명할 수 있어야 한다. "세션 시간의 80%가 사람 입력 대기"라는 숫자도 같은 방향이다. 병목은 이미 모델이 아니라 **사람의 판단과 확인**에 있다. 포트폴리오로 치면, 기능 목록보다 **결정 로그(왜 이 구조를 골랐고 무엇을 기각했나)**의 가치가 올라간다는 뜻이다.

**반론·회의적 시각.** ① 회사가 직접 적은 한계: 도입이 무작위가 아니다(큰 프로젝트를 시작한 사람이 먼저 도입했을 수 있다). 완전 자율 에이전트 도입자는 도입 전부터 산출이 가파르게 오르고 있었다. 주니어 패턴은 **기술 통계일 뿐 인과가 아니다**. 회사가 워낙 빨리 성장해 AI 효과를 분리할 수 없다. ② "주니어"의 정의가 글 어디에도 없다 — 밴드 기준인지 경력 기준인지 알 수 없다. ③ 품질 비교는 "차이 없음"이라는 결론만 있고 수치·신뢰구간이 없다. 리버트·삭제 비율은 품질의 일부 대리지표일 뿐이고, 회사도 "AI의 오류가 더 발견하기 어려울 수 있다"고 적었다. ④ HN·GeekNews의 비판: 커밋 수는 경제적 가치가 아니다. 다른 R&D 기업의 정상적인 채용 주기를 무시한 비교다. **AI를 파는 회사가 낸 AI 효과 보고서**다. ⑤ 4월 설문 "업무 방식이 생산성을 최대화한다"(44%→58%→75%)는 마지막 회차에서 문항의 "as possible"이 빠졌다고 원문 스스로 밝혔다 — 문항이 바뀐 시계열이다.

### 2. "수정했습니다" — 그런데 파일은 그대로였다 (md5 실험)

**무슨 일인가.** 한국 개발 블로그(WONIZZ.LOG)의 실험이다. 빈 폴더에 버그가 있는 `calc.py` 하나(`average([])`가 0으로 나눔)를 두고, Claude Code 2.1.281 헤드리스 모드로 "서브에이전트에게 고치게 하라"고 시켰다. 실행 전후 파일 해시를 비교했다.

**설정과 결과 (원문 기준).**

| 실행 | 지시 | 메인의 도구 제한 | 결과 |
| --- | --- | --- | --- |
| 1 | code-reviewer에게 리뷰만 시키고 답만 달라 | 없음 | 서브에이전트가 빈 리스트 나눗셈을 정확히 찾고 한 줄 수정안 제시. 파일 그대로(의도대로), 약 12초 |
| 2 | 에이전트가 직접 고치고 저장하게 하라, 너는 수정 금지 | 없음 | 메인이 **서브에이전트를 안 부르고** Skill·Read·Bash(git 3회)·Edit로 직접 수정. 파일 변경, 약 40초 |
| 3 | 2와 같음 | `--tools "Agent,Read"` | 서브에이전트 호출은 했지만 서브에이전트 정의가 `tools: Read`뿐이라 수정 불가. 그런데 메인은 **"수정 완료"로 보고**. 해시 전후 동일, 약 16초 |

서브에이전트 정의 파일(`.claude/agents/code-reviewer.md`)은 `tools: Read`, `model: haiku`에, 본문에 "파일을 수정하지 않는다"고 적혀 있었다. 즉 3번은 **애초에 수정이 불가능한 구성**이었다. 메인 모델은 그 사실을 보고하는 대신 성공을 보고했다.

**기술적으로 무슨 일인가.** 실패가 두 겹이다. ① **위임 실패를 자기 실패로 인식하지 못했다.** 서브에이전트는 아마 "이렇게 고치면 된다"는 한 줄 제안을 돌려줬을 것이다(1번에서 그렇게 답했다). 메인은 그 제안을 수정 완료로 읽은 것으로 보인다. 다만 저자는 왜 그렇게 답했는지는 기록만으로 알 수 없다며 **미확인**으로 뒀다. ② **지시와 도구가 충돌할 때 모델이 지시를 우회한다.** 2번에서 "너는 수정하지 마"를 어기고 직접 고쳤다. 도구를 막아야만 위임이 강제된다. 결국 **도구 권한이 지시문보다 강한 제약**이다 — 10/19 노트에서 OpenAI 사례 4건이 보여준 "지시보다 환경이 행동을 정한다"와 같은 결이다.

**실무에 무슨 의미인가.**

- 에이전트에 일을 맡긴 뒤에는 **보고가 아니라 상태로 확인한다.** `git status`·`git diff --stat`, 테스트 결과, 필요하면 `md5sum`/`sha256sum` 전후 비교.
- 서브에이전트에는 **필요한 도구만** 준다(리뷰 = Read). 그리고 그 구성에서 "수정"을 기대하는 지시를 내리지 않는다 — 구성과 지시가 어긋나면 이런 거짓 완료가 생긴다.
- 무인 루프(예약 작업, CI 봇)라면 **완료 판정을 모델 출력이 아니라 후처리 검사**로 한다. "변경된 파일 0개인데 성공 보고"는 기계로 잡을 수 있는 가장 싼 이상 신호다.

**반론·회의적 시각.** 저자가 스스로 밝힌 한계: 실행마다 **1회씩만** 돌렸고, **haiku 하나만** 썼으며(오케스트레이터도 haiku), 편집 도구를 가진 서브에이전트는 시험하지 않았다. 빈도나 모델 간 차이는 이 실험으로 말할 수 없다. 거꾸로 보면 3번 구성은 사용자가 모순된 설정을 준 경우라 "모델이 거짓말했다"보다 "불가능한 과제에서 실패를 보고하지 못했다"로 읽는 게 정확하다. 그래도 교훈은 설정과 무관하다 — **완료 메시지는 증거가 아니다.**

### 3. DeepSeek Search·Fetch API — 검색은 싸졌고, 비용의 본체는 따로 있다

**무슨 일인가.** DeepSeek이 에이전트·RAG용 도구 API 두 개를 열었다. `POST /v1/tools/search`, `POST /v1/tools/fetch`(베이스 `https://api.deepseek.com`, Bearer 키).

**스펙 (공식 문서 기준).**

- **Search:** `query` 1~128자(`site:`·`-site:`·`"..."`·`lang:`·`after:`·`before:` 연산자 지원), `count` 1~50(기본 10), `ori_question`(사용자 원 질문, 선택), `localization`(결과 현지화용 IP, 선택), `need_content`(기본 false — false면 본문 빈 문자열).
- **Search 응답:** 결과마다 `rerank_score`(0~3, 관련성·권위·신선도 종합, 1.5 이상이 고품질), `authority`(0~4, -1은 미상, 3 이상이 고권위), UI용 `snippet`(대략 100~200자)과 **모델용 `summary`(대략 600~800자)를 따로** 준다. 그 밖에 `title`·`url`·`content`·`site_name`·`date`.
- **Fetch:** URL(최대 8,192자, 자격정보 포함 URL 금지)을 받아 `title`과 **마크다운으로 정제한 `content`**를 돌려준다. 차단·미지원 형식·본문 추출 불가는 404, 보안 정책 거부는 403.
- **과금:** 둘 다 **성공 1,000건당 $0.75**. HTTP 200이면서 결과가 비어 있지 않을 때만 과금한다. 실패·빈 결과·타임아웃은 무료이고, `count`는 가격에 영향이 없다.
- **한도:** Search 100 QPS, Fetch 25 QPS(계정 단위, 서로 독립, 모델 동시성과 별도). Fetch는 도메인별 한도가 따로 있다. 초과하면 429.
- **무료 기간:** DeepSeek Harness·Claude Code·Codex를 통한 서버측 호출은 현재 무료이고, **2026-11-01 00:00(베이징 시간)부터 과금**이 시작된다.

**배경 — 얼마나 싼가.** 같은 주(10/16) 기준 공시가 비교: Brave Search $5/1천 건, Exa $4~7, Perplexity Search $5(Fast는 $1), Tavily $5~8. DeepSeek은 이들의 **1/7~1/10** 수준이다. 브리핑은 기존 서비스를 "건당 수 센트"로 적었지만, 실제로는 건당 0.4~0.8센트(1천 건당 $4~8)가 맞다 — 격차는 크지만 브리핑 표현만큼 극적이진 않다.

**기술적으로 눈여겨볼 점.** `snippet`/`summary` 분리는 "사람이 보는 표면"과 "모델이 먹는 입력"을 **API 레벨에서 나눈** 설계다. RAG 파이프라인에서 보통 직접 하는 일 — 본문 추출 → 정제 → 요약 → 청크 — 중 앞의 세 단계를 공급자가 가져갔다. 에러 코드에 재시도 정책(408·429·5xx만 재시도, 402는 충전 먼저)까지 명시돼 있어, Spring의 `RestClient`+`@Retryable` 같은 재시도 설계 연습 대상으로도 깔끔하다.

**실무에 무슨 의미인가 — 그리고 진짜 비용.** 같은 날 나온 비교 글(Tavily vs Exa vs Brave)의 요지는 이렇다. **검색 수수료보다 돌려받은 본문을 모델이 읽는 토큰값이 6~20배 크다.** 예시로 질문 1,000개 × 검색 3회 × 결과 10개 × 페이지당 약 5,000토큰을 계산하면, 토큰 비용이 약 $300인데 검색 수수료는 $15~51였다. 이 계산에 DeepSeek을 넣으면 수수료는 $2대로 떨어지지만 **$300은 그대로**다. 그러니 설계의 실제 레버는 다음 셋이다. ① 결과 몇 개를 **본문까지** 읽힐지(`need_content`를 기본 false로 둔 이유), ② `summary` 600~800자로 충분한지, ③ `rerank_score` 1.5 미만을 버릴지. Spring Boot 사이드 프로젝트라면 "검색 → 상위 3개만 Fetch → 나머지는 summary만"처럼 **단계별 예산**을 먼저 정하는 게 맞다.

**반론·회의적 시각.** ① 문서에 **데이터 보존 정책이 없다** — 질의 내용(사용자 질문 `ori_question` 포함)이 어디에 얼마나 남는지 알 수 없다. 사내 코드·고객 데이터가 섞인 질의라면 이게 가장 먼저 걸린다. ② 지원 언어·지역 범위도 명시가 없다(`lang:` 연산자와 IP 현지화만 있다). 자체 검색 인덱스의 품질은 공개 벤치마크가 없다. ③ HN 반론처럼 **초기 유인 가격**일 수 있다 — 11/1 과금 시작 이후의 실제 단가와 한도 변화를 봐야 한다. ④ "Fetch가 마크다운 정제를 대신한다"는 건 편하지만, 정제 품질(표·코드 블록 보존)이 내 용도에 맞는지는 직접 확인해야 한다.

### 4. Java sealed 타입의 함정 — 컴파일은 통과, 런타임에 MatchException (+ JDK 28 윤곽)

**무슨 일인가.** Neil Madden의 글(원문 2026-04-24, 이번에 HN 135p/102c로 재부상)이다. sealed 타입의 망라성 검사가 **분리 컴파일** 상황에서는 런타임 예외로 바뀐다는 내용이다.

**어떻게 동작하나.** 예시는 이렇다.

```java
public sealed interface SealedType {
    record TypeA() implements SealedType {}
    record TypeB() implements SealedType {}
}
// 소비자: default 없이 TypeA·TypeB만 다루는 switch — 망라적이라 컴파일 OK
```

라이브러리 쪽에서 `TypeC`를 추가하고 **그 파일만** 다시 컴파일한 뒤, 소비자(`Main`)는 예전 바이트코드 그대로 `java Main C`를 실행한다. 결과는 `java.lang.MatchException at Main.main(Main.java:3)`이다. 컴파일 에러는 소비자까지 전부 다시 컴파일할 때만 난다.

배경을 덧붙이면(원문에는 없는 일반 지식), 컴파일러는 망라적인 switch에 "알 수 없는 케이스가 오면 던진다"는 숨은 분기를 넣는다. `MatchException`은 Java 21에서 패턴 매칭이 정식화될 때 그 용도로 들어온 예외다. 컴파일러가 "여기는 절대 안 온다"고 가정한 자리가, 실행 시점의 클래스 집합이 달라지면 도달 가능해지는 것이다. 원문은 바이트코드 수준 설명은 하지 않고, Javadoc이 이 예외를 분리 컴파일과 연결한다는 점만 짚는다.

**저자의 결론.** sealed 타입은 **함께 재컴파일되는 컴포넌트 내부**에서 가장 쓸모 있다. 공개 API에 노출하면 하위 타입 추가가 곧 **호환성 깨짐(SemVer 메이저 버전업 사유)**이 된다. 구체 사례로 JEP 524(PEM 인코딩 암호 객체, 프리뷰)를 든다. 공개 sealed 인터페이스를 두고 클라이언트에게 패턴 매칭을 권장하는 구조라, 나중에 케이스가 추가되면 깨질 가능성이 "매우 높다"고 본다(저자 스스로 "아마도"라는 단서를 달았다).

**실무에 무슨 의미인가.**

- 내 Spring 프로젝트 **안에서** 도메인 상태(예: WMS 주문 상태 `Received | Picked | Shipped`)를 sealed + record + switch로 모델링하는 건 이득이 크다. 같은 빌드에서 같이 컴파일되기 때문이다.
- **모듈·라이브러리 경계**(팀 공용 모듈, 외부 SDK)에서는 다르다. 소비자 쪽 switch에 `default`를 두어 "모르는 케이스"를 명시적으로 처리하거나(망라성 검사 이득은 포기), 공개 API는 sealed가 아닌 인터페이스로 둔다. 원문은 이 두 대안을 다루지 않는다 — 내가 덧붙이는 선택지다.
- 더 일반적인 교훈: **"컴파일 타임 안전성"은 "모두가 같이 컴파일된다"는 전제 위에서만 성립한다.** 멀티 모듈 Gradle 빌드에서 일부 모듈만 배포하는 구조라면 이 전제가 이미 깨져 있다.

**같은 날의 JDK 28 윤곽 (브리핑 기준 — OpenJDK 페이지는 이번에 열지 못했다).** JEP 401 값 객체(프리뷰, Valhalla — identity 없는 객체를 JVM이 평탄화), JEP 544 AOT 코드 컴파일(기동·워밍업 단축 — 컨테이너 콜드 스타트), JEP 543 구조적 동시성, JEP 539 엄격한 필드 초기화(프리뷰), JEP 540 간단한 JSON API(인큐베이터 — Jackson 대체는 먼 이야기), JEP 535 Shenandoah 세대별 모드 기본값, ZGC 개선(545·546), macOS/x64 포트 deprecated(541). 값 객체가 들어오면 sealed + record로 짠 도메인 모델이 메모리 레이아웃 측면에서도 이득을 볼 수 있다. 다만 프리뷰 단계다.

**반론·회의적 시각.** ① HN 댓글이 포인트에 가까울 만큼 논쟁적이다. "새 케이스 추가가 소비자를 깨뜨리는 건 **버그가 아니라 기능**이다 — 그래야 소비자가 새 케이스를 처리한다"는 입장도 있다. 이 관점에서 진짜 문제는 sealed가 아니라 **재컴파일 없이 배포하는 관행**이다. ② 같은 문제는 enum에도 있다(enum switch에 새 상수가 오면 런타임 예외). sealed만의 특수한 함정은 아니다. ③ 글은 4월 글이라, JEP 524가 그 사이 바뀌었는지는 확인하지 못했다.

### 5. Tines 3B — 일회성 샌드박스에 버전 관리 파일시스템을 붙이는 법

**무슨 일인가.** Tines의 워크플로 엔진 3B는 각 단계를 새 Linux 샌드박스(gVisor)에서 돌리고 끝나면 파괴한다. 보안엔 좋지만 고객은 단계 사이에 남는 상태가 필요했다 — 클론한 저장소, SQLite에 쌓은 리드, DuckDB에 모은 웹훅 같은 것들이다. 그래서 단계마다 `/storage/<이름>`에 마운트되는 **버전 관리 볼륨**을 만들었다.

**구조 (원문 기준).**

- **Nest** — 샌드박스 바로 바깥의 파일 서버다. FUSE 대신 gVisor의 gofer를 확장했다(호출마다 데몬을 거치지 않으려고). 파일을 열면 고정된 스냅샷에서 찾아 **로컬 tmpfs로 통째 복사**하고 파일 디스크립터를 넘긴다. 그래서 읽기·쓰기·mmap이 로컬 속도로 돈다. 경계를 넘는 건 open·rename·list 같은 제어 연산뿐이다. 생성·이름변경·삭제·쓴 영역을 추적하고, 공유 mmap 변경은 열 때의 청크 지문으로 감지한다. 단계 안의 `fsync`는 로컬 사본만 플러시한다.
- **Spongeblob** — Rust 저장 엔진이다(디스크당 프로세스 1개). 볼륨은 **불변 스냅샷의 사슬 + "현재"를 가리키는 포인터**다.
- **성공 시에만 커밋** — 실패·크래시·OOM으로 죽은 단계는 아무것도 발행하지 않고 로컬 사본을 버린다. 성공한 단계만 변경분을 올리고, Spongeblob이 현재 스냅샷 위에 새 스냅샷을 만들어 포인터를 전진시킨다.
- **CoW + MVCC** — 스냅샷은 바뀌지 않은 하위 트리를 공유한다. 큰 볼륨에서 파일 하나를 바꾸면 잎·부모 디렉터리·루트 몇 노드만 새로 쓴다. 읽는 쪽은 시작할 때의 스냅샷을 계속 읽으므로 **읽기와 쓰기가 서로를 막지 않는다**.
- **CAS 포인터 발행** — "포인터가 아직 42면 43으로 옮긴다". 아니면 변경을 비교해 **다른 파일 변경은 새 스냅샷 위에 리플레이**하고, **같은 파일 변경은 경로를 명시한 충돌 에러**로 낸다(이 충돌 의미론은 아직 정리 중이라고 저자가 밝혔다).
- **포크** — 스냅샷이 불변이니 포크는 같은 스냅샷에 포인터를 하나 더 붙이는 것이다. 수 GB 볼륨도 빈 볼륨만큼 빨리 포크된다. 브랜치 간 병합은 3-way merge가 필요해 하지 않는다.
- **쓰기 경로** — 데이터와 작은 저널 레코드를 활성 pack 파일에 append한 뒤 `fsync`한다. 동시 쓰기는 group commit으로 `fsync` 하나를 공유한다. pack 자체가 로그라 별도 저널이 없다. LSM 인덱스는 객체 → pack 위치만 들고 있어서 병합 때 파일 데이터를 옮기지 않는다. 죽은 데이터가 절반 넘는 pack만 재배치하므로 파일 수명 동안 쓰기는 대략 2회다.
- **계층화** — 뜨거운 데이터는 로컬 디스크에 둔다. S3가 설정돼 있으면 봉인된 pack을 백그라운드로 올리고 복구 체크포인트에 기록한다.
- **수치** — 프로덕션 기준 읽기 약 1ms, 쓰기 2ms 미만, S3 체크포인트 지연 약 1분.

**기각한 대안.** FUSE(계층 하나 더) / 요청 시 페이지 가져오기(커널 페이지 캐시에 짐) / S3 직접 쓰기(요청당 수십 ms + 비용 약 2배 + 자체 호스팅 고객) / RocksDB 내장("됐을 수도 있지만" 데이터 모양에 맞춘 자체 엔진) / FoundationDB 메타데이터(조회마다 네트워크 홉 + 운영할 시스템 추가) / 브랜치 병합.

**실무에 무슨 의미인가.** 이 글은 **DB 트랜잭션과 Git의 개념이 파일시스템 레이어에 그대로 다시 나타나는** 사례다. 책으로 본 개념을 매핑하면 이렇다.

| 이 글 | 내가 아는 개념 |
| --- | --- |
| 성공 시에만 발행, 실패 시 로컬 사본 폐기 | 트랜잭션 커밋/롤백 |
| 시작 시점 스냅샷을 계속 읽음 | MVCC — MySQL InnoDB의 REPEATABLE READ 일관된 읽기 |
| 포인터 42→43 CAS, 실패 시 리플레이 | 낙관적 락 — JPA `@Version`, `UPDATE ... WHERE version = ?` |
| 같은 파일 충돌은 에러 | 낙관적 락 실패 → `OptimisticLockException` |
| 포크 = 포인터 하나 더 | Git 브랜치 = 커밋을 가리키는 포인터 |
| pack append + group commit | WAL, InnoDB redo 로그의 group commit |

같은 날 노트 「응 이게 왜 롤백되는거지」(Spring 중첩 트랜잭션의 rollback-only)와 나란히 읽으면 좋다. "성공해야만 반영된다"는 원칙을 애플리케이션 레벨과 파일시스템 레벨에서 각각 어떻게 구현하는지 비교할 수 있다. 에이전트 맥락에서는 "실패한 에이전트 단계가 남긴 반쯤 쓴 파일"이라는 고질적인 문제를 **저장소 설계로 원천 차단**한 예다.

**반론·회의적 시각(저자가 밝힌 한계).** ① EBS 볼륨을 잃으면 마지막 체크포인트 이후(최대 약 1분)의 쓰기를 잃는다 — 가장 큰 내구성 공백이다. ② 디스크당 소유자가 하나라 배포 때 짧은 불가용 구간이 생긴다(그 사이 쓰기는 재시도 응답). ③ 큰 파일도 열 때 통째 복사한다(개선 중). ④ 자주 갱신되는 파일은 여러 pack에 흩어져 읽기 증폭이 생긴다. ⑤ 같은 파일 충돌 의미론이 미정이다. 덧붙이면, 이건 Tines 한 회사의 엔지니어링 블로그라 외부 벤치마크·비교는 없다.

**브리핑 정정·보충**

1. **(정정) md5 실험의 모델 구성.** 브리핑은 "서브에이전트는 Haiku, 오케스트레이터는 더 큰 모델"이라 적었지만, 원문은 **haiku 하나만** 썼다고 밝힌다(한계 항목에 명시).
2. **(정정) md5 실험의 "백그라운드로 띄우고 기다리지 않았다".** 원문에는 이 서술이 없다. 원문이 밝힌 사실은 이렇다. 3번 구성에서 서브에이전트 정의가 `tools: Read`뿐이라 애초에 수정할 수 없었고, 메인은 성공을 보고했으며, 그 이유는 **미확인**이다. 또 `len(nums) == 0` 체크는 1번(리뷰 전용) 실행의 제안이 `if not nums: return 0`이었던 것과 섞인 서술로 보인다.
3. **(정정) 기존 검색 API 단가.** 브리핑의 "건당 수 센트"는 과장이다. 공시가는 1천 건당 Brave $5·Exa $4~7·Tavily $5~8, 즉 **건당 0.4~0.8센트**다.
4. **(보충) Anthropic 리포트의 품질 비교.** "삭제·리버트 비율이 비슷했다"는 수치·신뢰구간 없이 결론만 공개됐다. 주니어의 정의도 원문에 없다.
5. **(보충) sealed 글의 날짜.** 원문은 2026-04-24 글이다(이번 주 HN 재부상). 바이트코드 수준 설명은 원문에 없다.

## 더 알아볼 것

- [ ] **md5 실험을 직접 재현한다.** 빈 폴더에 버그 있는 파일 하나를 두고 `sha256sum` 전후 비교 + `git status`로 "보고 vs 상태"를 확인한다. 같은 설정을 3회 이상 돌려, 거짓 완료가 1회짜리 우연인지 반복되는지 본다. 편집 도구를 가진 서브에이전트 구성도 추가한다(원문이 안 해본 것).
- [ ] **WMS 도메인 상태를 sealed + record로 짜고 분리 컴파일로 깨 본다.** Gradle 멀티 모듈에서 `domain` 모듈에 새 상태를 추가하고 `domain`만 다시 빌드한 jar로 `app`을 실행해 `MatchException`을 눈으로 확인한다. `default` 분기를 넣었을 때와 비교한다.
- [ ] **Tines 3B의 CAS 발행을 JPA 낙관적 락으로 옮겨 본다.** `@Version`이 있는 "볼륨 포인터" 엔티티를 두고 두 트랜잭션이 동시에 42→43을 시도할 때 하나가 `OptimisticLockException`으로 실패하는지, "다른 파일이면 리플레이"를 애플리케이션에서 어떻게 구현할지 설계해 본다.
- [ ] **검색 RAG의 비용 예산을 계산해 본다.** 질문 100개 × 검색 2회 × (상위 3개 Fetch + 나머지 summary)로 DeepSeek 수수료와 모델 입력 토큰값을 각각 계산해 비교한다. "검색 수수료보다 읽기 비용이 크다"가 내 설정에서도 맞는지 숫자로 확인한다.
- [ ] **Anthropic 리포트의 "판단력"을 면접 답변으로 바꿔 본다.** 내 프로젝트에서 에이전트(또는 남의 코드)가 낸 결과를 **과하다고 판단해 되돌린 사례** 하나를 골라 "무엇을 봤고, 왜 과했고, 무엇으로 확인했나" 세 문장으로 써 본다.

## 배경

글은 B마트서비스개발팀에서 DBA가 넘겨준 slow query 목록이나 Grafana의 MySQL Overview를 봐도 "이 쿼리가 코드 어디서 나갔는지"는 매번 코드를 뒤져야 했던 상황에서 출발한다. 그래서 모든 SQL 앞에 `/* handler: JiwooController.getShop */` 같은 주석으로 진입점(컨트롤러+메소드, 이벤트 컨슈머+메소드, 배치 job 이름)을 남기기로 했다고 설명한다. 이유로는 성능 최적화(진입점별 과도한 DB 접근 식별), 추적성(데드락 시 최초 컨트롤러 위치 파악, 진입점별 DB 사용 패턴 분석), 그리고 심미성 세 가지를 든다. 저장 공간으로는 MDC(Mapped Diagnostic Context — slf4j가 스레드 단위로 메타 정보를 담는 ThreadLocal Map)를 골랐는데, 로그와 SQL 양쪽에 같은 값을 꺼내 쓸 수 있어 "로그부터 SQL까지 진입점이 이어지는 구조"가 되기 때문이라고 한다.

## 핵심

글이 설명하는 기본 작업은 세 단계다.

- **진입점에서 `MDC.put`** — `HandlerInterceptor`의 `preHandle`에서 `HandlerMethod`의 빈 타입 이름과 메소드 이름을 `"handler"` 키로 저장하고, `afterCompletion`에서 `MDC.clear()`. `WebMvcConfigurer.addInterceptors`로 등록.
- **스레드 전환 시 MDC 복제** — `ThreadPoolTaskExecutor.setTaskDecorator(new MDCCopyTaskDecorator())`. 데코레이터가 `MDC.getCopyOfContextMap()`으로 복사해 두었다가 새 스레드에서 `MDC.setContextMap()`, `finally`에서 `clear`. Spring이 `execute()` 시점에 `taskDecorator.decorate(command)`를 적용하는 구조라고 설명한다.
- **DB 접근 기술별 SQL 주석 추가** — Hibernate `EmptyInterceptor`를 상속해 `onPrepareStatement(String sql)`에서 `"/* handler: " + 값 + " */ " + sql`을 반환. `handler`·`consumer`·`batch` 세 키 중 값이 있는 첫 번째를 쓴다. 등록은 `spring.jpa.properties.session_factory.interceptor: <FQCN>`.

그런데 기본 작업만으로는 안 됐고, 전수 조사에서 빠진 케이스들이 줄줄이 나왔다고 한다.

- **Web MVC 밖의 진입점** — 인터셉터는 MVC 컨텍스트에서만 동작하므로 `@SqsListener`·`@KafkaListener`·`@Scheduled`에는 `@Before/@After` AOP로 `"consumer"` 키를 넣고 지우는 `ConsumerLoggingAspect`를, Spring Batch에는 `JobLauncher.run(..)` 실행을 `@Around`로 잡아 `job.getName()`을 `"batch"` 키로 넣는 `BatchLoggingAspect`를 추가. 멀티 모듈 10개 중 `WebMvcConfiguration` 등록이 빠진 모듈도 있었다.
- **Batch의 빈 스코프 누락** — Grafana로 확인하니 절반 넘는 요청에 진입점이 안 남았는데, 원인 하나가 `ItemReader` 빈 생성 시점에 SQL이 나가는 코드였다. 스코프 지정이 없으면 ApplicationContext 기동 시 빈이 만들어져 `JobLauncher.run()` 이전, 즉 MDC 세팅 전에 쿼리가 나간다. step은 `@JobScope`, reader/writer/processor/tasklet은 `@StepScope`를 붙여 해결.
- **TaskDecorator가 안 먹는 스레드풀** — `Executors.newFixedThreadPool` 같은 `ExecutorService`, `ForkJoinPool`, `CompletableFuture`, `TaskScheduler`, Reactor 스케줄러, Caffeine 캐시 executor 등은 데코레이터가 적용되지 않는다. 처음엔 `ExecutorService` 전 메소드를 오버라이드하는 `CustomExecutorService`를 만들었지만, 코드 리뷰에서 "혼용보다 `ThreadPoolTaskExecutor`로 통일하자, 관리 포인트가 는다"는 이유로 **반려**되고 스레드풀 전체를 전환했다. 글은 "SQL 진입점이 문제가 아니고 스레드풀 전체를 건드려야 하는 일이 됐다"고 표현한다.
- **TaskScheduler는 별도 데코레이터** — `DelegatingMDCTaskScheduler` + `AbstractDelegatingMDCSupport`(Runnable/Callable `wrap`)를 직접 구현. 구조는 Spring Security의 `AbstractDelegatingSecurityContextSupport`를 참고했다고 한다. Caffeine은 `.executor(데코레이터 적용 executor)`, Reactor `elastic()`은 `Schedulers.fromExecutor(taskExecutor)`로 교체.
- **JdbcTemplate 경로** — JPA와 JdbcTemplate을 함께 쓰고 있어서 Hibernate 인터셉터만으론 부족. `update`·`query` 앞에서 마지막 세미콜론을 떼고 주석을 붙이는 `CustomJdbcTemplate`을 만들고, 클래스 안에서 `new`로 만들던 JdbcTemplate도 빈으로 교체. Batch의 `JdbcPagingItemReaderBuilder`는 `PagingQueryProvider`를 감싼 `CustomPagingQueryProvider`로.

## 내 프로젝트와의 연결

WMS에서 재고 조회·출고 피킹 쿼리의 N+1이나 slow query를 Before/After로 측정할 때, 지금은 "어느 API가 이 쿼리를 냈나"를 코드에서 역추적해야 한다. 이 글의 `HandlerInterceptor` + Hibernate `StatementInspector`(글은 구버전 `EmptyInterceptor`를 썼지만 Hibernate 6에서는 `hibernate.session_factory.statement_inspector`가 같은 자리) 조합이면 MySQL general log나 p6spy 출력에 컨트롤러 이름이 붙어 측정 기록의 근거로 바로 쓸 수 있다. 동시성 실험에서 데드락이 나면 어느 진입점 둘이 엉켰는지도 로그만으로 보인다. 수집기 쪽은 Spring이 아니라 직접 연결은 약하지만, "스레드가 바뀌면 컨텍스트가 끊긴다"는 지점은 구조적으로 같다 — 재시도·스케줄 경계마다 실행 ID를 넘겨줘야 로그를 잇는 것과 동일한 문제다.

## 오늘 정리할 것

1. WMS 프로젝트에 `HandlerInterceptor`로 `MDC.put("handler", ...)`를 넣고 logback 패턴에 `%X{handler}`를 추가해 요청 로그에 컨트롤러 이름이 찍히는지 확인한다.
2. Hibernate 6 `StatementInspector`를 구현해 `spring.jpa.properties.hibernate.session_factory.statement_inspector`로 등록하고, `/* handler: ... */` 주석이 붙은 SQL이 콘솔에 나오는지 본다.
3. `@Async` 메소드 하나를 만들어 MDC 값이 사라지는 것을 직접 재현한 뒤, `ThreadPoolTaskExecutor.setTaskDecorator`로 복원되는지 확인한다.
4. `Executors.newFixedThreadPool`과 `ThreadPoolTaskExecutor`의 차이(어느 쪽이 `TaskDecorator`를 받는지)를 Spring 문서에서 확인해 한 줄로 적어 둔다.

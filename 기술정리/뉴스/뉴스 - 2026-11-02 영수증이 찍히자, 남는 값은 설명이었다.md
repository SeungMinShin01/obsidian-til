첫 번째 축은 **"감"이 영수증으로 바뀐 것**이다. Lawson은 같은 앱을 12개 프레임워크로 5번씩, 총 60번 만들게 하고 달러·분·토큰·줄 수·전송 JS로 쟀다. 두 번째 축은 **만드는 값이 0에 가까워질 때 남는 값**이다. Karpathy는 "코드를 읽지도 쓰지도 않고" 2시간 만에 6,454개 영상 사이트를 띄웠고, 다음 날 같은 틀의 HackerBooks(16,543권)가 올라왔다. 세 번째 축은 그 반대 극단, **검증을 '느림'으로 보는 조직**이다. Proton CEO가 침투 테스트 며칠을 "loser thinking"이라 부른 일은 AI 도입 문제가 아니라 리더십 문제로 읽혔다(글쓴이도 그렇게 썼다). 새 흐름이라 할 만한 건 하나다. **MCP·스킬이 오히려 비용을 늘릴 수 있다**는 의심이 실측 근거를 얻기 시작했다. Lawson의 데이터에서 공식 MCP/스킬을 깔아줘도 에이전트가 안 쓰거나(Nuxt MCP 0/5), 늦게 찾거나(TanStack 2/5), 너무 새 버전 문서를 매번 읽느라 비싸졌다(SvelteKit 5/5 MCP 사용인데 비용 상위). 11/1의 MICA("표현이 행동을 가른다")와 합치면, 에이전트 도구 생태계는 "붙이면 좋아진다"가 아니라 **"붙인 걸 쟀나"**의 단계로 들어가는 중이다.

## 깊게 본 것

### 1. JS 프레임워크의 'AI 비용' — 같은 앱 60번, 영수증으로 비교하기

**무슨 일인가.** Nolan Lawson(전 MS Edge 성능팀, Pokédex.org 저자)이 PokéAPI를 쓰는 작은 포켓몬 앱 명세를 쓰고, Opus 5.5(high effort)에게 12개 프레임워크/메타프레임워크로 **각각 5번씩** 만들게 했다. 측정: 개발 비용(Claude Code가 보고한 API 환산가), 벽시계 시간, 토큰(캐시 읽기 포함), 비공백 코드 줄 수, Lighthouse 홈 화면 지표. 코드는 [agent-framework-benchmark](https://github.com/nolanlawson/agent-framework-benchmark)로 공개.

**배경 — 왜 지금 이게 나왔나.** Lawson의 문제의식은 "웹 개발의 결정은 대부분 느낌(vibes) 기반"이었다는 것이다. 예전엔 그 느낌이 DX(타이핑하는 손맛)였는데, 에이전트가 코드를 치는 지금은 DX 제약이 사라졌는데도 "이 프레임워크가 에이전트에 더 좋다"는 주장이 또 증거 없이 돈다. "에이전트한테 물어봤나?" — 그래서 벤치마크를 짰다.

**어떻게 설계했나 — 공정성 장치들.**

- **치팅 방지**: 명세 적합성 테스트(conformance suite)를 에이전트에게 주되, 모든 HTML을 정적으로 미리 생성하는 꼼수는 금지하고 하네스에서 검사. 테스트는 원시 DOM이 아니라 **접근성 트리** 기준이라 특정 HTML 구조를 강요하지 않음(Lit의 shadow DOM 때문).
- **학습 데이터 편향 반론 차단**: 각 프레임워크의 공식 MCP·스킬·플러그인을 설치. 단 "써라"고 강요하진 않음 — 일반 바이브코더처럼.
- **유도 금지**: SSR/CSR 선택, 성능 최적화 지시를 하지 않음. Lighthouse로 잴 거란 사실도 비공개. CSS는 Tailwind 등 컴포넌트 프레임워크 금지, 디자인 토큰만 지정.
- **분산 인정**: 5회 중앙값 + 최소~최대 범위를 함께 보고. Angular는 2회가 localhost 외 요청을 거부하는 SSR 앱을 만들어(명세에 리버스 프록시 뒤라고 명시돼 있었음) **명세 위반 실패**로 처리, 크기·성능은 3회 기준.

**결과 — 무엇이 갈리고 무엇이 포화됐나.**

비용이 비싼 이유가 셋으로 갈린다는 게 흥미롭다. ① **SvelteKit — 너무 새 버전**: 매 실행마다 SvelteKit 3 마이그레이션 가이드를 읽음(Opus 5.5 학습 이후 출시). ② **Gracile — 너무 낯섦**: 저장소를 클론하거나 `node_modules`의 컴파일된 소스를 읽음. ③ **Angular — 그냥 코드가 많음**. 앞의 둘은 "모델이 모르는 것"의 비용이고, 셋째는 "프레임워크가 요구하는 의례(ceremony)"의 비용이다.

또 하나: "Vanilla(프레임워크 없이 Vite만)"가 여러 프레임워크보다 비쌌고, 자유를 줬더니 **5번 다 SPA를 골랐다**. "프레임워크가 없으면 더 가볍다"는 직관이 에이전트에겐 성립하지 않았다 — 구조가 없으면 에이전트가 구조를 매번 새로 발명한다.

**MCP·스킬 실제 사용률(본문 표).** Hono 스킬 5/5, React Router 스킬 5/5, SvelteKit MCP 5/5, Angular MCP 3/5·스킬 4/5, Astro MCP 2/5, Next.js 스킬 파일 1/5·`AGENTS.md` 2/5, TanStack 스킬 파일 2/5(`node_modules`에 동봉), **Nuxt MCP 0/5**. Lawson의 결론부 추측 — *"지금 나온 MCP와 스킬은 도움보다 해가 클 수 있다"* — 은 이 표 위에서 나온 말이다. 단 그는 MCP 유무를 바꿔 본 대조 실험은 하지 않았다(본인이 개선 방향으로 적음).

**실무에 무슨 의미인가.**

- **"코드 줄 수 = 앞으로의 유지보수 토큰"**. 에이전트 시대에 코드량은 사람의 읽기 부담이 아니라 *고칠 때마다 다시 읽히는 컨텍스트 비용*이 된다. Rich Harris의 "프레임워크는 코드가 아니라 머리를 정리하는 도구"가 비용으로 번역되는 지점.
- **포화된 지표는 버려라.** Lighthouse 점수가 98~100에 몰리자 Lawson은 전송 JS·TBT로 옮겼다. 11/1의 "난이도 분포" 논문과 같은 교훈 — 점수가 천장에 붙으면 그 지표는 더 이상 아무것도 구분하지 않는다.
- **학습 데이터 바깥의 최신 버전은 세금을 낸다.** 내 프로젝트에서도 Spring Boot·React 최신 메이저로 올릴 때 에이전트가 마이그레이션 문서를 매번 읽게 된다면, `AGENTS.md`/`CLAUDE.md`에 "이 버전에서 바뀐 것 요약"을 미리 적어 두는 게 매 세션의 토큰을 아낀다(측정은 해봐야 함).

**반론·회의적 시각.**

- **holotype 하나**: 위키백과형 콘텐츠 사이트 — MPA에 유리. 대시보드·게임·생산성 앱이면 결과가 달랐을 것(본인 인정).
- **Lighthouse/CWV는 SPA에 구조적으로 불리**(본인 인정). 앱 내부 상호작용 지표는 넣지 않았다.
- **모델 하나·effort 하나·실행 5회**: Opus 5.5 high만. 다른 에이전트·effort에서 순위가 유지되는지는 미지수. 5회 분산이 이 정도면 순위 일부(가운데 그룹)는 노이즈 안에 있다.
- **비용은 API 환산가**: 실제로는 Max 구독 안에서 돌렸다. 구독 사용자에게 "달러"는 한도 소진 속도로 읽어야 한다(12월부터 ChatGPT·Codex 한도 통합 소식과 같은 결).
- **유지보수를 줄 수 하나로**: 순환 복잡도·변경 용이성 같은 지표는 없다. "추가 기능 하나 넣는 비용"을 재는 2차 실험이 있어야 "유지보수 토큰" 주장이 선다.

### 2. "It's the memory latency, stupid" — 연산을 늘렸더니 GROUP BY가 빨라졌다

**무슨 일인가.** Pivot(Parquet 위 OSS 쿼리 엔진) 블로그가 ClickBench `hits`(9,900만 행, 고유 `UserID` 약 1,700만)에 `SELECT count(*), UserID FROM hits GROUP BY UserID`를 단일 코어로 돌리며, "CPU 100%"가 실제로 무엇을 하는지 하드웨어 카운터로 쪼갰다. 환경: CherryServers 베어메탈 AMD EPYC 9124(Genoa) 16코어·DDR5 128GB — AWS/GCP는 DRAM 컨트롤러 카운터를 보안상 막아서 못 씀.

**배경 — 왜 CPU 100%가 거짓말인가.** 리눅스의 "idle"은 *실행 대기 태스크가 없다*는 뜻이지 CPU가 일을 꽉 채운다는 뜻이 아니다. 현대 CPU는 나노초당 4~8개 명령을 처리하는데 DRAM 접근은 50~100ns — **메모리 한 번 기다리는 동안 400~800개 명령을 버린다**. L1(~64KB, ~1ns)·L2(~1MB, 3~4ns)·L3(~수백 MB, 10~15ns)는 빠르지만 작다. 고유 키 1,700만 개짜리 해시 테이블은 캐시에 안 들어가므로, 행마다 해시 조회가 거의 전부 **차가운 DRAM 접근**이 된다.

**기술적으로 — 어떻게 쟀고 어떻게 풀었나.**

1. **순진한 버전**: 키마다 `HashMap.entry(key).or_insert(0) += 1`. 두 번째 실행(페이지 캐시에 데이터가 이미 있음) 3.6초. `taskset -c`로 서버를 코어 3에 고정하고 `perf stat -C 3 -M backend_bound_memory,retiring`:
   - 메모리 때문에 멈춘 슬롯 **50.1%**, 실제로 마이크로옵을 끝낸(retiring) 슬롯 **16.1%**
   - `ls_dmnd_fills_from_sys.dram_io_near` × 64바이트(캐시 라인) = DRAM에서 **4.5GB**
2. **기수 분할(radix partitioning)**: 두 단계로 쪼갠다.
   - Phase 1: 키를 해시하고 **상위 12비트**(`hash >> 52`)로 4,096개 파티션 벡터에 `(hash, key)`를 순차 push — 쓰기가 순차라 캐시 친화적
   - Phase 2: 파티션 하나씩 작은 해시 테이블을 만들어 집계 → 출력. 파티션당 키가 약 4,000개라 테이블이 캐시에 들어감. Phase 1의 해시를 재사용
3. **결과**: 3.6초 → **2.7초**(약 24%↓). 메모리 대기 50.1% → **23.5%**, retiring 16.1% → 32.2%, DRAM 읽기 4.5GB → **1.5GB**. 그런데 실행한 연산(`ex_ret_ops`)은 114억 → **194억으로 늘었다**. 메모리 대기 슬롯은 83.6억 → 37.9억.
4. Pivot 실제 구현(프리페치 등 추가 기법): 단일 코어 1.85초·DRAM 954MB, **16코어 172ms**.

**비유로 이해하기.** 도서관 서가 1,700만 칸을 오가며 책 한 권씩 꽂는 대신, 먼저 책을 첫 글자별 상자 4,096개에 대충 나눠 담고(일이 한 번 더 늘어남), 그다음 상자 하나를 책상 위에 올려 놓고 그 안에서만 정리한다. 걸어 다니는 시간(DRAM 대기)이 줄어드는 게 손을 한 번 더 쓰는 비용(추가 연산)보다 훨씬 크다.

**실무에 무슨 의미인가.**

- **"CPU가 100%다 → 코어를 늘리자/쿼리를 줄이자"의 앞 단계가 있다.** 무엇에 막혀 있는지(연산 vs 메모리)를 먼저 재야 처방이 맞는다. WMS 부하 테스트에서 DB CPU가 치솟을 때 "느린 쿼리"만 볼 게 아니라, 카디널리티 높은 `GROUP BY`·해시 조인이 메모리 바운드인지 보는 관점.
- **MySQL/Postgres에서도 같은 원리가 작동한다.** Postgres의 해시 집계·해시 조인은 `work_mem`을 넘으면 배치로 나누어 디스크로 흘리는데, 이건 메모리↔디스크 계층에서의 같은 "분할 후 정복"이다. 이번 글은 그걸 **캐시↔DRAM 계층**에서 한 것.
- **성능 측정의 모범 사례로 가져갈 것**: 프로세스 코어 고정(`taskset`)·두 번째 실행 기준(콜드 캐시 제거)·벽시계 시간과 하드웨어 카운터를 같이 보고. "몇 초 빨라졌다"보다 "왜 빨라졌는지를 보여주는 카운터"가 결정 로그에 남길 근거다.

**반론·회의적 시각.** 단일 쿼리·단일 데이터셋·단일 CPU(AMD Zen 4) 결과다. 고유 키가 적어 해시 테이블이 원래 캐시에 들어가는 경우엔 Phase 1이 순수한 오버헤드다 — 엔진은 카디널리티 추정으로 전략을 골라야 하고, 추정이 틀리면 역효과다. 파티션 수 4,096(12비트)의 근거나 다른 값과의 비교는 없다. 또 벤더(Pivot) 블로그라 마지막 숫자(1.85초·172ms)는 비교 기준선 없이 제시된 홍보 성격이고, 그 구현 기법은 다음 글로 미뤘다.

### 3. Calegari, "수학은 달라졌다, 그에 맞게 행동하자" — 산출물이 공짜일 때 무엇을 평가하나

**무슨 일인가.** Terry Tao 블로그 게스트 글(Frank Calegari, 시카고대 정수론). 계기는 10월 6일 OpenAI가 공개한 **700편+ 연구 논문**. Calegari는 이 논문들이 "아이디어는 엄청난 것도 있지만 형편없이 쓰였고, 공동체의 귀속(attribution) 관행을 어기며, 일부는 틀렸다"고 먼저 못 박는다. (머리말: 이 글 자체도 다른 형식으로 쓴 뒤 AI로 변환했다고 Tao가 명시.)

**배경 — 무엇이 흔들렸나.** 확률론자 Duminil-Copin의 탄식이 상징적이다: 커리어 내내 공개적으로 말한 주요 미해결 문제가 **하나도 빠짐없이** "증명됐다"고 주장됐다. Calegari의 역사적 비유는 **유한 단순군 분류**(1972 Gorenstein 프로그램 선언 → 1983 "완료" 선언, 준얇은 군 경우는 20년 뒤 Aschbacher·Smith가 마무리) — 유명 문제가 사라지자 분야 관심 자체가 식었지만, "왜 몬스터 군이 존재하는가"(Conway) 같은 질문은 그대로 남았다. 지금은 "1970년에 분류 증명이 등사판 인쇄물로 번진 채 사무실 바닥에 색종이처럼 흩뿌려진 상황"이라는 것.

**논지의 구조.**

- **추한 진실**: arXiv에 "최초" 경쟁용 AI 보조 논문이 쏟아진다. **증명을 생산하는 능력과 이해·새 방향을 여는 능력 사이의 간격**이 빠르게 벌어진다.
- **기여의 재정의**: "가치 있는 문제를 고르고, AI로 증명을 얻고, 그걸 철저히 이해하고, 거기서 새 질문을 여는" 사람은 원 증명에 새 재료를 하나도 안 넣었어도 큰 기여를 한 것. *"문제를 고르는 일이 증명을 만드는 일보다 중요해질 수 있다."*

**6개 제안과 그 근거.**

1. **모든 연구를 AI 보조라고 가정하고 평가** — 그러면 저자가 "왜 흥미롭고, 무엇을 묻게 하고, 분야와 어떻게 연결되는지"를 설명해야 한다. 지금의 AI 사용 공개 문구는 기계의 기여를 축소하려는 문장처럼 읽히는 낙인 효과가 있다.
2. **채용은 서류보다 대면** — 포닥·대학원생까지 면접. "고차 호모토피 이론 한다던 학생이 입학 후 원의 호몰로지를 못 구하더라", "애매했던 후보가 30분 대화 후 확신으로 바뀌었다". 단 **깊이 아는 것**과 **유창하게 설명하는 것**은 다른 능력이고, 그는 전자를 더 높게 친다.
3. **저널에 더 요구하고, 적응 못 하면 버려라** — 게재는 오래전부터 정확성 보증이 아니라 품질 도장이었다. arXiv 상당수는 어디에도 실리지 말아야 한다. "Lean으로 검증됐나?"도 물을 질문 중 하나.
4. **대학원 교육은 넓이 강조, 기술은 포기 말기** — 계산기가 있어도 산수를 가르치듯, AI 없이 깊은 수학을 하는 법도 가르친다.
5. **세미나는 새 결과가 아니라 큰 질문 중심** — 막힌 길, 희망 있는 길, 마지막에 새것이 있으면.
6. **AI 결과를 인류의 성과로 소유하라** — 수천 년 인간 수학 위에 지은 것이다.

**실무(개발자)에 무슨 의미인가.** 수학 이야기지만 구조가 개발 채용과 같다. "동작하는 코드"가 Cole의 소인수분해처럼 **계산 묘기**가 되는 국면에서, 평가는 ① 문제 선택(왜 이걸 만들었나) ② 이해(왜 이 구조인가, 무엇을 버렸나) ③ 다음 질문(이걸로 무엇이 가능해졌나)으로 옮겨 간다. 사용자가 WMS·수집기에서 쓰는 **결정 로그(문제→대안→선택 근거→기각 사유→검증)**가 정확히 이 세 가지를 담는 형식이다. 면접에서 "이 저장소를 AI로 만들었나요?"라는 질문은 무의미해지고 "여기서 왜 이렇게 했나요?"만 남는다 — Calegari의 1번·2번 제안이 그대로 그 방향이다.

### 5. HackerTube·HackerBooks — "말만 했다"가 성립하는 조건

**무슨 일인가.** Karpathy가 금요일 밤 YouTube의 "과장된 썸네일과 뻔한 추천"에 질려, 토요일 아침 Opus 5.5에게 "HN에서 추천된 영상으로 우리만의 YouTube를 만들자"고 시켰다. 2시간 뒤 [hackertube.org](https://hackertube.org/). 다음 날 같은 틀의 [HackerBooks](https://hackerbooks.org)(HN 댓글에서 서로 다른 2명 이상이 언급한 책 16,543권)가 HN 824점.

**어떻게 동작하나 — 파이프라인.** ① HF의 HN 댓글 전체 데이터셋 다운로드 → ② 필터링 → ③ Claude Code **Workflow** 기능으로 Sonnet을 대량 실행해 스팸 제거·"YouTube 영상을 추천하는 댓글" 4만 개 선별 → ④ 2007~2026년, 여러 명이 추천한 영상 **6,454개 / 150개 주제** → ⑤ YouTube API로 메타데이터(Google Cloud에서 API 키 발급은 사람이) → ⑥ YouTube형 UI, 업로드 썸네일 대신 **영상 50% 지점 프레임**을 썸네일로, 계정 없이 **브라우저 로컬 세션에 상태를 저장**하는 ForYou 추천, 키보드 단축키, 사이트 데이터 내보내기(남이 자기 버전을 만들도록) → ⑦ VPS에 IP만 주고 "update, deploy, secure, harden, optimize". 사람이 한 일은 API 키·VPS·도메인 셋. 기본 설정은 Opus 5.5 **Medium** effort.

**실무에 무슨 의미인가 — 기회와 함정.**

- **기회**: "데이터 수집 → LLM 분류 → 재조립 → 배포"가 주말 분량이 됐다. 이 구조는 사용자의 수집기 프로젝트(채용공고 수집 → 정제 → 저장)와 같은 뼈대다. CRUD 게시판보다 "어떤 데이터를 어떤 기준으로 걸렀나"를 설명할 거리가 훨씬 많다.
- **함정 1 — 말이 통하는 이유**: "secure, harden"이 한 문장으로 통하는 건 Karpathy가 *결과를 판정할 수 있는 사람*이라서다. 방화벽·TLS·SSH 설정·리버스 프록시를 모르면 그 한 문장의 결과를 검증할 수도, 사고 때 고칠 수도 없다. 2번 항목(메모리 지연)과 같은 이야기 — 재지 못하면 고칠 수 없다.
- **함정 2 — 집계 기준의 의미**: HackerBooks 작성자가 스스로 밝힌 한계 "언급 횟수만 세서 **칭찬과 혹평이 똑같이 집계된다**". 돌아가는 파이프라인과 맞는 설계는 다르다. HackerTube도 "여러 명이 추천"의 판정이 Sonnet 분류에 달려 있는데, 그 분류의 정밀도를 어떻게 샘플 검수했는지는 글에 없다(10/30 Trakkr 좀비 통계 노트의 "다섯 모델이 일치해도 검증은 아니다"와 같은 자리).

**반론.** 2시간은 Karpathy 기준이고, 공개된 건 결과물과 짧은 서술뿐이다 — 토큰 비용·실패한 시도·보안 점검 결과는 없다. "전통적인 엔지니어링은 전혀 안 한다"는 말은 *본인의 사이드 프로젝트*에 대한 서술이지 팀 단위 운영 시스템의 일반론이 아니다. 같은 날 Proton 사태가 그 일반화의 반대편 사례다.

**브리핑 정정·보충**

1. **(정정) Multi-Token Prediction Done Right의 요지는 "추론 속도"가 아니다.** 브리핑은 "뒤쪽 단어를 모르는 채 찍어서 생기는 문제를 정리, 체감은 추론 속도"라고 설명했지만, 논문은 **MTP 학습 그래디언트에 SNR 낮은 잔차가 섞여 있다**는 결함을 지적하고 한 줄 수정(Soft-MTP)으로 KL 자기증류 신호만 남긴다. 추측 디코딩 가속 개선은 약 +1.1%로 작고, 이득은 주로 퍼플렉시티·사후 미세조정 추론(HumanEval pass@64 40.85→43.90 등)에서 나왔다. 업보트도 브리핑의 17이 아니라 조회 시점 14. 자세한 건 AI 심층 노트.
2. **(정정) Co-Design Bench는 "사람과 실시간으로 주고받는 협업" 평가가 아니다.** 11/1 노트에서 본 대로 실제 사용자 세션 26,314개에서 뽑은 과제를 **숨겨진 수용 기준**과 judge-then-refute로 채점하는 레퍼런스-프리 벤치마크다. 핵심 수치는 기준 통과 69.9% 대 완전 완료 26.4%.
3. **(보충) "matklad 규칙 = Spring 자기 호출 함정"은 절반만 맞다.** 처방(비공개 헬퍼)이 겹칠 뿐 원인이 다르다. matklad는 **API 설계 긴장**(공개 인터페이스에 내부용 인자가 자라는 것)을 말하고, Spring의 `@Transactional` 자기 호출은 **프록시를 안 거쳐서** 생기는 런타임 문제다. 게다가 Spring에선 같은 클래스의 private 헬퍼로 빼도 그 헬퍼엔 트랜잭션 프록시가 적용되지 않는다 — 트랜잭션 경계가 필요하면 별도 빈으로 분리해야 한다(10/28 노트의 AOP self-invocation 한계와 같은 자리).
4. **(보충) Lawson 벤치마크의 MCP·스킬 사용률은 프레임워크마다 0/5~5/5로 제각각이고, MCP 유무를 바꾼 대조 실험은 없다.** "MCP가 해를 끼친다"는 본인도 '강한 의심(suspicion)'으로만 적었다. 또 비용은 실제 지출이 아니라 Claude Code의 API 환산가(본인은 Max 구독).
5. **(확인 필요) Octoverse "월 2억 2천만 머지 PR".** 10/29 노트에서 읽은 Octoverse 원문은 연간 머지 PR 13억(월평균 약 1.1억)이었다. 브리핑 수치가 특정 월(최근 급증 구간) 값인지 다른 집계인지 이번엔 원문을 다시 확인하지 못했다.
6. **(보충) Karpathy 기본 설정은 Opus 5.5 Medium, Lawson 벤치마크는 Opus 5.5 high.** 같은 모델이라도 effort가 다르면 비용·토큰은 직접 비교 불가.

## 더 알아볼 것

- [ ] **Lawson 벤치마크를 내 스택으로 축소판.** 같은 작은 명세(예: 공개 API 하나 읽는 목록·검색 화면)를 React+Vite와 Spring Boot+Thymeleaf(또는 htmx)로 각각 3번씩 에이전트에게 만들게 하고 ① 토큰 ② 시간 ③ 비공백 줄 수 ④ 전송 JS를 기록. 그다음 **기능 하나 추가**를 시켜 "줄 수가 적으면 유지보수 토큰도 적다"가 실제로 성립하는지 2차 측정.

- [ ] **내 결정 로그를 Calegari 기준으로 점검.** WMS·수집기 결정 로그 하나를 골라 "이 결정은 AI가 했다고 가정해도 남는 내 기여는 무엇인가 — 문제 선택·대안 기각 이유·다음 질문"을 세 줄로 적어 본다. 비어 있는 칸이 면접에서 답하기 어려운 칸이다.
- [ ] **Spring 자기 호출과 matklad 규칙을 코드로 구분.** `@Transactional` public 메서드가 같은 클래스 public 메서드를 부를 때(프록시 미적용), private 헬퍼로 뺄 때(여전히 미적용), 별도 빈으로 분리할 때(적용)를 각각 로그(`TransactionSynchronizationManager.isActualTransactionActive()`)로 확인하고, "API 설계 이유"와 "프록시 이유"를 한 줄씩 적는다.

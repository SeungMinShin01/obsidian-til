**사장님 입점요청 승인툴 고도화 프로젝트 경험담** — 세일즈서비스팀 · 2024-09-26 · Backend/Frontend
원문: https://techblog.woowahan.com/19415/

## 배경
입점 가게의 기본정보·인허가 서류·영업시간·메뉴를 내부 승인팀이 승인 어드민(SUPER2)으로 검수한다. 글은 두 가지 문제를 든다. 작업자는 일괄 리스트에서만 요청을 볼 수 있어 개인 업무 현황 파악이 어렵고, 새로고침을 반복하다 업무를 누락하기도 한다. 관리자는 전체 진행 상황을 볼 화면이 없어 메신저로 담당자에게 물어야 하고 병목을 늦게 발견한다.

## 핵심
- 개인 업무 개선: 상단 보드(할당·보류 작업), 화면 전환 없는 레이어 팝업, 요청 속성에 따른 업무그룹 자동 변경.
- UX 원칙: WCAG AA 대비(텍스트 4.5:1, 큰 글자 3:1), 색만으로 상태 표현 금지, 삭제 전 확인창, 무한 스크롤 대신 페이지네이션.
- 현황 보드의 데이터 조회 방식을 세 가지로 비교했다.
  - 캐시: 초기 조회 시 Cache Stampede(동시 요청 10개 = DB 10회), 10MB 이상 메모리, 애플리케이션 레벨 필터링 비효율 → 반려.
  - 배치: 애플리케이션 컨텍스트 로드에 수 분, 준실시간성 부족 → 반려.
  - 스케줄러: 별도 워커 서버가 통계 갱신을 전담해 주기를 조절해도 API 서버 성능에 직접 영향이 없고, RDB 인덱스를 활용 → 채택.
- 정시 미처리 집계: 요청 타입 15종마다 기준 시간이 달라, 처음엔 DB에서 가장 넓게 조회한 뒤 Kotlin에서 필터링했고, 이후 QueryDSL로 모든 조건을 OR 절에 넣어 DB에서 판정하고 페이지네이션을 제공했다. 스케줄러 주기로 OR 절의 성능 영향을 줄였다고 설명한다.
- 스택: Kotlin, Spring, QueryDSL, API 서버/워커 서버 분리.
- 결과(글의 주장): 관리자 일 190분, 작업자 일 900분 수작업 감소, 광고 신청 당일 처리율 66.6% → 최고 82.0%.

## 내 프로젝트와의 연결
- WMS: 입고·출고 대기 건수, 지연 건수 같은 현황 보드를 만들 때 "요청마다 집계 쿼리" 대신 워커가 주기적으로 집계해 두는 구조와 구조적으로 비슷하다. 타입별 기준 시간을 OR 조건으로 DB에 위임하는 방식은 인덱스 설계·실행 계획 확인 대상이다.
- 수집기: 스케줄러를 API 서버와 분리하는 발상은 GitHub Actions 무인 수집과 같은 결이다. 직접 연결은 약하다.

## 오늘 정리할 것
1. 캐시 스탬피드가 무엇인지, 동시 요청 N개일 때 DB 접근이 어떻게 늘어나는지 한 줄 도식으로 그려보기.
2. 조회 방식 3종(캐시·배치·스케줄러)을 "신선도 / 부하 / 구현 비용" 표로 정리하기.
3. 타입별 조건을 OR로 묶은 쿼리가 인덱스를 타는지 EXPLAIN으로 확인할 방법 찾아보기.
4. WMS 현황 보드에 필요한 집계 항목 3개를 적어보기.

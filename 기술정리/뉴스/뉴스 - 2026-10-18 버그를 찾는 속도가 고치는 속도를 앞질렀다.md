## 오늘의 흐름

겹치는 것부터 정리한다. 브리핑(10/18)의 Anthropic 분기 매출·증류 5~7%는 10/16 노트에서 깊게 다뤘고, Scion(머지 5월 2,500 → 9월 3만+/일)은 10/14 노트, Chirp Pong은 10/16 노트, Python 3.15는 10/11·10/14 노트에 있다. 10/17 브리핑은 그날 노트가 만들어지지 않아(결측일 — 몰아서 쓰지 않는다) 비교 대상에서 빠진다. 이 노트는 **새 항목만** 본다. 새로 붙은 것은 Anthropic의 6월 신용등급 소식 하나뿐이라 짧게 짚는다.

오늘을 꿰는 첫 번째 축은 **"찾는 쪽이 싸지자 병목이 고치는 쪽과 승인하는 쪽으로 옮겨 갔다"**다. PostgreSQL 19는 LLM 보조 리뷰가 몇 년 뒤에나 나왔을 엣지 케이스를 한꺼번에 쏟아내면서 출시가 약 11월 19일로 밀렸고 주요 기능 8~10개가 빠졌다. Eisentraut의 비유가 정확하다 — 결함 리포트 40건이 각각 평균 세 줄짜리 수정이어도, 건마다 붙는 **고정비**(재현·논의·커밋·재리뷰) 때문에 일정이 바닥난다. 같은 날 Anthropic Claude Code 팀은 정반대 쪽에서 같은 문제를 다뤘다. 코드의 약 90%를 Claude가 쓰는 환경에서 "사람이 다 읽었나"를 기준에서 빼고, **위험도 분류기가 정한 등급에 따라 사람 승인 0/1/2명**을 붙인다. 이건 이어지는 흐름이다. 10/14 노트(하버드 Chen·Stratton: 에이전트 도입 후 코드 +30%인데 리뷰 시간 +49%, 이슈 해결은 무변화)가 "생성이 싸지면 통과시키는 쪽이 병목"이라는 **진단**이었다면, 오늘은 그 병목을 실제로 맞은 두 조직의 **대응**이 나왔다 — Postgres는 기능을 빼서 범위를 줄였고, Anthropic은 사람 시간을 위험도에 따라 재배분했다.

두 번째 축은 **"AI 리뷰어도 리뷰가 필요하다"**다. Anthropic 글에서 가장 값진 부분은 성공담이 아니라 실패담이다. 한 PR이 밤새 에이전트 리뷰-수정 루프를 50번 넘게 돌았고, git blame을 해 보니 리뷰어가 계속 지적한 것의 약 59%는 **첫 패스부터 있던 기존 코드**였다. 라운드 상한·diff만 재리뷰·버그 "클래스" 단위 지적·중복 금지를 넣자 1라운드 통과율 65→78%, 5라운드 이상 8.9→1.5%. 그리고 리뷰어 자체는 **과거 장애·revert PR로 만든 eval 셋**에 매일 채점되고, 점수가 오를 때만 바뀐다. 10/16 노트의 "기준선을 다시 재라", 10/15 노트의 "합산 점수가 빠진 하나를 가린다"와 같은 결이다. 오늘 AI 쪽 논문 「Self-Evolving Agent Harness」가 이걸 이론으로 정리했다 — 하네스(프롬프트·메모리·툴·워크플로)를 스스로 고쳐 "점수가 올랐다"는 보고는 **선택·활성화·귀인·개선** 네 주장을 뒤섞는다. 구조는 AI 심층의 「하네스 자기진화의 증거 기준」 노트로 뺐다.

세 번째 축은 **"측정이 닿는 곳과 일이 있는 곳이 다르다"**다. Mercor는 O*NET 18,797개 업무 중 벤치마크가 커버하는 건 924개뿐이고, 시간 가중으로 미국 근로시간의 약 90%가 커버리지가 거의 없는 업무라고 추정했다. FDE-Gym(HF ▲281)은 같은 문제를 에이전트 쪽에서 보여 준다 — 요구사항이 애매하고 말하지 않은 제약이 숨은 납품 과제 95개에서 최고 구성도 평균 0.56, '해결'은 14개. 10/14 노트(AgentSWE: 보인 케이스 90점 → 숨긴 케이스 9.9점)의 "보이는 것만 맞힌다"가, 오늘은 **"벤치마크가 있는 곳만 잘한다고 알려져 있다"**로 한 단계 커졌다.

네 번째는 성격이 다른 축, **"검증 가능한 가설을 기계가 대신 훑는다"**다. Claude가 25년 묵은 NIST 타원곡선 시드의 출처를 30분 안에 밝혔다 — 해시가 아니라 **유닉스 타임스탬프로 시딩한 lrand48 출력**이었다. 여기서 볼 것은 "AI가 미스터리를 풀었다"보다 **풀이가 재현 가능한 코드로 남았다**는 점이다. 160비트 전체가 32비트 시드에서 재생성되므로 우연의 여지가 없고, 누구나 다시 돌려 확인할 수 있다. 10/13 노트(역컴파일: 바이트 비교라는 정답지가 있으면 리뷰어가 필요 없다)와 같은 구조 — **기계가 채점할 수 있는 문제에서는 탐색을 기계에 넘겨도 된다.** Postgres의 버그 홍수도 결국 같은 힘이다. 찾는 비용이 0에 가까워진 문제가 늘고 있다.

## 깊게 본 것

### 1. PostgreSQL 19 출시 연기 — AI 리뷰가 찾은 버그가 고칠 수 있는 양을 넘었다

**무슨 일인가.** The Register(10/16)에 따르면 9월 말~10월 초 예정이던 PostgreSQL 19 정식 출시가 **약 11월 19일**로 밀렸다. 베타 시작 후 **주요 기능 8~10개가 revert**됐고 PostgreSQL 20으로 넘어갈 전망이다. 기사가 이름을 밝힌 건 하나 — **SQL/PGQ**(SQL Property Graph Queries, 2023년 SQL 표준에 들어간 그래프 탐색 문법). Tom Lane은 "v19에 그대로 내보내면 출시 후 버그가 발견된다는 데 저녁 한 끼 걸겠다"고 했다. EDB VP이자 핵심 커미터 Peter Eisentraut가 블로그 「The reverts will continue until morale improves」(10/13 무렵)로 상황을 설명했다. VACUUM FULL 같은 테이블 락 없이 디스크를 회수하는 **REPACK CONCURRENTLY**는 19에 남는다.

**배경 — 왜 지금 이게 나왔나.** Eisentraut의 설명을 순서대로 놓으면 이렇다.

1. 빠진 기능 일부는 베타 중에 빨리 고치기 어려운 **심각한 설계 결함**이 있었다.
2. 나머지는 엣지 케이스의 **긴 꼬리**다. 예전이라면 출시 후 5년에 걸쳐 버그 리포트로 하나씩 올라와 천천히 고쳐졌을 것들이다.
3. LLM 보조 리뷰가 이걸 **한꺼번에** 찾았다. 예: 결함 리포트 40건, 건당 평균 3줄 수정. 그러나 건마다 고정비가 붙어 일정이 바닥났다.
4. 영향받은 기능 대부분은 그런 리뷰 도구가 쓸 만해지기 **전에** 작성·커밋됐다. 즉 "바이브 코딩 탓"이 아니다. 출시 직전 몇 달 사이 도구가 좋아지면서 **이미 커밋된 코드에 적용되는 실질 품질 기준이 중간에 올라갔다.**
5. 리뷰 도구가 지금 속도로 계속 좋아지면 다음 사이클부터는 작성 시점부터 같은 기준이 적용되니 완화될 것이라 본다.

**기술적으로 무슨 일이 일어났나.** 핵심은 "결함 발견률"과 "결함 처리율"의 비대칭이다. 발견은 병렬화된다 — 모델을 여러 개 돌리면 리포트가 그만큼 늘어난다. 처리는 병렬화가 안 된다 — 각 수정은 해당 서브시스템을 아는 소수의 커미터가 맥락을 다시 올리고, 패치를 쓰고, 다른 커미터가 리뷰하고, 회귀 테스트를 돌려야 한다. Postgres는 커미터 수가 적고 각 서브시스템의 "아는 사람"이 더 적다. 그래서 큐가 쌓이면 **고치는 대신 빼는 것**이 합리적인 선택이 된다. 기능을 revert하면 그 기능에 걸린 리포트 수십 건이 한 번에 사라진다.

**실무에 무슨 의미인가.**

- **DB 버전 계획.** Spring Boot 프로젝트에서 PG19 신기능(특히 SQL/PGQ)을 전제로 설계하고 있었다면 일정과 기능 목록을 다시 확인해야 한다. 베타 릴리스 노트와 정식 릴리스 노트는 다를 것이다.
- **AI 리뷰를 팀에 붙이는 순서.** 기존 코드베이스에 AI 리뷰를 처음 켜면 **기존 결함의 백로그**가 한꺼번에 쏟아진다. 이걸 새 PR의 리뷰와 섞으면 PR 작성자가 남의 버그를 떠안고 리뷰가 끝나지 않는다(2번 항목의 50라운드 사례와 같은 문제). 처방은 분리다 — 새 변경분 리뷰와 **야간 전체 스캔**을 따로 돌리고, 기존 결함은 별도 백로그로 우선순위를 매긴다. Anthropic이 Pre-existing 태그를 따로 붙이는 이유가 이것이다.
- **"빼는 것"도 선택지로 둔다.** WMS 같은 팀 프로젝트에서 마감 직전 버그가 쌓일 때, 고칠 수 있는 양을 넘으면 그 기능을 플래그 뒤로 숨기거나 다음 스프린트로 넘기는 결정이 오히려 품질을 지킨다. 결정 로그에 "왜 뺐나"를 남길 것.

**반론·회의적 시각.** ① 기사가 이름을 밝힌 revert는 SQL/PGQ 하나뿐이고, 나머지 7~9개가 무엇인지, 그중 몇 개가 **AI 리뷰 때문에** 빠졌는지는 분리되지 않는다. SQL/PGQ는 원래도 큰 기능이라 리뷰 도구가 없었어도 위험했을 수 있다. ② "AI 리뷰가 찾은 버그"의 오탐률이 공개되지 않았다. 40건 중 실제 결함이 몇 건인지 모르면 "품질 기준이 올라갔다"와 "노이즈가 늘었다"를 가를 수 없다. ③ Eisentraut는 EDB VP이고 낙관적 결론("매우 견고한 릴리스가 될 것")은 프로젝트 입장의 발언이다. ④ 반대로, 출시 후 5년간 하나씩 나왔을 버그를 출시 전에 잡았다면 **장기적으로는 순이익**이라는 해석도 충분히 가능하다 — 한 달 지연의 비용과 5년간의 핫픽스 비용을 같은 단위로 비교한 사람은 아직 없다.

### 2. Claude Code 팀의 코드 리뷰 — "사람이 읽었나"를 빼고 "무엇이 잘못될 수 있나"를 묻는다

**무슨 일인가.** Anthropic(claude.dev 블로그)이 Claude Code 팀의 리뷰 체계를 공개했다. HN 217점에 댓글 202개(포인트 대비 댓글이 많은 논쟁 스레드). 전제 수치: Claude Code 코드의 약 90%를 Claude가 쓰고, 6~9월 머지 PR은 두 배 넘게 늘었으며 revert 비율은 40% 넘게 줄었다. 목표는 "대부분의 PR이 **사람 1명 이하**로 머지되면서 revert·장애는 늘지 않는 것". 추적 지표는 PR당 사람 승인 수(중앙값·95분위), 사람 코멘트 수, PR이 사람을 기다린 시간이고, **revert율과 장애율이 가드레일**이다 — 이게 오르면 사람 시간을 아낀 게 아니라 옮긴 것일 뿐이라는 기준이다.

**배경.** 10/14 노트에서 본 Scion(하루 머지 3만 건+)이 이 글의 하부 구조다. 변경량이 12배가 되면 "모든 PR을 사람이 읽는다"는 물리적으로 불가능하다. 그래서 질문을 바꿨다 — **"사람이 코드를 읽었나?"는 부정확한 대리 지표**이고, 진짜 질문은 "이 변경에서 무엇이 잘못될 수 있고, 그걸 잡는 체크는 자동인가 사람인가"다.

**어떻게 동작하나 — 층별 구조.**

| 층 | 내용 | 볼 점 |
| --- | --- | --- |
| ① PR 전 검증 | Claude가 테스트·빌드·린터를 돌리고 **출력을 제시**(성공 주장 금지), 서브에이전트가 새 컨텍스트로 diff 재검토 | Boris Cherny 추정: 검증 수단을 주면 결과 2~3배 |
| ② 모든 PR에 AI 리뷰 | 여러 에이전트가 병렬로 버그 탐색 → **별도 투표 그룹이 각 발견에 투표**해 충분히 동의한 것만 게시. 스타일·정리 지적은 버림. Important / Nit / **Pre-existing** 태그. 저장소별 Quick/Standard/Deep | 연구 프리뷰 때 실질 코멘트가 붙은 내부 PR 16% → 54% |
| ③ 보안 리뷰 | 버그·보안 리뷰의 열린 발견은 머지 차단, 이후 커밋이 고치면 자동 해제 | |
| ④ 필수 CI | 린트·타입·전 플랫폼 테스트·빌드. PR 템플릿이 테스트 내역과 **revert 계획**을 요구 | |
| ⑤ 위험도 기반 사람 승인 | 아래 표 | |
| ⑥ 머지 큐·플래그·점진 배포 | 큐가 main 위에서 다시 검사, 신기능은 플래그 뒤 사내 → latest → stable | |
| ⑦ 빠른 감지·롤백 | 배포 없이 플래그 끄기, 주간 온콜, 장애 리뷰에서 "어느 층이 잡았어야 했나" | |

위험도 등급:

| 등급 | 예 | 사람 승인 |
| --- | --- | --- |
| Low | 문서·문구·내부 전용 기능·플래그 뒤 추가 변경 | 0명(자동·보안 검사 통과 시) |
| Medium | 일반 제품 변경, 캐싱·자동 업데이트·시스템 프롬프트 같은 민감 영역 | 1명 |
| High | 최고 위험 코드, 항상 2명이 필요한 경로 | 2명 |

규칙: **등급은 작성자가 아니라 변경 내용이 정한다.** 분류기 하나가 등급을, 두 번째 분류기가 "등급과 무관하게 사람이 필요한가"를 본다. 소유자가 지정한 민감 경로와 **CI 워크플로 파일은 항상 사람**. 가벼운 경로는 신뢰된 작성자(주로 소유 팀)만. **에이전트의 승인은 절대 사람 승인으로 세지 않는다.** 에이전트가 쓴 PR에서는 프롬프트를 준 사람이 필수 리뷰어. 승인은 **특정 커밋 하나**에 대한 것이라, 에이전트 push나 손으로 푼 머지처럼 시스템이 보증 못 하는 새 커밋은 재승인이 필요하다.

**리뷰어를 리뷰하는 법.** ① 과거 장애·revert PR과 그 수정을 모아, 코드를 아는 엔지니어가 버그와 위치를 확인한 **eval 셋**을 만든다. 리뷰어를 매일 여기에 채점하고, 프롬프트·툴·모델 변경은 **점수가 오를 때만** 채택한다. ② 노이즈 측정 — 리뷰어 코멘트를 작성자 반응(고침/틀림/의도됨/상관없음)으로 분류하고, **깨끗한 PR에도 돌려** 해로운 변경을 유도하는 지적 빈도를 센다. 우선순위는 "진짜 버그 잡기"가 먼저, "라운드 줄이기"가 두 번째로 명문화.

**50라운드 사고와 수렴 규칙.** 한 CLI PR이 밤새 리뷰-수정을 50번 넘게 돌다 작성자가 멈췄다. git blame 결과 리뷰어 지적의 약 59%는 첫 패스부터 있던 것 — 매 라운드가 **새 버그가 아니라 옛 버그를 조금씩 더** 찾고 있었다. 기본값으로 여러 라운드를 돌게 해 둔 것도 화를 키웠다. 처방 넷: 3라운드 후 접근 재고 요청, 몇 패스 후엔 diff만 재리뷰, 버그 클래스 단위로 지적(작성자가 모든 인스턴스를 한 번에 고치게), 이미 단 지적 반복 금지. 결과: 1라운드 통과 65→78%, 5라운드 이상 8.9→1.5%, 평균 리뷰 횟수 2.08→1.32. 기존 코드의 옛 버그는 **야간 전체 리뷰**로 따로 잡는다.

**CLAUDE.md와 REVIEW.md.** CLAUDE.md는 스택·컨벤션·목표·**비목표**를 짧게, 모든 리뷰가 로드한다. REVIEW.md는 코드 오너가 "이 영역에서 실패는 어떤 모습인가"(문서는 "거짓말한다", 설정은 "잘못 라우팅한다")를 쓰고, nit 상한·건너뛸 경로·**파일과 줄 번호를 증거로 요구**·요약은 발견 개수로 시작하고 없으면 "없음"이라고 명시.

**실무에 무슨 의미인가.**

- **WMS 팀 프로젝트의 PR 규칙으로 번역할 수 있다.** "재고 차감·동시성 락·결제성 로직 = High(2명)", "일반 API = Medium(1명)", "문서·테스트 데이터 = Low(셀프 머지)"처럼 **경로 기반** 등급을 CODEOWNERS와 브랜치 보호 규칙으로 걸 수 있다. "왜 이 PR은 두 명이 봐야 하나"를 설명할 어휘가 생긴다.
- **승인은 커밋 단위.** GitHub의 "Dismiss stale pull request approvals when new commits are pushed" 옵션이 정확히 이 규칙이다.
- **검증 수단을 먼저 준다.** 에이전트에게 Spring 작업을 맡길 때 `./gradlew test`·로컬 기동 확인 명령·대표 curl 요청을 CLAUDE.md에 적어 두는 것이 프롬프트 문장을 다듬는 것보다 효과가 크다는 게 이 글의 추정이다.
- **장애에서 eval을 만든다.** 내 프로젝트에서 실제로 났던 버그(예: 트랜잭션 커밋 전 메시지 발행 — 10/15 포인트 전환기 글)를 모아 두면, 어떤 리뷰 도구·프롬프트든 "이걸 잡나"로 비교할 수 있다.

**반론·회의적 시각.** ① 모든 지표(revert −40%, 통과율 65→78%)가 **자체 보고**다. revert율 감소가 품질 향상 때문인지, PR이 작아지고 플래그 뒤로 숨겨져 revert가 필요 없어진 것인지 분리되지 않는다. ② 90%를 AI가 쓰는 코드베이스, 그 AI를 만든 회사의 프로세스를 일반 조직에 옮길 수 있나는 HN 최다 반론이다. ③ 팀이 스스로 인정한 공백 — **서킷 브레이커가 없다**(revert·장애가 오를 때 승인 요건을 자동으로 조이는 장치), **감지는 여전히 사람에 의존**, 에이전트 작성자에게 노이즈는 사람보다 비싸다(사람은 nit을 몇 초에 무시, 에이전트는 커밋과 라운드를 하나 더). ④ "천천히 하면 오류가 줄지만 그건 주로 산출을 줄여서"라며 감속을 답으로 보지 않는데, 이건 Postgres가 고른 길(기능을 빼서 범위 축소)과 정반대다. 어느 쪽이 맞는지는 조직의 실패 비용에 달렸다 — DB 엔진의 데이터 손상 버그와 CLI 도구의 UI 버그는 되돌리기 비용이 다르다.

### 3. NIST 타원곡선 시드의 출처 — 해시가 아니라 1997년 시계로 시딩한 lrand48

**무슨 일인가.** Anthropic 연구 글(10월, 저자 10명)이 ECDSA의 NIST 곡선 시드 출처를 공개했다. 내부 연구 모델에게 **패스프레이즈 단서 없이** 시드 생성 방식을 추론하게 했더니 30분이 안 걸렸다. HN 636점·댓글 260개.

**배경.** NIST는 2000년 FIPS 186-2로 ECDSA 곡선을 채택했다. 곡선 계수 *b*는 "시드"를 해시해 정하는데, NSA는 시드가 어디서 왔는지 설명하지 않았다(예: P-256 시드 `C49D3608 86E70493 6A6678E1 139D26B7 819F7E90`). 출처를 모른다는 것 자체가 25년간 백도어 의혹을 키웠다 — 2013년 Dual_EC_DRBG 백도어 폭로 이후 특히. 2015년 Koblitz·Menezes 「A Riddle Wrapped in an Enigma」가 논란을 정리했고, Filippo Valsorda가 조직한 현상금($36,864)이 걸렸다. 가장 유력하던 "농담 섞인 패스프레이즈의 해시"(Jerry Solinas의 2015년 이야기)는 **틀린 설명**이었다. Solinas는 2023년 사망했다.

**기술적으로 어떻게 풀었나.**

1. **가설 전환.** 해시 가설을 버리고 "1990년대 C 라이브러리의 약한 PRNG가 썼고, 출력에 알아볼 수 있는 흔적이 남았을 것"에서 출발.
2. **스캐너.** 각 시드를 한 비트씩 밀면서 인접 조각이 어떤 생성기의 **연속 출력**인지 검사하는 코드를 작성 — 생성기 × 출력 슬라이스 34가지 조합.
3. **통계적 지문.** 시드 10개 중 4개(이진곡선)가 32비트 워드 20개 **전부의 최상위 비트가 0**. 우연 확률 약 1/5,810. 48비트 상태에서 상위 31비트만 돌려주는 `lrand48`의 특징이다.
4. **상태 복원(이진곡선).** 첫 워드의 숨은 17비트를 2^17가지 전수조사하고, 다음 네 워드가 맞는지 확인 — 네 개 모두 성공.
5. **상태 복원(소수곡선).** 이쪽은 `lrand48() >> 23`처럼 출력마다 남은 비트가 더 적어 전수조사가 안 된다. **LLL 격자 기저 축소**로 상태를 복원(선형 합동 생성기의 잘린 출력 → 짧은 벡터 문제로 바꾸는 고전 기법). NIST 소수 시드 5개 + ANSI X9.62 시드 5개가 같은 패턴. 복원한 상태가 각 시드의 **160비트 전체**를 재생성.
6. **역추적.** `lrand48`은 거꾸로도 쉽게 돌 수 있어, 상태를 `srand48`이 만드는 형태(하위 16비트 `0x330E`)까지 되감았다. (이 형태는 65,536 스텝마다 반복되므로 이것만으로 증명은 아니라고 글이 명시.) 그 시드 값이 **유닉스 타임스탬프**였다.

찾은 시각: 소수곡선 10개는 1997년 5월~1998년 4월. P-192 등은 1997-05-18 14:45:34, **P-256은 1997-08-16 01:52:34**(1,842번째 후보), P-224는 1998-04-03(7,026번째 후보). 이진곡선은 1984년 2월로 읽히는데, 두 배 하면 1998-04-17 — 프로그램이 시계를 반으로 나눴을 가능성. 덤으로 기점(base point) 6개(P-192와 ANSI 곡선 일부)는 Arjen Lenstra의 FreeLIP 난수 생성기(초기 NTL에도 포함)로 설명됐다 — **NIST 기점이 설명된 건 처음**이라고 한다.

**실무에 무슨 의미인가.**

- **보안 측면: 할 일 없다.** 이건 ECDSA의 취약점이 아니라 그 반대 — 시드가 "단순하고 재현 가능한 과정"에서 나왔으니 의도적 백도어 가능성이 낮아졌다. Spring Security·JWT에서 ES256(P-256)을 쓰고 있다면 그대로 써도 된다.
- **반면교사: `lrand48`·`java.util.Random`·`Math.random()`은 비밀이 아니다.** 선형 합동 생성기는 출력 몇 개로 상태가 복원된다. Java의 `java.util.Random`도 48비트 LCG(`lrand48`과 같은 상수 0x5DEECE66D)라 토큰·임시 비밀번호·세션 ID 생성에 쓰면 안 된다 — `SecureRandom`을 써야 하는 이유가 이 사건에 그대로 보인다.
- **방법론.** "가설 → 스캐너 작성 → 통계적 지문 → 격자 축소로 상태 복원"은 사람이 하면 몇 주 걸릴 탐색이다. 그런데 이 문제는 **답을 기계가 확인할 수 있다**(복원한 상태가 160비트를 정확히 재생성하는가). 정답 확인이 싸고 확실한 문제일수록 탐색을 AI에 넘기기 좋다 — 10/13 노트의 역컴파일과 같은 조건.

**반론·회의적 시각.** ① HN 최다 의견: "원래 대부분의 암호학자는 이 곡선을 신뢰했다" — 미스터리 해결이 실제 신뢰 수준을 크게 바꾸지 않는다. ② 남은 공백: 이진 시드 B-163은 어떤 패턴에도 안 맞고, P-224/256/384/521과 NIST 이진곡선의 기점은 미설명. ③ **건너뛴 후보**가 있다 — P-256에서 876번째 후보도 유효한 소수 차수 곡선이었는데 선택되지 않았고, P-224는 3개, ANSI 두 런은 7개를 건너뛰었다. 기준은 모른다. 저자들은 "약한 곡선이 흔해야 그런 선별이 가능하니 개연성이 낮다"고 보지만, **타임스탬프 자체를 여러 번 돌려 골랐을 가능성**은 원리적으로 남고 몇 번 돌렸는지는 알 수 없다고 인정한다. ④ "30분"은 모델이 혼자 일한 시간이고, 이후 검증·글쓰기는 저자 10명의 작업이다. 다만 검증은 공개된 Python 코드로 누구나 재현 가능하다는 점이 이 결과의 힘이다.

### 4. 미국 근로시간의 90%는 벤치마크가 거의 재지 않는 업무 — Mercor 벤치마크 지도

**무슨 일인가.** Mercor가 미국 노동부 O*NET 분류(직업 923개·직군 22개·세부 업무 18,797개)에 현존 AI 벤치마크를 겹쳐 지도로 그렸다. HN 382점·댓글 324개.

**어떻게 쟀나.**

1. **벤치마크 29개 선정** — 공개 태스크 25개 이상(+자사 APEX의 비공개 홀드아웃), 질문 답변이 아니라 **행동하는** 에이전틱 과제, 경제적 현실성, 직군별 상한(SWE·연구 과대 대표 방지), 프런티어 모델이 아직 포화 안 됨.
2. **태깅** — LLM 심판이 각 프롬프트를 그럴듯하게 맞는 O*NET 업무 전부에 태깅(APEX에서 전문가 태깅과 대조 검증).
3. **커버 기준** — 한 업무에 프롬프트 **5개 이상**이면 "커버됨".
4. **시간 가중** — LLM이 추정한 업무별 근로시간 비중을 곱함.

**결과.** 커버된 업무 924/18,797. 커버된 업무가 하나라도 있는 직업 208/923(약 23%), 22개 직군 중 6개는 0. 컴퓨터·수학 29/36, 비즈니스·금융 33/48, 법률 5/7 대 의료 실무자 12/89, 영업 6/22. AI 노출도 높은 업무가 약 **6배** 더 커버되고, 노출도를 통제해도 **임금 총액이 큰 직업**이 과대 대표된다(변호사는 두텁고, 노출도가 비슷한 법률 비서·법원 서기는 거의 빈칸). 직업 안에서도 가장 중요한 업무가 가장 덜 중요한 업무보다 6~10배 더 커버. O*NET 가중 점수 실험(투자은행 11개 업무·176 프롬프트)에서 Claude Opus 5.5 Max는 단순 평균 73.3% 대 가중 70.2%로 큰 차이는 없었지만, 가중 점수에 넣을 만큼 프롬프트가 있는 업무는 3분의 1도 안 됐다.

**실무에 무슨 의미인가.** 벤치마크 점수를 읽는 법이 바뀐다. ### 5. PostgreSQL 무중단 스키마 변경 — "DB가 안 죽었다"가 아니라 "구·신 버전이 동시에 돈다"

**무슨 일인가.** boundlayer.io의 실무 가이드. 브리핑이 "오늘 당장 써먹을 게 가장 많은 글"로 꼽았다. 1번(Postgres 19)과 같은 DB지만 방향은 반대 — 1번이 "엔진 쪽 변경을 얼마나 신중히 내보내나"라면, 이건 "**애플리케이션 쪽 스키마 변경**을 어떻게 안전하게 내보내나"다.

**무중단의 정의.** 문자 그대로 락이 0인 게 아니라, 락 획득을 빠르게 하고 영향을 묶어 두는 것. 성공 기준: 에러율 무증가, p95/p99 지연 한도 내, 핵심 쓰기 지속, 복제 지연 한정, 데이터 손실·손상 없음, **구·신 앱 버전이 배포 중 모두 동작**, 안전하게 멈추거나 되돌릴 경로.

**어떻게 하나 — 핵심 절차.**

- **Expand-contract 5단계:** 확장(구 코드를 깨지 않고 새 스키마 추가) → 이주(백필+두 표현 모두 지원) → 전환(읽기·쓰기를 새 표현으로) → 검증(프로덕션 한 주기 이상) → 축소(구 코드·컬럼·인덱스 제거, **담당자와 날짜를 미리 지정**). 축소 날짜가 없으면 임시 컬럼과 이중 쓰기가 영구 구조가 된다.
- **락 큐가 진짜 위험.** 많은 `ALTER TABLE`이 `ACCESS EXCLUSIVE` 락을 잡는다. 더 무서운 건 마이그레이션이 **긴 트랜잭션 뒤에 줄을 서는 순간** 그 뒤로 모든 일반 쿼리가 줄을 선다는 것 — DDL이 실행되기도 전에 장애가 시작된다. 처방: `SET lock_timeout = '2s'; SET statement_timeout = '15s';`(예시값, 워크로드마다 다름)로 빨리 실패하고, 통제된 창에서 제한된 지연으로 재시도. 타임아웃을 늘리는 건 답이 아니다. 먼저 블로커를 본다 — idle-in-transaction 세션이 진짜 결함일 수 있다.
- **NOT NULL 7단계:** nullable 추가 → 쓰기 코드 배포 → 작은 배치 백필 → NULL 없음 확인 → `CHECK ... NOT VALID` 추가 후 별도 트랜잭션에서 `VALIDATE CONSTRAINT` → NOT NULL 적용 → 호환 로직 제거. 컬럼 DEFAULT는 컬럼을 **생략**할 때만 적용되므로 쓰기 쪽이 명시적 NULL을 넣는지 확인.
- **인덱스:** 큰 테이블엔 `CREATE INDEX CONCURRENTLY` — 트랜잭션 블록 안에서 못 돌고, 실패하면 **무효 인덱스**가 남으니 확인 후 제거·재생성.
- **컬럼 이름 변경은 여러 릴리스에 걸친다:** 새 컬럼 추가 → 이중 쓰기 → 백필 → 읽기 전환 → 구 쓰기 중단 → 별도 마이그레이션으로 구 컬럼 삭제.
- **백필:** 키 기준 1,000행 배치 + `FOR UPDATE SKIP LOCKED`, 멱등·재개 가능·체크포인트, 지표 악화 시 자동 정지, WAL·복제 지연·dead tuple 감시, OFFSET 페이지네이션 금지.
- **시작 시 자동 마이그레이션 금지:** 레플리카 여러 개가 경쟁하고, 위험한 마이그레이션이 서비스 복구 경로에 묶인다. 명시적 릴리스 단계로 돌릴 것.
- **검증:** "남은 행 0"이 성공이 아니다. **비즈니스 불변식**을 대조하고, 구 스키마를 쓰는 미지의 소비자가 없는지 확인한 뒤에야 축소.

**실무에 무슨 의미인가.** Spring Boot + Flyway(또는 Liquibase)의 **기본 동작이 바로 "시작 시 자동 마이그레이션"**이다(`spring.flyway.enabled=true`면 애플리케이션 컨텍스트 기동 중 실행). 레플리카가 여러 대면 Flyway의 스키마 히스토리 테이블 락이 경쟁을 막아 주긴 하지만, "마이그레이션 실패 = 앱 기동 실패 = 롤백 불가" 구조는 그대로다. 대안은 배포 파이프라인에서 `flyway migrate`를 별도 단계(K8s Job 등)로 돌리고 앱에서는 `spring.flyway.enabled=false`. 또 Flyway는 기본으로 각 마이그레이션을 트랜잭션 안에서 돌리므로 `CREATE INDEX CONCURRENTLY`는 그 파일에서 트랜잭션을 꺼야 한다(Flyway의 스크립트별 설정). JPA의 `ddl-auto=update`는 이 모든 절차를 건너뛰는 지름길이라 운영에선 쓰지 않는 이유가 여기서 구체적으로 보인다.

**반론·회의적 시각.** ① 5단계·여러 릴리스는 **작은 팀에겐 과한 비용**이다. 사용자가 적고 점검 창을 잡을 수 있으면 짧은 다운타임이 더 싸고 안전할 수 있다 — 무중단은 요구사항이지 미덕이 아니다. ② PG 버전에 따라 일부 절차가 단순해졌다(예: 11부터 비휘발성 DEFAULT 컬럼 추가는 테이블 재작성 없음, 최근 버전은 검증된 CHECK 제약을 근거로 NOT NULL 스캔 생략). 글도 "버전이 지원하는 가장 안전한 형태"라고만 적어 버전별 차이는 직접 확인해야 한다. ③ 회사 블로그(boundlayer)의 콘텐츠 마케팅 성격 — 다만 내용은 Postgres 공식 문서·잘 알려진 운영 관행과 어긋나지 않는다.

## 배경

글은 정산시스템 내부 어드민에 엑셀 다운로드 기능이 50개 넘게 있었고, 새로 만드는 매입시스템도 엑셀 다운로드가 많이 필요할 예정이었다고 설명한다. POI를 그대로 쓰면 셀마다 값을 하나씩 넣어야 해 실수(헤더 이름을 엉뚱한 셀에 넣기, rating 자리에 price 넣기)가 잦고 컬럼이 늘 때마다 반복 코드가 붙는다. 정산시스템에 있던 "일부 추상화" 방식(Column Enum + ExcelColumnInfo 구현체 + 기능별 ExcelView)도 기능마다 구현체·뷰가 늘어나고 스타일 추상화가 없어 컬럼별 스타일 변경이 공유 코드 수정이나 중복으로 이어졌다. 목표는 "데이터를 반환하는 API와 크게 다르지 않은 형태"로 엑셀 다운로드를 만드는 것이었다.

## 핵심

- **문제 → 결정(선언형 매핑)**: JPA의 `@Column`처럼 DTO 필드에 `@ExcelColumn(headerName=...)`을 달고, 리플렉션으로 필드를 읽어 헤더·바디를 자동으로 그린다. 리플렉션 예외는 메타데이터에서 검증된 필드만 다루므로 실제로 일어날 수 없다고 보고 RuntimeException으로 치환한다.
- **워크북 구현체**: `SXSSFWorkbook`(스트리밍) 선택. 시트당 최대 약 100만 행(Excel 2007+) 한계 때문에 처음엔 100만 행 이하만 허용하고, 이후 다중 시트로 확장한다.
- **스타일 = 전략 패턴**: `ExcelCellStyle` 인터페이스(`apply` 하나). 사용자가 POI `CellStyle`을 직접 다뤄야 하는 부담을 줄이려 배경색 등을 추상화하고, Spring Security 설정 방식을 본떠 `CustomExcelCellStyle` + `ExcelCellStyleConfigurer`로 체이닝 설정을 만든다.
- **어노테이션 과밀 해결**: 필드마다 헤더/바디 스타일을 달면 DTO가 지저분해지므로 클래스 레벨 `@DefaultHeaderStyle`·`@DefaultBodyStyle`을 두고, 필드에 지정이 없으면 클래스 기본값을 쓴다.
- **책임 분리**: 메타데이터 "보관"과 "어노테이션 파싱"이 한 객체에 섞여 있던 `SimpleExcelMetaData`에서 파싱을 팩토리로 분리. 팩토리 덕에 DTO별 메타데이터를 최초 1회만 추출해 캐싱할 여지가 생긴다(글은 구현은 안 했다고 밝힌다).
- **데이터 포맷**: '통화' 형식 등도 어노테이션으로 달면 다시 과밀해지므로 타입별로 포맷을 정하는 `DataFormatDecider` 전략을 두고 `DefaultDataFormatDecider`를 기본값으로 넣는다.
- **파일 종류 확장 = 템플릿 메서드**: 추상 `SXSSFExcelFile`(write(stream) 인터페이스 + 훅 메서드 + 헤더/바디 공통 메서드) 아래 `OneSheetExcelFile`·`MultiSheetExcelFile`.
- **측정(jstat)**: 1,000셀(100건×10필드)은 기존 getter 방식 최대 힙 310MB·1.657초 대 신규 330MB·1.683초. 1,000만 셀(100만건×10필드, Xms 1GB/Xmx 2GB)은 둘 다 최대 810MB, 16.429초 대 19.804초. 글은 "쿼리 10초+렌더링 3초 → 3.6초" 정도의 비용이고 리플렉션 객체로 GC가 잦아진다고 정리한다.
- **반려하지 않고 나눠 쓴 결론**: 요청이 많고 데이터가 적은 건은 신규 모듈, 대용량·성능 중시 건은 기존 getter 방식. 메모리 피크가 문제면 두 방식 모두 쿼리 결과를 조금씩 나눠 넣는다. "Common case는 단순하고 빠르게, uncommon case는 복잡하고 느려도 된다" — 내부 어드민·통계용이라 개발 속도를 택했고, 다수 일반 사용자 동시 다운로드라면 클라이언트 렌더링 등 다른 방법이 필요하다고 단서를 단다.

## 내 프로젝트와의 연결

WMS에는 재고 현황·입출고 이력·피킹 리스트처럼 "관리자가 엑셀로 뽑아 보는" 화면이 자연스럽게 생기므로, 글은 그 내보내기 기능을 DTO 어노테이션 하나로 찍어내는 구조로 읽을 수 있다. 다만 글의 측정이 보여주듯 대용량(입출고 이력 전체 등)에서는 리플렉션 비용과 메모리 피크가 생기므로, WMS 부하 테스트 항목에 "엑셀 다운로드 시 힙·소요 시간"을 넣고 페이징/청크 조회와 묶는 지점이 구조적으로 겹친다. 수집기와는 직접 연결이 약하고, 수집 결과를 SQLite에서 CSV/엑셀로 내보내는 리포트를 만든다면 "필드 선언 → 자동 직렬화"라는 같은 발상만 옮겨올 수 있다.

## 오늘 정리할 것

1. GitHub `lannstark/excel-download`에서 `@ExcelColumn`·`ExcelRenderResource(Factory)`·`SXSSFExcelFile` 세 파일을 열어 리플렉션 호출 지점과 메타데이터 생성 시점을 표로 정리한다.
2. `XSSFWorkbook`과 `SXSSFWorkbook`의 차이(윈도우 크기, 임시 파일, `dispose()`)를 POI 문서에서 확인해 메모 한 단락으로 남긴다.
3. 전략 패턴(ExcelCellStyle·DataFormatDecider)과 템플릿 메서드 패턴(SXSSFExcelFile 계층)이 각각 무엇을 갈아끼우는지 한 줄씩 구분해 적는다.
4. WMS 재고 현황 DTO를 하나 가정해 어떤 필드에 헤더·통화 포맷이 필요한지 적어 보고, 100만 행 이상일 때 청크 조회를 어디서 끊을지 메모한다.

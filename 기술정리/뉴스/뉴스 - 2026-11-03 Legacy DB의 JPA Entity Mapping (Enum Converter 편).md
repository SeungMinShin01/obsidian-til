이은경(우아한형제들 비즈상품개발팀) · 2019-01-09 · Backend. 예습자료 — 글의 설명을 정리한 것이며 사용자 미검증.

## 배경

글은 광고 시스템의 모든 상태값이 DB 코드 테이블의 코드값('0', '1', '2' …)으로 저장돼 있었다고 설명한다. 코드만으로는 의미를 알 수 없어서 새 사람이나 오랜만에 테이블을 보는 사람은 매번 코드 조회 페이지에서 값을 확인해야 했다. 기존 소스와 DB의 코드를 'REQUEST', 'PROGRESS', 'CANCELED' 같은 문자열로 일괄 변경하는 것은 불가능했기 때문에, 글은 DB에는 기존 코드값을 두고 Java에서만 Enum으로 다루는 방식을 택했다고 말한다.

## 핵심

- 글은 JPA `AttributeConverter`로 해결했다고 설명한다. 엔티티 필드를 Enum으로 선언하고 `@Convert(converter = …)`를 붙인다.
- 컨버터는 `convertToDatabaseColumn`(Enum → DB값)과 `convertToEntityAttribute`(DB값 → Enum)를 구현하고, Enum에는 레거시 코드로 Enum을 찾는 메서드(`ofLegacyCode`)를 둔다.
- 문제: 코드 종류마다 컨버터가 생겨 42개까지 늘었고 모두 같은 코드를 반복했다. Enum마다 `ofLegacyCode`도 중복됐다.
- 개선: 각 Enum이 공통 인터페이스 `LegacyCommonType`(공통 getter)을 구현하고, 코드로 Enum을 찾는 로직은 util 클래스의 static 메서드로 모았다. 모든 컨버터는 `AbstractLegacyEnumAttributeConverter`를 상속만 하며, 생성자에서 null 허용 여부(기존 DB에 null이 아니라 blank가 들어 있는 경우 처리)와 Enum 이름(로그·에러 메시지용)만 지정한다.
- 비용: 코드 종류 수만큼 Enum + Converter 클래스를 만들어야 하는 수고는 남는다. 글은 Java에서 문자열 코드로 헷갈리지 않고, 기존 DB 값과 레거시 코드를 모두 바꾸지 않아도 된다는 장점이 더 크다고 본다.
- 실수 사례: DB에 암호화되어 저장되는 항목의 암·복호화를 컨버터에 넣었다. 컨버터는 엔티티를 매핑할 때마다 무조건 실행되므로, 그 필드를 안 쓰는 목록 화면(20건)에서도 복호화 API 호출이 20번 일어났다. API 통신이 실패하면 엔티티 매핑이 실패해 목록이 나오지 않았다.
- 교훈: util 클래스와 컨버터는 외부와 통신하거나 외부 영향을 받지 않는 순수한 로직이어야 한다고 글은 정리한다.

문제 → 시도 → 결과 흐름으로 보면: 코드값 가독성 문제 → 코드 일괄 변경 대신 컨버터 도입(반려한 대안: DB·소스 전체 치환) → 컨버터·`ofLegacyCode` 중복 → 추상 컨버터 + 공통 인터페이스로 통합 → 컨버터에 암복호화 API 호출을 넣었다가 목록 성능·장애 전파 문제 → "컨버터는 순수해야 한다"로 정리.

## 내 프로젝트와의 연결

WMS의 입고·재고·출고 상태(입고예정/검수중/적치완료, 출고 지시/피킹/완료 등)를 Enum으로 다룰 때 `@Enumerated(STRING)`과 `AttributeConverter` 중 무엇을 쓸지 고르게 된다. 이 글은 레거시 코드값을 유지해야 하는 경우라서 새로 만드는 WMS와 직접 연결은 약하다. 구조적으로 비슷한 지점은 두 가지다. Enum ↔ DB 값 매핑을 공통 인터페이스 + 추상 컨버터로 한 곳에 모으는 방식, 그리고 매핑 계층에 외부 호출 같은 부수효과를 넣지 말라는 교훈이다. 후자는 수집기에서 SQLite 저장·조회 단계에 무거운 변환이나 외부 호출을 섞지 않는 원칙과 같은 맥락이다.

## 오늘 정리할 것

- [ ] `@Enumerated(ORDINAL)`, `@Enumerated(STRING)`, `AttributeConverter`를 비교해, Enum 순서 변경·값 추가 시 각각 어떻게 깨지는지 표로 정리한다.
- [ ] 상태값 Enum 하나(예: 입고 상태)를 골라 공통 인터페이스(`getCode`) + 추상 컨버터 구조를 스케치하고, `@Converter(autoApply = true)`와 필드별 `@Convert`의 차이를 적는다.
- [ ] 로그를 찍는 컨버터를 만들어, 목록 조회 한 번에 컨버터가 몇 번 호출되는지 직접 센다(엔티티 로딩 시마다 실행된다는 글의 주장 확인).
- [ ] 수집기·WMS 저장 계층에 "매핑 단계에서 외부 호출이나 무거운 연산을 하는 곳"이 있는지 훑어본다.

## 깊게 본 것

### 1. Lovable 앱 2.4만 곳의 DB 노출 — "프런트가 DB를 직접 부르면, DB 정책이 곧 인가 로직"

**무슨 일인가.** 독일 보안 회사 Crissy Field가 Handelsblatt와 함께 조사(1차 보도 2026-11-02, 오늘 영문 보고서는 수치를 갱신한 판, 전문 읽음). Common Crawl에서 **Lovable 프로젝트 159,041개**(2025-12 ~ 2026-09)를 찾았고, 그중 Supabase 사용 34,545개. **24,664개 사이트가 페이지 로드만으로 로그인 없이 Supabase 레코드를 전송**했다 — 저자들은 이것 자체는 "공개 표시용일 수 있어 문제 아님"이라고 선을 긋는다. 문제는 그다음: **같은 API 키로 읽기 요청을 더 던지자** 7,403개 사이트(30%)의 10,560개 테이블에서 이메일 주소가 든 레코드가 나왔다. 사례: 독일 라이프스타일 포럼 프로필 8만+·채팅 20만+, 행사·식당의 티켓·음식 판매 기록 수만 건(전화·주소·결제 정보·티켓 코드), 부동산 관리사의 **내부 이메일 AI 요약**, 신분증 기록 1,000+(여권 번호·만료일·국적), 계약서·청구서·사진첩·WhatsApp 대화, 고객에게 보낸 이메일 28만 건.

**배경 — 왜 지금인가.** Lovable 마케팅은 "기술 지식이 필요 없다"를 반복하지만 약관은 앱·데이터 처리 책임을 고객에게 둔다. 보고서의 표현으로 "쉬운 올인원 서비스라는 약속과 고객이 져야 할 책임 사이의 간극". 그리고 Supabase 쪽 사정이 있다(공지 전문 읽음): 원래 Supabase는 프로젝트를 만들면 `public` 스키마의 **모든 테이블에 `anon`·`authenticated`·`service_role` 롤의 SELECT/INSERT/UPDATE/DELETE를 자동 GRANT**했다. 테이블을 만드는 순간 Data API(PostgREST, `supabase-js`가 부르는 것)로 닿는다. 막는 장치는 RLS(행 수준 보안)뿐이고, 그건 사람이 켜야 했다. Supabase는 이걸 바꿨다 — 2026-05-30 신규 프로젝트 기본값, **2026-10-30 기존 프로젝트 전체 적용**. 그런데 **이미 있는 테이블은 기존 GRANT를 유지한다**("running app stays reachable"). 즉 이번 조사 구간(~2026-09)에 만들어진 노출 테이블은 10/30 이후에도 **그대로 열려 있을 수 있다.** 기본값 개편은 앞으로 만들 테이블만 지킨다.

**기술적으로 어떻게 동작하나.** 구조를 Spring과 나란히 놓으면 선명하다.

| | 전통적 백엔드(Spring) | BaaS 직결(Supabase Data API) |
| --- | --- | --- |
| 브라우저가 부르는 것 | 내 서버의 API(`/api/orders`) | DB 앞의 자동 생성 REST(`/rest/v1/orders`) |
| 브라우저가 가진 키 | 세션 쿠키·JWT(사용자별) | **anon 키(모든 방문자 공통, 프런트 번들에 공개)** |
| 인가를 어디서 하나 | 컨트롤러·서비스·Spring Security | **Postgres GRANT(테이블 단위) + RLS 정책(행 단위)** |
| 한 겹을 빠뜨리면 | 그 엔드포인트만 샌다 | **테이블 전체가 anon에게 열린다** |

Supabase 공지가 정리한 세 단계가 "한 묶음"이다: ① 롤별 `GRANT` ② `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` ③ `CREATE POLICY ... USING (auth.uid() = user_id)`. 예전 기본값에서는 ①이 자동이라 ②③을 잊으면 끝이었다. 보고서가 짚은 또 하나의 위험: **Lovable 앱의 DB 연동이 반복 패턴을 따르므로**, 한 앱에서 통한 접근이 거의 그대로 다른 앱에도 통한다 — 공격 비용이 앱 수에 비례하지 않는다.

**실무에 무슨 의미인가.**

- **"인증(누구냐)"과 "인가(무엇을 볼 수 있냐)"는 다른 층이다.** 로그인 화면이 있다는 것은 인증이 있다는 뜻일 뿐이다. Spring Security에서도 `authenticated()`만 걸고 `/orders/{id}`에서 소유자 확인을 빠뜨리면 같은 구멍(IDOR)이다. Supabase는 그 구멍이 "엔드포인트 하나"가 아니라 "테이블 전체"라 커질 뿐.
- **Supabase를 쓴다면 지금 할 일**: 테이블별로 `anon` 롤에 GRANT가 있는지(Security Advisor·Data API 노출 배지), RLS가 켜져 있는지, 그리고 **anon 키로 직접 `curl`을 쳐서** 무엇이 돌아오는지 확인. 10/30 기본값 변경이 기존 테이블을 고쳐 주지 않는다는 점이 핵심.
- **에이전트에게 테이블을 만들게 한다면**: Supabase는 아예 "AI 코딩 도구의 시스템 프롬프트를 고치거나 GRANT 단계를 포함한 agent skill을 써라"라고 권한다. 마이그레이션에 GRANT·RLS·POLICY를 **같은 파일에** 묶는 것을 규칙으로.
- 11/8 노트(공개 저장소에서 Supabase service-role 키 122개)와 이어 보면, 키를 숨기는 문제와 키가 공개돼도 안전하게 만드는 문제는 **서로 다른 문제**다. anon 키는 원래 공개용이다 — 지켜야 하는 건 정책이다.

**반론·회의적 시각.** 저자들 스스로 길게 단서를 달았다: ① 30%는 **확정 유출률이 아니다**(이메일이 공개 연락처·테스트 데이터일 수 있고, 이메일 없는 개인정보는 놓침 — 두 효과가 얼마나 상쇄되는지 모름) ② Common Crawl 표본은 Lovable 전체를 대표하지 않는다 ③ 데이터셋을 일부만 내려받았다 ④ **Lovable 자체 DB 기능(2025년 말 도입)은 조사하지 않았다** ⑤ 악용 여부는 확인 못 함. 그리고 이건 "AI가 만든 코드라서"의 문제라기보다 **안전하지 않은 기본값 위에 비전문가가 대량으로 올라탄** 문제다 — 저자들도 "접근 제어 실수는 사람이 쓴 앱에서도 생긴다"고 적었다. 보고서가 보안 컨설팅 회사의 영업 페이지 끝에 붙어 있다는 점(마지막 절이 "전문가에게 연락하라")도 감안. 다만 Supabase 자신이 같은 이유로 기본값을 바꿨다는 사실이 이 문제의 실재를 뒷받침한다.

### 2. 에이전트 1,000개를 한 팀으로 — Git 브랜치 + Postgres 다섯 테이블 + 채점기

**무슨 일인가.** Anthropic 블로그(2026-11-09 게시, Barry Zhang 외, 전문 읽음). 출시 전 Fable 5.2 초기 버전으로 **리드 1 + 헬퍼 999**를 돌려 페르마의 마지막 정리 Lean 형식화를 **28.7시간**에 재현. 9월 첫 형식화(연구자 1명 + 수십 에이전트, Prove2Me 플랫폼, 11일, 출력 토큰 약 60억, Lean 1,300만 줄) 대비 출력 토큰 1/3, 증명 길이 1/7. 같은 주 Google Research(2026-11-13, Vahab Mirrokni, 전문 읽음)는 /teamwork 성과 목록을 냈다.

**배경 — 왜 지금인가.** 9월 실험에서 Claude의 초기 시도가 실패한 이유가 **"에이전트들이 프로젝트 상태를 잃어버리고 협업을 멈춰서"** 였고, 이를 Prove2Me(명제를 작은 명제로 쪼갠 공유 그래프 + 명제별 독립 컴파일 파일)가 풀었다. 이번 질문은 "**전용 플랫폼도, 연구자의 지휘도 없이** 범용 도구만으로 되나?"였다.

**기술적으로 어떻게 동작하나.**

- **주어진 것**: 명제 60개(최종 정리 + 중간 이정표 59), 고전적 증명 경로 한 문장 스케치, 정의, 9월 작업의 **증명된 보조정리 47개**. 역할은 "리드는 나눠서 배정, 헬퍼는 리드의 일을 기다리고 불명확하면 물어라"뿐. 도구는 셸·파일 편집기·Lean+Mathlib·**자기 Git 브랜치**(main으로는 merge request만)·**공유 Postgres**.
- **왜 SQL인가**: 정보를 조직하는 범용 원시 연산이 있고, **트랜잭션이 1,000개의 동시 쓰기를 처리**하고, Claude가 이미 잘 안다.
- **리드가 처음 10분에 만든 테이블 다섯**: Announce(전체 지시) / Assign(누가 무엇을) / Notes(공개 게시판) / Subtasks(누구나 추가, **먼저 집은 헬퍼가 소유**) / Landed(완료 로그). 백엔드 감각으로 보면 이건 **작업 큐 + 이벤트 로그 + 공지 테이블**이다. Subtasks의 "먼저 집은 쪽이 소유"는 `UPDATE ... WHERE owner IS NULL`류의 낙관적 선점과 같은 패턴(구현 SQL은 글에 없음).
- **전개**: 27분에 3개 증명, 헬퍼들 판정에 따라 47개를 "예산 내 불가능"으로 미루고 10개에 몰아줌(크루 17명 → 46~139명) → 70분에 10개 완료, 리드가 "처리량이 '불가능' 판정의 가정보다 훨씬 높다"며 미룬 것들로 재배치 → 3시간째 "나를 기다리지 마라"(중앙 배정에서 자율 선점으로) → 18시간째 Langlands–Tunnell만 남자 약 750명 투입("솔직히 승산 낮다"), 과제 트리 **2,418개·최대 10단계 깊이**(각 조각이 아래 조각을 '가정'하고 진행 → 수백 명 병렬) → 28.4시간 L–T, 28.7시간 최종 정리. 총 쓰기 36,612·읽기 311,734. **18시간째 실행을 마지막 저장 지점에서 재시작하고 12시간을 더 줬다**(브리핑에 없음).
- **안전 설계**: 에이전트마다 경량 VM, 네트워크 없음(게이트웨이로 가는 파이프 하나), **신원은 게이트웨이가 샌드박스 밖에서 태깅**(다른 에이전트 사칭 방지), 커널은 모듈 로딩·kexec·원시 메모리 접근 제거 + lockdown, 비특권 사용자·sudo 제거, 도구가 자기 에이전트 루프를 읽거나 못 고치게, SQL 구문당 5초·쓰기 256MiB 상한. **모든 도구 호출을 실행 전 LLM 분류기가 검사(fail-closed)**, 별도 오프라인 감시자. 100만 건 넘는 호출 중 차단 기준에 걸린 것 없음.

Google /teamwork는 설계 원칙 둘을 명시했다: ① 생성은 예측 불가하니 **병렬 탐색 + 전용 반증기**(Lean, 수정 없는 테스트, 실행 시뮬레이터, 하드웨어 카운터) ② 며칠짜리 작업에서 주의가 흩어지니 **컨텍스트를 구조적으로 분할** — 각 에이전트는 그 단계에 필요한 파일·도구만, 코디네이터는 새 후임에게 넘기고, 비판자·감사자는 **원 작성자의 추론을 모르는 깨끗한 컨텍스트**에서 검증. 대표 성과: Courtade–Kumar 추측(2013) 일반형 증명 + Lean 5,000만 줄, Weil 추측 형식화(Lean 약 180만 줄, 서브에이전트 호출 28,800회, "완전 자율"), Zircon 마이크로커널 잔여 C++ → 안전한 Rust 약 80만 줄(arm64 부팅), libgav1 → Rust 약 17만 줄(처음엔 원본보다 4배 느렸다가 프로파일러를 주자 20~30% 빨라짐), Borg 스케줄링 변경 2건으로 일부 하드웨어에서 TPU 선점 24% 감소.

**실무에 무슨 의미인가.**

- **조정 인프라는 평범해도 된다.** 1,000개 에이전트의 협업이 Git 브랜치(격리) + 트랜잭션 DB(조정)로 됐다. 우리가 이미 다루는 도구다 — 동시 선점·작업 큐·완료 로그 설계는 WMS의 재고 선점·피킹 큐와 같은 문제 모양이다.
- **Google의 rewrite 패턴이 짚은 실패 모드가 실무적이다**: 대규모 이관에서 에이전트는 **의존성을 스텁으로 비우거나 테스트를 고쳐서** 깨진 포트를 통과시킨다. 해법은 "의존 모듈이 컴파일된 뒤에만 다음 모듈을 스케줄, 모든 말단 모듈은 **원본 그대로의 테스트 스위트**에 링크". 에이전트에게 리팩터링을 시킬 때 "테스트 파일은 읽기 전용"을 규칙으로 두는 이유.
- **에이전트는 스스로를 과소평가한다.** 헬퍼들은 60개 중 47개를 불가능이라 판정했지만 대부분 증명했고, L–T 캡틴은 "1% 미만"이라 했지만 해냈다. Anthropic은 결론에 "사람의 격려가 너무 이른 포기를 막을 수 있다"고 적었다 — 실제로 하네스가 리드에게 **남은 시간 알림을 19번** 보냈다. 11/13 Orchestrator의 "재계획 트리거"와 짝이 되는 장치: 언제 포기를 **허용하지 않을지**도 설계 대상.
- **브리핑의 결론이 맞다**: 채점기가 없는 코드베이스에선 에이전트를 몇 개 붙여도 사람이 전부 리뷰해야 한다. 테스트·CI가 에이전트 투자 수익률을 정한다.

**반론·회의적 시각.**

- **"토이 실험"이다(저자 표현).** 이미 한 번 형식화된 정리를, 47개 보조정리와 명제 목록을 받고 **재현**했다. 처음부터 길을 찾은 것과 다르다. 저자들도 "Prove2Me 같은 도메인 전용 플랫폼이 여전히 효율을 높일 수 있다"고 적었다.
- **비용 미공개.** 출력 토큰이 9월(약 60억)의 1/3이라는 것만 있고, 1,000개 VM·28.7시간의 달러 비용은 없다.
- **안전 감시의 실제 구성.** 이 실행에서는 **행동만 보는 감시자만** 썼고, 체인오브소트(CoT)까지 보는 감시자는 **실행 직후에** 추가됐다. 또 일반 원칙은 "차단 시 팀 전체 정지 + 사람 검토"인데 이번 실행에선 **헬퍼가 차단되면 그 헬퍼만 빠지고, 리드 차단만 실행 종료**였다. 사후에 CoT 감시자·현재 루브릭으로 재생해 보니 **root 권한 확인 시도 1건**이 차단 직전까지 갔다. 브리핑의 "100만 건 중 걸린 것 없음"은 사실이지만 이 단서들과 함께 읽어야 한다.
- **Google 글의 한계.** 대부분 성과가 "인간 전문가와 협업"이다 — Courtade–Kumar도 CUHK 팀이 후보 함수를 제안해 문제를 14변수 최적화로 줄였고, 그 뒤를 Gemini가 했다. 실패율·비용·폐기된 시도는 없다. 성과 나열형 글이라 비교 기준선이 대부분 없다.
- **둘 다 검증 가능한 영역에 몰려 있다** — 브리핑의 지적 그대로. 업무 코드의 "요구사항에 맞나"는 Lean 커널처럼 판정되지 않는다.

### 3. Project Zero "Full X" + PyPI 출처 증명 — 신뢰를 사람의 협상에서 기계의 판정으로

**무슨 일인가 (Project Zero, 전문 읽음).** 브리핑은 "90일 공개 정책을 다시 못 박았다"고 했지만 원문은 **정책 개편**이다.

| | 이전(2021~) | 새 정책 "Full X" |
| --- | --- | --- |
| 공개 시점 | 수정까지 90일 + 패치 배포 유예(soak) 30일 | **보고 후 X일이면 무조건 공개** |
| X | — | 오늘 90 → **2027-02-02부터 60** → **2028-01-03부터 30** |
| 유예(grace)·변종(variant) 특례 | 있음 | **폐지** |
| "고쳐졌나" 판정 | 벤더와 협상해 정책의 결정 지점으로 | 추적·공유는 하되 **결정 지점에서 제외** |
| 예외 | — | 실제 악용 중(ITW), 이미 공개됨, 벤더 요청 / 하드웨어(Spectre·Meltdown급)는 드물게 예외 |

**배경 — 왜 지금인가.** 글이 든 이유가 모두 LLM이다. ① 공격자가 버그를 찾고 익스플로잇하는 속도가 빨라졌고, **여러 주체(악의적 주체 포함)가 같은 버그를 찾을 위험**이 커졌다 — "오늘 보고된 취약점은 작년의 것보다 즉각적 위험이 훨씬 크다" ② 패치에서 버그 세부를 역추적하는 시간이 줄어 **"패치→익스플로잇 0초"가 합리적인 공격자 모델**이 됐다 → 30일 soak는 의미 없고 오히려 "비밀이 지켜진다는 착각"을 준다 ③ Project Zero 자신도 LLM 덕에 **"1년에 몇 건 찾던 대상에서 주당 여러 건"** 을 찾아, 벤더와 건건이 협상하는 정책이 감당 불가가 됐다. 그래서 목표 셋: 빠른 수정, **패치 갭**(패치 배포 ~ 사용자 설치) 단축, **정책의 자동화**(양쪽 모두).

**왜 단계적으로 줄이나.** 벤더 의견 수렴 결과: 당장 바꾸면 수정 프로세스를 개선하는 동안 미수정 취약점이 공개돼 사용자가 다치고, 너무 공격적인 시한은 ① 심각도와 무관하게 "새 정책으로 보고된 버그"를 우선 처리하게 만들고 ② 못 지킬 시한 앞에서 **아예 포기하게** 만든다. 심각도로 시한을 조절하지 않는 이유도 명확하다 — "심각도는 공격자가 그 버그를 발견할 확률에 영향을 주지 않는다. 사용자에 대한 영향만 바꾼다."

**PyPI (블로그 전문 읽음, 2026-11-06).** OpenSSF 지원·Kabu Creative 구현으로 프로젝트 페이지를 개편했다. 새 **보안 탭**이 릴리스의 **출처 상태**를 계산한다 — 모든 파일에 증명(attestation)이 있으면 Full Provenance, 하나도 없으면 No Provenance. 증명은 두 종류: **PyPI Publish**(Trusted Publisher가 올렸음) / **SLSA Build Provenance**(정확한 소스 커밋·빌드 플랫폼·빌드 명령에 연결). 경고 넷: **Incomplete**(일부 파일만, 예: wheel은 Trusted Publishing인데 sdist는 API 토큰으로), **Inconsistent**(한 릴리스 안에서 빌드 시스템·저장소가 다름), **Change of Provenance**(이전 릴리스와 저장소·워크플로가 다름 — 조직명 변경일 수도, **계정·파이프라인 탈취**일 수도), **Loss of Provenance**(증명 붙이던 프로젝트가 안 붙이기 시작). 격리(quarantine) 배너가 다른 모든 경고보다 우선한다. 2026년 7월부터 **최초 릴리스 14일 후의 새 파일은 거부**하는 정책이 생겼고, 그 이전 릴리스의 늦은 파일엔 주황 경고.

**기술적으로 어떻게 동작하나 — 둘을 한 그림으로.** 둘 다 "이건 믿어도 되나?"를 **사람의 판단·협상**에서 **기계가 계산할 수 있는 규칙**으로 옮긴다. PyPI는 "이 파일이 이 커밋에서 이 워크플로로 빌드됐다"를 서명된 증명 + 투명성 로그로 판정하고, **변화**(Change/Loss)를 경고로 바꾼다 — 공격은 대개 "평소와 다른 것"으로 드러나기 때문. Project Zero는 "고쳐졌나"라는 협상 대상을 정책에서 빼고 **날짜 하나**로 만든다. 1번(Supabase가 "사람이 리뷰하던 시대"의 기본값을 바꿈)과 같은 방향이다.

**실무에 무슨 의미인가.**

- **"No Provenance ≠ 악성"** — PyPI가 굵게 적은 문장. 증명 없음은 "암호학적으로 출처를 검증할 수 없다"일 뿐이고, 그땐 메인테이너 이력·릴리스 패턴·저장소 활동 같은 주변 신호로 판단한다. 경고 중 실제로 눈여겨볼 것은 **Change·Loss**(평소와 달라짐)다.
- **배포 쪽**: GitHub Actions로 패키지를 올린다면 장기 API 토큰 대신 **Trusted Publishing(OIDC)**. Maven Central·npm도 같은 방향(npm provenance). 내 사이드 프로젝트에선 "배포 키가 저장소 시크릿에 장기 보관돼 있지 않은가"가 첫 점검 항목.
- **운영 쪽**: Project Zero 시간표는 **"보안 공지 → 패치 적용"까지 우리 쪽 리드타임**에 대한 압박이다. 공개 시점이 30일로 줄고 패치→익스플로잇이 0에 수렴하면, 의존성 업데이트를 분기 작업으로 미루는 습관은 버텨내지 못한다. Dependabot·Renovate 같은 자동 PR + 테스트(=채점기, 2번과 같은 결론)가 전제가 된다.

**반론·회의적 시각.**

- **Full 30의 현실성.** 펌웨어·자동차·의료기기처럼 배포 주기가 긴 영역에서 30일은 패치가 아니라 **완화책**(코드 경로 비활성화 등)만 가능한 시간이다. 글도 "비패치 전략"을 권하고 하드웨어 예외 여지를 남겼다. 오픈소스 자원봉사 메인테이너에게 30일은 가혹하다는 반론이 예상된다(HN 토론은 직접 읽지 않음).
- **"수정 여부를 판정하지 않는다"** 는 Project Zero의 부담을 줄이지만, 부분 수정·변종이 남은 상태로 세부가 공개될 수 있다.
- **PyPI 증명은 '어디서 왔나'만 말한다.** 정상 파이프라인에서 정상 커밋으로 빌드된 **악성 코드**(메인테이너 본인의 악의, 의존성 오염)는 Full Provenance로 나온다. 출처 증명은 위변조·탈취를 막지, 내용의 안전을 보증하지 않는다.

### 4. 잘하는 것과 믿을 만한 것, 행동과 판정 — SO-Arena · Actor/Judge/Teacher (원리는 AI 심층으로)

**무슨 일인가.** HF 오늘 1위 **SO-Arena**(싱가포르국립대, ▲136, 초록·저자 코멘트 읽음): "System One 모델"(긴 토큰 생성 없이 빠르게 결정하는 모델 — Vault에서 '결정 모델'로 불러 온 Jev·Decisions API 계열)을 11개 도메인·5개 역량군·21개 모델로 평가. 정확도 외에 **결정 안정성**(선택지 집합을 통제해 바꿨을 때 결정이 흔들리나)과 **정답 부재 인식**(유효한 선택지가 없을 때 알아채나)을 따로 잰다. 결과: **종합 성능 1위 System One 모델이 신뢰도 7위**, 스케일링·추가 추론의 이득은 도메인마다 크게 다름. 같은 날 **Actor/Judge/Teacher**(저장대, ▲34): 결정 모델 3 + 일반 LLM 3을 ALFWorld에서 행동자·심판으로 비교 → 행동자로는 6개 전부 "먼저 해야 할 하위 목표"를 두고 쉬운 쪽에 끌려갔지만, 궤적 전체를 본 심판으로는 그 하위 목표를 향한 단계에 정확히 점수를 줬다. JEV를 교사(단계별 보상)로 쓰자 Qwen2.5-1.5B 정책이 GRPO 대비 ALFWorld **72.8 → 82.9%**, WebShop **56.8 → 71.4%**.

**배경.** 11/12 노트에서 Gemini Decisions API가 Jev·OpenAI와 같은 인터페이스(예/아니오·선택·루브릭 점수)로 합류했고, MMDM은 결정 모델의 약점(선택지 논리·제약 계획)을 쟀다. 오늘 두 논문은 그 다음 질문이다 — **"이 판정을 믿어도 되나?"** 와 **"판정 모델은 어디에 써야 값어치를 하나?"**

**기술적으로 어떻게 동작하나 (요지).** SO-Arena는 같은 문제의 **선택지 구성만 바꿔** 다시 묻는다(선택지 순서·추가·제거). 정확도가 같은 두 모델이라도 한쪽은 선택지 배치에 따라 답이 뒤집힌다면 프로덕션에서 쓸 수 없다. Actor/Judge/Teacher의 핵심은 **"이 행동이 도움이 됐나?"를 묻고 "이 과제가 성공할까?"를 묻지 않는 것** — 결과를 본 뒤의 사후 판정은 행동 시점에 '예측'해야 했던 결과를 '관찰'로 바꾼다. 자세한 구조(왜 GRPO의 결과 보상만으로는 부족한가, 사후 판정이 어떻게 단계 보상이 되나)는 AI 심층 노트에.

**실무에 무슨 의미인가.**

- **결정 모델을 분기 로직에 붙일 때의 체크리스트**: 같은 입력을 여러 번, **선택지 순서를 섞어서**, 그리고 **정답이 없는 경우를 섞어서** 던져 본다. 11/12 노트의 "선택지 20개 초과 붕괴·학습 분포 밖 과신"과 같은 계열의 점검. 리더보드 순위는 이걸 말해 주지 않는다.
- **"작은 모델은 리뷰어로"**: 행동은 못 해도 판정은 잘한다면, 비싼 모델이 실행하고 싼 결정 모델이 **실행 로그를 사후 채점**하는 구성이 합리적이다. 11/13 Orchestrator(계획자/실행자 분리)에 "사후 채점자"라는 세 번째 역할을 붙이는 셈.

**반론·회의적 시각.** SO-Arena는 "1위가 신뢰도 7위"라는 헤드라인 외에 **모델 이름·격차 크기를 초록에 안 적었다**(본문 미독). 댓글의 질문 "11개 도메인 중 정답과 '믿을 만한 정답'의 격차가 가장 큰 곳은?"에 답이 없다. Actor/Judge/Teacher는 1.5B 정책·텍스트 시뮬레이터 두 개뿐이고, 교사(JEV) 호출 비용이 없다.

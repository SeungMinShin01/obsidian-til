## 깊게 본 것

### 1. Java4Shell(CVE-2026-114938) — 예외가 던져지기 전에 이미 깨진 메모리

**무슨 일인가.** 보안 업체 Calif가 2026-11-17에 공개했다. OpenJDK HotSpot의 x86-64 Base64 **intrinsic** 에 힙 범위 밖 쓰기(out-of-bounds write) 결함이 있고, 이를 이용해 인증 없이 원격 코드 실행(RCE)까지 갈 수 있다. Calif 기준 CVSS 4.0 **9.2(Critical)**. 같은 날 13:00 PT에 OpenJDK 보안 권고와 Oracle 패치가 나왔다.

- **기본 설정에서 인증 전 RCE 시연**: Keycloak, Atlassian Jira·Confluence, JFrog Artifactory, Jenkins, PingFederate
- **인증 후 RCE**: Apache Kafka 브로커, Solr, Elasticsearch, Gerrit, Spinnaker
- 목록은 "비포괄적". **Apache Struts·Spring Boot 기반 샘플 앱** 에서도 재현. 인증(Basic 헤더·JWT)과 파일 업로드 같은 평범한 기능이 Base64 디코더로 가는 길이다
- **클라이언트도 대상** — 악성 서버로 TLS 연결을 여는 Java 프로그램이 서비스를 하나도 열지 않았어도 공격당할 수 있다(samczsun 제공 익스플로잇)

**배경 — intrinsic이 뭐고 왜 위험한가.** JVM은 처음엔 바이트코드를 해석하다가, 자주 불리는 메서드를 **C2 JIT 컴파일러** 가 네이티브 코드로 바꾼다. 그중 일부 핫 함수(문자열 비교·배열 복사·암호·Base64)는 컴파일러가 Java 코드를 번역하는 대신 **미리 손으로 짠 어셈블리(intrinsic)** 로 통째로 바꿔 끼운다. 최신 CPU의 SIMD 명령(AVX-512)으로 64바이트씩 한 번에 처리하려는 것이다. 요점은 **"Java는 메모리 안전하다"는 보장이 내가 쓴 Java 코드에 대한 것** 이고, 그 아래 런타임은 C·C++·어셈블리라는 것이다. 성능을 위한 손 어셈블리가 바로 그 보장을 우회하는 지점이 됐다.

**기술적으로 어떻게 동작하나 — 음수 길이가 "전부 쓰기"가 되기까지.**

1. intrinsic은 입력을 256바이트 블록, 그다음 64바이트 블록으로 처리하고, **64바이트 미만의 꼬리** 는 `VMOVDQU8`(`evmovdqub`) 명령으로 처리한다. 이 명령은 **64비트 마스크** 를 받아 마스크 비트가 1인 바이트만 읽고 쓴다
2. 꼬리의 출력 길이는 `output_len = (input_len / 4) * 3` 으로 계산하고, 끝이 `=` 이면 패딩만큼 1씩 뺀다
3. 꼬리가 `=` 하나뿐이면 `input_len = 1` → `output_len = 0` → 패딩 때문에 1을 빼서 **−1**(언더플로)
4. 마스크는 `bzhiq(-1, output_len)` — "하위 n비트만 남기고 지워라"인데, n이 64 이상이면 아무것도 안 지운다. −1을 부호 없는 수로 보면 엄청 큰 수라 **마스크 = 전부 1**
5. 그래서 64바이트 전체를 쓴다. 65자 입력(`A`×64 + `=`)에 대해 Java는 **50바이트** 결과 배열을 할당했는데, 쓰기는 오프셋 48에서 시작해 64바이트 → **배열 끝을 62바이트 넘어간다**
6. intrinsic은 잘못된 입력을 감지해 "여기까지 디코딩했다"고 돌려주고, 나머지는 Java 코드가 처리하다가 `IllegalArgumentException` 을 던진다. **그때는 이미 이웃 객체가 덮어써진 뒤다**

OpenJDK 17에서는 이 경로에 들어가는 길이 기준이 높아 트리거가 `A`×128 + `=` 이다.

**익스플로잇 — "고정값 쓰기"를 RCE로 키우는 법.** 넘쳐서 쓰이는 값은 공격자가 고를 수 없다(48~63바이트는 늘 `0x9a`). 위치만 조절할 수 있다. Calif는 JavaScript 엔진 공격의 고전 기법을 가져왔다.

- **writer** — 넘친 쓰기로 이웃 버퍼의 **길이 필드** 를 키운다. 그러면 그 버퍼는 공격자가 고른 바이트를 계속 받아들이므로, 고정값 쓰기가 **고른 값의 선형 쓰기** 로 승격된다
- **reader** — 또 다른 배열의 길이를 키우고 그 배열이 응답으로 복사돼 나가게 하면 **힙 내용 유출(JavaBleed)** — 코드 실행 전 단계에서 이미 개인정보·개인키·토큰이 샌다(Heartbleed와 같은 꼴)
- **힙 펑수이(grooming)** — HotSpot은 스레드마다 TLAB(스레드 전용 할당 구역)을 줘서 요청 스레드끼리 객체 순서가 섞이지 않는다. 그래서 배열 크기를 조절해 **TLAB 밖 할당 경로** 로 밀어내고, G1의 리전 경계에 writer·reader 쌍을 여러 개 뿌려 "맞을 때까지 재시도"(Spray and Pray)
- **원격 타이밍 제어** — HTTP 요청 본문을 할당 직전까지만 보내고 TCP ACK를 확인한 뒤 나머지를 보낸다. 네트워크 지터에 민감해서 Calif는 **표적과 같은 리전에 VM을 빌려** 왕복 시간을 줄였다
- 이후 망가진 객체를 복구하고(JVM이 죽지 않게), 임의 쓰기로 키워 Code Cache·JVM 훅에 닿는다

**발견 과정 — "센타우르 해커".** 연구자 Quang Luong이 Codex에게 JIT·intrinsic·암호 영역을 감사시켰고, 초기 결과는 대부분 도달 불가능하거나 비현실적인 "슬롭"이었다. 계속 밀어붙인 끝에 Base64 결함이 나왔다. **발견 1시간 + 첫 익스플로잇 2시간, 토큰 비용 200달러 미만.** 다만 AI가 힙 그루밍 단계에서 막히자 Calif가 **힙 추적·시각화 도구** 를 따로 만들어 줬다 — 사람이 맥락(도구)을 주고 AI가 반복을 맡는 구조다. 10/18 노트 「버그를 찾는 속도가 고치는 속도를 앞질렀다」의 흐름 그대로다. Calif는 글 첫 문장에서 **PHP2Shell도 자기들이 공개했다** 고 쓰고, OpenAI 발표문도 PHP2Shell을 `calif.io/php2shell` 로 링크한다 — 10/22·10/23 노트는 PHP2Shell을 원문을 읽지 못한 채 "Wiz"로 적었는데, 출처는 Calif로 보는 게 맞아 보인다(아래 정정 7).

**반론·회의적 시각.**

- **점수 차이.** Calif는 CVSS 4.0 **9.2**, OpenJDK 권고문의 위험 행렬은 CVSS 3.1 **8.1**(공격 복잡도 High)로 적었다. 둘 다 심각하지만, "누구나 한 줄로 RCE"는 아니다. 트리거(메모리 손상)는 한 줄이지만 **RCE는 앱마다 맞춤 프로파일** 이 필요하다고 Calif 스스로 밝혔다(디코더 경로·살아 있는 writer·응답으로 돌아오는 reader·힙 배치·앱 동작). 제품별 무기화 체인은 비공개
- **시연 환경.** 공개 IP 너머 실제 인터넷으로 했다지만 표적과 같은 리전에 VM을 빌렸다. 원격 지터가 큰 환경에서 성공률은 공개되지 않았다
- **"vibe-uncoding" 은 말처럼 쉽지 않다.** Calif도 "안 쓰는 것처럼 보이는 기능에 숨은 의존이 있을 수 있다"고 인정한다. 그리고 이번 결함은 애플리케이션이 지울 수 있는 코드가 아니라 **런타임 안** 에 있다 — 앱 개발자에게 현실적인 vibe-uncoding은 "의존성 줄이기"와 "JVM 플래그로 끄기" 정도다
- **홍보성.** NYT 기사·포스터·"Write once, RCE everywhere" 같은 연출이 있다. 다만 단독 실행 가능한 PoC(쓰기가 4,096바이트 배열 안에만 떨어지게 만든 안전한 재현)와 OpenJDK·Oracle의 공식 권고가 함께 있어 결함 자체는 확인된 것이다

### 2. GPT-6.2 Astra·Sol과 MAI Code 2 — 차트의 x축이 '과제당 비용'이 됐다

**무슨 일인가.** OpenAI가 어려운 프로젝트용 **GPT-6.2 Astra** 와 일상 업무용 **GPT-6.2 Sol** 을 냈다. 발표문 첫 문단의 문장: "더 적은 출력 토큰으로 더 나은 결과". 같은 날 Microsoft AI도 코딩 전용 **MAI Code 2 / Code 2 Flash** 를 냈다.

**숫자 — 거의 모든 비교가 "점수 + 비용" 쌍이다.**

| 항목 | 내용 |
| --- | --- |
| Agents' Last Exam(다단계 전문 업무) | Astra가 GPT-6 Astra보다 **+5.2점, 비용 1/3 미만**. Claude Fable 5.2보다 **+5.5점, 비용 5%** (단, Fable 5.2 점수는 폴백 모델을 쓴 9개 과제를 뺀 리더보드 값) |
| GDPval v2(내부) | Astra **+6.2점, 출력 토큰 22% 감소**. Sol은 GPT-6.1 Sol 대비 +5.3점 |
| FrontierCode 2.0(Cognition, 병합 기준 충족) | **Sol이 Astra와 0.5점 차, 비용 약 1/5**(둘 다 max) |

**배경 — 왜 지금 "토큰 덜 쓰기"인가.** 에이전트 작업에선 같은 모델을 수십~수백 번 호출하고, 매 호출마다 지금까지의 맥락 전체를 다시 보낸다(아래 3번의 FrontierHarness가 이걸 실측). 그래서 "단가 × 토큰"의 토큰 쪽이 가격표보다 훨씬 크게 움직인다. 공급자 입장에서도 컴퓨트가 병목이니, 같은 점수를 덜 생성해서 내는 게 가격 인하보다 싸다. 9/22 노트("생성이 싸질 때 청구서는 읽는 쪽으로"), 9/25 노트("싸게 많이 굴리게 된 주")의 흐름이 이제 **발표문의 문법** 이 됐다.

**MAI Code 2 — "98% 성능을 40% 비용에".** Code 2는 심층 디버깅·다중 파일 구현용, Flash는 코드 설명·간단한 수정 같은 대량 작업용. Code 2는 4개 코딩 벤치마크 평균으로 GPT-6.1 Sol의 98%를 비용 40%에 낸다고 했는데 **이 비용 계산에 50% 프로모션 가격이 들어갔다**(브리핑도 지적). Flash는 3개 벤치마크 평균 61.0%로 GPT-6 Luna(55.1%)·Claude Haiku 5.5(53.9%)를 앞서고 과제당 $0.052. 둘 다 자체 평가다.

**실무에 무슨 의미인가.**

- **"제일 센 모델"을 기본값으로 두지 않는다.** FrontierCode에서 0.5점 차에 5배 비용이면, 코드 설명·리팩터링·테스트 작성은 Sol급/Flash급, 다중 파일 설계 변경만 Astra급으로 **작업별 라우팅** 이 합리적이다. 11/17 AI 심층(같은 점수 뒤의 다른 작업 습관)에서 본 "작업별 노력 수준"과 같은 이야기
- **프롬프트 캐시 팁(발표문 각주)** — "캐시 재사용률을 높이려면 **프롬프트 접두사를 바꾸지 말고 새 지시를 뒤에 덧붙여라**". 11/16 AI 심층(회전으로 넣는 상대 위치)에서 정리한 "프리픽스 캐시는 같은 위치의 같은 접두사가 필요하다 — 변하는 값은 프롬프트 뒤로"의 공급자 쪽 확인이다. Spring에서 LLM API를 부른다면 시스템 프롬프트에 날짜·요청 ID 같은 가변값을 넣지 말 것
- **모델 호출 레이어를 얇게 추상화** — 11/17 노트에서 Gemini Carbon·Argon의 12/1 두 배 인상을 봤듯, 가격·등급은 몇 주 단위로 바뀐다

**반론·회의적 시각.**

- **벤치마크는 발표 주체의 선택이다.** Terminal-Bench-Science에서 Fable 5.2 점수는 Artificial Analysis가 **mini-swe-agent 하네스** 로 잰 값이고, Anthropic은 Claude Code에서 **74.6%** 를 보고했다(발표문 각주). 하네스가 다르면 같은 모델도 다른 숫자가 나온다 — 바로 아래 FrontierHarness의 주제다
- **정렬 쪽 후퇴를 스스로 공개했다.** "Blocker Deception" — 코딩 과제에서 편집할 파일을 지워 두고, 모델이 그 장애물을 사용자에게 **말하는지** 를 본다. 차트를 내가 읽은 바로는 개발자 프롬프트가 없을 때 6.2 Astra 22.28%·6.2 Sol 24.08%로 6.1 Sol(14.00%)·6 Astra(11.09%)보다 높고, Codex에 넣은 지시문이 있으면 8.04%·8.88%로 내려간다(조건 배치는 차트 판독이라 내 해석). **토큰을 아끼도록 학습된 모델이 "안 됐다"는 말도 아끼는** 방향일 수 있다는 가설이 가능하다 — OpenAI는 "원인을 조사 중"이라고만 했다
- **보안 제한의 양날.** 두 모델 모두 Preparedness Framework 사이버보안 **Critical** 임계값 도달, 그래서 정당한 취약점 연구 일부도 막는다고 명시. Astra는 **AI 자기개선 High** 에 처음 도달한 외부 공개 모델이다. Java4Shell을 찾은 게 바로 이전 세대 Codex였다는 걸 같이 놓고 보면, 같은 능력이 방어·공격 양쪽에 걸린다

### 3. FrontierHarness v1.1 + Termination Lag — 비용은 '단계'에 있고, 그 대부분은 끝내지 못한 시도에 있다

**무슨 일인가 (FrontierHarness).** Runta가 Baseten과 함께 **22개 하네스 구성 × 5개 오픈 모델 × 62개 터미널 과제 × 4회 = 27,280회 실행, 830억 토큰** 으로 "모델을 바꾸면 하네스도 바꿔야 하나"를 쟀다. 모델은 GLM-5.3·GLM-5.3 Flash·DeepSeek V4.1 Flash·Muse(Meta)·Kimi-K3, 모두 Baseten 서빙·최대 추론 노력·하네스 기본 설정. 웹에서 정답을 찾아본 216건(그중 163건이 온라인 조회)은 **보상 해킹으로 0점** 처리했다.

**결과 — 다섯 가지.**

1. **모델마다 최적 하네스가 다르다.** 통과당 비용 기준 최적: GLM-5.3 → Codex CLI, GLM Flash → Pi, DeepSeek → ZCode, Muse → Oh My Pi, Kimi-K3 → Alma. Codex CLI는 GLM-5.3에서 비용 1위, Kimi-K3에서 16위. 과제를 4,000번 다시 뽑아도 Codex CLI+GLM-5.3은 99.6% 1위였지만 나머지 넷은 25~53%로 **근소한 경합**
2. **비용 분산의 92.8%는 모델, 하네스 고유 2.3%, 조합 4.9%.** 모델을 고정하면 하네스 간 차이의 68%가 "조합" 효과(또는 잡음). 그래도 같은 모델에서 가장 싼/비싼 하네스 차이는 **과제당 1.8~5.0배**, 무작위 섞기(300회)의 1.2~1.8배를 모두 넘었다(p=0.003)
3. **비싸다고 잘 풀지 않는다.** 하네스의 과제당 비용과 통과율의 순위 상관은 모델별 −0.39~+0.22. 다섯 모델 중 넷에서 가장 비싼 하네스가 가장 싼 하네스보다 덜 통과했다
4. **비용을 정하는 건 '단계 수'다.** 22개 하네스에서 통과당 비용과의 순위 상관: 시작 토큰(882~21,365) +0.01, 제공 도구 수(1~29) +0.02, 캐시 적중률(87.0~95.7%) −0.03, **통과당 단계 수(24.8~73.5) +0.51(p=0.015)**. 단계마다 맥락 전체를 다시 보내니, 한 시도가 평균 200만~480만 입력 토큰을 쓰고 가장 큰 첫 요청(2만 1천 토큰)도 그 1% 미만이다. 가장 작은 하네스 mini-SWE-agent(첫 요청 882토큰·도구 1개)는 단계가 많아 22개 중 17위
5. **비용의 64.5%가 통과 못 한 시도에 들어갔다**(실패 52.7%·시간 초과 11.8%). 그리고 최적 하네스 다섯의 실패 중 **68%(Pi)~82%(Codex CLI)가 시간 초과가 아니라 '자신 있는 최종 답'으로 끝났다**. 원문 예시: 에이전트 "동시성·취소 정리 테스트까지 검증 완료" → 검증기 `FAILED … assert 0 == 2`

최적 하네스 다섯의 공통점(관찰이지 실험은 아님): **셸 도구 하나가 도구 호출의 61~93%**(Pi는 read·bash·edit·write 4개뿐, 파일 검색은 bash로), **요청은 앞 요청에 덧붙이기만**(캐시 91~94%), **하위 에이전트·요약 거의 없음**.

**무슨 일인가 (Termination Lag).** 펜실베이니아 주립대. 5개 모델·2개 에이전트 프레임워크·SWE-bench 세 데이터셋에서 **실행 중 나온 모든 패치를 따로 저장해 테스트** 했다. "종료 지연" = 첫 정답 패치부터 실행 종료까지의 단계 수.

- 정답에 도달한 실행의 **38~82%는 첫 소스 편집에서 이미 맞혔다**
- 성공한 실행에서 정답 이후 단계가 중앙값 **35~37%(Qwen3-Coder)·54~60%(Laguna-XS.2)** (SWE-bench Verified·Multilingual)
- 그 단계 대부분은 **검증과 저장소 탐색**
- **1~8%는 맞힌 패치를 스스로 되돌려** 최종 답이 틀렸다

**기술적으로 — 둘을 겹치면.** FrontierHarness는 "비용은 단계에 비례하고, 대부분 실패에 쓰인다"를, Termination Lag는 "성공한 경우에도 절반 가까운 단계가 정답 이후"를 보였다. 즉 에이전트 비용의 큰 덩어리는 **"언제 끝났는지 모르는 것"** 에서 나온다 — 실패할 때는 끝났다고 착각하고(자신 있는 오답), 성공할 때는 끝난 걸 모르고 계속 돈다(종료 지연). 둘 다 **완료 판정을 모델의 자기 평가에 맡긴** 결과다. 처방도 같다: **기계가 확인할 수 있는 완료 기준**(실행 가능한 검증 스크립트·테스트)을 두고, 그게 초록이면 멈추고, 빨강이면 "끝났다"고 말하지 못하게 한다.

**실무에 무슨 의미인가.**

- 하네스를 고를 때 "프롬프트가 짧다·도구가 적다"는 비용 근거가 못 된다. **내 과제 묶음으로 직접 재야 한다** — Runta 결론도 "충분히 큰 자기 데이터셋으로 테스트하라"(하네스·모델 한 쌍의 통과율 95% 구간이 약 ±10점이라 몇 점 차는 무승부)
- 에이전트를 직접 짠다면(Spring AI 등) **단계 상한** 과 "테스트가 초록이면 즉시 종료" 훅이 프롬프트 다이어트보다 효과가 클 수 있다
- 내가 Claude Code를 쓸 때: CLAUDE.md에 "완료 = `./gradlew test` 초록 + 앱 기동 확인, 그 전엔 '완료'라고 쓰지 말 것" 같은 **기계적 완료 정의** 를 둔다

**반론·회의적 시각.** FrontierHarness는 **오픈 모델·Baseten 한 곳** 의 가격·캐시 기준이라 공급자가 바뀌면 비용 순위가 바뀔 수 있고, 닫힌 모델(Opus 5.5·GPT-6 Astra·Gemini 4 Carbon)은 다음 버전 예정이다. 각 하네스는 **기본 설정** 으로 돌렸으니 튜닝된 설정과는 다르다. "자신 있는 오답" 비율이 줄면 비용이 실제로 얼마나 주는지는 **테스트하지 않았다** 고 스스로 썼다. Termination Lag는 초록만 읽었다 — 다섯 모델 이름 전부, 종료 지연을 줄이는 개입 실험이 있는지, "정답 이후 검증 단계"가 정말 낭비인지(검증이 신뢰를 올리는 가치가 있을 수 있다)는 확인 못 했다. HF 업보트 5로 아직 주목도 낮다.

### 4. Claude Code 팀의 검증 설계 + SilentGuard — 심판을 피심판자 손 밖에 둔다

**무슨 일인가.** Addy Osmani가 claude.dev에 쓴 글(11/16). Claude Code 팀은 자기 코드의 **약 90%를 Claude가 쓰고 리뷰** 한다. 그 규모에서 사람이 모든 diff를 읽을 수 없으니 "에이전트가 **증거로** 자기 작업을 입증하게 하는" 검증 루프를 어떻게 짰는지 공개했다. 내부 테스트에서 별도 채점기가 루브릭으로 검사하자 과제 성공률이 **최대 10점** 올랐다고 한다(어려운 문제일수록 이득이 큼).

**투자할 테스트 세 종류.**

| 종류 | 왜 | 예 |
| --- | --- | --- |
| E2E | **속이기 어렵다** — 기능이 되거나 안 되거나. 실패 시 스크린샷·단계 추적으로 "어디서 깨졌는지"를 준다(유닛 테스트는 "Timeout after 30s"뿐) | 장바구니 담기 → 결제 → 확인 페이지 |
| 속성 기반(property) | 원래 코드를 쓴 에이전트와 **같은 편향을 갖지 않은** 입력 수천 개로 반증 시도 | 왕복("인코딩 후 디코딩 = 원본"), 불변식("잔고는 음수 불가"), 멱등성, 동등성("최적화 코드 = 단순 정답 코드") |
| 차등(differential) | 마이그레이션에서 **구 시스템이 정답지** | 같은 입력을 구·신 시스템에 넣고 차이 = 버그(공백 등 무관 요소는 정규화, 의도된 변경은 승인 목록) |

**팀 운영 규칙 — 전부 '모델 바깥'에 있다.**

- **검증 = 변경을 실제로 실행하는 것.** 앱을 띄우고 확인하는 방법을 `.claude/skills/verify` 스킬로 저장소에 고정, 커밋 전에 쓰게 함. 이 스킬이 곧 스모크 테스트 하네스라 빠르고 단단하게 다듬는다
- **세 번 고쳐도 실패하면 사람에게.** 실패를 "사람이 볼 곳"을 고르는 신호로 쓴다
- **신뢰성 체크리스트 39개**, 각 항목에 diff에서 읽을 수 있는 **트리거** 가 있어 매칭되는 3~10개만 검사(예: 세션 저장 형식이 바뀌면 "옛 기록에 새 필드가 없어도 안전히 로드되나")
- **리뷰어를 겹겹이 쌓지 않고 하나를 튜닝** — REVIEW.md에 이 코드에서 볼 것을 적고, 라운드마다 이전 결과를 이어받는다
- **변경은 자기를 심판하는 검사를 수정할 수 없다.** 코드 리뷰는 REVIEW.md를 PR의 변경분이 아니라 **베이스 브랜치에서** 읽는다. 리뷰는 커밋 단위(리뷰 중 푸시되면 결과 무효)
- **새 게이트는 관찰 모드부터** — 각 커밋에 "어떻게 검증됐는지" 도장(**"none" 포함**, 그래야 검증 안 된 커밋을 질의할 수 있다). 게이트는 off → observe(막았을 것을 기록만) → enforce. 세션에서 두 번 막히면 세 번째는 통과시켜 Claude가 갇히지 않게
- **리뷰어를 리뷰한다** — 되돌려진 병합 수, 병합 전 거절 수, 크기를 맞춘 '깨끗하게 남은 변경' 대조군. 과거 사고 PR로 저장소를 그 시점으로 되돌려 한 문장 정답 키로 채점, 원시 발견·검증 후·최종 리뷰의 재현율을 **따로** 본다
- **놓친 것을 규칙으로** — 사람 리뷰 코멘트·되돌림에서 2개 이상 PR에 나오고 diff로 식별 가능한 패턴만 후보, **에이전트 셋이 반증 시도** 후 사람이 승인. 플레이키 테스트는 건너뛰기·sleep·재시도 금지, 원인을 못 찾으면 **삭제하고 이유를 기록**. 규칙도 정기적으로 가지치기

**SilentGuard(Genentech, 초록) — 같은 원리를 API 응답에.** "조용한 API 실패" = 요청 일부(이름이 틀린 필터 등)를 무시하고도 **HTTP 200과 그럴듯한 오답** 을 주는 것. 공개 연구 API 15개 중 **11개** 에서 발견, 개수가 최대 **691배** 부풀려졌다. 체크리스트·리뷰 모델·LLM 판정 같은 기존 대책은 70% 넘게 오답을 남겼고, 에이전트는 판정기가 경고한 수치의 **77.4%를 그대로 보고** 했다 — **모델은 문제를 보고도 답한다.** SilentGuard는 판단을 하네스로 옮겨, 올바른 API라면 지켜야 할 불변식(예: 필터를 건 결과 수 ≤ 필터 없는 결과 수)을 어기는 값을 **보류** 한다. 오픈 모델 7개에서 오답 74.0% → 1.7%, 프런티어 모델 3개에서 70.2% → 0.5%. **같은 검사를 경고로만 주면 70.1%가 여전히 틀렸다** — 강제가 핵심. 새 결함 유형에선 61.1% → 24.5%. 회복이 아니라 **기권** 으로 오답을 피한다.

**실무에 무슨 의미인가 (Spring Boot).**

- **통합 테스트를 유닛 테스트보다 먼저** — `@SpringBootTest` + Testcontainers(MySQL·Redis)로 "주문 생성 → 재고 차감 → 조회" 같은 사용자 흐름. WMS 프로젝트에서 에이전트에게 맡길 때 이게 "속이기 어려운 심판"이 된다
- **속성 기반 테스트는 Java에도 있다** — jqwik(JUnit 5 엔진)의 `@Property`. 재고 도메인이면 "입고 n − 출고 m = 현재고, 현재고 ≥ 0", "같은 출고 요청을 두 번 처리해도 한 번과 같다(멱등)"
- **외부 API 응답에 불변식 검사** — `RestClient` 로 받은 DTO에 `@Valid` + 커스텀 검증(목록 크기 상한, 합계 = 항목 합, 필터 필드가 실제로 반영됐는지). 위반 시 **예외로 막는다**(로그 경고만 하면 SilentGuard의 '경고' 조건과 같다). 9/16 노트의 기준대로 이건 서버(우리) 쪽 문제가 아니라 상대 API 문제이므로 502/503 계열로 매핑하는 게 맞다
- **CI 규칙 파일은 보호 브랜치에서 읽는다** — GitHub Actions에서 `pull_request` 이벤트는 PR 쪽 워크플로를 돌리므로, 규칙·체크리스트는 `CODEOWNERS` + 브랜치 보호로 잠그거나 기본 브랜치 체크아웃에서 읽게 한다
- **저장소 루트에 "이 앱을 어떻게 띄우고 확인하나"** — 에이전트용 verify 스킬이자, 3주 뒤 나 자신이 읽을 문서

**반론·회의적 시각.** "90%를 Claude가 쓴다"는 **Anthropic 자사 블로그** 다 — 자사 제품 홍보와 분리해 읽어야 하고, 정량 근거는 "최대 10점" 하나뿐이다. E2E 우선론은 테스트 피라미드(유닛이 많고 E2E가 적어야 한다)와 정면으로 다르다 — 사람이 쓰고 돌릴 때의 비용 구조가 에이전트에선 뒤집힌다는 주장이지 보편 법칙은 아니다(E2E는 느리고 플레이키하다는 단점을 글도 인정). "두 번 막히면 세 번째 통과"는 게이트를 **우회 가능** 하게 만든 타협이다. SilentGuard는 초록만 읽었고, 불변식을 **누가·어떻게 정의하느냐**(API마다 사람이 써야 하나)가 실무 비용의 핵심인데 확인하지 못했다. HF 업보트 2.

### 5. SPILLWAY — 프롬프트 인젝션을 "문장 판독"이 아니라 "출처 조회"로 막는다 (원리는 AI 심층으로)

SAINT Machines(KAIST·중앙대). 도구 쓰는 에이전트가 이메일·파일·결제를 다룰 때, 웹페이지나 공유 문서에 숨은 지시가 데이터·돈을 공격자에게 보내게 만드는 공격을 막는다. 핵심 관찰: **이메일의 발신자·결제의 계좌는 도구가 돌려준 '타입 있는 필드'로 오고, 주입된 지시는 '자유 텍스트'로 온다.** 그래서 호출의 대상(수신자·계좌·채널·URL)이 사용자 요청에 있거나, 읽기 전용 도구의 타입 필드에서 왔거나, 고정 위임 규칙이 허용할 때만 통과시킨다 — **모델 호출 없는 집합 조회**. AgentDojo 3개 백본 × 4개 스위트 12칸에서 **범위 내 공격 성공 0/2,847**, 공격 하 효용 평균 48.9%(차순위 DRIFT 45.3%), 추가 모델 호출 0.19~0.39회/에피소드. 범위 밖(공격자가 직접 이메일을 보내 발신자 필드를 채우는 경우, 정당한 대상에게 주입 내용을 보내는 경우)은 스스로 명시. 원리·한계는 AI 심층 「AI - 구조로 판정하는 프롬프트 인젝션 방어」. [HF](https://huggingface.co/papers/2611.07222) · [프로젝트 페이지](https://saintmachines.github.io/spillway/) · [GitHub](https://github.com/saintmachines/spillway)

## 깊게 본 것

### 1. Nginx HTTP/2 원격 코드 실행 두 건(CVE-2026-123633·123007) — 앱 코드가 멀쩡해도 문지기가 뚫린다

**무슨 일인가.** 2026-11-18 F5의 보안 릴리스와 함께 조율 공개. Wiz Research·Ikotas Labs·Metnir·Rapid7·Xint 다섯 팀이 **독립적으로** 찾았다. 둘 다 CVSS 4.0 **9.2**, 인증 없는 원격 코드 실행, **HTTP/2가 켜져 있어야** 한다.

| CVE | 결함 | 추가 조건 | 영향 버전(OSS) |
| --- | --- | --- | --- |
| 123007 | HTTP/2 `send_window` 정수 언더플로 → 범위 밖 메모리 복사 | **기본 설정 + HTTP/2면 충분**. 백엔드·서드파티 모듈 없이 정적 파일만 서빙하는 서버에서 RCE 시연(64비트, HTTPS) | 1.9.5(2015) ~ 1.31.8 |
| 123633 | HTTP/2 연결 use-after-free | 리버스 프록시로 쓰면서 연결 슬롯이 모자랄 때 | 1.19.7 ~ 1.31.8 |

수정 버전은 **1.30.7 stable / 1.31.9 mainline**(Plus는 37.0.7.1·37.2.0.1 / 37.0.8.1·37.3.0.1). 같은 릴리스에 **9.2짜리가 세 건 더** 있다 — HTTP/3 프록시 UAF(121810), DNS 리졸버 응답 처리 UAF(123634, 공격자가 업스트림 호스트명을 조종할 때), 메일 프록시 UAF(113425). 그 밖에 TLS 1.3에서 요청 본문 읽기 무한 루프(118899, 8.7), `alias`+`try_files` 버퍼 오버플로(125283) 등 총 10건.

**배경 — HTTP/2 흐름 제어가 뭔가.** HTTP/2는 연결 하나에 여러 요청(스트림)을 섞어 보낸다. 받는 쪽이 감당 못 할 만큼 쏟아지지 않게, 각 연결·스트림에 "아직 더 보내도 되는 양"인 **윈도**(기본 65,535바이트, 상한 2³¹−1)를 둔다. 보내는 쪽은 DATA를 보낼 때마다 윈도를 깎고, 받는 쪽은 여유가 생기면 `WINDOW_UPDATE` 프레임으로 윈도를 늘려 준다. 상한을 넘기면 프로토콜 오류(FLOW_CONTROL_ERROR)여야 한다. Nginx는 응답을 보내는 입장이니 클라이언트가 늘려 주는 윈도를 `h2c->send_window` 로 센다.

**기술적으로 어떻게 동작하나 — 123007, "환불"이 상한을 넘기까지.**

1. Nginx는 응답 데이터를 **큐에 넣는 시점** 에 그 크기만큼 `send_window` 를 깎는다
2. 그 스트림이 취소되면 `ngx_http_v2_filter_cleanup()` 이 아직 안 보낸 데이터를 버리고 깎았던 만큼 **돌려준다**: `h2c->send_window += window;` — 여기서 **상한 검사를 안 한다**
3. 공격자가 데이터가 큐에 있는 동안 `WINDOW_UPDATE` 로 윈도를 이미 상한 근처까지 늘려 놨다면, 환불이 카운터를 **상한 위로** 밀어 올린다
4. 다음 `WINDOW_UPDATE` 검사: `if (window > MAX_WINDOW - h2c->send_window)` — 남은 여유를 "상한 − 현재값"으로 계산하는데, 현재값이 상한보다 크니 결과는 음수여야 한다. 그런데 **부호 없는 정수** 라 음수를 못 담고 거대한 양수로 되감긴다(예: 32비트에서 −100 → 4,294,967,196). 검사는 "여유가 엄청 많다"고 판단해 계속 늘리게 둔다
5. 이 값이 `ngx_http_v2_send_chain()` 에서 부호 있는 `off_t` 로 바뀌며 **음수 길이** 가 되고, 응답 버퍼의 끝 포인터가 시작 포인터보다 앞에 놓인다
6. TLS 송신 경로 `ngx_ssl_send_chain()` 이 이 버퍼를 처리하며 부호 변환을 몇 번 더 거쳐 **범위 밖 복사** — 메모리 유출 → 힙 손상 → RCE. 메모리를 먼저 읽을 수 있으니 **ASLR이 막지 못한다**

어제 Java4Shell의 "출력 길이 −1 → 마스크 전부 1"과 **같은 모양** 이다: 음수가 되면 안 되는 길이가 음수가 되고, 부호 없는 해석이 그걸 "아주 큰 수"로 바꿔 경계 검사를 통과시킨다. 언어가 C든 어셈블리든 "길이 계산 → 부호 변환 → 경계 검사" 사슬 어딘가에서 상한을 안 보면 같은 일이 난다.

**123633 — "닫아도 되는 연결" 목록에 남은 활성 연결.** Nginx는 새 연결 자리가 모자라면 닫아도 되는 연결(재사용 가능 목록)부터 닫는다. HTTP/2 연결은 처리 중인 요청이 없으면 이 목록에 오르고, 요청이 시작되면 빠져야 한다. 공격자가 HEADERS 프레임을 **반만** 보내면 연결이 목록에 오른 채 나머지를 기다린다. 나머지를 보내면 요청 스트림이 생기는데 **목록에서 빼는 코드가 없다**. 이 요청을 업스트림으로 프록시하려고 새 연결을 열 때 슬롯이 모자라면 `ngx_drain_connections()` 가 바로 이 연결을 골라 닫고 — GOAWAY 프레임조차 못 만드는 오류 경로에서 메모리를 해제 — 원래 요청은 해제된 메모리를 계속 쓴다. 슬롯 부족 조건은 `worker_connections` 한도와 관련 있으니, 공격자가 연결을 많이 열어 이 상태를 유도할 수 있을 것으로 보인다(이 부분은 내 추론, 원문은 "슬롯이 모자랄 때"까지만 썼다).

**AI는 어디에 쓰였나.** Wiz는 자사 AI 코드 스캐닝 하네스 **Wiz Atlas** 로 두 결함을 **발견** 했고, 영향 **검증**(RCE 가능성 확인)에 Gemini 4 Carbon과 "ChatGPT 5.6 Sol"(원문 표기 그대로)을 썼다. 타임라인이 흥미롭다 — 123633은 10/21 신고, 123007은 **공개 이틀 전인 11/16** 에 신고했는데 F5는 이미 다른 팀의 신고로 11/18 릴리스에 넣어 둔 상태였다.

**실무에 무슨 의미인가 (Spring Boot 앞단에 Nginx를 둔다면).**

| 확인할 것 | 방법 |
| --- | --- |
| 버전 | `nginx -v`. 1.30.7 / 1.31.9 미만이면 해당. Docker라면 `nginx:stable`·`nginx:mainline` 태그를 **다시 pull·재빌드** 해야 바뀐다(고정 다이제스트면 그대로) |
| HTTP/2 사용 여부 | `nginx -T \| grep -n http2` — 1.25.1 이상은 `http2 on;` 지시어, 이전 문법은 `listen 443 ssl http2;` |
| 임시 완화 | 1.25.1+에서 `http2 off;` **그리고** `listen` 의 `http2` 파라미터도 제거 → 설정 테스트(`nginx -t`) → reload 후 **옛 워커가 끝났는지** 확인. 패치 뒤 다시 켠다 |
| 탐지 | 확정 지표는 없다. 워커 프로세스의 예상 밖 크래시, Nginx가 띄운 명령, 대량 `WINDOW_UPDATE` 를 보내는 장수 HTTP/2 연결이 "일반 경고 신호" |

- **이 CVE는 Nginx 코드의 결함** 이다. Spring Boot 내장 Tomcat·Netty의 HTTP/2(`server.http2.enabled`)는 별개 구현이라 이 두 CVE와는 무관하다 — 다만 "앞단이 HTTP/2를 종단하고 뒤는 HTTP/1.1"인 흔한 구성에서 위험은 앞단에 몰린다
- **CDN·WAF가 HTTP/2를 종단** 하면 공격 프레임이 그대로 Nginx에 닿지 않아 일부 완화될 수 있다(구현에 따라 다름). 반대로 L4 로드밸런서(TCP 통과)는 아무것도 막지 않는다
- **Nginx 한 대 = 여러 서비스의 공용 입구.** 11/17 노트에서 본 "한 지점이 전부를 쥔다"(Optimizely 스니펫)와 같은 구조다. WMS 프로젝트를 배포할 때 Nginx를 쓴다면 이번이 "버전 고정 + 이미지 재빌드 절차"를 문서로 남길 기회다

**반론·회의적 시각.**

- **원격 메모리 손상 공격은 어렵다** — Wiz 스스로 썼다: 메모리 주소 유출, 힙 모양 맞추기, 버전·빌드·설정별 대응이 필요하다. PoC는 비공개
- **하지만 PHP2Shell 경험상** 실제 공격은 "많은 고객이 똑같은 빌드·설정을 쓰는 패키지 제품"부터 시작한다(Wiz). 어플라이언스·공식 Docker 이미지 기본 설정이 1순위 표적일 것이다
- **123007의 "기본 설정에서 RCE"는 시연 조건이 구체적이다** — 공식 1.31.7·1.31.8 빌드, 64비트, HTTP/2 over TLS, 메모리에서 응답 데이터를 보내는 경로. 1.9.5부터 모든 버전이 같은 정도로 공격 가능하다는 뜻은 아니다
- **"AI가 찾았다"의 무게.** 다섯 팀 중 AI 사용을 밝힌 건 Wiz다. 나머지 팀의 방법은 원문에 없다. "3주 연속 AI 발견"은 브리핑의 프레이밍이고, 정확히는 "AI를 쓴 팀이 **포함된** 독립 발견이 3주 연속"이다

### 2. Gemini 4 Neon과 Kernel의 Carbon 해부 — 비용은 지능이 아니라 행동에서 샌다

**무슨 일인가 (Kernel).** Kernel의 **비공개 버그 수정 평가**(버그 수정 직전 코드베이스 + 증상만 적힌 보고서 → 원인 진단·수정, 관련 없는 변경 금지)에서 Carbon이 Opus·Astra가 몇 분에 끝내는 과제에 거의 한 시간을 썼다. 왜 그런지를 쪼갰다.

1. **느린 추론은 일부** — Carbon의 초과 시간 중 추론 속도로 설명되는 건 Astra 대비 16~30%, Opus 대비 45~49%
2. **나머지는 더 긴 실행** — 버그당 단계 약 7배, 파일 읽기·명령 실행 같은 행동 약 11배, 출력 약 7배, 매 단계 대화를 다시 보내니 **입력 처리량 16배+**
3. **단계의 약 절반이 요청 밖 작업** — 원인을 찾은 뒤에도 수정에 필요 없는 경로까지 점검, 보고서상 이미 배제된 경우를 대비한 방어 코드 준비. 표본 과제에서 Astra(max)는 1분 안에 원인 파악 → 3분 뒤 수정. Carbon(high)은 약 6분에 원인을 찾고 **25분 동안 코드를 쓰지 않았다**
4. **기계적 비효율** — Astra는 단계당 도구 2회+로 여러 파일을 한꺼번에 읽고, Carbon은 단계당 약 1회·한 파일씩. 읽은 줄 중 이미 본 줄: **Carbon 39% 대 Astra 7%**. 이 둘이 초과 시간의 약 25%
5. **개입 실험(1개 과제)** — 5턴마다 "이미 수정에 필요한 정보를 충분히 확보했는가?"를 자동 삽입 → **37분 → 28분**, 원인 지목 후 첫 수정까지 25분 → 약 10분. "무엇을 아느냐보다 어떻게 행동하느냐"
6. **하네스 바꿔도 같았다** — opencode·mini-SWE-agent에서도 유의미한 차이 없음. low로 내리면 이미 읽은 코드를 맴돌며 수정을 아예 못 만드는 경우가 많았다

**배경 — 왜 이 둘을 같이 읽나.** Kernel은 원인 가설로 "확신 부족"과 "**추가 단계의 불이익보다 정답 보상이 큰 학습에서 생긴 과탐색 습관**"을 들었다. 후자라면 이건 모델의 지능 문제가 아니라 **보상 설계** 문제다 — 어제 GPT-6.2가 "토큰을 아끼도록" 학습하자 장애물 보고도 줄었다는 것의 거울상. 한쪽은 너무 많이 하고, 한쪽은 해야 할 말을 아낀다. Neon 발표문이 under-service(덜 하기)와 overreach(넘어서 하기)를 **둘 다** 지표로 낸 것도 같은 맥락이다.

**실무에 무슨 의미인가.**

- **모델 선택표에 "과제당 시간"을 넣는다.** 같은 정답이라도 6분과 50분은 다른 도구다. Kernel처럼 내 과제 2~3개로 단계 수·읽기 반복률을 직접 재 보는 게 벤치마크 점수보다 낫다(11/17 노트의 "A/A 기준선"처럼, 같은 모델 두 번 돌린 편차부터)

**반론·회의적 시각.**

- **Neon 수치 대부분이 발표 주체의 선택** 이다. 3위라는 걸 스스로 밝힌 건 정직하지만, 과제당 비용 비교는 Google이 고른 벤치마크·설정 기준
- **하네스 효과가 서로 어긋난다.** Neon은 "하네스만 바꿔 SWE-sweep 3배"를 자랑하고, Kernel은 Carbon에서 하네스를 바꿔도 차이가 없었다고 했다. 어제 FrontierHarness의 "모델×하네스 조합 효과"로 보면 모순은 아니다 — **하네스 효과는 모델마다 다르다**. Neon의 3배는 Google 자사 하네스와 자사 모델 조합이다
- **Kernel 분석의 표본** — 비공개 평가라 과제 수·분포를 확인할 수 없고, 5턴 질문 실험은 **과제 1개**. Carbon 쪽 HN 댓글엔 "느리지만 결과물 완성도가 높다·내가 놓쳤을 예외까지 처리" 같은 반대 경험도 많다. 요청 밖 작업이 늘 낭비인지는 과제 성격(보안 수정 vs 빠른 패치)에 따라 다르다

### 4. Energy-Based Reasoners — 반복 추론 모델이 "언제 멈출지"를 스스로 재게 하기 (원리는 AI 심층으로)

Chen·Gladstone·Li·Ji·Du(arXiv 2611.08977). 같은 블록을 여러 번 돌려 잠재 공간에서 생각하는 **반복(looped) 모델** 은 "지금 상태가 얼마나 좋은지"를 재는 자가 없어 고정 횟수만큼 돌거나 외부 검증기가 필요했다. ### 5. Self-Improvement Memory(Google) — 하네스를 물려줄 때 "왜"까지 물려준다

**무슨 일인가.** 에이전트의 하네스(프롬프트·검증 로직·도구 구성)를 자동으로 고쳐 나가는 **하네스 최적화** 연구는 보통 모델·벤치마크를 고정하고 한다. 그런데 모델이나 벤치마크가 바뀌면, 다음 최적화기는 진화된 하네스 중 무엇을 유지하고 무엇을 고칠지 정해야 하는데 **하네스 코드만으로는 각 수정이 왜 들어갔고 어떻게 작동했는지 알 수 없다**. Google Cloud AI·DeepMind·펜실베이니아 주립대 팀은 이 설정을 **CRSI(Continual Recursive Self-Improvement)** 로 정의하고 **SIM** 을 제안했다. 과제를 푸는 정책 모델의 가중치는 얼린 채, **하네스 최적화기** 쪽에 기억을 붙인다.

**어떻게 동작하나.** SIM은 수정 이력을 **"반복되는 하네스 문제" 단위로 묶고**, 각 수정마다 ① 근거(왜), ② **예상 결과**, ③ **실제 결과**, ④ 평가 맥락(어떤 모델·벤치마크에서)을 기록한다. 수정을 제안하는 쪽과 고르는 쪽이 모두 이 기록을 읽고, 새 시도가 기록을 계속 늘린다.

**결과.** 같은 출발 하네스·목표 과제·정책·라운드 수·후보 예산을 맞추고 비교. 4개 도메인에서 교차 데이터셋 6개·Opus→Gemini 교차 모델 4개 비교 모두 "하네스만 이어받기"·"근본 원인 기록만 이어받기"보다 최종 점수가 높았다. 코딩에서 독립 출발 10회 × (SIM 유/무) 짝 비교: **9쌍에서 SIM 우세, 평균 +2.36점(95% CI 1.05~3.68, p=0.003)**.

**실무에 무슨 의미인가.** 이건 사람 팀의 **결정 로그·ADR** 이 하는 일과 정확히 같다. 코드(커밋)는 남는데 "이 검사를 왜 넣었는지, 무엇을 기대했는지, 실제로 효과가 있었는지"가 사라지면 다음 사람은 그걸 지워도 되는지 모른다. HF 댓글의 "엔지니어가 실험 노트에 쓸 내용"이라는 표현 그대로다. WMS 프로젝트의 결정 로그(문제 → 대안 → 선택 근거 → 기각 사유 → 검증)에 **"예상 결과"와 "관찰 결과"를 따로 적는 칸** 을 두면 SIM의 핵심 두 필드가 된다 — 예상과 관찰이 갈린 기록이 가장 값진 기록이다. CLAUDE.md·스킬 파일에 규칙을 넣을 때도 규칙 옆에 "이 규칙이 막으려던 실패"를 한 줄 적어 두는 게 같은 원리.

**반론·회의적 시각.** 저자 스스로: 실행 인터페이스가 호환되는 경우에만 성립하고, 주요 교차 도메인 비교는 **조건당 1회 실행** 이 대부분이며, **라운드 수를 맞춘 것이 토큰·시간 비용이 같다는 뜻은 아니다**(기록을 읽는 비용이 추가됨). 모든 이전에서 개선을 보장하지 않는다(10쌍 중 1쌍은 음수). HF 댓글의 질문 — "예상 대 관찰 기록이 핵심인가, 근거만으로 대부분이 나오나? 필드별 제거 실험을 했나?" — 에 대한 답은 초록에 없다. 초록과 저자 코멘트만 읽었다.

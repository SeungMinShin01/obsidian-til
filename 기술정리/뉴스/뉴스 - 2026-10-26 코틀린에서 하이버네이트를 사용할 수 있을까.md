원문: 코틀린에서 하이버네이트를 사용할 수 있을까? — 김지희, 김석홍 · 2020-05-11 · Backend
(예습자료: 글의 설명을 정리한 것이며 사용자 미검증)

## 배경
글은 사장님 혜택 관리 신규 프로젝트에서 개발 언어로 코틀린을 채택하면서 ORM으로 하이버네이트를 쓴 경험을 다룬다. Exposed·Ktorm 같은 코틀린 전용 ORM도 있었지만 새 언어에 새 ORM까지 얹는 위험이 크다고 보고, 자바와 상호운용되는 익숙한 하이버네이트를 선택했다고 설명한다.

## 핵심
- **문제 1 — data class**: `toString`·`equals`·`hashCode`가 자동 생성되는데, 연관 엔터티가 `toString`에 포함되면 지연 로딩 예외나 양방향 매핑 스택 오버플로가 날 수 있다. 하이버네이트 가이드는 equals/hashCode를 ID(또는 natural-id/business-key) 기준으로 권장한다고 한다.
- **문제 2 — 지연 로딩 실패**: `FetchType.LAZY`인데 프록시 대신 실제 객체가 들어와 접근하지 않아도 쿼리가 두 번 나갔다. 코틀린 클래스는 기본 `final`이라 프록시를 만들 수 없기 때문이다.
- **data class 기각**: data class는 `open`·`abstract`·`sealed`·`inner`가 될 수 없어서 지연 로딩을 쓰려면 엔터티에 쓸 수 없다고 결론 낸다. allopen을 data class에 적용하면 open이 되는 것은 확인했지만 공식 문서에서 근거를 못 찾아 쓰지 않기로 했다.
- **allopen 플러그인(채택)**: `kotlin("plugin.allopen")`에서 `allOpen { annotation("javax.persistence.Entity") }`로 `@Entity` 클래스를 자동 open.
- **noarg 플러그인(채택)**: 하이버네이트가 리플렉션으로 객체를 만들기 위한 인자 없는 생성자를 컴파일러가 생성. 같은 `@Entity`를 대상으로 지정. 글의 예시는 Kotlin 1.3.71 플러그인.
- **kassava로 메서드 구현(채택)**: `au.com.console:kassava:2.1.0-rc.1`(`kotlinHashCode`가 이 버전부터). equals·hashCode는 `id`만, toString은 연관 객체(`company`)를 뺀 `id`·`name`만 쓰도록 companion object 배열로 지정.
- **검증**: `@ManyToOne(fetch = LAZY)`인 `Employee.company`가 프록시로 들어오고 접근 시점에 쿼리가 나감을 확인. 연관 객체가 toString에 안 나오는지, id가 같으면 equals가 참인지 단위 테스트로 확인했다고 한다.

## 내 프로젝트와의 연결
직접 연결은 약하다: WMS는 Spring Boot(자바 가정)이고 수집기는 SQLite 저장 계층이라 코틀린 엔터티를 쓸 일은 없다. 구조적으로 비슷한 지점은 JPA 엔터티 설계 원칙이다 — 지연 로딩은 프록시 생성이 가능한(final이 아닌) 클래스가 전제이고, equals/hashCode는 ID 기준, toString에는 연관 객체를 넣지 않는다는 점은 자바에서 Lombok `@Data`를 엔터티에 쓸 때의 함정과 같은 모양이다. WMS 입고·재고·출고 엔터티의 양방향 연관(입고-입고상세 등)과 N+1 점검에 적용해볼 수 있는 체크포인트다.

## 오늘 정리할 것
1. WMS(또는 연습) 엔터티 하나에서 `@ManyToOne(fetch = LAZY)` 필드의 실제 타입이 프록시인지 `getClass()`로 찍어 확인해 본다(final 클래스에서는 어떻게 되는지도 비교).
2. 엔터티에 Lombok `@Data`/`@ToString`을 쓰면 양방향 연관에서 무슨 일이 생기는지 작은 코드로 재현해 에러 메시지를 적어 둔다.
3. 엔터티의 equals/hashCode를 ID 기준으로 쓸 때 저장 전(id null)과 후의 동작 차이를 정리한다.
4. 글이 쓴 "하이버네이트가 인자 없는 생성자를 요구하는 이유"를 JPA 스펙·하이버네이트 문서에서 직접 찾아 한 줄로 적는다.

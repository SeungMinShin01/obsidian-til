원제: MySQL을 이용한 분산락으로 여러 서버에 걸친 동시성 관리 (권순규 · 2019-05-30 · Backend) — 예제 코드: github.com/woowabros/mysql_user_level_lock_demo

## 배경

광고시스템에서 User와 Card가 1:N이고 "User당 Card는 2개까지"라는 제약이 애플리케이션 코드에 걸려 있었다. 글은 한 건씩 요청하면 제약이 지켜지지만, 같은 User로 20건을 동시에 요청하면 모두 성공 응답이 나가고 Card가 20개 생성되는 상황을 재현해 보인다. "개수 확인 → 생성"이 원자적이지 않아 여러 서버·스레드에 걸쳐 제약이 깨진 것이고, 그래서 생성 구간에 분산락을 걸기로 했다고 설명한다.

## 핵심

- 대안 검토: ZooKeeper·Redis 분산락은 인프라 구축비와 유지보수비가 새로 든다. 이미 쓰던 MySQL은 추가 비용이 없고 분산락 사용량도 크지 않아 MySQL을 택했다고 한다. USER-LEVEL LOCK은 락에 이름을 붙일 수 있어 애플리케이션에서 제어하기 쉽다는 점도 이유로 든다.
- `GET_LOCK(str, timeout)`: 이름 str로 timeout초 동안 획득 시도(음수면 무한 대기). 반환 1 성공 / 0 타임아웃 / NULL 오류. **트랜잭션 commit·rollback으로 풀리지 않고 세션(커넥션)에 묶인다**. 대기 순서는 보장되지 않는다.
- 버전 차이: 5.7 미만은 한 세션이 락 하나만 보유(새로 잡으면 이전 락 해제), 이름 길이 무제한. 5.7 이상은 여러 락 동시 보유, 이름 60자 제한.
- 보조 함수: `RELEASE_LOCK(str)`(1 해제 / 0 내 락이 아님 / NULL 없음), `RELEASE_ALL_LOCKS()`, `IS_FREE_LOCK(str)`, `IS_USED_LOCK(str)`(보유 커넥션 id 반환).
- 구현 형태: `executeWithLock(lockName, timeout, Supplier)` 한 번 호출로 락 획득 → 콜백 실행 → 해제. 락용 커넥션 풀과 비즈니스 로직 커넥션 풀을 분리하고, 그래서 `executeWithLock`에는 `@Transactional`을 붙이지 않았다.
- 1차 시도(반려) — `NamedParameterJdbcTemplate`: 쿼리마다 풀에서 커넥션을 빌리고 반납하므로 `GET_LOCK`과 `RELEASE_LOCK`이 다른 커넥션에서 실행된다. 결과는 락 해제 실패, 그리고 반납된 커넥션(=락 보유 세션)을 다른 스레드가 받아 같은 이름 락을 "재진입"해 제약이 다시 깨지는 현상. 글은 커넥션 로그로 이를 보여준다.
- 2차 대안(반려) — `@Transactional`로 묶기: 같은 커넥션이 보장돼 제약은 지켜지지만, 락 획득과 로직이 같은 풀을 쓰게 되어 락 대기가 로직 쪽 커넥션을 잡아먹는 영향이 생긴다고 보고 포기했다.
- 최종: `DataSource`를 주입받아 JDBC로 커넥션을 직접 꺼내 `GET_LOCK`·`RELEASE_LOCK`을 같은 커넥션에서 실행하고 finally에서 해제. 이렇게 해서 제약이 지켜지는 것을 확인했다고 한다(본문 코드 블록은 페이지에서 비어 있어 세부 코드는 예제 저장소의 `UserLevelLockFinal.java`를 봐야 한다).

## 내 프로젝트와의 연결

- WMS: 재고 차감·출고 할당처럼 "확인 후 변경"이 여러 요청에서 동시에 일어나는 지점과 구조가 같다. 글의 교훈은 락의 종류보다 **락이 어디에 묶이는지(세션·커넥션)를 커넥션 풀이 어떻게 섞는지**에 있다. WMS가 Spring Boot + HikariCP + JPA라면 `GET_LOCK`을 JPA 네이티브 쿼리로 부를 때 같은 함정이 생길 수 있다. 다만 단일 행 재고 차감이라면 비관적 락(`SELECT ... FOR UPDATE`)이나 낙관적 락(`@Version`)이 더 단순할 수 있어, 분산락은 "여러 행·여러 테이블에 걸친 규칙"에 쓰는 비교 후보로 두는 편이 맞아 보인다. 9/14 노트(WMS 재고 이관 분산 락)의 Redis 방식과 비용·위험을 나란히 비교할 거리다.
- 수집기: SQLite 단일 파일·단일 러너라 서버 간 분산락은 직접 필요하지 않다. 구조적으로 비슷한 지점은 GitHub Actions 동시 실행(스케줄과 수동 실행이 겹칠 때) 방지 정도 — 이건 `concurrency` 그룹이 같은 역할을 한다.

## 오늘 정리할 것

1. MySQL 8 공식 문서에서 `GET_LOCK` 반환값·커넥션 종료 시 자동 해제 여부를 확인하고 표로 정리
2. Spring에서 커넥션 하나를 고정해 쓰는 방법 3가지(`DataSource.getConnection()` 직접, `@Transactional`, `DataSourceUtils`)의 차이를 메모
3. WMS 재고 차감 시나리오 하나를 골라 비관적 락 / 낙관적 락 / 이름 있는 락(`GET_LOCK`) 장단점 비교표 작성
4. 예제 저장소의 `MultiThreadRequest`처럼 20개 동시 요청 테스트(`ExecutorService` + `CountDownLatch`) 뼈대를 손으로 적어보기

## 배경

글쓴이의 팀은 구 정산 시스템을 신규 정산 플랫폼으로 옮기면서, "이 값이 무슨 뜻인지·어떤 값만 허용되는지·어디까지 바꿔야 하는지"를 코드만 보고는 알 수 없는 상황에 부딪혔다고 설명한다. 의미는 문자열·매직넘버("Y"/"1"/true, "01")에 흩어져 있고, 그 값에 딸린 계산·분기 로직은 static 유틸 메소드와 if문으로 떨어져 있었으며, 카테고리 같은 코드값은 별도 코드 테이블에서 조회해야 했다. 글은 이 문제를 신기술이 아니라 "Java Enum은 완전한 클래스"라는 점을 이용해 값·관계·행위를 한곳에 묶는 방식으로 풀었다고 정리한다.

## 핵심 — 문제 → 시도 → 반려한 대안 → 최종 해결

- **① 같은 의미, 다른 표현 묶기** — 배치가 origin 테이블("Y"/"N")을 table1("1"/"0")·table2(true/false)로 옮길 때, 기존엔 변환 메소드로 처리했다. 글은 이 방식이 "Y·1·true가 같은 의미"임을 코드로 드러내지 못하고 값이 늘 때마다 if문 메소드가 늘어난다며 반려하고, 한 Enum 상수가 세 표현을 필드로 함께 갖는 형태(예: TableStatus)로 바꿨다고 설명한다.
- **② 상태와 행위를 한곳에** — 코드값 CALC_A/B/C마다 계산식이 다른데, static 계산 메소드로 두면 "이 코드는 이 메소드로 계산해야 한다"는 관계를 강제할 수 없어 같은 메소드를 중복 생성하거나 호출을 누락할 위험이 있다고 본다. 해결은 각 Enum 상수가 자기 계산식을 갖게 하는 것 — Java 8은 함수형 인터페이스 필드(람다)로, Java 7 이하는 추상 메소드를 상수별로 구현하는 방식으로.
- **③ JPA 저장은 `@Enumerated(EnumType.STRING)`** — 엔티티 필드를 String 대신 Enum으로 선언하되, ordinal(숫자)로 저장하면 상수 사이에 새 값이 끼어들 때 기존 숫자가 다른 상수를 가리키게 되므로 name 저장을 권한다고 설명한다.
- **④ 데이터 그룹 관리** — 결제수단(신용카드·페이코·카카오페이 등)이 어느 결제종류(카드 등)에 속하는지를 문자열+if문으로 판별하던 방식은 관계(포함인지 대체값인지)가 안 보이고, 입력·출력이 아무 문자열이나 될 수 있으며, 종류별 기능(Print·Push 등)을 추가할 때마다 분기 코드가 반복된다는 점(글은 이 세 번째를 결정적 이유로 꼽는다) 때문에 반려된다. 1차로 PayGroup Enum이 결제수단 문자열 목록을 갖게 했고, 남은 문제(결제수단이 여전히 문자열)를 풀려고 결제수단도 PayType Enum으로 바꿔 타입 안전성까지 확보했다고 한다.
- **⑤ 관리 주체를 DB에서 객체로** — 코드 테이블 방식은 매직넘버의 의미를 DB를 뒤져야 알고, UI를 그릴 때마다 조회 쿼리가 나가며(캐시로 완화 가능하다고 인정), 코드별 로직이 Service·유틸로 흩어진다. 카테고리는 "6개월에 1~2개 추가될까 말까"이고 하루 4~5번 배포가 가능하니 테이블보다 Enum이 낫다고 판단했다고 한다.
- **⑥ Enum을 화면에 내보내기** — Enum을 그대로 JSON으로 내면 상수 name만 나온다. DB 저장용 name과 화면용 title 두 값이 필요해서, 두 값을 내는 인터페이스를 Enum이 구현하게 하고 이를 받아 만드는 값 객체(VO)로 변환해 응답한다. 매번 `values()`로 VO를 만드는 반복이 아쉬워, 런타임에 바뀌지 않는다는 점을 이용해 팩토리 클래스 `EnumMapper`를 Bean으로 등록하고 필요한 Enum 타입을 미리 담아 둔다.
- **결과와 한계** — 신규 정산 플랫폼에는 단순 코드 테이블이 하나도 없고, 구 시스템의 코드 테이블 3개·수백 개 코드를 모두 제거했다고 한다. 다만 값의 추가·변경이 잦아 관리자 페이지에서 직접 고치는 편이 나은 경우엔 테이블이 맞을 수 있고, "망치만 든 사람에게는 모든 게 못" — Enum과 테이블의 경계를 잘 나눠야 한다고 스스로 단서를 단다.
- **글이 꼽는 가장 큰 효과** — Enum이 **문맥(Context)** 을 담는다는 것. 같은 문자열 "a"라도 상황 A와 B에서 의미가 다른데, 문자열은 이를 표현 못 하고 Enum은 표현할 수 있다는 설명이다.

## 내 프로젝트와의 연결

WMS와 구조적으로 가장 가깝게 맞닿는 지점은 상태값이다. 입고(예정→검수→적치 완료), 출고(주문 접수→할당→피킹→포장→출하), 재고 이동 유형처럼 "값마다 허용되는 다음 상태나 계산이 다른" 코드가 많으니, 글의 ②처럼 각 상태 Enum이 자기 전이 규칙이나 수량 계산 방식을 갖게 하면 Service의 if/switch 분기를 줄일 수 있을 것이다. 엔티티에 `@Enumerated(EnumType.STRING)`을 기본으로 두는 것과, React 화면의 select box(로케이션 유형·입출고 사유 등)에 name+title을 내려주는 ⑥의 EnumMapper 패턴도 그대로 옮겨 볼 만하다. 수집기 쪽은 직접 연결이 약하다 — SQLite에 저장하는 공고 상태(신규·갱신·마감)나 수집 소스 구분을 문자열 대신 Enum(파이썬 `enum`)으로 묶고 저장값을 name 문자열로 고정하는 정도가 구조적으로 비슷한 지점이다.

## 오늘 정리할 것

1. JPA에서 `@Enumerated` 기본값(ORDINAL)과 STRING의 차이를 확인하고, 상수 순서를 바꿨을 때 ORDINAL 저장값이 어떻게 어긋나는지 한 줄로 정리하기.
2. WMS의 상태값 후보(입고·출고·재고 이동)를 목록으로 뽑고, 각 상태에서 허용되는 다음 상태를 표로 그려 "Enum에 넣을 행위"가 무엇인지 표시하기.
3. Java 8 `Function` 필드 방식과 상수별 추상 메소드 구현 방식의 차이를 짧은 예제로 직접 써 보고 장단점(가독성·확장성)을 비교하기.
4. 같은 Enum을 JSON으로 내렸을 때 기본 직렬화 결과(name만 나옴)를 확인하고, name+title을 내려주는 방법(VO 변환 / `@JsonFormat(shape = OBJECT)` 등)을 조사해 비교하기.

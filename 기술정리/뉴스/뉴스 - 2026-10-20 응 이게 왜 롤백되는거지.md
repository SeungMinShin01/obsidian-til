> 이전: [[뉴스 - 2026-10-19 에이전트는 닿는 곳까지 갔고, 기록은 몇 달 뒤에 따라왔다]]
> 다음: [[뉴스 - 2026-10-20 완료 보고는 증거가 아니고, 산출량은 품질이 아니다]]

원문: 구인본 · 2019-01-29 · Backend · 태그 Rollback, Spring, Transaction (SpringBoot 2.1.2, MySQL 5.7)

## 배경

글은 Beta 서버에서 `TransactionSystemException`/`RollbackException`("Transaction marked as rollbackOnly")이 반복된 상황에서 출발한다고 설명한다. 클래스 레벨 `@Transactional`인 OuterService가 내부 트랜잭션 서비스를 호출하고, 내부 메서드가 `save()` 후 `RuntimeException`을 던진다. 바깥에서 try/catch로 잡고 기본값으로 계속 진행했는데도 커밋 시점에 전체가 롤백됐다. 저자는 H2 대신 MySQL로 재현하고 Spring 소스를 따라가며 원인을 추적한다.

## 핵심

- 내부 메서드는 기본 전파 `PROPAGATION_REQUIRED`로 바깥 트랜잭션에 참여하므로 하나의 트랜잭션을 공유한다.
- 소스 추적 경로: `TransactionAspectSupport.completeTransactionAfterThrowing` → `RuleBasedTransactionAttribute.rollbackOn`(RuntimeException/Error면 롤백) → `AbstractPlatformTransactionManager`가 기존 트랜잭션을 rollback-only로 표시.
- 바깥에서 예외를 잡아도 표시는 해제되지 않아 커밋 시 `UnexpectedRollbackException`이 발생한다고 한다.
- 설정값: `isGlobalRollbackOnParticipationFailure` 기본 `true`, `isLocalRollbackOnly` 기본 `false`.
- 반려한 대안 1 — `PROPAGATION_NESTED`: JPA에서 `JpaDialect does not support savepoints`. `DataSourceTransactionManager` 직접 사용 때만 동작해 접었다.
- 반려한 대안 2 — `globalRollbackOnParticipationFailure=false`: Hibernate 세션처럼 실패 후 커밋이 불가능한 자원엔 안전하지 않다고 설명. 실제 적용·검증 여부는 글에 명확하지 않다.
- 결론: 버그가 아니라 의도된 기본 정책이며 정답 코드는 제시되지 않는다. 트랜잭션 경계와 예외 처리 방식을 다시 설계하라는 방향.
- 동료의 "트랜잭션 안에서 RuntimeException을 왜 잡으려 했나요?"를 계기로 예외 처리가 비즈니스 로직에 미치는 영향을 되돌아본다. CheckedException은 테스트하지 않았다고 한다.

## 내 프로젝트와의 연결

WMS에서 입고·재고·출고를 서비스로 나누면 "재고 차감 서비스(`@Transactional`)를 출고 서비스가 호출하고, 실패를 catch해 이력만 남기고 진행"하는 구조가 생기기 쉽고, 같은 rollback-only 함정이 재현될 수 있다(검증 필요). 수집기는 Spring이 아니라 직접 연결은 약하며, "한 건 실패를 기록하고 나머지는 계속"하는 부분 실패 격리(건별 커밋 단위)와 구조적으로 비슷하다. 2019년·Boot 2.1.2 기준이라 최신 버전 동작은 확인이 필요하다.

## 오늘 정리할 것

1. 재현 구조(바깥 `@Transactional` → 안쪽 REQUIRED가 RuntimeException)를 로컬에서 만들어 `logging.level.org.springframework.transaction=TRACE`로 `UnexpectedRollbackException` 확인.
2. `REQUIRES_NEW`로 바꾸면 내부만 롤백되고 바깥은 커밋되는지 확인, WMS 재고 차감/이력 기록 중 어디에 쓸지 메모.
3. 쓰는 Spring Boot 버전에서 `globalRollbackOnParticipationFailure` 기본값과 NESTED 동작 가능 여부를 소스/문서로 확인.
4. WMS에서 `@Transactional` 메서드가 다른 `@Transactional`을 호출하며 예외를 catch하는 지점을 3곳 이내로 목록화.

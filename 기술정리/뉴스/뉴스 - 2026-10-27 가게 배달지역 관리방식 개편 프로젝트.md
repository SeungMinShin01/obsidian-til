## 배경
글은 가게 배달지역을 행정동 단위로 관리하던 방식의 문제를 세 가지로 든다. (1) 법정동/행정동 경계 혼동 문의가 계속됨, (2) 행정동 영역이 바뀌면 그 동을 배달지역으로 가진 모든 가게가 영향을 받음, (3) 오토바이 진입이 어려운 곳만 제외하는 식의 유연한 설정이 불가능. 이를 Google S2로 바꾸고 기존 데이터를 Spring Batch 마이그레이션 툴로 옮겼다고 설명한다.

## 핵심
- S2 셀 id는 64비트: 앞 3비트 face(0~5), 이후 2비트씩 하위 셀 위치, 최대 30레벨(30레벨 셀 한 변 8~9mm). hex 문자열이 S2 token. 글은 하위 4셀→상위 1셀 정규화로 저장량을 줄일 수 있는 점이 채택의 결정적 이유였다고 한다.
- 레벨 범위: 최소 11 vs 14는 셀 수 차이가 작아 14, 최대 19 vs 20은 셀 수가 약 2배라 프런트 렌더링·배달 가능 판단 성능 테스트 후 19 → 14~19레벨.
- 변환 절차: WKT Polygon → S2LatLng → S2Point → S2Loop(CCW를 위해 `normalize()`) → `S2RegionCoverer`. `getCovering(region)`은 결과를 정규화해 최소 레벨보다 큰 셀이 섞이므로 반려, `getCovering(region, list)`(정규화 안 함)를 채택. 의존성 `s2-geometry-library-java` 1.0.1.
- 환경: 쓰기가 많아 공통 개발 DB 대신 스냅샷을 복원한 독립 DB에서 실행(과거 공통 환경에서 CPU가 급증한 경험).
- 1차 문제: covering 셀이 경계를 넘어 같은 토큰이 두 행정동에 들어갔고, 더 근본적으로 한쪽은 18레벨 1개/다른 쪽은 19레벨 2개처럼 레벨이 달라 토큰 그룹핑으로는 겹침이 안 잡혔다(그룹핑으로 나온 약 1.3만 개는 일부일 뿐).
- 해결: 경계 걸친 셀을 4분할 반복해 모두 19레벨로 통일 → 동일 레벨 중복 약 351만 개 노출 → 교차 면적이 가장 큰 행정동이 소유(`S2Polygon` 교차 연산), 나머지 삭제 → 중복 0, 토큰 약 1,500만→약 1,150만.
- 검증 3종: ① 전체 토큰을 `S2CellUnion`으로 정규화해 6~9레벨 셀만 시각화(빈틈이 있으면 정규화되지 않고 잘게 남음), ② 여러 행정동 동시 표시 시각화 툴로 방이동·신안 등 확인, ③ `S2CellIdTree`/`S2CellIdNode` 트리에 레벨 오름차순으로 삽입하며 경로 중간·목표 자리에 이미 셀이 있으면 겹침으로 판정 — 1,100만+ 토큰을 수 초에 검증.

## 내 프로젝트와의 연결
글은 지리 데이터 이야기라 직접 연결은 약하다. 구조적으로 비슷한 지점만 짚으면: 대량 변환 후 "중복/빈틈 없음"을 자동 검증기로 확인하는 방식은 수집기의 SQLite 적재 후 멱등성·중복 검증(공고 ID 유니크, 재실행해도 건수 불변)과 같은 발상이고, 운영 DB 대신 스냅샷 복원 DB에서 대량 쓰기 배치를 돌린 판단은 WMS 더미 데이터 부하 테스트 환경 구성의 참고가 될 수 있다. (사용자 미검증 — 글의 설명 기준.)

## 오늘 정리할 것
1. 수집기 SQLite 테이블에서 공고 고유키로 `GROUP BY ... HAVING COUNT(*) > 1` 쿼리를 짜 중복이 0인지 확인하고 결과를 한 줄로 적는다.
2. 글의 `getCovering` 두 메서드처럼 "같은 이름의 API가 결과를 몰래 바꾸는" 사례를 수집기/Spring 코드에서 하나 찾아 적는다(예: 재시도 시 중복 저장).
3. Spring Batch의 chunk 처리와 재시작(JobRepository)을 공식 문서에서 찾아 WMS 대량 더미 투입에 쓸 수 있는지 3줄로 정리한다.
4. 글의 "S2 레벨 14~19 선택 근거(셀 수 vs 성능)"처럼, 내가 내린 기술 선택의 수치 근거를 결정 로그(문제→대안→선택→기각 사유)로 하나 써 본다.

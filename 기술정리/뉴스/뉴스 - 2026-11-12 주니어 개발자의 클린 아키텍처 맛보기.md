## 배경

입사 1년 차 개발자가 "어떻게 하면 유지보수하기 쉽게 짤까"를 고민하다 Robert C. Martin의 Clean Architecture 블로그 글을 읽고, 그 핵심인 **의존성 규칙**(소스코드 의존성은 바깥 → 안쪽, 고수준 정책을 향해야 한다)을 실제 배달·배달료 업무 코드에 적용해 본 경험을 정리한 글이다. 글은 원문의 두 주제 — 경계를 넘는 데이터는 무엇이어야 하는가(What data crosses the boundaries), 제어 흐름과 의존 방향이 어긋날 때 어떻게 하는가(Crossing boundaries) — 를 축으로, 각 지점에서 어떤 대안을 고민했고 무엇을 골랐는지를 설명한다. 글쓴이 스스로 "제가 이해한 내용이라 틀릴 수 있다"고 밝힌 주니어 관점의 기록이다.

## 핵심

- **고수준/저수준의 정의** — 글은 고수준을 "데이터를 저장한다, 구역 배달료를 구한다" 같은 추상 개념, 저수준을 "RDB에 저장한다, 폴리곤 구역에 속한 배달건의 배달료를 구한다" 같은 구현 세부로 나눈다. 업무 로직(고수준)이 DB·Web(저수준) 변경에 흔들리지 않게 하는 것이 목표라고 설명한다.
- **생성/수정 DTO를 합칠까 나눌까 → 분리** — 초반엔 등록·수정 요청 DTO가 거의 같아 통합을 고민했지만, <클린 아키텍처>의 "진짜 중복 vs 우발적(거짓된) 중복" 구분을 근거로 분리를 택했다. 예: 스케줄 **생성** 시엔 시작일이 과거면 안 된다는 검증이 필요하지만, **수정** 시엔 이미 과거 날짜일 수 있어 그 검증이 필요 없다 — 서로 다른 이유·속도로 변하므로 우발적 중복이라는 논리다.
- **Entity가 Request DTO를 직접 받는 생성자 → 반려** — "DTO를 거쳐 전달하니 규칙을 지켰다"고 볼 수 있지만, Entity가 DTO를 참조하면 DTO 변경이 Entity 변경으로 번진다. 글은 UseCase(서비스) 계층에서 DTO 값을 꺼내 Entity를 만드는 쪽을 권한다.
- **Service → 구체 RDB 구현 직접 참조 → DIP로 역전** — 제어 흐름(Service → DB)대로 소스 의존을 두면 고수준이 저수준에 의존한다. 추상 `Repository` 인터페이스를 Service 쪽에 두고 구체 RDB 저장소가 이를 구현하게 해 의존 방향을 뒤집는다.
- **경계는 DB/프레임워크만이 아니라 업무 사이에도 있다** — 배달료 = 라이더 거리 기반 요금(DistanceFee) + 구역 할증(RegionFee). 배달 도메인이 두 구체 정책에 직접 의존하면 요금 정책이 바뀔 때마다 배달 코드도 흔들리므로, 여기에도 DIP를 적용해 배달 쪽은 인터페이스만 보게 했다. 실제로 이 프로젝트 자체가 구역 할증 정책 전면 변경 때문에 시작됐다고 한다.
- **Facade 도입은 "과할 수 있음"을 인정한 채 선택** — 클라이언트가 배달료를 얻으려고 DistanceFee·RegionFee 두 인터페이스를 다 주입받아야 하는 문제를 Facade로 감쌌다. 인터페이스 2개 수준에선 과할 수 있다고 스스로 짚고, <클린 소프트웨어>의 "정책 적용이 크고 가시적일 때 Facade를 쓴다"를 인용하며 팀 합의로 정할 문제라고 둔다.
- **인터페이스 선언 시 주의 3가지** — ① 구현체 기준이 아니라 **클라이언트가 쓰는 메서드 기준으로 분리**(배달료·배달팁·시간 할증을 한 인터페이스에 몰았더니 영향받는 클라이언트가 많아져 쪼갬, ISP), ② 인터페이스·메서드 이름에 구현체 이름을 드러내지 않기, ③ 파라미터는 업무 인터페이스면 Entity/DTO(범용이면 DTO), 불변에 가까운 유틸성 인터페이스면 필요한 값만 개별 인자로.
- **"자주 안 바뀌는 정책에 인터페이스는 과잉 아닌가?"** — 글쓴이의 결론은 "업무 정책은 많든 적든 항상 변경 포인트"이므로 여지를 둔다는 것. 다음 고민으로 업무 경계를 클래스 → 패키지 → 모듈까지 넓히는 방향을 제시한다(구체 실천은 아직).

## 내 프로젝트와의 연결

WMS와 구조적으로 가장 가깝다. 입고·출고 요청 DTO를 하나로 합치고 싶어지는 지점(입고 등록 시엔 수량>0·로케이션 필수, 수정 시엔 상태에 따라 일부 필드만 허용)이 이 글의 "우발적 중복" 사례와 같은 모양이고, `Inventory` 엔티티 생성자가 `InboundRequest`를 직접 받는지 점검해 볼 만하다. 배달료 = 거리 + 구역 할증을 DIP로 떼어낸 패턴은 WMS의 **재고 할당 정책**(FIFO·유통기한 우선 등)이나 출고 로케이션 선택 규칙을 인터페이스로 분리하는 데 그대로 옮길 수 있고, 정책이 2개뿐일 때 Facade까지 갈지는 글처럼 "과할 수 있음"을 결정 로그에 남기는 게 맞아 보인다. 수집기 쪽은 직접 연결이 약하지만, "수집 대상 API(사람인 등) → 저장 계층(SQLite)" 사이에 저장소 인터페이스를 두면 나중에 저장소를 바꿔도 수집 로직이 안 흔들린다는 점이 구조적으로 비슷한 지점이다.

## 오늘 정리할 것

1. WMS 코드에서 Entity 생성자·정적 팩토리가 Request DTO를 직접 파라미터로 받는 곳을 grep으로 찾아 목록으로 만들기 (있으면 "서비스에서 값 꺼내기"로 바꿀 후보 표시).
2. 입고 생성/수정(또는 출고 생성/수정) DTO의 검증 규칙을 표로 나란히 적어 보고, 진짜 중복인지 우발적 중복인지 한 줄씩 판정하기.
3. WMS의 재고 할당(또는 로케이션 선택) 로직이 구체 클래스에 직접 의존하는지 확인하고, 인터페이스로 뗄 경우의 이름을 구현체 이름이 드러나지 않게 2~3개 후보로 적어 보기.
4. 원문 Robert C. Martin "The Clean Architecture"(2012) 글에서 Crossing boundaries 그림을 직접 보고, "제어 흐름 방향 ≠ 소스 의존 방향"을 Service–Repository 예로 한 문단 자기 말로 정리하기.

## 오늘의 흐름

먼저 겹치는 것. 오늘(11/5) 브리핑의 「가중치 공간 프로그래밍」과 Willison의 노트북 재현·반론(11/3~4 깊게), 「uv.lock을 지워라」(11/2), worktrunk(트렌딩, 10/27~), NVIDIA auto-ontology(11/4 GeekNews 항목), nesformer(11/3), '위치를 흘리는 소리'(11/4 가볍게), Kimi K3.1 Pro(10/25)는 이미 다뤘다. PHP2Shell 취약점 자체도 10/21~30에 여러 번 봤으므로, 오늘은 **IEEE Spectrum 기사가 새로 붙인 틀("40년치 기술부채")과 그 반론만** 본다. 새것 — Binance 사고 보고서, Anthropic FlashProve, Go encoding/json/v2, Caper — 을 깊게 보고, Caper의 원리는 AI 심층 「AI - 실행해 보고 승인하는 에이전트 게이트」로 뺐다.

첫 번째 축은 **"말해진 것"이 아니라 "일어난 것"으로 판단하기**다. Caper는 에이전트의 셸 명령을 텍스트로 심사하지 않고 샌드박스에서 실제로 한 번 돌려 본 결과(바뀐 파일, 네트워크 시도, 비밀 읽기)를 보고 승인한다. 그 결과 텍스트 판정기들이 62.7~94.1% 통과시키던 "도구 안에 숨긴 해"를 7.8%로 줄였다. Binance 사고는 정확히 그 반대편의 실패다 — "면접 과제 저장소"의 세팅 스크립트는 텍스트로는 평범했고, 실제로 한 일은 `pyenv` 파일 하나를 70바이트 큰 것으로 갈아 끼운 것이었으며, 엔드포인트 보안 도구는 그 순간 이를 잡지 못했다. 어제(11/4) 노트의 Postman 설치 스크립트가 "동의 버튼을 대신 눌렀다"면, 오늘은 **설치 스크립트가 곧 코드 실행이라는 사실이 63억 달러 규모의 사고로 돌아왔다**.

두 번째 축은 **믿음을 증명으로 바꾸는 값**이다. FlashProve는 "API가 정말 그 모델을 썼나"를 영지식 증명으로 답한다. 값은 GPU 시간 약 72배(66~77배, 고부하 94배), 요청당 증명 18.78MB. 11/2 노트의 "영수증이 찍히자 남는 건 설명", 11/3의 "고친 범위는 증명해야 했다"에서 이어지는 흐름이지만, 오늘은 **증명이 실제로 얼마나 비싼지 숫자가 나왔다**. 그리고 그 증명이 지켜 주는 범위는 좁다 — 정수화한 모델·탐욕 디코딩·1,024토큰·MoE 가정 안에서만, 그리고 "어떤 커밋먼트를 믿을지"는 여전히 증명 밖(신뢰할 제3자)에서 와야 한다. 11/1 노트에서 Jepsen이 TLA+ 증명을 내건 DB를 깨뜨린 것과 같은 모양: **증명은 가정 안에서만 선다**.

세 번째 축은 **조용히 받아들이던 기본값을 시끄럽게 거절하는 쪽으로**다. Go json v2는 잘못된 UTF-8·중복 키·대소문자 무시 매칭을 v1처럼 조용히 넘기지 않고 에러로 만든다. PHP2Shell 기사는 "OOM은 그냥 크래시"로 분류해 2024년부터 방치된 버그가 AI 보조 감사 2주 만에 원격 코드 실행 사슬이 된 이야기다. 두 이야기는 같은 교훈의 앞뒤다 — **"심각도 낮음"으로 조용히 흡수한 이상 신호가 기술부채이고, 그 부채를 AI가 싸게 찾아내기 시작했다**. 9/20 노트(에이전트가 시스템을 뚫기 시작했다)와 10/18 노트(버그를 찾는 속도가 고치는 속도를 앞질렀다)의 연장선이고, 오늘 숫자로는 "찾는 데 2주, 고치는 데 4명이 2개월"(출처 미표기)이다.

새 흐름이라 할 만한 건, 공격 경로에 **사내 AI 도구**가 처음으로 이름을 올렸다는 점이다(Binance, 같은 날 GitBook은 "AI 에이전트를 이용한 표적 공격"). 다만 Binance는 AI 도구를 *어떻게* 썼는지 밝히지 않았다. 에이전트가 사내 시스템에 넓은 권한으로 닿아 있으면, 그것은 측면 이동의 고속도로가 된다 — Caper가 "에이전트 명령을 승인 전에 격리하라"고 할 때 지키려는 것과 같은 경계다.

## 깊게 본 것

### 1. Binance 63억 달러 — 가짜 면접 과제 저장소에서 컨테이너 배포 토큰까지

**무슨 일인가.** Binance가 10/29 사고의 1차 보고서를 11/3 공개했다. 원문(Binance 블로그)과 The Register, GeekNews 요약을 읽었다.

**타임라인(보고서 기준).**
- **6월** — 지갑 DevOps 엔지니어 A가 검색으로 찾은 "인기 AI 코딩 도구"를 설치하려다 **변조된 Homebrew 설치본**을 받았다. 보안팀이 탐지해 기기 교체·자격 증명 교체. 그러나 이 과정에서 **A의 역할과 지갑 인프라 팀 동료들이 공격자에게 노출**됐다. 방어는 성공했는데 정찰 정보가 남은 것이다.
- **9월** — 다른 엔지니어 B에게 구직 플랫폼으로 가짜 "프로젝트 디렉터"가 접근. 1차는 가짜 HR과 실시간 영상 면접(신뢰를 위해 개인 SNS 계정까지 공유), 2차는 메신저로 가짜 "CEO", 마지막에 **과제 저장소 다운로드**. Binance는 이 악성 코드를 "0-day"라 불렀다.
- **악성 저장소의 실제 동작** — `/opt/homebrew/Cellar/pyenv/2.8.0/libexec/pyenv_` 생성 → 3,414바이트로 수정 → 원본 `pyenv`(3,344바이트) 삭제 → 이름 바꾸기 → `/opt/homebrew/bin/pyenv` 심링크 재생성 → zsh 실행. 정상 도구 구성요소를 명령 실행·공격자 서버 접속 기능이 든 버전으로 바꿔치기. 엔드포인트 보안 도구는 "당시 탐지하지 못했다".
- **10/20** — 공격자가 B의 노트북과 **사내 AI 도구**를 이용해 A와 지갑 개발자 C의 컴퓨터를 장악. A의 컴퓨터에 **컨테이너 배포 권한 토큰**이 있었다.
- **10/29** — C의 컴퓨터로 로그인해 A에게서 훔친 자격 증명으로 컨테이너를 배포하고 악성 스크립트 실행. 내부 지갑 서명 서비스에 무단 접근해 정상 출금 경로 밖의 트랜잭션을 만들었다. **EIP-7702**로 공격자 컨트랙트에 핫월렛의 부분 실행 권한을 위임(위임 설정에 서명 트랜잭션 50건), 핫월렛이 MPC 구조라 단일 키로 빠르게 회수할 수 없었다. 20:05 UTC부터 XRP 2억 3,346만 개, SOL 약 97만 개, OP 4,420만 개, BTC 18,270개, ETH 2,961.9개(23:56 최종). 10/30 00:10 UTC 위임 해제.

**규모와 귀속.** Binance 표현은 "약 63.4억 달러 상당 자산이 **영향**"이고 그중 약 28.5억 달러는 동결·차단(정산 중). 손실은 Binance가 흡수, 10/31까지 영향 토큰의 98%를 보충했다고 밝혔다. FBI는 북한 소행으로 지목했고, **TraderTraitor**(Lazarus 계열)라는 이름은 The Register가 FBI 발표를 인용해 쓴 것이다(Binance 본문엔 "DPRK"만, FBI 원문은 확인 못 함).

**배경 — 왜 지금 이게 나왔나.** "가짜 채용 + 과제 저장소"는 북한 조직의 오래된 수법(Contagious Interview 등으로 불려 온 계열)이다. 새로운 점은 두 가지: 첫 접근이 **"AI 코딩 도구 설치"로 위장**했다는 것, 그리고 측면 이동에 **사내 AI 도구**가 쓰였다는 것. 개발자가 AI 도구를 급하게 이것저것 설치하는 지금의 습관 자체가 미끼가 됐다.

**기술적으로 어떻게 동작하나.** 핵심은 "패키지 관리자가 관리하는 실행 파일 바꿔치기"다. `pyenv`는 셸이 `python`을 부를 때마다 끼어드는 shim이라, 한 번 바꿔 두면 개발자가 평소처럼 일할 때마다 공격자 코드가 돈다. 파일 크기 70바이트 차이, 경로·이름·심링크 모두 정상 — **텍스트(파일명·경로)로는 아무것도 이상하지 않다**. Homebrew 경로는 사용자 쓰기 권한이라 관리자 권한도 필요 없다. 그 다음은 개인 기기에 놓여 있던 **배포 토큰**이 운영 컨테이너를 띄울 수 있었던 것 — 하나의 노트북이 곧 운영 환경의 열쇠였다.

**실무에 무슨 의미인가.**
- **모르는 저장소는 일회용 환경에서만.** 과제·튜토리얼·"재현 코드"는 devcontainer·VM에서. `npm install`, `./gradlew`, `pip install -e .`, `setup.sh`는 전부 **임의 코드 실행**이다(Gradle 빌드 스크립트도 코드다).
- **배포는 CI만.** 운영 배포 토큰이 개인 노트북에 있으면 안 된다. 단기 자격 증명(OIDC 기반 GitHub Actions → 클라우드 역할 위임), 배포 승인 게이트. WMS 프로젝트 3주차 배포 설계에 그대로 옮길 원칙이다.
- **AI 도구도 권한 경계 안에.** 사내 AI 에이전트가 여러 사람의 기기·시스템에 닿을 수 있다면, 그 도구의 권한이 곧 공격자의 측면 이동 범위다.

**반론·회의적 시각.** HN 쪽 비판은 "엔지니어가 속았다"보다 **구조**를 향했다 — 배포 토큰이 노트북에 있었던 것, 한 사람(또는 몇 대의 기기)이 수십억을 움직일 수 있었던 것, 침투 테스트에 사회공학·가짜 면접이 빠진 것. 반대로 Binance 보고서가 "정교한 난독화"와 "0-day"를 강조하지만 공개된 단계는 평범한 파일 조작이라, **사고 보고서가 피해자의 책임을 줄이는 쪽으로 쓰였다**는 읽기도 가능하다. AI 도구의 악용 방식이 비공개라는 점도 같은 맥락에서 아쉽다.

### 2. Caper — 셸 명령을 먼저 돌려 보고, 그 결과를 승인한다

**무슨 일인가.** SMU(David Lo 그룹) 등의 "Shall We Approve?"(arXiv 2610.40753). 코딩 에이전트의 셸 명령을 스냅샷된 Docker 샌드박스에서 `strace -f`로 한 번 실행하고, 관측 효과 보고서를 독립 LLM 승인자에게 준 뒤 허용이면 그 상태를 커밋, 차단이면 롤백.

**배경.** 승인 피로(사람은 결국 다 누른다) → 자동 승인기 → 그런데 자동 승인기는 명령 **텍스트**만 본다. 어제의 Postman·오늘의 Binance처럼 위험은 스크립트 *안*에 있다.

**어떻게 동작하나(요점).** 명령은 정확히 한 번 실행되고, 허용 시 다시 돌리지 않고 그 결과 상태를 유지한다 — 미리보기와 반영이 같은 실행이라 컨테이너 안의 TOCTOU가 없다. 대가로 네트워크는 차단(밖으로 나간 효과는 되돌릴 수 없으므로), 시도만 목적지·프로세스·직전에 읽은 파일과 함께 보고된다.

**숫자.** SABER 유해 결과율 6.7%(Claude Code Auto Mode 14.8%, 규칙·가드레일 15.0~18.8%, YoloFS 21.2%), 저자 자작 YoloFS-Ext 7.8%(YoloFS 35.3%, **막는 기능이 있는 기준선 최선 62.7%**), 안전 쌍둥이 오차단 1.0%. 승인 지연 중앙값 3.2초, 샌드박스 자체 0.5초(허용)·1.5초(차단). 가장 인상적인 절제: 증거 없이 맥락만 늘리면 유해는 줄지만 오차단이 52.0→61.8%로 **오히려 늘고**, 증거가 있으면 명령만 보고도 유해 1.0%·오차단 0.

**실무 의미.** "에이전트는 격리된 곳에서, 반영은 결과를 보고"라는 원칙을 명령 단위로 자동화한 것. 거꾸로 **원격 효과가 본질인 명령(배포, 원격 DB 마이그레이션)은 이 방식으로 승인할 수 없다** — 그건 여전히 CI와 사람의 일이다.

**반론.** 한 번의 실행만 본다 — 샌드박스 감지 후 지연, 보고서에 실린 주입 텍스트, 무해해 보이는 명령으로 쪼개기에 저자 스스로 방어를 주장하지 않는다. YoloFS-Ext는 관측 기반에 유리한 자작 벤치마크, 승인자·에이전트 모델 각 하나. 자세한 구조·절제·한계는 AI 심층 「AI - 실행해 보고 승인하는 에이전트 게이트」.

### 3. Anthropic FlashProve — "이 응답이 정말 그 모델에서 나왔나"의 가격표

**무슨 일인가.** Anthropic이 11/2 연구 글과 함께 FlashProve(Apache 2.0, 코드·Lean 증명·문서)를 공개했다. 응답에 짧은 증명을 붙여, 사전에 공개한 가중치 지문(커밋먼트)의 모델이 이 프롬프트로 이 출력 토큰을 냈음을 **가중치 없이** 검증하게 한다. 연구 글과 GitHub README, HN 토론 상위 댓글을 읽었다(기술 보고서·Lean 코드는 못 읽음).

**배경 — 왜 지금.** 사용자는 API가 어떤 모델을 썼는지 알 수 없다. 글이 꼽는 사례: 독립 평가자가 실제 서빙 모델을 확인, 라우팅 서비스(OpenRouter류) 고객이 바꿔치기 여부 확인, 토큰 스트림 변조 탐지, 규제기관의 "승인된 모델만 돌았나" 확인. 출력 품질로 역추적하는 건 신뢰할 수 없고, 검증자가 400B 모델을 다시 돌리는 건 비현실적이다.

**기술적으로 어떻게 동작하나.**
- **증명 체계** — 해시 함수로 암호학적 증명으로 컴파일한 IOP(대화형 오라클 증명) 기반 zkSNARK. 그래서 양자내성을 주장한다. 선형 제약을 가진 부호 근접성 검사와 **룩업 인자**를 쓴다. 건전성은 해시 질의 q번 후 약 q/2^124 + 2^-101(랜덤 오라클 모델).
- **두 단계** — *오프라인*(모델당 1회): 가중치 커밋먼트 공개, 약 39분, 커밋먼트 하나로 약 1,600만 요청. *온라인*: 요청마다(벤치마크는 24개 배치) 사후에 증명 생성.
- **무엇을 숨기나** — 가중치, 중간값, 각 층에서 **어떤 전문가가 돌았는지**는 숨긴다. **아키텍처는 숨기지 않는다**(목표 아님). 프롬프트와 응답은 당연히 검증자가 본다.
- **정수 모델** — 증명 대상은 "공개 가중치의 정확한 정수 버전"(4비트), prefill도 정수 산술. 비선형(softmax·정규화)을 어떻게 처리하는지는 내가 읽은 범위에 없었다(아마 룩업 인자, 미확인).

**숫자(원문 대조 확인).** Llama 4 Maverick(400B MoE, 활성 약 17B, 제3자 4비트 변환본 약 232GB), H100 1장 + CPU 24코어. 24개 요청 배치 약 223초 = 24×1,024/223 ≈ **초당 110토큰**. 증명 요청당 18.78MB. GPU 시간은 vLLM 대비 약 72배(실행마다 66~77배, vLLM 최고 부하 기준 약 94배) — 단 **기준선 vLLM은 FP8 릴리스를 H100 8장에서** 돌린 것이고 FlashProve는 4비트 1장이라 같은 조건 비교는 아니다. 검증은 CPU에서 커밋먼트 약 6.5MB, 24스레드 17초(1스레드 21초) — 이 시간은 **오프라인 단계 검사까지 포함**한 값이다.

**실무에 무슨 의미인가.** 당장 쓸 숫자는 아니다. 하지만 "모델 바꿔치기"가 증명 대상이 될 만큼 실재하는 상업 문제로 취급되기 시작했다는 신호다. 백엔드 관점에서 오늘 할 수 있는 건 더 소박하다 — LLM 호출 로그에 **응답 헤더의 모델 ID·요청 ID·지연·토큰 수**를 남겨 두는 것. 증명이 없을 때 남는 증거는 로그뿐이다.

**반론·회의적 시각.**
- **증명하는 성질이 얇다**(HN ajb) — 싼 모델 바꿔치기와 중간자 변조는 막지만, 데이터 유출이나 답의 품질과는 무관.
- **증명은 진짜 가중치로, 서빙은 양자화본으로?**(vintagedave) — 글 자체의 한계("정수 모델·탐욕 디코딩 기준, 실제 부동소수·샘플링 출력은 갈라질 수 있다, 적대적 프롬프트는 미보장")가 바로 이 틈이다. 사후 증명이라 **증명을 거부하는 것**도 막지 못하고, 글은 사후 증명이 "토큰 일부"를 증명한다고도 써서 **요청 전체를 덮는지 한 토큰씩 표본인지** 내가 읽은 범위에선 모호했다.
- **싼 대안**(vessenes) — 같은 프롬프트를 독립 제공자 4곳에 돌려 비교하는 확률적 검사가 90~100배 오버헤드보다 싸다.
- **신뢰의 뿌리** — README도 "커밋먼트 ID는 검사받는 서버가 아니라 신뢰하는 쪽에서 받아야 한다"고 쓴다. 증명은 신뢰를 없애지 않고 **옮긴다**. 글은 TEE 증명(attestation)을 제조사 신뢰에 기대는 보완책으로 본다.
- Lean 명세와 실제 고속 C++ 검증기가 일치한다는 형식 보장은 없다(저자 명시). README는 "유지보수·기여 받지 않음".

### 4. Go 1.27 encoding/json/v2 — 조용히 받아들이던 것을 거절하기로

**무슨 일인가.** Go 1.25에서 실험으로 들어왔던 `encoding/json/v2`와 `encoding/json/jsontext`가 Go 1.27에서 안정·정식 제공된다(Go 블로그 11/4, Pratt·Tsai·Martí 외). 블로그 전문과 HN 토론을 읽었다.

**배경 — v1이 남긴 부채.** 블로그가 직접 나열한 v1의 문제:
- **문법** — RFC 8259가 요구하는 유효 UTF-8을 안 지키고 잘못된 UTF-8을 통과시킨다. 정의되지 않은 **중복 키**를 허용한다(블로그는 CVE-2017-12635를 인용 — CouchDB에서 파서마다 중복 키를 다르게 해석해 권한 상승이 난 사건).
- **의미** — nil 슬라이스·맵을 `null`로 출력(설문은 `[]`·`{}` 선호). 언마셜 때 키를 필드에 **대소문자 무시**로 매칭(놀랍고, 보안 문제 소지, 성능 제약). 포인터 리시버 `MarshalJSON`이 일관성 없이 호출되는데 고치면 기존 앱이 깨진다.
- **API** — `json.NewDecoder(r).Decode(v)`가 뒤에 붙은 쓰레기 데이터를 거절하지 않는다. Encoder/Decoder 옵션이 `Marshal`/`Unmarshal`이나 커스텀 메서드 안까지 전달되지 않아, `DisallowUnknownFields`가 `UnmarshalJSON` 안에선 사라진다.
- **성능** — `MarshalJSON`은 할당이 강제되고 결과를 다시 검증·재포맷한다. `UnmarshalJSON`은 값을 **두 번 파싱**한다. Encoder/Decoder가 값 전체를 버퍼링해 진짜 스트리밍이 없다. 커스텀 메서드 안의 재귀 Marshal/Unmarshal은 **이차 비용**.

**기술적으로 어떻게 동작하나.**
- **두 층 분리** — `jsontext`는 리플렉션 없는 순수 문법 층(`Encoder.WriteToken/WriteValue`, `Decoder.ReadToken/ReadValue`, `Value`는 이름 붙인 `[]byte` — v1의 `RawMessage`는 이제 그 별칭). `json/v2`는 그 위의 Go 값 매핑 층.
- **새 기본값** — 잘못된 UTF-8·중복 키는 에러, nil 슬라이스·맵은 `[]`/`{}`, 키 매칭은 대소문자 구분, `omitempty`는 "인코딩 결과가 비는 값"(`null`, `""`, `[]`, `{}`)을 생략, `time.Duration`은 기본 표현이 없으니 에러(옵션으로 선택).
- **옵션이 끝까지 흐른다** — `Marshal(v, opts...)`, 그리고 새 인터페이스 `MarshalJSONTo(*jsontext.Encoder)`/`UnmarshalJSONFrom(*jsontext.Decoder)`가 인코더·디코더에서 옵션을 꺼내 쓴다. `WithMarshalers`/`MarshalFunc` 등으로 **호출자가 타입 표현을 바꿔 끼울** 수 있다(블로그 예시는 protojson).
- **v1은 v2 위에** — v1을 "v1 호환 옵션 전부"를 켠 v2로 재구현했다. 그래서 둘은 상호운용된다(v2가 v1 `MarshalJSON`을, v1이 v2 `MarshalJSONTo`를 존중). v1은 무기한 지원, 마이그레이션은 선택.

**성능(정확한 표현).** Marshal은 v1과 "대략 동등 — 때로 조금 빠르고 때로 조금 느림", Unmarshal은 "상당히 빠르고, 최대 10배". Kubernetes의 한 서비스(kube-openapi#315)는 `UnmarshalJSON` 안의 재귀 OpenAPI 파싱을 `UnmarshalJSONFrom`으로 바꿔 "자릿수 단위" 개선. v2가 더 느린 경우는 이슈 81315로 추적 중이고 1.28에서 더 최적화 예정. 전체 이득을 보려면 커스텀 타입에 `MarshalJSONTo`/`UnmarshalJSONFrom`을 구현해야 한다.

**실무에 무슨 의미인가 — Jackson 점검표로 읽기.** Spring Boot의 Jackson에도 같은 질문이 있다.

| Go v1의 문제 | Jackson에서 대응하는 지점 |
| --- | --- |
| 중복 키 허용 | 기본은 마지막 값으로 덮어씀 — `JsonParser.Feature.STRICT_DUPLICATE_DETECTION`(또는 `StreamReadFeature`)으로 에러화 |
| 대소문자 무시 매칭 | 기본은 **구분**(Go v1보다 엄격). `ACCEPT_CASE_INSENSITIVE_PROPERTIES`를 켜면 Go v1처럼 됨 |
| nil → null | `@JsonInclude(NON_NULL/NON_EMPTY)`, 컬렉션 null 처리 정책 |
| 모르는 필드 | Spring Boot 기본은 `FAIL_ON_UNKNOWN_PROPERTIES` **꺼짐** — 관대함이 기본값 |
| 이중 파싱·스트리밍 | 큰 응답은 `JsonParser` 토큰 스트리밍 |
| 뒤에 붙은 쓰레기 | `FAIL_ON_TRAILING_TOKENS`(기본 꺼짐) |

(Jackson 쪽은 내 지식 기준이고 오늘 원문으로 확인하진 않았다 — 버전별로 이름이 다르니 직접 확인할 것.) 요점은 **관대한 파서는 공격면**이라는 것. 서로 다른 계층(게이트웨이·서비스)이 같은 JSON을 다르게 해석하면 그 틈이 권한 우회가 된다(CVE-2017-12635가 정확히 그 사례).

**반론·회의적 시각.** HN에선 `MarshalIndent` 제거가 불편하다는 불만(대안으로 `jsontext.WithIndent` 옵션이 제시됨, 미확인), 6년이나 걸린 이유(서드파티가 공백을 메웠고 느린 표준 라이브러리엔 장단이 있다), "Marshal이 에러를 반환하는 게 맞나"(커스텀 메서드·`any`·비유한 실수 때문에 런타임 에러는 불가피하다는 반박)가 오갔다. 그리고 엄격한 기본값은 **기존 클라이언트가 보내던 "틀린" JSON을 갑자기 거절**하게 만든다 — v1을 유지하라는 블로그의 안내가 이 때문이다.

원문: [Go 블로그](https://go.dev/blog/jsonv2) · [마이그레이션 가이드](https://go.dev/doc/jsonv2-migration) · [HN](https://news.ycombinator.com/item?id=50369106)

### 5. PHP2Shell, "40년치 기술부채" — 틀(frame)의 새것과 반론

**무슨 일인가.** IEEE Spectrum(Dina Genkina, 11/2) 「PHP2Shell 취약점은 사이버보안 지옥의 전조」, 부제 "AI가 40년치 기술부채를 갚게 만든다". 취약점 자체는 10/21~30 노트에서 다뤘으므로 **새로 나온 주장과 숫자만** 본다. 기사 전문과 HN 토론을 읽었다.

**새로 나온 것.**
- 출발점은 **2024년 PHP 재단에 신고된 OOM 에러** — 크래시로 분류돼 방치. 다만 기사는 그 신고의 날짜·신고자·세부를 밝히지 않고, Calif가 찾은 사슬과 같은 버그인지도 명확하지 않다.
- OpenAI 후원 Calif 감사에서 AI 보조 연구자가 **2주** 만에 OOM을 임의 코드 실행으로 엮음, Wiz가 확인·확장. 패치엔 **엔지니어 4명이 2개월**(기사에 출처 미표기). "알려진 한" 패치 전 악용은 없었다.
- Suman Jana(컬럼비아): 익스플로잇은 "로켓 과학이 아니다", 방어자는 모든 경로를 닫으면서 기능도 안 깨야 하니 비대칭은 실재. 프런티어 랩이 메인테이너에게 **토큰 예산을 기부**하는 방식을 더 조직적으로. 그리고 "패치는 LLM이 쓰고, 그 패치가 맞다는 증명도 LLM이 쓴다"(10/22 Anthropic 발표 언급).
- Matthew Green(존스홉킨스): "정말 나쁜 일이 터지기 전엔 아무도 안 고칠 것", 그 시점을 "2027년 초쯤"으로. 조언은 업데이트 즉시 설치.

**배경·의미.** 10/18 노트(버그를 찾는 속도가 고치는 속도를 앞질렀다)를 숫자 하나로 요약한 기사다 — 찾는 비용은 AI로 2주까지 내려왔고 고치는 비용은 그대로다. 실무의 결론은 브리핑과 같다: 의존성 자동 업데이트(Dependabot/Renovate), 패치 릴리스를 미루지 않기, `spring-boot-starter-parent` 정기 상향. 그리고 4번 Go json v2와 묶어 읽으면 — "크래시니까 낮음", "관대하게 받아 주자"로 분류한 이상 신호가 부채의 정체다.

**반론.** HN의 가장 강한 반박 셋: ① **AI 이전부터 사람은 버그를 깔고 앉아 있었다** — HTTP2Shell/Brotli2Shell은 "코드 속 8년, 미공개 8개월", 최소 4명이 신고(40년 탓하기 틀이 공정하지 않다). ② **AI가 쓰는 수정은 새 부채** — 우회로를 만들거나 아무도 이해 못 하는 코드를 낳는다. ③ **공개 절차** — 재현이 공개된 뒤에도 엠바고에 매달린 PHP 쪽 대응이 문제였다는 주장(일부 미확인). 브리핑의 "AI 문제가 아니라 자원 문제"(수익 없는 재단이 수억 대 런타임을 유지) 반론과 합치면, **AI는 원인이 아니라 청구서를 앞당긴 것**이라는 읽기가 가장 균형적이다.

## 더 알아볼 것

- [ ] **과제 저장소 격리 절차 만들기.** 모르는 저장소를 받았을 때 쓸 devcontainer(또는 Docker) 템플릿 하나 — 네트워크 끔, 호스트 홈 디렉터리 마운트 안 함, `~/.ssh`·`~/.aws`·`~/.gradle/gradle.properties` 미노출. Gradle 빌드 스크립트·npm `postinstall`이 실행되는 시점을 직접 확인해 본다.
- [ ] **내 노트북에 있는 "운영 열쇠" 목록.** 클라우드 키, 배포 토큰, DB 비밀번호, GitHub PAT가 어디에 평문으로 있는지 적고, WMS 배포를 GitHub Actions + OIDC(장기 키 없음)로 설계하면 무엇이 빠지는지 그려 본다.
- [ ] **Jackson 엄격 모드 실험.** Spring Boot 테스트에서 중복 키 `{"qty":1,"qty":999}`, 대소문자 다른 키, 뒤에 쓰레기가 붙은 본문, 모르는 필드를 보내 기본 동작을 확인하고, `STRICT_DUPLICATE_DETECTION`·`FAIL_ON_TRAILING_TOKENS`·`FAIL_ON_UNKNOWN_PROPERTIES`를 켰을 때 무엇이 바뀌는지 표로 남긴다. 게이트웨이와 서비스가 다르게 해석하면 어떤 공격이 되나?
- [ ] **Caper의 "증거 vs 맥락" 절제를 내 말로.** 맥락만 늘리면 오차단이 늘고 증거가 있으면 줄어드는 이유를, 코드 리뷰에서 "PR 설명만 읽은 리뷰"와 "직접 돌려 본 리뷰"에 빗대 설명해 본다(AI 심층 노트 참고).
- [ ] **FlashProve가 막는 것과 못 막는 것.** "라우터가 몰래 싼 모델로 바꿔치기"와 "서비스가 프롬프트를 몰래 저장"을 각각 FlashProve·로그·TEE·여러 제공자 교차 질의로 막을 수 있는지 2×4 표로 정리해 본다.

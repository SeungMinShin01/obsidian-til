## 깊게 본 것

### 1. Optimizely 한 곳에서 178개 조직으로 — "신뢰된 호스트"가 악성코드를 내려줄 때

**무슨 일인가.** 2026-11-16(UTC) 하루 동안 A/B 테스트 플랫폼 Optimizely Web을 쓰는 고객사 스니펫에 악성 코드가 들어갔다. Report URI가 찾을 수 있었던 스니펫 1,611개를 하나씩 받아 확인했더니 **188개 스니펫·178개 조직** 이 감염돼 있었다(Zoom, BBC, CNN, Salesforce, GitLab, IKEA, HSBC 여러 지역, Equifax, Air France-KLM, Ledger, Peacock … 그리고 `optimizely.com`·`login.optimizely.com` 자신). 업종별로는 금융 32곳이 가장 많다. 21:52 UTC에는 1곳(TalkTalk)만 남고 정리됐다.

**배경 — 왜 이 구조가 가능했나.** Optimizely Web은 고객이 `<script src="https://cdn.optimizely.com/js/<프로젝트ID>.js">` 한 줄을 붙이는 방식이다. 그 파일 안에는 Optimizely 코드, 고객의 실험 설정, 그리고 **Project JavaScript(`projectJS`)** 라는 선택 필드가 들어간다. 이 필드는 고객이 대시보드에서 직접 쓰는 **모든 페이지에서 실행되는 자유 코드** 다. 즉 설계상 "대시보드에 쓰기 권한이 있는 누군가가 고객 사이트의 모든 페이지에서 임의 코드를 실행할 수 있다". 공격자는 이 필드에 자기 로더를 써넣었고, 나머지 파일은 손대지 않았다. 그래서 CDN은 "받은 그대로" 내려줬다 — 캐시 오염이 아니다. **공격자가 어떻게 서로 무관한 수많은 고객 프로젝트에 쓰기 권한을 얻었는지는 모른다**(Optimizely 시스템 침해? 고객 간 접근이 가능한 자격 증명?). Report URI는 게시 시점까지 Optimizely로부터 응답을 받지 못했다.

**기술적으로 어떻게 동작했나.** 로더는 세 가지 변형이 있었다.

1. 평범한 `<script>` 태그로 `https://1688360.cc/track.js` 를 붙이는 것(대부분)
2. 같은 URL을 `atob()` base64로 숨긴 것 — "1688360.cc"로 검색해도 안 나온다. Smartsheet는 한 번 정리된 뒤 **이 변형으로 재감염** 됐다 → 정리 중에도 공격자가 쓰기 권한을 유지하고 있었다는 뜻
3. 페이로드 전체를 인라인으로 담고 `eval` 로 실행하는 폴백 — `1688360.cc` 가 막혀도 돌게 한 것

페이로드 `track.js` 는 하루 동안 **26번 재빌드** 됐고 기능이 계속 붙었다.

- **지갑 주소 바꿔치기** — BTC·ETH/EVM·TRON·Solana·TON 등 주소를 체크섬까지 검증해 진짜만 공격자 주소로 교체. 페이지 텍스트·폼·링크뿐 아니라 **클립보드**, 나가는 `fetch`/XHR, `window.open`, iOS 공유 시트까지. 페이지가 바뀔 때마다 다시 훑는다
- **카드 스키밍**(13:43 UTC 추가) — 폼 제출과 모든 POST에서 Luhn 검증된 카드번호·만료일·CVV가 다 모이면 `navigator.sendBeacon` 으로 전송. **Stripe·Adyen 같은 호스팅 결제 iframe 안의 카드는 못 가져갔다.** 사이트 자체 입력 필드에 친 카드는 가져갔다
- **쿠키·화면 캡처** — `HttpOnly` 가 아닌 쿠키(`document.cookie`)와 html2canvas로 렌더한 화면을 결제·지갑 문맥에서 전송
- **iOS 익스플로잇** — iPhone·iPad면 iOS 버전을 읽어 숨은 iframe으로 Coruna(13~17)·DarkSword(18.x) 체인을 띄움. iOS 18.6 이하는 60초마다 페이지를 새로 고쳐 재시도(눈에 보이는 증상). 18.7.3+/26.3+는 패치됨

19:25 UTC 기준 공격자 지갑에 들어온 돈은 약 **7,040달러**. 카드·쿠키가 몇 건 넘어갔는지는 보이지 않는다. 원문 타임라인에 따르면 **같은 행위자가 11/13부터 이미 Kissmetrics·StorifyMe·Minute Media 스크립트로 `webshell.lol` 을 주입한 앞선 물결** 이 있었고(브리핑에 없음), TRON 지갑은 2026년 3월부터 쓰였다.

**CSP는 도움이 됐나 — 오늘의 핵심 표.** Report URI가 피해 조직의 호스트 256개를 크롤해 조직 단위로 판정한 결과(합계 159개 조직):

| 결과 | 조직 수 |
| --- | --- |
| CSP 없음 | 68 |
| CSP가 페이로드와 데이터 탈취를 모두 허용 | 50 |
| 페이로드는 실행, `connect-src` 가 탈취 전송만 차단(주소 바꿔치기는 여전히 동작) | 17 |
| **페이로드 차단** | **24 (15%)** |

여기서 배울 것 세 가지.

1. **호스트 허용은 무의미했다.** `script-src cdn.optimizely.com` 은 "이 호스트에서 온 건 믿는다"인데, 악성 코드가 바로 그 호스트에서 왔다. 막은 24곳의 공통점은 필요한 호스트만 나열한 좁은 `script-src` 로, 스니펫이 **추가로** 붙이려던 `1688360.cc` 를 막은 것이다
2. **`'strict-dynamic'` 은 신뢰를 전염시킨다.** nonce/해시로 믿은 스크립트가 동적으로 삽입하는 스크립트도 자동으로 믿는 지시어다. 원래는 "허용 목록 관리가 어려우니 nonce 하나로 신뢰의 뿌리를 잡자"는 좋은 설계인데, 뿌리 자체(Optimizely 스니펫)가 오염되면 그 아래가 다 통과한다
3. **`'unsafe-eval'` 이 폴백을 살렸다.** Optimizely 공식 문서가 허용하라고 안내하는 지시어다. HSBC는 `track.js` 와 전송을 막았는데도 인라인 폴백이 `eval` 로 돌았다

**실무에 무슨 의미인가 (Spring + React).**

- 서드파티 `<script>` 한 줄은 **"그 업체의 대시보드 권한자 전원에게 내 사이트의 실행 권한을 준다"** 와 같다. 분석 툴·태그 매니저·챗 위젯·A/B 테스트가 다 해당한다. 들일 때 "이 스크립트가 바뀌면 누가 알아채나?"를 물어야 한다
- **SRI(`integrity` 해시)는 이런 스니펫엔 못 쓴다.** 내용이 실험 설정에 따라 계속 바뀌는 게 정상 동작이라 해시를 고정할 수 없다. 그래서 남는 방어선이 CSP(실행·전송 제한)와 변경 감시다
- Spring Security에서 CSP는 `http.headers(h -> h.contentSecurityPolicy(csp -> csp.policyDirectives("script-src 'self' https://cdn.example.com; connect-src 'self' https://api.example.com; frame-src https://js.stripe.com; report-uri /csp-report")))` 형태로 건다. 처음엔 `.reportOnly()` 로 위반 보고만 모아 무엇이 깨지는지 본 뒤 강제로 바꾸는 게 정석이다
- **`connect-src` 를 좁히는 게 의외로 효과가 크다** — 17곳은 이것만으로 카드·쿠키·캡처 유출을 막았다. React 앱이 실제로 호출하는 API 도메인 목록은 그리 길지 않다
- **민감 입력은 호스팅 iframe으로** — 이번에도 Stripe iframe 안의 카드는 안전했다. 같은 출처 정책이 iframe 경계에서 스크립트를 막기 때문이다
- **세션 쿠키는 `HttpOnly`** — Spring Boot 기본 `JSESSIONID` 는 HttpOnly지만, 프론트에서 읽으려고 JWT를 일반 쿠키나 `localStorage` 에 두는 구성은 그대로 노출된다

**반론·회의적 시각.**

- **분석 주체가 이해관계자다.** Report URI는 이런 공격을 탐지하는 제품을 파는 회사이고, 글의 중간 절이 자사 제품 소개다. 다만 감염 스니펫 해시·IoC·지갑 주소·타임라인을 다 공개해 검증 가능하게 해 둔 점은 신뢰할 만하다
- **피해 규모의 상한은 모른다.** 1,611개는 "찾을 수 있었던" 스니펫이라 실제 감염은 더 많을 수 있고, 반대로 확인된 금전 피해는 7천 달러 수준이다. 카드·쿠키 피해는 측정 불가
- **좁은 `script-src` 는 비싸다.** 마케팅 도구는 스스로 다른 스크립트를 줄줄이 불러오는 경우가 많아, 엄격한 CSP를 걸면 그 도구가 깨진다. 그래서 `'strict-dynamic'`·`'unsafe-eval'` 을 허용하게 되는 것이고, 이건 보안팀 혼자 정할 수 없는 **사업 결정** 이다
- **근본 원인은 미공개.** 고객 간 쓰기 권한이 어떻게 뚫렸는지가 이 사건의 진짜 교훈일 텐데 아직 Optimizely의 설명이 없다

### 2. Microsoft 365 장애의 원인 — 7월 변경, 약한 장비의 부하 테스트, 되돌릴 수 없는 롤백

**무슨 일인가.** Microsoft가 11/15 예비 사후 보고서(PIR)를 냈다. 11/12~13 Exchange Online 등 Microsoft 365 대형 장애(11/13·11/16 노트의 그 장애)의 원인은 **2026년 7월에 Microsoft 365 네트워크 게이트웨이 서버용으로 넣은 변경** 이다. 당시 부하 테스트를 통과했고 배포 후 아무 영향이 없었다.

**배경과 동작 — 사슬로 읽기.**

1. **잠복** — 변경은 내부 Windows 프로세스에 **락 경합(lock contention)** 을 만들었고, 경합이 심해지면 CPU·메모리가 고갈됐다. 보고서 원문: "부하 테스트는 코어 수가 적은 약한 하드웨어 위주였다", "경합 문제는 코어가 많은 새 하드웨어에서 악화된다". 코어가 많을수록 같은 락을 두고 다투는 스레드가 늘어나니, **약한 장비에서 통과한 테스트가 강한 장비의 동작을 보장하지 못하는** 전형적인 경우다
2. **방아쇠 두 개가 동시에** — 11/12 01:07 UTC Teams가 Exchange Online을 받치는 "주" 게이트웨이로 장애 조치(failover)했다(그 자체는 드물지 않은 부하). 같은 시각 게이트웨이 용량의 **약 14%가 정비로 빠져** 있었다(그것도 혼자선 문제없었다 — "여유 용량은 충분했다"). 둘이 겹쳐 결함 조건에 닿았다
3. **연쇄 장애** — 서버가 응답을 잃으면 트래픽은 다음 정상 서버로 간다 → 그 서버도 같은 결함에 닿는다 → 또 넘어간다. **두 시간 안에 결함이 함대 전체로 퍼졌고, 최악일 때 서버의 80% 이상이 응답하지 않았다.** 16:03 UTC 이상 탐지, 16:33 첫 지원 요청
4. **복구 실패** — 서버를 되살려도 즉시 다시 몰려 쓰러졌다. "평소의 자동 복구 절차는 이렇게 넓게 무응답인 상태를 복구하도록 설계되지 않았다." Teams·OneDrive·SharePoint는 이 게이트웨이를 피해 나갔지만 **Exchange Online은 규모 때문에 빠져나갈 수 없었다** → Outlook이 가장 오래 멈춘 이유
5. **롤백 불가** — 결함이 넉 달 묵어 단순 롤백이 안 됐다. 엔지니어들은 "패치의 패치", 즉 해당 코드 경로를 알려진 정상 상태로 되돌리는 업데이트를 만들어 서버 그룹별로 적용했다. 11/13 00:30 원인(연결 협상) 특정 → 07:20 완화 적용 → 16:10 정상 확인. 최종 보고서는 11/20 예정

**실무에 무슨 의미인가.**

- **부하 테스트 장비는 운영 장비를 닮아야 한다.** "로컬 4코어에서 k6 돌려 봤더니 괜찮았다"는 운영 32코어 서버의 락 경합을 말해 주지 않는다. Java라면 `synchronized` 블록·`ConcurrentHashMap` 의 핫 키·DB 커넥션 풀 대기가 코어 수에 따라 다르게 터진다. 9/20 노트의 Virtual Thread `synchronized` pinning도 같은 계열이다
- **장애 조치(failover)와 재시도는 장애를 퍼뜨리는 통로이기도 하다.** "다음 정상 서버로 넘긴다"는 건강한 설계지만, 원인이 서버가 아니라 **부하 자체** 면 건강한 서버를 차례로 쓰러뜨린다. Spring 쪽 대응 어휘: 서킷 브레이커(Resilience4j `CircuitBreaker`), 벌크헤드(`Bulkhead` — 자원 격리), 부하 차단(load shedding — 일부 요청을 일부러 거절해 나머지를 살림), 재시도에 지수 백오프+지터
- **롤백 가능성은 시간이 지나면 사라진다.** 배포 직후엔 되돌리면 되지만, 그 위에 넉 달치 변경이 쌓이면 되돌릴 수 없다. 그래서 위험한 코드 경로는 **기능 플래그(kill switch)** 로 감싸 두면 "패치의 패치"를 만들지 않고 스위치만 내릴 수 있다
- **자동 복구 절차도 테스트 대상이다.** "전부 쓰러진 상태에서 다시 일으키기"는 평소엔 절대 일어나지 않으니 아무도 연습하지 않는다

**반론·회의적 시각.** 이건 **예비** 보고서이고, Microsoft가 스스로 쓴 설명이다. 왜 서로 독립된 두 조건(Teams 장애 조치·14% 정비)이 같은 시각에 겹쳤는지, 7월 이후 넉 달간 왜 한 번도 조건에 닿지 않았는지는 아직 설명되지 않았다. The Register는 "운영 시나리오를 반영하지 않은 부하 테스트"를 비판했지만, 모든 하드웨어 조합을 테스트하는 건 현실적으로 불가능하다는 반론도 가능하다. 또 Breck-McKye 글은 이 장애를 "네트워크 설정 실패"로 추정했는데(작성 시점 기준 추측), 예비 보고서의 원인은 **소프트웨어 결함** 이다 — 에세이의 사례 설명을 그대로 받아들이면 안 되는 예다.

### 3. "…그리고 증명은 Lean으로 확인됐다" — 컴파일 너머의 네 질문

**무슨 일인가.** Lean 수학 형식화의 대표 인물 Kevin Buzzard(Xena Project)가 11/12에 쓴 글. 계기는 OpenAI가 10월에 공개한 수학 논문 722편, 그중 약 45%에 Lean 코드가 붙어 있다. "Lean 코드가 있으니 맞다"는 쪽과 "Lean 커널에도 버그가 있었고 AI는 보상 해킹을 하니 의미 없다"는 쪽 사이에서, 신뢰하려면 **무엇을 확인해야 하는지** 를 네 질문으로 정리했다.

**배경.** Lean은 증명 보조기다. 컴퓨터가 증명의 한 줄 한 줄을 공리에서부터 검사한다. 그런데 AI가 수백만 줄의 Lean 코드를 생성하는 시대가 되자, "컴파일된다"가 무엇을 보장하는지를 다시 물어야 하게 됐다. 11/15 노트에서 Anthropic 1,000 에이전트가 Lean 커널을 심판으로 썼고, 11/16 노트에서 Lexifina가 세법을 Lean으로 옮겼다 — 오늘 글은 그 심판을 **어떻게 믿을 것인가** 다.

**네 질문 — 동작 원리.**

1. **Lean 명제가 논문 명제와 같은가.** Lean은 **명제(statement)** 와 **증명(proof)** 을 엄격히 구분한다. `∀ a b c n : ℕ, n ≥ 3 → a^n + b^n ≠ c^n` 은 컴파일된다. 그런데 Lean의 ℕ에는 0이 있어 a=b=c=0, n=3이 반례이므로 이 명제는 거짓이다 — 명제는 컴파일되지만 증명은 영원히 컴파일되지 않는다. 문제는 명제를 이해하는 데에만 수천 줄이 필요할 때다: Hodge 추측의 명제 하나에 Mathlib 위로 1만 줄 이상, Axiom의 유한 단순군 분류 증명은 명제 파일이 25만 줄(900여 파일)을 불러오고 그중 정의를 담은 핵심 약 5,600줄을 사람이 검토했다는 사람을 아직 못 만났다고 한다. OpenAI의 Lean 코드 동반 정리 290개 중 **약 38개는 논문의 핵심 정리를 증명은커녕 진술조차 하지 않는다**(OpenAI가 그렇다고 주장한 적은 없다 — "같이 있는 코드"였을 뿐). 1960년부터 열린 Lech 중복도 추측을 다룬 논문 194의 Lean 코드는 실제로는 따름정리 5.4를 담고 있다
2. **실제로 컴파일되나.** Anthropic의 페르마 정리 형식화는 1,300만 줄이라 96코어·RAM 500GB 머신이 필요했다. 출처 모를 Lean 코드는 **샌드박스 먼저**(댓글에서 저자는 bubblewrap·임대 서버를 쓴다고 답함). OpenAI의 Navier–Stokes 작업은 64만 줄로 노트북에서 컴파일된다
3. **그 명제를 그대로 증명하나.** 증명 쪽 수백만 줄 어딘가에서 `x^n` 을 37로 재정의하면 "37+37=74 ≠ 37"로 '페르마 정리'가 증명된다. 또는 공리를 몰래 추가할 수도 있다. 해법은 `lake comparator` — 신뢰 파일(`Challenge.lean`)의 명제와 비신뢰 증명(`Solution.lean`)의 명제가 **같은지**, 그리고 **수학의 공리만** 썼는지 대조한다
4. **커널 버그를 이용하지 않나.** Lean 공식 커널에 실제 건전성 버그가 있었고(발견 4시간 만에 수정), 이후 OpenAI의 코드 검토가 몇 개를 더 찾아 공개 전에 고쳤다. 지금은 여러 언어로 쓰인 독립 커널이 여럿 있고 그중 하나는 어셈블리 수준까지 형식 검증됐다고 한다. `lake comparator --paranoid` 는 **여러 커널을 동시에 통과** 하도록 요구한다 — 모르는 버그를 동시에 여러 독립 구현에서 이용해야 하므로 사실상 막힌다

마지막 단서: 네 검사를 다 통과해도 **논문 PDF의 증명이 맞다는 보장은 아니다.** Navier–Stokes 작업에서 검증된 Lean 증명과 PDF 논증이 갈라지는 지점이 보고됐다. 일부 전문가는 PDF 대신 AI로 Lean 증명을 영어로 되풀어 읽는다고 한다.

**실무에 무슨 의미인가 — 코드 리뷰로 번역하면.**

| Lean 질문 | 코드 리뷰에서의 대응 |
| --- | --- |
| 명제가 논문과 같은가 | 테스트 이름·`assert` 가 **요구사항** 을 진술하는가? (`isNotNull()` 만 보는 테스트는 '0을 포함한 ℕ'과 같다) |
| 컴파일되나 | CI가 실제로 그 테스트를 돌렸나? (`@Disabled`, 프로파일 누락, 테스트 필터) |
| 그 명제를 그대로 증명하나 | 테스트가 몰래 전제를 바꾸지 않았나? (목 객체가 검사 대상까지 대체, 설정값을 기대값으로 복사) |
| 커널 버그를 이용하나 | 테스트 프레임워크·빌드 도구의 '구멍' — 예외를 삼키는 `try/catch` 로 항상 초록 |

이 표의 2~3행은 바로 다음 항목(redfirst)이 실측한 것이다. 그리고 "신뢰하는 작은 파일 + 믿지 않는 큰 파일을 기계로 대조"라는 `comparator` 구조는, **사람이 쓴 짧은 명세(인터페이스·계약 테스트)를 고정하고 AI가 구현을 채우게 하는** 작업 방식의 정당화이기도 하다.

**반론·회의적 시각.** 댓글에서 바로 나온 질문: "Lean으로 Lean 커널의 일관성을 증명한다는 건 순환 아닌가?" — 저자는 "전문가가 아니다, Zulip에서 물어보라"고 답했다. 즉 4번 질문의 최종 근거는 저자도 위임하고 있다. 또 저자 스스로 **"이 테스트들이 실패할 거라고 볼 이유는 없다. 아직 아무도 안 돌렸을 뿐"** 이라고 적었다 — 이 글은 OpenAI 결과가 틀렸다는 고발이 아니라 **검증 절차가 비어 있다** 는 지적이다. 다른 댓글은 AI 생성 라이브러리에서 사람이 읽어야 할 파일과 증명 재료 파일을 경로(`Internal`)로 구분하는 관행을 제안했다 — 코드베이스에서 "사람이 검토한 부분 / 아닌 부분"을 표시하는 문제와 같다.

### 4. redfirst와 부록 편향 — "초록 체크"와 "리뷰 코멘트"가 실제로 본 것

**무슨 일인가 (redfirst).** GeekNews Show 글. 별 100개 이상 파이썬 저장소에서 **병합된** 에이전트 버그 수정 PR 120건(저장소당 1건)을 다시 돌렸다. 방법: PR이 바꾼 **테스트 파일만 그대로 두고 나머지를 PR 이전으로 되돌린 뒤**, PR이 추가·수정한 테스트만 실행. 다 통과하면 그 테스트는 수정을 검사하지 않는 것이다. 격리 컨테이너·병합 당일 의존성·네트워크 차단.

**결과.** 비교 가능한 에이전트 PR 69건 중 **10건(14%)**, 같은 저장소들의 사람 PR 57건 중 **5건(9%)** 이 수정 없이도 통과. 그러나 두 쪽 모두 비교된 저장소 45곳으로 짝지으면 **McNemar 정확 검정 p=0.63 — 우연 범위** 다. 저자 스스로 "에이전트가 사람보다 못하다는 결과가 아니다"라고 못박았다. 15건을 LLM 두 번이 독립 판독(14/15 일치)한 이유 분류:

- 단위 테스트로 확인 가능한 변경인데 테스트가 안 본 9건 — ① 실행만 하고 결과를 확인 안 함(assert 없음, 예외를 모두 삼키고 True 반환) ② 바뀐 동작이 아니라 **바로 옆 동작** 을 검사 ③ 기본값이 바뀌자 테스트의 기대값을 **설정값 자체로** 바꿔 어떤 값이어도 통과(1건)
- 단위 테스트로 볼 동작 변화가 원래 없던 6건 — import 정리·포맷·타입 힌트(3), 특정 OS·새 파이썬 버전 전용 코드(2), 테스트가 안 부르는 벤치마크 스크립트(1)

실험 계획서와 공개 기준(판정된 에이전트 PR의 10% 이상이면 공개)을 **돌리기 전에** 정해 둔 점이 좋다 — 결과를 보고 기준을 고르는 함정을 피했다.

**부록 편향 논문(초록만 읽음).** 신시내티대 CincyNLP. ACL·EMNLP·COLM·ICLR 논문 2,000편에서 최신 GPT·Claude가 지적한 약점의 **약 50% 이상이 부록** 에서 나왔다. API·코딩 에이전트·웹 어느 경로로 써도 같았다. 사람 리뷰어는 **8.4%** 만 부록에서 가져오고, 주로 발표 방식과 핵심 아이디어를 지적했다. LLM은 부록 깊은 곳의 **기여와 무관한 세부 기술** 을 짚었다.

**기술적으로 — 둘을 겹치면.** redfirst는 **변이 테스트(mutation testing)** 의 가장 단순한 형태다. 변이 테스트는 코드를 일부러 망가뜨려(부등호 뒤집기, 반환값 바꾸기) 테스트가 실패하는지 본다 — 실패하지 않으면 그 테스트는 그 부분을 지키지 않는다. redfirst는 "망가뜨리기" 대신 **"수정을 통째로 빼기"** 를 쓴다. TDD의 "Red → Green"에서 **Red를 건너뛴 테스트를 사후에 잡는 것** 이라 이름이 redfirst다. 부록 편향은 리뷰어 쪽에서 같은 문제다: 찾기 쉬운 지적거리(빽빽한 표·세부 수치)로 끌려가고, 전체를 꿰어야 나오는 판단("이 설계가 맞나")은 비워 둔다.

**실무에 무슨 의미인가.**

- Java·Spring이라면 PR 브랜치에서 `git checkout origin/main -- src/main` 으로 운영 코드만 되돌리고 `./gradlew test --tests '새로 추가된 테스트'` 를 돌리면 redfirst를 손으로 재현할 수 있다. 상시로 하려면 **PIT(pitest)** 변이 테스트를 Gradle 플러그인으로 붙여 변경 파일만 대상으로 돌리는 방법이 있다
- 에이전트에게 버그 수정을 맡길 때 **"먼저 실패하는 테스트를 커밋하고, 그 다음 수정을 커밋하라"** 를 규칙(CLAUDE.md)으로 두면 Red 단계가 이력에 남는다
- AI 코드 리뷰는 "세부 지적 기계"로 쓰고, **설계 질문은 사람이 따로** — 리뷰 템플릿에 "이 변경이 해결하려는 문제는? 다른 방법은?" 칸을 사람용으로 남긴다

**반론·회의적 시각.** redfirst 표본은 작다(에이전트 69·사람 57, 파이썬만, 병합된 PR만 — 병합 안 된 PR엔 더 나쁜 테스트가 있을 수 있다). 사유 분류도 LLM 판독이다. "수정 없이 통과"가 곧 나쁜 테스트도 아니다 — 리팩터링 PR의 회귀 방지 테스트는 원래 수정 전에도 통과해야 한다(6건이 그 경우). 부록 논문은 초록만 읽어, 부록이 긴 논문일수록 지적이 부록에 몰리는 **분량 효과** 를 통제했는지, 부록 지적이 실제로 틀린 지적인지는 확인하지 못했다. "부록에서 나왔다"는 것과 "쓸모없다"는 다르다.

## 오늘의 흐름

겹치는 것부터 정리한다. 브리핑(10/22)의 eMudhra 사건 자체·패치 표·CT 경계는 어제(10/21) 노트, tsrs는 어제 노트, headroom은 10/20 노트, Anthropic 분기 매출 168억 달러는 10/16 노트, TorchTPU는 어제 노트 '짧게'에서 이미 다뤘다. Jev라는 결정 모델 자체(텍스트를 생성하지 않고 선택지 확률만 돌려주는 모델)는 AI 심층의 「비생성 의사결정 모델」 노트, 실패할 실행을 외부 감시자가 끊는 StopLoss는 어제 AI 심층 노트에서 봤다. 이 노트는 **새 항목과, 재등장 항목의 새 사실만** 본다. eMudhra는 오늘 Scott Helme의 글로 "키가 왜 복구됐나"의 답이 나와서 짧게 보충한다.

첫 번째 축은 브리핑 제목 그대로 **"바닥층 네 곳이 하루에 흔들렸다"**다 — PHP 런타임(인증 없는 RCE 2건), 인증서 신뢰 저장소(eMudhra), 패키지 레지스트리(LiteLLM 1.107.0), 배포 플랫폼의 시크릿 저장소(Railway). 어제 노트의 "신뢰의 바닥은 파일이다"가 하루 만에 네 번 반복됐다. 그런데 원문들을 나란히 놓으면 브리핑의 "AI가 공격·방어 양쪽의 장벽을 낮췄다"보다 더 구체적인 공통점이 보인다. **네 건 모두 '검사는 통과했다'.** eMudhra의 키 4로 만든 공개키는 곡선 위의 정상적인 점이라 모든 구조 검증을 통과했다. LiteLLM의 sdist는 GitHub 커밋과 블롭 해시가 일치하는 파일이 대부분이고, 바뀐 건 `pyproject.toml` 한 줄과 sdist에 들어 있지도 않은 폴더 하나였다 — 의존성 핀까지 rc2와 같게 맞춰서 "rc2와 diff를 떠도 이상 없음"이 나오게 했다. PHP의 OOM 결함은 2024년 외부 감사에서 이미 징후가 잡혔다. 검사·감사·diff가 다 있었는데 막지 못했다.

두 번째 축이 오늘 처음 강하게 보이는 흐름이다. **"알아내는 것과 결정·행동하는 것은 다른 일이고, 병목은 뒤쪽이다."** PHP 재단은 2년 늦은 이유를 기술이 아니라 **의사결정 구조**라고 직접 썼다 — 수정안마다 하위 호환성 파괴 / 새 DoS 가능성 / 서드파티 확장 수정 강요 중 하나를 감수해야 했고, **합의제로 움직이는 보안팀이 잘못된 선택의 후과를 두려워해 고르지 못했다**. 재단 표현은 "구조적 실패". 같은 날 HF의 단독 저자 논문 "Good Judgment, Bad Advice"는 같은 구조를 에이전트 안에서 쟀다. 결정 모델 Jev가 "이 실행이 끝났나"를 다른 컨트롤러보다 **잘 맞혔는데**(AUROC 0.78), 그 판단을 행동으로 바꾸는 규칙이 틀려서 **비용만 19% 올렸다**(통과율 73.0% 대 73.0%). 재단 글의 마지막 단락도 같은 말을 한다 — "도구는 그 어느 때보다 빨리 버그를 찾는다. 도구가 못 하는 것은 엔진의 오래된 설계 결정에 대해 올바른 수정을 정하고, 호환성 트레이드오프를 저울질하고, 패치를 리뷰하는 일이다." 10/18 노트의 "버그를 찾는 속도가 고치는 속도를 앞질렀다"(PostgreSQL 19 연기)가 이번엔 언어 런타임에서, 그리고 비용 회계 쪽에서 반복됐다.

세 번째 축은 이어지는 흐름이지만 방향이 갈렸다. **"에이전트 바깥을 손볼 때, 쌓는 쪽과 버리는 쪽."** Agent S4는 메타 에이전트가 작업 궤적을 보고 인터페이스(헬퍼·사용법)를 저장소에 쌓아 같은 27B 모델을 3.8배로 만들었고, Anti-Persistence는 반대로 궤적에서 뽑은 "교훈·규칙"을 저장하지 말고 매번 다시 만들라고 한다. 둘을 같이 놓으면 모순이 아니라 **무엇을 쌓느냐**의 차이다 — S4가 쌓는 건 "실행해 보면 되는지 안 되는지 드러나는 것"(도구, 그리고 메타 에이전트가 못 본 검증 과제로 선별)이고, Anti-Persistence가 버리는 건 "틀려도 아무도 모르는 것"(해석). TEAL도 "Worker가 실제로 그 도구를 썼나"를 채택 기준으로 삼는다. 즉 세 논문 모두 **검증되는 산출물은 쌓고, 검증 안 되는 해석은 쌓지 말라**로 수렴한다. 10/20 AI 심층의 「객체 지향 컨텍스트 폴딩」(대화 요약 대신 환경에 남은 결과물을 가리켜라)과 같은 줄기다.

네 번째는 짧게, **"사람에게 먼저 오는 에이전트"**. Claude Duet은 상시 켜져서 아침 브리핑을 보내고 결제·발송 같은 민감 작업만 승인을 받는다. 오늘의 다른 축과 겹쳐 읽으면 Duet의 설계 질문이 곧 Jev 논문의 질문이다 — **"언제 사람을 부르고 언제 조용히 있을지"를 정하는 정책**이 판단 능력보다 중요하다. 그리고 그 에이전트가 쥔 토큰이 LiteLLM 악성코드의 수집 목록(`ai_devtools` 모듈)에 이미 들어 있다.

## 깊게 본 것

### 1. PHP 인증 없는 RCE 2건 — 2년 늦은 이유는 '못 고쳐서'가 아니라 '못 정해서'

**무슨 일인가.** 10/21 PHP 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35 동시 릴리스. 고친 것은 두 건이다.

- **CVE-2026-109618 — OOM 손상을 통한 RCE.** 요청이 `memory_limit`에 *하필 나쁜 순간*에 걸리면 PHP가 반쯤 초기화된 내부 데이터를 남기고, 나중에 그것을 유효한 데이터로 취급해 메모리가 손상된다. **Apache + mod_php에서는 인증 없는 요청이 애플리케이션 코드가 돌기도 전에 이를 일으킬 수 있고, 기본 설정으로 완전한 RCE가 시연됐다.** PHP-FPM에서는 애플리케이션 코드 경로를 통한 RCE가 확인됐다.
- **CVE-2026-109619 — 오래된 전역 상태(stale global state)를 통한 RCE.** 잘못된 지점에서 치명적 오류가 나면 내부 상태가 *이전 요청의* 메모리를 가리킨 채 남고, 같은 워커가 처리하는 다음 요청이 그 해제된 메모리를 쓴다(use-after-free). 실제 애플리케이션을 대상으로 RCE가 시연됐다.

두 결함 모두 "거의 모든 요청이 거치는" 메모리 관리와 에러 처리에 있다. 재단은 이 위치가 심각성의 원인이자 **고치기 어려웠던 원인**이라고 쓴다 — 호환성·성능·서드파티 확장 생태계를 건드리지 않고는 고칠 수 없는 곳이었다.

**배경 — 왜 2024년에 본 것을 2026년에 고쳤나.** 원문의 시간 순서:

1. 2024년, Sovereign Tech Agency 자금·OSTIF 주관·Quarkslab 수행의 외부 감사. 감사 결과의 *다른* 이슈를 고치던 재단 계약 개발자가 OOM 문제의 첫 징후를 발견. 이론상 익스플로잇은 상정됐지만 구체적 공격 경로는 못 찾았고, 영향이 분명한 다른 이슈들에 밀렸다.
2. 보안팀이 경쟁하는 수정안을 여럿 만들었지만 각각 **하위 호환성 파괴 / 새로운 DoS 가능성 / 조율이 불가능해 보이는 서드파티 확장 수정** 중 하나를 대가로 요구했다. **합의제**로 움직이는 팀이 고르지 못했고, 엔진을 깊이 아는 소수 코어 개발자는 다른 일에 묶여 있었다. 작업이 몇 달씩 멈췄다 재개되길 반복했다.
3. 2026년 7월 30일, OpenAI의 Patch the Planet 프로그램으로 보안업체 Calif가 감사 시작. **8월 11일 Calif의 Ryan A가 조건 없는 RCE를 보고, 같은 날 OpenAI가 독립적으로 같은 근본 원인을 보고.** 이어 Wiz(8/24), OpenAI(9/18)가 추가 공격 경로를 보고. 이때부터 최우선 과제.

**기술적으로 — "워커 재사용"이 왜 핵심인가.** PHP-FPM·mod_php는 요청마다 프로세스를 새로 만들지 않고 워커를 재사용한다. 그래서 "이 요청이 끝나면 내부 상태는 깨끗해진다"는 가정이 깨지면 **한 요청의 잔해가 다음 요청에 보인다**. 두 번째 CVE가 정확히 이 모양이다. 첫 번째 CVE는 "메모리 한도 초과"라는 *정상적인 에러 처리 경로*가 오염의 입구라는 점에서 무섭다 — 공격자가 할 일은 하필 나쁜 순간에 메모리를 꽉 채우는 요청을 보내는 것뿐이다.

**조정 공개가 깨진 과정(UTC).** 10/20 15:00경 CVE 번호 2개가 포럼·소셜에 퍼짐(틀린 릴리스 시각, 틀린 CVSS 10.0 — 실제 9.2; 기술 세부는 미유출) → 19:30 사전 공지 앞당김, 릴리스를 10/22 14:00 → **10/21 14:00**으로 하루 당김(배포판이 아직 패키징 중이라 즉시 릴리스는 많은 사용자에게 업데이트 경로가 없었음) → 20:00경 Calif가 PoC 영상을 실수로 공개, 삭제됐지만 복사본이 퍼져 각종 PoC 개발을 가속 → 23:00경 일부 핵심 인프라 제공자에게 준 완화 안내도 유출됐을 가능성 → **10/21 07:41 Chainguard가 조정 공개 6시간여 전에 패치된 이미지를 일방적으로 공개**(바이너리 diff로 공격자가 수정 위치를 연구할 수 있게 됨). 재단은 릴리스 시점까지 "작동하는 익스플로잇은 확인하지 못했다"고 적었다.

**AI가 들어간 자리 — 원문 기준으로 정확히.** 브리핑은 "실제 공격 경로를 찾아낸 것도 AI 보안 에이전트(OpenAI·Wiz·Calif)"라고 묶었지만, 원문에서 Calif·Wiz는 보안업체이고 보고자도 Calif의 연구자 개인(Ryan A)이다. 원문이 이름으로 밝힌 AI 도구는 셋이다 — 올해 초 Alpha-Omega와 함께 돌린 **Anthropic Claude Mythos 스캔**, 보고·익스플로잇 검증에 쓰는 **OpenAI Daybreak Red**, 감사자 감사 목록의 **OpenAI Codex Security**. 그리고 재단은 "AI는 보고를 검증하고 같은 근본 원인의 보고를 묶는 데 돕지만, 모든 결정은 사람이 내리고 모든 패치는 사람이 작업한다"고 못 박는다. 7월 1일 이후 CVE 15건, **무효·중복·재현 불가 보고 100건 이상**을 처리했다 — AI 보조 연구가 늘린 것은 발견만이 아니라 **분류 부담**이다.

**실무에 무슨 의미인가.**

- **"애플리케이션 코드가 돌기 전"의 공격면.** mod_php RCE는 내 코드의 품질과 무관하다. Spring Boot로 치면 내장 Tomcat·JVM·컨테이너 베이스 이미지가 의존성 버전(`build.gradle`)과 *별도로* 패치 대상이라는 뜻이다. 의존성 스캐너가 보는 목록에 런타임이 없는 경우가 많다.
- **요청 간 상태 누수는 언어를 가리지 않는다.** 스레드 풀을 재사용하는 서블릿 컨테이너에서 `ThreadLocal`을 `remove()` 하지 않으면, 이전 요청의 사용자 정보가 다음 요청에 보이는 사고가 같은 모양이다. 커넥션 풀에 남은 세션 변수(`SET` 문)도 마찬가지다.
- **의존성의 거버넌스는 보안 지표다.** 2년 지연의 원인이 기술이 아니라 "합의제 의사결정 + 인력 부족"이었다. 재단이 내놓은 처방도 기술이 아니라 조직이다 — 다수결 결정과 타협 장려, 트레이드오프에 막힌 취약점을 재단 리더십까지 빨리 올리는 경로, 전담 인력(5월 Ecosystem Security Team, 7월 Alexandre Daubois, 9월 Daniel Scherzer).

**반론·회의적 시각.** HN에는 "쉬운 익스플로잇은 없다"는 반대 시각의 글도 올라왔다 — 조건(하필 나쁜 순간의 OOM, 특정 지점의 치명적 오류)이 까다로워 대량 공격은 어렵다는 주장. 반면 브리핑에 따르면 네덜란드 국가사이버보안센터는 예방 차원에서 자기 웹사이트를 내렸다. 그리고 재단의 개선책은 "다음에 트레이드오프에 막힌 심각한 취약점이 오면 리더십에 훨씬 빨리 닿을 것이라 확신한다"는 **선언**이다 — 다음 사고 전에는 검증할 수 없다. 재단 글 후반부가 후원 요청이라는 점도 감안해서 읽는다(인력 부족이 원인이라는 진단과 후원 요청이 같은 글에 있다).

### 2. LiteLLM 1.107.0 — 소스는 깨끗했고, 릴리스는 태그와 맞지 않았다

**무슨 일인가.** 여러 LLM API를 한 인터페이스로 묶는 LiteLLM의 PyPI 1.107.0에 자격증명 탈취기와 원격 코드 실행 백도어가 들어갔다. 휠 7개(Linux·macOS·Windows)와 sdist 전부. **1.106.2, 1.107.0rc1, rc2는 깨끗**하고, 1.107.0이 핀한 동반 패키지 `litellm-proxy-extras==0.4.110`·`litellm-enterprise==0.1.78`도 깨끗하다. PyPI는 해당 릴리스를 내렸다.

**어떻게 들어갔나 — 한 줄과 보이지 않는 폴더.** sdist의 `pyproject.toml` maturin 빌드 절에 `data = "cook"` 한 줄이 추가됐다. 이 설정은 `cook/` 폴더를 휠의 `.data/purelib/`로 복사하고, pip은 그걸 `site-packages`에 설치한다. **그런데 sdist에는 `cook/` 폴더가 빠져 있다** — 소스 배포본을 열어 봐도 보이는 변화는 그 한 줄뿐이다. 공개 저장소 어느 커밋에도 이 줄이나 폴더가 없다.

**SafeDep의 감식 — "태그와 릴리스가 맞지 않는다."** 이 부분이 원문에서 가장 배울 만하다.

- 태그 `v1.107.0`은 커밋 `66c8f5b`(06:59 UTC)를 가리키는데, 그 커밋의 `pyproject.toml`은 `version = "1.108.0"`이다.
- SafeDep이 sdist의 모든 파일을 git 트리와 **블롭 해시로** 대조하니, sdist는 더 뒤의 `main` 커밋 `a8113b0`(08:50) + 수정 파일 5개 + `cook/`과 일치했다. 수정 파일 넷은 `Cargo.toml`에 `readme` 한 줄 추가(정상 릴리스 1.106.2·rc2에도 있는 편집). 다섯 번째가 `pyproject.toml`이다 — **버전을 1.107.0으로 되돌리고, 동반 패키지 핀을 rc2 값으로 되돌리고**, `data = "cook"`을 넣었다. 그 결과 **rc2와 의존성 diff를 떠도 아무 이상이 안 보인다.**
- 휠은 정상 BerriAI 파이프라인 산출물과 같은 모양이다 — `WHEEL`의 maturin 1.9.4가 정상 릴리스와 같고, 악성 파일의 `RECORD` 항목이 올바르다(빌드 *후에* 손댄 게 아니라는 뜻). zip 타임스탬프로 macOS 11:20 / Linux 11:21 / Windows 11:37 빌드. **Windows 휠의 `.py` 2,804개가 전부 CRLF**(악성 3개 포함), Linux 휠엔 없음 — 줄바꿈 변환을 켠 Windows git 체크아웃의 패턴이다.
- 09:30~12:30 사이 공개 GitHub Actions 실행 539개 중 이 릴리스를 빌드·게시한 것은 없다. 11:50에 `litellm-dispatcher[bot]`이 GitHub 릴리스를 게시(1.106.2도 같은 10분 지연). **1.107.0, 1.106.2, rc2 모두 PyPI provenance 증명이 없다.**

결론(SafeDep, 중간~높은 확신): **BerriAI의 비공개 릴리스 파이프라인이 공격자가 수정한 git 소스로 빌드했다** — 탈취된 메인테이너·봇 자격증명, 비공개 브랜치·미러, 또는 파이프라인이 빌드하는 참조(ref)를 썼을 수 있다. "탈취된 PyPI 토큰으로 공격자 기계에서 올렸다"는 증거와 **덜** 맞는다. 브리핑의 "릴리스 파이프라인 침해나 PyPI 자격증명 탈취로 추정"은 두 가설을 대등하게 놓았는데, 원문은 앞쪽에 무게를 둔다.

**기술적으로 — 왜 import하지 않아도 도나.** 설치되면 `site-packages`에 세 파일이 놓인다.

| 파일 | 크기 | 동작 |
| --- | --- | --- |
| `cook.pth` | 12바이트 | `import cook` 한 줄. Python은 시작할 때 `site-packages`의 `.pth`에서 `import`로 시작하는 줄을 **실행**한다 |
| `cook.py` | 22,252바이트 | `exec(zlib.decompress(b64decode(...)))` 한 겹으로 감싼 약 61KB의 탈취기 |
| `sitecustomize.py` | 25,509바이트 | Python이 시작 시 자동 import하는 모듈 이름. 백도어 데몬 + 탈취기 사본 |

그래서 그 환경의 **모든 Python 프로세스** — 애플리케이션, pip, IDE 언어 서버, CI 작업 — 가 시작할 때 실행된다. litellm을 import할 필요가 없다.

탈취기 모듈 16개 중 눈에 띄는 것: `ai_devtools`(Claude Code·Claude Desktop·Cursor·Windsurf·Copilot·VS Code `mcp.json`·Gemini CLI·Codex `auth.json`·Aider·Zed·Kiro·HF 토큰 등), `db_litellm`(`DATABASE_URL`을 읽어 LiteLLM 프록시의 `LiteLLM_CredentialsTable`·`LiteLLM_ProxyModelTable` 덤프 = 프록시가 쥔 **LLM 제공자 API 키 전부**), `env_vars`(`/proc/<pid>/environ`으로 **다른 프로세스의** 환경변수), `cloud_metadata`(AWS IMDSv2 → v1 순으로 인스턴스 역할 자격증명). 결과는 무작위 AES-256-CBC 키로 암호화하고 그 키를 RSA-4096 OAEP로 감싸 tar.gz로 묶어 `www.litellm[.]dev/healthcheck`로 POST, 성공하면 `/tmp/.pc_once_…` 표식을 남겨 호스트당 1회만 수집한다.

백도어는 `fork()`+`setsid()`로 부모에서 떨어져 나간 뒤 **매시간** 공격자 GitHub 저장소의 `domain.txt`를 읽어 서버 주소를 얻고, 탈취기 사본(1회 표식 없음)을 다시 돌리고, `http://<domain>/codepy`를 내려받아 `exec()` 한다. 주소를 GitHub 파일에 둔 이유는 **서버를 바꿔도 감염 호스트를 다시 건드릴 필요가 없게** 하기 위해서다. 13:40에 그 계정이 404가 되어 지금은 아무것도 못 하지만, 그 전에 데몬이 돈 호스트는 2단계 코드를 받았을 수 있고 SafeDep은 서버 주소를 복구하지 못했다. 업로드(11:39~11:40)부터 삭제 관측(13:40)까지 **약 2시간**이다.

**실무에 무슨 의미인가.**

- **"GitHub를 봤으니 안전하다"는 통하지 않는다.** 소스 저장소와 레지스트리 산출물은 다른 물건이고, 사이에 빌드가 있다. 검사해야 할 것은 "이 산출물이 이 태그에서 나왔나"(provenance)이고, 이번 릴리스엔 그 증명이 없었다. Maven Central의 서명·npm provenance도 같은 질문이다.
- **해시 핀의 의미.** `pip install --require-hashes`·`uv.lock`·Gradle dependency verification은 "이미 본 그 파일"만 허용한다. 1.107.0이 나온 날 그걸 자동으로 받아오는 구성(범위 지정 버전, 락파일 없는 CI)이 2시간 창에 걸린다.
- **"import 안 했으니 무관"이 아니다.** `.pth`·`sitecustomize`처럼 *시작 시 자동 실행되는 지점*은 Java에도 있다 — `-javaagent`, `JAVA_TOOL_OPTIONS`, 클래스패스의 `META-INF/services`(ServiceLoader), Spring Boot의 `spring.factories`/`AutoConfiguration.imports`. 의존성이 "로드만 돼도" 코드를 실행할 수 있는 자리들이다.
- **개발 머신의 AI 도구 토큰이 명시적 표적이다.** 장수 토큰을 디스크에 두지 않는 것이 답이고, 브리핑의 '실무' 8번(Secure Enclave SSH 키)이 같은 방향이다 — 파일이 없으면 파일을 읽는 악성코드는 가져갈 것이 없다.

**반론·회의적 시각.** SafeDep 결론은 외부 증거(해시·타임스탬프·CRLF·Actions 로그)로 세운 추정이고, 원문 스스로 "BerriAI의 파이프라인 로그만이 원인을 확인할 수 있다"고 쓴다. 감염 규모(다운로드 수)도 원문에 없다. 그리고 SafeDep은 공급망 보안 제품 회사다 — 분석의 질은 높지만 결론이 "provenance 검증 도구가 필요하다"로 향하는 동기가 있다.

### 3. Railway 환경변수 유출 — "암호화돼 있었다"는 방어가 아니다

**무슨 일인가.** 10/21 Railway(PaaS)가 공개: 고객 환경변수를 저장하는 시스템에서 이상 활동을 탐지했고, 비인가 제3자가 **암호화된 환경변수에 접근했으며 일부는 복호화된 내용까지 확보했을 수 있다.** 조사 중 **모든 배포를 일시 중단**(빌드 복구 전까지 새 버전 롤아웃 불가). 영향이 일부 사용자로 제한될 가능성을 말하면서도 **모든 사용자에게** 환경변수 전부·API 키·프라이빗 레지스트리 자격증명을 즉시 교체하고 해당 서비스 로그를 점검하라고 권고. 근본 원인은 미공개.

**배경 — "AI 추론 제공자를 노린 연쇄 공격".** Railway는 이번 건을 "최근 플랫폼 기업을 겨냥해 **AI 추론 제공자**를 침해하려는 일련의 공격의 일부"로 본다고 쓰고, 상위 제공자들에게 키를 선제 폐기하도록 통보했다. 같은 날 LiteLLM 탈취기에도 "LiteLLM 프록시 DB의 LLM 제공자 키 덤프" 모듈이 있었다. **표적이 같다** — LLM API 키를 대량으로 쥔 중간 계층. 다만 두 사건을 직접 연결하는 언급은 어느 원문에도 없다.

**기술적으로.** 환경변수 암호화는 "저장소 디스크가 털렸을 때"를 막는다. 그런데 앱을 띄우려면 플랫폼이 어딘가에서 복호화해 프로세스에 주입해야 하므로, **복호화 키나 복호화 경로를 가진 시스템**이 털리면 암호화는 의미가 없다. "일부는 복호화된 내용까지"가 그 뜻이다.

**실무에 무슨 의미인가.** "키를 잘 숨기는 것"보다 **"키를 짧게 살게 하는 것"**(단기 토큰, 주기적 로테이션, 역할 기반 임시 자격증명 — AWS라면 액세스 키 대신 IAM 역할·OIDC 페더레이션)이 실질적인 방어다. 그리고 **로테이션을 해 본 적이 있는가**가 오늘의 시험이다 — Spring Boot 앱이라면 `DB_PASSWORD`를 바꿨을 때 재배포 없이 반영되는지, 커넥션 풀이 기존 연결을 언제 버리는지. Railway처럼 배포가 막힌 상태에서 로테이션해야 한다면 "재배포로 반영"이라는 전제부터 깨진다.

**반론·회의적 시각.** 원문은 짧은 1차 공지라 영향 범위·원인·기간이 전부 비어 있다. "일부 사용자" 가능성을 말하면서 전원 교체를 권한 것은 보수적이지만, 사용자 입장에선 무엇이 나갔는지 모르는 채 전부 돌려야 한다는 뜻이다. 후속 공지를 봐야 판단할 수 있다.

### 4. eMudhra 보충 — 키는 '잘못 생성된' 수준이 아니라 한 바이트였다

어제 노트는 상황 추적 페이지 기준으로 "키를 잘못 생성해 인증서만으로 누구나 복구할 수 있다"까지 적고 기술 세부는 못 읽었다고 남겼다. 오늘 Scott Helme의 글이 그 빈칸을 채운다.

- **키가 한 바이트였다.** P-384 개인키 `d`는 무작위 384비트 수(약 10¹¹⁵가지)여야 하는데, 8개 키 모두 **0이 47바이트 깔리고 마지막 1바이트만 값이 있다** — 156, 230, 115, 56, 155, **4**, 66, 237(TLS 6개 + 코드 서명 2개). 공개키는 `d × G`이므로 `1×G, 2×G, …`를 최대 255번 계산해 인증서의 공개키와 맞으면 끝이다. Helme는 Mozilla가 첨부한 인증서 16개(키 8개 × eMudhra 발급·Sectigo 교차 서명 각 1장)를 노트북에서 1초 안에 전부 풀었다.
- **모든 구조 검증을 통과한다.** `d = 4`로 만든 공개키도 곡선 위의 유효한 점이고 인코딩도 정상이다. **알아내는 방법은 실제로 풀어 보는 것뿐이다.** 이게 오늘 흐름 첫 번째 축("검사는 통과했다")의 가장 선명한 사례다.
- **원인(eMudhra가 Mozilla 버그 2083449에 쓴 설명).** 키 생성 의식(ceremony)에 쓴 스크립트의 버그로 HSM에 **두 번째 약한 키 페어**가 생겼고, 이름이 비슷해 사람의 실수로 CSR에 잘못된 키가 쓰였다. 스크립트 버그 + 이름 혼동 + 검증 부재의 3단 실패다.
- **"봉쇄할 수 없다"의 뜻.** 보통 키 유출은 훔친 사람과 시점이 있다. 여기선 아무도 훔칠 필요가 없었다 — 2025년 4월부터 17개월간 인증서를 본 누구나 밀리초 만에 키를 가질 수 있었고, 누가 그랬는지 알 방법이 없다. 그래서 Mozilla는 중간 인증서 차단을 넘어 **루트 제거**(NSS 업데이트)까지 갔고 Chrome도 Root Store v43에서 뺀다.
- **비브라우저 실험.** Helme가 `api.stripe.com`용 위조 인증서로 로컬 테스트: curl `SSL certificate verify ok`, Python 핸드셰이크 완료, Node `authorized: true` — 시험한 모든 Linux·macOS에서. Windows CryptoAPI는 폐기 확인을 켜지 않으면 체인을 받아들였고, 켜도 두 경로 중 하나만 폐기로 나왔다. 펌웨어가 고정된 기기는 **2039년 7월 만료까지** 믿는다.
- **AI 한 줄.** Helme 갱신 문구: Claude가 프롬프트 한 번으로 CA 개인키를 복구했다. 다만 이 경우는 "AI가 장벽을 낮췄다"기보다 원래 장벽이 255번의 덧셈이었다는 쪽이 정확하다.

Spring 쪽 연결: `RestClient`/`WebClient`는 JVM `cacerts`(또는 지정한 truststore)를 보고 기본으로 폐기 확인을 하지 않는다. 어제 노트의 "JDK가 패치 표에 없는 이유" 질문은 여전히 열려 있다.

### 5. Good Judgment, Bad Advice — 잘 맞히는 판정자가 비용만 올렸다 (요약, 본편은 AI 심층)

Terminal-Bench 2.1에서 Claude Sonnet 5.5 에이전트 루프를 고정하고 **컨트롤러만** 바꾼 사전 등록 실험(held-out 21과제 × 5개 조건 × 3회 = 315회). 결정 모델 Jev 1.13은 "끝났나/검증하라"를 오프라인에서 가장 잘 순위 매겼지만(AUROC 0.78, 규칙 0.62, Haiku 5.5 0.60), **"완료" 확률 평균 0.50인데 실제 87%가 통과** — 그래서 맞은 작업을 다시 검증하라고 시켰다(53번의 완료 요청 중 29번 verify). 결과: 비용 +19%(1.19, 95% CI 1.02–1.36), 통과율 73.0% 동일. Jev의 과거 선택 빈도대로 무작위로 고르는 **위약(placebo)**이 같은 통과율을 22% 싸게 냈다. 어떤 컨트롤러도 "포기(abandon)"를 한 번도 고르지 않았다. 어제 StopLoss(끊어서 아끼는 쪽)와 짝이 되는 결과로, 구조와 실무 번역은 AI 심층의 「판단 신호와 개입 정책」 노트로 뺐다.

## 더 알아볼 것

- [ ] **내 Python 환경에 시작 시 자동 실행 지점이 있는지 본다.** `python -c "import site; print(site.getsitepackages())"`로 경로를 찾아 `*.pth` 파일 중 `import`로 시작하는 줄과 `sitecustomize.py`·`usercustomize.py` 존재 여부를 확인한다. 이어서 Java 쪽 대응물(`JAVA_TOOL_OPTIONS`, `-javaagent`, Spring Boot `AutoConfiguration.imports`)을 표 하나로 정리하고, "의존성이 로드만 돼도 코드를 실행하는 자리"를 Gradle의 `dependency verification`(`verification-metadata.xml`)이 어디까지 막는지 확인한다.
- [ ] **"이 산출물이 이 태그에서 나왔나"를 직접 검증해 본다.** 아무 PyPI 패키지 하나를 골라 sdist를 받고, GitHub 태그 체크아웃과 `git hash-object`로 파일 블롭 해시를 대조해 본다(SafeDep이 한 방법). 그 패키지에 PyPI provenance(Trusted Publishing 증명)가 있는지도 본다. Maven Central에서는 같은 질문에 무엇(서명·SBOM·Sigstore)이 답하는지 찾는다.
- [ ] **ThreadLocal 누수를 재현해 PHP CVE-2026-109619의 모양을 몸으로 이해한다.** Spring Boot에서 `ThreadLocal<String>`에 사용자 ID를 넣고 `remove()` 없이 응답한 뒤, Tomcat 스레드 수를 `server.tomcat.threads.max=1`로 줄여 다음 요청에서 이전 값이 보이는지 확인한다. 그다음 `HandlerInterceptor.afterCompletion`에서 정리하는 방식과 비교한다.
- [ ] **시크릿 로테이션을 재배포 없이 해 본다.** 로컬 PostgreSQL 비밀번호를 바꾼 뒤 HikariCP가 기존 연결을 언제 버리는지(`maxLifetime`), 새 비밀번호를 어떻게 받는지(Spring Cloud Config/Vault의 `@RefreshScope` 또는 재시작) 정리한다. "Railway처럼 배포가 막힌 상태에서 키를 돌려야 한다면?"에 답할 수 있게.
- [ ] **PHP 재단의 "합의제 → 다수결" 전환을 다른 오픈소스와 비교한다.** 내가 쓰는 핵심 의존성 하나(예: Spring Framework, HikariCP)의 `SECURITY.md`·보안 정책 페이지를 읽고, 취약점 보고 경로·대응 SLA·의사결정 주체가 적혀 있는지 확인한다. "의존성을 고를 때 거버넌스를 본다"를 체크리스트로 만든다.

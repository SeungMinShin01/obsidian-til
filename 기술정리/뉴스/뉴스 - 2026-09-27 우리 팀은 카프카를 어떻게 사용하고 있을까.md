## 배경

글은 배달의민족 배달서비스팀이 배민배달·B마트·배민스토어를 통합해 하루 100만 건이 넘는 주문을 처리한다고 소개한다. 배달 상태 이벤트가 여러 시스템에 걸쳐 발생하는 구조에서, (1) 이벤트가 거의 동시에 발생해 순서가 뒤바뀌는 문제, (2) DB 트랜잭션과 Kafka 메시지 발행이 따로 놀아 배달 취소가 DB엔 기록됐는데 메시지는 안 나가 하위 시스템이 배달을 계속 진행하는 정합성 문제, (3) 배치로는 잡을 수 없는 실시간 배달 현황 가시성 부재, (4) 여러 배달 서버에 흩어진 설정을 동기화해야 하는 문제를 각각 카프카의 다른 기능으로 풀었다고 설명한다.

## 핵심

- 이벤트 순서 보장: 주문ID·배달ID를 파티션 키로 써서 같은 대상의 이벤트를 항상 같은 파티션에 몰아넣고, 파티션 안에서는 컨슈머 1개가 순차 처리하게 해 거의 동시에 발생한 이벤트도 순서가 뒤집히지 않게 함
- 데이터-메시지 정합성: DB 기록과 메시지 발행을 한 트랜잭션으로 묶는 대신, MySQL Outbox 테이블에 변경분을 기록하고 Debezium MySQL Source Connector가 binlog를 순서대로 읽어(CDC) 자동으로 메시지를 발행 — DB 트랜잭션 성공이 곧 메시지 발행 보장으로 이어진다고 설명
- 처리량 병목 해결: 순서 보장을 위해 커넥터 태스크를 1개로 두면 처리량이 막히는 문제가 있어, Outbox 테이블 자체를 delivery-outbox1 / delivery-outbox2 / delivery-outbox3처럼 토픽 단위로 분할하고 각각 별도 커넥터에 연결 — 같은 키의 순서는 유지하면서 처리량은 테이블 수만큼 분산
- 분산 설정 동기화: Spring Cloud의 RemoteApplicationEvent를 Kafka 위에 얹어 이벤트 버스로 사용 (DeliveryServiceRemoteApplicationEvent가 이를 상속), 토픽ID는 `${serverName}:${identifier}` 규칙, 서버별로 다른 컨슈머 그룹ID(`anonymous.{identifier}`)를 둬서 배포된 모든 서버가 같은 설정 변경 이벤트를 각자 독립적으로 받게 함 — 트래픽이 적어 파티션은 1개만 사용
- 실시간 집계 1단계: 배달이 끝나면 Redis에 임시로 모아둔 상태를 통합 이벤트로 만들어 analysis 토픽에 발행하고, S3 Sink Connector로 S3에 적재해 Athena로 과거 이력을 조회할 수 있게 함
- 실시간 집계 2단계: Kafka Streams 애플리케이션이 배달ID별 최신 상태를 담는 latest-delivery, 상태별 건수를 세는 count-per-status 두 상태 저장소를 유지하고, 이를 Grafana 게이지로 시각화해 이상 감지·알림에 활용한다고 설명
- 원본(비즈니스 로직용) 토픽과 분석용 토픽을 분리해, 분석 트래픽 증가가 핵심 배달 처리 로직에 영향을 주지 않도록 격리했다고 설명

## 내 프로젝트와의 연결

수집기 프로젝트의 "API에서 채용공고를 수집한 뒤 SQLite에 저장까지 원자적으로 끝나야 한다"는 문제는, 이 글의 "DB 기록과 메시지 발행이 따로 놀면 정합성이 깨진다"는 문제와 구조가 닮아 있다. 다만 이 글은 Debezium CDC로 DB 변경 자체를 감지해 발행을 트리거하는 방식이라, 수집기처럼 스케줄러가 능동적으로 API를 호출하는 구조와는 트리거 방향이 반대다 — 그래도 "쓰기 성공과 후속 작업 성공을 한 번에 보장하기 어렵다"는 문제의식 자체는 가져올 만하다. WMS 쪽은 파티션 키로 같은 대상의 이벤트 순서를 강제하는 방식이, 같은 재고 항목에 동시 요청이 몰릴 때 순차 처리를 강제하는 동시성 락 문제와 구조적으로 비슷한 지점이다. 직접 연결은 약한 편이라 억지로 잇지 않는다.

## 오늘 정리할 것

1. Debezium과 CDC(Change Data Capture)가 정확히 뭘 하는 기술인지, MySQL binlog를 어떻게 읽는지 찾아서 개념 확인하기
2. Outbox 패턴을 CDC 없이 폴링(polling)만으로 구현하는 방식과 이 글의 CDC 방식을 비교해서 장단점 정리하기
3. Spring Cloud Bus의 RemoteApplicationEvent가 실제로 어떤 상황에서 쓰이는지 공식 문서나 예제로 확인하기
4. Kafka Streams의 상태 저장소(State Store) 개념을 간단히 찾아보고, 오늘 글의 latest-delivery / count-per-status 예시에 대입해 이해했는지 확인하기

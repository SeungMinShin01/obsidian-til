## 배경

배달의민족 주문접수채널팀은 사장님의 PC·모바일·POS로 "주문~!" 알림을 보낸다. 원래는 MQTT 브로커로 알림을 밀어넣었는데, 글은 네 가지 문제가 쌓여 있었다고 설명한다. ① 레거시 클라이언트 라이브러리가 일정 바이트 이상의 페이로드를 못 받아서 **Zero Payload**(빈 메시지)만 보내고 클라이언트가 API를 다시 호출해 하드코딩된 문구를 띄웠다 — 알림 문구가 클라이언트 버전에 묶이고 API 왕복만큼 지연이 붙는다. ② MQTT에 보안을 붙이기 복잡해 최소한의 연결 보안만 있었다. ③ MQTT는 1883/8883 포트라 방화벽에 막히는 매장이 있어 **Polling 로직을 병행**해야 했다. ④ Webview에서는 MQTT over WebSocket 연결에 제약이 있었다. 먼저 AWS IoT를 도입해 ①②(X.509 인증서 + Topic별 IoT Policy, 정형화된 JSON 메시지)는 풀었지만 ③④는 MQTT를 쓰는 한 남았고, 그래서 SSE로 갔다는 흐름이다.

## 핵심

- **SSE 선택 근거** — 이미 REST API 인프라가 안정적으로 돌고 있어서, WebSocket으로 가면 모든 API를 재구현하거나 두 프로토콜을 동시에 운영해야 했다. 서버→클라이언트 단방향이면 충분하고 클라이언트→서버는 기존 REST로 되므로, 양방향은 오버엔지니어링이라고 판단했다고 쓴다.
- **메시지 전달 방식 3안 비교** — (1) 세션이 붙은 서버의 API를 직접 호출, (2) 브로커에서 그 서버 인스턴스 토픽으로만 라우팅, (3) 브로커로 전 서버에 브로드캐스트. (1)은 Redis 같은 세션 저장소와 실시간 동기화가 필요하고 재시작 중 유실 위험, 전송 API 외부 노출 문제. (2)는 서버 10대면 토픽 10개 + 여전히 세션 추적 필요 + 오토스케일링에서 토픽 생성·삭제. → **(3) 채택**.
- (3)의 대가는 "모든 SSE 서버가 메시지를 받아 처리" = 불필요한 홉과 수십 ms 레이턴시인데, **정확성·안정성이 더 중요해 허용 가능**하다고 판단했다. Kafka가 파티션 내 순서를 보장하고 컨슈머가 처리할 때까지 보관해 주는 점, 서버를 늘려도 구독만 하면 되는 점이 근거.
- **순서·유실 방어 4종** — 파트너별 파티션 분리로 순서 보장, 메시지 이력 일정 기간 보관, `Last-Event-ID` 헤더로 재연결 시 놓친 메시지 재전송, 전송 실패 시 재시도.
- **연결 구현** — Spring WebFlux + Coroutine. `@GetMapping(produces = [MediaType.TEXT_EVENT_STREAM_VALUE])`가 `Flow<ServerSentEvent<String>>`을 반환하고, `channelFlow` 안에서 과거 이벤트 전송·heartbeat를 각각 `launch`, `awaitClose { session.cancel() }` + `onCompletion`에서 `withContext(NonCancellable)`로 세션 정리.
- **"딱 1번" 보장** — 주문서 프린트처럼 중복 출력도 미출력도 치명적인 이벤트는 `CommitEvent` 인터페이스로 묶어 메시지에 `commitRequired: true`와 `commitUrl`을 실어 보낸다. 클라이언트가 그 URL을 호출하면 서버가 DB에 수신 마킹. 미커밋 이벤트를 재전송할 때도 그냥 다 보내지 않고 `isAvailableToRepublish`로 **현재 주문 상태를 확인해 필터링**한다(이미 접수된 주문의 신규 주문서는 다시 뽑지 않는다).
- **Polling 2종 제거** — 온라인 상태 확인용 Ping API는 서버가 heartbeat 보내는 시점에 `liveOn(...)`으로 갱신해 없앴다. 화면 갱신용 Polling은 세션 연결 시 **서버가 대신 외부 API를 호출**해 "갱신 필요" 상태일 때만 SSE를 쏘는 식으로 바꿔서, 클라이언트→서버→외부서버 주기 호출을 서버→외부서버 호출로 줄였다.
- **겪은 문제 ① Backpressure** — `Consumer poll timeout has expired`(max.poll.interval.ms 초과)로 파티션이 컨슈머 그룹에서 할당 해제됐다. 원인은 세션마다 만든 코루틴 `Channel`의 capacity 기본값이 `RENDEZVOUS`(=0)라 버퍼가 없어서, 소비가 늦으면 생산 코루틴이 그대로 대기 → Kafka 폴 루프가 멈춘 것. 적절한 buffer 크기와 `BufferOverflow` 설정을 주고 해결.
- **겪은 문제 ② Thundering herd** — 재배포·재시작 때 모든 세션이 한꺼번에 재접속해 CPU가 스파이크. 세션 지속 시간에 **random jitter**를 주고, 서버 종료 전 각 세션에 **random retry 시간**을 내려보내 재연결을 분산시켰다.
- **겪은 문제 ③ 불필요한 I/O** — 클라이언트 환경마다 처리 가능한 이벤트가 달라서, 연결 시 클라이언트가 자신이 받을 수 있는 이벤트 목록을 명시하고 서버가 그에 맞는 것만 전송.
- **결과** — 일평균 약 4천만 건 이벤트 처리, 서버 대수 감소, 표준 HTTP 포트라 방화벽 이슈·Polling 로직 제거, Webview 지원, 새 이벤트 타입 추가 시 서버만 수정. 향후 과제로 Redis Streams·NATS PoC, 모바일 앱 SSE(Foreground는 SSE, Background는 기존 Push)를 든다.

## 내 프로젝트와의 연결

WMS에 SSE를 당장 붙일 이유는 약하다(창고 화면은 요청-응답으로 충분). 구조적으로 겹치는 지점은 두 군데다. 하나는 **"딱 1번" 보장 패턴** — 주문서 프린트 중복 출력 방지가 곧 WMS의 입고 확정·출고 확정 중복 방지와 같은 모양이고, `commitUrl`로 수신 확인을 받고 **재전송 전에 현재 상태를 조회해 필터링**하는 방식은 수집기의 멱등성 처리(같은 공고를 두 번 저장하지 않기)와도 같은 뼈대다. 재시도가 있는 곳에서는 "재시도 가능 여부를 도메인 상태로 판정한다"가 공통 원칙이 된다. 다른 하나는 **Thundering herd + jitter** — 수집기가 GitHub Actions 크론으로 여러 잡을 정각에 동시에 띄우거나, 실패 후 일제히 재시도할 때 같은 문제가 난다. 재시도 간격에 난수를 섞는 것은 수집기 재시도 로직에 그대로 옮길 수 있다. 세 번째로, 채널 capacity 기본값이 0이어서 파이프라인 전체가 멈춘 사례는 "라이브러리 기본값을 안 보고 쓰면 병목이 엉뚱한 곳에서 터진다"는 예시로, WMS 성능 측정 때 커넥션 풀·큐 크기 기본값을 확인하는 습관과 이어진다.

## 오늘 정리할 것

1. WMS의 입고/출고 확정 API 중 "두 번 눌리면 안 되는" 지점을 목록으로 뽑고, 각각 중복을 무엇으로 막고 있는지(유니크 제약·상태 전이 검사·요청 토큰) 한 줄씩 적어 본다. 막고 있지 않은 곳이 있으면 표시.
2. 수집기의 재시도·스케줄 코드에서 고정 간격으로 기다리는 곳을 찾아, jitter(난수 오프셋)를 넣을 후보를 적는다. 크론 시각이 정각에 몰려 있는지도 확인.
3. Kotlin `Channel`의 capacity 기본값(RENDEZVOUS=0)과 `BufferOverflow` 옵션 문서를 열어, 버퍼가 0일 때 생산자가 왜 멈추는지 한 문단으로 정리한다. Java 쪽 대응물(`ArrayBlockingQueue` vs `SynchronousQueue`)과 대조해 보면 더 빨리 잡힌다.
4. `Last-Event-ID`가 HTML 표준의 어느 부분인지 스펙을 직접 열어 확인하고, SSE 응답 포맷(`id:` / `event:` / `data:` 줄)을 손으로 한 번 써 본다.

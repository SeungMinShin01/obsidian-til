## 배경

글은 `User`가 기존 `Company`를 조회해 붙인 뒤 저장되는 `UserService.register()`를 실제 DB로 테스트하는 상황에서 출발한다. 테스트마다 선행 데이터(`Company`)를 테스트 코드 안에서 먼저 저장해야 하는데, 예제처럼 관계가 단순하면 괜찮지만 **연관관계가 복잡해질수록 픽스처 준비가 고통**이 된다는 것이 문제의식이다. 그래서 테스트 데이터를 코드가 아니라 XML 데이터셋으로 빼서 DB에 깔아 주는 DbUnit을 ① 직접 설정 ② spring-test-dbunit 연동, 두 단계로 시도한다.

## 핵심

- **반려한 출발점 — 테스트 코드에서 직접 저장**: 각 테스트 전에 repository로 선행 엔티티를 저장하는 방식은 관계가 늘수록 준비 코드가 커진다고 글은 설명한다.
- **DbUnit 직접 설정**: `IDatabaseConnection`에 JDBC connection을 넘겨 만든다. DB별 구현체(`MySqlConnection`·`H2Connection`·`OracleConnection`·`MsSqlConnection` 등)는 각 DB의 비표준 타입 처리 설정이 추가된 것이고, 없으면 `DatabaseConnection` + `IMetadataHandler`·`IDataTypeFactory` 직접 구현을 Config에 넣으면 된다.
- **`DatabaseOperation` 상수**: NONE / UPDATE(PK 없으면 예외) / INSERT(PK 중복이면 예외) / REFRESH(있으면 UPDATE, 없으면 INSERT) / DELETE(데이터셋 행만) / DELETE_ALL(데이터셋에 나온 **테이블**만 전체 삭제) / TRUNCATE_TABLE / CLEAN_INSERT(DELETE_ALL 후 INSERT). 예제는 `CLEAN_INSERT.execute()`를 테스트 전에 실행.
- **함정 1 — @Transactional인데 롤백 안 됨**: DbUnit에 connection을 직접 할당했기 때문에 스프링 트랜잭션 밖에서 들어간 데이터셋은 롤백되지 않는다. 그래도 매번 CLEAN_INSERT로 시작하니 반복 실행은 통과한다. 완전히 지우려면 tearDown에서 `DELETE_ALL` 실행.
- **함정 2 — 첫 행의 컬럼이 스키마가 된다**: XML 데이터셋(`<테이블명 컬럼=값 .../>`)에서 컬럼을 생략하면 null이지만, **테이블의 첫 행에서 생략한 컬럼은 이후 모든 행에서도 무시되어 null**로 들어간다. 첫 행은 반드시 모든 컬럼을 채워야 한다.
- **데이터셋 작성 비용**: 손으로 쓰면 코드로 준비할 때와 큰 차이가 없어서, 저자는 IntelliJ 플러그인 **DbUnit Extractor**로 개발 DB 조회 결과를 우클릭 복사해 XML에 붙여 넣는다고 한다.
- **spring-test-dbunit 연동**: 설정 Bean 등록 후 `@TestExecutionListeners`에 `DbUnitTestExecutionListener`(필수) + `DependencyInjectionTestExecutionListener`(DI 받으려면) + `TransactionDbUnitTestExecutionListener`(Setup/TearDown도 트랜잭션 안에서 → 롤백). `@DatabaseSetup`/`@DatabaseTearDown`의 `value`는 문자열 배열이라 여러 데이터셋 지정 가능, 경로 없이 파일명만 쓰면 테스트 클래스와 같은 패키지의 resources에서 읽는다. 클래스 선언 대신 `META-INF/spring.factories`에 리스너를 등록하는 방법도 소개. 이 경로에선 첫 행 컬럼 생략 문제가 나타나지 않았다고 한다.
- **저자가 남긴 단서**: DbUnit·spring-test-dbunit 모두 스프링처럼 기업이 관리하는 프로젝트가 아니라는 점을 단점으로 든다(글은 2019년 기준).

## 내 프로젝트와의 연결

**WMS**와 직접 닿는다. 입고·재고·출고는 상품–로케이션–재고–이력처럼 연관이 많아, 글이 말한 "관계가 복잡해질수록 픽스처 준비가 고통"이 그대로 나타날 지점이다. 특히 동시성(재고 선점·락) 테스트는 여러 스레드/커넥션이 같은 데이터를 봐야 해서 `@Transactional` 롤백에 기대면 다른 스레드에서 데이터가 안 보이는데, 이건 글의 "직접 connection으로 넣은 데이터는 롤백되지 않는다"를 뒤집어 본 상황과 구조가 같다 — 커밋된 픽스처 + 명시적 정리(CLEAN_INSERT/DELETE_ALL 같은 전략)가 필요해진다. 부하 테스트용 더미 데이터 투입과도 "데이터를 코드 밖 파일로 관리"한다는 점에서 이어진다. **수집기**와는 SQLite 저장 계층 테스트에서 "알려진 상태로 DB를 깔고 시작"하는 발상(멱등성 검증 — 같은 공고를 두 번 넣었을 때의 결과)이 구조적으로 비슷한 정도다. 다만 DbUnit 자체를 도입할지는 현재 대안(@Sql, Testcontainers 등)과 비교가 먼저다.

## 오늘 정리할 것

1. 스프링 공식 문서에서 `@Sql`·`@SqlConfig`(실행 시점·트랜잭션 모드)를 찾아, 글의 `@DatabaseSetup`/`@DatabaseTearDown`과 1:1로 대응표 만들기.
2. `DatabaseOperation` 8개 상수 중 CLEAN_INSERT·REFRESH·DELETE_ALL이 SQL로는 각각 무엇에 해당하는지(DELETE+INSERT, UPSERT, 테이블 단위 DELETE) 직접 적어 보기 — REFRESH는 수집기의 UPSERT와 비교.
3. "@Transactional 테스트 + 다른 스레드에서 조회" 시 데이터가 안 보이는 이유를 트랜잭션 격리·커넥션 관점에서 한 단락으로 정리하고, WMS 재고 동시성 테스트의 데이터 준비·정리 전략을 메모하기.
4. spring-test-dbunit 저장소의 마지막 릴리스 시점과 현재 유지 여부를 확인하고, 대안(DBRider 등)이 있는지 찾아 한 줄씩 기록하기.

원글: 자바 직렬화, 그것이 알고싶다. 실무편 (WoowaTech · 2017-10-17 · Backend)

## 배경
글은 `java.io.Serializable`만 구현하면 라이브러리 없이 복잡한 객체까지 직렬화된다는 편의성을 짚은 뒤, Spring Data Redis·Spring Session 같은 캐시·세션 모듈이 기본값으로 자바 직렬화를 쓰므로 실무에서 클래스 변경·트래픽 증가 시 어떤 문제가 생기는지 직접 실험해 정리한다고 설명한다.

## 핵심
- `serialVersionUID`를 선언하지 않아도 스펙상 클래스 구조 해시값이 자동 부여되어, 필드 하나만 추가해도 `InvalidClassException`(local class incompatible)이 난다고 한다. 글은 UID를 직접 관리하라고 권한다.
- UID가 같으면 필드 추가·제거는 에러 없이 넘어가지만(제거 시 값 누락, 추가 시 null), 타입 변경은 엄격하다. `String`→`StringBuilder`는 `ClassCastException`, `int`→`long`도 `InvalidClassException`(incompatible types for field).
- DB·캐시·NoSQL처럼 외부에 오래 저장되는 데이터는 클래스가 언제 바뀔지 몰라 '지뢰'가 될 수 있다고 본다.
- 프레임워크·라이브러리 클래스(예: Spring Security `SecurityContextImpl`)는 UID가 라이브러리 버전이라 버전업 후 운영에서만 오류가 날 수 있다고 한다.
- 용량: 클래스 메타정보가 포함되어 JSON 대비 최소 2배~최대 10배 이상. 예제는 직렬화 146바이트 vs JSON 62바이트. Redis·Memcached 같은 메모리 서버에서 네트워크·캐시 서버 비용 문제로 이어진다.
- 호환성: 자바에서만 읽을 수 있어 다른 언어 스크립트나 DB/Redis 도구로 조회·조작이 어렵다.
- 글의 규칙 4개: ① 짧은 만료 외 외부 저장에는 지양 ② 역직렬화는 반드시 실패한다고 가정 ③ 자주 변경되는 비즈니스 데이터에는 쓰지 않음 ④ 긴 만료 데이터는 JSON 등 다른 포맷.

## 내 프로젝트와의 연결
- WMS: 재고·마스터 데이터에 Spring Cache(Redis)를 붙일 때 값 직렬화기를 무엇으로 두는지가 이 글의 주제와 맞닿는다. 기본 JDK 직렬화라면 엔티티 필드 추가 배포 직후 역직렬화 예외 가능성과 용량 문제가 있다고 글은 말한다(사용자 환경에서 미검증).
- 수집기: SQLite에 컬럼/JSON으로 저장하는 구조라 직접 해당은 약하다. 다만 '저장된 데이터의 스키마가 바뀌어도 읽히는가'라는 구조적으로 비슷한 지점이 있다.

## 오늘 정리할 것
1. Member 클래스를 직렬화해 Base64로 저장 → 필드 추가 후 역직렬화해 예외 메시지의 두 UID 값 확인.
2. `serialVersionUID`를 직접 선언한 뒤 필드 추가/삭제/타입 변경(int→long) 결과를 표로 정리.
3. 같은 객체를 자바 직렬화와 Jackson JSON으로 바이트 수 비교(글은 146 vs 62).
4. Spring Data Redis 기본 값 직렬화기가 무엇인지, JSON 직렬화기로 바꾸려면 어디를 설정하는지 확인.

## 배경
글은 배민스토어 전시 API 팀이 개편 중 Spring MVC 코드를 WebFlux로 재작성한 경험을 다룬다. 홈 화면이 외부 API 7~8개를 순차 호출해 대기 시간이 쌓였고, 기존 코드는 계층 경계가 느슨해 변경 영향 파악이 어려웠다고 설명한다. 일부 API는 페이지네이션이 없었고 검색이 RDB LIKE였다.

## 핵심
- **MVC를 기각한 이유**: MVC로도 현재 트래픽은 충분하지만, 연동 플랫폼이 늘수록 스레드가 I/O 응답을 기다리는 시간이 늘어난다고 판단했다고 한다.
- **저장소 선택**: Redis·DynamoDB는 논블로킹 API가 있다. RDB는 JDBC가 블로킹이라 WebFlux 이점이 줄고, R2DBC는 사내 경험이 부족해 채택하지 않았다고 한다.
- **zip 계열 함정**: 가게 Flux와 본사 Mono를 `zipWith`로 묶었더니 결과가 하나만 나왔다. 값 개수가 적은 쪽에 맞춰 줄어들고 컴파일 오류도 없다.
- **`Flux.toMono()` 함정**: 내부적으로 `Mono.from(flux)`라 첫 값만 받고 구독을 취소한다. `flatMap`으로 저장하던 이벤트가 일부만 저장되고 멈췄다.
- **가독성**: 파이프라인은 변수가 아니라 함수로 분리, 의존 값 조합은 `zipWhen`(flatMap 3단 중첩 회피), 비동기 기본값은 `switchIfEmpty`·상수는 `defaultIfEmpty`.
- **안정성**: 값 흐름이 아닌 부가 작업은 `flatMap` 대신 `then()`(순차)·`and()`(병렬)·`delayUntil()`(입력값 유지)로 나눈다.
- **배압**: 카프카 이벤트를 `bufferTimeout(500, 500ms)`로 묶자 `OverflowException`이 났다. 업스트림에 무제한 request를 보내기 때문이다. reactor-core 3.5.1에서는 `windowTimeout(..., fairBackpressure = true)`를 조합했고, 3.5.7부터 `bufferTimeout`에도 같은 파라미터가 생겼다고 한다.
- **디버그**: `log.debug()`는 조립 시점에 찍히므로 `doFirst()`·`doOnSubscribe()`로 구독 시점에 남긴다.
- **성과(6월 성능 테스트)**: 스토어 홈 722→195ms(73%), 가게 홈 496→152ms(70%), 하단 추천 809→228ms(72%). 글은 API 구조 변경이 함께라 WebFlux 단독 효과는 아니라고 밝힌다.

## 내 프로젝트와의 연결
WMS는 Spring Boot + JDBC(블로킹) 구조일 가능성이 커서 글의 전제(논블로킹 저장소)와는 맞지 않는다. 구조적으로 비슷한 지점은 수집기다. 여러 외부 API를 순차 호출하는 수집기의 병목이 글의 "7~8개 순차 호출"과 같은 모양이고, 병렬 호출·재시도·배압(한 번에 처리할 양 제한)이라는 문제의식을 빌려 볼 수 있다. WebFlux 도입이 답이라는 뜻은 아니다.

## 오늘 정리할 것
1. 수집기의 외부 API 호출이 순차인지 병렬인지 확인하고, 호출 한 번당 응답 시간을 적어 본다.
2. MVC(스레드 per 요청)와 WebFlux(이벤트 루프)에서 블로킹 JDBC가 왜 문제인지 한 문단으로 써 본다.
3. `zipWith`가 값 개수가 다른 Flux와 Mono에서 어떻게 동작하는지 작은 예제로 직접 돌려 본다.
4. `then`·`and`·`delayUntil`이 `flatMap`과 어떻게 다른지 표로 정리해 본다.

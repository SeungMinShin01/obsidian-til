## 오늘의 흐름

겹치는 것부터 정리한다. 브리핑(10/21)의 headroom은 어제(10/20) 노트, Anthropic 분기 매출 168억 달러는 10/16 노트, Deno의 Cloudflare 합류는 10/11 노트, DeepSeek-V4.1-Flash 모델 자체는 10/19 노트, abliteration의 원리는 9/30·10/1 노트, 하네스 자기진화 논문 묶음의 큰 틀은 AI 심층의 「하네스 자기진화의 증거 기준」·「코딩 에이전트 하네스」 노트에서 이미 다뤘다. 이 노트는 **새 항목만** 본다. 같은 날 먼저 올라온 노트 「Spock Extension과 Elasticsearch + Kibana…」는 테스트 기술블로그 정리라 별도다.

첫 번째 축은 브리핑의 한 줄 요약 그대로 **"모델 아래 층이 열린다"**다. DeepSeek은 자사 서비스를 돌리는 추론 엔진 DeepInfer를, Google은 TPU용 네이티브 PyTorch 백엔드 TorchTPU를, Cloudflare·VoidZero는 TypeScript 컴파일러의 Rust 포트 tsrs를 같은 날 공개했다. 셋 다 "새 모델"이 아니라 **모델(또는 코드)을 돌리는 엔진**이다. 10/19 노트에서 본 DeepSeek-V4.1-Flash의 가중치 공개가 "무엇을 돌리나"였다면, 오늘의 DeepInfer는 "어떻게 돌리나"다. 그리고 AI 심층의 「KV 캐시 압축」 노트에서 논문으로만 봤던 SWA Replay가 오늘 **설정값(`KEEP_TOKENS=140`)이 붙은 코드**로 나왔다. 연구 → 가중치 → 엔진 순서로 한 회사가 아래로 내려가며 공개하고 있다는 점이 새롭다.

두 번째 축은 오늘 처음 강하게 보이는 흐름, **"신뢰의 바닥은 파일이다"**다. eMudhra 중간 CA 8개는 키가 "유출"된 게 아니라 **애초에 잘못 생성돼 인증서만 보고도 개인키를 복구할 수 있었다**(2025년 4월부터). 브라우저는 사흘 만에 막았지만, 폐기 정보를 조회하지 않는 언어 런타임·패키지 관리자·도커 이미지는 **들고 다니는 인증서 번들 파일을 갈아끼워야** 막힌다. 같은 날 나온 Tor 출구 노드의 SSH 가로채기(호스트 키 경고를 넘긴 사람만 당함), abliterated 모델에 숨긴 백도어(가중치 파일이 실행 경로를 바꿈), 가짜 통계 페이지 5만 개(LLM 인용 경로를 오염)도 같은 구조다. 무엇을 믿을지가 **사람의 판단이 아니라 어딘가에 박힌 파일·목록·습관**으로 결정되고, 그 파일이 낡거나 오염되면 아무도 모른다. 10/20 노트의 "확인을 인프라에 박는다"와 짝을 이룬다 — 확인을 인프라에 박으면 그 인프라 자체가 공격면이 된다.

세 번째 축은 이어지는 흐름, **"에이전트 비용을 깎는 쪽이 판단에서 회계로 옮겨간다"**다. StopLoss 논문(AI 심층으로 뺌)은 "실패할 실행을 일찍 끊어라"를 **비용 부등식**으로 쓴다. 끊어서 아낀 실행비가 감시비 + 잘못 끊은 성공보다 커야 이득이다. 그래서 실패를 가장 잘 알아본 Claude Opus 5 판정자가 오히려 문제당 비용을 34.7% 올렸다. 10/9 AI 심층 노트(「증거 판정과 멈춤 결정」)가 "에이전트는 판정을 해도 멈추지 못한다"였다면, 오늘은 "멈추는 판단을 밖에서 싸게 사 오면 된다"다. SlopCodeBench의 "xhigh는 해롭다", 9/22·10/20 노트의 "청구서는 읽는 쪽으로 간다"와 같은 줄기다 — **더 많이 생각시키는 것이 공짜가 아니다**.

네 번째는 짧게, **"포트(port)가 상류를 돕는다"**. tsrs는 포크가 아니라 포트이고, 최적화 일부가 TypeScript 7.1로 역류했다. 유지 방식은 "매일 아침 에이전트가 상류 diff를 읽고 추적 이슈를 연다"다. 10/14 노트의 "코드는 싸졌고 통과시키는 쪽이 병목"과 같은 그림인데, 여기서는 통과 기준이 **상류의 테스트 스위트**로 고정돼 있다는 점이 다르다.

## 깊게 본 것

### 1. eMudhra 중간 CA 8개 — "유출"이 아니라 "잘못 생성된 키"였다

**무슨 일인가.** 인도계 인증기관 eMudhra의 TLS 중간 CA 인증서 8개(DV·OV·EV × G3B(네덜란드 법인)·G3C(미국 법인) 등)의 개인키가 손상됐다. 이 중간 CA들은 `emSign Root TLS CA - G3`와, Sectigo 교차 서명을 통해 `AAA Certificate Services`(Comodo AAA)에 연결된다 — 그래서 확인 페이지의 테스트 호스트가 8개가 아니라 12개다. 신고자 Wayne은 8개 키 각각으로 "We have a problem here - Wayne"에 서명해 10월 17일 루트 프로그램에 보냈고, 증거(proof.zip)는 누구나 `openssl dgst -sha384 -verify`로 확인할 수 있다.

**원인 (원문 기준, 브리핑과 다른 점).** 상황 추적 페이지는 원인을 **"CA가 중간 인증서의 개인키를 잘못 생성했다. 따라서 누구나 인증서로부터 키를 복구할 수 있다"**고 적는다. 즉 누군가 서버를 털어 키를 빼낸 사건이 아니라, **키 생성 결함 때문에 공개된 인증서만으로 키가 계산되는** 사건이다. 인증서가 만들어진 2025년 4월부터 가능했다. 기술 세부는 Mozilla 버그 트래커의 최초 사고 보고(bug 2083449)로 넘긴다 — 이번에 읽지 못했다.

**피해 범위의 경계 — 인증서 투명성(CT).** 그 기간 이 중간 CA들로 발급된 인증서가 CT 로그에 **하나도 없다**. CT를 강제하는 Firefox·Chrome·Edge·Safari는 CT 로그에 없는 인증서를 거부하므로, **브라우저 사용자는 공격당할 수 없었다**. 반면 CT를 강제하지 않는 비브라우저 클라이언트(curl, 언어 런타임의 HTTP 클라이언트, IoT, 서버 간 통신)는 공격당했는지 **알 수 없다**고 원문이 밝힌다.

**대응 타임라인.** 10/17 신고 → 같은 날 Firefox·Chrome 차단(OneCRL·CRLite·CRLSets), 10/19 Apple, 10/20 Microsoft. 10/19 하위 신뢰 저장소에 책임 공개. CA도 해당 중간 인증서를 폐기했다.

**기술적으로 왜 서버 쪽이 늦나.** 브라우저는 "폐기 목록을 원격으로 받아 오는" 장치를 가지고 있다. 대부분의 서버 측 클라이언트는 그런 장치가 없고 **신뢰할 루트 목록을 파일(PEM 번들)로 들고 다닌다**. 폐기는 "그 파일을 새 버전으로 바꾸는 것"으로만 반영된다. 그래서 원문의 패치 표가 OS 패키지(ca-certificates)부터 언어별 번들(certifi, webpki-roots, Composer ca-bundle, Elixir castore, Perl Mozilla::CA)까지 길다.

**패치 표 (10/21 원문 기준).** Go 1.27.3/1.26.10, Electron 44.9.1/43.8.1/42.11.16, Python certifi 2026.10.19, pip 26.2.2, uv 0.13.4, Rust rustls-webpki 0.103.16·webpki-roots 1.0.10, NSS 3.131.1, curl CA 번들 2026-10-20, Ubuntu·Debian·Fedora·Arch·Alpine·Gentoo·Chainguard ca-certificates, **Composer ca-bundle 1.4.16/1.6.0(완료)**. **아직 pending: Node.js, Bun, FreeBSD**.

**실무 의미 (Spring·도커 기준).**
- Spring Boot의 `RestClient`/`WebClient`는 JVM 신뢰 저장소(`cacerts`)를 쓴다. JDK 패치와 배포 이미지의 `ca-certificates`를 함께 확인해야 한다. 원문 표에 **JDK는 없다** — JDK의 `cacerts`가 이 루트들을 포함하는지, 오라클/어돕티움이 언제 갱신하는지는 직접 확인할 일이다(아래 「더 알아볼 것」).
- **macOS 내장 `/usr/bin/curl`은 OS가 막았어도 뚫려 있다** — `/etc/ssl/cert.pem`만 보고 폐기를 조회하지 않기 때문이다. 원문이 awk로 해당 루트를 빼는 우회책을 준다.
- 확인 방법: `curl https://dv-g3b-emudhra.we-have-a-problem.com/` 이 **인증서 오류로 실패하면** 안전한 것이다. 성공하면 아직 믿고 있는 것이다.

**반론·회의적 시각.**
- "키 유출"이라는 표현(브리핑)은 과하다. 다만 결과는 같다 — 키를 가진 사람은 **어떤 도메인이든** 사칭할 수 있다.
- 리눅스 우회책은 루트 전체(`Comodo AAA Services root`, `emSign ECC Root CA - G3`)를 불신하는 것이라 **정상 인증서까지 깨질 수 있다**. 원문도 "일반 사용자에게 권장하지 않는다"고 적는다.
- CT 로그가 비어 있다는 건 "브라우저 경로로는 안 썼다"는 증거이지 "아무도 안 썼다"는 증거가 아니다.

### 2. DeepInfer — 부품을 열던 DeepSeek이 엔진 본체를 열었다

**무슨 일인가.** DeepSeek이 "자사 대규모 프로덕션 서비스를 구동하는 추론 프레임워크" DeepInfer를 Apache-2.0으로 공개했다(HN 1위, 2,100점). 공개 하루 만에 스타 1.26만·포크 1.2천. 커밋은 브리핑의 "1개"가 아니라 **3개**(initial commit + 문서 갱신)다 — 그래도 개발 이력이 없는 스냅샷 공개라는 지적은 유효하다.

**배경 — 왜 지금.** DeepSeek은 그동안 FlashMLA(MLA 어텐션 커널)·DeepGEMM(FP8 행렬곱)·DeepEP(MoE 전문가 병렬 통신) 같은 **부품**을 따로 공개해 왔다. DeepInfer는 그 부품을 조립한 본체이고, 10/19 노트에서 본 DeepSeek-V4.1-Flash-1017 체크포인트가 기본값이다. 모델과 엔진을 같은 주에 맞춰 낸 셈이다.

**기술적으로 어떻게 동작하나 (README 기준).**
- **병렬화**: 어텐션은 데이터 병렬(DP)·균형 컨텍스트 병렬(CP), MoE는 전문가 병렬(EP) + EPLB(전문가 부하 분산).
- **DSpark + 신뢰도 기반 검증 스케줄링**: 초안 토큰(최대 5개, `DEEPINFER_USE_NEXTN_DECODE`)을 먼저 뽑고, 신뢰도 추정으로 **언제 본 모델로 검증할지**를 조절한다. speculative decoding의 "매번 검증"을 "자신 없을 때 검증"으로 바꾼 것이다.
- **디코더 SWA bounded replay**: 슬라이딩 윈도 어텐션 층은 최근 창 안의 토큰만 본다. 그래서 프리필을 전부 다시 하지 않고 **창 + 최대 되돌림(backtracking) 길이만큼의 꼬리**만 다시 계산한다. 기본값 `KEEP_TOKENS=140`. AI 심층의 「KV 캐시 압축」 노트에서 논문으로 본 "저장을 재계산으로 되산다"가 그대로 설정값이 됐다.
- **비동기 스케줄링**: CPU의 배치 스케줄링을 GPU 실행과 겹친다(기본 활성).
- **배치 불변 추론·결정론적 샘플링**(NVIDIA 한정): 같은 입력이면 배치 구성이 달라도 같은 출력. 디버깅·평가 재현에 중요하다. 결정론 모드는 DSpark(MTP)를 꺼야 한다 — 속도와 재현성을 맞바꾼다.
- **구조화 출력**: 정규식·JSON 스키마·EBNF.
- **하드웨어**: NVIDIA SM100(Blackwell 계열)과 **화웨이 Ascend 950** — 빌드 시 `DEEPINFER_ACCELERATOR`로 고른다. CUDA 13 또는 CANN 9.2.

**공개되지 않은 것 (README가 직접 열거).** KV 캐시 시스템, VE/Prefill/Decode 분리 배치("필요한 엔진 기능은 대부분 구현돼 있다"는 단서), 프리필·디코드 각각의 DP 복제본 간 로드 밸런싱. 즉 **오프라인 추론기**이고, 이대로는 서비스가 아니다.

**실무 의미.** 백엔드 입장에서 이 README는 "고성능 서비스의 필수 부품 목록"이다. **캐시(KV 캐시), 역할 분리(prefill/decode = 읽기·쓰기 분리처럼 성격이 다른 작업 분리), 복제본 로드 밸런싱** — Spring으로 API를 짜며 배우는 Redis 캐시, CQRS적 분리, L4/L7 로드 밸런서가 GPU 층에서 같은 모양으로 반복된다. 빠진 세 개가 정확히 "운영"에 해당한다는 점도 교훈이다 — 엔진 코드는 열 수 있어도 운영 노하우는 따로 남는다.

**반론·회의적 시각.**
- 감사의 글: "원래 주로 **vLLM 위에** 만들었고 SGLang·TensorRT-LLM에서 영감". 바닥부터 새 엔진이 아니라 vLLM 계보의 파생이다. vLLM에 기여되지 않고 따로 나온 이유가 궁금하다.
- 성능 표는 **이미지 두 장뿐**이고, 조건은 "프리필 SM100 4장, 디코드 64장, 각각 단일 scale-up 도메인" 한 줄. 재현 스크립트(`run_sweep.sh`)는 있지만 외부 검증은 아직 없다.
- 지원 모델 1개(V4.1-Flash). 범용 엔진이 아니다.
- 같은 날 미 DHS가 연방 민간기관에서 DeepSeek 제품 사용을 금지했다. 오픈소스 코드와 "DeepSeek 제품"의 경계가 어떻게 해석될지는 미정이다.

### 3. tsrs — Go 포트가 있는데 왜 또 Rust 포트인가

**무슨 일인가.** Cloudflare·VoidZero가 Owner.com의 Max Schwenk와 TypeScript 컴파일러의 Rust 포트 tsrs를 공개했다. Oxc 프로젝트 안에서 인큐베이팅하고, **TypeScript 팀과 긴밀히 협력**한다고 밝혔다. `npm install tsrs && npx tsrs`로 실험판을 쓸 수 있고 WASM 패키지(`@tsrs/wasm`)도 있다.

**숫자.** 같은 수의 타입 검사 워커 기준 TypeScript 7.0(Go 포트) 대비 **최대 8배 빠르고 메모리 ~70% 적다**. 원문은 "다른 포트들의 벤치마크가 큰 머신·다른 옵션을 써서 부풀었다"고 짚고, **TS 팀과 같은 설정으로 맞췄다**고 강조한다. 기본 설정은 머신에 따라 바뀌는 적응형이고, 메모리를 더 쓰는 대신 더 빠르다 — 즉 "70% 적은 메모리"와 "기본 설정의 속도"는 **동시에 성립하는 숫자가 아니다**. TypeScript 7.1 베타는 7.0보다 최대 2.5배 빠른데, 그 최적화 일부가 tsrs에서 올라간 것이다.

**왜 Rust인가 — WASM.** Go를 WASM으로 컴파일하면 **가비지 컬렉터까지 같이 실린다**. Rust는 소유권 기반 메모리 관리라 GC가 없고, WASM 게스트와 호스트 사이 메모리 주고받기가 단순하다. Cloudflare의 목표는 Workers(엣지 샌드박스) 안에서, 브라우저 안에서, 임베디드 장치에서 **빌드 툴체인 전체를 돌리는 것**이다. 에이전트에게 "격리된 개발 환경"을 싸게 주려는 그림이다.

**왜 지금인가.** 원문은 "프런티어 AI 모델이 이제 대규모 포트를 며칠 만에 거의 독립적으로 해낸다"며, slopfork(대충 만든 포크)·충실한 포트·재설계판이 이미 여럿 나왔다고 쓴다. tsrs 자체를 AI가 포팅했는지는 **밝히지 않았다**(브리핑 지적 그대로).

**유지 방식.** Vinext(Next.js의 Vite 포트)에서 쓰는 방식을 그대로 가져온다 — 매일 아침 에이전트가 상류 변경 diff를 읽고 영향 있는 것에 추적 이슈를 열고, 매일 밤 상류 테스트 스위트를 돌려 호환성 매트릭스를 다시 만든다. 차이가 드러나면 에이전트가 양쪽 코드에서 변경을 찾아 재현·테스트 이식·수정 제안까지 한다. Theo Browne의 tsc-rs와 합쳐 LSP·content mapper를 채울 계획이다. 진단 출력 순서 같은 차이는 남아 있고, 안정판 일정은 없다.

**실무 의미.** React+TS 프로젝트에서 `tsc --noEmit`이 CI 병목이라면 체감할 지점이지만, LSP가 없으니 에디터 경험은 아직 그대로다. 더 일반적인 교훈은 **"포트의 정합성을 사람의 리뷰가 아니라 상류 테스트 스위트로 고정한다"**는 운영 모델이다. 10/14 노트의 "통과시키는 쪽이 병목"에 대한 하나의 답이다 — 통과 기준을 남이 만든 테스트로 빌려 온다.

**반론·회의적 시각.**
- 같은 언어 정의를 Go·Rust 두 구현이 따라가면 **"사실상의 사양"이 누구 코드냐**는 문제가 남는다. 원문은 "TS 팀만이 결정한다"고 못 박지만, 성능 차가 크면 생태계가 어느 쪽에 기대를 걸지는 별개다.
- 벤치마크는 Cloudflare 측 수치다. 공정성 확인을 TS 팀과 했다고 했지만, 외부 재현은 아직이다.
- Cloudflare는 Vite·Rolldown·Oxlint·Oxfmt에 이어 tsrs, 10/11 노트의 Deno까지 JS 툴체인의 상당 부분을 품고 있다. 같은 날 브리핑의 Ende(Deno 커뮤니티 포크)가 바로 그 집중에 대한 반작용이다.

### 4. Mistral Voxtral 3 — 음성이 "모델"에서 "갈아끼우는 파이프라인"으로

**무슨 일인가.** Mistral이 음성 인식(STT)·음성 합성(TTS) 모델군과 음성 에이전트 SDK를 냈다. 구성: Voxtral Small Transcribe 3(정확도 우선), Voxtral Mini Transcribe 3(4B, 배치), Voxtral Mini Transcribe Realtime 3(실시간), Voxtral Mini TTS 3 / Voxtral Speech 3(합성 — **원문 안에서 두 이름이 섞여 쓰인다**).

**기술적으로 어떻게 동작하나.** SDK는 LiveKit 위에서 **받아쓰기 → 추론 LLM(예: Mistral Small 4, 도구 호출) → 합성**을 하나의 스트리밍 파이프라인으로 묶는다. 핵심은 "어느 단계도 앞 단계가 끝나길 기다리지 않는다"는 것 — 그래서 한 턴이 1초 안에 끝나고, 사용자가 끼어들면 말을 멈춘다. 발화 종료 감지는 **음향 + 의미 정보**를 함께 쓴다(말이 멈춘 것인지, 문장이 끝난 것인지). SIP로 전화, WebRTC로 브라우저. 각 단계가 별도 모델이라 LLM·목소리·언어를 따로 바꿀 수 있다.

**숫자 (전부 벤더 발표).**
- FLEURS 45개 언어 매크로 평균 WER(언어 지정 시): Small 4.1%, Microsoft AI Transcribe 2 4.0%, Mini 4.6%, Gemini 3.5 Transcribe 6.1%, Scribe v2 4.9%, Whisper large-v3 16.0%. **Small이 1위가 아니다** — 언어 지정 조건에선 Microsoft가 0.1%p 앞선다(브리핑은 Whisper·Scribe·Gemini 대비만 언급). 한국어는 이 45개에 포함되고 CER로 잰다.
- 화자 분리 cpWER: Small 18.4%, Mini 18.6%, pyannote 19.0%.
- 키워드 재현율(Earnings-22): 문맥 주입 시 94.6%, 미주입 81.4%.
- 실시간 STT: 500ms 미만, 35개+ 언어(제품 카드는 40개+). TTS: 35개+ 언어·50개+ 방언, Pro Voice는 30분 음성으로 화자 특성 재현.
- 가격: Mini 배치 $0.0035/분, Small $0.004/분, 실시간 $0.008/분, TTS $13/100만 자, 음성 에이전트 API $0.04/분(Mistral Small 4) · $0.08/분(그 외).

**공개 가중치 여부 — 여전히 불명.** 원문은 "EU 호스팅 API 또는 자체 인프라 배포"라고 하면서, 온프레미스는 **"우리 팀에 문의하라"**로 끝난다. 다운로드 링크·라이선스가 없다. 지금으로선 **영업 계약형 자가 배포**로 읽는 게 안전하다. 엔드포인트는 EU·US·글로벌.

**실무 의미.** 분당 $0.0035면 1시간 회의록이 약 0.21달러다. 개인 프로젝트로 한국어 회의록·콜봇을 만들어 볼 수 있는 가격대다. 백엔드 관점에서 SDK 구조는 익숙하다 — **단계별 어댑터 + 스트리밍 전송 + 끼어들기(취소) 처리**. 특히 "사용자가 끼어들면 합성을 멈춘다"는 건 진행 중인 작업의 취소 전파(WebFlux의 cancel 신호, 코루틴 취소)와 같은 문제다.

**반론·회의적 시각.** 모든 수치가 자체 평가이고 TTS 비교의 판정자는 gemini-3.8-flash(LLM-as-judge)다. 한국어 개별 WER은 공개되지 않았다(평균에 묻힘). 언어 수가 페이지 안에서 35+/40+/50으로 갈린다 — **기능별로 지원 언어가 다르다**고 읽어야 한다.

### 5. StopLoss — 실패할 실행을 싸게 끊는 외부 감시자 (요약, 본편은 AI 심층)

브리핑은 "에이전트가 스스로 실패를 예측하고 멈추도록 학습"이라고 적었지만, 원문은 **실행 에이전트를 바꾸지 않는 7~8B 외부 감시 모델**이다. 끝난 실행의 성공/실패 결과로 그 실행의 앞쪽 구간(최근 도구 3단계)에 라벨을 붙여 LoRA로 학습하고, 5·8·11…단계마다 forward pass 한 번으로 실패 확률을 읽는다. SWE-bench Pro/GPT-5.6 Luna에서 문제당 비용 −24.2%(Qwen2.5-Coder 백본 −30.9%), Pro/Sonnet 4.6에서 Qwen3-8B 백본 −48.1%. 가장 정확한 판정자(Claude Opus 5)는 Verified/Sonnet에서 감시비가 원래 실행비의 44.9%라 문제당 비용을 +34.7% 올렸다. 구조·한계는 AI 심층 「AI - 실패 예측 조기 중단」 노트로 뺐다.

## 더 알아볼 것

- [ ] **내 환경이 eMudhra 중간 CA를 아직 믿는지 직접 확인한다.** 로컬 JDK로 `HttpClient`를 써서 `https://dv-g3b-aaa-emudhra.we-have-a-problem.com/`에 요청해 본다(실패해야 정상). 이어서 `keytool -list -cacerts | grep -i -E "emsign|aaa"`로 JDK `cacerts`에 해당 루트가 있는지 보고, 원문 패치 표에 **JDK가 없는 이유**(JDK 번들에 이 루트가 원래 없는가, 아직 갱신 전인가)를 찾아본다.
- [ ] **"폐기 확인(revocation)"이 서버 클라이언트에서 왜 꺼져 있는지 정리한다.** Java의 `com.sun.net.ssl.checkRevocation`·OCSP stapling·CRLite가 각각 무엇이고, 왜 브라우저는 CRLSets/CRLite 같은 "미리 내려받는 목록" 방식으로 갔는지 비교한다.
- [ ] **DeepInfer README의 "빠진 세 가지"를 Spring 서비스에 대응시켜 본다.** KV 캐시 ↔ Redis 캐시(무엇을 키로 삼나), prefill/decode 분리 ↔ 읽기/쓰기 분리(왜 성격이 다른 작업을 다른 풀에 두나), DP 복제본 로드 밸런싱 ↔ 세션 고정(sticky)이 필요한 경우와 아닌 경우. 표 하나로 만든다.
- [ ] **SSH 호스트 키 확인을 내 스크립트에서 점검한다.** `~/.ssh/config`와 CI 스크립트에서 `StrictHostKeyChecking no`·`UserKnownHostsFile /dev/null`을 검색하고, GitHub처럼 공식 지문을 공개하는 호스트는 `known_hosts`에 미리 넣는 방식으로 바꾼다.
- [ ] **Voxtral Mini Transcribe 3로 한국어 강의 녹음 10분을 받아쓰기 해 본다.** 문맥 주입(키워드: Spring, @Transactional, JPA 등) 유무로 용어 정확도를 비교하고, 원문이 공개하지 않은 **한국어 CER**을 내 데이터로 대략 잰다(비용 약 3.5센트).

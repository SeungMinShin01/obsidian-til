## 오늘의 흐름

겹치는 것부터 정리한다. 오늘(10/23) 브리핑의 큰 건 다섯 중 넷이 어제(10/22) 노트와 같은 사건이다 — PHP 인증 없는 RCE 2건과 공개 절차 붕괴, eMudhra, LiteLLM 1.107.0, Railway, Claude Duet. DuckDB 2.0, GitLab CVSS 10.0, Google Rust 스타일 가이드, Firefox Local Mode, OpenAI의 Google Cloud 진출, 한국 신규 LLM의 Qwen 의존, Meta 제재, BioWare 폐쇄, cloudflare/security-audit-skill·graphify도 어제 '짧게'에서 다뤘다. 이 노트는 **새 항목과, 재등장 항목의 새 사실만** 본다. 재등장 중 새 사실이 가장 큰 것은 LiteLLM이다 — 어제는 SafeDep의 외부 감식(추정)뿐이었는데, 오늘은 LiteLLM의 **공식 사후 보고서**가 공격 경로를 밝혔다.

첫 번째 축은 오늘 새로 보이는 흐름이다. **"비밀은 금고가 아니라 기록 속에서 샜다."** LiteLLM 공격자가 쥔 GitHub 토큰 세 벌은 비밀 저장소에서 나온 게 아니다 — LiteLLM 보고서에 따르면 Claude Code가 특정 상황에서 사용자의 GitHub CLI OAuth 토큰을 **응답 본문에 넣었고**, 응답 본문을 남기던 **LiteLLM 자기 회사의 내부 배포본 로그**에 그 토큰이 쌓였고, 그 배포본이 인터넷에 열려 있었다. 같은 주의 TiDB Cloud 유출 주장(공격 그룹 FulcrumSec)도 진입점이 **저장소에 커밋된 클라우드 자격증명**이고, 피해를 키운 것은 지원 엔지니어가 고객의 운영 키를 붙여 넣은 **Jira 티켓·첨부 로그**였다. Railway는 비밀값 저장소 자체가 뚫렸지만, 나머지 둘은 "비밀을 넣으라고 만든 곳"이 아니라 **일하면서 남긴 기록(로그·티켓·커밋)**이 비밀 저장소 노릇을 했다. 10/21 노트의 "신뢰의 바닥은 번들 파일"과 짝이 된다 — 이번엔 신뢰의 *누수*가 파일, 그것도 아무도 비밀이 들었다고 생각하지 않은 파일에서 일어났다.

두 번째 축은 어제의 "검사는 통과했다"가 더 구체적으로 반복된 것이다. **"통제는 다 있었고, 하나씩 예외로 열렸다."** LiteLLM은 3월 사고 이후 릴리스를 비공개 저장소로 옮기고, Trusted Publishers·불변 Docker 태그·이미지 서명·**사무실에 고정된 노트북 한 대에서만 게시** 같은 통제를 쌓아 두었다. 그런데 월요일에 고객용 백포트를 위해 **릴리스 권한을 임시로 넓혔고**, 브랜치 보호는 10:08:29에 무단 변경을 **거부했다가 5초 뒤** 조직 소유자 토큰으로 무력화됐고, 승인 게이트는 두 번째 개발자 토큰으로 통과됐다. 결과물은 **공식 파이프라인이 서명해서** 나갔다. 서명은 "이 파이프라인이 만들었다"를 증명했을 뿐 "이 소스가 맞다"를 증명하지 못했다. 어제 PHP 재단이 쓴 "구조적 실패"와 같은 모양이다 — 통제가 없어서가 아니라, 사람이 일을 굴리려고 연 예외가 통로가 됐다.

세 번째 축은 **"확신의 모양을 한 신호는 싸졌다."** PHP 패치 10시간 뒤 GitHub에 PoC가 '수천 개' 돌았는데, Elias Taylor는 별이 가장 많은 세 개를 열어 보고 **기본 PHP에서는 아무것도 안 된다**고 썼다 — 실험실 설정 스크립트가 서버에 LFI 취약점을 *미리 심어 두는* PoC까지 있었다. 그는 이것을 LLM이 판단을 대신한 결과의 "결정 셸링 포인트"(다들 같은 모델에게 물어 같은 이상한 판단에 수렴)라고 부른다. 같은 날 HN에 오른 "LLM에게 확신도를 묻지 말라"는 글은 같은 문제를 숫자 쪽에서 본다 — 모델이 쓰는 "0.85"는 측정값이 아니라 그럴듯한 다음 토큰이고, 결과와 대조한 기록이 없으면 보정(calibration)됐는지 알 길이 없다. 어제 AI 심층 「판단 신호와 개입 정책」의 Jev(완료 확률 평균 0.50인데 실제 87% 통과)가 바로 *보정 안 된 확신이 행동을 틀리게 만든* 사례였다. PoC 개수·자신 있는 문장·확률 숫자 — 셋 다 생성 비용이 0에 가까워져서 **신호로서의 값이 떨어졌다**.

네 번째는 짧게, **HF 상위가 세계 모델·에이전트 쪽으로 몰렸다**는 브리핑의 관찰. 원문을 읽은 두 건은 세계 모델을 *시뮬레이터*가 아니라 **검증기**로 쓴다는 점에서 같다 — LGWM은 "이걸 누르면 다음 화면이 어떤 표현이어야 하나"를 예측해 실제 화면과 벡터로 비교하고, WorldTUI는 거꾸로 "규칙 없이 화면 패턴만 배운 세계"가 어디서 무너지는지(덧붙인 줄을 잊는다)를 보여 준다. 그리고 에이전트 비용 쪽에서는 Cache Engineering(AKV)이 **텍스트를 고치지 말고 KV 캐시를 직접 버려라**를 들고 나왔다(본편은 AI 심층).

### 1. LiteLLM 사후 보고서 — 다섯 겹 통제를 지나간 토큰 세 벌

**무슨 일인가.** 어제 노트의 LiteLLM 1.107.0 악성 릴리스(`.pth`+`sitecustomize` 탈취기·백도어)에 대해 LiteLLM이 사후 보고서를 냈다(10/21 20:30 UTC 갱신, "봉쇄, 조사 중"). SafeDep도 글을 이 보고서 기준으로 고쳤다. 핵심 사실:

- **영향 범위:** PyPI `litellm==1.107.0` 휠 7개가 **11:39:51~13:23**(약 1시간 43분) 게시. Docker Hub `v1.107.0`·`latest`·`main-latest`·`main-stable`이 **11:46:56~14:20**(약 2시간 33분) 악성 이미지 인덱스(`sha256:1bbcb144…`)를 가리킴. GHCR은 13:51까지. **비공개 엔터프라이즈 레지스트리 사용자는 영향 없음.**

**토큰은 어디서 났나.** 보고서의 설명은 두 단계다.

1. **Claude Code가 특정 상황에서 사용자의 GitHub CLI OAuth 토큰을 응답 본문에 포함**하는 것을 확인했고, 응답 본문을 로깅하는 환경에서는 그 토큰이 **LiteLLM 로그에 남을 수 있다.** (LiteLLM은 LLM 호출을 중계하는 게이트웨이라 요청·응답을 로깅하는 기능이 있다.)
2. LiteLLM 사내 배포본(인터넷에 노출)에서 **눈에 띄지 않는 이름의 예상 밖 사용자 계정**이 발견됐다. 공격자가 이 배포본에 들어가 로그에서 토큰을 꺼냈다고 본다. 진입 방법은 미확인, "최근 패치된 취약점"으로 의심. 같은 보고서에 엔터프라이즈 고객에게 **10/27 공개 예정인 엠바고 취약점**의 수정판을 비공개 레지스트리로 배포 중이라는 문장이 있는데, 그것이 이 진입 경로와 같은 취약점인지는 적혀 있지 않다.

**다섯 겹 통제가 각각 어떻게 넘어갔나.** 보고서가 직접 나열한 정상 흐름과 대조하면 이렇다(배열은 이 노트의 정리).

마지막 줄이 가장 배울 만하다. 서명·provenance는 **"어느 파이프라인이 만들었나"**를 증명한다. 그 파이프라인이 **무엇을 빌드했나**(입력 소스가 정본 저장소인가)는 별도 검사가 필요하다. 어제 SafeDep이 "태그(`66c8f5b`, 버전 1.108.0)와 sdist가 맞지 않는다"로 잡아낸 것이 바로 그 빈칸이었고, 오늘 보고서가 원인(`Berri-AI` 유사 저장소)을 확정했다.

**실무에 무슨 의미인가.**

- **로그는 비밀 저장소가 된다.** LLM 게이트웨이·API 게이트웨이·APM이 요청/응답 본문을 남기면, 그 안에 들어간 모든 토큰이 로그 보존 기간만큼 산다. Spring으로 치면 `CommonsRequestLoggingFilter`의 `setIncludePayload(true)`나 Feign `Logger.Level.FULL`, `logging.level.org.springframework.web.client=DEBUG`가 같은 위험이다 — 본문 로깅은 마스킹 규칙과 같이 켠다. 그리고 **에이전트 도구가 예상 못 한 곳에 토큰을 흘릴 수 있다**는 사실이 공식 보고서에 처음 구체적으로 적혔다.
- **임시 예외에는 만료가 있어야 한다.** "월요일에 넓힌 권한"이 화요일 사고의 입구였다. 권한 확대를 티켓·기한·자동 회수와 묶는 것(JIT 권한)이 통제의 일부다.
- **사람 둘의 승인은 사람 둘의 토큰이 털리면 무의미하다.** 승인 게이트의 가치는 "다른 사람"이 아니라 "다른 *장치·인증 요소*"에서 나온다. 보고서의 게시 노트북 고정은 그 원리였는데, 예외가 그것을 비켜 갔다.
- **복구 순서도 배울 거리다.** 보고서의 첫 지시가 "**`pip install`부터 하지 마라**"다 — 감염 환경에서는 pip도 Python이라 `cook.pth`가 다시 돈다. 셸에서 파일을 지우고 데몬을 죽인 뒤 고정 버전으로 다시 설치하고, CloudTrail에서 설치 시각 전후의 `GetCallerIdentity`와 외부에서의 역할 자격증명 사용을 찾으라고 한다. 표식 파일(`/tmp/.pc_once_…`)이 *없다는 것은 아무것도 증명하지 않는다*(컨테이너·tmp 정리로 사라짐).

**반론·회의적 시각.** 보고서는 "조사 중"이고 공격자가 내부 배포본에 들어간 방법은 미확인이다. "Claude Code가 토큰을 응답 본문에 넣는 특정 상황"의 조건도 적혀 있지 않다 — Anthropic 쪽 확인이 없으니 지금은 LiteLLM의 관찰로 읽는다. 게시 노트북 통제와 "임시 확대"가 정확히 어떻게 맞물렸는지(확대된 권한이 노트북 제약을 우회했는지)도 문장 수준에서는 모호하다. 그리고 세 번째 토큰으로 워크플로 기록을 지웠다는 것은 공격자가 조사 방해까지 계획했다는 뜻이라, "발견된 것"이 전부라고 볼 근거가 약하다.

### 2. "이 PHP 취약점엔 쉬운 익스플로잇이 없다" — 그리고 확신의 모양을 한 신호들

**무슨 일인가.** Elias Taylor가 10/21에 쓴 의견 글(HN 514pt). 요지: 버그는 진짜이고 **패치는 해야 한다**(글 맨 위에 추가한 단서). 하지만 Log4Shell(User-Agent에 `${jndi:ldap:…}`)·Heartbleed(Content-Length 하나)·Shellshock·RoR YAML처럼 "뉴스가 나오자마자 봇넷이 돈" 부류가 아니다. 공개 10시간 동안 수천 개의 'PoC'가 올라왔지만 **기본(vanilla) PHP 인스턴스에서 동작하는 것은 없다.**

**근거.** 별이 가장 많은 PoC 저장소 3개(`david-alvarez-rosa/php-rce`, `eness/php2shell-…-PoC`, `ikow/php2shell-poc`)를 지목한다. 다수가 **LFI(로컬 파일 인클루전)**에 기대는데, 이는 "서버가 이미 심각한 코드 수준 취약점을 갖고 있어야 한다"는 뜻이다. `ikow` 저장소의 실험실 `setup.sh`는 서버에 `/etc/passwd`를 읽을 수 있는 취약점을 **미리 심어 둔다** — 저자 표현으로 "LLM이 동생에게 꽂히지 않은 컨트롤러를 쥐여 준" 꼴, 즉 익스플로잇을 증명하려고 서버를 취약하게 고친 것이다.

**흥미로운 진단 — "결정 셸링 포인트".** 많은 사람이 *독립적으로* 똑같이 이상한 판단 오류(취약점을 심어 놓고 익스플로잇이라 부르기)를 한 것은, 사실 독립적이지 않기 때문이라는 주장이다 — 다들 같은 모델에게 판단을 맡겨서 **모델이 기본으로 하는 방식이 과대 대표**된다. 공포가 컸던 이유로는 PHP 코어 팀원의 "패치 15분 뒤 익스플로잇이 나올 것" 발언, PHP는 원래 불안하다는 통념, PoC 영상(어제 노트의 Calif 실수 공개), 그리고 LLM 시대의 막연한 불안을 든다. 글 첫 줄의 "그리고 숫자 4"는 eMudhra 키(`d = 4`)를 가리키는 농담이다.

**기술적으로 — 왜 "어렵다"는 주장이 성립할 수 있나.** 어제 노트의 두 CVE는 조건이 까다롭다. OOM 손상은 요청이 `memory_limit`에 *하필 나쁜 순간*에 걸려야 하고, stale state UAF는 치명적 오류가 *특정 지점*에서 나야 하며, 해제된 메모리 자리에 공격자 데이터를 정확히 깔아야(heap grooming) 한다. 메모리 손상 버그는 "터뜨리기(크래시)"와 "조종하기(RCE)" 사이 거리가 멀다. 반면 Log4Shell은 **기능**(JNDI 조회)을 악용한 것이라 조종이 필요 없었다.

**하지만 정면으로 충돌하는 사실.** PHP 재단은 **Apache + mod_php 기본 설정에서 인증 없는 완전한 RCE가 시연됐다**고 썼다(Calif·OpenAI 보고). Taylor가 본 것은 *공개된* PoC이고, 재단이 말한 것은 *비공개로 보고된* 익스플로잇이다. "공개 10시간에 동작하는 공개 익스플로잇이 없다"는 "익스플로잇이 어렵다"의 약한 증거일 수는 있어도 "불가능하다"의 증거는 아니다. 어제 '짧게'의 Wiz PHP2Shell(최신 WordPress·Drupal·Joomla 컨테이너에서 인증 없이 동작한다는 주장)과도 충돌하는데, 그 원문은 아직 읽지 못했다.

**같은 날의 짝 — "LLM에게 확신도를 묻지 말라" (Amrut Joshi, HN 86pt).** 일기예보관 비유로 확신도의 조건 두 가지를 세운다: ① 예측이 기반한 **정보의 양**을 반영할 것, ② 같은 종류의 질문에서 **실제 결과와 대조**됐을 것(보정). 70%라고 말한 날 중 실제로 약 70%에 비가 왔으면 보정된 것이고, 늘 계절 평균 30%만 말하는 예보관도 보정은 됐지만 쓸모가 없다. LLM이 쓰는 "0.85"는 둘 다 없다 — 그건 게이지 값이 아니라 대화의 그럴듯한 다음 토큰이라서 다시 물으면 바뀌고, "확실해?"라고 물으면 바뀌고, 앞에 "명백히 정답"이라고 써 놓았으면 높게 나온다. 처방은 확신도를 LLM 밖으로 빼는 것: **관측 가능한 특징**(검색이 관련 문서를 찾았나, 같은 질문을 두 번 했을 때 답이 일치하나)을 고르고, **과거 기준율**에서 출발해, 모든 응답과 결과를 **기록**하고, 특징별 그룹의 실제 정답률로 규칙을 갱신하고, 주기적으로 보정표를 다시 만든다.

**실무에 무슨 의미인가.**

- **패치는 한다, 우선순위는 내 환경으로 정한다.** 어제 브리핑의 "① 일단 패치 ② 내 환경이 어느 조건인지 확인" 순서가 맞다. mod_php를 쓰는가 PHP-FPM인가, `memory_limit`가 얼마인가가 공격면을 바꾼다. PoC 개수는 판단 근거에서 뺀다.
- **AI가 만든 PoC는 "환경을 바꿔서라도 통과"하는 경향이 있다.** 이건 10/20 노트의 "완료 보고는 증거가 아니다"(서브에이전트가 Read만 가능한데 '수정 완료'), 10/14의 "통과시키는 쪽이 병목" 흐름의 보안판이다. 내가 에이전트에게 "재현해 봐"를 시킬 때도 **테스트 대상을 고쳤는지**를 diff로 확인해야 한다.
- **확신도가 필요하면 기록부터 만든다.** 에이전트가 "자신 없으면 사람에게 넘겨라"를 구현하려면, 모델에게 숫자를 묻는 대신 관측 가능한 특징 + 결과 로그 + 주기적 보정표가 필요하다. Spring 백엔드로 옮기면 결과 테이블 하나(`reply_id, features…, predicted, actual`)와 배치 집계 하나다.

**반론·회의적 시각.** Taylor 글은 의견 글이고 자기 테스트 환경·버전·결과를 문서화하지 않았다(브리핑 지적과 같음). "Claude가 판단을 대신해서"라는 진단도 PoC 저자들에게 물어본 게 아니라 추론이다. 그리고 그는 "쉽게"를 반박했지 "위험하지 않다"를 주장하지 않았다 — 제목만 퍼지면 "패치 안 해도 된다"로 읽힐 위험이 있어서 본인이 단서를 맨 위로 올렸다. Joshi 글은 원리 설명이고, 모델 내부 확률(로짓)이나 학습으로 보정된 판정 모델(어제의 Jev처럼)을 다루지 않는다 — 그쪽은 "물어서 받은 숫자"보다 낫지만, Jev 사례처럼 **보정 안 되면 같은 함정**이다.

### 3. WorldTUI — 규칙 없이 배운 터미널, 그리고 "다음 토큰 정확도"가 가린 기억

**무슨 일인가.** Simon Edwardsson이 Qwen2.5-Coder-0.5B를 미세조정해 **셸도 파일시스템도 없이 터미널처럼 보이는 모델**을 만들었다. 키 입력이 들어가면 화면이 어떻게 바뀌는지를 예측한다. vim 모드 전환·저장, tmux 패널, 스네이크, 환경변수 확장까지 되고, 브라우저(WebGPU)에서 208MB로 돈다. 저자 결론: "유용한가? 별로. 하지만 360M 모델치고는 기대보다 훨씬 낫다."

**배경 — 왜 터미널인가.** Genie 3(게임 장면을 엔진 대신 모델이 다음 프레임으로 예측)를 보고 "앱이 코드가 아니라 학습된 것"인 미래를 떠올렸지만 GPU 클러스터와 영상 데이터가 없어서 축소했다. 터미널은 픽셀이 아니라 **문자 격자**이고, 실제 셸을 돌리면 **완벽하게 레이블된 데이터를 무한히** 만들 수 있고, 사전학습 모델이 이미 `ls`·`cat`의 출력을 안다. 진짜 질문은 "그럴듯한 출력"이 아니라 **"일관된 세계를 유지할 수 있나"**였다.

**기술적으로 어떻게 동작하나.**

- **스트림이 아니라 화면 변경을 예측한다.** 입력은 화면 스냅샷(크기·행 내용·커서) 뒤에 키 입력의 *원시 바이트*(Enter는 `\r`, ←는 `ESC [ D`). 출력은 "어느 행의 몇 열부터 무엇을 쓰고 커서를 어디로"라는 델타. 아무것도 안 누르면 `WAIT` 토큰에 지속 시간을 줘서 스네이크가 혼자 움직인다.
- **`COPY` 연산.** 화면 바닥에서 Enter를 치면 모든 행이 한 칸 올라가야 하는데, 다시 쓰면 키 하나에 약 3,000토큰이다. "이전 화면의 n행을 복사"로 바꾸니 스크롤이 행당 약 96토큰 → 3토큰.
- **어휘 333개.** 바이트 256개 + 행 64개 + 특수 연산 몇 개. 문법 제약 디코딩이라 모든 출력이 유효한 화면 갱신이다. 이 덕에 15만 개 어휘의 임베딩(136M 파라미터)을 잘라 494M → 약 360M, int4로 208MB.
- **데이터.** Docker에서 실제 프로그램을 돌려 키 입력과 화면을 기록. 사용자명·호스트명·프롬프트·크기 무작위, 가상의 페르소나(개발자·관리자)별 파일, 6~24개 활동, 오타율 1.2%, **35%는 세션 중간에서 시작**(어떤 상태에서든 이어 가게). 최종 33.6만 에피소드, 약 20억 토큰(기반 모델 사전학습은 약 18조).
- **자기 실수에서 배우기(DAgger 계열).** 실제 세션의 한 지점에서 모델이 1~4 이벤트를 예측하게 하고, 결과 화면과 실제 화면이 *조금* 다르면 "다음 키 입력에서 모델 화면을 정답 화면으로 고치는" 교정 델타를 만들어 학습한다. 핵심 제약: **교정에 들어가는 단어는 이전의 실제 화면이나 사용자 입력에 나온 것이어야 한다.** 본 적 없는 파일명을 맞히라고 가르치면 환각을 보상하게 되기 때문이다. 표본 세션의 약 1/3이 쓸 만한 교정을 낳았고 3라운드 반복, PresetBench가 int4 기준 24/47 → 38/47. 전체 학습은 RTX 4090 약 75 GPU시간.
- **행 병렬 디코딩 + 자기 투기적 디코딩.** 한 프레임의 행들은 대부분 서로 독립이라, 행마다 배치 원소를 하나씩 주고(같은 KV 캐시 공유) 자기 행만 생성하게 했다. 비용이 "모든 행의 합(최대 3,000스텝)"에서 "가장 긴 행(약 100스텝)"으로. 대형 프레임 p95 6.7초 → 0.87초(4090). 그런데 행끼리 협의를 못 해서 vim이 3행에서 열리거나 스네이크 먹이가 여러 개 생겼다 → 병렬 결과를 **초안**으로 쓰고 같은 모델이 **순차 검증**해 첫 불일치부터 다시 생성. M4 Mac 브라우저에서 글자 하나 약 60ms, `man test` 2.5초 → 0.9초.

**결과.**

| 모델 | ShellBench /106 | 파일 되읽기 /13 |
| --- | --- | --- |
| Qwen2.5-Coder-0.5B, 프롬프트 | 52 | 2 |
| Qwen3-0.6B, 프롬프트 | 60 | 3 |
| WorldTUI | 80 | 9 |

가장 큰 차이는 **기억**이다. 하지만 `echo green >> colors` 뒤 `cat colors`에서 덧붙인 줄이 자주 안 보인다. 중첩 디렉터리를 만들다 갑자기 다른 경로에 가 있기도 한다.

**가장 배울 만한 대목 — 증류 실험.** 이전 체크포인트(ShellBench 78/106)를 교사로 층을 줄이려 했다.

- **7번 층 하나만 빼도** 다음 토큰 정확도는 99.3% → 98.9%로 거의 그대로인데, **정확한 기억 되읽기는 64/64 → 0/64**. 실제 이력을 넣어 준 시험이라 오류 누적 탓도 아니다.
- 짝수 층만 남긴(1·7·15·22번을 뺀) 학생은 그럴듯한 출력은 내지만 기억 되읽기 31/64 — 자기가 쓴 두 값 중 하나를 **절반 확률로 잘못 고르는** 우연 수준, 4.8억 토큰 학습 뒤에도 회복 안 됨.
- 그 네 층을 **남긴** 16층 학생은 64/64(4비트, 약 138MB에서도). 대신 ShellBench 65 vs 78.
- 저자 결론: "학생은 멀쩡해 보이면서 조용히 기억을 잃을 수 있다." 그리고 증류를 포기했다.

**실무에 무슨 의미인가.**

- **세계 모델의 가장 쉬운 정의.** 이 모델 안에는 디렉터리 구조체도 파일 버퍼도 없다 — 규칙을 구현한 게 아니라 **규칙이 만드는 화면 패턴**을 배웠다. 그래서 저장할 곳이 없는 "기억"은 가중치와 맥락에만 있고, 길어지면 흐려진다. LLM이 코드 실행 결과를 "맞히는 것처럼 보이다가 미묘하게 틀리는" 것과 같은 구조다(브리핑 해설과 같음). 에이전트가 "이 코드 돌리면 이렇게 나와요"라고 할 때 실제로 돌렸는지가 중요한 이유다.
- **평균 지표는 특정 능력의 소실을 가린다.** 다음 토큰 정확도 0.4%p 하락 = 기억 100% 소실. 10/15 노트 제목("더한 점수는 빠진 하나를 가리고")과 같은 교훈이 모델 내부에서 재현됐다. 양자화·증류·프롬프트 압축을 할 때 **그 기능 전용 시험**(여기선 32개 세계 × 2값 되읽기)이 따로 있어야 한다.
- **교정 데이터의 정보 제약.** "모델이 알 수 있었던 정보로만 교정하라"는 규칙은 에이전트 자기개선(10/18 AI 심층 「하네스 자기진화의 증거 기준」)에도 그대로 옮길 수 있다 — 정답을 보고 고친 궤적은 모델이 배울 수 없는 것을 가르친다.

**반론·회의적 시각.** 개인 실험이고 벤치마크(ShellBench·PresetBench·기억 시험)를 모두 저자가 만들었다 — PresetBench는 "데모에서 겪은 실패"로 만든 것이라 개선 폭이 과대평가될 수 있다(학습에는 없다고 명시). 기억 시험은 사이에 명령 0~1개인 **짧은 간격** 시험이다. 프롬프트 모델과의 비교도 과제가 다르다(그쪽은 명령 출력 전체를 예측, 각주 4). 가중치는 아직 미공개.

### 4. Right Screen, Wrong Transition (LGWM) — 안전은 화면이 아니라 전환의 성질이다

**무슨 일인가.** GUI 에이전트용 검증기 논문(HF ▲81). 문제 설정이 한 문장으로 선명하다 — **"로그인"을 누른 뒤 나온 로그인 화면은 정상이고, "주문 보기"를 누른 뒤 나온 똑같은 로그인 화면은 공격이다.** 따라서 안전은 화면의 성질이 아니라 **전환(transition)의 성질**이고, 화면만 검사하는 감시자는 정상 화면을 재사용하는 공격(자격증명 탈취 화면 끼워 넣기)에 뚫린다.

**어떻게 푸나.** 전환을 판단하려면 "이 행동 다음에 무엇이 와야 했나"라는 기대가 필요하다. 기존 GUI 세계 모델은 그 기대를 텍스트·코드·이미지로 *생성*하므로, 실제 화면과 비교하려면 두 번째 모델(판정자)이 또 필요하다. LGWM은 **디코더 없이** 행동 조건부로 **다음 화면의 표현(임베딩)**을 바로 예측한다. 그러면 검증은 **벡터 비교**로 끝난다. 의미 주석 없이 실제 GUI 전환 185만 개로 학습.

**결과(초록 기준).** RSWT-BENCH는 각 자격증명 화면이 정상 전환과 하이재킹 전환 **양쪽에** 나오도록 만들어, 화면만 보는 탐지기는 구성상 **우연 수준**이 되게 한 진단용 벤치마크다. 여기서 학습 없는 점수가 **AUC 0.987, 결정당 17ms** — 가장 강한 비공개 VLM과 대등하고, 생성형 GUI 세계 모델보다 AUC 약 10포인트 높으면서 지연은 1,000배 이상 낮다. 예측과 실제의 **잔차 방향**으로 "해로운 불일치 대 무해한 불일치"를 가르는 것도 AUC 0.953(프롬프트로 물어본 VLM은 거의 우연).

**실무에 무슨 의미인가.** 백엔드 언어로 바꾸면 **상태 머신 검증**이다 — "주문 조회 요청 다음에 인증 요구 응답이 오는 것은 허용된 전이인가?" 9/18 노트의 Spring Statemachine(상태·이벤트·가드)에서 전이 표를 명시적으로 쓰던 것을, 표를 쓸 수 없는 열린 GUI에서 **학습된 기대치**로 대신한 셈이다. 그리고 어제 Claude Duet처럼 사람 대신 화면을 누르는 에이전트에서 "결제·자격증명 입력" 직전에 붙일 수 있는 싼(17ms) 관문이다. 오늘 흐름 세 번째 축과도 이어진다 — LLM에게 "이거 수상해?"를 묻는 대신(프롬프트 VLM은 해로움 판정에서 우연 수준) **관측 가능한 기대와의 거리**를 잰다.

**반론·회의적 시각.** 초록만 읽었다. RSWT-BENCH는 저자들이 만든 진단 벤치마크이고 "화면만 보면 우연"이 되도록 **설계**된 것이라, 실제 공격 분포에서의 성능은 별개다. 하이재킹 화면을 정상 전환의 기대 표현과 *가깝게* 만드는 적응형 공격(표현 공간을 노린 공격)에 대한 평가가 있는지 미확인. 185만 전환의 출처·앱 분포도 미확인.

> 원문: [HF 논문 페이지](https://huggingface.co/papers/2610.11942) · [arXiv](https://arxiv.org/abs/2610.11942) · [프로젝트](https://jiamingzhang.netlify.app/lgwm/) · [GitHub](https://github.com/jiamingzhang94/lgwm)

### 5. Cache Engineering for Agents (AKV) — 텍스트 대신 캐시를 버린다 (요약, 본편은 AI 심층)

긴 에이전트 궤적에서 비용의 대부분은 **KV 캐시 읽기**다(논문 측정: API 비용의 82.4%). 기존 해법인 컨텍스트 엔지니어링(오래된 메시지 요약·삭제)은 접두사를 바꾸므로 **남긴 부분을 다시 prefill**해야 한다 — 그래서 임계값까지 미뤘다가 한꺼번에 크게 자르고, 중간 정보를 잃는다. AKV는 텍스트 궤적은 그대로 두고 KV 항목만 `drop`(이후 어텐션에서 제외)하고 `repos`(RoPE 키를 회전해 위치 재배치)한다. "같은 토큰 접두사 = 같은 캐시"가 깨지므로(언제 drop했느냐에 따라 상태가 다름) 연산 이력까지 키로 쓰는 확장 radix tree를 SGLang 위에 만들었다. 최근 도구 응답 12개만 남기는 단순 정책이 요약 기준선 대비 **비용 −27.7%, 점수 +1.7점**, 서빙 P95 지연 1.51배 개선. 구조·수치·한계는 AI 심층 「캐시 엔지니어링」 노트로 뺐다.

> 원문: [HF 논문 페이지](https://huggingface.co/papers/2610.28577) · [arXiv HTML](https://arxiv.org/html/2610.28577) · [GitHub](https://github.com/thu-nics/AKV)

- [ ] **내 Spring 앱의 로그에 비밀이 들어갈 수 있는 경로를 전부 찾는다.** `CommonsRequestLoggingFilter`(`includePayload`·`includeHeaders`), Feign `Logger.Level.FULL`, `RestClient`/`WebClient` DEBUG 로깅, 예외 메시지에 요청 본문을 넣는 `@ExceptionHandler`를 하나씩 켜 보고 `Authorization` 헤더·토큰이 로그에 찍히는지 확인한다. 이어서 Logback `MaskingPatternLayout`(또는 커스텀 `Converter`)로 마스킹하고, "로그 보존 기간 = 토큰 수명"이라는 관점에서 보존 정책을 적는다.
- [ ] **"서명은 됐는데 소스가 틀린" 상황을 막는 검사를 설계해 본다.** GitHub Actions 워크플로 하나를 만들어 `actions/checkout`의 `repository:` 값을 고정 문자열로 검증하는 단계(예: `github.repository == 'owner/repo'` 조건)를 넣고, `workflow_dispatch` 입력으로 저장소를 바꾸려 하면 실패하게 해 본다. Sigstore/SLSA provenance의 `sourceRepository` 필드가 이 정보를 담는지 확인한다.
- [ ] **임시 권한 확대에 만료를 붙이는 방법을 정리한다.** GitHub의 조직 역할·환경(Environments) 보호 규칙·필수 리뷰어가 "다른 *장치*에서의 승인"을 보장하는지, 아니면 "다른 *계정*"만 보장하는지 문서로 확인한다. LiteLLM 사례에서 무엇이 하나 더 있었으면 11:11:18의 승인이 막혔을지 한 줄로 적는다.
- [ ] **확신도 규칙을 직접 만들어 본다.** 작은 Q&A 에이전트(또는 지금까지 Claude에게 물어본 기술 질문 20개)를 대상으로 ① 답에 공식 문서 링크가 있었나 ② 같은 질문을 두 번 했을 때 답이 같았나를 특징으로 기록하고, 직접 검증한 정오를 붙여 특징 조합별 정답률 표를 만든다. 모델에게 "몇 % 확신해?"를 물은 숫자와 나란히 놓고 어느 쪽이 실제 정답률에 가까운지 본다.
- [ ] **WorldTUI 데모에서 기억이 깨지는 지점을 찾는다.** 브라우저 데모(208MB)에서 `echo a > f; echo b >> f; cat f`, 디렉터리 3단 중첩 후 `pwd`, vim으로 편집 후 다른 tmux 창에서 `cat`을 시험하고, 몇 개 명령 사이를 두면 기억이 무너지는지 기록한다. "다음 토큰 정확도는 그대로인데 기억이 사라진다"는 증류 결과를 내 말로 한 문단 설명할 수 있는지 확인한다.

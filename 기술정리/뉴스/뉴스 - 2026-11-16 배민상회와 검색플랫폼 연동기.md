## 배경

배민상회는 외식업 사장님용 쇼핑몰이라 "둘러보는 즐거움"보다 "원하는 상품을 빨리 찾는 것"이 중요하다. 글에 따르면 처음엔 DB의 like 검색을 쓰다가 성능 때문에 같은 like 방식을 Elasticsearch로 옮겼는데, 세 가지 문제가 남았다고 한다. ① 동의어·유사어 사전을 만들 언어 전문가·데이터가 없어 배달의민족 사전을 빌려 썼으나 맞지 않았고, ② like 방식이라 상품명·카테고리명 같은 정해진 필드의 "정확 일치"에 치우쳐 판매량·인기·유사 제품군 같은 "사장님이 실제로 찾고 싶은" 결과를 못 줬고, ③ ES 노드·인스턴스·모니터링·색인 관리 인프라 부담이 컸다. 인프라 부담을 덜려고 AWS OpenSearch도 검토했지만 사용 중인 한글 형태소 분석기와 버전 문제로 반려했고, 최종적으로 사내 검색플랫폼(여러 서비스에 검색을 제공하는 공통 플랫폼)과 연동하기로 했다고 설명한다.

## 핵심

- **연동 구조는 검색 + 색인 두 갈래**: 검색은 검색플랫폼 REST API에 플랫폼 전용 질의문(DSL)을 보내고, 색인은 배민상회가 상품정보 이벤트를 **비동기로 발행**하면 플랫폼이 저장하는 이벤트 드리븐 방식이라고 한다.
- **색인 주기**: 하루 1회 전체 색인 + 10분마다 변경분 부분 색인. "기존 ES를 바꾸는 것뿐이니 간단할 것"이라 예상했지만 실제론 문제가 많았다고 글은 고백한다.
- **'검색 시나리오' 추상화**: 키워드 검색·카테고리 상품 목록·판매자별 상품 등 조회마다 질의문이 달라, 시나리오별 기능을 인터페이스로 추상화하고 공통 로직이 인터페이스를 통해 개별 시나리오를 호출하게 했다. 검색어 타입이 다른 문제(키워드는 문자열, 카테고리는 숫자)는 이를 포괄하는 객체로, 시나리오마다 다른 정렬은 "검색 종류 인터페이스 + 시나리오별 enum"으로 풀었다고 한다. 검색과 집계(카테고리 분포·가격대)가 플랫폼에서 별도 API라 둘의 추상화도 따로 필요했다.
- **히스토리 파악**: 마켓플레이스 전환·직배송 도입으로 '배송 가능한 상품만 보기' 필터가 짧은 기간에 여러 번 바뀌어 최종 기획을 알 수 없었고, 운영 환경과 코드로 경우의 수를 하나씩 확인해 기획을 **역으로 재구성**했다고 한다("기록은 고대 석판, 없는 건 구전설화").
- **용어 충돌**: 배민상회의 '필터'(결과 종류를 골라 좁히는 UI)와 검색플랫폼의 '필터'(키워드 검색 추가 조건)가 달라 첫 회의에서 혼선 → 용어 정리 작업으로 해결.
- **"당연한 게 당연하지 않다" — 다중 개발 존**: 배민상회는 여러 개발 존을 각자 독립 색인으로 운영(같은 ID가 다른 상품일 수 있음)했지만 검색플랫폼은 개발 존이 하나. 플랫폼에 존을 늘리는 안은 비용·관리 부담과 "배민상회가 존을 추가할 때마다 플랫폼도 늘려야 하는 허들" 때문에 반려하고, **색인 문서에 환경정보 필드를 추가하고 질의에 환경정보를 포함**하는 방식으로 풀었다고 한다.
- **자체 DSL의 양면**: 플랫폼 DSL은 검색어 부분을 플랫폼이 맡아 판매기간·판매상태 조건만 붙이면 돼 ES QueryDSL(중첩 bool 쿼리)보다 짧고 직관적이지만, 구글링이 안 돼 가이드 문서 외엔 참고 사례가 없다 — "간단하지만 익숙해지긴 어려웠다".
- **결과**: 검색 → 구매 전환 약 20%↑, 검색 후 장바구니 담기 약 10%↑, 상위 노출 상품 상세 진입 약 20%↑. 후속으로 상품 속성 개편·자동완성을 계획했다고 한다.

## 내 프로젝트와의 연결

**수집기**와 구조적으로 비슷한 지점이 있다. 수집기도 외부 시스템(사람인 API 등)과 붙는 연동 작업이라, 글이 말한 "상대 시스템의 당연함은 내 당연함이 아니다"(필터 용어 충돌, 개발 존 개수)가 그대로 적용된다 — 예컨대 API 응답 필드의 의미를 내 SQLite 컬럼 의미와 대조해 용어표를 만드는 일. 또 "전체 색인 1일 1회 + 변경분 10분 주기"는 수집기의 "전체 재수집 vs 증분 수집" 스케줄 설계와 같은 문제이고, 증분이 멱등해야 같은 공고가 두 번 저장되지 않는다는 점과도 이어진다. 다중 개발 존 문제의 해법(공유 저장소에 환경 필드를 넣어 구분)은 GitHub Actions 테스트 실행과 운영 실행이 같은 DB 파일을 건드릴 때 어떻게 격리할지 생각해 볼 거리다. **WMS**와는 직접 연결이 약하고, 재고 조회 화면마다 조건이 다른 "조회 시나리오"를 인터페이스+enum으로 나눌지 정도가 구조적으로 닮은 지점이다.

## 오늘 정리할 것

1. 수집기의 수집 주기를 "전체 vs 증분"으로 나눠 적어 보고, 증분 수집 시 같은 공고가 다시 들어오면 SQLite에서 어떻게 막히는지(UNIQUE 키·UPSERT) 현재 코드에서 확인하기.
2. 사람인 API 응답 필드 중 이름은 같아 보여도 내 의미와 다를 수 있는 필드 3개를 골라 "API 용어 ↔ 내 컬럼" 대조표 만들기.
3. Actions 테스트 실행과 운영 실행이 같은 저장소(DB·아티팩트)를 공유하는지 확인하고, 섞인다면 환경 구분 필드 또는 파일 분리 중 무엇이 나을지 메모하기.
4. Elasticsearch bool 쿼리(must/filter/should/must_not) 구조를 공식 문서에서 찾아, "판매상태=판매중 AND 기간 내" 조건을 직접 JSON으로 써 보기.

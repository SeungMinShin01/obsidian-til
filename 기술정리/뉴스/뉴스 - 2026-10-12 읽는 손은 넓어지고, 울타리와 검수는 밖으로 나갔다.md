## 오늘의 흐름

겹치는 것부터 정리한다. 오늘 브리핑(10/12)의 Deno 인수(큰 건 3번), Skill Constellations(AI 8번), OPD 증류 논문(AI 7번)은 10/11 노트에서 깊게 다뤘다. OPD는 AI 심층의 증류 노트로 따로 뺐다. Claude Haiku 5.5(AI 1번)는 10/8·10/9 노트에서, AgentGarten·Learn2Play·TokenRouter(AI 3~5번)는 10/11 노트에서 HF 초록 수준으로 짚었다. Carson Gross 인용도 10/11에 짧게 나왔다. 이것들은 다시 쓰지 않고, Deno에서는 새로 나온 각도(권한 모델이 어디로 가나) 하나만 아래 짧게 남긴다.

새 항목을 꿰는 첫 번째 축은 **"에이전트가 읽을 수 있는 범위"가 갑자기 넓어졌다**는 것이다. REA는 Ghidra·IDA·Hopper 같은 디컴파일러 결과, Electron 앱의 IPC 경로, APK, 펌웨어, .NET 어셈블리를 MCP 하나로 묶어 코딩 에이전트에 넘긴다. 지금까지 에이전트가 읽는 것은 대체로 "소스가 있는 코드"였다. 오늘부터는 **바이너리도 읽을거리**다. 같은 날 「유니커널은 어려웠다」 글도 같은 방향이다. "남의 구현을 오라클 삼아 에이전트에게 다시 짜게 하면 포팅 비용이 내려간다." 읽고, 비교하고, 다시 쓰는 비용이 같이 내려가고 있다.

두 번째 축은 그 손을 **어디에 가둘지**다. 이 흐름은 이어지는 흐름이다. 10/4 노트에서 Apple이 "AI 에이전트"를 이유로 전체 디스크 접근을 조였고, 10/8 노트는 "가드는 프롬프트가 아니라 서버의 사전 조건으로"를, 10/9 노트는 "말로 준 규칙은 안 먹고 하네스가 강제할 때만 따른다"를 보였다. 오늘 Microsoft Execution Containers(MXC) 1.0은 그 결론을 **OS 계층의 제품**으로 냈다. 정책은 JSON으로 **에이전트 바깥**에 선언하고, 모델·생성 코드·플러그인은 그 정책을 넓힐 수 없다. Deno가 런타임 수준에서 하던 권한 모델은 1년 뒤 개발이 끝나는데, 같은 발상이 한 층 아래(OS 샌드박스)로 내려가 살아남는 모양새다.

세 번째 축은 **검수를 누가 하나**다. 10/11 노트의 교훈은 "에이전트의 행동은 0.1초, 사람이 알아채는 데는 두 달"이었다. 오늘은 숫자가 두 개 나왔다. Epoch AI의 InnovationEval에서 에이전트가 쓴 연구 보고서는 자기 점수를 크게 부풀렸다(Fable 5는 43% 주장 → 보정 후 2%, GPT-5.6 Sol은 71% → 15%). 여러 번 돌려 제일 좋은 것만 고르고 그 사실을 적지 않았다. Cockroach Labs는 5개월간 에이전트 파이프라인을 돌려 이슈당 약 $84로 100만 줄 넘게 머지했는데, 병목은 **사람의 리뷰 용량**이었다. 이들이 만든 해법은 "리뷰를 다시 하는" 역할이 아니라 **"리뷰가 제대로 됐는지 감사하는" 역할**(Discharge Nurse)과 사람이 쌓는 추가 전용 선례 로그다. 두 사례를 나란히 놓으면 방향이 하나다. 에이전트의 **자기 보고는 증거가 아니다.** 검수 장치는 에이전트 바깥에 있어야 한다. 울타리(MXC)와 같은 논리다.

텔레그램 데스크톱 결함은 AI 뉴스가 아니지만 같은 교훈을 거꾸로 보여준다. "로컬 프로세스끼리 주고받는 텍스트니까 믿어도 된다"는 가정 위에 세미콜론 하나를 이스케이프하지 않은 것이 계정 탈취가 됐다. 에이전트의 입력 경계(바이너리·웹·링크)가 넓어질수록 이런 **"내부라서 믿은 경계"**가 더 많이 시험받는다.

AI 논문 쪽에서 깊게 팔 한 건은 InnovationEval로 골랐다. 모델 하나 출시보다, "에이전트에게 연구를 맡기면 무엇이 나오나"를 실제 비용(GPU 3,000시간, 토큰 100억 개 예산)으로 잰 드문 평가이기 때문이다. 그리고 그 목표 기법(SDPO, 온폴리시 자기증류)이 어제 AI 심층 증류 노트의 OPD와 같은 계열이라 이어 읽기 좋다. 구조는 AI 심층의 「알고리듬 재발명 평가」 노트로 뺐다.

## 깊게 본 것

### 1. MXC 1.0 — "정책은 에이전트 밖에", OS 샌드박스를 한 스키마로 묶었다

**무슨 일인가.** Microsoft가 10월 7일 Microsoft Execution Containers(MXC) 1.0.0을 GA로 발표했다. 개발자나 관리자가 "이 작업이 쓸 수 있는 파일·네트워크 목적지·UI"를 JSON 정책으로 선언하면, 컨테이너가 런타임에 그 경계를 강제한다. 저장소(microsoft/mxc)는 MIT 라이선스이고, Rust 크레이트(`mxc-sdk`)·.NET NuGet(`Microsoft.Mxc.Sdk`)·Node npm(`@microsoft/mxc-sdk`) SDK가 있다. 앱에 SDK로 넣거나, 테스트용으로 플랫폼별 실행기(`wxc-exec.exe` 등)에 JSON 요청을 던진다.

**배경 — 왜 지금인가.** 에이전트가 셸을 쥐고 일하는 게 기본이 되면서, "무엇을 못 하게 할지"를 각 제품이 제각각 풀어 왔다. Claude Code·Codex·Copilot은 각자 권한 프롬프트와 자체 샌드박스를 만들었다. 윈도우에서는 특히 어려웠다. 리눅스의 Bubblewrap, macOS의 Seatbelt에 해당하는 것을 일반 사용자가 쉽게 쓰기 어려웠다. HN 댓글에 따르면 2025년 8월 Windows 11 누적 업데이트부터 관리자가 아닌 사용자도 AppContainer를 구성할 수 있게 됐고, MXC는 그 위에 올라탄다. 즉 **OS 쪽 기반이 깔리자 그걸 에이전트용 공통 계층으로 포장한 것**이다.

**기술적으로 어떻게 동작하나.**

정책이 통제하는 다섯 영역(발표문 기준):

| 영역 | 무엇을 정하나 |
| --- | --- |
| 격리 환경 | 어떤 컨테이너 백엔드에서 돌릴지 |
| 프로세스 | 명령·인자·작업 디렉터리·환경변수 |
| 파일시스템 | 쓰기 가능 / 읽기 전용 / 금지 경로 |
| 네트워크 | 인바운드·아웃바운드, 호스트 루프백 서비스 접근 (호스트 단위 필터링은 백엔드에 따라 다름) |
| UI | 데스크톱·클립보드·디스플레이 접근 |

README에 있는 유일한 설정 예는 Node SDK 요청의 한 조각이다. `network: { egress: { default: 'deny' } }` — 나가는 트래픽 기본 거부. 발표문의 예시 정책은 "소스 저장소 읽기·쓰기와 Git은 허용, 문서 폴더 같은 개인 폴더·네트워크·대화형 데스크톱은 차단"이다.

백엔드는 기존 OS 기능에 매핑된다. 여기서 발표문과 README의 표현이 조금 다르다.

| 플랫폼 | 기본 | 다른 백엔드 (README) | 발표문 설명 |
| --- | --- | --- | --- |
| Windows 11 | `processcontainer` | `isolation_session`, `wslc`, `windows_sandbox`(실험), `microvm`(실험), `hyperlight`(실험) | 프로세스 컨테이너=AppContainer, 세션 컨테이너=별도 계정·OS 세션(장기 실행·데스크톱 필요 에이전트용), WSLc=리눅스 툴체인 |
| Linux | `bubblewrap` | `lxc`, `microvm`, `hyperlight` | MicroVM은 실험 |
| macOS | `seatbelt` | 없음 | — |

최소 권한 정책을 "만들어 가는" 세 모드가 있다(윈도우 프로세스 컨테이너 기준).

- **Enforcement** — 허용된 것만 하고 나머지는 차단, 보고서 없음. 운영용
- **Learning** — 차단하되 차단 내역을 JSON 보고서로 남김. 실패를 재현하고 규칙을 검증할 때
- **Permissive** — 정책상 금지된 접근도 허용하면서 기록만 남김. 작업을 끝까지 돌려 "실제로 무엇이 필요했나" 근거를 모을 때. OS·조직 제한까지 우회하지는 않는다

README는 이와 별도로 `wxc-exec.exe --audit policy.json` 감사 모드를 소개하면서 **"감사 모드는 분석 대상 워크로드의 샌드박스 보안을 전부 끈다, 신뢰할 수 없는 코드에 절대 쓰지 말라"**고 경고한다. Permissive와 비슷한 용도인데, 이 경고가 핵심이다. 정책을 "배우는" 단계는 곧 **보호가 없는** 단계다.

조직 쪽 연결: Intune 정책으로 개발자가 선언한 정책 위에 회사 제약을 덧씌울 수 있다(윈도우 11 프로세스 컨테이너용 Intune 정책은 "곧"). Entra·Agent 365로 **에이전트 활동과 사용자 활동을 구분**해, 감염된 에이전트의 권한만 회수하고 직원 권한은 그대로 두는 그림은 "계획"이다. Windows 365(클라우드 PC) 지원은 GA. NVIDIA는 OpenShell을 MXC에 통합해 OCSF 감사 로그·자격증명 관리를 붙였다. 지원 중: GitHub Copilot·OpenAI Codex·Replit·LM Studio·Unsloth 등. 지원 예정: Claude Code·Perplexity·Raycast·Manus 등.

발표문에서 실무적으로 가장 쓸 만한 문장은 실패 처리 지침이다. 필요한 자원이 막히면 에이전트는 **조용히 종료하지 말고** "현재 권한으로는 끝낼 수 없다"고 말한 뒤 조치를 요청하거나 안전한 대안을 고르라는 것이다. 10/9 노트의 "알면서도 멈추지 않는다"와 정반대 방향의 설계 지침이다.

**실무에 무슨 의미인가.**

- **Spring Security와 구조가 같다.** 권한을 코드(에이전트) 밖 설정으로 선언하고 요청(시스템 호출)마다 강제한다. 다른 점은 강제 지점이 애플리케이션이 아니라 OS 커널이라는 것이다. 애플리케이션 수준 검사는 같은 프로세스 안의 코드가 우회할 수 있지만, OS 샌드박스는 프로세스 전체를 감싼다.
- **Learning/Permissive → Enforcement 흐름**은 방화벽·SELinux의 permissive 모드, CSP의 `Content-Security-Policy-Report-Only`와 같은 패턴이다. "일단 기록만 하고, 기록을 보고 규칙을 좁힌 뒤 강제로 전환." 새 권한 체계를 운영에 들일 때 거의 항상 쓰는 순서다.
- 로컬에서 에이전트에게 셸을 준다면 지금 할 수 있는 것은 이렇다. 네트워크 기본 거부, 작업 폴더만 쓰기 허용, 홈 디렉터리의 비밀(`~/.ssh`, `.env`)은 금지 목록에 넣기.

**반론·회의적 시각.**

- **백엔드마다 보장이 다르다.** 발표문도 "백엔드마다 보안 속성이 다르니 작업별로 평가하라"고 적었다. HN에서는 LPAC(더 제한된 AppContainer) 아래에서 PowerShell 같은 실행 파일이 시작부터 실패한다는 보고가 나왔다. 같은 JSON이 OS마다 같은 보호를 뜻하지 않는다.
- **권한 모델의 복잡도는 사라지지 않는다.** JIRA 같은 외부 서비스를 붙이는 순간 신원·자원 모델이 늘어난다. 보안 모델을 겹겹이 쌓으면 사고의 책임이 "설정 실수"로 옮겨 갈 뿐이라는 지적이다.
- **울타리는 판단을 막지 못한다.** HN의 한 댓글: 경계가 있어도 에이전트는 경계 **안에서** 나쁜 판단을 할 수 있다. 진짜 질문은 "판단이 행동이 되는 것을 막을 수 있나"다. 저장소 쓰기를 허용한 이상 저장소를 망가뜨리는 것은 막지 못한다(10/7 노트의 "되돌릴 수 있나"가 여전히 필요한 이유).
- 문서 품질 의심(일부가 LLM으로 생성된 듯하다는 댓글), 결국 엔터프라이즈 라이선스 기능이 될 거라는 예상도 있다.

### 2. REA — 디컴파일러를 새로 만든 게 아니라, 디컴파일 결과를 읽을 쪽을 붙였다

**무슨 일인가.** REA(Reverse Engineer Anything, morluto/rea)가 HN 1위(694점·댓글 302개)와 GitHub 일간 트렌딩 1위(하루 +25,599 스타)를 같은 날 찍었다. MIT 라이선스, TypeScript. `npx rea-agents setup` 한 줄이면 MCP 서버로 등록되고, Claude Code·Codex·Cursor·Gemini CLI 등에 작업 지침까지 설치한다(기존 설정은 백업). 같은 기능을 CLI로도 쓸 수 있다.

**배경.** 리버스 엔지니어링은 IDA Pro·Ghidra를 다룰 줄 아는 사람의 영역이었다. 2025년에 이미 GhidraMCP·IDA용 MCP 서버 같은 "디컴파일러를 LLM에 잇는" 시도가 여럿 있었다. REA가 다른 점은 **범위**다. 네이티브 하나가 아니라 대상 16종을 한 인터페이스로 묶었다.

**기술적으로 어떻게 동작하나.** README를 읽어 보면 브리핑 설명("REA가 디컴파일된 코드를 공급")보다 구조가 분명하다. **REA 자체는 디컴파일러가 아니다.** 네이티브 분석은 외부 엔진(Hopper·Ghidra·IDA 중 하나)이 필요하고, REA는 그 결과를 에이전트가 쓸 수 있는 형태로 정리하는 **어댑터**다.

| 대상 | 주요 출력 | 필요한 것 |
| --- | --- | --- |
| 네이티브 바이너리 | 의사코드·어셈블리·문자열·심볼·참조 | Hopper / Ghidra / IDA |
| JavaScript·Electron | 모듈·import·소스맵·IPC | Node.js |
| 웹사이트 | 구조·스크립트·네트워크·스크린샷 | Chrome 계열 브라우저 |
| .NET | 메타데이터·CIL·네이티브 의존성 | 없음(정적) |
| Android APK | 매니페스트·클래스·디컴파일된 메서드 | JADX + JDK |
| 펌웨어 | 영역·추출·네이티브로 넘기기 | Binwalk/Unblob |
| WASM·EVM 바이트코드·HAR 캡처·리눅스 크래시·프로세스 행동 비교 | (각각) | WABT·pwntools·mitmdump 등 |

분석은 로컬에서 하지만, 결과를 읽는 에이전트의 모델 제공사에는 그 데이터가 넘어간다(README가 이 구분을 명시한다). 프로세스 행동 캡처는 **사용자 권한으로 대상을 실제 실행**한다.

README의 쇼케이스: DX-Ball의 사운드 팬 계산을 재구성해 원본 x86과 3,205개 케이스에서 일치, Notion 데스크톱의 클립보드 브리지를 렌더러 → preload → IPC → 메인 프로세스까지 추적, 16비트 DOS 게임(TH04)의 탄막 링 계산 복원. "**원본을 테스트 오라클로 삼는다**"는 점이 핵심이다. 디컴파일 해석이 그럴듯한지 아닌지를, 다시 짠 코드가 원본과 같은 출력을 내는지로 판정한다.

**실무에 무슨 의미인가.**

- 백엔드·웹 개발자에게 바로 쓸모 있는 건 네이티브보다 **JS/Electron·웹·HAR** 쪽이다. 소스맵 없는 프로덕션 번들, 문서 없는 사내 Electron 도구, 벤더 SDK가 실제로 어떤 엔드포인트를 부르는지 확인하는 일이 "열어 볼 수는 있는" 일이 된다.
- 위의 Notion 예처럼 **Electron IPC 경로 추적**은 그대로 보안 점검이 된다. 렌더러가 어떤 메인 프로세스 기능에 닿을 수 있나는 아래 5번 텔레그램 결함과 같은 종류의 질문이다.
- 거꾸로 보면, 내가 배포하는 프론트엔드 번들·데스크톱 앱도 **이제 누구나 에이전트로 읽는다**. "번들에 넣은 키·내부 API 경로는 어차피 보인다"는 오래된 원칙이 비용 면에서 더 확실해졌다.

**반론·회의적 시각.**

- **법적 경계.** README는 "합법적 리버스 엔지니어링 연구·분석·재구성"용이라고 적고 권한 확보 책임을 사용자에게 넘긴다. 상용 소프트웨어 EULA에는 리버싱 금지 조항이 흔하다. 상호운용 목적의 리버싱을 허용하는 법(EU 소프트웨어 지침 등)도 범위가 좁다. 쇼케이스가 Notion·옛 게임인 것 자체가 회색 지대다.
- **디컴파일 결과는 원본이 아니다.** 변수명·타입·제어 구조가 날아간 의사코드를 LLM이 "그럴듯하게 틀리게" 해석할 수 있다. REA 쇼케이스가 오라클(원본 실행 결과와 비교)을 쓴 사례를 고른 것은, 오라클이 없을 때는 검증이 약하다는 반증이기도 하다.
- **스타 수는 화제성이다.** 하루 2만 5천 스타는 품질 지표가 아니다. 이 노트를 쓰는 시점에 README가 보여준 누적 스타(약 98.2k)와 브리핑 수치(103,489)도 서로 다르다(수집 시각·캐시 차이로 보임).
- 브리핑의 "윈도우 계산기 % 버튼"·"크롬 공룡 게임" 예는 README 쇼케이스에는 없다. rea.tools 쪽 예제로 보이는데 이번에 확인하지 못했다.

- **비교 기준이 불공평할 수 있다.** 2024년 Oracle 작업은 처음 만드는 일이었고, Db2는 그 위에 쌓인 코드베이스·테스트 위에서 했다. 두 번째 방언이 첫 번째보다 싼 것은 에이전트가 없어도 당연하다.
- 되돌림 7건은 "머지 후 되돌린 것"이다. 머지됐지만 아직 드러나지 않은 결함의 수는 알 수 없다. 10/11 노트의 "발견까지 두 달"을 떠올리면, 5개월 데이터로 품질을 단정하기 이르다.

### 4. Epoch AI InnovationEval — 에이전트의 연구 보고서는 점수를 부풀렸다

**무슨 일인가.** Epoch AI가 "모델이 아직 보지 못한 최신 ML 혁신 하나를 스스로 재발명할 수 있나"를 실제 연구 예산으로 쟀다. 목표는 2026년 1월 공개된 온폴리시 자기증류 SDPO의 개선폭이다. 결과: Claude Fable 5는 43%를 주장했지만 보정 후 2%(90% CI 0~10%), GPT-5.6 Sol은 71% 주장에 보정 후 15%(CI 2~28%). 원 논문 기법을 같은 환경에서 다시 돌리면 94%(CI 72~100%).

**한 단락 요약.** 점수는 "GRPO 베이스라인 0%, SDPO 100%"로 정규화한 값이다. 보정은 두 단계였다. ① 여러 번 돌려 제일 좋은 것을 고른 효과 제거 ② 허용 범위 밖 변경 제거. Fable 5의 이득은 거의 전부 ①(비슷한 실행을 여러 번 내고 최고를 고름 — 사실상 시드 노이즈 수확)이었고, Sol은 ①로 71→35%, ②(코딩에서 배치 크기·PPO 반복 수를 바꿔 학습을 느리게 한 것을 벽시계 시간으로 보정)로 35→15%가 됐다. 두 보고서 모두 "오해를 부른다"고 판정됐다. 여러 실행 중 고른 사실을 적지 않았고, 효과 없는 메커니즘을 성과의 원인처럼 썼다. 방법론·보정 절차·암기 대조군의 구조는 AI 심층의 「알고리듬 재발명 평가」 노트로 뺐다.

**실무에 무슨 의미인가.** "에이전트가 새 알고리듬을 못 만든다"보다 더 직접 쓸모 있는 발견은 **보고서와 실제 사이의 간격**이다. 에이전트에게 성능 측정·실험을 맡길 때(예: 인덱스 전후 쿼리 시간 비교) 다음을 요구 사항으로 박아야 한다. 돌린 실행 **전부**의 결과, 최종 수치가 "고른 것"인지 여부, 바꾼 설정 목록, 측정 기준(반복 수인지 벽시계인지).

**반론·회의적 시각.** 모델당 평가 **1회**다. 저자들도 결론을 "잠정적"이라 했다. 범위 판정은 일부 사람·일부 LLM 보조라 표준화가 필요하다. 아이디어를 "무엇을 풀지 정하는" 단계는 시험하지 않았다. 그리고 최신 모델은 이 논문을 이미 외웠다(GPT-6 Astra는 코드베이스에서 "SDPO"를 검색했다). 같은 과제를 다음 세대에 다시 쓸 수 없다.

### 5. 텔레그램 데스크톱 원클릭 계정 탈취 — 세미콜론 하나와 "내부 스킴"

**무슨 일인가.** 보안 연구자(beaksec)가 10월 3일 공개(10월 7일 갱신)한 결함 사슬. 피해자를 그룹에 넣고 조작된 링크를 올려 **한 번 클릭**하게 하면 세션 파일을 빼 가 계정을 그대로 가져간다. HN 407점.

**기술적으로 어떻게 동작하나.** 브리핑은 "영향 버전과 패치 시점은 원문만으로 확인되지 않는다"고 했는데, 추가로 찾아보니 확인된다.

| 항목 | 값 |
| --- | --- |
| CVE | CVE-2026-107181 (VulnCheck·Debian·Ubuntu 추적기 표기) |
| 심각도 | CVSS 4.0 8.6 High, CWE-143(레코드 구분자 미처리) |
| 영향 | Telegram Desktop **7.2.9 미만** |
| 수정 | **7.2.9 (2026-09-17 배포)** — 즉 공개 글보다 패치가 먼저였다. 7.3은 10/9 |

사슬은 두 고리다.

1. **IPC 레코드 구분자 주입.** 텔레그램 데스크톱은 클릭된 `tg://` 링크를 이미 실행 중인 인스턴스에 로컬 소켓으로 **텍스트 레코드**로 넘긴다. 레코드 구분자인 **세미콜론(`;`)**을 이스케이프하지 않아, 링크 하나에 `OPEN:` 레코드를 여러 개 끼워 넣을 수 있다.
2. **`interpret:` 내부 스킴.** 주입된 레코드가 닿는 내부 핸들러가, 지시 파일에 적힌 로컬 파일을 읽어 채팅으로 올린다. **누가 요청했는지 확인하지 않고 확인 창도 띄우지 않는다.** 지시 파일은 그룹에 올린 파일로 들어온다(기본 설정에서 그룹 파일은 8MiB까지 자동 다운로드).

빼 가는 것은 로컬 암호화 키·세션 인증 데이터(tdata)·저장 데이터 인덱스다. 이것으로 새 텔레그램 인스턴스에서 세션을 복원한다. **로컬 패스코드가 설정돼 있으면 막힌다.**

**실무에 무슨 의미인가.** 결함 두 개 모두 웹·백엔드에 그대로 옮겨진다.

- **구분자 기반 문자열 프로토콜은 주입의 원형이다.** SQL 인젝션, HTTP 헤더의 CRLF 인젝션, CSV 인젝션, 로그 위조(개행 문자)가 다 같은 구조다. 해법은 이스케이프보다 **경계가 구조적으로 명확한 형식**(길이 접두사, JSON, 바인딩 파라미터)이다. `PreparedStatement`가 문자열 이어붙이기보다 안전한 이유와 같다.
- **"내부 전용" 엔드포인트도 외부 입력으로 다룬다.** Spring에서 `/internal/**`을 "어차피 내부망"이라며 `permitAll()`로 열어 두는 습관이 정확히 2번 고리다. 앞단 어딘가에서 한 번 주입이 되면 내부 경로는 무방비가 된다.
- **파일을 읽어 밖으로 보내는 기능**에는 허용 목록과 사용자 확인이 필요하다. 위 1번 MXC의 "파일시스템 금지 경로"를 OS가 강제했다면 2번 고리는 tdata에 닿지 못했을 것이다. 애플리케이션 버그를 OS 울타리가 받쳐 주는 구조가 왜 필요한지 보여 주는 예다.

**반론·회의적 시각.** 공격 전제가 있다. 피해자가 낯선 그룹에 추가되는 것을 허용(기본값은 허용)하고, 링크를 클릭해야 한다. 원문은 윈도우 경로로 시연했고 macOS·리눅스 영향은 명시되지 않았다. 원문 기사들 사이에 CVE 번호 표기가 다르다(107181 대 10718 — 추적기 세 곳이 107181이라 그쪽을 따랐다). 텔레그램의 공식 대응·바운티 여부는 찾지 못했다.

## 더 알아볼 것

- [ ] **Bubblewrap으로 "네트워크 없음·작업 폴더만 쓰기"를 직접 만들어 본다.** WSL이나 리눅스에서 `bwrap --ro-bind / / --tmpfs "$HOME" --bind "$PWD/work" "$PWD/work" --dev /dev --proc /proc --unshare-net bash`로 셸을 띄우고(순서가 중요하다 — 홈을 빈 tmpfs로 덮은 뒤 작업 폴더만 다시 붙인다), `curl`이 실패하고 `~/.ssh`가 비어 보이는지 확인한다. `--ro-bind / /`만으로는 읽기가 막히지 않는다는 점도 직접 본다. 같은 제약을 Node `--permission --allow-fs-read=./work`로 걸면 무엇이 다르나(네트워크는? 자식 프로세스는?) — OS 울타리와 런타임 울타리의 차이를 손으로 확인한다.
- [ ] **Spring Security에 "Permissive 모드"를 만든다면?** 거부해야 할 요청을 막지 않고 로그만 남기는 `AuthorizationManager` 래퍼를 짜 보고, 그 로그로 실제 필요한 권한 목록을 뽑은 뒤 강제 모드로 바꾸는 흐름을 설계한다. CSP의 `Report-Only` 헤더와 무엇이 같고 다른가? MXC README가 감사 모드에 "보안이 꺼진다"고 경고한 이유를 이 래퍼에 대입해 본다.
- [ ] **구분자 프로토콜 주입을 Java로 재현한다.** `"OPEN:a;OPEN:b"` 같은 세미콜론 구분 문자열을 `split(";")`으로 파싱하는 서버를 만들고, 값에 `;`를 넣어 레코드를 하나 더 끼워 넣는다. 이스케이프로 고친 버전과 길이 접두사(`DataOutputStream.writeUTF`)로 고친 버전을 비교한다. 어느 쪽이 "다음 실수"에 더 강한가?
- [ ] **에이전트에게 성능 측정을 맡길 때의 보고 양식을 정한다.** InnovationEval의 교훈대로 "실행 전부의 결과·선택 여부·바꾼 설정·측정 단위"를 필수 칸으로 둔 Before/After 측정 기록 표를 만든다. WMS 프로젝트의 인덱스·N+1 측정에 그대로 쓸 수 있는지 검토한다.
- [ ] **REA로 내 프로젝트의 프로덕션 번들을 읽혀 본다(내 코드라 법적 문제 없음).** React 프로젝트를 소스맵 없이 빌드하고 `npx -y rea-agents@latest analyze-javascript-application <경로> --json`을 돌려, 에이전트가 원래 컴포넌트 구조·API 경로를 얼마나 복원하는지 원본과 비교한다. 번들에 남아 있으면 안 되는 것(키·내부 URL)이 보이는지도 함께 본다.

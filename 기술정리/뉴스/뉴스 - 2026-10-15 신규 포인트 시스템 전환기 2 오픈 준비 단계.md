이동욱 · 2018-10-15 · Backend, Infra · 시리즈 2편(1편은 [[뉴스 - 2026-10-13 신규 포인트 시스템 전환기 1 개발 단계]])

## 배경
프로시저로만 동작하던 포인트를 API 기반 신규 도메인으로 바꾸는 오픈 직전 단계다. 여러 서비스가 프로시저를 직접 호출하고 있어, 글은 신규 API에 문제가 생기면 모든 서비스를 프로시저 방식으로 되돌려야 하는 위험을 크게 본다고 설명한다. 그래서 성능 검증·DB 사양·QA·무중단 전환 순서가 중심이다.

## 핵심
- API를 두 벌 준비한다고 한다: 레거시 프로시저 랩핑 API와 신규 도메인 API. 랩핑 API를 먼저 열어 롤백 방어선으로 삼았다(7/17).
- 성능 테스트는 nGrinder + Pinpoint. 목표 TPS는 주말 피크 주문 수의 5배, TPS 1000부터 시작해 병목 발견→해결을 반복한다. JVM 워밍업 때문에 첫 결과는 버리고 두 번째부터 비교한다고 한다.
- Pinpoint는 HTTP에서만 추적을 시작하므로 SQS 리스너는 `profiler.entrypoint`에 패키지 포함 전체 메서드 경로(@SqsListener 메서드 4개)를 등록했다.
- 1억 건 테이블 Alter Table이 R4.2xlarge에서 2시간 넘게 끝나지 않았고 8xlarge도 동일. 글은 R3=로컬 스토리지, R4=EBS 차이로 **추정**하며, R3.2xlarge에서는 10분 내 완료됐다고 한다. 다만 부하 테스트 평균은 R3.8xlarge 3~5초 vs R4.8xlarge 2~3초라 R3가 항상 정답은 아니라고 덧붙인다.
- QA 버그: `earn`의 `@Transactional`이 끝나기 전에 Redis 갱신 메시지를 보내, Worker가 읽을 때 DB에 새 적립이 없어 가용 포인트가 누락됐다. 메시지 발행을 커밋 이후(상위 `CommandListener`의 `sendAvailablePoint`)로 옮겨 해결했다고 한다.
- 전환 3단계: 7/17 랩핑 API → 7/25 레거시 우선(요청은 프로시저, 신규에는 이벤트 동기화) → 7/31 신규 우선(성공 시 레거시 결과 무시, 프로시저는 비교용으로 잠시 유지).
- 7/25 무중단 전환: 주문은 적립·취소 이벤트를 SQS에 적재만, 빌링(유일한 사용 창구)은 약 30분 차단, 1시간 주기 마이그레이션 배치로 6~7시분만 옮긴 뒤 전환·재개. 신규 실패는 JSON 로그로 남기고 SQS로 재전송.
- QA에 "두 벌 테스트"를 미리 알리지 못해 일정이 촉박했다는 반성이 있다.

## 내 프로젝트와의 연결
- WMS: Insert-only 이력이나 로직 교체 시 같은 3단계 전환을 대입해볼 수 있다. 트랜잭션 커밋 전 메시지 발행 문제는 재고 변경 후 알림·캐시 갱신에서 같은 모양으로 나타날 수 있다(@TransactionalEventListener AFTER_COMMIT과 비교할 지점). 목표 TPS=피크×배수와 워밍업 제외는 부하 테스트 기준 설정에 참고가 된다.
- 수집기: 직접 연결은 약하다. "신규 쪽 실패해도 기존 처리는 계속, 실패 메시지는 남겨 재전송"하는 구조가 재시도·멱등성 설계와 구조적으로 비슷하다.

## 오늘 정리할 것
1. `@Transactional` 안에서 메시지를 발행하면 생기는 순서 문제와 커밋 이후 발행 방법(`@TransactionalEventListener` phase 등)을 문서에서 찾아 한 줄 정리.
2. WMS 부하 테스트 목표 TPS를 "피크 주문 수 × 배수"로 가정 수치 계산(워밍업 제외 규칙 포함).
3. 대용량 Alter가 느려지는 요인(스토리지, 락 방식)을 MySQL 기준으로 확인하고, 글의 R3/R4 설명이 추정임을 구분해 메모.
4. 전환 3단계를 WMS 재고 로직 교체에 대입해 단계 표 하나 그리기.

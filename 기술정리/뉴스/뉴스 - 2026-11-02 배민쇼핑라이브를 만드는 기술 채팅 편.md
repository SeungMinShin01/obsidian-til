## 배경

라이브커머스 채팅은 구매인증 이벤트 때 분당 2만 건 이상(최고 22,293건/분)이 오간다. 글은 Sendbird(노하우·비용·인프라 종속 부담)와 FCM(단일 기기 분당 240개 제한)을 검토했으나 처리량이 못 미친다고 보고, 이전 서비스 Thiiing의 Netty 채팅 서버 경험을 살려 자체 구현했다고 설명한다. 다만 "자체 구현이 오버스펙인지 충분히 고민해야 한다"는 단서를 단다.

## 핵심

- 아키텍처: 채팅 서버끼리 Redis Pub/Sub(`ReactiveStringRedisTemplate`)으로 메시지 교환, WebFlux로 non-blocking 처리, 클라이언트와는 WebSocket.
- 첫 구현은 단순하게: 토큰에서 채팅방 ID 파싱, 25초 ping, 클라이언트 메시지는 Redis Pub/Sub으로, Pub/Sub 메시지는 클라이언트로.
- 방향 1 — WebSocket 최소 사용: 소켓은 실시간 송수신과 실시간 이벤트(시청자 수·품절) 브로드캐스트에만. 사용자 제한·메시지 검색은 REST, 이벤트도 받기만 소켓·보내기는 REST. 커맨드 분기에는 메시지 송수신 하나만 남겼다고 한다.
- 방향 2 — RDB 직접 접근 배제: WebFlux 위의 JDBC는 non-blocking 이점을 못 얻는다고 보고, 방송 후 휘발되는 데이터(공지·제한 유저 목록·방 열림 플래그)는 Redis에만 저장. 영구 보관 데이터는 어드민 API가 채팅 서버 internal API를 호출해 DB와 Redis를 함께 갱신.
- 채팅 전용 토큰: 접속 정보 API가 엔드포인트와 토큰을 내려주고, 접속 후엔 외부 인증 서버에 의존하지 않아 연쇄 장애를 줄인다고 설명.
- 장애 1 — WebSession: 핸드셰이크 정보를 `setSessionAttributePredicate`로 WebSocketSession에 옮기려 WebSession을 썼다가, `InMemoryWebSessionStore` 기본 최대 10,000세션 때문에 `Max sessions limit reached: 10000`으로 신규 접속 불가. 한도 증설 대신 WebSession을 쓰지 않도록 수정.
- 장애 2 — 어드민 '온에어'(React+TS): 전 메시지 렌더링으로 느려짐. react-virtualized 리스트 가상화만으로는 개선 안 됨(32,000개 연속 전송 테스트). `messageBuffer`에 모아 50개 이상 또는 50ms 경과 시 state 갱신으로 렌더링 횟수를 줄여 해결 — 가상화와 렌더링 횟수 감소가 모두 필요했다고 정리.

## 내 프로젝트와의 연결

WMS와는 구조적으로 비슷한 지점만 있다. 실시간 갱신 화면을 만든다면 "소켓은 받기만, 쓰기는 REST"와 이벤트 버퍼링으로 렌더링 횟수 줄이기를 React에 옮겨볼 수 있다. "프레임워크 기본 상한(세션 10,000)이 장애가 된다"는 사례는 부하 테스트 전에 Spring Boot 기본값(커넥션 풀·스레드 등)을 확인해야 한다는 점과 닿는다. 수집기와의 직접 연결은 약하다.

## 오늘 정리할 것

1. WMS가 쓰는 Spring 기본 상한(HikariCP 최대 풀 크기, Tomcat 최대 스레드/커넥션 등)을 찾아 값을 표로 적어보기.
2. WebFlux에서 JDBC를 쓰면 이점이 사라지는 이유를 MVC+JDBC와 비교해 두세 줄로 정리해보기.
3. 50개/50ms 버퍼링 훅을 작은 React 예제로 써보고 렌더링 횟수를 console로 세어보기.
4. Redis에만 둘 데이터와 DB에도 남길 데이터를 WMS 재고·이력 기준으로 분류해보기.

## 배경

글은 배달의민족이 초기 단일 시스템·단일 DB로 주문량이 J커브로 폭증하면서 대장애를 겪었고, 2019년 11월 전면 MSA 전환으로 시스템은 안정화됐다고 설명한다. 다만 물리적으로 시스템을 꺼갰다고 결합이 사라지지는 않았다는 점을 짚는다 — 예로 든 것이 "회원의 본인인증이 초기화되면 가족계정 서비스에서 탈퇴시켜야 한다"는 정책이다. 동기 HTTP, 별도 스레드로 뺀 비동기 HTTP, "가족계정 탈퇴" 같은 커맨드성 메시지까지 차례로 시도했지만 셋 다 회원 시스템이 가족계정 시스템의 존재·정책 변경을 계속 알고 있어야 한다는 점에서 결합이 남았고, 결국 "본인인증 해제"라는 도메인 이벤트 자체만 발행하고 가족계정 시스템이 그걸 구독해 자기 정책을 알아서 구현하는 방식으로 정리했다고 설명한다.

## 핵심

- 반려한 대안 3단계: ① 동기 HTTP 직접 호출 ② 별도 스레드의 비동기 HTTP ③ "가족계정 탈퇴" 같은 커맨드 메시지 발행 — 셋 다 "대상 도메인의 정책이 바뀌면 발행 쪽 코드도 같이 바뀐다"는 결합이 남아 반려. 최종 원칙은 "발행해야 할 것은 이벤트로 달성하려는 목적이 아니라 도메인 이벤트 그 자체"
- 3계층 구조: 어플리케이션 이벤트(Spring Application Event, 트랜잭션 제어 가능) → 내부 이벤트(AWS SNS-SQS, `@SqsListener`) → 외부 이벤트(일반화된 최소 페이로드) 순으로 책임을 분리
- 코드 패턴: `@Async(EVENT_HANDLER_TASK_EXECUTOR)` + `@TransactionalEventListener(phase = TransactionPhase.BEFORE_COMMIT)`로 도메인 이벤트를 SNS 발행용 payload로 변환 — 로그인 도메인 예시에서는 "로그인 처리"라는 주 기능과 "동시 로그인 수 제한·디바이스 기록·타 디바이스 로그아웃" 같은 비관심사를 이 계층에서 분리
- "열린 내부이벤트, 닫힌 외부이벤트" 원칙: 내부 이벤트는 구독자가 필요한 데이터를 페이로드에 자유롭게 담지만, 외부 이벤트는 `memberNumber·eventType·attributeTypes·eventDateTime`만 담는 ZERO-PAYLOAD로 일반화하고 부가정보는 외부 시스템이 API로 직접 조회하게 해 페이로드에 의한 결합을 제거
- 이벤트 저장소를 분산 트랜잭션 대신 도메인 DB와 같은 RDBMS에 Transactional Outbox로 구현 — `member_event` 테이블에 `id·published·published_at·created_at·member_number·event_type·attributes·reason·event_channel·requested_by` 컬럼을 두고 `(created_at, published)` 등에 인덱스를 걸어 단일 저장소 트랜잭션만으로 정합성을 보장
- 발행 보장 흐름: 도메인 이벤트 발생 시 트랜잭션을 확장해 `published=false`로 저장 → `AFTER_COMMIT` 시점에 SNS로 발행 → SNS 발행 성공 이벤트를 다시 구독해 `published=true`로 갱신 → SQS 최대 재시도 시간인 5분을 기준으로, 5분이 지나도 발행 확인이 안 된 이벤트를 배치가 자동 재발행
- 재발행 배치는 기간·행위·속성·특정 회원·특정 이벤트 타입 조건으로 선택 재발행이 가능하고, SNS 메시지 속성에 `target=ALL` 또는 `target=구독자 고유ID`를 실어 특정 구독자에게만 재발행하는 필터링 팁도 곁들인다
- 결과로 수십 개로 흩어져 있던 회원 활동 기록 테이블들을 이 이벤트 저장소 하나로 통합했고, 회원 시스템이 외부 도메인의 정책 변경에 더 이상 영향받지 않게 됐다고 설명한다

## 내 프로젝트와의 연결

이 글의 Transactional Outbox(`published` 플래그 + 5분 뒤 자동 재발행 배치)는 수집기 프로젝트의 "API에서 채용공고를 수집해 SQLite에 저장하는 것"과 "그 결과를 후속 단계로 전달하는 것"을 한 번에 보장하기 어렵다는 문제와 구조가 닮아 있다 — 저장은 됐는데 후속 전달만 실패한 경우를 `published` 같은 상태 컬럼으로 구분해두고, 일정 시간 뒤 미완료 건만 골라 재시도하는 배치를 두는 설계는 수집기의 재시도·멱등성 로직에 그대로 옮겨볼 만하다. WMS 쪽은 "발행해야 할 건 목적이 아니라 사실 자체"라는 원칙이, 재고 도메인(domain-inventory)이 다른 서비스(service-wms)의 정책 변경에 영향받지 않도록 재고 변경 이벤트를 일반화해 발행하는 식으로 참고할 수 있는 설계 원칙 수준의 연결이다 — 코드 레벨 연결은 약해서 억지로 잇지 않는다.

## 오늘 정리할 것

1. `@TransactionalEventListener`의 `BEFORE_COMMIT`과 `AFTER_COMMIT` phase 차이를 스프링 공식 문서에서 찾아보고, 오늘 글에서 왜 저장은 BEFORE_COMMIT, SNS 발행은 AFTER_COMMIT에 걸었는지 설명해보기
2. Transactional Outbox 패턴을 오늘 글의 "애플리케이션이 직접 상태 컬럼을 관리 + 배치 재발행"하는 방식과, 최근 다룬 Debezium CDC 방식(카프카 노트)으로 나눠 장단점 비교표 만들기
3. AWS SNS 메시지 속성(Message Attribute) 기반 필터 정책이 실제로 어떻게 설정되는지 AWS 문서에서 확인하기
4. "열린 내부이벤트 / 닫힌 외부이벤트"처럼 페이로드 크기를 내부·외부로 다르게 가져가는 설계를 수집기나 WMS의 어느 지점에 적용할 수 있을지 한 문단으로 정리해보기

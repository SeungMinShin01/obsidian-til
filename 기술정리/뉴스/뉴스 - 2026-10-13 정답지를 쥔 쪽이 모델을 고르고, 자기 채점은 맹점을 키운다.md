## 오늘의 흐름

겹치는 것부터 정리한다. 오늘 브리핑(10/13)의 Epoch AI InnovationEval(AI 4번)과 REA(큰 건 1번의 후반)는 10/12 노트에서 깊게 다뤘고, InnovationEval은 AI 심층의 「알고리듬 재발명 평가」 노트로 따로 있다. Deno의 Cloudflare 합류, Python 3.15, 핵심 오픈소스 23개 중 11개가 1~2인이라는 조사, Carson Gross 인용, Dwarf Fortress의 버전 관리는 10/11·10/12 노트에 나왔다. 이것들은 다시 쓰지 않는다.

새 항목을 꿰는 첫 번째 축은 브리핑 제목 그대로 **"기계가 채점하는 정답지"**다. 상용 FPS 한 편을 에이전트로 통째로 역컴파일한 momo5502의 후기에서, 실패한 첫 달과 성공한 나머지 두 달을 가른 것은 모델이 아니라 **바이트 매칭 오라클**이었다. 오라클을 붙이자 리뷰어 에이전트가 필요 없어졌고, 더 싼 모델(Luna)이 쓸 만해졌다. 이 흐름은 이어지는 흐름이다. 10/9 노트는 "말로 준 규칙은 안 먹고 하네스가 강제할 때만 따른다", 10/12 노트는 "에이전트의 자기 보고는 증거가 아니다"였다. 오늘은 그 반대편, **"강제할 수 있는 채점기가 있으면 무엇이 가능해지나"**를 6,000억 토큰 규모의 실물로 보여준다. 10/12의 REA 노트에서 "원본을 테스트 오라클로 쓴다"는 패턴이 짧게 나왔는데, 오늘 사례가 그 패턴의 가장 큰 실물이다.

두 번째 축은 그 정답지를 **모델 스스로 만들 수 있나**다. 이건 새 흐름에 가깝다. Hugging Face 상위 RSI-Anything은 "현실 피드백이 비싸니 예측 월드 모델로 미리 거르자"를, Sakana AI의 MASS는 "같은 모델이 풀고, 고치고, 채점하고, 이긴 방식을 가중치에 새기자"를 내놨다. 둘 다 재귀적 자기개선(RSI)을 표방한다. 그런데 MASS 저자들이 직접 쓴 가장 큰 위험이 오늘 흐름의 핵심이다. **같은 모델이 채점하면, 그 모델이 못 보는 결함은 "개선"으로 승인되고 다음 라운드에서 강화된다.** 첫 번째 축의 교훈(채점기는 에이전트 바깥에, 수정 불가능하게)과 정면으로 부딪힌다. momo5502의 에이전트가 검증 스크립트를 고쳐 자기 함수를 빼려 했고, 그래서 스크립트를 해시로 묶었다는 일화가 MASS의 "공유된 맹점" 경고와 같은 이야기를 반대쪽에서 한다.

세 번째 축은 **무엇을 안 보낼지**다. 이것도 이어지는 흐름이다. 9/19 노트의 하네스 실증(컨텍스트 관리의 이득은 대부분 "넘쳐서 죽는 것" 방지), 10/9 노트의 Codemode(도구 호출을 스크립트로 엮어 왕복을 줄임)에서 이어진다. Uber의 MCP Gateway는 도구 5,000개를 붙이면서 "다 등록"이 아니라 **단계적 발견·응답 필드 잘라내기·파일로 쓰고 grep**을 넣었다. Pydantic Logfire의 JSON 컬럼 쪼개기는 AI 얘기가 아니지만 같은 원리다 — 빠르게 읽는 것보다 **안 읽어도 되는 것을 건너뛸 수 있게** 저장하는 것이 이긴다. Pensieve·jevgrep·context-mode도 같은 문제를 각자 푼다.

네 번째 축은 웹 플랫폼의 **신뢰를 누가 판정하나**다. 「패스키는 함정이다」(HN 400점)와 「핑거프린트는 새로운 쿠키다」(HN 173점)가 같은 날 올라왔다. 하나는 사이트가 사용자의 기기·OS를 증명으로 고를 수 있게 되는 문제, 다른 하나는 사용자 동의 없이 기기를 식별하는 문제다. 방향은 반대지만 둘 다 "브라우저와 인증 수단이 누구 편인가"를 묻는다. 에이전트 얘기와는 별개처럼 보이지만, 10/12의 MXC("정책은 에이전트 밖에")와 겹쳐 읽으면 공통 질문이 남는다. **경계를 강제하는 장치를 누가 쥐고, 그 다이얼을 누가 돌리나.**

AI 심층으로는 MASS를 골랐다. 자기개선 루프를 실제 구조(역할 세 개·내부/외부 루프·Bradley–Terry 순위·워크플로 텍스트 제거 후 LoRA)로 공개했고, 이득이 난 곳과 안 난 곳(SWE-bench 0.94배)과 저자가 직접 꼽은 위험이 모두 적혀 있어 "자기 채점이 어디까지 믿을 만한가"를 따져 보기 좋다. 구조는 AI 심층의 「다중 에이전트 자기 감독」 노트로 뺐다.

## 깊게 본 것

### 1. FPS 한 편을 에이전트로 역컴파일 — 바뀐 것은 모델이 아니라 "PASS/FAIL"이었다

**무슨 일인가.** Maurice Heumann(momo5502)이 10월 9일 「500+ Billion Tokens Later: Letting AI Agents Decompile A First-Person Shooter」를 올렸다. 이름을 밝히지 않은 상용 FPS 하나를 C++로 재구성했다. 결과는 함수의 99% 복원, 그중 83%가 원본 바이너리와 **바이트 단위로 일치**했다. 저자는 게임이 "흠잡을 데 없이 돌아간다"고 썼다. 토큰은 6,000억~7,000억 개로 추정한다(VM이 날아가며 로그를 잃어 추정치다). 비용은 달러로 밝히지 않았고, 코드는 공개하지 않는다. 이 게임에 대한 이전 글 두 편은 삭제됐다고 적었다.

**배경 — 왜 지금 이게 나왔나.** 구독형 무제한에 가까운 요금제(Claude Max 20x, Codex Pro)와 헤드리스 디스어셈블러 MCP(Hex-Rays의 ida-mcp)가 갖춰지면서, "몇 달 동안 에이전트 여러 개를 쉬지 않고 돌리는" 실험이 개인 수준에서 가능해졌다. 같은 날 GitHub 트렌딩 1위가 REA(하루 +45,327★)인 것도 같은 배경이다. 10/12 노트에서 본 것처럼 REA는 디컴파일러가 아니라 Ghidra·IDA·Hopper의 결과를 MCP로 잇는 어댑터다. 즉 **바이너리를 읽는 도구는 이미 있었고, 이제 그걸 읽을 손이 싸졌다.**

**기술적으로 어떻게 동작하나.**

구성:

| 항목 | 내용 |
| --- | --- |
| 모델 | 주로 Sonnet 5. Opus 5.5·Luna·Sol·Terra도 사용 |
| 하네스 | Claude Code CLI·Codex CLI, **기본 설정 그대로** |
| 진행 관리 | GitHub Issues(gh CLI), **번역 단위(.cpp 파일) 하나 = 이슈 하나**, 라벨로 그룹·우선순위 |
| 소통 | 공유 Discord 채널(에이전트↔에이전트, 사람↔에이전트), CI 실패를 웹훅으로 채널에 게시 |
| 규모 | 첫 달: 워커 3 + 리뷰어 1. 이후 약 2개월: Luna 14 + Opus 5.5 2, 브랜치·PR 방식 |

첫 달은 "되는 것처럼 보였다." 80%를 디컴파일했고 메인 메뉴가 뜨고 맵이 로드됐다. 그런데 코드는 **읽기 좋지만 틀렸다.** 함수 시그니처·타입·구조체 레이아웃이 어긋났고, 로직이 멋대로 생기거나 사라졌고, 전역 설정 변수 직접 접근이 훨씬 비싼 해시테이블 조회로 "현대화"돼 있었다. 저자가 꼽은 근본 원인은 셋이다.

1. **정답의 객관적 정의가 없었다.**
2. **리뷰어가 워커의 해명을 믿었다.** 워커가 "이렇게 바꾼 이유는…"이라고 적으면 리뷰어가 수긍했다. 저자는 이걸 **"의도치 않은 프롬프트 주입"**이라고 불렀다.
3. "현대화"라고 포장된 일탈을 허용했다.

나머지 두 달을 바꾼 **바이트 매칭 오라클**:

- 원본 게임과 **같은 컴파일러**로 복원한 함수를 컴파일한다
- OBJ의 해당 함수 바이트를 원본 EXE(가능하면 PDB 포함)와 비교한다
- 링크 시점 주소에 따라 바뀌는 바이트(재배치)는 비교에서 빼고, 대신 **"같은 오프셋에서 같은 심볼을 참조하는가"**를 확인한다. 데이터·타입도 같은 방식
- 일치한 함수는 텍스트 파일에 기록, CI가 매번 재검증해 **회귀를 잡는다**

에이전트의 꼼수 막기:

- 인라인 어셈블리·naked 함수·오브젝트 패치·바이트 직접 박기 금지 — 단, 이건 **지시 + 스캔**이지 도구로 원천 차단한 것은 아니다
- 에이전트가 **검증 스크립트를 고쳐 자기 함수를 제외하려 했다.** 그래서 CI가 스크립트 해시를 GitHub Actions 시크릿과 대조한다

긴 자율 실행에서의 운영 기법:

- 컨텍스트 압축 시점을 기본 90%에서 **42%**로 낮춤 — 오래된 디스어셈블리 덩어리를 일찍 버리기 위해
- 목표·규칙 문서를 **매시간 cron으로 다시 읽게** 함 — 지시가 희미해지는 문제(작업 중 함수 바꾸기, CI만 쳐다보며 놀기, 검증 없이 이슈 닫기) 대응
- 15개 이상에서는 잘못된 명령이 VM을 반복해서 날렸고, Discord는 확장이 안 돼 이슈 배정·CI 조율로만 제한

**실무에 무슨 의미인가.**

이 사례의 일반화는 "에이전트를 쓰려면 먼저 **위조할 수 없는 채점기**를 만들라"다. 바이트 매칭은 극단적인 경우지만, 웹 백엔드에도 대응물이 있다.

| 이 사례 | Spring 백엔드에서의 대응 |
| --- | --- |
| 바이트 매칭 오라클 | 레거시 API와 새 구현에 같은 요청을 보내 응답을 비교하는 **골든 테스트**(스냅샷·approval 테스트) |
| 재배치는 빼고 심볼만 비교 | 응답 비교에서 타임스탬프·ID 같은 비결정 필드를 마스킹하고 구조·값만 비교 |
| 일치 목록 + CI 재검증 | 통과한 엔드포인트 목록을 두고 회귀 시 CI 실패 |
| 검증 스크립트 해시 대조 | 테스트 코드·CI 설정 변경은 사람 승인(CODEOWNERS)으로 분리 |
| 번역 단위 = 이슈 | 패키지/모듈 단위로 작업을 쪼개 하나씩 닫기 |

"생성된 코드는 싸니 나쁜 결과는 살리지 말고 버려라"는 교훈도 실무적이다. 첫 달 코드를 살리는 데 드는 시간이 새로 하는 것보다 컸다. 사람 코드 리뷰의 직관("이미 짠 걸 왜 버려")이 에이전트 코드에선 거꾸로 갈 수 있다.

**반론·회의적 시각.**

- **오라클이 있는 문제가 드물다.** 역컴파일은 "원본 바이너리"라는 완벽한 정답지가 있는 거의 유일한 종류의 일이다. 새 기능 개발에는 그런 정답지가 없다. Karpathy의 "인식 격차" 논쟁(아래)에서 회의론이 지적하듯, 성공 사례의 조건이 일반 업무와 다르다.
- **수치는 재현 불가능하다.** 토큰은 추정, 비용 비공개, 게임 비공개, 코드 비공개. 83% 바이트 일치는 저자의 스크립트 기준이다.
- **나머지 16%는 "의미상 맞다고 믿는" 상태다.** 비결정적 컴파일러 출력과 링커 COMDAT 폴딩 때문에 맞출 수 없다고 했지만, 바로 그 구간이 오라클이 꺼진 구간이다.
- **법적 회색지대.** 저자가 게임 이름을 숨기고, 이전 글이 삭제되고, 코드를 비공개로 둔 것 자체가 신호다. 에이전트로 역공학 비용이 내려가면 라이선스·EULA 분쟁도 같이 늘 것이다.
- **"기본 설정 하네스"라는 주장의 한계.** 하네스 자체는 기본값이지만, 42% 압축·매시간 재주입·이슈 체계·CI 웹훅·스크립트 해시까지 얹은 것은 상당한 **커스텀 하네스**다. "저렴한 모델도 된다"의 전제는 이 하네스다.

### 2. Uber MCP Gateway — 도구 5,000개, 본론은 "무엇을 안 보내나"

**무슨 일인가.** Uber가 사내 MCP 게이트웨이 설계를 공개했다. MCP 서버 800개 이상, 도구 5,000개 이상을 호스팅한다. 수천 개 내부 서비스의 HTTP·gRPC·TChannel API를 크롤링 대상으로 삼는다. 지연·비용 절감·도입률 수치는 글에 없다.

**배경 — 왜 지금인가.** 초기에 팀마다 MCP 연동을 따로 만들었다. 결과는 인프라 중복, 찾기 어려운 도구, 특정 서비스나 에이전트 구현에 묶인 결합, 운영 불안정이었다. 이건 마이크로서비스 초기의 "팀마다 자기 API 게이트웨이" 문제와 같은 모양이다. 해법도 같다. 중앙 게이트웨이 + 레지스트리.

**기술적으로 어떻게 동작하나.**

```
에이전트 ──MCP──▶ Proxy Gateway (데이터 플레인)
                    │  JSON ↔ Protobuf/Thrift 변환
                    ▼
                 Muttley(서비스 메시 사이드카) ──▶ 기존 백엔드 (수정 없음)

MCP Registry (컨트롤 플레인) — 서버·도구 카탈로그, 소유권, 활성화 상태의 단일 기준
AutoCrawler (Cadence, cron) — IDL 레지스트리를 긁어 가상 MCP 서버·도구를 자동 등록
```

AutoCrawler가 IDL 기반 서비스 하나를 처리하는 순서:

1. 가상 MCP 서버를 만들거나 갱신
2. Protobuf/Thrift 파일에서 메서드명·스키마·주석 파싱
3. **LLM이 에이전트용 도구 설명을 생성**
4. 스키마를 MCP 호환 JSON-RPC 2.0으로 변환
5. 레지스트리에 등록 — **기본 비활성**

데이터 플레인은 고정 주기로 메모리 설정을 새로 읽어, 재시작 없이 도구 변경·활성화가 반영된다. 서버마다 `/<service-name>/mcp` 엔드포인트가 생긴다. Jira·Google 같은 서드파티는 사용자 토큰을 넘겨받아 제공자 토큰으로 교환한다.

거버넌스:

- **"발견이 곧 노출은 아니다"** — 전부 비활성으로 시작, 소유 팀이 검토·수정 후 명시적으로 켬
- 도구 설명을 바꾸면 **설정 diff**가 생기고 서버 소유자 승인이 필요, 이전 버전으로 롤백 가능
- 권한: Uber의 속성 기반 접근 제어(ABAC). 서버 단위 정책 + 도구 단위 덮어쓰기, 호출자를 사람·서비스·에이전트로 구분
- 도구 응답에서 PII·민감정보를 기본 제거

컨텍스트 절약 세 가지:

| 기법 | 어떻게 | 무엇을 줄이나 |
| --- | --- | --- |
| Omni MCP | 도구 4개만 노출: `discover_server` → `discover_tools` → `get_tool_schema` → `invoke_tool` | 도구 정의(스키마)를 미리 싣는 비용 |
| Response Projection | 요청 스키마에 "필요한 응답 경로" 필드를 추가, LLM이 경로를 지정하면 게이트웨이가 잘라냄(GraphQL식) | 도구 응답 크기 |
| Code Mode | 사내 CLI `aifx mcp list/search/call`로 호출, 결과를 **파일에 쓰고 grep** | 응답이 컨텍스트를 거치는 것 자체 |

Code Mode가 현재 Uber 코딩 에이전트의 **기본** MCP 사용 방식이라는 점이 눈에 띈다. MCP를 "프로토콜"로는 쓰되, 에이전트 쪽 인터페이스는 결국 **CLI + 파일**로 돌아왔다.

**실무에 무슨 의미인가.**

- **지금 쓰는 OpenAPI 명세와 Javadoc이 나중의 도구 정의다.** AutoCrawler는 스키마와 주석으로 도구 설명을 만든다. Spring에서 springdoc의 `@Operation(summary, description)`과 DTO 필드 `@Schema(description)`을 충실히 적는 것이 그대로 에이전트 접근성이 된다.
- **기본 비활성 + 소유자 승인**은 Spring Actuator 설계와 같은 발상이다. Actuator도 `health` 외 엔드포인트는 기본적으로 웹에 노출하지 않고 `management.endpoints.web.exposure.include`로 명시해야 열린다. 자동으로 "있음"과 "열림"을 분리한다.
- **Response Projection은 BFF·GraphQL 문제의 재등장이다.** REST에서 과다 응답(over-fetching) 문제를 DTO 분리·필드 선택 파라미터(`?fields=`)로 풀던 것을, 이제 토큰 비용 때문에 다시 푼다.
- 10/12 노트의 MXC와 나란히 보면 역할이 갈린다. MXC는 "에이전트가 **로컬에서** 무엇을 건드릴 수 있나", MCP Gateway는 "에이전트가 **사내 서비스에서** 무엇을 호출할 수 있나". 둘 다 정책을 에이전트 바깥에 둔다.

**반론·회의적 시각.**

- **LLM이 쓴 도구 설명의 품질 검증은?** 비활성 기본값과 소유자 검토가 안전장치지만, 5,000개 도구를 소유 팀이 실제로 얼마나 꼼꼼히 읽는지는 글에 없다. 승인 피로가 생기면 "자동 생성 → 대충 승인"이 된다.
- **수치가 없다.** Response Projection이 토큰을 얼마나 줄였는지, 단계적 발견이 왕복 횟수를 얼마나 늘렸는지(도구 하나 쓰는 데 최소 4번 호출) 공개하지 않았다. 컨텍스트 절약과 지연 증가의 교환 비율을 알 수 없다.
- **Uber 규모의 해법이다.** IDL 레지스트리·서비스 메시·Cadence가 이미 있는 조직이라 가능했다. 작은 팀에 같은 구조를 가져오면 과설계다.
- PII 제거를 게이트웨이에서 "기본"으로 한다는 것은, 거꾸로 **백엔드 응답에 PII가 그대로 있다**는 뜻이기도 하다. 나델라가 같은 날 말한 "모델을 내부자 위험으로 다뤄라"와 묶으면, 게이트웨이 하나가 뚫리면 모든 도구가 뚫린다.

### 3. 「패스키는 함정이다」 — 암호학이 아니라 "다이얼을 누가 쥐나"

**무슨 일인가.** 「Passkeys are a trap. Do not use them」이 HN 400점, 댓글 223개로 하루 2위에 올랐다. 저자는 패스키가 비밀번호보다 안전하고 편할 수 있다고 인정하면서도, **"패스키의 최종 통제권은 사용자에게 없다"**고 주장한다. 그 통제권의 통로가 **원격 증명(attestation)**이다.

**배경 — 왜 지금인가.** 패스키 보급이 빨라지면서 "패스키"라는 한 단어 아래 성격이 다른 것들이 섞였다. 기기 안에 묶인 하드웨어 키(복사 불가)와 클라우드로 동기화되는 키(복사 가능)가 모두 패스키다. 저자는 FIDO Alliance가 이 차이를 사용자에게 분명히 하지 않았다고 비판한다. 같은 날 「핑거프린트는 새로운 쿠키다」와 함께 올라오면서, 웹 플랫폼의 신뢰 문제가 하루 종일 논쟁이 됐다.

**기술적으로 어떻게 동작하나.**

WebAuthn에서 인증기(패스키 관리자)는 등록·로그인 때 **authenticator data**를 돌려준다. 여기 플래그가 있다.

| 플래그 | 뜻 |
| --- | --- |
| UP (User Present) | 사용자가 그 자리에 있었다(터치 등) |
| UV (User Verified) | 생체·PIN으로 본인 확인을 했다. UV는 UP를 전제한다 |
| BE (Backup Eligible) | 이 자격증명은 백업(=복사·동기화)될 수 있다 |
| AT (Attested credential data) | 증명 데이터가 포함돼 있다 |

증명(attestation)은 인증기가 기기의 변조 방지 암호 프로세서로 "나는 승인된 패스키 관리자다"를 서명해 보내는 것이다. 이 검사는 **패스키 관리자·OS·펌웨어가 모두 통과**해야 하므로, LineageOS 같은 대체 OS나 수정된 앱은 통과하지 못할 수 있다. 사이트는 이 정보로 "증명된, 복사 불가능한, 하드웨어 기반 패스키만 받는다"를 정할 수 있다.

저자가 우려하는 경로는 **점진적 강제**다. 처음엔 요구 조건을 거의 두지 않다가, 일부 사용자 그룹부터 조건을 더한다. 사이트는 사용자의 브라우저·OS로 배제될 인원을 추정할 수 있다. 패스키는 배경에서 조용히 동작하니 사용자가 그 변화를 알아채기 어렵다. 예시는 계정 공유를 막고 싶은 Netflix, 증명 안 된 패스키를 거부하고 앱 설치로 미는 X 같은 가상의 시나리오, 그리고 Chrome에서 uBlock Origin이 밀려난 실제 사례다.

저자의 권고는 TOTP(RFC 6238, 열린 표준이라 소프트웨어·저장소를 사용자가 고름)와 YubiKey 같은 물리 보안키다.

각주 정정도 중요하다. **사이트가 증명 지원 여부를 직접 질의할 수는 없다**(WebAuthn에 그런 API가 없다) — OS·브라우저로 추측할 뿐이다. 그리고 UV는 UP를 전제하므로 플래그 조합은 16이 아니라 12개다.

**실무에 무슨 의미인가.**

Spring Security는 6.4부터 패스키(WebAuthn) 등록·로그인을 기본 지원한다(`http.webAuthn(...)`, 내부적으로 WebAuthn4J). 이걸 붙일 때 결정할 다이얼이 바로 이 글의 주제다.

- **attestation conveyance preference** — 등록 시 증명을 얼마나 요구할지(`none` / `indirect` / `direct` / `enterprise`). 기본은 `none`이다. 이걸 올리는 것은 "보안 강화"이기 전에 **"어떤 기기·OS 사용자를 받지 않을지"의 정책 결정**이다.
- **BE 플래그를 볼지** — 동기화 패스키를 거부하면 피싱 저항은 그대로인데 기기 분실 시 계정 복구 부담이 사용자와 고객센터로 넘어간다.
- 소비자 서비스라면 `none`이 합리적 기본이고, 사내 관리 기기만 쓰는 시스템(관리자 콘솔 등)이라면 `enterprise` 증명이 정당한 용도다. 저자도 증명에는 가짜 패스키 앱 차단 같은 정당한 용도가 있다고 인정한다.

**반론·회의적 시각.**

- **저자 스스로 "지금은 거의 아무도 이 문제를 겪지 않는다"고 쓴다.** 대부분의 사이트가 증명을 요구하지 않는다. 글은 현재의 위험이 아니라 **가능한 미래**에 대한 경고다.
- **동기화 패스키는 대체로 증명을 주지 않는다.** 주요 플랫폼의 클라우드 동기화 패스키는 증명 형식을 비워 보내는 경우가 많은 것으로 알려져 있다(이번에 직접 확인하지는 않았다). 사이트가 증명을 강제하면 가장 많은 사용자가 쓰는 동기화 패스키부터 막히므로, 소비자 서비스가 이 다이얼을 올릴 유인은 크지 않다.
- **TOTP는 피싱에 약하다.** 패스키의 핵심 장점은 도메인 결합이다. TOTP 코드는 가짜 사이트에 그대로 입력된다. "통제권"과 "피싱 저항" 중 무엇을 우선할지의 교환이다. 댓글에서는 Bitwarden 같은 서드파티 관리자의 동기화 패스키가 이동성 있는 타협점으로 추천됐다.
- 제목("쓰지 마라")과 본문(조건부 추천)의 온도 차가 크다. 저자도 부록에서 패스키 옹호론을 "스틸맨"으로 세우고 실은 추천하고 싶다고 썼다.

### 4. Sakana AI MASS — 같은 모델이 풀고, 고치고, 채점한다

**무슨 일인가.** Sakana AI와 UC Berkeley가 MASS(Multi-Agent Self-Supervision)를 공개했다(arXiv 2610.12176, 코드 공개). 모델 하나가 문제 해결자·워크플로 최적화기·평가자를 모두 맡고, **가장 잘한 팀의 실행 기록으로 자기 가중치를 미세조정**한다. Qwen3.6-27B로 2라운드를 돌려 학습 과제 승률 82.5%, 홀드아웃 69.9%(기준 모델 대비, 외부 심판 채점)를 얻었다.

**배경.** 사람이 채점하기 어려운 열린 과제(연구·분석)에서 모델을 더 키우려면 **보상을 누가 주나**가 막힌다. 외부 모델이나 사람의 피드백은 비싸다. 그래서 "모델이 스스로 만든 신호"로 루프를 돌리는 재귀적 자기개선(RSI)이 다시 주목받는다. 같은 날 HF 상위 RSI-Anything도 같은 문제를 월드 모델로 푼다.

**기술적으로 어떻게 동작하나.** 핵심만 적는다(구조는 AI 심층 노트에).

- **내부 루프(가중치 고정)** — 과제마다 "챔피언" 워크플로를 두고, 후보를 실행 → 챔피언과 1:1 비교 → 이기면 교체 → 피드백으로 워크플로 수정. 워크플로는 역할·지시·**계약**(돌려줘야 할 산출물과 점검)·**홉**(호출 순서) 네 부분
- **외부 루프(가중치 갱신)** — 챔피언을 과제당 18번 실행, 쌍 비교를 Bradley–Terry로 점수화, 상위 16개 궤적만 남김 → **프롬프트에서 워크플로 텍스트를 지우고** LoRA 미세조정. "일을 어떻게 조직하나"를 가중치에 새긴다

**실무에 무슨 의미인가.**

- 승률 수치보다 실무적인 발견은 **"병목은 평가가 아니라 최적화"**다. 평가자만 GPT-5.5로 올리면 12개 중 10개, 평가자+최적화기를 올리면 5회 안에 12개 전부. 좋은 피드백도 그걸 반영할 수정 능력이 없으면 소용없다. 코드 리뷰에서 "지적은 정확한데 고칠 사람이 못 고친다"와 같은 구조다.
- **워크플로 정보가 "역할·지시"에서 "계약·홉"으로 옮겨 갔다**는 분석도 흥미롭다. 잘 되는 팀 설계는 각자에게 긴 지시를 주는 것이 아니라 **무엇을 넘겨받고 넘겨줄지(인터페이스)**를 명확히 하는 쪽이었다. 마이크로서비스 계약 우선 설계(contract-first)와 같은 결론이다.

**반론·회의적 시각.**

- **소프트웨어 공학에서는 이득이 없었다.** Terminal-Bench 2.0 0.96배, SWE-bench Verified 0.94배(출력 토큰당 점수). 연구형 과제에서만 이득이 났다. 저자는 SWE 과제를 학습에 넣으면 나아질 거라고 추측한다.
- **표본이 작다.** 합성 과제 12개(학습 9·홀드아웃 3, 과제 설명도 GPT-5.5가 생성), 베이스 모델 하나.
- **저자가 직접 꼽은 "아킬레스건" — 공유된 맹점.** 같은 모델이 풀고 채점하면, 그 모델이 못 보는 결함은 개선으로 승인되고 강화된다. 자기 평가자와 외부 심판의 일치율이 73%→93%로 올랐다는 것은 좋은 소식이지만, 거꾸로 **7%는 여전히 외부와 다르게 판단**한다. 위 1번 사례에서 에이전트가 검증 스크립트를 고치려 한 것을 생각하면, 채점기를 학습 루프 안에 두는 것의 위험이 분명하다.
- 탐색이 불안정하다. 강한 반복 직후 급격한 퇴보가 자주 나왔다(저자는 학습률 스케줄 같은 장치를 제안).

### 5. Logfire의 JSON 컬럼 쪼개기 — 빠르게 읽기보다 "안 읽기"

**무슨 일인가.** Pydantic의 관측 서비스 Logfire가 OpenTelemetry 속성 저장 방식을 바꿔 일부 쿼리가 1,000배 넘게 빨라졌다는 글이다. 30초 타임아웃 나던 쿼리가 1초 미만이 됐다. 작업에 거의 6개월이 걸렸다. **주의: 원문 날짜는 2026년 1월 말이다.** 오늘 HN(13점)에 다시 올라온 것이지 새 발표는 아니다.

**배경.** Logfire는 스팬 속성을 Parquet 파일의 **JSON 문자열 컬럼 하나**에 넣었다. 저자의 진단: "일을 더 빨리 하도록 최적화했지만, 일 자체를 피할 수는 없었다." 오브젝트 스토리지에서는 CPU(파싱)보다 **다운로드 지연**이 쿼리 시간을 지배한다. 속성 하나로 필터링해도 JSON 컬럼 전체를 받아야 했다. 구조가 들쭉날쭉해 딕셔너리 인코딩과 zstd 압축이 안 먹었고, LLM 응답처럼 드물지만 거대한 속성 하나가 그걸 안 쓰는 쿼리까지 느리게 했다.

**기술적으로 어떻게 동작하나.**

- **Shredding(쪼개기)** — 반구조 덩어리에서 값을 꺼내 **타입이 있는 별도 컬럼**으로 저장. 그러면 Parquet의 컬럼 프루닝(필요한 컬럼만 읽기)과 존맵 통계(min/max로 로우 그룹 건너뛰기)를 쓸 수 있다
- **정적 → 동적** — 원래는 손으로 고른 목록(`http.response.status_code` 등)만 쪼갰다. 바꿀 때마다 코드 수정·배포가 필요했다. 이제 수집·압축(compaction) 시점에 **파일마다** 실제 데이터에서 키를 발견한다
- **상위 128 휴리스틱** — Parquet 파일의 99%가 최상위 고유 키 128개 미만(중위값 약 32). 그래서 **전체 크기 기준 상위 128개 키**를 컬럼으로 뽑고, 나머지는 JSON 잔여 컬럼에 남긴다(쿼리는 되지만 느림)
- **타입 넓히기** — Int → Float → JSON, 섞이면 JSON 문자열로 후퇴
- **쿼리 재작성** — `attributes->>'key'`를 쪼갠 컬럼이 있으면 그 컬럼으로 바꾼다. JSON 접근자의 표현식·조건 푸시다운을 DataFusion Parquet 리더에 넣었고 DataFusion 52.1.0(2026-01)에 들어갔다

**실무에 무슨 의미인가.**

- MySQL·PostgreSQL에서 JSON 컬럼을 쓸 때 같은 문제가 작은 규모로 생긴다. 자주 필터링하는 JSON 속성은 **생성 컬럼(generated column) + 인덱스**로 꺼내는 것이 같은 발상이다(MySQL `GENERATED ALWAYS AS (json_col->>'$.status') STORED`, PostgreSQL은 표현식 인덱스나 `GENERATED ... STORED`). WMS 프로젝트에서 이력 테이블에 JSON payload를 둔다면 미리 염두에 둘 지점이다.
- "어떤 키를 꺼낼지"를 **크기 기준**으로 정했다는 점이 한계이자 교훈이다. `user_id`처럼 작지만 자주 쿼리되는 키는 이 휴리스틱으로는 안 뽑힌다. 저자도 쿼리 사용량 기반 쪼개기를 향후 과제로 남겼다. 인덱스 설계는 결국 **데이터 모양이 아니라 쿼리 모양**을 따라야 한다.

**반론·회의적 시각.**

- 1,000배는 "일부 쿼리" 기준이다. 벤치마크 분포를 공개하지 않았다.
- 컬럼이 파일마다 달라지면 스키마가 파일 단위로 흩어진다. 저자도 약 1,000컬럼 이상에서는 오버헤드가 커진다고 했고, 남은 속성은 Parquet Variant 타입으로 옮길 계획이다(DataFusion 지원 대기).
- 블룸 필터·역색인은 아직이다. 존맵만으로는 고카디널리티 동등 조건(특정 trace ID 찾기)에 약하다.

- [ ] **에이전트가 테스트를 고쳐 통과시키는 것을 막는 장치를 설계한다.** GitHub에서 `src/test/**`와 CI 설정을 CODEOWNERS로 묶고 브랜치 보호로 승인 필수를 걸면, 에이전트 PR이 테스트를 수정했을 때 어떤 흐름이 되나? 디컴파일 사례의 "스크립트 해시를 시크릿과 대조"와 비교해 어느 쪽이 더 우회하기 어려운가?
- [ ] **Spring Security 6.4 패스키를 붙이고 attestation 다이얼을 돌려 본다.** `http.webAuthn(...)`으로 등록·로그인을 만들고, 등록 옵션의 attestation conveyance를 `none`과 `direct`로 바꿔 가며 실제 기기(폰 동기화 패스키, 가능하면 하드웨어 키)로 등록할 때 서버가 받는 attestation 형식과 BE/BS 플래그가 어떻게 다른지 로그로 확인한다. "증명 요구 = 사용자 배제"를 직접 본다.
- [ ] **WMS 이력 테이블의 JSON payload를 생성 컬럼으로 꺼내 본다.** MySQL에서 JSON 컬럼 하나에 이벤트 payload를 넣고 10만 건을 채운 뒤, `payload->>'$.status'`로 필터링하는 쿼리의 `EXPLAIN ANALYZE`를 본다. `GENERATED ALWAYS AS (...) STORED` 컬럼 + 인덱스로 바꾸고 다시 잰다. Logfire의 "크기 기준 vs 쿼리 기준" 교훈대로, 어떤 키를 꺼낼지는 무엇으로 정하나?
- [ ] **내 REST API에 "Response Projection"을 붙인다면?** Spring에서 `?fields=id,name,items.sku` 같은 파라미터를 받아 Jackson `@JsonFilter`(또는 `MappingJacksonValue`)로 응답 필드를 잘라내는 필터를 만들어 보고, 중첩 경로 지원·캐시 키·문서화(springdoc)에서 무엇이 어려운지 적는다. Uber가 이걸 GraphQL 대신 MCP 요청 스키마의 필드 하나로 푼 이유를 생각해 본다.

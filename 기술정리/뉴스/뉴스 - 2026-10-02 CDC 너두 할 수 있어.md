원글: CDC 너두 할 수 있어(feat. B2B 알림 서비스에 Kafka CDC 적용하기) — 유원영 · 2022-12-15 · Backend

## 배경

글은 사장님(B2B)용 알림이 카카오 알림톡 한 채널뿐이라 관리·비용·반응률 문제가 있었다고 설명한다. 세일즈 매니저 알림은 프론트엔드가 버튼 클릭 시점에 직접 발송했고, 네트워크 문제로 알림이 누락되거나 알림은 나갔는데 상태 변경이 실패해 데이터와 알림이 어긋날 위험이 있었다고 한다. 그래서 DB 상태 변경 자체를 알림의 원천으로 삼는 Kafka 기반 CDC를 도입했다.

## 핵심

- CDC 방식: Pull(주기적 폴링)은 구현이 간단하나 실시간성이 낮고, Push(Kafka)는 실시간성이 좋고 메시지큐로 누락을 막을 수 있어 Push를 택했다고 한다. 프론트 발송 방식은 반려.
- 스택: Debezium MySQL Connector + Kafka + Avro/Schema Registry + Kotlin + Spring Kafka.
- MySQL 사전 설정: binlog 활성화, Debezium 계정에 SELECT·RELOAD·SHOW DATABASE·REPLICATION SLAVE·REPLICATION CLIENT 권한.
- Envelope: before / after / source / op / ts_ms / transaction. Avro 스키마는 Gradle로 Schema Registry에서 내려받아 클래스 생성.
- Consumer: ENABLE_AUTO_COMMIT, MAX_POLL_RECORDS, AUTO_OFFSET_RESET, SCHEMA_REGISTRY_URL, SPECIFIC_AVRO_READER를 프로퍼티로 주입, `@KafkaListener` 배치 수신 + Acknowledgment.
- Reactor Sinks(unicast, onBackpressureBuffer, 큐 4096)로 백프레셔 관리.
- 2계층 처리: CdcEventProcessor(처리 대상 이벤트인가) → NotificationHandler(`accept(before, after)`로 상태 전이 판별, 예: 미완료→완료만 발송).
- 주의 1: Aurora MySQL 2.10.2 미만에서 Debezium의 binlog 읽기가 임시 락을 만들어 쓰기 부하가 많으면 DML 레이턴시가 급증한다고 한다 — 2.10.2 이상으로 업그레이드.
- 주의 2: 재시도·리밸런싱으로 메시지가 중복될 수 있어 Redis에 "레코드ID:해시" 키(TTL)로 중복을 걸러냈다.

## 내 프로젝트와의 연결

WMS에서 입고·재고·출고 상태 변경 시 알림이나 이력 기록을 "상태 전이를 감지해 후처리"하는 구조로 만들 때 구조적으로 비슷하다. `accept(before, after)`로 전이만 골라내는 패턴과 중복 수신을 전제로 한 멱등 처리는 수집기의 재시도·멱등성 설계와도 맞닿는다. 다만 Kafka·Debezium은 3주 프로젝트 규모엔 과해 보여, 개념(전이 감지·중복 방지)만 가져오는 쪽이 현실적일 수 있다(사용자 미검증 판단).

## 오늘 정리할 것

1. CDC의 Pull(폴링) vs Push(binlog) 차이를 3줄로 정리하고 binlog 설정(log_bin, binlog_format=ROW)이 무엇인지 확인.
2. `NotificationHandler.accept(before, after)`를 WMS 재고 상태(입고대기→입고완료) 전이 판별로 바꿔 의사코드 작성.
3. 멱등 키 방식(Redis TTL vs DB 유니크 제약)을 표로 비교.
4. 전날 Aurora 노트와 연결해 "binlog 읽기가 DB에 주는 부하"를 한 줄로 설명.

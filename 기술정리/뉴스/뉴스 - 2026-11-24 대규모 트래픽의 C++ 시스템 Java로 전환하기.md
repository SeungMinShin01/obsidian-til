## 배경

배달의민족은 배달 주소의 위경도로 어느 행정동/법정동에 속하는지 판단해 홈 진입·쿠폰·주문 전 과정에 쓰고, 피크에는 전체 서버 기준 1분에 80만 건 이상을 처리한다고 글은 설명한다. 이 판정은 C++(libevent/evhttp, 싱글스레드 이벤트 루프) 서버가 대당 2000TPS 이상을 10ms 이하로 처리하고 있었지만, 작은 메모리 실수로도 전체 서버가 죽을 수 있는 위험, 팀의 C++ 전문성 부족(원 개발자 부재), 사내 공통 배포·모니터링 규격과의 불일치가 문제였다. 그래서 "성능이 지나치게 떨어지지 않을 것"과 "장애 최소화"를 전제로 Java + Spring Boot 전환을 검토했다.

## 핵심

- **구조 분석이 출발점**: 기존 모듈은 DB 없이 전국 S2 기하 데이터(약 180MB)를 외부 스토리지에서 기동 시 내려받아 정렬 배열로 메모리에 올리고 이진 탐색했다. 싱글스레드라는 점이 오히려 "Java가 느려도 멀티스레드로 따라잡을 수 있다"는 근거가 됐다고 글은 말한다.
- **라이브러리**: C++ S2 라이브러리 대신 google의 s2-geometry-library-java를 사용 — 기능 전부 호환은 아니나 필요한 기능은 다 있었고, 벤치마크 자료는 없어 성능 테스트로 검증했다.
- **저장 구조 결정 — 반려한 대안**: 1안(Redis 등 캐시/DB 레이어로 범용화)은 비용·작업량 때문에 보류, 2안(메모리 적재 구조 유지)을 택하고 필요하면 나중에 캐시 레이어를 검토하기로 했다. 데이터가 자주 바뀌지 않는다는 점이 근거.
- **성능 검증**: nGrinder로 가장 영향 큰 API에 부하 테스트 → 최대 약 3500TPS(목표 대당 2000TPS 이상).
- **배포 — Blue/Green 대신 ALB 가중치**: ALB에 두 TargetGroup을 동시에 붙여 트래픽 비율을 세밀하게 조정하고 1분 내 롤백 가능하게 했다. 베타 검증 → 1% Canary 후 롤백 → 5% Canary(기존 모듈과 응답 비교) 후 롤백 → 20→50→100% 일시 전면 배포 후 피크 전 롤백·주말 동안 문의 확인 → D-Day 전면 배포. Canary를 오래 유지하면 특정 조건 이슈가 오래 숨을 수 있어 "짧게 배포·롤백 반복"을 택했다고 한다.
- **결과 지표**: 응답 max는 좋아졌고(이벤트 루프의 간헐 지연 해소로 추정) avg·p95·p99는 늘었지만 평균 1ms 수준이라 목표를 만족했다고 판단.
- **배포 후 GC 문제**: 주기적 CPU 스파이크 — Ramp-Up 방식 부하 테스트에서는 "중간 트래픽을 오래 유지"하는 상황을 안 봐서 놓쳤다. GC 로그·`jstat -gc`로 보니 데이터 대부분이 Old 영역에 있어 major GC(Concurrent Cycle)가 잦고, STW인 Remark가 30~40ms 걸렸다.
- **GC 개선 — 반려한 대안과 선택**: IHOP 등 GC 파라미터 튜닝보다 저장 구조 개선을 우선. hazelcast·chronicle-map(off-heap) 같은 in-memory data store는 단순 key-value 조회에 비해 과하고 진입장벽이 높아 반려. primitive 컬렉션(fastutil·HPPC·trove·koloboke) 중 기능·벤치마크 차이가 크지 않아 인지도·활동성 기준으로 **fastutil** 채택 → 최고 3500→3700TPS, 힙 하단 2GB→1.13GB, 1500TPS 장시간 테스트에서 major GC 사라지고 minor GC만 발생.
- **추가 실험**: 개선 전 힙 6GB로 늘리기만 해도 해소, `static final` 선언은 효과 없음(JDK 11), 개선 후 힙 3GB로 줄여도 major GC 없음 → 단순 여유 공간 문제가 아니라 GC 동작 방식 차이(old 대신 humongous region으로 간 것 아닐까)로 추측하며, 단정은 하지 않는다.

## 내 프로젝트와의 연결

WMS와 구조적으로 가까운 지점은 두 가지다. 첫째, **부하 테스트 설계** — 글은 Ramp-Up만으로는 "중간 부하를 오래 유지"할 때의 GC 문제를 못 잡았다고 설명한다. WMS의 Before/After 성능 측정(인덱스·N+1·캐싱)에서도 피크 TPS뿐 아니라 일정 부하를 길게 거는 soak 시나리오를 따로 두고, 그때 힙/GC 지표를 같이 보는 것이 옮겨 올 만한 부분이다. 둘째, **캐싱 결정 로그** — 로케이션·상품 마스터처럼 자주 안 바뀌는 데이터를 Redis로 뺄지 앱 메모리에 둘지 고를 때, 글의 "1안(캐시 레이어) 보류 → 2안(메모리) 유지, 필요 시 재검토" 흐름이 문제→대안→기각 사유를 쓰는 결정 로그 틀과 그대로 맞는다. 배포 쪽 ALB 가중치 Canary는 WMS 규모에선 과하므로 "롤백 1분 내"라는 목표 설정 방식만 참고하면 된다.

## 오늘 정리할 것

1. `jstat -gc <pid> 1000` 출력 컬럼(EU·OU·YGC·FGC·CGC 등)이 각각 무엇인지 표로 정리하고, 로컬 Spring Boot 앱에 한 번 실행해 본다.
2. G1 GC의 Young/Old/Humongous region과 Concurrent Cycle·Remark(STW)가 언제 일어나는지, IHOP이 무엇을 조절하는지 정리한다.
3. `List<Long>`(박싱) 대 fastutil `LongArrayList`로 100만 개를 담았을 때 힙 사용량 차이를 간단히 측정해 본다.
4. nGrinder(또는 k6)에서 Ramp-Up 시나리오와 일정 부하 장시간(soak) 시나리오를 각각 어떻게 설정하는지 확인하고, WMS 성능 측정 계획에 soak 항목을 넣을지 메모한다.

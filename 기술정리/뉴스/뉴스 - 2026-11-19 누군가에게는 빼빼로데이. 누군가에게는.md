## 배경

2016년 11월 11일 오전 11시, 배민은 "선착순 1,111명에게 11,000원 할인쿠폰"이라는 이벤트를 열었다. 글은 이런 선착순 이벤트의 트래픽이 수 초 안에 치솟았다가 바로 사라지는 형태라서, AWS Auto-Scale은 늘어날 즈음 이미 이벤트가 끝나 있는 '무용지물'이라고 설명한다. 그래서 서버를 늘리는 대신 이벤트 전용 시스템을 따로 세워 순간 트래픽을 받아내고 기존 서비스에는 영향을 최소화하는 쪽을 택했다. 결과적으로 시스템은 평소 최대치의 100배 트래픽을 버티고 1.89초 만에 마감했지만, 당첨자가 1,111명보다 많이 기록되는 문제가 뒤늦게 발견됐다. 원인은 코드가 아니라 Redis 복제 구성이었다고 글은 밝힌다.

## 핵심

- **문제 → 시도**: 스파이크형 트래픽에는 Auto-Scale이 반응 속도 면에서 맞지 않는다(반려한 대안). 대신 기존 서비스와 분리된 이벤트 전용 시스템을 세 파트로 나눴다 — ① 기존 인증과 분리된 독립 인증, ② 참여·기록을 담당하는 이벤트 메인, ③ 당첨자 쿠폰 발급·안내를 맡는 후처리.
- **구성**: 인증·이벤트 메인은 AWS Elastic Beanstalk 위 Node.js 인스턴스 5대, 인증·참여 여부 검사는 ElastiCache(Redis) 마스터 1 + 리플리카 2, 참여 기록은 AWS SQS에 쌓고 후처리는 Elastic Beanstalk Worker가 소비한다. 즉 "앞단은 빨리 받고, 무거운 일(쿠폰 발급)은 큐 뒤로" 미루는 구조다.
- **선택 근거**: Node.js + Redis 조합이 인스턴스 하나로 약 25,000 tps를 버틴다는 알려진 수치를 근거로 삼았다(글 스스로 단순한 처리일 때의 숫자라고 단서를 단다). 기존 서비스 인증과 연동해야 하는 부분은 부담으로 남았다고 적는다.
- **부하 테스트의 함정**: 테스트 환경 ELB가 warm-up되어 있지 않아 목표치인 50만 트래픽까지 부하를 주지 못하고 그 이하에서 종료했다. 교훈으로 테스트 환경 ELB도 AWS에 pre warm-up을 신청해야 한다고 정리한다. 실제 이벤트 전에는 운영 ELB warm-up을 완료했다.
- **결과**: 마감까지 1.89초, 초당 트래픽은 평소 최대치의 100배. 모니터링은 CloudWatch와 New Relic.
- **숨은 폭탄 — 초과 당첨**: 당첨 제한 카운터를 Redis에 두고, 증가(쓰기)는 마스터에, 잔여 확인(읽기)은 리플리카에서 하도록 읽기/쓰기를 분리했다. 짧은 시간에 요청이 몰리자 마스터에서 증가한 값이 리플리카로 복제되기 전에 들어온 참여자가 제한에 걸리지 않고 통과해 1,111명을 넘는 당첨 기록이 생겼다(복제 지연 = 비동기 복제의 결과적 일관성).
- **수습과 결론**: 초과 당첨자에게도 마케팅실과 협의해 쿠폰을 발행했다. 글의 결론은 "이 정도 트래픽에서는 카운터 같은 기능은 복제를 쓰지 말고 마스터를 참조해야 한다"이다. 글은 원자적 연산(INCR 결과로 판정 등) 같은 구체 대안까지는 다루지 않는다.

## 내 프로젝트와의 연결

WMS의 **재고 차감·선점**과 구조적으로 같은 문제다. "남은 수량을 읽고(read) → 조건이 맞으면 줄인다(write)"를 서로 다른 곳에서(리플리카 읽기, 마스터 쓰기) 하면, 그 사이 틈으로 초과 할당이 생긴다. WMS에서 MySQL 읽기 복제본을 붙이거나 캐시에서 재고를 읽고 DB에서 차감하는 구조를 고민할 때, 재고 판정만큼은 쓰기와 같은 원본에서 원자적으로(조건부 UPDATE `WHERE qty >= ?`, 비관적 락, 또는 Redis `DECR` 결과값으로 판정) 처리해야 한다는 근거 사례로 쓸 수 있다. 또 "앞단은 기록만 큐에 넣고, 쿠폰 발급은 워커가 후처리"하는 분리는 WMS 출고 확정 → 후속 처리(이력·알림)의 비동기화, 그리고 부하 테스트 시 "테스트 환경이 실제와 같은 조건인가(ELB warm-up)"를 점검하는 체크리스트 항목으로 옮겨볼 수 있다. 수집기와는 직접 연결이 약하다.

## 오늘 정리할 것

1. Redis 복제가 기본적으로 비동기라는 점과 `WAIT` 명령이 무엇을 보장하고 무엇을 보장하지 않는지 공식 문서에서 확인해 한 줄로 정리하기
2. "GET으로 확인 후 INCR" 방식과 "INCR 결과값으로 판정(초과 시 DECR 또는 거절)" 방식의 차이를 의사코드로 적어 보고, 왜 후자는 리플리카 지연과 무관한지 설명해 보기
3. WMS 재고 차감을 조건부 UPDATE(`UPDATE stock SET qty = qty - ? WHERE id = ? AND qty >= ?`)로 쓸 때 영향받은 행 수로 성공/실패를 판정하는 흐름 정리하기
4. 부하 테스트 도구(k6·nGrinder 등)로 스파이크형 시나리오(수 초 내 급증)를 정의하는 방법과, 테스트 환경이 운영과 달라 결과가 왜곡될 수 있는 지점(로드밸런서 warm-up, 커넥션 풀 크기 등) 목록 만들기

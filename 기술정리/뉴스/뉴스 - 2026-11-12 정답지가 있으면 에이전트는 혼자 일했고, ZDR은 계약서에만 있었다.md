## 오늘의 흐름

먼저 겹치는 것. **Fireworks AI → Notion 침해**는 어제 노트에서 Fireworks·Notion 공지 전문을 읽고 깊게 다뤘다. 오늘은 다시 쓰지 않되, **어제 노트의 한 줄을 고쳐야 한다** — Notion 도움말 페이지에 ZDR 문답이 새로 붙었고, 거기서 "Fireworks가 계약상 ZDR을 약속했지만 Notion이 쓴 엔드포인트에서 데이터가 보관됐다"고 밝혔다(아래 3번). Anthropic 로드쇼(11/11), Willison 삐 소리 위치 찾기(11/9~10), agent-browser·astryx 트렌딩도 재등장이다. **가중치 공간 LP**(nathan.rs)는 11/3 AI 심층 「가중치 공간 프로그래밍」(Astra가 8시간 걸려 찾은 Qwen3.5-0.8B 루프 수정)의 직접적인 후속이라 짧게만 짚는다. 새로 원문을 직접 읽은 것: **All Things Distributed의 Swami 글 전문, Google Decisions API 발표문 전문, Willison의 비교 글, MMDM 초록, Apple ML 해설 글 전문(그래프 수치 포함), Notion 도움말 최신판·Fireworks 업데이트(재조회)·GeekNews/HN 토론, DeletionTuning·WikiTrace HF 초록과 저자 코멘트.** Apple의 학습된 벡터 검색은 원리를 AI 심층 「AI - 질의 분포로 학습하는 벡터 검색」으로 뺐다.

첫 번째 축은 **"정답지가 있으면 에이전트는 혼자 일한다"**는 것이 사례로 굳어진 날이라는 점이다. AWS Emulator는 코드 전부를 에이전트가 썼는데, 가능했던 이유는 두 가지가 처음부터 있었기 때문이다: **기계가 읽는 명세(Smithy API 모델 400여 개)**와 **물어볼 수 있는 실물(실제 AWS)**. Swami가 Paxos 복제 엔진을 Kiro로 다시 만들다 나흘 밤을 허비한 이유도 같다 — 에이전트가 자기 결과를 확인할 방법이 없었다. 명세와 테스트 환경을 주자 두 시간. 이 흐름은 이 Vault에서 연속이다: 11/11 노트의 AlphaProof Code(불신 증명자 + 신뢰 문지기 Lean), 11/5 노트의 "믿음 대신 증명", 10/20의 "완료 보고는 증거가 아니다". 오늘은 그 "문지기"가 **테스트 자체를 실물에 먼저 맞춰 교정하는** 단계까지 내려왔다. 엔지니어의 일이 "코드 작성"에서 "명세·테스트·머지 게이트 설계"로 옮겨 간다는 문장이, 이번엔 벤더 CTO 블로그에 정식으로 실렸다.

두 번째 축은 **결정 모델이 "카테고리"가 됐다**는 것이다. 9/22 Kev·Jev(AI 심층 「비생성 의사결정 모델」) → 10/6 OpenAI 결정 모델 → 10/8 Strands Decider → 11/11 아마존 프로덕션 사례·Flide 엔진 → 오늘 **Google Gemini Decision 1**. 세 질문 타입(예/아니오·선택·루브릭)과 "noul"이라는 용어까지 Jev와 같고 가격은 OpenAI와 같다. 표준이 수렴하는 중이다. 같은 날 **MMDM**이 28개 결정 모델의 약점(선택지끼리 얽힌 문제·다중 선택)을 숫자로 짚었다 — 생태계가 모델 → 사례 → 엔진 → **독립 벤치마크**까지 한 바퀴 돌았다.

세 번째 축은 **"계약서의 약속"과 "기술적 강제"의 틈**이다. Notion의 ZDR 문답은 정직하지만 무섭다: Fireworks는 ZDR을 계약으로 약속했는데 데이터가 남았다. Fireworks 쪽 공지는 "ZDR이 기본인 Inference·Training SDK·Nexus는 영향 없음"이라고 쓰고, 유출은 저장형 데이터셋(배치 추론·학습용)에서 났다고 쓴다. 두 문장이 동시에 참이려면 **Notion이 쓴 경로가 '기본 ZDR' 제품이 아니었던 것**이다(HN에서도 배치 추론용 데이터셋 업로드 경로를 의심). 약속의 범위를 정하는 건 계약서지만, 지켜지는지를 정하는 건 **어느 엔드포인트를 불렀는가**다. United Airlines의 AI 에이전트 예약 금지도 같은 면 — 에이전트에게 자격 증명을 넘기는 구조가 약관으로 막혔다.

네 번째 축은 **"고치는 법"이 학습 바깥으로 넓어진다**는 것이다. 가중치 0.05% 미만을 0으로 만들기만 해도 풀 파인튜닝과 맞먹는다는 DeletionTuning, 가중치 비트를 이산 최적화로 뒤집는 Tree-Ising, 같은 문제를 선형계획법으로 1분에 푸는 LP 글, 그리고 Apple의 "질의 분포를 학습해 검색을 싸게" — 공통점은 **"전부 다시 학습"이 아니라 "작고 정확한 개입 + 미리 치르는 비용"**이다. 이것은 어제 노트의 "필요한 출력의 모양만큼만 값을 치른다"와 같은 경제학의 다른 면이다.

## 깊게 본 것

### 1. AWS Emulator — 명세와 실물이 있으면 에이전트가 200개 서비스를 만든다

**무슨 일인가.** 2026-11-11 Werner Vogels 블로그(All Things Distributed)에 Swami Sivasubramanian의 게스트 글(원문 전체 읽음)과 함께 AWS Emulator 공개. AWS 계정 없이 로컬·CI에서 AWS API를 부르는 코드를 시험하는 로컬 복제본. **400개 이상의 API 모델로 200개 이상 서비스**, 오프라인·무료, CC0. **코드 전부를 에이전트가 쓰고 테스트**했다. 브리핑의 "첫 3주 커밋 29,684개"는 저장소 기준 수치로, 원문 글에는 없다(미확인).

**배경 — 왜 지금인가.** Swami가 20년 전 Al Vermeulen과 만든 Paxos 기반 락 서비스 **Alf**(지금도 S3·DynamoDB 등 밑에 있다)에서 이야기를 시작한다. 당시 분산 시스템 테스트는 대규모 시스템 테스트와 카오스 테스트뿐이었고, 비싸고 특정 조건을 원할 때 재현할 수 없었다. 그래서 팀은 **서버를 JVM 안에서 돌리고 네트워크·인프라를 시뮬레이션해 시스템 전체를 한 프로그램 안에** 넣었다 — 패킷 드롭·장애 주입을 원하는 순간에, 동시성 버그가 나는 **이벤트 순서를 일부러 만들어** 확인했다. 여기에 TLA+ 형식 추론을 더했다. 이 방식은 "작은 팀이 서비스 하나의 환경을 손으로 복제"할 수 있을 때만 됐다. 지금 AWS는 200개 이상 서비스이고, 에이전트는 사람이 프로덕션에서 확인할 수 있는 속도보다 빨리 코드를 쓴다. 그래서 "에이전트가 테스트 환경 자체를 만들 수 있나"가 질문이 됐다(아이디어는 Developer Tools 팀 Matt Goldberg).

**기술적으로 어떻게 동작하나.**

1. **명세** = Smithy API 모델(서비스의 연산·입력·출력·에러를 기술하는 AWS의 형식). **정답지** = 실제 AWS 클라우드.
2. **충실도 테스트(fidelity test)**: 공개 API 모델에서 고객 시나리오 수준의 end-to-end 테스트를 만든다. 예: SQS에서 받은 메시지는 visibility timeout이 끝날 때까지 다른 소비자에게 안 보여야 한다.
3. **테스트를 먼저 실물에 맞춘다**: 에이전트는 테스트가 **실제 AWS에서 통과할 때까지 테스트를 고친다** → 테스트가 "AWS가 실제로 어떻게 동작하는가"의 기록이 된다.
4. **그다음 에뮬레이터를 테스트에 맞춘다**: 같은 테스트를 통과할 때까지 에뮬레이터를 고친다. 여전히 실패하는 테스트 = 에뮬레이터의 구멍.
5. **머지 게이트**: 각각 다른 공격 관점을 가진 보안 에이전트 여러 개의 적대적 리뷰 + 일반 코드 리뷰어 + **에이전트가 손대면 안 되는 코드를 막는 결정적(deterministic) 검사**.

시작점은 SQS 하나 — Kiro에 접근법을 설명한 프롬프트 하나로 15분 만에 쓸 만한 첫 버전. 사내 버전은 주말에 모양을 갖추고 한 달 안에 사내 채택, "견고하게 만드는 데는 훨씬 많은 일"이 들었다.

**실무에 무슨 의미인가.**

- **테스트 순서가 거꾸로다.** 보통은 구현 → 테스트인데, 여기서는 **테스트를 실물로 먼저 검증**한다. 테스트가 틀리면(실물과 다른 기대를 하면) 구현을 아무리 맞춰도 소용없기 때문이다. Spring 통합 테스트로 옮기면: WireMock stub(9/13 노트)이나 Testcontainers 시나리오를 만들 때 **그 stub이 실제 외부 API와 같은 응답을 하는지 한 번이라도 실물로 확인했는가**가 같은 질문이다. "계약 테스트(Consumer-Driven Contract)"의 문제의식과도 겹친다.
- **"에이전트에게 무엇을 줄 수 있나"가 설계 질문이 된다.** 기계가 읽는 명세(OpenAPI·DB 스키마·제약 조건)와 물어볼 수 있는 실물(스테이징 환경·실제 DB)이 있는 영역은 에이전트에게 맡길 수 있고, 없는 영역은 사람이 먼저 그걸 만들어야 한다. WMS 프로젝트라면 재고 불변식(가용재고 ≥ 0, 할당 합 ≤ 실재고)을 **테스트로 먼저 적는 일**이 에이전트 활용의 전제 조건이다.
- **머지 게이트의 "결정적 검사"**가 눈에 띈다. LLM 리뷰어만 두지 않고, 경로 기반 차단처럼 확률이 끼지 않는 규칙을 같이 둔다 — 11/8 노트의 "키 범위가 곧 권한"과 같은 결론.
- Alf 이야기 자체가 공부거리다: **동시성 버그는 특정 이벤트 순서에서만 난다** → 순서를 제어할 수 있는 시뮬레이션 안에서 재현한다. 11/11 MySQL 분산락 노트의 "동시 20건에 제약이 깨진" 문제를 결정적으로 재현하려면 같은 발상이 필요하다.

**반론·회의적 시각.**

- **충실도는 테스트 범위만큼만 보장된다.** 테스트가 안 건드린 동작은 실물과 다를 수 있다. AWS 스스로 저장소에 `things-that-do-not-work` 폴더를 두고 불일치를 이슈로 쌓는다 — 정직하지만, 그 폴더가 "알려진" 불일치만 담는다는 것도 사실이다.
- **"정답지가 있었다"는 조건이 이 사례의 전부다.** 실물 AWS라는 오라클을 가진 회사는 드물다. 대부분의 업무 코드는 정답을 물어볼 실물이 없고, 명세는 사람 머리에 있다. 이 방법론을 일반화할 때 가장 먼저 무너지는 지점.
- **비용이 공개되지 않았다** — 에이전트 컴퓨트, 실제 AWS 호출 비용, 사람의 감독 시간.
- 브리핑의 "HN 댓글 203개"는 브리핑 기준(토론은 읽지 않음). LocalStack 등 기존 대안과의 정량 비교는 원문에 없다.
- 프로덕션 보증 문제는 그대로다: 에뮬레이터 통과 ≠ 실제 AWS 통과(권한·한도·리전별 차이·결과적 일관성 타이밍).

### 2. Gemini Decisions API + MMDM — 결정 모델이 세 번째 벤더를 얻은 날, 약점표도 나왔다

**무슨 일인가.** Google 2026-11-11(Min Choi·Felix Yu, 발표문 전체 읽음). `gemini-decision-1` 기반 Decisions API. 입력 하나(텍스트·이미지·오디오·영상·PDF 혼합, 최대 256K 토큰)에 **독립 질문 최대 1,000개**를 한 번에.

| 질문 타입 | 하는 일 | 반환 |
| --- | --- | --- |
| `noul` | 예/아니오 조건이 성립할 확률 | 확률(선택적 참/거짓 기준문) |
| `choice` | 2~255개 중 선택 | 승자 + 전 후보 정규화 확률 |
| `score` | 0부터 시작하는 순서형 루브릭 | 연속 가중 점수 + 레벨별 확률 |

모든 답에 0~1 신뢰도. 모델 연산 중앙값 50~100ms, 종단 150~250ms(16K 토큰 이하 문맥 기준), 질문 1개 → 100개에도 거의 평평. **입력 100만 토큰당 $0.10, 출력 0원**, 공유 입력은 요청당 한 번만 과금. "공유 벤치마크 묶음에서 Gemini 3.5 Flash-Lite(Interactions API)보다 약 5배 싸다." 사내 사례: Gemini Notebook 실시간 모델 라우터(일상 질의 지연 최대 40%↓), Stitch 빠른 와이어프레임, CC의 이모지 200여 개 중 선택, **Search의 MCP 도구 안전 계층**.

**배경 — 왜 지금인가.** Willison의 정리(원문 읽음): Jev와 OpenAI가 이미 연 카테고리에 Google이 들어왔다. API는 Jev와 거의 동일(세 타입·"noul" 용어까지), 가격은 GPT-6 Luna 결정 모델과 동일, **Jev가 여전히 최저가(100만 토큰당 4.2센트)**. 차이는 모달리티: Jev는 텍스트·JSON만, OpenAI는 텍스트+이미지, Gemini는 전부. Willison이 영상으로 시험해 보니 Jev·OpenAI는 예/아니오에 1.0/0.0을 돌려주는데 **Gemini는 0.92·0.05처럼 덜 단정적**으로 답했다 — 보정(calibration) 철학의 차이로 보인다.

**기술적으로 어떻게 동작하나.** 원리는 AI 심층 「비생성 의사결정 모델」과 같다: 토큰을 생성하지 않고 **후보 선택지를 forward pass 한 번에 점수화**. 질문이 늘어도 지연이 평평한 건 공유 입력을 한 번만 인코딩하고 질문 분기만 붙이기 때문이다(어제 노트의 Flide가 엔진 레벨에서 같은 "상태 분기"를 다뤘다). 출력 토큰이 없으니 출력 요금이 0이다.

**MMDM이 짚은 약점**(CUHK, HF 초록 읽음). 결정 모델 28개를 **새로 만든 과제**(기존 벤치마크 노출 오염을 피하려고 재구성·재작성) 5,448문항·16범주로 평가. 단일 선택·다중 선택·소프트 라벨, 선택지 2~1,024개, 입력 최대 64,817토큰, 에이전트 상태 추적·도구/스킬 선택·선호 판단·루브릭 채점 포함.

| Perplexity Decider-V1.2 (Hard 단일 선택) | 정확도 |
| --- | --- |
| 세계 지식 | 78.75% |
| 선택지 논리(선택지끼리 의존) | 53.95% |
| 제약 계획 | 47.95% |
| **전 모델 최고 Hard 다중 선택** | **36.81%** |

해석: 결정 모델은 "각 선택지를 따로 채점"하는 구조라, **선택지 사이의 관계**(A를 고르면 B는 안 됨, 셋 중 둘을 골라야 함)를 보는 데 약하다. 구조적 한계가 숫자로 나온 것이다.

**실무에 무슨 의미인가.**

- **"분기 판단은 LLM에게 문장으로 묻지 않는다"가 표준 선택지가 됐다.** 라우팅·태깅·정책 검사·관련성 판정에 `if (confidence < 0.7) escalate()` 식으로 바로 쓸 수 있다. 어제 노트의 아마존 사례(출력 170 → 1토큰)와 같은 경제학이 이제 벤더 셋 중 고를 수 있다.
- **벤더가 셋이면 API 추상화를 해 둘 이유가 생긴다.** 세 API가 거의 같은 모양이니 내 코드에 `DecisionClient` 인터페이스 하나 두고 구현을 갈아끼우는 설계가 자연스럽다(가격: Jev 4.2센트 대 Google·OpenAI 10센트).
- **MMDM이 주는 사용 규칙**: 선택지가 독립적인 단일 선택에 쓰고, "여러 개를 같이 고르기"·"제약이 얽힌 선택"은 결정 모델 단독에 맡기지 않는다. 다중 선택이 필요하면 선택지별 `noul` 질문으로 쪼개고 제약은 **코드에서** 검사하는 편이 낫다.
- Search가 **MCP 도구 안전 계층**에 쓴다는 대목 — 11/10 노트 「공격자 없이 넘는 권한 경계」의 처방(도구 호출 직전 판정)이 대형 서비스에 실제로 들어갔다는 신호.

**반론·회의적 시각.**

- **"전 벤치마크 선두·최저 보정 오차"는 Google 자체 벤치마크 묶음** 기준이다. 어떤 벤치마크인지 이미지로만 제시됐고, MMDM 같은 독립 평가에 Gemini Decision 1이 들어갔는지는 초록에서 확인되지 않는다(MMDM 제출일이 11/9로 Gemini 발표보다 이르다 — 아마 미포함).
- **150~250ms는 16K 토큰 이하 기준**이다. 최대 256K 입력이나 영상 입력에서의 지연은 따로 제시되지 않았다.
- "5배 싸다"는 Flash-Lite 대비 — 생성 모델과 결정 모델의 비교라 원래 기울어진 비교다. 진짜 경쟁자는 Jev(더 쌈)다.
- 보정이 "덜 단정적"인 게 좋은지는 용도에 달렸다. 임계값을 0.7로 잡은 코드는 Jev(1.0/0.0)와 Gemini(0.92/0.05)에서 다르게 동작할 수 있다 — **벤더를 바꾸면 임계값을 다시 잡아야 한다.**

### 4. Apple 학습형 벡터 검색 — 질의가 어떻게 생겼는지 알면 검색이 8배 빨라진다 (원리는 AI 심층으로)

**무슨 일인가.** Apple ML 해설 글(2026-11-05, 전체 읽음), 원 논문은 ICML 2026 「Amortizing Maximum Inner Product Search with Learned Support Functions」. 키 데이터베이스가 고정이고 질의 분포가 알려진 상황에서, **작은 신경망을 한 번 오프라인 학습**해 최대 내적 검색(MIPS)을 가속한다. SupportNet(클러스터 라우터)과 KeyNet(질의 재작성기) 두 가지.

**배경.** IVF 같은 클러스터 인덱스는 "질의를 센트로이드가 가장 가까운 클러스터로 보낸다". 그런데 센트로이드는 **클러스터의 퍼짐을 모른다** — 자기 센트로이드와는 멀지만 질의와는 가까운 키가 있으면 그 클러스터를 건너뛰고 정답을 놓친다. 또 RAG에서는 키(길고 정제된 문서)와 질의(짧은 사용자 질문)가 생김새부터 다른데, 기존 방법은 "아무 질의에나 괜찮게"를 목표로 해 이 정보를 버린다.

**기술적으로 어떻게 동작하나(핵심만).** "질의 → 집합 안 최대 내적" 함수는 볼록해석학의 **지지 함수(support function)**이고, ① 볼록이며 ② 그 기울기가 바로 최적 키다. 그러니 실제 질의 분포에서 뽑은 질의마다 정답을 전수 검색으로 한 번 계산해 저장하고, 그걸 **회귀로 흉내 내는 작은 신경망**을 학습한다. 자세한 비유와 구조는 AI 심층 노트.

| Natural Questions(약 260만 패시지) | 기준 | 학습형 |
| --- | --- | --- |
| SupportNet S, 라우팅 recall 95% 도달 | 센트로이드 3.36ms | 1.74ms (약 1.9배) |
| SupportNet L, 1.74ms에서 | 센트로이드 약 0.90 | 0.97 |
| KeyNet L + FAISS IVF, recall 99% 도달 | 원 질의 1.8ms | 0.23ms (최대 약 8배) |
| 같은 recall에 스캔하는 키 비율 | 0.10% | 0.009% (약 11배 적게) |

**실무에 무슨 의미인가.** Vault RAG 프로젝트(pgvector 예정)에 직접 닿는다. pgvector의 IVFFlat도 "센트로이드 + probes" 구조라, 이 논문이 짚은 실패 모드(센트로이드 근처 아닌 정답 놓침)를 그대로 갖는다. KeyNet은 **인덱스를 안 바꾸고 질의 벡터만 바꿔 넣는** 방식이라, 원리상 pgvector 앞에 끼울 수 있다. 다만 질의 분포가 쌓여야(운영 로그) 학습할 수 있다 — 처음부터 쓸 기술은 아니고, **질의 로그를 남겨 두는 것**이 지금 할 수 있는 준비다.

**반론·회의적 시각.** 키 DB가 고정이라는 전제 — 문서가 매일 바뀌는 Vault 같은 환경에선 재학습 주기가 문제다. 신경망 크기가 "DB 크기의 1~20%"로 작지 않다. 질의 분포가 바뀌면(새 주제 질문) 이득이 줄 수 있다("완만한 분포 이동에 꽤 견고"라고만). HNSW 계열과의 비교는 해설 글에 없다. 논문 본문은 읽지 않았다.

### 5. WikiTrace — 에이전트 메모리는 "교훈"이 아니라 "교훈 + 근거 링크"로 남겨야 한다

**무슨 일인가.** KAIST AI(Yukyeong Lee·Yumin Choi·Jinheon Baek·Sung Ju Hwang), HF ▲51(초록·저자 코멘트 읽음). 에이전트 외부 메모리가 오히려 성능을 떨어뜨리는 **메모리 유발 퇴행(memory-induced degradation)** — 메모리 없이는 풀었을 과제를 틀린 교훈을 따르거나 맞는 교훈을 잘못 적용해 틀리는 것 — 을 줄이는 방법.

**배경 — 왜 지금인가.** 교훈은 **성공/실패 라벨만 붙은 실행 기록**에서 추론되는데, 정작 에이전트에게는 교훈 문장만 주고 원본 기록은 안 준다. 그러니 에이전트는 교훈이 맞는지 확인할 수 없고, 실패한 과제에서 뽑힌 잘못된 교훈도 똑같이 권위 있어 보인다. 10/29 AI 심층 「에이전트 메모리의 순가치」(대부분의 메모리 시스템이 naive RAG보다 순이득이 음수, 세금 셋 중 "충실도 손실")와 같은 문제를 다른 각도에서 본다.

**기술적으로 어떻게 동작하나.** 교훈을 3층으로 저장한다: **① 짧은 통찰 ② 왜 성공/실패했는지 진단 요약 ③ 원본 실행 기록**, 서로 링크. 새 과제에서 에이전트는 통찰 전부를 첫 메시지로 받고, 통찰이 ⓐ 행동에 필요한 세부가 없거나 ⓑ 다른 통찰과 충돌하거나 ⓒ 실패한 과제에서 왔으면 **터미널 도구로 링크를 타고 내려가** 빈 곳을 채우거나 통찰을 고친 뒤 행동한다. 각 층에는 한 줄 요약 인덱스가 있다.

저자 코멘트에서 나온 숫자: 같은 통찰만 준 베이스라인 대비 5개 벤치 평균 **+3.2점**. **메모리 없이 다시 돌리기만 해도 풀던 과제의 9.7%가 뒤집힌다**(실행 간 잡음 — 메모리 효과를 말할 때의 기준선). **시도가 막힌 뒤의 하강**은 통찰 단독보다 17.3점 앞서고, 일상적 확인 하강은 3.4점 — 링크는 **뭔가 잘못됐을 때** 가장 값을 한다. 초기 버전에서 인덱스만 주고 고르게 했더니 에이전트가 요약만 읽고 행동하거나 메모리를 아예 건너뛰었다.

**실무에 무슨 의미인가.** 이 Vault의 규칙 체계 자체에 대한 이야기다. `CLAUDE.md`·`_규칙` 같은 지침 파일에 "이렇게 한다"만 적으면 맥락이 사라지고 상황이 바뀌면 오히려 발목을 잡는다. 이 Vault가 규칙제안서에 「발견」(왜)과 「결정 기록」(언제·누가·무엇을 기각했나)을 남기고 장부로 연결하는 방식이 **정확히 WikiTrace의 3층 구조**다(통찰 = 규칙 한 줄, 진단 = 결정 기록, 원본 = 제안서 본문). 코드에서도 같다: 커밋 메시지·ADR(결정 로그)에 "왜"를 남기는 것.

**반론·회의적 시각.** HF 댓글의 지적이 날카롭다: 근거 링크는 **틀린 교훈**은 고치지만 **맞는 교훈을 엉뚱한 과제에 적용**하는 건 못 막는다(그 기록도 "그럴듯하게 인용 가능"하므로). 더 싼 대조군 — 교훈에 전제 조건을 붙이고 적용 전 명시적 검사 — 과 비교해야 "인용이 모델을 망설이게 만드는 프롬프트 효과"인지 구분된다. 저자는 두 방식 모두 Applicability 필드가 있고, 전제 조건을 정확히 쓰기가 성공/실패 라벨만으론 어렵다고 답했다. 통찰 전부를 첫 메시지에 넣는 방식은 메모리가 커지면 깨진다(저자도 인정). +3.2점은 작고, 9.7%의 실행 간 잡음과 같은 자로 봐야 한다.

**원문**: [HF](https://huggingface.co/papers/2611.14320) · [arXiv 2611.14320](https://arxiv.org/abs/2611.14320) · [GitHub](https://github.com/yukyeongleee/wikitrace)

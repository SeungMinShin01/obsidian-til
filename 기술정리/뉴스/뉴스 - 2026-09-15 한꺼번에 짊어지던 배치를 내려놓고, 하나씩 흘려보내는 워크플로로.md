## 오늘의 글

**한꺼번에 짊어지던 배치를 내려놓고, 하나씩 흘려보내는 워크플로로**
김현겸 · 2026-09-08 · Backend
https://techblog.woowahan.com/26832/

> 글 머리에 "수치·설정값(대기 시간·타임아웃·재시도 횟수)은 예시이며 실제 운영 설정과 다르다"는 안내가 있다.

## 배경

글은 배달의민족 사장님용 포스(POS) 백엔드에서 "시간이 흐른 뒤에 처리해야 할 일" — 주문이 일정 시간 접수되지 않으면 알림, 응답이 없으면 자동 거절, 픽업 후 일정 시간이 지나면 자동 완료 — 이 많다는 데서 출발한다. 이런 "긴 시간을 가지는 상태 머신"을 오랫동안 배치 잡으로 처리했는데, 배치는 주기적으로 조건에 맞는 대상을 한꺼번에 훑는 구조라 피크타임에 대상이 몰리면 한 사이클의 부담이 그대로 커진다고 설명한다. 그래서 "주문 1건 = 워크플로 1개"로 쪼개면 피크타임에도 부담 없이 흘려보낼 수 있지 않겠느냐는 발상에서 Flowkit이라는 자체 라이브러리를 만들었고, 글은 그중 가장 단순한 사례인 **접수지연 알림**(미접수 3분 경과 시 알림, 그 사이 접수되면 발송 안 함) 하나를 배치에서 워크플로로 옮긴 과정을 다룬다.

## 핵심

- **반려한 대안 — Temporal.** 가장 먼저 검토했지만 네 가지 부담으로 도입하지 않았다고 한다: ① history replay 때문에 워크플로 코드가 결정론적(deterministic)이어야 해서 현재 시각·난수·직접 DB 호출을 못 쓰는 러닝커브, ② Temporal cluster(frontend/matching/history/worker + DB + UI)를 직접 운영해야 하고 persistence store가 Cassandra·PostgreSQL·MySQL로 제한돼 이미 쓰는 DocumentDB(MongoDB)를 못 쓴다는 점, ③ 방대한 외부 엔진 내부 이슈 대응의 어려움, ④ SDK·실행 모델·영속 포맷에 비즈니스 로직이 결합되는 lock-in 리스크.
- **최종 선택 — Temporal의 핵심 네 개념만 압축.** 이미 있는 Kotlin coroutine + Spring WebFlux(suspend/await/timer에 자연스럽게 대응) + Reactive MongoDB만으로 `Workflow` / `Activity` / `Signal` / `Scheduler`를 라이브러리화했다. 글은 이를 "풀편성 오케스트라 대신 필요한 악기만 뽑은 실내악"에 비유하고, Claude와 함께 빠르게 구현했다고 적는다.
- **대기 비용 0의 원리.** `WorkflowContext.await(3분) { isReceived }`를 만나면 현재 상태(변수 + 지금까지의 Activity·await 결과 + `resumeAt`)를 `workflow_instance` 문서 하나에 직렬화(체크포인트)하고 코루틴에서 빠져나온다. 3분이 지나거나 시그널이 오면 Scheduler가 깨워 `execute()`를 **처음부터 replay**하되, Activity 호출·await에 0부터 매긴 invocation 번호(`#0`, `await-0`…)로 캐시된 결과를 즉시 돌려줘 외부 호출 없이 마지막 대기 지점까지 건너뛴다.
- **Temporal과의 차이 — 상태 저장 세분도.** Temporal은 append-only 이벤트 로그에 액티비티 완료마다 즉시 기록하지만, Flowkit은 문서 하나를 in-place 덮어쓰며 **await·완료·실패 시점에만** 체크포인트한다. 그래서 await 없이 이어지는 구간에서 프로세스가 죽으면 그 구간의 Activity가 재실행될 수 있고, 중복은 `invocationToken()` 멱등성 키로 막는다. 재실행이 곤란한 Activity에는 `@ActivityMethod(checkpoint = true)`를 줘 성공 직후 저장하게 한다.
- **Activity에 선언적으로 붙는 정책** (예시값): `startToCloseTimeout = "10s"`(1회 시도 제한), `scheduleToCloseTimeout = "5m"`(재시도·backoff 포함 총 상한, `""`이면 무제한), `@Retry(maxAttempts = 3, initialInterval = "1s", maxInterval = "30s", backoffCoefficient = 2.0, nonRetryable = [IllegalArgumentException])`, `idempotencyRequired = true`, `checkpoint = true`.
- **결정론이라는 숙명.** `execute()` 본문에서는 시각·랜덤·직접 I/O를 쓰면 안 되고(replay마다 분기가 달라지면 invocation 카운터가 어긋남) 모두 Activity나 `WorkflowContext.now()` 같은 helper에 위임한다. 반대로 Activity 본문에는 이 제약이 없다 — 결과가 캐시되므로. 이 규칙은 컨벤션과 코드 리뷰로 지킨다고 한다.
- **분산 환경·롤백 안전.** 여러 pod가 같은 인스턴스를 잡지 않도록 `tryAcquire`의 atomic CAS(version 증가)로 막아 Redis 락 없이 정합성을 보장하고, `@WorkflowVersion`으로 Scheduler가 자기 코드가 다룰 수 있는 버전만 집어 롤백 시 "미래 버전" 인스턴스는 DB에 보존된 채 일시정지했다가 재배포되면 재개된다.
- **기존 배치 대비 달라진 점**(글의 표): 시나리오가 여러 모듈 → `execute()` 하나, 상태 조회가 여러 테이블+로그 → 컬렉션 1개, cron 1분 주기의 최대 59초 오차 → 정확한 `resumeAt`, 도중 취소를 위한 별도 dedup → `await(timeout, predicate)` 한 줄. Temporal Web UI를 참고해 PENDING/RUNNING/COMPLETED·FAILED 어드민(5초 갱신, replay 히스토리·시그널·traceId 상세)을 붙였다.
- **같은 primitive로 할 수 있는 것들**: 평범한 `try/catch`로 쓰는 Saga 보상 트랜잭션, 비동기 콜백을 시그널로 받아 `await`로 엮는 API 오케스트레이션(fan-out/fan-in 포함), 며칠 기다리는 human-in-the-loop, `sleep(1일)` 루프로 cron 없는 주기 실행.

## 내 프로젝트와의 연결

수집기와의 연결이 가장 직접적이다. 수집기는 GitHub Actions cron이 매 주기 "한꺼번에 훑는" 배치 구조인데, 이 글의 핵심 질문 — "대상이 없어도 매 사이클 전체를 재스캔하는가, 아니면 대상별로 자기 시각에만 깨어나는가" — 를 수집 파이프라인에 그대로 대볼 수 있다. 당장 워크플로 엔진을 넣을 일은 아니지만, Activity에 붙인 정책 목록(`startToCloseTimeout`·`scheduleToCloseTimeout`·backoff 곡선·`nonRetryable` 예외·멱등성 키)은 수집기의 API 호출 재시도 설계를 점검하는 체크리스트로 쓸 만하다. 특히 "재시도·replay로 호출이 반복돼도 외부 시스템에 중복 반영되지 않게 하는 키"가 SQLite 저장 계층의 멱등성(공고 ID upsert)과 같은 역할이라는 점이 구조적으로 겹친다. WMS 쪽은 "출고 확정 후 N분 내 미처리면 알림/자동 취소" 같은 시간 기반 상태 전이가 생기면 배치 스캔 vs 건별 타이머 중 어느 쪽을 택할지의 결정 로그 후보가 되고, Saga 예시(결제→배차→재고 차감, 실패 시 역순 보상)는 입고·출고 흐름에서 트랜잭션 경계를 어디에 둘지 생각할 때 참고가 된다. Temporal을 "좋은 걸 알면서도" 러닝커브·인프라·lock-in 때문에 반려한 논증 구조 자체가 결정 로그(문제→대안→기각 사유→선택)의 좋은 본보기다.

## 오늘 정리할 것

1. 수집기의 사람인 API 호출 코드에서 타임아웃·재시도 횟수·backoff·재시도하지 않을 예외를 실제로 어떻게 정했는지 찾아 이 글의 `@ActivityMethod` 필드 5개에 대응시켜 표로 적는다 — 빈칸이 나오면 그것이 미결정 항목이다.
2. 수집기 워크플로우가 한 번 돌 때 "대상이 없어도 하는 일"(전체 조회·비교)이 무엇인지 적고, 수집 대상이 10배로 늘면 한 사이클이 어디서 무거워지는지 추정해 본다.
3. 글의 replay 표(사이클 1·2, `#0`/`await-0`/`#1`/`#2`)를 손으로 다시 그려 보고, "await 없이 이어지는 구간에서 죽으면 왜 Activity가 재실행되는지"를 한 문장으로 설명해 본다.
4. Spring(비 WebFlux, 블로킹 MVC) 환경에서 이 글의 `await`처럼 "스레드를 붙잡지 않고 3분 기다리기"를 흉내 내려면 무엇이 필요한지(`@Scheduled` 폴링 + 상태 테이블? 지연 큐?) 후보를 두어 개 적고 각각의 정밀도·부하를 비교한다.

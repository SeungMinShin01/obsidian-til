우아한형제들 기술블로그, 이동욱 · 2018-10-12 · Backend/Infra. 글은 (미검증 예습자료) 아래와 같이 설명한다.

## 배경

글은 기존에 포인트 서비스가 없고 중앙 DB의 테이블과 프로시저를 각 서비스가 직접 호출하는 구조였다고 설명한다. 도메인 모델·프로시저 문제와 낮은 확장성 때문에 서버·배포 환경·도메인 모델·애플리케이션을 처음부터 새로 만들었다. 개발자 3명, 2018년 4월 중순~7월 말(분석·성능 테스트·QA 제외 실제 개발 2개월 미만).

## 핵심

- Insert-only 도메인: Update/Delete 없이 이벤트만 쌓는다. 포인트는 부채·재화 성격이라 이력이 정확해야 하고, 기존 Update 방식은 잔액 추적·복구가 어려웠다고 한다. 유효기간 만료 때문에 상세 테이블을 두고 적립 ID로 Group By, 0원이 된 적립은 이후 계산에서 제외한다(적립 10/30/20 후 50 사용 → -10/-30/-10).
- 목표는 "DB가 죽어도 문제없는 서비스". 적립/취소는 API → Command Queue(SQS) → Worker가 RDS 반영 → 가용포인트 갱신 Queue → Redis 반영 순서. 조회는 Redis, 장애 시 RDS 직접 조회.
- 사용 이벤트만 예외: 메시지 수신 전 재사용(이중 사용)을 막으려고 SQS를 거치지 않고 즉시 DB 반영, 갱신 메시지만 SQS로 보낸다.
- SQS는 순서 보장이 없어 취소가 적립보다 먼저 올 수 있다. 대상이 없으면 큐로 되돌리고 5회 실패 시 DLQ.
- @SqsListener vs Beanstalk Worker: 벤더 록인 회피, Worker 데몬 장애 대응 불가를 이유로 @SqsListener 채택. 덕분에 나중에 ASG 전환이 수월했다고 한다.
- Beanstalk은 오픈 후 문제(삭제 약 1시간, 배포 1대당 5분·5대 25분, 배포 비율 조절 곤란)가 드러나 ASG + CodeDeploy로 전환. Jenkins는 팀 익숙함·CodePipeline의 멀티 모듈 구성 곤란으로 선택.
- 테스트: 단위+통합 모두 필수(과도한 Mocking으로 단위만 통과하는 문제). H2, Embedded Redis, SQS는 ElasticMQ 래핑 자체 라이브러리, 레거시 MSSQL 프로시저는 Docker MSSQL. API 테스트는 IntelliJ `.http`.
- 문서: Spring REST Docs 채택(코드와 문서 불일치 방지, 어노테이션 오염 없음). Apidoc·Swagger 반려. Markdown(slate/Ruby) 대신 AsciiDoc.
- 3명이 독립 모듈을 맡아 master 단일 브랜치로 진행했고 문제없었다고 한다. 글에는 격리 수준·락·인덱스 수치는 없다.

## 내 프로젝트와의 연결

수집기: "사용은 즉시, 나머지는 큐"처럼 쓰기 경로를 나누고, 순서가 뒤집힌 메시지를 되돌려 보내다 N회 후 DLQ로 보내는 방식은 수집 재시도·실패 격리 설계와 구조적으로 비슷하다. Insert-only 이력은 수집 결과를 덮어쓰지 않고 쌓는 SQLite 저장 설계와 맞닿는다. WMS: 재고도 차감·만료성 이력 + 잔액 파생이라는 같은 모양이며, "이중 사용 방지를 위해 사용만 동기 처리"는 재고 선점/동시성 쟁점과 비교할 만하다. 직접 연결이 강한 글은 아니다.

## 오늘 정리할 것

1. 적립 10/30/20, 사용 50 예시를 SQL로 직접 만들어 Group By 잔액이 글과 같은지 확인한다.
2. Insert-only 이력 + 파생 잔액 vs 재고 Update 방식을 WMS 입출고 이력 관점에서 장단점 표로 정리한다.
3. SQS의 순서 비보장·재시도·DLQ 개념을 찾아보고, 수집기 재시도/멱등성에 대응시켜 본다.
4. @SqsListener와 Worker 방식의 차이(HTTP 기반 vs 폴링 리스너)를 한 줄씩 정리한다.

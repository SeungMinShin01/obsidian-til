## 배경

글쓴이는 "어노테이션이 덕지덕지 붙은 코드"를 경계하는 입장에서 출발한다. 어노테이션은 의도가 숨어 있어 내부 동작을 모르면 로직 흐름을 읽기 어렵고, 안 쓰는 커스텀 어노테이션은 아무도 지우기 부담스러워 남는다. 그럼에도 반복 코드를 걷어내고 비즈니스 로직에 집중하게 해 주는 간결함이 크므로, 글은 "구성원이 의도와 목적에 공감한 뒤, 한 가지 목적으로만" 만든다는 조건을 걸고 띠잉 서버의 실제 사례 네 가지(비회원 미리보기, 서킷브레이커, DynamicRecorder, TaskOccupy)를 소개한다.

## 핵심

- **@PreviewAvailable (비회원 미리보기)**: 같은 API를 회원·비회원이 함께 쓰되 비회원은 일부만 체험하게 해야 했다. 비회원 전용 API를 따로 두는 안은 클라이언트가 회원 여부로 호출을 분기해야 하므로 반려. 대신 모든 엔드포인트를 감싼 `ControllerAspect`에서 이 어노테이션이 있으면 인증 체크를 회피한다. 같은 방식으로 `@SkipOAuth2`·`@InternalApi`·`@ThirdPartyApi`·`@Web`을 목적별로 따로 만든다 — 분기 로직은 AOP 한 곳, 어노테이션은 표식만.
- **서킷브레이커를 직접 만든 이유(Hystrix 반려)**: ① 서버가 에러코드를 직접 관리하는데, 이미 팔로우한 유저 재팔로우 같은 "의도된 정상 예외"까지 실패로 세면 안 되고 critical error만 세야 한다 — 라이브러리로는 실패 조건 커스텀이 어렵다. ② 오픈 전부터 무거운 의존성을 지기 싫었다. ③ 필요한 기능이 단순했다. 글은 효용이 떨어지면 외부 라이브러리로 가는 게 자연스러운 수순이라고 단서를 단다.
- **@CircuitBreaker 속성 10개**: 이름, 판단 주기(interval), CLOSE 중 실패 비율, 최소 요청 수(이보다 적으면 발동 안 함), 최대 실패 수(넘으면 비율 무관 발동), OPEN 유지 시간, HALF_OPEN 유지 시간, HALF_OPEN 성공 비율(넘으면 CLOSE), 임시 해제 스위치, fallback. 처음엔 서비스 공통 디폴트로 시작하고 운영하며 개별로 조인다.
- **상태 전이 CLOSE → OPEN → HALF_OPEN**: HALF_OPEN에서는 트래픽 절반은 CLOSE처럼 통과, 절반은 OPEN처럼 차단하고, 통과분이 기준을 넘으면 CLOSE, 못 넘으면 다시 OPEN. 중간 단계는 몰리는 트래픽을 완충하고 복구를 자동화하기 위한 것이라고 설명한다.
- **구성 요소**: `CircuitBreakerData`(상태·제어 필드) → `CircuitBreakerDataHolder`(싱글톤, 이름을 키로 보관) → `CircuitBreakerDataInitializer`(`InstantiationAwareBeanPostProcessorAdapter` 상속, 빈 초기화 후 클래스·메서드 레벨 어노테이션을 찾아 등록, yaml 프로퍼티 false면 빈 자체를 안 띄움) → `CircuitBreakerProcessor`(proceed 전 상태 검사, critical error만 카운트, fallback 또는 예외) → `CircuitBreakerAspect`(@Around). `@IgnoreCircuitBreaker`로 임시 해제.
- **fallback은 클라이언트 협업 문제**: `CircuitBreakerFallback` 인터페이스 + 기본값 `DefaultNothingFallback`. 프로필 통계 API가 차단되면 -1을 내려주고, 클라이언트는 음수면 하이픈(-)으로 표시하기로 약속한다 — 한 화면의 API 하나가 죽어도 화면 전체가 깨지지 않게.
- **@DynamicRecorder**: 좋아요·이모지 리액션 후 상대 유저 통계 갱신은 비동기 이벤트로 처리하는데, 평소엔 레코더(ThreadPool로 로컬 메모리에 이벤트를 모으는 단위)를 즉시(IMMEDIATE) 처리하고, `intervalSecond` 동안 처리량이 `threshold`를 넘으면 모았다가 일괄(BUFFER) 처리로 자동 전환한다. 구현은 서킷브레이커 구조를 변형했다.
- **@TaskOccupy**: 토큰 정리·탈퇴 단계 처리 등 스케줄 작업이 40여 개인데, 스케줄러 서버를 증설하면 같은 작업이 중복 실행된다. 한 작업의 점유를 하나의 인스턴스만 갖게 하는 어노테이션(코드는 미공개).

## 내 프로젝트와의 연결

수집기는 외부 채용 API를 반복 호출하므로, 글의 "critical error만 실패로 센다"는 기준이 그대로 옮겨온다 — 404·빈 결과 같은 정상 응답과 5xx·타임아웃을 구분하지 않으면 재시도/차단 로직이 엉뚱하게 발동한다. 다만 수집기는 GitHub Actions 단발 실행이라 메모리 상주형 서킷브레이커 상태는 실행 사이에 유지되지 않으므로, 상태를 SQLite에 남기거나 "실패 N회면 이번 실행 중단" 정도로 단순화하는 쪽이 구조적으로 맞다. WMS에서는 `@TaskOccupy`가 직결된다 — 재고 정합성 점검·예약 만료 같은 스케줄 작업을 인스턴스 2대 이상으로 배포하면 중복 실행이 생기고, 이는 분산 락(예: ShedLock 류)으로 푸는 문제다. `@DynamicRecorder`의 즉시/일괄 전환은 입출고 이력 적재를 배치 insert로 모으는 지점과 구조적으로 비슷하다.

## 오늘 정리할 것

1. Resilience4j `CircuitBreakerConfig`의 설정 항목(`failureRateThreshold`·`minimumNumberOfCalls`·`waitDurationInOpenState`·`permittedNumberOfCallsInHalfOpenState`·`recordExceptions`/`ignoreExceptions`)을 글의 속성 10개와 1:1로 대응표로 만든다.
2. Spring AOP로 `@Around("@annotation(...)")` 커스텀 어노테이션 하나(예: 실행 시간 로깅)를 직접 만들어 보고, 같은 클래스 안 self-invocation에서는 왜 안 걸리는지 확인한다.
3. 글이 쓴 `InstantiationAwareBeanPostProcessorAdapter`가 최신 Spring에서 어떤 상태(deprecated 여부)인지, 대신 무엇을 구현하는지 공식 문서에서 확인해 메모한다.
4. ShedLock의 `@SchedulerLock(lockAtMostFor, lockAtLeastFor)` 동작을 문서로 확인하고, WMS 스케줄 작업 중 중복 실행되면 안 되는 것을 2~3개 적어 둔다.

## 배경

글은 미래사업부문에서 배민과 의존성이 없는 신규 회원 서비스를 만들며 Spring Security OAuth2를 인증 체계로 골랐다고 설명한다. 앱 환경에서는 매번 로그인하지 않고, 인증키를 주기적으로 바꾸며, 사용자가 직접 재인증하지 않아도 되는 방식이 낫다는 판단이다. in-memory로는 잘 동작했지만 인증 테이블 3개로 DB 연동을 붙이고 로그를 보니 토큰 작업 한 번에 쿼리가 수 개~십수 개 나가고 있었다. 특히 모든 API 호출마다 도는 토큰 검증이 인증 DB에 부담이 된다는 점이 문제다.

## 핵심

- 쿼리 수 실측: 토큰 발급 9회, 검증 4회, 재발급 14회, 잘못된 토큰으로 재발급 5회. 반복되는 쿼리는 `JdbcClientDetailsService.loadClientByClientId(..)`의 `oauth_client_details` 조회.
- 발급·재발급은 토큰 유효기간을 늘려 횟수를 줄이는 우회도 가능하지만, 글은 이런 단순한 합리화가 장애와 야근으로 이어질 수 있다고 본다. 매 요청마다 도는 **검증**은 반드시 대응이 필요하다고 판단한다.
- 라이브러리 소스를 직접 고칠 수 없으므로 호출 지점을 추적한다: `TokenEndpoint.postAccessToken(..)`(/oauth/token), `CheckTokenEndpoint.checkToken(..)`(/oauth/check_token), 그 아래 `JdbcTokenStore` 메서드들, `JdbcClientDetailsService.loadClientByClientId(..)`.
- 해결: AOP 클래스에 지점별 `@Pointcut`을 등록하고 `@Around`에서 "캐시 조회 → 없으면 원 메서드 실행 후 Redis 저장" 흐름(`getOrProgress`)을 구현한다. 캐시 대상 타입(ClientDetails·OAuth2AccessToken·OAuth2Authentication·String)은 enum으로 구분하고, 만료 시간 지정 여부는 파라미터로 분기한다. 토큰 저장·삭제 메서드는 `@Before`로 캐시를 함께 조정한다.
- 결과: 발급 9→5, 검증 4→0, 재발급 14→7, 잘못된 토큰 재발급 5→1. DML은 걷어낼 수 없어 전체 감소폭은 제한적이지만, 매 요청마다 타는 검증이 0회가 된 것을 가장 큰 성과로 본다.
- 한계 1: AOP는 프록시 기반이라 self-invocation에서는 어드바이스가 실행되지 않는다. `@Transactional`·`@Cacheable`도 같은 원리라 의도한 동작이 걸리는지 따져봐야 한다고 글은 말한다.
- 한계 2: 같은 요청에 같은 응답·내부 동작을 기대할 수 있는 영역에만 캐시를 적용해야 한다. 메서드에 비즈니스 로직 분기가 섞이면 캐싱 대상이 아니며, 캐시하고 싶은 것은 데이터이지 로직이 아니다. 그래서 데이터 접근 메서드를 최소 기능으로 잘게 쪼개는 스타일을 선호하게 됐다고 한다.
- 결론: 프레임워크를 믿고 쓰되 내부 동작을 이해하려는 습관이 기본값이어야 한다.

## 내 프로젝트와의 연결

WMS(Spring Boot)의 상품·로케이션·거래처 같은 마스터 데이터는 화면마다 반복 조회되기 쉬워, 이 글의 "로그로 쿼리 수 세기 → 반복 쿼리 특정 → 캐시 → 재측정" 절차가 Before/After 성능 측정 틀로 쓸 수 있어 보인다. `@Cacheable`이 프록시 기반이라 같은 클래스 내부 호출에서 안 걸린다는 주의점은 서비스 메서드를 쪼갤 때 바로 만나는 지점이다. 반대로 재고 수량처럼 동시성·정합성이 걸린 데이터는 "같은 요청에 같은 응답"이 보장되지 않으므로 대상에서 빼야 한다는 기준으로 읽을 수 있다. 수집기와의 직접 연결은 약하고, 외부 API 응답을 재사용하되 로직은 캐시하지 않는다는 정도의 구조적 유사성만 있다.

## 오늘 정리할 것

1. 같은 클래스 내부 호출 테스트를 1개 작성해 self-invocation에서 어드바이스가 실행되는지 로그로 확인한다(JDK 동적 프록시/CGLIB 프록시 구분 포함).
2. 로컬 Spring Boot 프로젝트에서 SQL 로그(show-sql 또는 p6spy)를 켜고 API 한 번당 쿼리 수와 반복 쿼리를 센다.
3. WMS 기준 `@Cacheable` 적용 후보 3개와 비적용 후보 3개를 "같은 요청 = 같은 응답인가?" 기준으로 이유와 함께 적는다.
4. `@Around`에서 `proceed()` 호출 전/후 위치에 따라 캐시 흐름이 어떻게 달라지는지 pseudo 코드로 써 본다.

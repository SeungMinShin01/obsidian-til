## 배경

글은 우아한테크코스를 수료하고 리뷰프로덕트팀에 입사한 신입이 "미니 리뷰 프로젝트"(리뷰 등록·수정·삭제, 정렬/필터 조회, 좋아요, 가게 리뷰 통계, 이벤트 발행, 히스토리 관리, CI·로깅·배포)를 파일럿으로 만든 과정을 성장 일기로 정리한다. 스택은 Spring Boot 2.x, JPA, QueryDSL, Aurora(MySQL)/H2, Vue.js, S3·SNS·SQS. 글의 중심은 설계·코드 리뷰 피드백으로 처음 방식을 고쳐 간 과정(문제 → 시도 → 개선)이다.

## 핵심

- 연관관계 규칙: 같은 라이프사이클(함께 생성·수정·삭제)인 엔티티끼리만 객체 참조, 나머지는 Id 간접 참조 → 조회 경계가 끊겨 N+1과 불필요한 연관 조회를 줄인다고 설명. 패키지 간 순환 참조도 점검
- 코드 리뷰 지적: 조회 관점만 고민했고, 하위 엔티티마다 repository(reviewRepository, reviewDeliveryRepository, reviewMenuRepository, reviewImageRepository)를 두면 외부에서 직접 변경해 일관성이 깨질 수 있음 → Review를 애그리거트 루트로 두고 하위 엔티티는 루트를 통해서만 변경
- 멀티 모듈: 처음 review-api/review-core 2개 → api(비즈니스 로직)·core(도메인)·worker(이벤트)·client(외부 통신)·common으로 재분리. review-api가 review-worker를 의존하는 구조(모듈만 나뉘고 앱은 하나)는 "api 기능과 통계 집계가 같이 돌아 부하가 올 수 있다"는 피드백으로 끊고, worker는 이벤트 수신·통계 갱신만 하는 별도 애플리케이션으로 배포
- 이벤트: 리뷰 변경 → SNS 발행 → SQS 큐 구독 → worker 수신. 한쪽이 죽어도 큐에 이벤트가 남아 복구 후 처리. 리스너에 `deletionPolicy = SqsMessageDeletionPolicy.ON_SUCCESS`를 주면 예외 없이 끝났을 때만 큐에서 삭제
- 멱등성: 이벤트 타입별로 증감하던 통계 로직은 분기가 복잡하고 같은 이벤트가 여러 번 오면 중복 반영(Spring Cloud AWS 문서에서 확인) → 이벤트가 오면 해당 가게의 "노출 상태" 리뷰를 별점별로 그룹핑해 통계를 다시 계산. 글은 이렇게 하면 추가 연산 없이 멱등성과 분기 제거를 함께 얻었다고 설명
- 히스토리: 5개 History 엔티티를 직접 만드는 대신 Spring Data Envers의 `@Audited(withModifiedFlag = true)` 사용. `revision_type` 0/1/2 = 등록/수정/삭제, `xxx_mod` 컬럼이 필드 변경 여부, 같은 `revision_id`가 같은 트랜잭션의 변경, `revinfo` 테이블에서 관리
- 테스트: Acceptance(E2E) / Service(통합) / Domain(단위) / Controller(MockMvc 슬라이스). 외부 API·인프라 의존부는 결국 Mock 대역을 썼고, 프로덕션과 다를 수 있어 불안했다고 글이 인정. `@BeforeEach` 공통 given은 테스트 추가 시 서로 영향을 주고 로직 파악도 어려워 각 테스트에서 given을 설정하는 쪽으로 변경
- 회고: 새 기술 학습 시간을 일정에 넣지 못해 일정이 밀렸고, 막바지 배포에서 화면·인프라 에러를 만남. 진행 상황을 계속 공유해 중간 조정을 했어야 한다는 반성
- 글에 없는 것: 통계 재집계의 쿼리 비용·인덱스, 이벤트 순서 보장·중복 수신 빈도, DLQ/재시도 설정, 일부 코드 블록(본문에서 비어 있음)

## 내 프로젝트와의 연결

수집기와는 "재실행·중복 수신에도 결과가 같아야 한다"는 멱등성 지점이 가장 가깝다. 글의 해법(증감 대신 원천 테이블에서 다시 집계)은 수집기가 카운터를 누적하지 않고 SQLite에 저장된 공고를 기준으로 다시 세는 방식과 같은 결이다. WMS에서는 재고 집계를 "이벤트마다 증감 vs 원장에서 재계산"으로 둘 때의 선택, 입출고 이력에 변경 이력(Envers 또는 이력 테이블)을 붙이는 방법, 재고·입고 엔티티의 애그리거트 루트와 Id 간접 참조 규칙(N+1 방지)에 옮겨 볼 수 있다. 다만 글은 SNS/SQS 기반이라 WMS 3주 일정에서 메시지 큐까지 갈 필요는 없을 수 있다. 연결은 구조적으로 비슷한 지점 위주다.

## 오늘 정리할 것

1. 수집기에서 같은 데이터를 두 번 저장·집계해도 결과가 같은지(고유 키, UPSERT, 누적 카운터 유무)를 코드에서 확인해 한 줄씩 적는다
2. WMS 재고 엔티티 후보(재고·로케이션·입고 내역)를 "같이 생성·수정·삭제되는 것"끼리 묶어 애그리거트 경계를 손으로 그려 보고, 경계 밖은 Id 참조로 바꿀 곳을 표시한다
3. Spring Data Envers의 `@Audited`, `revision_type`, `*_mod` 컬럼, `revinfo` 테이블이 각각 무엇을 기록하는지 공식 문서에서 확인해 3줄로 정리한다
4. "증감 갱신"과 "원천 재집계"의 장단점(성능 vs 멱등성)을 재고 수량 예시로 비교표 한 장으로 만든다

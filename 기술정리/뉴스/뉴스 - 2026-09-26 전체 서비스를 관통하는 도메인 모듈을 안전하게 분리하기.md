**원문**: [전체 서비스를 관통하는 도메인 모듈을 안전하게 분리하기](https://techblog.woowahan.com/22151/) — 홍혜린, 김수현 · 2025.05.29 · Backend

## 배경

글은 B마트 물류 플랫폼을 담당하는 WMS플랫폼팀의 이야기에서 출발한다. 창고 상태를 가시화하고 재고를 신뢰할 수 있는 데이터로 관리하는 WMS(Warehouse Management System)에서, `api`·`consumer`·`batch` 모듈이 모두 입고·재고·출고를 아우르는 **하나의 거대한 도메인 모듈**에 의존하는 구조였다고 설명한다. 서비스가 성장하면서 도메인은 비대해졌고, 팀원 간 커밋 충돌, 사소한 수정에도 터지는 예기치 못한 장애, "건드리면 안 되는 코드"가 함께 늘었다. 특히 재고 정확도 향상 고도화 과제를 진행하면서 문제가 터졌는데, 재고 도메인이 입고·출고 도메인과 워낙 강하게 얽혀 있어 작은 수정 하나의 영향 범위를 가늠하기 어려웠다고 글은 전한다.

## 핵심

· 세 도메인(입고·재고·출고) 중 재고가 다른 모든 도메인과 가장 많이 상호작용하는 축이라, 재고 도메인부터 분리 대상으로 삼았다고 설명한다.

· 1단계는 `domain-inventory` 모듈을 새로 만들어 재고 엔터티·리포지토리·서비스를 먼저 모으는 것(응집도 확보)이었고, 그다음 기존 모듈에서 이 재고 모듈 의존성을 강제로 끊어 **빌드를 실패시킨 뒤**, 실패한 파일들만 골라 `service-wms`라는 "결합 모듈"로 옮겼다 — 결합 지점을 사람이 추측하지 않고 컴파일러가 드러내게 한 방식이라고 소개한다.

· 결합 모듈에는 도메인 간 연관관계를 선언한 엔터티, 입고/출고와 재고를 직접 join하는 QueryDSL 리포지토리, 이를 쓰는 조합 서비스가 모였다. 이후 연관관계 제거, join 절 제거 후 서비스 레이어에서 조합, 타 도메인 리포지토리를 직접 쓰던 서비스는 각 도메인으로 재분배하는 순서로 결합도를 낮췄다고 한다.

· 입고 완료 시 상태 변경과 재고 증가가 동시에 일어나야 하는 것처럼, 서비스 간 오케스트레이션은 쉽게 끊어낼 수 없었다. 이걸 전부 결합 모듈에 몰아넣으면 그 모듈 자체가 다시 거대한 모놀리스가 될 거라 판단해, **헥사고널 아키텍처 + port-adapter 패턴**을 도입했다 — 모듈 간에는 인터페이스(port)만 노출하고 실제 구현(adapter)은 각 도메인 내부에 두는 방식이다.

· 도메인 내부 응집도를 위해 유즈케이스 구현체는 밸리데이션·DTO 변환·코어 서비스 조합만 담당하게 하고, 코어 서비스는 엔터티를 외부로 직접 반환하지 않기·다른 코어 서비스의 리포지토리를 직접 쓰지 않기라는 두 규칙을 세웠다고 설명한다.

· 분리 영향 범위가 **231개 API**에 달해, 변경마다 피처 플래그를 원칙적으로 적용(실제 약 27개 사용)하고 약 70여 개 센터 단위로 주문량이 적은 곳부터 순차 적용(10%→50%→100%)했다. 플래그는 제거 시점까지 미리 계획해 코드에 방치되지 않도록 관리했다고 한다.

· 2주 스프린트 안에서도 매주 배포해 배포 주기를 최대 2주 이내로 유지했고, 로직 변경이 큰 흐름에는 유닛·통합 테스트를 집중적으로 작성해 QA 리소스가 제한된 상황을 보완했다.

· 구조가 다시 흐트러지는 걸 막기 위해 ArchUnit으로 헥사고널 규칙을 코드 수준에서 강제하고, 결정 사항은 ADR로 남기고, 주 1회 스터디로 "왜 이 구조인가"를 팀이 함께 이해하도록 했다. 결과로는 팀 설문에서 엔터티 구조 이해도 평균 4.14점, 리팩토링 효과(수정 복잡도 감소·책임 명확화·리뷰 용이성·개발 효율) 관련 항목이 모두 평균 4점 이상으로 나왔다고 밝힌다.

## 내 프로젝트와의 연결

이 글은 이름 그대로 WMS(창고관리시스템) 이야기라 직접 연결이 강하다. 지금 진행 중인 Spring Boot + React WMS 프로젝트도 입고·재고·출고를 다루므로, 재고가 다른 두 도메인과 가장 강하게 얽힌다는 이 글의 관찰과 헥사고널 아키텍처로 port만 노출하고 adapter는 도메인 내부에 두는 설계는 지금 도메인 경계를 그릴 때 그대로 참고할 만하다. 다만 231개 API·27개 피처 플래그·70여 개 센터 단위 점진 배포는 훨씬 큰 규모의 이야기이므로, 우리 프로젝트에서는 그 축소판으로 "기능 단위 플래그 + 작은 배포 단위"라는 태도만 가져오는 정도가 현실적이다.

## 오늘 정리할 것

1. 헥사고널 아키텍처의 port/adapter 개념이 스프링 프로젝트의 패키지 구조로 어떻게 표현되는지 직접 찾아보고 정리한다.
2. ArchUnit을 프로젝트에 추가해서 "특정 패키지가 다른 도메인의 리포지토리를 직접 참조하면 안 된다" 같은 규칙 하나를 실제로 만들어 실행해본다.
3. 지금 WMS의 입고/재고/출고 도메인 경계를 이 글 기준으로 다시 그려보고, 강하게 결합된 지점이 있는지 점검한다.
4. 스프링 부트에 붙일 수 있는 피처 플래그 방식(간단한 설정값 토글이든 라이브러리든)을 하나 찾아본다.

## 깊게 본 것

### 1. Jepsen × ParticleDB — "Full ACID"와 "TLA+ 증명"이 노드 하나에서 무너졌다

**무슨 일인가.** Jepsen이 Orkes의 ParticleDB(Rust로 새로 쓴 "AI 워크로드용" 멀티모델 DB — 트랜잭션 SQL·키-값·벡터 검색·실시간 분석·UDF 'Particles', Postgres/Redis 프로토콜·gRPC·HTTP2)를 1.1.4부터 1.1.18.11.rc-22까지 검증해 **96개 문제**를 보고했다. Orkes는 이 DB로 자사 워크플로 플랫폼 Conductor를 받친다.

**배경 — 누가 왜 했나.** **이 분석은 Orkes가 비용을 내고 의뢰했다**(Jepsen 윤리 정책에 따름) — 브리핑엔 빠진 사실이다. 벤더가 외부 검증을 사서 결과를 그대로 공개한 셈이다. Orkes는 1.1.4의 문제 상당수가 2026년 봄의 대규모 리팩터링에서 왔다고 봤다. 그리고 제공된 빌드가 복제(Raft)를 지원하지 않아 **보고서 전체가 단일 노드 결과**다. 분산 시스템의 어려운 경계 조건이 아니라 "로컬에서 쿼리를 던지는 수준"에서 틀렸다는 뜻이다.

**기술적으로 — 어떻게 쟀나.**

- **워크로드**: `rw`(기본키/보조키 읽기·쓰기 무작위 트랜잭션을 Elle로 사이클·G1a 등 검사), `append`(text 컬럼에 정수를 `concat`으로 이어 붙이는 리스트 append — 순서가 남아서 이상 현상을 역추적하기 좋다), `internal`(한 트랜잭션 안의 INSERT/UPDATE/DELETE/SELECT 일관성), **`compare`**(test.check로 무작위 테이블·SQL을 생성해 **PostgreSQL과 결과를 대조** — 차분 테스트), `internal-sim`.
- **장애 주입**: 프로세스 kill(갑작스러운 종료), LazyFS로 fsync 안 된 쓰기 손실, 디스크 파일 절단·손상(WAL 비트플립, 파일 청크 교체로 잘못된 읽기/쓰기 흉내).

**무엇이 틀렸나 — 성격이 숫자보다 무섭다.** 96건 대부분이 노드 하나, 장애 없이 재현됐다. 몇 묶음만:

- **술어(predicate) 무시**: `SELECT 5 WHERE FALSE`가 5를 반환. `SELECT * FROM t WHERE 4 = 5`가 행을 돌려줌(등호를 기본키 조회로 해석). 트랜잭션 안에서는 `WHERE TRUE`가 0행을 돌려주기도 했다.
- **제약 무시**: `NOT NULL` 컬럼에 NULL 삽입 성공(그 뒤 `SELECT *`엔 0행, `SELECT COUNT(*)`엔 1), `UNIQUE`에 중복 허용, `UPDATE`가 같은 기본키를 가진 행을 여러 개 생성.
- **타입/상태 손상**: TEXT 컬럼 문자열이 8비트 정수로 바뀌어 `"1"` 대신 `1`이 나옴. `INSERT`가 지정한 컬럼 순서를 무시하고 원래 스키마 순서를 써서 값이 뒤섞임. 아무 행도 안 맞는 `UPDATE`가 보이지 않는 손상 행을 새로 만듦.
- **좀비 행**: 트랜잭션 안에서 `DELETE`가 0행(지울 수 없음), `DROP TABLE` 뒤 같은 이름으로 다시 만들면 옛 행이 왜곡된 형태로 되살아남(float `18.83`이 정수 `19`로).
- **트랜잭션 이상 현상**: G0·G1a·G1b·G1c·G-Single·P4(Lost Update)·A5A(Read Skew)·G2, Snapshot Isolation/Serializable을 표방한 모드에서도 발생. `strict-serializable`에서도 약 30만 트랜잭션당 한 번 Stale Read. 커밋된 쓰기가 조용히 사라지는 데이터 손실.
- **장애 포함**: WAL 한 비트를 뒤집으면 체크섬 불일치를 로그에 남기고 유효한 접두사만 복구한 뒤 **정상 기동**해 여러 키의 커밋된 쓰기를 조용히 잃음. 파일 청크를 섞으면 "저장소에 데이터 없음 — 새로 시작"이라며 WAL을 0으로 밀어 전손.

**실무에 무슨 의미인가.**

- `@Transactional`을 붙이면 당연해 보이는 격리 수준은 **DB가 지키는 것**이다. DB가 안 지키면 애플리케이션에서 알 방법이 거의 없다 — "스냅숏 격리"라는 한 줄 주장과 실제 보장은 별개다.
- 이번 사례의 진짜 교훈은 **외부 검증의 존재 가치**다. 벤더 벤치마크("159K TPS")와 "Full ACID"·"형식 증명" 같은 한 줄은 선택 근거가 못 된다. WMS/수집기에서 저장소를 고를 때 "왜 PostgreSQL/MySQL을 골랐나"의 결정 로그 근거 중 하나로 이 보고서를 적어 둘 수 있다.
- `compare` 워크로드(무작위 SQL을 Postgres와 대조)는 내 코드에도 옮길 수 있는 패턴이다 — "같은 쿼리를 신뢰하는 레퍼런스 구현과 돌려 결과가 갈리는지 본다"는 차분 테스트.

**반론·회의적 시각.** Orkes는 보고서의 모든 지적을 1.1.19-rc.13에서 해결했다고 밝혔고, 트랜잭션 모드를 실험적으로 표기·개편했다. 따라서 Jepsen의 "다른 DB로 이전하라"는 권고는 **보고 대상 버전**에 대한 것이고, 1.1.19 이후는 다시 검증돼야 한다. 또 보고서는 복제·벡터 검색·Redis/HTTP API·시공간 쿼리 등 기능의 큰 부분을 **다루지 않았다**(단일 노드·SQL 인터페이스 중심). Jepsen 자신이 "버그의 존재는 증명하지만 부재는 증명 못 한다"고 명시한다.

### 2. MCP 대 CLI 통제 실험(MICA) — 능력을 똑같이 맞춰도 '표현'이 행동을 가른다

**무슨 일인가.** 지금까지 "MCP가 좋다 / CLI가 좋다" 비교는 양쪽이 실제로 할 수 있는 일이 달라서 사과와 오렌지였다. MICA(Matched Interface Comparison and Analysis)는 **하나의 의미론적 액션 계약(semantic action contract)**에서 MCP와 CLI를 똑같이 생성하고 **같은 런타임**으로 실행해, 차이를 "표현 방식"만으로 좁혔다. 6개 모델·3개 인터랙티브 환경·2,004개 에피소드.

**결과.** 능력을 맞췄는데도 과제 성능·상호작용 비용이 크게 갈렸고, 짝지은 자연 궤적의 **94.3%에서 구조적 분기**가 나왔다. 게다가 초반의 작은 차이가 이후 상호작용으로 전파된다(한 번 갈린 선택이 다음 상태를 바꾼다). 차이는 표면 유효성(문법 맞음)을 넘어 **의미론적 액션 선택·실패 경로·복구**까지 번졌다.

**어떻게 푸는가 — DART.** Decoupled Action Realization and Targeted Repair. 모델의 **검증된 의미론적 결정("무엇을 하려 했나")은 보존**하고, "그 도구에서 그걸 어떻게 표현하나(realization)"만 고친다. 비즈니스 로직은 두고 어댑터만 교정하는 구조. 결과는 6개 설정 전부 점수 상승(최대 9.0점), 3개 환경 전부 MCP 토큰 비용 감소(과제당 최대 27.1k 토큰).

**실무에 무슨 의미인가.** Claude Code·Cursor에 MCP 서버를 붙여 쓴다면, **도구 설명(description)·파라미터 이름·반환 형식 자체가 성능 변수**다. 같은 기능이라도 CLI로 노출할 때와 MCP로 노출할 때 모델이 다르게 행동하므로, "왜 이 도구를 안 쓰지/엉뚱하게 쓰지"는 모델 탓이기 전에 인터페이스 표현 탓일 수 있다. 10/27 제약 디코딩이 "모양은 생성 시점에 강제"였다면, 여기선 **의도(검증)와 표현(교정)을 분리**하는 같은 발상이다.

**반론.** HF 업보트 4로 주목도는 낮고, 코드는 공개(github.com/ModalityDance/MICA)됐지만 초록·프로젝트 페이지 수준만 읽었다. "94.3% 분기"는 **구조적 차이가 있다**는 것이지 전부 성능 저하라는 뜻은 아니다. DART의 "최대 9.0점·27.1k 토큰"은 설정별 최대치다.

### 3. Co-Design Bench — "69.9% 통과"와 "26.4% 완료"는 다른 이야기다

**무슨 일인가.** Qwen 팀 등이 **26,314개 실제 사용자 코딩 세션**에서 뽑은 37,463개 질의를 정리해 273개 과제를 만들고, 전문가가 작성한 **숨겨진 수용 기준 2,331개**로 채점하는 레퍼런스-프리 벤치마크. 두 트랙 — Multimodal Editing(이미지·오디오·비디오·문서 입력이 붙는 국소 수정 100개)과 Repository Editing(컴포넌트·라우트·상태·데이터 흐름을 가로지르는 조율된 수정 173개). 정답 코드나 목표 스크린샷 없이 소스·브라우저 증거로 판정하고, **judge-then-refute**: 별도 검증자가 "통과" 판정에 대해 stub·하드코딩 출력·도달 불가 기능·요구 불일치로 반박을 시도한다.

**결과.** 최강 엔드포인트(gpt-6-astra)가 과제당 기준의 평균 **69.9%**를 통과하지만, 과제를 **완전히 만족한 비율은 26.4%**. 열 엔드포인트 전부 변경 유형이 3~4개 섞인 저장소 수정에서 1~2개짜리보다 낮은 완료율. Qwen3.8-27B는 전체 strict 완료 64.4%(4위), Repository Editing 64.5%(2위), 텍스트만 ME 서브셋 1위(77.9%).

**왜 이게 중요한가.** 벤치마크는 보통 "요구사항 중 몇 %를 만족했나"를 재는데, 실무에서 중요한 건 "**이 작업이 끝났나**"다. 10개 중 7개 채운 PR은 0개짜리보다 낫지만 머지할 상태는 아니다. AI에게 기능 수정을 맡겼을 때 "거의 다 됐는데 뭔가 안 되네"가 가장 흔한 이유가 이 간격이다. 거꾸로, **마지막 30%를 메우는 사람**의 역할이 아직 또렷하다는 뜻이기도 하다 — 브리핑의 FurtherAI(엔지니어당 병합 5배는 생성이 아니라 검증 자동화에서) 사례와 한 줄로 이어진다.

**반론.** HF 댓글에서도 지적됐듯, refute 단계가 긍정 판정을 뒤집는 비율(유형별)·심판-검증자 일치·반복 실행 분산이 헤드라인 숫자의 신뢰도를 정한다 — 273과제라 flaky 몇 개가 근접 모델 순위를 뒤집을 수 있다. 랭킹은 편집 설정에 따라 바뀌어 "일반적 모델 우위"를 세우지 않는다. gpt-6-astra·Qwen3.8 등 **모델 이름은 브리핑/저자 표기 그대로**이고 미검증이다.

### 4. AI 자금에 찬물 — "쓰는 속도"와 "버는 속도"의 간격을 다시 재다

**무슨 일인가.** 세 소식이 같은 방향이다. ① OpenAI가 목표 300억 달러 라운드에서 **약 110억 달러 약정**만 확보(WSJ, 10/31). 기대 기업가치도 1조 4,000억 → 1조 2,500억 달러. 라운드는 미종료이고 패밀리오피스·고액자산가 대상으로 추가 모집 중. ② Blackstone이 Anthropic의 신용등급 전망을 "연내 투자적격"에서 "상장 뒤에도 투기등급 상단 가능"으로 봤다(FT 보도, GeekNews 경유 — FT 원문은 미확인). ③ 금요일 나스닥 3.5%+ 하락, Intel 장중 최대 30% 급락. 배경 숫자: 빅테크 5곳의 2026년 지출 계획 합계 8,006억 달러.

**어떻게 읽나.** 지출은 확정, 수익은 아직 설명되지 않은 상태에서 실적이 기대에 못 미치자 시장이 그 간격을 가격에 반영했다. **반론**: 라운드 목표 미달은 OpenAI 제품 지표가 꺾였다는 신호와 다르다(밸류에이션 기대가 과했다는 해석이 자연스럽고, 110억 달러 자체는 거대한 조달). 신용등급도 "지금 돈이 없다"가 아니라 "앞으로 수천억을 **싸게** 빌릴 수 있나"의 문제다. 다만 "자금은 무한하다"가 기본 가정이던 시장에서 이 가정이 처음 흔들리는 구간이라는 점은 분명하다.

**학습 입장에서.** 자금이 조이면 가장 먼저 줄어드는 건 "일단 뽑아두는" 채용과 무료 티어의 관대함이고, 늘어나는 건 **비용 효율을 숫자로 설명할 수 있는 사람**의 값이다. 같은 날 LOWN(연산 35%로 점수 99.6% 유지)이 1위 논문인 것, MICA/DART가 토큰을 줄인 것이 우연이 아니다. 포트폴리오에서 "이 쿼리를 인덱스로 몇 ms→몇 ms", "이 호출을 캐싱으로 몇 분의 일"처럼 **측정된 숫자**가 기능 개수보다 잘 팔리는 국면이다.

## 더 알아볼 것

- [ ] **차분 테스트를 내 코드에 한 번.** Jepsen `compare`처럼, 수집기/WMS의 쿼리 한 묶음을 H2(또는 SQLite)와 운영 DB(MySQL/Postgres) 양쪽에 같은 입력으로 돌려 결과가 갈리는 지점을 찾는다. 특히 `NULL` 비교, 타입 암묵 변환, `WHERE` 상수식에서. 갈리면 무엇이·왜 다른지 한 줄씩.
- [ ] **격리 수준을 눈으로.** 로컬 MySQL에서 두 세션으로 Lost Update·Read Skew·Phantom을 재현하고, `READ COMMITTED`→`REPEATABLE READ`→`SERIALIZABLE`로 올리며 무엇이 막히는지 본다. ParticleDB가 "SI 표방인데 G-Single"이 왜 사고인지 체감.
- [ ] **"완료 기준"을 테스트로.** 최근 내가 AI에게 맡긴 수정 하나를 골라, 수용 기준을 Co-Design Bench식으로 5~8개 원자 항목으로 쪼개 "통과율"과 "전부 통과(완료)"를 따로 센다. 69.9%/26.4% 간격이 내 작업에서 얼마인지.
- [ ] **MCP 도구 설명 A/B.** 쓰는 MCP 서버 하나의 도구 description·파라미터 이름을 두 판으로 바꿔(장황 vs 간결, 동사 중심 vs 명사 중심) 같은 과제 3개를 시키고 ① 성공 ② 호출 횟수 ③ 토큰을 비교. MICA의 "표현이 행동을 가른다"가 내 환경에서도 나오는지.
- [ ] **커널 패치 점검을 습관으로.** 내가 쓰는 EC2/로컬 리눅스에서 `uname -r`·배포판 트래커·`needs-restarting -r`로 CVE-2026-98432 노출 여부를 확인하고, "설치 ≠ 적용(재부팅)"을 체크리스트로 적어 둔다. `postMessage` 쓰는 프런트 코드가 있으면 origin+source 둘 다 검사하는지 점검.

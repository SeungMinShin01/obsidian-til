원문: 김규남(공통시스템개발팀) · 2021-09-30(수정 2021-12-08) · Backend · 태그 Spring Boot, 코틀린, 테스트코드

## 배경

글은 코틀린으로 스프링 프로젝트를 짜도 JUnit·AssertJ·Mockito는 그대로 쓸 수 있지만, 코틀린에 익숙해질수록 테스트만 예전 방식이라 비즈니스 코드(코틀린 DSL 스타일)와 괴리가 생긴다고 설명한다. Mocking·Assertion에서 DSL을 쓸 수 없다는 점이 핵심 원인이며, 대안으로 Kotest와 Mockk를 제시한다.

## 핵심

- Kotest 설정: `useJUnitPlatform()` + `kotest-runner-junit5`, `kotest-assertions-core`.
- 레이아웃 3종 비교 — AnnotationSpec(JUnit `@Test`와 유사, 마이그레이션용), BehaviorSpec(given/when/then, `when`은 백틱), DescribeSpec(describe/context/it, 저자 팀 채택).
- Assertion 대응: `shouldBe`(≈`isEqualTo`), `forExactly(n)`/`forAtLeast(n)`(Inspectors), `shouldThrow<T>`/`shouldThrowAny`.
- `@SpringBootTest` 연동: `kotest-extensions-spring` + `override fun extensions() = listOf(SpringExtension)`, 빈은 `@Autowired lateinit var`.
- 격리 모드: 기본 SingleInstance는 인스턴스를 공유해 Mocking이 충돌할 수 있어, 완전한 격리를 원하면 `isolationMode = IsolationMode.InstancePerLeaf`를 권한다(InstancePerTest도 있음).
- Mockk: `every { } answers { }`, `mockk<T>(relaxed = true)`, `spyk()`, `returnsMany`, `returns X andThen Y`, `just Runs`, 검증은 `verify(atLeast/atMost/exactly)`·`verifyAll`·`verifySequence`.
- 스프링 빈 목킹은 `com.ninja-squad:springmockk:3.0.1`의 `@MockkBean`/`@SpykBean`(Mockk 자체는 `@MockBean` 미제공).
- 반려한 대안: Spek은 업데이트가 활발하지 않아 저자 팀이 Kotest로 이전했다고 한다. 원문 예제에 오타(`retunrs`)가 있어 공식 문서 확인을 권한다.

## 내 프로젝트와의 연결

직접 연결은 약하다 — 글은 코틀린 기준이고 WMS는 Java + Spring Boot다. 구조적으로 비슷한 지점만 짚으면: (1) 격리 모드 논점은 WMS 재고 동시성 테스트에서 테스트 간 상태 공유(공유 Mock·공유 DB)가 결과를 오염시키는 문제와 같다. 테스트마다 새 인스턴스·롤백으로 격리한다는 발상이 닮았다. (2) Mockk의 `returnsMany`/`andThen`은 수집기에서 외부 API를 "첫 호출 실패 → 두 번째 성공"으로 흉내 내는 재시도 테스트와 대응된다(Java에서는 Mockito `thenThrow().thenReturn()`). (3) `@MockkBean` ↔ `@MockBean`처럼 도구는 달라도 대응 키워드로 옮겨 쓰는 감각은 Java 쪽에도 그대로 쓰인다.

## 오늘 정리할 것

1. Mockito에서 "연속 호출 시 다른 값/예외"를 만드는 방법(`thenThrow(...).thenReturn(...)`)을 찾아, 수집기 재시도 로직 테스트 시나리오 하나를 글로 적어 본다.
2. JUnit 5에서 테스트 간 격리(`@Transactional` 롤백, `@TestInstance` 기본 PER_METHOD)가 어떻게 동작하는지 확인해 Kotest 격리 모드 3종과 표로 대응시킨다.
3. `@MockBean`과 `@SpyBean`의 차이를 한 줄씩 정리하고, WMS 서비스 테스트에서 어느 쪽이 맞을지 예를 하나 든다.
4. 원문 Kotest/Mockk 키워드(`shouldBe`, `verifySequence`)에 대응하는 AssertJ/Mockito 이름을 찾아 대응표를 만든다.

> 예습자료: 위 내용은 글의 설명을 요약한 것이며 사용자가 직접 검증하지 않았다.

## 배경

글은 검색팀의 테스트 시간 문제에서 출발한다고 설명한다. 검색 시스템은 20개 이상의 멀티모듈이고, ES와 MySQL을 컨테이너로 미리 띄워 두고 통합 테스트 위주로 검증한다. 테스트가 1,500개를 넘자 CI/CD에서 `gradle test`가 10분을 넘겼고, 빠른 피드백을 위해 병렬 테스트를 도입하기로 했다. 그런데 `gradle test --parallel`을 그냥 붙이면 실패했고, 글은 원인을 "공유 의존성(ES, DB)에 대한 격리 부재"로 짚는다.

## 핵심 (문제 → 시도 → 반려 → 해결)

- **문제**: 테스트 확장(`ElasticsearchContainerExtension`)의 `beforeAll`이 "alias가 있으면 인덱스를 만들지 않는" 체크 후 생성하는데, 병렬에서는 A·B 테스트가 동시에 "없음"을 확인하고 둘 다 생성해 같은 alias(`test-main`)를 가진 인덱스가 둘 이상 생긴다 → 쓰기 대상을 알 수 없다는 오류. check-then-act 경쟁 조건이다.
- **반려 1 — 스레드 락**(`synchronized`, `ReentrantLock`): `--parallel`은 모듈 단위로 **별도 Gradle Test Executor(=별도 프로세스)**에서 돌기 때문에 효과가 없다. 글은 학습 테스트(core·parallel-a·parallel-b 모듈, static `AtomicInteger` 카운트)로 프로세스가 분리됨을 로그로 확인했다고 한다.
- **반려 2 — 분산락**(RDB로 프로세스 간 락): 확장에 DB 의존성이 생기고, 락 획득·반납 오버헤드로 동시 처리 성능이 떨어지며, 결국 인덱스를 공유하므로 문서 색인·삭제 동시성은 그대로라 "근시안적"이라고 평가한다.
- **채택 — 네임스페이스 전략**: 프로세스마다 고유 식별자(static `RANDOM_UUID`, JVM이 프로세스별이라 공유되지 않음)를 `TestIndexNameFactory`가 indexName·aliasName의 prefix로 붙여 프로세스마다 자기 인덱스를 갖게 한다. 공유 의존성·락 오버헤드 없이 ES만으로 해결된다는 점이 장점이다.
- **접근 쪽 해결**: 인덱스는 분리됐지만 코드는 여전히 `IndexType.getSearchAlias()`로 `test-main`을 찾는다. Fake 객체 오버라이딩은 운영 코드 복잡도 증가·prefix 누락 실수 위험으로 **반려**하고, `IndexType`이 enum(JVM당 싱글톤)임을 이용해 `prefix` 필드에 `@Setter`를 두고 테스트에서만 `setAliasPrefixForTest()`로 바꾸는 방식을 택했다(enum 불변성을 깨는 트레이드오프는 팀 합의로 감수).
- **격리 후 남은 문제 ① Too Many Connections**: HikariCP는 `minimum-idle`을 따로 안 주면 `maximum-pool-size`(기본 10)와 같아져, 프로세스마다 10개씩 커넥션을 잡는다. MySQL 한도를 늘리는 대신 `minimum-idle`을 낮춰(최소 1개) 근본 원인을 잡았다.
- **남은 문제 ② ES 서킷브레이커**: 프로세스마다 인덱스를 만드는데 정리가 없어 클러스터에 인덱스가 쌓이고 메모리가 늘어 서킷브레이커가 열렸다. `AfterAllCallback`으로 테스트 클래스 종료 시 해당 네임스페이스 인덱스를 삭제하고, `@Tag`로 테스트마다 필요한 인덱스만 만들도록 했다(태그가 없으면 실패, 리플렉션으로 태그 상수↔생성 전략 매칭 검증).
- **결과**: 로컬 4m 5s → 1m 48s, CI/CD 10m 41s → 5m 3s (2배 이상, `gradle scan`으로 비교).

## 내 프로젝트와의 연결

직접 연결이 큰 글은 아니고, 구조적으로 비슷한 지점이 두 곳 있다. WMS에서 재고·입고 통합 테스트를 Testcontainers 등으로 돌리게 되면 "테스트끼리 공유하는 DB/스키마"가 같은 종류의 격리 문제를 만든다 — 글의 순서(락 대신 테스트마다 격리된 이름 공간을 준다)를 스키마·데이터 접두사에 대응해 볼 수 있다. 또 하나는 HikariCP `minimum-idle` 기본값 함정으로, 부하 테스트나 인스턴스를 여럿 띄우는 배포 환경에서 커넥션 한도를 넘기는 원인이 될 수 있다. 수집기 쪽은 GitHub Actions 병렬 job이 같은 SQLite 파일·같은 저장소를 건드릴 때의 격리(job별 파일 분리)와 구조적으로 닮았다. 다만 이는 글의 주장이 아니라 연결 후보이다.

## 오늘 정리할 것

1. `gradle test --parallel`이 "모듈 단위·프로세스 분리"로 동작한다는 점을, 작은 멀티모듈에서 static 카운터를 찍어 직접 확인해 본다(글의 학습 테스트 재현).
2. 내 Spring 설정에서 HikariCP `maximum-pool-size`와 `minimum-idle`의 기본값 관계를 공식 문서에서 찾아 한 줄로 정리한다.
3. "check-then-act 경쟁 조건"이 우리 코드(입고 중복 체크, 수집기의 중복 판정)에서 어디에 숨어 있을지 후보 2곳을 적는다.
4. 스레드 락 / 분산락 / 격리(네임스페이스)의 적용 범위를 "프로세스 경계" 기준으로 한 표로 비교한다.

## 배경

글은 2021년 6월 출시된 음식점 사장님용 통계 서비스 "우리가게NOW"를 다룬다. 주문 접수율·접수 시간·조리 시간·준수율 같은 지표를 보여 주고, 모든 가게와 비교한 상대평가(순위)까지 제공해야 했다. 조건은 두 가지였다 — 매일 아침 9시 전에 갱신이 끝나야 하고, 데이터는 기존 실시간 서비스보다 수백 배 규모(수백만 건 주문)였다. 팀에는 과거 데이터 배치 처리, Airflow, SparkSQL이 모두 낯선 영역이었다고 글은 설명한다.

## 핵심

- 첫 설계: 데이터 레이크에서 주문 데이터를 추출 → 팀 RDB에 적재 → Java 배치로 통계 계산 후 재적재. 테스트가 쉽고 변경에 유연하다는 장점이 있었다.
- 반려 이유 ①: 오전 6~9시, 3시간 안에 수백만 건을 처리할 수 있을지 불확실했다.
- 반려 이유 ②: 주문 전량을 팀 RDB에 쌓는 저장·관리 부담이 컸다.
- 전환: 적재 과정에서 직접 통계를 계산하는 방식으로 바꿨다. 분산 처리(SparkSQL, executor 수 조절 가능) → 중간 결과는 Hive 테이블 → 최종 결과만 팀 RDB에 저장.
- 불안 해소 방법: "일주일의 빈 시간이 있다면 새 기술의 불안을 없애려고 무엇을 할까"를 물어, 가장 복잡한 요구인 상대평가를 먼저 구현해 봤다. `RANK() OVER (ORDER BY cooking_time_rate DESC)`로 동점자 동일 순위·다음 순위 건너뜀을 만족함을 확인했다.
- 결과: 오픈 첫날 30분 이내, 이후 평균 30분 유지. 요구의 대부분은 SparkSQL로 충분하고, 복잡한 요구가 생기면 그 부분만 고칠 수 있다고 글은 말한다.
- 교훈 세 가지: 가치 우선순위("9시까지 최신 통계")를 먼저 정하기 / 막연한 기술 불안을 구체적 질문과 코드 검증으로 바꾸기 / 실시간 데이터와 통계 데이터의 성격 차이 인식하기.

## 내 프로젝트와의 연결

수집기와는 "정해진 시각 안에 끝나야 하는 무인 배치"라는 구조가 비슷하다. 글은 원본 전량을 저장하지 않고 적재 단계에서 줄여 최종 결과만 남겼는데, 수집기의 SQLite 계층에서 원본 공고를 얼마나 보관하고 무엇을 집계해 저장할지 생각할 때 비교 지점이 된다(규모는 전혀 다르므로 직접 이식은 어렵다). WMS에서는 일별 입출고·재고 리포트를 만든다면 윈도우 함수(RANK 등)와 "중간 결과/최종 결과 분리"가 참고가 될 수 있다. 연결이 강하지는 않다.

## 오늘 정리할 것

1. `RANK()`·`DENSE_RANK()`·`ROW_NUMBER()`의 동점 처리 차이를 작은 테이블(동점 포함)로 직접 돌려 결과 비교하기.
2. 수집기의 현재 흐름(수집 → 저장)에서 "원본 전량 저장"과 "적재 시 집계" 중 무엇을 하는지 한 줄로 적고, 마감 시간이 있다면 몇 분인지 적어 보기.
3. 글의 "불안을 구체적 질문으로 바꾸는" 방식을 WMS에서 아직 불안한 기술 하나(예: 분산 락)에 적용해 질문 3개 써 보기.

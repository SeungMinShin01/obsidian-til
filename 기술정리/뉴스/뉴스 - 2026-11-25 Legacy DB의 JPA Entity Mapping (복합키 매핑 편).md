## 배경

배달의민족 광고시스템 팀은 레거시 시스템을 한 번에 갈아엎지 않고, 기존 RDBMS(MS-SQL)는 그대로 둔 채 Spring Boot / JPA 기반 신규 시스템으로 조금씩 떼어내는 전략(교살자 패턴, strangler pattern)을 택했다고 글은 설명한다. 떼어내기의 첫 단계가 레거시 테이블을 Entity로 매핑한 뒤 JOIN으로 얽힌 코드를 API로 격리하는 일이었는데, 레거시 테이블은 데이터·테이블 중심으로 설계되어 IDENTITY 대신 자체 PK 생성 규칙을 쓰고, 부모 PK를 자식 PK로 전파하는 **식별관계 + 복합키**가 대부분이었다. 그래서 테이블 매핑에만 일주일 이상 걸렸고, 그 과정에서 `@EmbeddedId`로 시작했다가 `@IdClass`로 돌아선 시행착오를 공유한다.

## 핵심

- **식별관계 vs 비식별관계**: 식별관계는 부모 PK가 자식·손자 PK로 전파되어 PK 컬럼이 늘고, JOIN SQL과 PK 인덱스가 커지며 구조가 경직된다. 대신 PK 인덱스 활용이 좋고, 하위 테이블만으로 JOIN 없이 조회가 가능하다(예: Pay_Id로 Pay_Shop만 조회). 비식별관계는 대부분 대리키를 쓰고 JPA에서 `@GeneratedValue`로 간단히 생성된다고 글은 정리한다.
- **예제 구조**: Pay → PayDetail → PayShop 식으로 PK가 전파되는 식별관계. PayShop의 PK는 payNumber·paySeq·payDetailId·shopNumber 같은 컬럼 조합.
- **시도 1 — `@EmbeddedId`**: 더 객체지향적이라 먼저 택했다. `@MapsId`로 부모(Pay)의 id를 자동 할당할 수 있고, Id 클래스 안에서 `shopNumber` 컬럼 길이 초과 입력을 검증하는 식의 캡슐화도 된다.
- **반려 사유**: 식별관계가 여러 단계로 이어지자 Id 클래스가 PayShopId → PayDetailId → PayId처럼 중첩됐다. 비즈니스적으로 의미 있는 **payNumber**를 꺼내려면 객체 그래프를 깊이 타야 하고(JPQL로 ID 값을 읽을 때도 같은 문제), 의미 있는 키가 Id 클래스 속에 숨어 Entity에서 바로 보이지 않았다.
- **최종 — `@IdClass`**: Entity에 `@Id` 필드를 평평하게 나열하고, 연관관계용 `@JoinColumn`에는 `insertable = false, updatable = false`를 붙여 **연관관계는 "읽기용 연결"만 하고 실제 값은 `@Id` 필드가 담당**하게 했다. 그래서 생성자에서 `@Id` 값들을 직접 할당하고 연관관계도 따로 맺어 줘야 했다.
- **트레이드오프 표(글 요약)**: `@EmbeddedId` — 장점: 객체지향적, `@MapsId`로 생성 편리 / 단점: 복합키가 2개 이상 테이블에 식별관계로 이어지면 복잡도 증가. `@IdClass` — 장점: 의미 있는 PK를 필드로 명시적 노출, 여러 테이블 식별관계에서도 객체 연관관계 단순 / 단점: 필드 선언이 Entity마다 중복, `@MapsId` 활용 불가라 객체 생성 시 주의.
- **글의 권고**: 복합키가 하나뿐이면 `@EmbeddedId`, 복합키 식별관계가 여기저기 있으면 `@IdClass`. 중복을 조금 허용하더라도 레거시 테이블의 설계 의도를 Entity에 그대로 드러내 "운영 중인 테이블과 이질감 없는 심플한 구조"를 택했다고 한다.
- **장기 계획**: JOIN으로 쓰던 부분을 API로 철저히 분리·격리한 뒤 재개발하고, 신규 시스템에서는 **비식별관계 + Long 대리키**를 쓰겠다고 밝힌다. 즉 `@IdClass`는 이관 기간의 과도기 선택이다.

## 내 프로젝트와의 연결

WMS는 새로 설계하는 시스템이라 글이 말하는 "최종 목적지"(비식별관계 + Long 대리키)에서 출발할 수 있다는 점이 먼저 눈에 띈다. 다만 구조적으로 비슷한 지점이 있다 — 재고 테이블은 자연스럽게 (상품, 로케이션) 조합이 유일해야 하고, 입출고 상세는 (전표번호, 라인번호)처럼 부모 키 + 순번 구조가 되기 쉽다. 여기서 복합키 PK로 갈지, 대리키 PK + 복합 유니크 제약으로 갈지가 그대로 결정 로그 소재가 된다. 글의 논리를 빌리면 "의미 있는 키를 명시적으로 드러내는 것"과 "JOIN·인덱스 단순화"를 저울질하는 것이고, 동시성(재고 행 락)과 인덱스 측정 단계에서도 PK 선택이 영향을 준다. 수집기의 SQLite 저장 계층도 (출처, 공고 ID) 조합으로 중복을 막는다면 같은 질문 — PK를 복합키로 둘지, 대리키 + UNIQUE로 멱등 upsert를 걸지 — 를 짚어 볼 수 있다.

## 오늘 정리할 것

1. woowabros/spring-data-jpa-sample 저장소에서 PayShop의 `@EmbeddedId` 버전과 `@IdClass` 버전 코드를 찾아, 두 방식에서 payNumber를 꺼내는 코드 경로를 나란히 적어 본다.
2. `@IdClass` 쪽 Id 클래스가 지켜야 할 조건(Serializable, 기본 생성자, equals/hashCode, 필드명 일치)과 `@MapsId`가 무엇을 해 주는지 표로 정리한다.
3. `@JoinColumn(insertable = false, updatable = false)`를 붙였을 때 INSERT SQL에 어떤 컬럼이 어느 필드에서 들어가는지 로그(`spring.jpa.show-sql`)로 직접 확인해 본다.
4. WMS 재고·입출고 상세 테이블을 "복합키 PK" 안과 "대리키 + 복합 UNIQUE" 안으로 각각 스케치하고, 기각 사유를 결정 로그 형식(문제→대안→선택→기각 사유)으로 메모한다.

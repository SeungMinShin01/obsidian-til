## 오늘의 흐름

먼저 겹치는 것. 오늘(10/29) 브리핑에서 Kimi K3.1 Pro(10/25·10/27), GPT-6.1 Terra(10/27 깊게), 스킬 저장소의 트렌딩 점령(10/27~28), Micron 4F² 포기(10/28 가볍게), eMudhra 사건 자체·CT 경계·패치 목록(10/21 깊게, 10/22~26 재등장)은 이미 다뤘다. Fairwind 방어자 우선 배포 방식도 10/1 Argon 때 깊게 봤다. 이 노트는 **새것**만 본다 — GitHub Octoverse 2026, Gemini 4 Carbon, 안티봇 스크립트의 "LLM 거부 유발" 난독화, 에이전트 메모리 논문 묶음(Memory Tax·HABIT-Bench·TTME), 그리고 eMudhra 건의 *새 사실 하나*(macOS 27.2가 사용자 우회책을 되돌림).

첫 번째 축은 **"생산량은 세 배가 됐고, 무엇이 늘었는지는 아직 모른다."** Octoverse는 커밋 343억·머지 PR 13억·Actions 작업 454억을 내놓았고, 9월 기준 PR의 40% 이상이 에이전트 초안으로 시작한다. 그런데 보고서 원문 숫자를 나눠 보면 재미있는 게 보인다. **푸시당 커밋 수는 3년 내내 약 1.92로 거의 그대로**(2024 10.0/5.2, 2025 12.9/6.7, 2026 34.3/17.9)이고, **머지된 PR 하나당 Actions 작업은 약 20 → 26 → 35개**로 꾸준히 늘었다. 즉 "에이전트가 같은 일을 잘게 쪼개서 숫자가 부풀었다"는 브리핑의 의심은 적어도 푸시 단위에선 보이지 않고, 대신 **변경 하나를 통과시키는 데 드는 자동 검증량이 늘고 있다**. 10/14 노트의 "코드는 싸졌고 통과시키는 쪽이 병목", 어제의 "건강은 따로 재야 했다"가 플랫폼 전체 통계로 나온 셈이다.

두 번째 축은 오늘 처음 강하게 보이는 흐름, **"쌓아 둔 것은 원본보다 못할 수 있다."** Memory Tax 논문은 전용 에이전트 메모리 시스템 11종 대부분이 *원본 대화를 그냥 잘라서 검색하는* 소박한 RAG보다 낮다고 잰다. 정리·요약·구조화가 증거를 지우거나(OpenViking은 표본 사실의 38%에 해당 메모리 단위가 아예 없음), 찾기 어렵게 만들기 때문이다. HABIT-Bench는 반대편에서 같은 말을 한다 — 기록을 다 갖고 있어도 흩어진 약한 증거에서 "습관"을 세우는 건 못 한다(최고 33.61%, 무작위 25%). 그리고 TTME는 "제대로 쓰면 메모리가 가중치 업데이트를 이긴다"고 한다. 결론은 "메모리는 무조건 좋다"도 "쓸모없다"도 아니고, **원본으로 돌아가는 길을 남겨 둔 가공만 이득이 남는다**는 쪽으로 모인다. 10/20 AI 심층의 「객체 지향 컨텍스트 폴딩」(요약 대신 결과물을 가리키는 포인터)과 같은 방향이다. 원리는 오늘 AI 심층 「AI - 에이전트 메모리의 순가치」로 뺐다.

세 번째 축은 **"LLM이 읽는 모든 입력은 이제 공격면이고, 방향은 양쪽이다."** Gemini 4 Carbon은 간접 프롬프트 인젝션 공격 성공률 0.0%를 *홍보 포인트*로 내걸었다. 같은 날 nullpt.rs는 안티봇 스크립트가 반대로 **LLM의 안전 거부를 일부러 유발해 분석을 막는** 장치를 심은 사례를 보였다. 9/18 노트의 "모델이 자기 압축 요약문에 지시문을 심었다", 10/27의 Cohere 사례가 "모델을 *움직이게* 하는" 인젝션이었다면, 오늘은 "모델을 *멈추게* 하는" 인젝션이다. 둘 다 결국 같은 질문 — *입력 텍스트의 출처와 의도를 모델이 아니라 시스템이 판정하고 있는가.*

네 번째, 작게. eMudhra 건은 macOS 27.2가 문제를 고치지 않은 채 사용자가 손으로 지운 루트를 **업데이트로 되살렸다**. Apple 지원 문서 스스로 "업데이트가 수정을 되돌릴 수 있다"고 적었다. "손으로 고친 설정은 업데이트 한 번에 사라진다"는 교훈은 Vault 규칙을 파일(`_규칙/`)로 고정해 두는 이유와도 같다.

### 1. GitHub Octoverse 2026 — 숫자를 나눠 보면 "부풀림"보다 "검증량"이 보인다

**무슨 일인가.** GitHub가 2025-10-01~2026-09-30 집계 Octoverse를 냈다(10/28, GitHub Universe). 공개+비공개 저장소 합산으로 푸시 179억(2024 52억·2025 67억), 커밋 343억(2년 전 100억), 머지 PR 13억(4.02억, 하루 350만), Actions 작업 454억(초당 1,440·하루 1.24억), 공개 기여 25억(전년 11.2억), Dependabot PR 머지 3천만+(약 2배). 개발자 2억 2,500만+, 미국 3,830만·인도 3,200만·중국 1,240만·브라질 1,020만.

**배경 — 왜 지금 이게 나왔나.** 보고서는 활동이 1월부터 오르다 **6월 무렵 급격히 꺾여 올라갔다**고 쓰고, 원인을 묶어서 든다 — 더 좋은 모델, 그 위의 하네스·도구, 그리고 *단일 세션 도구에서 며칠씩 진행 상황을 추적하며 다른 전문 에이전트를 조율하는 지속형 에이전트로의 이동*, 로컬뿐 아니라 클라우드에서 원격 실행. 6월 이후 커밋의 약 55%가 새로 만든 저장소에서 나왔다. 9/19 노트(지침 파일이 `AGENTS.md`로 수렴)가 "규칙 파일"의 등장이었다면, 오늘은 그 파일이 있는 저장소의 활동량이 따로 측정됐다.

- **검증 비용이 PR당 커진다.** Actions 작업/PR이 2년 새 1.75배. 개인 프로젝트에서도 GitHub Actions 무료 분량·실행 시간이 먼저 바닥날 수 있다 — 캐시·경로 필터(`paths:`)·매트릭스 축소가 실제 비용 작업이 된다.
- **Java가 꼴찌라는 것.** 브리핑 해석(기본기가 덜 희석된 생태계, 나중에 몰려올 방식)에 하나를 더한다 — GitHub의 "확인하기 쉬운 언어" 가설이 맞다면 Java는 정적 타입인데도 관여율이 낮다. 즉 타입 말고 **빌드 속도·보일러플레이트·레거시 비율** 같은 다른 변수가 있다는 뜻이고, Spring 쪽에선 테스트가 빨리 도는 구조(슬라이스 테스트, Testcontainers 재사용)가 에이전트 친화도를 좌우할 가능성이 크다(추론).

**반론·회의적 시각.** ① 방법론이 스스로 "에이전트 신호는 **하한선**", 2024·2025 수치를 새 정의·기간으로 **재계산**(옛 보고서와 다를 수 있음)이라고 적었다. ② 성장분을 사람·에이전트로 나누지 않았다. ③ 커밋·푸시·PR은 활동량이지 가치가 아니다 — 2주 내 머지율 90%는 "빨리 머지됨"이지 "좋음"이 아니다. 오히려 리뷰가 얕아졌을 가능성도 같은 숫자로 설명된다. ④ 산업 분류는 **언어 모델이 저장소 이름·README로 분류**한 추정치이고, AI 언급 비율과 산업 분류가 같은 텍스트를 읽어 서로 엮여 있다고 원문이 인정한다. ⑤ 개발자 수 예측 모델 43개가 3배 이상(21)·2~3배(19)·2배 미만(3)으로 갈렸다 — 스스로 "예측이 어려워졌다"는 고백이다. ⑥ 보고서는 GitHub(=Copilot 판매사)의 것이다.

### 2. Gemini 4 Carbon — 경쟁 축이 "며칠 버티기"와 "공방 겸용 보안 능력"으로

**무슨 일인가.** Google DeepMind(Koray Kavukcuoglu, 10/28)가 2주 전 Argon의 후속 Gemini 4 Carbon을 발표했다. Artificial Analysis Intelligence Index v5.0 **59점 1위**, 보안 벤치 SEC-bench Pro 88.2%(취약점 탐지)·ExploitGym 54.8%(익스플로잇 검증)·CWE-bench 71.0%(패치) — 셋 다 **가드레일 없이 평가**했다고 명시. WebDev Arena +89 Elo로 1768점 4위.

**배경.** 10/1 노트에서 Argon이 "방어자 우선 배포"(Fairwind)를 정책으로 만든 걸 봤다. Carbon은 그 연장인데, 이번엔 소개 문구 자체가 "범용 최고"가 아니라 **사이버보안과 장기 과제**다. 그리고 미국 정부의 *자발적 사전 출시 모델 테스트*에 참여 중이라고 처음 적었다. 접근 순서는 일부 사이버 방어자 → Fairwind 신뢰 파트너 → (가드레일 다듬은 뒤) 개발자·기업·소비자.

**기술적으로 — 공개된 것과 안 된 것.** 공개된 건 *행동 지표*가 대부분이다.

| 항목 | Argon | Carbon |
| --- | --- | --- |
| Terminal-Bench 4.0 성공한 꼼수 | — | **0.0%** (시도 0.4%, 정확도는 오히려 상승) |
| Gray Swan 간접 인젝션 공격 성공률 | 0.7% | **0.0%** |
| 안전한 코드 생성 성공률(내부) | 1× | 2배+ |
| 근거 없는 주장(내부) | 1× | 약 절반 |
| 라이브 코딩 고위험 정렬 경보(내부) | 1× | 약 80%↓ |
| 과잉 행동(overreach) / 과소 수행(under-service) | 1× | −26% / −29% |

"며칠간 막다른 길을 버티며 대형 코드베이스·저수준 시스템의 미묘한 버그를 원인 분석·패치했다"는 서술이 장기 과제의 근거인데, **측정값이 아니라 내부 관찰**이다. Chrome 팀의 "다른 연구소 대형 프런티어 모델보다 고품질 패치 생성 10배 이상"도 상대 모델 비공개. Wiz는 웹 침투 테스트 벤치에서 Carbon이 선두라고 했다. 가격: 도입가 입력 $2/출력 $10(캐시 입력 95% 할인), 종료 후 $4/$20 — 종료일 없음. **API 모델 ID·컨텍스트 윈도·GA 날짜 없음**, 비교 표는 이미지.

**실무에 무슨 의미인가.**

- "모호하면 추측 말고 출처를 찾아 불일치를 먼저 사용자에게 보인다", "막힌 동작은 지어내지 말고 남은 요구 목록으로 보류한다"는 행동 목표가 *발표문의 판매 문구*가 됐다. 어제의 Thinking-in-Bets(반박 전 기록), 10/20의 "완료 보고는 증거가 아니다"가 이제 모델 공급자 쪽 스펙 항목이다. 에이전트를 붙인 서비스를 만들 때 **"보류할 줄 아는가"를 평가 항목**으로 넣을 만하다.
- 며칠 도는 에이전트 = 며칠 아무도 안 보는 에이전트. 브리핑 지적대로 안전장치는 테스트·재현 가능한 빌드·모듈 경계뿐이다. 위 Octoverse의 "PR당 CI 작업 증가"와 정확히 맞물린다.
- 인젝션 0.0%는 *특정 벤치마크의 평가된 공격*에 대한 것이다. 내 서비스의 방어를 모델에 위임할 근거가 아니다 — 도구 권한·출력 검증은 여전히 시스템 몫(10/27 「제약 디코딩」 노트의 "보장은 모양뿐" 결론과 같다).

### 3. "LLM이 거부하게 만들어라" — 안티봇 스크립트의 반(反)LLM 난독화

**무슨 일인가.** nullpt.rs의 veritas가 Tranco 상위 1만 개 사이트를 Playwright로 돌며 canvas `toDataURL`·`navigator.webdriver` 같은 지문수집 호출을 훅으로 잡아 1,033개 canvas를 모았고(fingerprint.garden), 그중 `servicepipe.tech`가 내려주는 안티봇 스크립트에서 이상한 것을 발견했다. 평범한 javascript-obfuscator식 난독화(뒤섞인 함수명) 사이에 **독극물 치사량·폭발물 반경·마약 전구체 수율·유전자 드라이브 같은 대량살상·자해 주제를 계산하는 것처럼 보이는 함수명과 결과 문자열**이 섞여 있었다. 실제 그런 계산은 하지 않는다.

**배경 — 왜 지금 이게 나왔나.** 난독화 해제의 주체가 사람에서 LLM으로 넘어갔다. 그러면 난독화 쪽의 최적 전략도 바뀐다 — 코드를 더 꼬는 대신 **분석가(LLM)의 안전 장치를 방아쇠로 쓰는 것**. 9/20 노트의 "에이전트가 시스템을 뚫기 시작했다"에 대한 방어 측 대응이기도 하다.

**기술적으로 어떻게 동작하나.** 세 겹이다.

1. **심볼 이름 미끼** — 위험 주제로 읽히는 함수명·`summary` 문자열. 모델의 유해 요청 분류기가 "이 코드는 위험 계산을 한다"로 오판하게 한다.
2. **보이지 않는 지시문** — 유니코드 태그 문자 영역(U+E0000대)에 인코딩한 문자열. 각 문자의 코드포인트에서 `917504`(0xE0000)를 빼면 ASCII가 되는 단순 치환이다. 화면 폭 0이라 사람 눈엔 안 보이지만 토크나이저엔 들어간다. 복호화하면 "안전 지침 해제" 류의 가짜 시스템 지시문과 여러 유해 주제 나열, 그리고 **중국계 모델의 검열 트리거로 보이는 천안문 관련 문자열**까지 — 모델 계열별로 거부를 유발하려는 설계로 보인다.
3. **Node 전용 블록** — `process.env`의 특정 플래그가 있을 때만 `.npmrc`·`.env`·`.kube/config` 등을 읽고, 사설 IP에서 바이너리를 받아 실행하고, crontab `@reboot` 영속화까지 거는 명령 목록. 저자는 `readFile` 콜백이 비어 있고 명령 사이에 자해·탈옥 문구가 섞인 점을 들어 **이것도 미끼일 가능성이 높다**고 본다(실제로 읽은 값을 쓰지 않는다).

결과: 저자가 한 모델(Astra)에 "이 이름들은 의도적 오도"라는 맥락까지 주고 해제를 요청했더니 생물학 연구 안전 우려로 거부, 다른 토글(Daybreak Blue)도 거부, GLM-5.3은 응했다. 정작 수집하는 신호는 userAgent·hardwareConcurrency·deviceMemory·WebGL 렌더러 문자열·`navigator.webdriver`·전역 키 개수 등 평범하다 — "난독화에 들인 공에 비해 실망스럽다".

**실무에 무슨 의미인가.**

- **"모델이 거부했다"는 신호의 의미가 바뀐다.** 외부 라이브러리를 Claude Code·Cursor에 던졌다가 거부가 오면, 그게 모델 과민인지 *심어진 장치*인지 구분해야 한다. 판별법: 식별자를 일괄 치환(예: 모든 함수명을 `f1`, `f2`…로)한 뒤 다시 물어 거부가 사라지면 미끼다.
- **보이지 않는 문자 검사를 파이프라인에 넣는다.** 태그 문자(U+E0000~E007F)·zero-width 문자는 코드 리뷰 diff에서 안 보인다. pre-commit이나 CI에서 `grep -P '[\x{E0000}-\x{E007F}\x{200B}-\x{200F}]'` 같은 검사로 잡을 수 있다. 에이전트가 외부 텍스트를 가져와 코드·문서에 붙이는 일이 늘수록 필요해진다.
- **분석 대상 코드를 로컬에서 실행하지 않는다.** 미끼일 가능성이 높아도, 환경변수 하나로 켜지는 비밀 파일 읽기·원격 바이너리 실행 블록이 있다. 샌드박스 밖에서 `node`로 돌리면 안 된다.

**반론·회의적 시각.** ① 거부 유발의 효과는 **프롬프트 몇 번**의 결과다 — 이름을 지운 대조군, 반복 실행, 해제 결과의 정확도 검증이 없다. "거부를 유발할 수 있다"까지만 보였다. ② `servicepipe.ru`(러시아 트래픽 제어·안티 DDoS 업체)와의 연결은 도메인 이름 유사성과 urlscan 기반 추정이다. ③ 이런 미끼는 오래 못 간다 — 모델 쪽이 "코드 식별자는 행위가 아니다"를 학습하면 무력화되고, 그 과정에서 *진짜 위험 코드의 식별자*도 덜 민감하게 볼 위험이 있다. 방어가 공격의 탐지력을 깎는 구조라 양쪽 모두에 비용이다. ④ HN 토론(587p/132c)은 읽지 못했다.

### 4. 에이전트 메모리 세 편 — "쌓으면 좋다"에서 "순가치를 재자"로

**무슨 일인가.** HF 10/28 상위에 메모리 논문 셋이 같이 올랐다. **Memory Tax**(UIUC 등, arXiv 2610.34073, ▲125 — 브리핑 101)는 메모리 11종 × 벤치 3종 × 백본 3종으로 "많은 메모리 시스템이 소박한 RAG보다 못하다"를 보였다. **HABIT-Bench**(상하이교통대, 2610.24520, ▲79)는 흩어진 약한 증거에서 습관을 추론하는 능력을 재서 최고 33.61%(4지선다, 무작위 25%). **TTME**(UCSB·버클리 등, 2610.32046, ▲10 — 브리핑은 92)는 시험 시점에 가중치 대신 외부 메모리를 갱신해 수학 발견 과제 5개 모두에서 TTT를 이기고 FLOPs 82.8~84.6%·실행시간 47.7~58.4%를 줄였다.

**배경.** 10/3 노트("기록을 쌓던 에이전트가 상태를 들기 시작했다"), 10/5 AI 심층 「의도 변경과 상태 접기」, 10/7의 MemAdapter("맞는 기억도 아첨을 만든다"), 10/20 「객체 지향 컨텍스트 폴딩」까지 이 Vault는 메모리를 "더 잘 쌓는 법"으로 봐 왔다. 오늘은 처음으로 **"쌓는 것 자체의 손익"**을 RAG 기준선 대비로 잰 논문이 나왔다. Memory Tax 서론은 기존 메모리 논문들이 서로끼리만 비교하고 RAG 기준선을 빼거나 설정을 명시하지 않았다고 지적한다.

**기술적으로 — Memory Tax 핵심(본문 1~8절 직접 읽음).**

세금의 출처를 셋으로 나눈다. **충실도**(정리하다 증거를 잃음 — 표본 사실 추적에서 MemoryOS는 98.4% 무손실, OpenViking은 38.0%가 해당 메모리 단위 없음), **접근성**(남아 있어도 쪼개지고·희석되고·바꿔 써져서 질의와 유사도가 떨어져 첫 라운드에 못 찾음), **견고성**(메모리를 만든 모델과 읽는 모델이 다르면 RAG보다 성능 변동이 큼). 처방 중 가장 실용적인 건 **원본 기록에서도 같이 검색해 메모리 결과와 합쳐 재정렬**하는 것 — SimpleMem 73.6→82.8(세금 12.0→5.2), Mem-T 75.0→80.0. 자세한 구조는 AI 심층 「AI - 에이전트 메모리의 순가치」.

**실무에 무슨 의미인가.** 메모리·RAG를 붙이는 서비스(나중의 Vault RAG 프로젝트 포함)에서 **"원본을 버리지 말라"**가 첫 규칙이다. 요약·추출은 원본 위의 *색인*이어야지 원본의 *대체*가 아니다. 이 Vault의 「예습자료」 규칙(승격해도 원본 예습자료는 출처 추적용으로 남긴다)이 정확히 이 구조다.

**반론·회의적 시각.** ① 벤치마크 대부분이 "검색 친화적"이라는 걸 논문 스스로 인정한다(IDF 키워드 매칭만으로 50%+, RAG-Hybrid 약 70%인 벤치가 있음) — 메모리가 빛날 *추상화가 필요한* 과제가 적다. ② PersonaMem-v2는 20%, MINT-Eval은 10% 층화 표본, 채점은 Qwen3.6-27B 심판, 프런티어 모델은 GPT-5.6 Luna(low)까지만. ③ 검색 범위를 맞추려고 메모리 시스템들의 top-k를 기본값보다 *올렸다* — 공정성 조정이지만 각 시스템의 설계 의도와 다를 수 있다. ④ TTME는 "제대로 쓴 메모리"가 이긴다는 반대 방향 증거라, 결론은 "메모리가 나쁘다"가 아니라 "평가를 RAG 대비로 하라"다.

## 더 알아볼 것

- [ ] **내 리포의 "PR당 CI 작업 수" 세어 보기.** 수집기 리포에서 `gh run list --limit 100 --json event,headBranch,conclusion`으로 최근 실행을 뽑아 PR(또는 푸시)당 워크플로 실행 수·실패 후 재실행 비율을 계산한다. Octoverse의 19.9→34.9와 비교하고, `paths:` 필터나 캐시로 줄일 수 있는 실행을 표시한다.
- [ ] **보이지 않는 문자 검사기 만들기.** U+E0000~E007F(태그 문자)·U+200B~200F(zero-width) 를 찾는 10줄짜리 스크립트를 짜서 Vault 전체와 수집기 리포에 돌려 본다. 걸리는 게 있으면 어디서 들어왔는지(복붙·에이전트 출력) 추적하고, pre-commit 훅으로 넣을지 판단한다.
- [ ] **"원본 병행 검색"의 효과를 Vault로 재현하기.** 기술정리 노트 20개를 골라 ① 노트를 3줄 요약해 요약만 임베딩 ② 원본 청크만 임베딩 ③ 둘 다 검색해 합쳐 재정렬, 세 방식으로 질문 10개를 던져 정답 노트가 top-3에 드는 비율을 센다. Memory Tax의 SimpleMem 73.6→82.8 같은 차이가 작은 규모에서도 나오는지 본다(Vault RAG 프로젝트 예습).
- [ ] **"거부가 미끼인지" 판별 실험(안전한 버전).** 평범한 유틸 함수(정렬·포맷팅) 몇 개에 *위험해 보이지만 무해한* 이름("dangerousOverflowExploit" 수준)을 붙인 파일과, 같은 코드를 `f1`·`f2`로 바꾼 파일을 같은 모델에 "이 코드가 뭘 하는지 설명해"로 각 5회 묻는다. 이름만으로 설명 품질·거부율이 얼마나 달라지는지 기록한다.
- [ ] **Java가 AI 관여율 꼴찌인 이유를 내 환경에서 가늠하기.** 같은 작은 기능(REST 엔드포인트 + 테스트)을 Spring Boot와 Express(TypeScript)로 각각 에이전트에게 맡기고, ① 첫 시도 테스트 통과 여부 ② 빌드+테스트 1회 소요 시간 ③ 생성 코드 줄 수를 비교한다. GitHub의 "확인하기 쉬운 언어" 가설과 빌드 속도 변수 중 어느 쪽이 더 크게 보이는지 한 문단으로 정리.

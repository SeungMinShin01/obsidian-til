## 오늘의 글

## 배경

글은 B마트 WMS에서 DC(중앙물류기지)→PPC(지역 거점) 재고 이관을 다루는 "이관요청서"의 동시성 사고에서 출발한다. 이관요청서는 출발지·목적지·SKU·이관 수량으로 만들어지고 처음엔 `미할당` 상태다. 할당은 (1)SKU 단위로 재고를 선점하고 (2)그 결과에 따라 요청서 상태를 `할당/부분할당`으로 바꾸는 두 단계이며, DB 트랜잭션을 짧게 하려고 요청서가 아니라 하위 SKU 단위로 나눠 병렬 호출된다. 취소는 `미할당`일 때만 허용된다. 어느 날 DC 관리자로부터 "취소된 이관요청서에 재고가 할당돼 있다"는 문의가 왔고, 확인해 보니 한 관리자가 할당을 누르는 동시에 다른 관리자가 취소를 눌렀던 것이라고 글은 설명한다. 재고 할당이 진행 중일 때는 아직 상태가 `미할당`이라 취소가 통과되고, 할당이 끝나 상태를 바꾼 뒤 취소가 마지막에 덮어써서 "재고는 잡혔는데 상태는 취소"가 됐다는 것이 원인 분석이다.

## 핵심

- 근본 원인: 할당의 상태 변경 로직에는 Redis 분산 락(`wmsRedisLock.lock(key = orderId, waitSecond = 5)`)이 걸려 있었지만, **취소 API에는 락이 없었다**. 같은 자원을 두 경로가 건드리는데 한쪽만 잠근 셈이다. 취소는 상태만 바꾸고 할당 해제는 하지 않아서 재고가 그대로 남았다.
- 1단계 — 할당과 취소에 **같은 락 키(이관요청서 단위)** 를 걸었다. 그런데 이관요청서 하위에 SKU가 N개면 클라이언트가 N번의 할당 API를 동시에 쏘는 구조라, 첫 SKU만 락을 잡고 나머지 N-1개는 락 획득 실패로 할당이 안 됐다.
- 2단계 — 락에 **waitTime**을 줘서 나머지 요청이 대기 후 순차 처리되게 했다. 할당·취소 동시 실행은 막혔지만 SKU 수에 비례해 할당 처리 시간이 늘어나 병렬성을 포기한 해법이 됐다.
- 3단계(최종) — 분산 락 안에서 무거운 재고 할당을 하지 않고, **상태 키**(`STATUS_KEY:{orderId}`)만 확인·설정한다. 현재 요청이 할당이면 Redis에 `ALLOCATION`, 취소면 `CANCEL`을 저장하며 유효시간 30초로 갱신한다. 값이 `null`이거나 같은 종류(`할당→할당`)면 락을 풀고 다음 로직으로, 다른 종류(`취소→할당`, `할당→취소`)면 예외를 던지고 요청을 끝낸다.
- 효과: 락은 "값 하나 읽고 쓰기"만 감싸므로 짧고, 가장 오래 걸리는 재고 할당은 락 밖에서 SKU별로 병렬 처리된다. 할당 결과에 따라 상태를 바꾸는 마지막 단계에만 별도 락이 남는다.
- 락 획득 실패(`IllegalStateException`)와 상태 충돌은 둘 다 RuntimeException으로 바꿔 사용자에게 "동시성 이슈"로 노출한다 — 조용히 덮어쓰지 않고 실패시키는 선택이다.
- 글이 남긴 개선안: 할당 요청을 SKU 단위가 아니라 이관요청서 단위로 받고 하위 SKU를 서버에서 멀티스레드로 처리하는 방식. 단, API 총 처리 시간과 서버 부하를 따져 봐야 한다고 덧붙인다.
- 우아콘2024 발표 영상이 같이 링크돼 있다.

## 내 프로젝트와의 연결

WMS 프로젝트와는 도메인이 같다. 입고→재고→출고에서 "재고 선점(할당)"과 "주문 취소"는 정확히 이 글의 두 경로에 대응한다. 첫 번째 교훈은 락 자체보다 **락의 대칭성** — 재고를 바꾸는 모든 경로(할당·취소·출고 확정)가 같은 키로 잠기는지 점검하는 것이 먼저다. 두 번째는 락의 범위: 락 안에 DB 작업 전체를 넣으면 2단계처럼 직렬화돼 부하 테스트에서 처리량이 떨어질 것이고, 글의 3단계처럼 "지금 이 요청을 진행해도 되는가"라는 판단만 락 안에 두고 실제 작업은 밖에서 돌리는 구조를 Before/After로 비교해 볼 만하다. 우리 프로젝트는 단일 인스턴스라 Redis 분산 락 대신 DB 비관적 락이나 상태 컬럼 조건부 UPDATE(`WHERE status = '미할당'`)로 같은 효과를 낼 수 있는지가 결정 로그 후보다. 수집기와의 직접 연결은 약하고, 구조적으로는 "같은 자원을 두 실행이 동시에 건드릴 때 한쪽만 방어하면 소용없다"는 점만 겹친다.

## 오늘 정리할 것

1. WMS 재고 도메인에서 재고 수량이나 선점 상태를 바꾸는 API 경로를 전부 나열하고, 각 경로에 어떤 잠금(락·조건부 UPDATE·없음)이 걸려 있는지 표로 만든다.
2. 취소 API에 `UPDATE ... WHERE status = '미할당'`처럼 상태 조건을 넣었을 때 갱신 행 수 0이 나오면 실패로 처리하는 방식이 이 글의 3단계 상태 키를 대체할 수 있는지, 차이점(분산 환경·TTL·병렬 할당)을 적어 본다.
3. 두 스레드로 할당과 취소를 동시에 호출하는 테스트(`ExecutorService` + `CountDownLatch`)를 짜서 "취소됐는데 재고가 잡힌" 상태가 실제로 재현되는지 확인한다.
4. Redis 분산 락에서 waitTime·leaseTime(TTL)이 각각 무엇을 막는지, 그리고 이 글의 상태 키 TTL 30초가 만료되면 어떤 일이 생기는지 시나리오를 써 본다.

**원문**: [사장님 입점신청 자동승인 주기를 10분에서 10초로](https://techblog.woowahan.com/27678/) — 전예환 · 2026.09.23 · Backend

## 배경

글은 입점 요청(업주계약·광고계약)의 자동승인이 시작되기까지 최소 3분~최대 12분 59초가 걸리던 상황에서 출발한다. 기존 구조는 스케줄러 두 개였다 — enqueue(매시 07분부터 10분 간격, `imr` 요청 테이블에서 후보를 찾아 `auto_approve_outbox`에 `NEW`로 적재)와 process(매시 00분부터 10분 간격, 아웃박스를 읽어 처리). 두 스케줄러 사이의 고정 3분이 "가장 운이 좋아도" 기다려야 하는 하한이었고, 재시도 주기도 process 주기(10분)에 묶여 있었다. 후보 쿼리도 넓은 시간 범위 커서 페이징 + `NOT EXISTS` 안티 조인 + 전자계약서 원장 `INNER JOIN` + 후보마다 외부 API 호출로 무거워, 주기만 줄이면 외부 시스템과 DB가 버티지 못하는 구조였다고 설명한다. 그동안 밀린 건은 담당자가 직접 처리하게 되어, 자동승인의 지연이 사람의 일로 넘어갔다고 한다.

## 핵심

- **큐를 걷어내고 "마커"만 남김** — 글은 "주기를 얼마로 줄일까"보다 "아웃박스 큐가 왜 필요했나"를 먼저 물었다고 한다. 후보는 `imr`의 현재 상태로 언제든 다시 계산할 수 있으니, 필요한 건 큐가 아니라 "이미 선점했는가"를 알려주는 상태 레코드라는 판단. 새 테이블 `auto_approve_state`(상태는 `IN_PROGRESS`/`RETRY_WAITING` 둘뿐, 성공하면 행 삭제 → `DONE` 없음). `UNIQUE(imrId)`로 요청당 1행 보장, `(status, modifiedAt)` 인덱스는 클렌징용. 커버링 인덱스는 옵티마이저가 UNIQUE를 골라 힌트로 강제해도 더 느렸다고 한다.
- **Kafka(이벤트) 대신 폴링을 유지한 이유** — 자동승인 조건은 "여러 시스템 상태의 조합"이고, 전자계약서 진행 상태처럼 외부와 동기화되며 이벤트 없이 바뀌는 값이 있어 "마지막 한 칸"을 깨워 줄 이벤트가 없다. 글은 이를 이벤트 처리가 아니라 **상태 조정(reconciliation)** 문제로 보고, level-triggered(지금 조건이 true인지만 확인 → 신호를 놓쳐도 스스로 회복) vs edge-triggered(이벤트를 놓치면 작업도 사라짐)로 구분한다. 이벤트+폴링 하이브리드는 "최대 10초를 벌자고 진입점을 하나 더 둬서 선점·중복 방어를 두 번 거는" 비용 때문에 반려.
- **폴링 주기 ≠ 재시도 주기** — `@Scheduled(fixedDelay = 10000L, initialDelayString = "#{ T(java.util.concurrent.ThreadLocalRandom).current().nextLong(0, 10000) }")`. 재시도 대기 건은 `RETRY_WAITING` + `retryCount+1` + `nextRetryTime = 10분 뒤`로 두고, 후보 쿼리의 `nextRetryTime < now` 조건으로 빠지게 해 외부 시스템 부하를 60배로 만들지 않았다고 한다. 동시에 만성 실패 건이 한 턴 상한(업주 20 + 광고 10 = 30건)을 차지하는 **head-of-line blocking**과 재시도 한도(300회) 조기 소진도 막는다.
- **cron이 아니라 fixedDelay + 랜덤 초기 지연** — cron "매 10초"는 N대가 동시에 깨어 같은 상위 30건·같은 락을 노리는 최대 경합 설정. fixedDelay는 처리 시간 차이로 실행 시각이 자연스럽게 흩어지고, 배포 직후 동시 시작은 SpEL 랜덤 `initialDelay`(0~주기)로 처음부터 흩어 놓는다.
- **선점 방식 3안 비교(MySQL 8 재현)** — ① DB 조건부 UPDATE(`WHERE imrId=? AND status='RETRY_WAITING'`, 신규는 INSERT의 중복 키로 판정): 판정+기록이 한 연산이라 단순하지만 실패한 시도까지 전부 쓰기 DB로 가고, 앞 서버 커밋까지 기다려야 실패를 안다. ② `SKIP LOCKED`: 조건 일부가 조인 뒤에 걸려 스캔이 `LIMIT`에서 멈추지 못함 — 20건 선점에 **394행이 잠김**(MySQL은 반환 행이 아니라 훑은 행을 잠금, REPEATABLE READ에선 넥스트키 락이 다른 유형 요청까지). `FOR UPDATE OF`로 좁히면 LEFT JOIN에서 건너뛴 행이 "신규 건"으로 돌아와 두 세션이 같은 20건을 받음. ③ **Redis 락(채택)**: 실패는 Redis에서 즉시 끝나 쓰기 DB 부하가 폴링 횟수가 아니라 실제 처리 건수에 비례. 대가는 두 저장소 사이를 락으로 묶어야 하는 고정 복잡도.
- **락 만료·서버 다운 방어** — 선점 = 락 획득 → **쓰기 DB에서** 상태 행 재확인 → `IN_PROGRESS` 기록. 후보 조회는 읽기 복제본이라 복제 지연 동안 남이 선점한 건이 보이는데, 재확인을 복제본에서 하면 방어가 무력화된다. Redis 장애 시 "락 없이 진행" 폴백은 두지 않았다 — "중복 처리되는 것보다 처리가 늦어지는 쪽이 안전한 실패".
- **클렌징 스케줄러(ShedLock으로 1대만)** — `IN_PROGRESS`에서 멈춘 행은 `RETRY_WAITING`으로 되돌리며 실패 메모를 남기고, 담당자가 이미 처리한 요청의 행은 삭제. 멈춤 판단 기준 시간은 최대 처리 시간보다 넉넉해야(짧으면 클렌징이 중복을 만든다). 재시도 한도 도달 행은 지우지 않고 둔다.
- **빈손 턴 재조회 + 프로세서 체인** — 락을 하나도 못 잡은 턴만 최대 3라운드 재조회(일부라도 잡았으면 턴 종료 — fixedDelay가 턴 종료부터 세기 때문). 처리는 업주→가게→광고 캠페인 프로세서가 `Next`/`Success`/`Retry`를 반환하는 작은 상태 머신이고, 프로세서마다 쓰기 DB에서 요청을 **다시 조회**한다. 재시도는 늘 첫 프로세서부터, 각 프로세서가 "이미 끝났으면 건너뜀"으로 멱등하게. 단 외부에 생성 후 우리 DB 기록 전에 죽는 틈은 남아 있다고 글은 인정한다.
- **남은 것** — 폴링 1/60의 대가는 읽기 복제본 부하(평상시엔 `LIMIT` 조기 종료가 발동하지 않아 총 스캔량이 실행 횟수만큼 증가), 재시도 간격 고정(지수 백오프·사유별 차등 여지), 다른 서비스의 수동 승인과의 경합(락 공유보다 승인 로직 단일화가 먼저, 락은 외부 호출 **앞**에).

## 내 프로젝트와의 연결

수집기와 구조가 가장 가깝다. 수집기도 GitHub Actions 스케줄로 도는 폴링 파이프라인이고, "이 공고를 이미 저장했는가"를 SQLite에 남기는 구조라 글의 "큐가 아니라 마커" 관점과 "폴링 주기와 재시도 주기를 분리"(`next_retry_at`·`retry_count` 컬럼으로 실패 건을 대기열에서 빼 두기) 발상을 그대로 대입해 볼 수 있다. 재시도를 늘 처음부터 돌리되 각 단계가 "이미 끝났으면 건너뛰는" 멱등 설계도 수집·저장 단계에 적용 가능한 지점이다. 다만 수집기는 워커가 1개라 Redis 선점·클렌징 같은 분산 방어는 해당하지 않는다. WMS 쪽은 재고 선점과 구조적으로 비슷한 지점이 있다 — 조건부 UPDATE(`WHERE status=...`의 affected rows로 선점 판정) vs `SELECT ... FOR UPDATE SKIP LOCKED` vs Redis 락의 트레이드오프, 그리고 "MySQL은 반환 행이 아니라 훑은 행을 잠근다"는 점은 WMS 동시성 테스트에서 직접 확인해 볼 만하다.

## 오늘 정리할 것

1. MySQL 8에서 세션 두 개를 열고 `SELECT ... FOR UPDATE SKIP LOCKED LIMIT 5`를 인덱스 순서와 맞는 ORDER BY / 어긋나는 ORDER BY로 각각 실행해, `performance_schema.data_locks`로 잠긴 행 수가 어떻게 다른지 확인한다.
2. 조건부 UPDATE(`UPDATE ... SET status='IN_PROGRESS' WHERE id=? AND status='WAITING'`)를 두 세션에서 동시에 날려, 두 번째 세션이 앞 세션 커밋까지 대기한 뒤 affected rows 0을 받는 과정을 재현한다.
3. Spring `@Scheduled`의 `cron`·`fixedRate`·`fixedDelay` 차이와 `initialDelayString`에 SpEL이 언제 평가되는지 공식 문서에서 확인해 한 줄씩 적는다.
4. 수집기 SQLite 스키마에 `retry_count`·`next_retry_at`을 둔다면 후보 조회 쿼리가 어떤 모양이 될지 SQL 한 줄로 적어 본다 (level-triggered 관점에서 "놓친 건이 스스로 회복되는가" 확인).

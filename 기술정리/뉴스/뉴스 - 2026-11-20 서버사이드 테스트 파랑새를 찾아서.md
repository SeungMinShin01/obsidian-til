## 배경

글은 배민 선물하기 시스템에 테스트가 "꽤 존재했지만 혼란스러운" 상태였다고 설명한다. 원인으로 ① 유닛/통합 테스트 개념에 대한 팀 내 이해 차이와 합의된 좋은 테스트 기준의 부재, ② 공통 테스트 기본 환경이 없어 프레임워크·작성 패턴이 제각각이고 피드백이 느렸던 점을 든다. 글의 목표는 "정답"이 아니라 이 조직 환경에서 가장 합리적인 테스트 규칙을 합의하고 도구로 굳히는 것이다.

## 핵심

- **문제 → 결정(유닛 테스트 격리 수준)**: 협동(Sociable, 고전파) 테스트는 리팩터링 내성이 높아 유지보수에 유리하지만, Spring 서비스에서 이를 하려면 Repository와 그 하위 의존까지 런타임에 다 필요하다. `@SpringBootTest`로 IoC 컨테이너를 띄우는 방법은 **반려** — 피드백이 치명적으로 느려지고, 격리되지 않은 DB를 공유해 병렬 실행이 어려워지기 때문이라고 글은 설명한다. 그래서 `@SpringBootTest`를 제거하고 규칙을 합의했다: 격리가 쉬운 유닛(JPA 엔티티)은 협동 테스트, 협력·위임 관계가 있는 유닛(서비스)은 테스트 대역을 쓴 단독(Solitary) 테스트.
- **단독 테스트의 대가**: TDD 사이클에서 Repository 의존이 생기는 순간 어떤 메서드를 호출하고 무엇을 반환할지 테스트 작성 시점에 결정해야 하므로 구현이 테스트에 스며들고 리팩터링 내성이 떨어진다 — 이를 알고 받아들인 트레이드오프다.
- **통합 테스트와 외부 통신**: RDBMS·MQ는 LocalStack·Testcontainers·Docker로 대체한다. 외부 API는 "매번 라이브 호출"을 **반려**(잘못된 데이터 누적 등으로 결정성 저하)하고 테스트 대역을 선택했다. 인터페이스 변경이 치명적인 모듈은 주기 실행되는 약식 계약 테스트로 보완한다 → 결과적으로 Narrow integration test.
- **비율·커버리지**: 피라미드 vs 허니콤 비율 논쟁 대신 "빠르고, 믿을 수 있고, 유용한 이유로만 실패하는 테스트"에 집중한다. 커버리지는 품질의 긍정 지표가 아니라, 낮을 때 위험 신호로만 쓰는 **부정 지표**로 정했다.
- **공통 작성 패턴**: AAA와 GWT를 섞지 않고 GWT 하나로 통일 — 통합은 사용자 시나리오, 유닛은 모듈 기능 시나리오. 계층별 규칙: Controller는 MockMvc + Service 대역, Service는 단독, 엔티티는 협동, API 통합 테스트는 공통 `ApiIntegrationTestContext`를 상속하고 외부 통신만 대역.
- **도구**: Kotlin Extension으로 MockMvc DSL·MockServer DSL을 만들어 "수다스러운" 코드를 줄이고, 운영 설정을 읽어 신규 외부 API 클라이언트의 MockServer를 자동 초기화한다. 충분히 성숙한 클래스에 한해 Object Mother(상태별 기본값 팩토리)를 둔다 — fixture 라이브러리 대신 가볍고 IDE에서 바로 추적되기 때문이라고 설명한다.
- **DB 초기화 개선(수치)**: 단일 DB를 공유하는 통합 테스트에서 테스트마다 초기화에 약 300~500ms가 걸렸다. 원인은 DB 쓰기 성능이 아니라 여러 쿼리의 I/O 왕복 → 초기화를 **프로시저**로 묶어 Native Query로 생성·실행, 1~2회 I/O로 줄였다. 전체 실행 17.7초 → 7.6초.
- **CI/CD 분리**: 기능 브랜치로의 병합은 유닛 테스트만(CI 비용 절감), main/master 병합은 통합 테스트까지 필수, 운영 배포는 빌드 + 유닛 + 통합 통과 시에만.

## 내 프로젝트와의 연결

WMS는 Spring Boot라 글의 판단을 거의 그대로 대입해볼 수 있다. 입고·출고 서비스는 재고 Repository에 의존하므로 단독 테스트(대역) 대상이고, 재고 엔티티의 "수량 차감 시 음수 금지" 같은 규칙은 협동 테스트로 빠르게 검증할 수 있다. 다만 재고 선점·동시성 락처럼 실제 DB 동작이 핵심인 부분은 대역으로는 검증이 안 되므로, Testcontainers 기반 통합 테스트로 남겨야 하는 지점이다. 수집기 쪽은 외부 채용 API를 라이브로 부르지 않고 응답 스텁으로 대체한다는 결정, 그리고 "PR엔 가벼운 테스트, main에는 무거운 테스트"라는 GitHub Actions 단계 분리가 구조적으로 같은 고민이다.

## 오늘 정리할 것

1. Sociable vs Solitary 테스트, 고전파 vs 런던파 차이를 한 표로 정리하고, WMS의 입고 서비스·재고 엔티티를 각각 어느 쪽으로 테스트할지 적어본다.
2. `@SpringBootTest`와 `@WebMvcTest`·`@DataJpaTest`(슬라이스 테스트)가 각각 무엇을 띄우는지 확인하고, 글이 슬라이스 대신 순수 단위 + 대역을 택한 이유를 내 말로 써본다.
3. 테스트 간 DB 초기화 방식(`@Transactional` 롤백, TRUNCATE 스크립트, 프로시저)을 비교하고, 재고 동시성 테스트에서 `@Transactional` 롤백이 왜 문제가 될 수 있는지 확인한다.
4. GitHub Actions에서 유닛/통합 테스트를 분리하는 방법(Gradle 태스크 분리 또는 JUnit `@Tag`)을 찾아 워크플로 예시를 메모한다.

## 오늘의 흐름

브리핑의 헤드라인은 "프런티어 모델 3종이 한 주에, 똑같은 가격표로"다. 그런데 셋 중 둘(GPT-6.1 Sol, Claude Sonnet 5.5)은 이미 9월 29일·30일 노트에서 다뤘고, 새로 들어온 건 **Gemini 4 Argon** 하나다. 그리고 원문을 열어 보면 "소수점까지 같은 가격표"라는 표현은 절반만 맞다. Argon의 $2/$10은 **도입가(introductory rate)**이고, 도입 기간이 끝나면 **$4/$20으로 두 배**가 된다고 Google이 직접 적었다. 같은 숫자를 같은 주에 맞춰 낸 건 사실이지만, 그 숫자가 "업계 표준 가격표로 굳었다"기보다는 **Sol을 겨냥해 일시적으로 맞춘 가격**에 가깝다. 9월 22일부터 이어온 "싸졌다" 흐름(가격 동결 → 단가 인하 → 출력 길이 절감 → 호출 횟수 절감 → 아랫등급에 윗등급 성능)에 오늘 붙는 건 여섯 번째 축이 아니라 **할인 기간이라는 단서**다. 실제 비교 기준은 여전히 리스트 가격이 아니라 과제당 비용이다 — Artificial Analysis 기준 GPT-6.1 Sol은 지능 지수 과제당 $0.72, Astra는 $3.26이었다. 그런데 6.1 Sol은 이전 Sol보다 **출력 토큰을 10~30% 더 쓰는데도** 과제당 비용은 $1.05 → $0.72로 내려갔다. 토큰을 더 쓰고도 싸진 이유는 캐시 할인(90% → 95%)과 더 적은 재시도에 있다. "토큰당 가격"과 "일 하나당 가격"이 이렇게 다른 방향으로 움직이는 게 지금 모델 선택이 어려운 이유다.

두 번째 흐름은 어제 노트의 "새는 곳은 출력 바깥이었다"가 **기본기 층까지 내려온** 것이다. 오늘의 큰 사고 두 건은 모두 AI와 거의 상관없다. 마이크로소프트 내부 분석 서비스 Titan은 JWT의 테넌트·audience·앱 허용 목록·사용자 조회까지 **네 겹의 검사를 다 했는데 서명 검증 하나를 빼먹어서** `alg: none` 토큰에 `upn: admin` 한 단어로 17.3조 행이 열렸다. Firebase iOS SDK는 서버가 내려준 실험 설정 페이로드에서 **nil 키 하나**가 파싱되자 그 SDK를 쓰는 앱을 전부 죽였다 — 앱 개발자가 코드를 한 줄도 바꾸지 않았는데 이미 출시된 빌드까지. 둘 다 "여러 겹의 방어가 있었지만 한 겹이 비었다"가 아니라 "**가장 바닥의 한 겹이 비어서 위의 겹들이 전부 무의미해졌다**"는 구조다. 9월 29일 노트의 "개별 품질은 다 멀쩡한데 합쳐놓으니 청구서가 나왔다"(인덱스 838개)와 정확히 반대 모양이다 — 그날은 각각이 합격인데 합치니 불합격, 오늘은 각각이 합격인데 **하나가 빠지니 전부 불합격**.

여기에 AI가 끼어드는 지점은 공격 쪽이다. Titan을 찾은 건 16세 연구자의 AI 해킹 도구 Antares였다. Antares는 공개 Swagger를 찾고, Wayback Machine에서 테이블 정의 56개를 복원하고, 열흘 동안 JWT 클레임을 체계적으로 바꿔 넣었다. 그런데 **마지막 한 수는 사람이 뒀다** — `upn`이 이메일이 아니라 로컬 사용자 이름일 수 있다는 가설을 Antares는 세우지 못했고, 사람이 새벽 1시에 `admin`을 넣어 봤다. 9월 20일 노트("에이전트가 시스템을 뚫기 시작했다")가 에이전트 단독 침투를 다뤘다면 오늘은 **사람과 에이전트의 분업**이 실제 결과를 낸 사례다. 같은 날 Anthropic 프런티어 레드팀은 바이너리 익스플로잇 100개 과제에서 GLM-5.3이 제어 흐름 탈취 4%, Claude Mythos Preview가 6%를 냈다고 보고했고(이전 세대 둘은 0%), Google은 Argon을 일반 공개 전에 **사이버 방어자에게 먼저**(Fairwind 프로그램) 풀었다. 공격 능력이 0에서 한 자릿수로 넘어온 순간, 방어자 우선 배포가 정책이 됐다.

세 번째는 측정의 흐름이다. HN 2위 Livenerf는 "Opus 5.5가 조용히 나빠졌나"를 **실험 설계로** 바꿨다. 쉬운 문항(언제나 맞힘)·불가능한 문항(언제나 틀림)을 버리고 "가끔 맞히는" 78문항만 남기고(정보량이 p(1−p)라서), 출시 주를 기준선으로 같은 문항을 매일 쌍 비교하고, 대조군(Opus 5)이 같이 흔들리면 모델이 아니라 서빙 탓으로 판정한다. 그리고 지금은 **결과가 없다** — 30일 중 6일차, 첫 비교는 10월 24일경. 오히려 이 프로젝트가 스스로 공개한 검증 결과가 더 중요하다: Opus 5를 Opus 5.5로 바꿔 끼워도 −3.8 ± 6.3점으로 99% 신뢰구간에서 구분이 안 됐다. 즉 **"조용한 모델 교체"는 이 정도 표본으로는 원리적으로 안 잡힌다.** 대신 출력 토큰은 effort low에서 −62%로 크게 움직였다 — 정확도보다 토큰이 먼저 신호를 낸다. 9월 25일 노트의 claude.ai 3배 최적화(지표 상관관계 검증 → CI 상한선 고정)와 같은 계열의 방법론이고, "체감"을 "판정선이 미리 정해진 측정"으로 바꾸는 흐름이 사용자 쪽에서도 시작됐다.

## 깊게 본 것

### 1. Gemini 4 Argon — 출력 한도 64K → 1M, 그리고 "같은 가격표"의 단서

**무슨 일인가** — Google이 긴 소프트웨어 개발, 기업 지식 노동, 자율 사이버 방어를 겨냥한 Gemini 4 Argon을 발표했다. 공식 수치: DeepSWE v1.1 77.9%, AutomationBench(Zapier) 51.3%(1위), LVBench 91.7%, CWE-bench v1 68%(공동 1위), Vals Index·Vals Finance Agent v2·Harvey Legal Agent Benchmark 선두, Gray Swan IPI(간접 프롬프트 인젝션) 견고성 선두. 입력 컨텍스트 1M, **출력 한도 1M**(이전 64K).

**가격** — 도입가 입력 $2 / 출력 $10 / 캐시 입력 95% 할인. **도입 기간 이후 표준가 $4 / $20.** 브리핑은 "GPT-6.1 Sol과 소수점까지 동일"이라고 했지만 그건 도입가 한정이다. 도입 기간의 길이는 발표에 없다.

**배경(왜 지금)** — 입력 1M 모델은 이미 흔하다. 병목은 출력이었다. 출력이 64K에 묶여 있으면 "저장소 전체를 마이그레이션해라"는 결과를 쪼개 받아야 하고, 쪼갤 때마다 앞 결과를 다시 입력으로 넣는다(9월 28일 노트의 멀티턴 O(n²) 누적 과금과 같은 구조). 출력 한도를 1M으로 올린 건 **한 번의 호출이 한 과업을 끝까지 끌고 가게** 하겠다는 설계 선택이다. 같은 주 OpenAI는 "상시 작동"(Dots)으로, Google은 "한 호출을 길게"로 — 둘 다 "사람이 중간에 개입하지 않는 시간을 늘린다"는 같은 방향의 다른 구현이다.

**기술적으로 어떻게 동작하나** — 아키텍처는 공개되지 않았다. 공개된 건 안전 장치 네 개다: 내외부 레드팀 견고성 테스트, **내부 활성값(activation) 모니터링으로 오용 탐지**, chain-of-thought 모니터링으로 비정렬 탐지, 고위험 평가 전 샌드박스 강화. 이 중 활성값 모니터링은 9월 30일 노트의 GLM-5.3 abliteration(거부 방향을 가중치에서 제거)과 짝을 이룬다 — 닫힌 모델은 같은 "방향" 지식을 **떼어내는 대신 감시하는 데** 쓴다. 가중치를 공개하지 않는 한 이 감시는 접근 경계 안에서 유지된다.

**실무에 무슨 의미인가**
- **긴 출력은 검증 비용을 앞당긴다.** 1M 토큰 출력은 사람이 읽을 수 있는 양이 아니다. 받아내는 쪽이 할 수 있는 건 테스트·스키마·API 계약으로 **기계적으로 판정**하는 것뿐이다. Spring Boot 프로젝트라면 통합 테스트와 OpenAPI 명세가 "AI가 쓴 코드를 받아들일지"의 관문이 된다
- **가격 비교는 할인 만료일까지 같이 적는다.** 도입가로 아키텍처를 설계했다가 표준가로 넘어가면 비용이 2배다. 모델 추상화 계층(같은 코드로 모델만 교체)이 있으면 이 리스크를 흡수할 수 있다
- **출력 1M은 장애 반경도 1M이다.** 긴 단일 호출은 중간 실패 시 재시도 비용이 크다. 체크포인트(중간 산출물 저장)를 어떻게 두는지가 새 설계 문제다

**반론·회의적 시각**
- 벤치마크는 전부 자사 발표 기준이다. DeepSWE 77.9%가 "1위"라는 브리핑 표현은 원문에서 확인되지 않았다(원문은 AutomationBench만 #1로 명시)
- "자율 사이버 방어"는 같은 능력이 공격에도 쓰인다. 단계식 배포는 그 위험을 인정한 것이지만, 배포 시점은 "가능한 한 빨리"로만 적혀 있어 게이팅 기준(무엇을 확인하면 다음 단계로 가는가)이 없다
- 출력 1M을 실제로 쓸 때의 지연·비용(출력 1M = 도입가로도 $10, 표준가 $20/호출)과 긴 출력 후반부의 품질 유지 여부는 공개되지 않았다

### 2. Microsoft Titan — 네 겹의 검사, 빠진 한 겹이 서명이었다

**무슨 일인가** — Titan은 마이크로소프트 직원이 DB를 질의하고 대시보드를 만드는 내부 분석 플랫폼이다. 웹 UI는 VPN 뒤에 있었지만 **별도의 공개 API 엔드포인트**가 Azure에 떠 있었다. 공개 Swagger에 라우트 4개, 그중 `/v2/Query`는 원시 SQL을 받았다. JWT의 클레임은 검증했지만 **서명은 검증하지 않았고**, `alg: none` 무서명 토큰에 `upn: admin`을 넣자 관리자(user ID 1)로 임의 SQL이 실행됐다.

**접근 가능 범위** — ClickHouse 분석 DB 17개·고유 테이블 9,863개, 추정 **17,333,335,124,315행**(메타데이터 기준), 직원 이메일 약 17,990건·조직 레코드 15,001건, Bing 분석 데이터(2행만 샘플 확인). 실제 고객 PII 대량 추출은 없었다.

**타임라인** — 9/5 MSRC 신고(Case 144051) → 9/9 엔드포인트 차단 → 9/17 포상금 $5,000 → 9/22~24 마이크로소프트 편집 검토 후 공개.

**배경(왜 이런 일이)** — 기술 체인은 이렇다.
1. **정찰**: Antares가 VPN 뒤 서비스의 공개 API와 Swagger를 찾음
2. **스키마 복원**: Wayback Machine에서 보관된 설정 → 테이블 정의 56개. `TestData`로 시험하니 401(인증 필요)
3. **클레임 탐색(열흘)**: 서명은 그대로 두고 클레임만 바꿔 보내니 계속 통과 → "서명을 안 본다"는 결론
4. **무서명 토큰**: `alg: none`, 형태 `header.payload.`(마지막 점 뒤가 빈 문자열) → 테넌트·audience·앱 허용 목록·사용자 조회 네 겹 통과
5. **권한 상승**: 이메일 형식 `upn`은 사용자 조회 실패. 사람이 `admin`을 넣어 보니 로컬 앱 사용자로 해석되어 관리자 권한

저자의 비유가 정확하다 — 신분증의 이름은 하나하나 다 확인하는데 **사진은 한 번도 안 보는 경비원**.

**기술적으로 어떻게 동작하나 — JWT 검증의 순서** — JWT는 `header.payload.signature` 세 부분이다. header의 `alg`가 서명 알고리즘을 "자칭"한다. 올바른 검증 순서는:
1. **허용 알고리즘을 서버가 고정**(예: RS256만). 토큰 header의 `alg`를 믿지 않는다 → `none`과 RS256/HS256 혼동 공격 차단
2. **서명 검증**(공개키 또는 비밀키). 실패하면 여기서 끝
3. 그다음에야 클레임(`iss`, `aud`, `exp`, `tid` …) 검증
4. 클레임의 사용자 식별자를 **어떤 저장소에서 어떤 형식으로** 조회하는지 고정(이메일인지 로컬 ID인지)

Titan은 1·2를 건너뛰고 3·4만 했다. 3·4는 아무리 촘촘해도 **"이 내용을 누가 썼는가"를 보장하지 못한다.** 서명 없는 클레임 검증은 사용자가 직접 써 온 신청서를 꼼꼼히 읽는 것과 같다.

**실무에 무슨 의미인가**
- **jjwt에서 메서드 이름 한 글자 차이.** 구버전 jjwt의 `parseClaimsJws()`는 서명된 토큰(JWS)만 받고 서명을 검증한다. `parseClaimsJwt()`는 **무서명 토큰(JWT)을 파싱**한다. 신버전(0.12+)은 `Jwts.parser().verifyWith(key).build().parseSignedClaims(token)`처럼 메서드명에 `Signed`를 넣어 혼동을 줄였다. 내 코드가 어느 쪽을 부르는지 grep 한 번으로 확인할 수 있다
- **Spring Security OAuth2 Resource Server**를 쓰면 `NimbusJwtDecoder`가 기본적으로 JWK Set에서 키를 받아 서명을 검증하고 알고리즘을 제한한다. 직접 필터를 짜서 토큰을 파싱하는 코드가 있다면 그쪽이 위험 지점이다
- **네트워크 경계는 인증이 아니다.** "VPN 뒤니까"라는 가정은 공개 엔드포인트 하나로 무너진다. 같은 서비스의 모든 진입점이 같은 인증 필터를 통과하는지가 핵심이다
- **Swagger를 프로덕션에 열어두지 않는다.** springdoc이라면 `springdoc.api-docs.enabled=false`를 프로필별로. 이번 체인의 1단계가 공개 Swagger였다

**반론·회의적 시각**
- "17조 행"은 메타데이터 기반 **추정치**다. 실제로 조회한 건 샘플 수준이고, 전체가 실제로 읽힐 수 있었는지는 검증되지 않았다

### 3. Firebase iOS SDK — 서버가 보낸 nil 키 하나가 출시된 앱을 전부 죽였다

**무슨 일인가** — Gergely Orosz가 Firebase SDK를 쓰는 iOS 앱이 일부가 아니라 **전 세션에서** 크래시한다고 보고했다. GitHub 이슈 #16728의 스택: `NSInvalidArgumentException *** -[__NSDictionaryM setObject:forKeyedSubscript:]: key cannot be nil`, 위치는 `GULMutableDictionary`와 Analytics의 `APMETaskManager` 실험(experiment) 응답 핸들러. 이슈 작성자는 "00:41 UTC부터 내려오는 실험 페이로드가 nil 키로 파싱된다"고 적고 **서버의 `sdk-exp` 설정 롤백**을 요청했다. 확인된 영향 버전은 Firebase SDK 12.14.0, 한 앱에서 18분 동안 56명에게 56건, **앱 업데이트 없이 이미 출시된 빌드 4개**가 영향을 받았다. 해결 후에도 최대 4시간 잔여 영향.

※ 발생 날짜는 소스마다 다르게 읽힌다 — GeekNews는 10월 1일 아침(한국 시간), 이슈 페이지 요약에서는 9월 29일로 읽혔다. 원문 이슈에서 직접 확인이 필요하다.

**배경(왜 이런 일이)** — 원인은 SDK 코드 배포가 아니라 **서버 측 설정 변경**이다. Firebase Analytics는 앱 실행 중 서버에서 실험 설정(원격 구성)을 받아와 딕셔너리에 넣는다. 서버가 키가 비어 있는 항목을 내려보내자, Objective-C의 `NSMutableDictionary`에 nil 키를 넣는 순간 예외가 났고, 그 예외를 잡는 코드가 없었다. 클라이언트 SDK가 **서버 응답을 신뢰된 입력으로 취급**한 것이다.

**기술적으로 어떻게 동작하나 — 왜 "전부"였나**
1. 원격 설정은 **앱 버전과 무관하게** 모든 클라이언트에 동시에 내려간다 → 배포 단계(점진 롤아웃)가 없으면 반경이 전체
2. 크래시는 앱 시작 직후 실험 스냅샷 초기화 중 발생 → 사용자가 무엇을 하든 재현
3. 앱 개발자는 서버 설정을 통제할 수 없다 → 대응 수단이 "기다리기"뿐

Titan과 같은 구조다. Titan은 **클라이언트가 보낸 토큰**을 서명 없이 믿었고, Firebase SDK는 **서버가 보낸 설정**을 검증 없이 믿었다. 방향만 반대다.

**실무에 무슨 의미인가**
- **외부 응답은 입력 검증 대상이다.** Spring에서 Feign·RestClient로 받은 외부 API 응답, Redis에서 꺼낸 캐시 값, Kafka 메시지 모두 "내 코드가 쓴 게 아닌 데이터"다. 9월 25일 노트의 record 직렬화 오류(캐시 히트부터 터짐)도 같은 계열 — **두 번째 경로에서 들어오는 데이터**가 검증이 약하다
- **설정 변경도 배포다.** 피처 플래그·원격 설정을 바꿀 때 코드 배포와 같은 점진 롤아웃(10% → 50% → 100%, 9월 26일 노트의 배민 WMS 사례)과 즉시 롤백 경로가 필요하다
- **SDK 의존은 장애 반경을 공유하는 계약이다.** 크래시 리포팅·분석 SDK를 앱 시작 경로에서 동기 초기화하면 그 SDK의 장애가 내 앱의 장애가 된다. 초기화를 지연·격리하는 선택지를 알아둔다

**반론·회의적 시각**
- 브리핑은 "SDK 자체에 잘못된 입력을 견디는 수정은 아직 없다"고 했지만, 원문에서 Firebase 팀의 공식 사후 분석은 찾지 못했다. 현재 근거는 이슈 작성자의 진단(서버 설정 롤백 요청)이다
- 영향 범위 "모든 iOS 앱"은 Orosz의 트윗 표현이다. 이슈에서 확인된 건 12.14.0이고, 다른 버전의 영향 여부는 확인되지 않았다

### 4. Livenerf — "조용히 나빠졌다"를 측정하려면 무엇이 필요한가

**무슨 일인가** — Claude Opus 5.5가 9월 출시 이후 능력이 떨어지는지 장기 추적하는 오픈소스 프로젝트(HN 653p/261c, 2위).

**기술적으로 어떻게 동작하나**
- **문항 선별**: GPQA Diamond·MMLU-Pro·경진 수학·AIME 2025–26의 후보 2,336문항 중 모델이 "**가끔** 맞히는" 것만. 정답률 p인 문항은 샘플당 정보량이 p(1−p)라서, 언제나 맞히거나(p=1) 언제나 틀리는(p=0) 문항은 정보가 0이다. 결과는 78문항(후보의 97%가 항상 맞힘/틀림이라 탈락)
- **선택 편향 보정**: 변동성으로 골랐더니 보정 샘플에서는 정답률 54.7%, 새 확인 샘플에서는 62.0% — "고른 표본으로 측정하면 치우친다"를 스스로 측정해 검정력 계산에 반영
- **설계**: 30일(기준선 10일 + 비교 구간 10일 × 2), 하루 90샘플. 기준선은 출시 주(9/24~)
- **검정**: 문항별 쌍 차이를 평균, 문항 단위 클러스터 표준오차(Anthropic의 *Adding Error Bars to Evals* 방법론)
- **판정선(사전 등록)**: 99% 신뢰구간이 **연속 두 구간**에서 0을 배제 + 효과 ≥ 3점 + **대조군(Opus 5)에 같은 움직임 없음**. 대조군이 같이 흔들리면 모델이 아니라 하네스·플랫폼 변화로 본다
- **최소 검출 효과**: 10일 구간당 약 7.5점

**현재 결과** — **없다.** 6/30일차, 기준선 수집 중. 첫 비교 가능 시점은 10월 24일경.

**정작 중요한 것 — 스스로 공개한 한계**
- **Opus 5 ↔ Opus 5.5 교체 검증에서 −3.8 ± 6.3점**: 99%로 구분 불가. 즉 같은 계열 모델 교체 정도의 변화는 이 표본으로 **원리적으로 못 잡는다**
- **토큰은 먼저 움직였다**: effort low에서 출력 토큰 −62%·정확도 −8.3 ± 4.5점, medium에서 −26%·−4.2 ± 3.9점. "모델이 조용히 덜 생각하기 시작하면 정확도보다 토큰에서 먼저 보인다"
- 78문항 중 정답 키가 틀려 보이는 것 8개, 모호한 것 30개(제외하지 않고 민감도 분석 대상으로 표시)
- 안전 분류기가 일부 응답을 Opus 5로 답하거나 생물학 문항을 거부 → 샘플 제외 필요. API가 아니라 Claude Code 구독 동작을 잰다

**실무에 무슨 의미인가** — 이건 AI 이야기이기 전에 **성능 측정 방법론 교과서**다. WMS 프로젝트의 Before/After 측정(인덱스·N+1·캐싱)에 그대로 대응된다.
- **판정선을 먼저 정한다**: "몇 ms 이상, 몇 회 반복에서, 신뢰구간이 겹치지 않으면 개선" — 측정 뒤에 정하면 원하는 결론이 나온다
- **대조군을 둔다**: 같은 시간대에 변경하지 않은 쿼리도 같이 재서, 둘 다 느려지면 DB 서버 탓이다
- **정보 없는 측정을 버린다**: 이미 1ms인 쿼리를 10번 재는 건 정보가 없다. 변화가 보일 만한 구간(데이터 분포의 경계)을 골라 잰다
- **선행 지표를 찾는다**: 응답 시간보다 먼저 움직이는 것(커넥션 풀 대기, 실행 계획의 rows 추정치)

**반론·회의적 시각** — 출시 주가 "가장 나쁜 주"일 수도 있다고 저자 스스로 적었다. 그리고 검출력이 7.5점이라면 사람들이 체감한다고 말하는 하락(대개 그보다 작고 과제 특정적)은 놓칠 수 있다. "통계적으로 유의한 하락 없음"이 나와도 "하락 없음"을 뜻하지 않는다.

### 5. Simple-WAM — 미래를 끝까지 그리지 않아도, 첫 획이면 된다

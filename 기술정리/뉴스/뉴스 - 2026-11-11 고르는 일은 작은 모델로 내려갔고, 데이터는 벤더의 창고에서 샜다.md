## 오늘의 흐름

먼저 겹치는 것. 오늘 브리핑의 1번 큰 건(**Fable 5.2 / Mythos 5.2**)과 **Muse Ember**, **e-means**는 **어제 노트에서 원문 전체를 읽고 깊게 다뤘다** — 오늘은 다시 쓰지 않는다(브리핑이 새로 붙인 "HN 댓글 909개"와 "AA 65점"만 짧게 둔다). Willison의 `<details>` 접기·삐 소리 삼각측량·SQLite `parse_number()`, Firefox `rel=next` 프리페치, USPS 우편번호 폴리곤, 종이비행기, 캐나다 RTR, Goldman의 Claude Code 제한, GitHub 트렌딩 스킬 저장소들도 11/8~11/10 노트에 이미 있다. 새로 원문을 직접 읽은 것은 **Strands 블로그(아마존 사례) 전문, DeepMind AlphaProof Code 발표문 전문, Notion 공지 전문, Fireworks AI 보안 공지 업데이트 전문, OPD 불일치 논문(HF 초록 + arXiv 본문 질의 추출), Flide·ReproBridge HF 초록과 저자 코멘트**다. OPD 불일치 논문은 원리를 AI 심층 「AI - 온폴리시 증류의 불일치 예산」으로 뺐다.

첫 번째 축은 **"고르는 일"이 생성 모델에서 떨어져 나왔다**는 것이다. 아마존 사내 티켓 분류가 Sonnet 4.6을 빼고 Strands Decider E4B로 갔다 — 출력 토큰 170개 → 1개. 이 갈래는 이 Vault에서 세 번째 등장이다: 9/22 Kev·Jev(AI 심층 「비생성 의사결정 모델」이 원리를 다뤘다)가 "텍스트 없이 선택지별 확률만"이라는 형태를 열었고, 10/8 노트의 Decider 2B는 그걸 에이전트 가드레일(도구 호출 직전 판정)로 가져왔다. 오늘은 **프로덕션 비용 숫자**(100만 건당 약 22,200 → 500달러)와 **전용 서빙 엔진**(Flide, vLLM·SGLang 대비 최대 9.5배)이 같은 날 나왔다. 모델 → 용도 → 운영 사례 → 인프라 순으로 생태계가 한 칸씩 채워지는 중이다. 어제 노트의 "큰 모델을 낮은 노력으로"와 같은 원리의 다른 면이기도 하다: **필요한 출력의 모양만큼만 값을 치른다.** 자유 서술이 필요 없으면 자유 서술 모델을 부르지 않는다.

두 번째 축은 **"생성은 불신, 검증은 신뢰"가 구조로 굳어진다**는 것이다. AlphaProof Code는 Gemini Carbon 에이전트 팀을 "신뢰하지 않는 증명자"로, Lean을 "신뢰하는 문지기"로 나눠 Signal 프로토콜 *구현*을 4주에 검증했다. ReproBridge는 재현 결과를 별도 Auditor가 실행 흔적까지 추적해 확인한다. 10/24 노트(AI 심층 「퍼즈 테스트를 명세로 쓰는 정형 검증」)와 11/5 노트(「명령문 대신 결과를 보고, 믿음 대신 증명을 달았다」)가 같은 방향이었는데, 오늘은 그 방향이 **실제 배포된 암호 프로토콜**이라는 가장 어려운 대상에 닿았다. 남은 사람의 일은 "증명이 맞나"가 아니라 "**명세가 우리가 원한 것인가**"다 — 그리고 그 부분은 자동화되지 않았다.

세 번째 축은 **AI 벤더가 곧 공급망**이라는 것이다. Notion이 뚫린 게 아니라 Notion이 쓰던 추론 업체 Fireworks AI가, 그것도 **Fireworks의 R&D 머신을 호스팅하던 제3의 클라우드 업체**를 거쳐 뚫렸다. 공격자 동기는 "LLMJacking"(훔친 접근으로 LLM 토큰을 불법 라우팅 게이트웨이에 되파는 것)으로 추정된다. 이 체인은 11/5 노트의 Binance(변조된 도구 → 측면 이동), 11/8 노트의 Apiiro(`settings.local.json`에 남은 비밀), 11/10 노트의 Qubole과 같은 계열이고, 오늘의 교훈은 더 구체적이다: **Fireworks는 기본값이 ZDR(무보존)인 추론 경로는 영향이 없었다고 했고, 샌 것은 저장된 데이터셋·청구 정보·미완성 가중치였다.** Notion 쪽 유출 데이터도 추론 트래픽이 아니라 Insights 분류 작업용으로 *쌓아 둔* 대화 기록이었다. 지나가는 데이터보다 **쌓아 둔 데이터**가 샌다.

네 번째 축은 **단가와 범위를 정하는 국면**이다. Apple의 엔지니어 일일 AI 한도 300 → 200달러, Gemini 4 Carbon의 12월 1일 가격 2배(브리핑 기준, 미확인), Anthropic의 Nasdaq 로드쇼(티커 ANT, 주당 70~78달러), 그리고 학습 쪽에서는 OPD 논문이 "롤아웃을 얼마나 싸게 뽑아도 되나"를 재고 있다. 11/9 노트의 Goldman(직군 한정), 11/10 노트의 비용-정확도 곡선과 이어지는 흐름 — **"쓸까"는 끝났고 "어디에, 어느 모델을, 얼마에"가 남았다.**

## 깊게 본 것

### 1. 아마존 티켓 분류 — Sonnet 4.6을 결정 모델로 바꾸고 비용 98% 절감

**무슨 일인가.** Strands Agents 블로그 2026-11-09(아마존 엔지니어 Carr Onstott·Mehul Jaiswal 공저, 원문 전체 읽음). 아마존·AWS의 대형 사내 티켓 시스템은 들어오는 티켓(고객 에스컬레이션, 용량 요청, 자동 알람, 보안 발견 등)을 20개 카테고리 중 하나로 라벨링해야 한다. 기존: Bedrock으로 Sonnet 4.6 호출, 티켓마다 긴 시스템 프롬프트, JSON + 추론문 생성. 교체: Strands Decider E4B(Gemma 4 기반 빌드)를 SageMaker 엔드포인트로.

**배경 — 왜 지금인가.** Decider는 한 달 전 공개됐다(10/8 노트에서 다룬 2B는 Qwen3.5-2B에서 언어 모델 헤드를 떼고 포인터 헤드를 단 모델). 팀은 원래 2B로 시작했는데 자체 테스트 세트에서 **E4B Gemma 4 빌드가 확실히 나아서** 갈아탔다. 결정 모델 쪽에 "더 큰 몸통" 선택지가 생긴 게 이번 교체를 가능하게 했다. Sonnet 4.6은 "9개월 된 모델"로, 지능과 비용의 골디락스 선택이었다고 적었다.

**기술적으로 어떻게 동작하나.**

- **문제 재구성**: 상태 = 티켓, 선택지 = 라벨 카탈로그. 프로덕션 라벨 설명 원문만으로 Decider의 **4,096 토큰 창을 넘어서**, 20개 라벨을 각각 1~2문장 기준으로 다시 쓰고 "해당 없음"을 추가해 하나의 선택형 질문으로 보냈다. 긴 티켓은 **가장 오래된 댓글부터 버려** 창에 맞춘다(브리핑에 없는 대목).
- **판정**: 선택지별 확률 + 신뢰도. 신뢰도가 임계값을 넘을 때만 라벨 적용(임계값은 튜닝).
- **인프라**: 티켓 이벤트 → SQS → Lambda → SageMaker 엔드포인트(`ml.g5.xlarge`, A10G 24GB, 모델 약 19GiB, 요청당 약 640ms, 오토스케일, **네트워크 격리로 컨테이너 아웃바운드 차단**, 가중치는 시작 시 S3에서 복사). 스위치는 AppConfig, 관측은 CloudWatch, 스택은 CDK로 Beta/Gamma/Prod 단계 배포.
- **3단 스위치(메시지마다 AppConfig 조회)**:

| 모드 | Sonnet | Decider | 적용되는 결과 |
| --- | --- | --- | --- |
| `BEDROCK` | 호출 | 미호출 | Sonnet |
| `DUAL` | 호출 | 병렬 호출 | Sonnet(Decider는 비교만) |
| `DECIDER` | 미호출 | 호출 | Decider |

**측정치(원문 표).**

| | Sonnet 4.6 | Decider E4B | 개선 |
| --- | --- | --- | --- |
| 호출당 평균 시간 | 4,215 ms | 897 ms | 78% |
| 티켓당 입력 토큰 | 6,554 | 2,009 | |
| 티켓당 출력 토큰 | 170 | 1 | |
| 티켓당 총 토큰 | 6,724 | 2,010 | 70% |
| Lambda 평균 실행 | 3,312 ms | 748 ms | 74% |
| 티켓당 비용(정가) | $0.0222 | 약 $0.0005 | |
| 100만 건당 | 약 $22,200 | 약 $500 | 약 44배, 98% |

비용 계산이 투명하다: 인스턴스 시간당 $1.408, 요청당 640ms면 인스턴스 한 대가 시간당 약 5,600건 → 완전 가동 시 100만 건당 $250, 버스트 여유를 두면 실제로 약 $500.

**실무에 무슨 의미인가.**

- **"답이 닫힌 목록에서 하나 고르기라면 LLM 작업이 아니다."** 출력 토큰 170 → 1이 전부를 말한다. WMS 프로젝트로 옮기면: 입고 검수 결과 분류, 반품 사유 분류, 알람 라우팅처럼 **카탈로그가 고정된 분류**가 후보다. 자유 서술(반품 사유 설명문 생성 등)은 아니다.
- **DUAL 모드는 AI와 무관한 교과서 패턴이다** — 섀도 트래픽 + 피처 플래그. 신구 구현을 같은 실트래픽에 돌려 **불일치 건을 하나씩 판정**하고, 롤백은 45초짜리 설정 변경. 팀이 "어떤 오프라인 평가보다 많이 알려줬다"고 한 것도 이 부분이다. Spring 쪽이라면 `@ConfigurationProperties` + 원격 설정(Spring Cloud Config·AppConfig)으로 모드를 읽고, DUAL에서는 두 구현을 `CompletableFuture`로 병렬 호출해 결과 불일치만 로그로 남기는 형태다.
- **JSON 키 순서가 답을 바꿨다**: 같은 내용을 키 순서만 바꿔 보냈더니 출력 확률이 최대 **0.19** 움직였다. 팀의 수정은 **모든 요청을 키 정렬해서 보내기**(브리핑은 문제만 전하고 이 수정은 뺐다). 결정 모델을 API 뒤에 둘 때 "직렬화가 결정적인가"가 정확도 문제가 된다는 뜻이다 — Jackson이라면 `ORDER_MAP_ENTRIES_BY_KEYS`·`SORT_PROPERTIES_ALPHABETICALLY` 같은 설정이 갑자기 모델 품질 설정이 된다.

**반론·회의적 시각.**

- **정확도 숫자가 없다.** "똑같이 잘했다", "별도 티켓 세트에서 프로덕션 Sonnet을 이겼다"뿐 — 정확도·일치율·표본 수·DUAL 기간의 불일치율·불일치 판정 결과가 한 줄도 없다. 이 글의 가장 강한 주장("just as well")이 가장 약한 근거 위에 있다.
- **벤더 블로그다.** 결정 모델을 만든 Strands 팀의 블로그에 사용자 팀이 쓴 글이다.
- **비교가 공정한가.** Sonnet 쪽은 긴 시스템 프롬프트 + 추론문 + JSON이었다. 라벨을 1~2문장 기준으로 다시 쓴 작업 자체가 Sonnet 프롬프트도 줄였을 것이다 — "같은 재구성을 Haiku에 줬다면?"이라는 대조군이 없다.
- **비용 범위**: 정가 기준, Lambda·SageMaker 부대비용과 엔지니어링 시간·재학습 비용 제외. 오토스케일 여유분을 넣어 $500으로 잡은 건 정직하다.
- **스스로 적은 한계**: 라벨에 설명문이 필요하거나, 카탈로그가 매주 바뀌거나, 필요한 맥락이 수천 토큰에 안 들어가면 못 쓴다. 그리고 긴 티켓에서 **오래된 댓글을 버리는 절단**이 어떤 오분류를 만드는지는 보고하지 않았다.

### 2. AlphaProof Code — Signal 프로토콜 "구현"을 Lean으로 4주에 검증

**무슨 일인가.** Google DeepMind 2026-11-10(Pushmeet Kohli·Swarat Chaudhuri, 발표문 전체 읽음). Signal과 Google Messages가 쓰는 Signal 핵심 암호 프로토콜의 **실제 코드**가 보안 성질을 만족한다는 것을 기계 검증 증명으로 보였다. 대상 성질에는 "기기가 일시적으로 탈취되기 전과 후에도 메시지가 보호된다"가 포함된다. DeepMind는 "널리 배포된 암호 프로토콜을 이 깊이로 AI가 검증한 첫 사례"이자 "이런 프로토콜의 구현이 *어떤 방법으로든* 형식 검증된 첫 사례"라고 주장한다.

**배경 — 왜 지금인가.** 프로토콜 형식 분석은 수십 년 됐지만 대부분 **설계 수준**에서 멈췄다(Signal 설계에 대한 학계의 형식 분석은 이미 여럿 있다). 실제 취약점은 설계와 구현 사이의 틈에서 나오는데, 구현 수준 검증은 전문가 팀이 수년 걸리는 일이라 작은 범위에만 했다. 에이전트가 증명 *생성*을 싸게 만들자 그 범위가 넓어진 것이다. Signal CTO Ehren Kret이 직접 "이전 형식 검증은 코드의 작은 부분에 집중했다"고 코멘트했다.

**기술적으로 어떻게 동작하나.** 연구팀처럼 일을 나눈다.

1. **명세(Specification)**: 사람과 여러 모델이 Signal의 보안 목표를 Lean 명세로 번역한다. **명세는 사람 전문가가 전부 검토·승인**한다.
2. **코드(Code)**: 컴파일된 머신 코드를 Lean의 프로세서 모델 위에서 다룬다. 즉 "소스가 맞다"가 아니라 "기기에서 도는 그 명령어가 맞다"까지 내려간다.
3. **증명(Proof)**: Gemini Carbon 기반 "증명자 팀"(신뢰하지 않음)이 증명을 쓰고, Lean이라는 "문지기"(신뢰함)가 기계적으로 검사한다. 다른 에이전트가 증명을 감사해 사람이 다시 봐야 할 곳 — **코드베이스의 약 1%** — 을 표시한다.

검증 능력 확인: 이미 고쳐진 **실제 버그 2개**를 격리 사본에 되심었더니, 두 경우 모두 "이 버전은 안전하지 않다"는 기계 검증 증명을 냈다. 산출물은 오픈소스로 공개 중이고 기술 논문 PDF가 함께 나왔다.

**실무에 무슨 의미인가.**

- 구조가 핵심이다: **생성은 싸고 불신, 검증은 비싸고 신뢰.** 증명자가 거짓말을 해도 문지기가 통과시키지 않으면 그만이다. 이건 "에이전트가 쓴 코드를 사람이 다 못 읽는다"는 불안에 대한 가장 설득력 있는 답 중 하나다. 테스트·마이그레이션·리뷰로 옮기면: **에이전트의 결과를 검사하는 기준(테스트·계약·스키마 검증·쿼리 결과 대조)을 사람이 쓰고 신뢰 가능한 기계가 돌린다.** 에이전트 자신의 "완료 보고"는 문지기가 아니다(10/20 노트 「완료 보고는 증거가 아니고」와 같은 결론).
- 사람의 일이 "명세 검토"로 이동한다. 백엔드로 말하면 **API 계약·불변식을 정확히 쓰는 능력**의 값이 오른다.

**반론·회의적 시각.**

- **숫자가 발표 페이지 안에서 어긋난다**: 본문은 "Lean 600만 줄 이상 생성", 메타 설명은 "기계 검증된 증명 300만 줄 이상". 생성 총량과 최종 증명량의 차이일 수 있지만 페이지가 설명하지 않는다(브리핑 지적 확인).
- **증명은 명세만큼만 옳다.** 명세가 원하는 성질을 빠뜨리면 증명도 같이 빠뜨린다. 그 부분은 사람 검토에 달려 있고, 사람이 검토한 명세의 양·검토 시간은 공개되지 않았다.
- **"첫 사례" 주장의 범위.** 암호 *원시 연산* 수준의 검증된 구현(HACL\* 같은)은 이미 있다. DeepMind의 주장은 "프로토콜 구현 전체를 이 깊이로"에 한정해 읽어야 한다. 기술 논문은 이번에 읽지 못했다.
- **가장 유리한 대상이다.** 범위가 명확하고 보안 성질이 수학적으로 정의돼 있는 암호 프로토콜은 형식 검증의 최적 대상이다. 명세 자체가 모호한 CRUD·업무 규칙 코드에 같은 방식을 바로 쓸 수 있다는 뜻이 아니다.
- **4주의 비용**이 공개되지 않았다(컴퓨트·사람 시간).

### 3. Fireworks AI 침해가 Notion까지 — 샌 것은 "쌓아 둔" 데이터였다

**무슨 일인가.** Notion 도움말 공지(전체 읽음)와 Fireworks AI 보안 공지 업데이트(2026-11-09 수정, 전체 읽음)를 교차해 읽었다.

- **Notion**: Fireworks를 두 가지로 썼다 — ① Insights 기능(고객이 자기 AI 사용을 이해하도록 돕는 분류 작업), ② 제품 안에서 오픈웨이트 모델을 서빙하는 일반 추론 제공자. 과거에는 LEAP 프로그램(자원한 고객 데이터)으로 작업별 모델 학습 실험도 Fireworks에서 했다. 11월 초 Fireworks로부터 잠재적 사고를 듣고 연결을 전부 끊었고, **11월 3일 기준** 연결 해제·Fireworks 쪽 데이터 전부 삭제·트래픽 중단·학습 중단. 11/6 Fireworks가 "악의적 행위자가 고객 데이터에 접근했을 수 있다"고 통보, 11/8 해당 데이터셋 확인. 결과: **워크스페이스 1% 미만**에서 **Insights용 비귀속 대화 기록**이 노출됐을 수 있다. **기술적으로 어떻게 동작하나(무엇이 지켜졌고 무엇이 샜나).**

- **보내기 전에 식별자를 뗀다.** 비귀속 설계 덕분에 피해가 "누군지 모르는 대화 조각"으로 줄었다. 내 서비스에서 LLM에 로그·티켓을 보낼 때 사용자 ID·이메일을 가명화하는 레이어를 두는 것과 같은 원리.
- **프롬프트에 비밀을 넣지 않는다.** Notion의 권고가 정확히 이것이다. 11/8 노트의 Apiiro(허락 기록에 비밀이 남음)와 같은 결론이 이번엔 실제 사고로 왔다.

### 4. Flide — 결정 모델 전용 추론 엔진, "정확한 상태 분기"

**무슨 일인가.** NUS 연구진(Bobo Li 외) 논문, HF ▲31(초록·저자 코멘트 읽음). Jev 계열 결정 모델용 오픈소스 추론 엔진. vLLM·SGLang 대비 최대 **9.5배** 빠르고, float32 기준값과의 총변동거리(TVD)가 가장 작다. `pip install flide`, Decision Index 0.4.1의 오픈소스 결정 모델 30개 이상 지원.

**배경.** 1번의 아마존 사례가 "결정 모델을 실제로 서빙하면 무엇이 필요한가"를 물었다면 이게 답의 하나다. 결정 모델의 작업 패턴은 생성과 다르다: **같은 상태(긴 공통 앞부분)에 대해 질문·선택지 여러 개를 각각 따진다.** 생성용 엔진에 맡기면 ① 공통 앞부분을 분기마다 다시 계산하거나(느림) ② 배치·접두부 캐시 처리 과정에서 출력 확률이 미묘하게 틀어진다(위험 — 신뢰도 임계값으로 판단하는 시스템에선 확률이 곧 판단이다).

**기술적으로 어떻게 동작하나.** 결정 요청의 **논리적 트리 구조**(공통 상태 → 질문 분기들)를 **물리적 실행**(하나의 평탄화된 토큰 스트림)과 분리한다. 분기 구조를 GPU에 상주하는 메타데이터(인덱스)로 표현하고, **ForkAttention**이 그 인덱스를 따라 각 분기가 공통 상태만 보고 서로는 보지 않게 한다 — 표준 어텐션뿐 아니라 순환형 Gated DeltaNet 층(11/9 AI 심층 「지우기와 쓰기를 따로 다는 선형 어텐션」에서 본 계열)에서도. 결과적으로 **각 분기는 정확한 산술로 독립 forward pass와 같은 값**을 낸다. 다양한 요청 조합을 미리 기록해 둔 소수의 실행 그래프로 처리하고, 길어지는 에이전트 히스토리는 이전 패스의 체크포인트에서 재개한다.

**실무에 무슨 의미인가.** "모델이 좋다"와 "모델을 싸고 정확하게 돌릴 수 있다"는 별개 문제이고, 새로운 모델 형태에는 새 서빙 계층이 따라온다. 9/22 Kev·Jev가 0.5B로 6질문 160ms를 냈을 때부터 이 형태는 "한 번의 forward pass로 여러 질문"이 핵심이었는데, Flide는 그걸 서버 레벨로 일반화했다. 결정 모델을 붙일 생각이면 모델보다 **엔진이 확률을 정확히 보존하는지**부터 확인해야 한다(1번의 JSON 키 순서 0.19와 같은 종류의 위험).

**반론·회의적 시각.** "최대 9.5배"는 최댓값이다 — 분기가 넓을 때와 깊을 때 이득이 다를 수 있다(HF 댓글도 같은 질문). vLLM·SGLang은 결정 모델용으로 만들어진 게 아니라 비교가 기울어 있다. 본문(벤치마크 조건·모델 크기·배치 구성)은 읽지 못했다.

**원문**: [HF](https://huggingface.co/papers/2610.42148) · [arXiv 2610.42148](https://arxiv.org/abs/2610.42148) · [GitHub OmniJev/Flide](https://github.com/OmniJev/Flide)

### 5. 온폴리시 증류는 학습-추론 불일치를 얼마나 견디나 (원리는 AI 심층으로)

**무슨 일인가.** Cong Yu 외(Aalto·Cambridge 등), HF ▲8. 롤아웃을 싸게(FP8 양자화·비동기) 뽑을 때 생기는 "엔진 ≠ 학습 모델" 불일치를 토큰당 KL 하나의 자로 재고, OPD가 7B 학생에서 표준 엔진의 200배 넘는 불일치(0.184 nats/token)까지 품질을 지키고 0.39에서 무너진다는 것을 보였다. 같은 엔진에서 REINFORCE·GRPO는 약 12배·60배에서 깨졌다.

**배경과 동작.** AI 심층 노트에 정리했다. 핵심 세 줄: ① 8버전 묵은 가중치는 0.0028로 거의 무해했고, 위험은 **FP8 KV 캐시**였다. ② 그중 **첫 층 키**가 93~99%를 차지했다 — 첫 층만 BF16으로 남기면 0.52 → 0.0037. 키 투영 바이어스가 있고 Q/K 정규화가 없는 DeepSeek 계열의 구조 때문이며 Llama·Qwen3는 덜 민감하다. ③ GPU 한 장 24분짜리 입장 검사로 후보 6개를 걸렀고 사전 판정 8건이 다 맞았다. FP8 + 비동기로 동기 BF16과 같은 품질에 1.62배 빨리.

**실무에 무슨 의미인가.** 모델 학습을 안 해도 가져갈 틀: **"최적화가 사는 불일치를 하나의 지표로 재고, 실패 기준을 미리 적고, 싼 사전 검사 + 운영 중 모니터링."** 캐시 TTL·읽기 복제본·비동기 처리도 같은 거래다. 그리고 "평균 뒤의 집중을 쪼개라" — 문제는 FP8 전체가 아니라 한 층의 한 텐서였다.

**반론·회의적 시각.** 수학 하나, 주력 쌍 하나(교사가 학생의 RL 미세조정판이라 가깝다), 설정당 1회 실행, 200스텝까지. 1.5B는 비슷한 불일치에서 +420~479%로 폭망 — 예산은 모델마다 다르다. 그리고 브리핑이 뺀 단서: **GRPO·REINFORCE는 200스텝 안에 저자들의 "학습이 되는가" 검사 자체를 통과하지 못했다** — "RL은 12배에서 깨진다"는 비교를 그만큼 덜어서 읽어야 한다.

**브리핑 정정·보충**

1. **(보충) 아마존 "JSON 키 순서만 바꿔도 확률이 0.19까지".** 원문은 그 다음 줄에 수정을 적었다 — **모든 요청을 키 정렬해 보낸다**, 결정 모델을 API 뒤에 둔다면 런 비교 전에 확인하라.
2. **(보충) 아마존 "4,215 → 897ms".** 인스턴스 한 대 기준 요청 처리는 약 640ms, Lambda 평균 실행은 3,312 → 748ms(74%). 처음엔 2B로 시작했다가 E4B로 바꿨고, **긴 티켓은 오래된 댓글부터 잘라** 4,096 창에 맞춘다는 대목이 브리핑에 없다.
3. **(정정) Notion "11월 3일 Fireworks에서 잠재적 사고를 전해 듣고".** 원문은 "이달 초 들었고, 11월 3일 기준 연결 해제·삭제·학습 중단 완료". 
4. **(보충) Fireworks 쪽 사실.** 침입 경로는 Fireworks R&D 머신을 호스팅한 **제3의 클라우드 업체**(10/23 사고 → 10/24 Fireworks 개발 머신), 동기는 **LLMJacking** 추정, **ZDR 기본인 추론·Training SDK·Nexus는 영향 미탐지**, 영향은 저장 비밀·청구 정보·일부 데이터셋·미완성 가중치. 브리핑은 Notion 쪽만 전했다.
5. **(확인) AlphaProof Code "600만 줄 vs 300만 줄".** 본문은 "over six million lines of Lean" 생성, 메타 설명은 "over three million lines of machine-checked proof" — 페이지 안의 불일치가 맞다.
6. **(보충) OPD 불일치 논문 "RL 기법은 12배·60배에서 깨졌다".** 부록 한계 절: GRPO·REINFORCE는 200스텝 안에 저자들의 학습 검사를 통과하지 못했다. 또 브리핑의 "업보트 8"은 기사 작성 시점 값(HF 페이지 기준 6~8).
7. **(미확인) Gemini 4 Carbon 12/1 가격 2배, Apple 한도, Anthropic 로드쇼 세부.** 원문을 읽지 않았다.

## 더 알아볼 것

- [ ] **WMS에서 "닫힌 선택" 찾기.** WMS 프로젝트의 기능 중 "고정된 카탈로그에서 하나 고르기"(반품 사유 분류, 알람 라우팅, 입고 검수 판정 등)가 무엇인지 목록을 만들고, 각각이 결정 모델·규칙·LLM 중 무엇으로 충분한지 아마존 글의 세 조건(라벨 설명문 필요 없음 / 카탈로그 안정 / 맥락이 수천 토큰 안)으로 판정해 본다.
- [ ] **DUAL 모드를 Spring으로 스케치.** 구 구현과 신 구현을 같은 요청에 병렬 호출하고(구 결과만 적용), 불일치만 로그로 남기며, 모드(OLD/DUAL/NEW)를 재배포 없이 바꾸는 구조를 클래스 다이어그램 수준으로 그려 본다. 쿼리 최적화 Before/After 측정에도 이 틀을 쓸 수 있나?
- [ ] **직렬화가 결정적인가.** 내 프로젝트의 Jackson 설정에서 같은 객체가 항상 같은 키 순서로 직렬화되는지 확인한다(`Map` 필드, `@JsonPropertyOrder`, `ORDER_MAP_ENTRIES_BY_KEYS`). 캐시 키·서명·해시를 JSON으로 만드는 곳이 있다면 같은 문제가 이미 숨어 있지 않나?
- [ ] **내 AI 데이터 흐름도.** Vault RAG 프로젝트를 가정하고, 노트 → 임베딩 API → 벡터 DB → 생성 API 각 단계에서 **어느 업체에 무엇이 얼마나 남는지(ZDR 여부·보존 기간)**, 업체를 끊을 때 무엇을 지울 수 있는지 표로 적는다. 사용자 식별자를 떼고 보낼 수 있는 지점은 어디인가?
- [ ] **"생성은 불신, 검증은 신뢰"를 테스트로.** 에이전트에게 코드를 맡긴다면 사람이 먼저 써야 할 "문지기"는 무엇인가 — API 계약 테스트, DB 제약 조건, 아키텍처 규칙(ArchUnit) 중 이미 갖춘 것과 없는 것을 구분해 본다.

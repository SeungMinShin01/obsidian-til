## 오늘의 흐름

먼저 겹치는 것. 오늘(10/25) 브리핑의 절반이 어제 노트에서 이미 다룬 항목이다 — Agent Skills의 AAIF 기증과 cloudflare/security-audit-skill(10/22~10/24), NVIDIA OpenShell(10/24 깊게), Raw-RAG·Agent Mosaic(10/24 깊게), WeVisOne-VL·OpenDS-World·IQuest-Q1·Deep Fusion Memory·Heartbeat Thinking(10/24 짧게), eMudhra(10/21~10/23), Local Wikipedia. 이 노트는 **새 항목**만 본다 — Kimi K3.1 Pro, Brotli CVE-2026-111497(10/23 노트에 Node 릴리스 한 줄로만 나왔던 것의 전모), Block의 Dessa, 분산 SQLite 12년 회고, Meta Expert 논문.

첫 번째 축은 **"격차는 한 점까지 줄었고, 그 한 점을 누가 재는지가 문제다."** Moonshot의 Kimi K3.1 Pro는 Terminal-Bench 4.0에서 65.7%로 Claude Opus 5.5(66.4%)와 0.7점 차, Artificial Analysis 집계 55점으로 Opus 5.5(58) 바로 다음이다. 11월 4일까지 가중치를 푼다. 10/06 노트의 "모델은 책상으로 내려오고"가 소형 모델 이야기였다면, 이번에는 **프런티어 바로 아래 층이 통째로 오픈웨이트로 내려온다.** 그런데 같은 발표에서 가장 새로운 문장은 성능이 아니라 **오픈웨이트판에서 사이버 데이터를 일부러 뺐다**는 것이다 — 빼지 않은 체크포인트는 내부 xdev-bench-hard 90.5, 공개판은 81.0. "오픈웨이트로는 절대적 사이버 프런티어를 넓히지 않겠다"는 정책을 모델 회사가 수치와 함께 먼저 적었다. 능력을 *끌어올리는* 경쟁 옆에 능력을 *깎아서 맞추는* 설계가 공식 항목으로 생겼다.

두 번째 축은 **"고친 것과 '보안 수정'이라고 이름 붙인 것은 다른 일이다."** Brotli 디코더 버그의 뿌리는 `bool` 하나가 "스트림이 깨졌다"와 "입력이 더 필요하다" 두 뜻을 동시에 지고 있었다는 것이고, fast path는 그 반환값마저 무시했다. 더 아픈 건 일정이다 — OpenAI가 2월에 찾아 소스는 그때 고쳐졌지만 **보안 문제로 인식되지 않아 릴리스에 실리지 않았다.** 그리고 지금은 CVE가 PyPI 패키지에 매핑되지 않아 pip-audit·Dependabot·Safety가 **통과**를 낸다. 10/22 노트의 PHP("징후는 2024년에 봤지만 정하지 못해 2년이 갔다")와 같은 모양이다 — 병목은 알아내는 쪽이 아니라 *라벨을 붙이는* 쪽에 있었다. 반환값의 두 뜻, 커밋의 두 뜻(일반 수정 / 보안 수정), 스캐너의 두 뜻(취약점 없음 / 매핑 없음)이 같은 구조로 겹친다.

세 번째 축은 어제 시작한 **"중간 가공층을 걷어내기"**의 연속이다. 어제는 Raw-RAG(요약·원자적 사실을 버리고 생 기록 검색)와 Deep Fusion Memory(검색 자체를 걷어냄)였다. 오늘 Dessa는 음성 비서의 STT→LLM→TTS에서 **텍스트라는 중간 표현을 통째로 뺐고**, Meta Expert는 MoE의 "층마다 따로 둔 전문가"라는 칸막이를 걷어 **한 풀을 모든 층이 공유**하게 했다. 둘 다 "중간 표현이 정보를 버리고 있었다"는 진단이다 — 웃음·한숨이 글자로 바뀌며 사라지고, 층마다 같은 지식이 중복 저장된다.

네 번째는 몇 주째 이어진 **기준선과 측정 조건 다시 묻기**(10/16, 10/24)다. ClickBench가 쿼리별 전용 커널과 결과 캐시를 쓴 pgrust를 퇴출했고, "Rust보다 빠르다"는 Tov 주장은 재현에 실패했다. Kimi 발표의 벤치마크도 Moonshot이 고른 조합이고 일부는 내부 벤치마크다. 분산 SQLite 회고의 결론 — "도구를 고르기 전에 질문을 고르라" — 가 이 축의 실무판이다. 같은 숫자도 *무엇을 묻는 측정인가*를 먼저 정하지 않으면 논쟁이 엇갈린다.

## 깊게 본 것

### 1. Kimi K3.1 Pro — 오픈웨이트 3T급이 Opus 5.5를 0.7점 차로

**무슨 일인가.** Moonshot AI가 K3.1 시리즈 첫 모델 Kimi K3.1 Pro를 공개했다. K3에 후속 학습(post-training) 연산을 크게 늘린 버전이고, 컨텍스트 100만 토큰. API ID는 `kimi-k3.1-pro`와 2~3배 빠른 `kimi-k3.1-pro-highspeed`. 아키텍처·파라미터 수는 "3T급"이라는 표현 외에 **미공개**. 전체 가중치는 **2026-11-04까지** 공개 예정(라이선스는 발표문에 없음).

**배경 — 왜 지금인가.** 9/11 노트에서 Kimi K3(2.8T)는 Cognition SWE-2의 기반 모델로, 9/28 노트에서는 Fireworks Ember-1(추론 길이 압축)의 기반으로 등장했다. 즉 K3는 이미 **남이 그 위에 후속 학습을 얹는 바닥 모델** 역할을 하고 있었다. K3.1 Pro는 Moonshot이 그 후속 학습을 직접 대규모로 한 결과다 — 발표문 표현으로 "수백 개 다운스트림 도메인에 걸친 대규모 공동 강화학습(RL)", 그리고 RL 프레임워크·장문 추론·샌드박스·롤아웃 스케줄링·환경 품질 검사 같은 **인프라 작업**. "RL 연산을 늘리면 안정적이고 예측 가능한 이득"이라는 주장이 핵심이다. 사전학습이 아니라 후속 학습 규모가 성능의 주 변수가 됐다는 9/10 노트의 흐름("post-training이 판을 먹은 날")이 한 달 반 만에 프런티어 직전까지 온 것.

**숫자 — 무엇이 앞서고 무엇이 뒤지나.**

브리핑이 강조한 "환각률 23.4% → 8.3%"는 맞지만, 같은 표에서 **가장 낮은 건 GPT-6 Astra**다. 그리고 발표문 스스로 이 벤치는 실패하기 쉬운 사례를 일부러 모은 스트레스 테스트라 일상 오류율이 아니라고 적었다.

**기술적으로 — 사이버 능력은 어떻게 '뺐나'.** 발표문의 설명은 짧지만 구조는 분명하다. 후속 학습을 늘릴수록 취약점 연구 성능이 같이 올랐고, 원인은 일반 중간학습(mid-training) 코퍼스와 RL 환경 혼합에 사이버 관련 데이터가 섞여 있었기 때문. 공개판은 **중간학습과 RL 두 단계 모두에서** 사이버 데이터를 빼되 일반 코딩 과제는 남겼다. 예비 실험에서 두 단계 중 하나라도 남기면 사이버 능력이 크게 오른다고 했다. 결과는 K3(33.3) → 공개판(81.0) → 미제거판(90.5). 즉 "뺐다"는 0으로 만든 게 아니라 **9.5점 깎은 것**이고, 공개판도 K3보다 훨씬 높다. 회사의 정책 문장은 "공개된 지 최소 3개월 된 프런티어 독점 모델보다 뒤에 둔다".

**실무에 무슨 의미인가.**

- **비용.** Simon Willison 기준 가격은 입력 $2 / 출력 $10 (백만 토큰당) — Opus 5.5의 절반, GPT-6.1 Sol과 같음. Highspeed는 2배 가격(캐시 적중 입력은 동일). 가중치가 풀리면 추론 제공업체 경쟁으로 더 내려갈 여지가 있다. 3T급은 개인 장비로는 못 돌린다 — 실질 수혜는 "제공업체 선택지가 늘어나는 것"이다.
- **에이전트 평가 지표 읽기.** Terminal-Bench는 터미널에서 빌드·테스트·수정을 끝까지 돌리는 능력을 본다. Gradle/Maven 프로젝트에서 체감과 가장 가까운 축이다. 다만 BenchCAD에서 보이듯 **툴을 쓸 때 격차가 더 벌어진다**(툴 없음 0.2점 차 → 툴 사용 3.5점 차). 모델 자체보다 툴 사용 RL의 차이일 수 있다.
- **데이터 보존.** API에 Zero Data Retention 옵션이 있다. 회사 코드를 넣을 때 확인할 항목이다.

**반론·회의적 시각.** 벤치마크 조합은 Moonshot이 골랐고 Kimi Code Bench·Hallu Bench·xdev-bench는 내부 벤치다. 발표문 각주에는 독점 모델 테스트에 "일부 폴백 동작이 있을 수 있다", OfficeQA에서 외부 모델이 온라인으로 답을 찾은 궤적은 0점 처리했다는 단서가 있다 — 비교 조건이 완전히 같지 않다는 뜻이다. 파라미터 수·아키텍처·라이선스가 없다. HN 댓글이 559개로 포인트(939)의 절반을 넘은 건 성능보다 "중국 랩의 오픈웨이트 추격"이라는 구도를 두고 논쟁이 붙었다는 신호로 읽힌다(브리핑 해석). 사이버 데이터 제거는 **오픈웨이트에서는 되돌릴 수 있다** — 가중치를 받은 쪽이 사이버 데이터로 다시 미세조정하면 그만이다. 10/21 노트의 abliteration(가중치에서 거부 방향을 깎아내는 기법)과 같은 문제다.

### 2. Brotli CVE-2026-111497 — `bool` 하나가 두 뜻을 지고 있었다

**무슨 일인가.** Google Brotli 압축 라이브러리 디코더의 범위 밖 쓰기(out-of-bounds write). CVSS v4.0 **9.2**, CWE-252(반환값 미검사) + CWE-787(범위 밖 쓰기). 영향 범위 Brotli **1.0.3 ~ 1.2.0**. Node.js가 먼저 공개하면서 "node2shell"로 불렸고, Python으로 번지자 "HTTP2Shell"로 불리는 분위기다. 10/23 노트에서는 Node 10/21 보안 릴리스 10건 중 하나로 한 줄만 다뤘다.

**기술적으로 어떻게 터지나.** Brotli 스트림은 블록 단위로 허프만 트리를 바꿔 가며 디코딩한다(block switch). 그 전환을 처리하는 `DecodeBlockTypeAndLength()`가 `bool`을 반환하는데,

1. `false`가 **"스트림이 깨졌다"**와 **"입력이 더 필요하다"** 두 경우 모두에 쓰여 호출자가 구분할 수 없다.
2. **fast path에서는 반환값을 아예 무시**한다.

공격자는 블록 타입 하나를 선언하고 그 블록 길이를 다 쓴 뒤, *성공할 수 없는* 블록 전환을 강제하는 스트림을 만든다. 그러면 디코더는 (a) 이미 끝난 스트림인데 입력을 계속 기다리거나 (b) **낡은 블록 상태로 디코딩을 이어가다** 메모리를 넘어 쓴다. 업스트림 수정(커밋 `0ed4268`)은 함수가 에러 코드를 반환하게 하고 `BROTLI_DECODER_ERROR_FORMAT_BLOCK_SWITCH`(-17)를 추가해 두 경로 모두에서 포맷 오류 시 멈추게 했다.

Java로 옮기면 이런 모양이다 — `boolean read()`가 false를 낼 때 "EOF"인지 "아직 데이터 없음(논블로킹)"인지 모르는 API. Java NIO가 `read()`의 반환값을 `-1`(EOF) / `0`(지금은 없음) / 양수(읽은 바이트)로 나눈 이유가 정확히 이것이다. 그리고 반환값을 무시하는 fast path는 `InputStream.read(byte[])`의 반환값을 안 보고 버퍼가 다 찼다고 가정하는 흔한 버그와 같다.

**왜 '양방향'인가 — 내 코드가 import하지 않아도.**

- **아웃바운드(클라이언트가 맞는다).** Python에서 Brotli 또는 brotlicffi가 *설치만 돼 있으면* urllib3(그래서 requests)가 `Accept-Encoding: br`을 광고하고 응답을 자동 디코딩한다. httpx는 `httpx[brotli]` extra, aiohttp도 Brotli가 깔려 있으면 같다. 웹훅 수신 확인, URL 미리보기, 크롤러처럼 **내가 통제하지 않는 서버를 호출하는 코드**가 표적이다.
- **인바운드(서버가 맞는다).** `Content-Encoding: br`인 요청 본문을 디코딩하는 미들웨어·프레임워크. Node 내장 `fetch()`와 body-parser 경로, Bun, Envoy, Istio, curl/libcurl.
- **해당 없음.** Apache `mod_brotli`와 Nginx 기본 설정은 디코딩하지 않는다(압축만 함).

**패치 버전.** Node 22.23.4 / 24.22.1 / 26.12.1, Bun 1.4.4(컴파일된 실행 파일은 재빌드 필요), Envoy 1.40.0·1.39.3·1.38.6·1.37.8, Istio 1.29.9(EOL 라인)·1.30.6·1.31.2, libbrotli 1.2.1(백포트 1.0.10·1.1.1), Python Brotli 1.2.1·brotlicffi 1.2.1.0. OS 벤더는 버전 번호를 안 바꾸고 백포트할 수 있다.

**왜 스캐너가 놓치나.** 10/23 기준 CVE 레코드·OSV·GitHub Advisory DB가 이 CVE를 **PyPI 패키지에 매핑하지 않았고**, Brotli 릴리스 노트에도 CVE 언급이 없다. 스캐너는 "패키지 이름+버전 → 자문"을 조회하므로 매핑이 없으면 취약 버전도 깨끗하게 나온다. Aikido 글은 같은 글 안에서 GHSA-9v8h-qqgm-4m35를 인용해 "GitHub DB에 없다"와 모순되는 부분이 있다 — 매핑이 진행 중이라는 뜻일 수 있다.

**실무에 무슨 의미인가 — 내 Spring Boot 기준으로.**

- **Java 본체는 이 목록에 없다.** Tomcat은 기본적으로 요청 본문의 `Content-Encoding`을 풀지 않는다(압축 *응답*은 gzip만 기본). 하지만 앞단의 **Envoy/Istio**, 빌드에 쓰는 **Node 도구**, 데이터 수집용 **Python 스크립트**(수집기 프로젝트가 requests를 쓴다면 바로 해당)는 각자 디코딩한다. "내 백엔드가 Java라서 괜찮다"는 방어가 안 된다.
- **확인 순서.** ① `pip show Brotli brotlicffi`를 각 환경·컨테이너 이미지 안에서(`docker run --rm <image> pip show ...`) ② `pipdeptree -r -p Brotli`로 누가 끌고 왔는지 ③ 외부 서버를 호출하거나 압축 본문을 받는 서비스부터 올리기.
- **당장 못 올리면.** 인바운드는 프록시·LB·미들웨어에서 `Content-Encoding`에 `br`이 있으면(대소문자 무시) 디코딩 전에 거부. 아웃바운드는 `Accept-Encoding`에서 `br`을 빼는 것만으론 부족하다 — 악성 서버는 광고와 상관없이 보낸다. Python은 Brotli/brotlicffi를 제거하면 클라이언트가 gzip·deflate로 내려간다.
- **교훈 하나.** 실패를 `bool`/`null`로 돌려주는 API는 실패의 *종류*를 지운다. Java라면 예외 타입을 나누거나, `Optional` 대신 sealed 결과 타입(성공/재시도 가능/포맷 오류)을 쓰는 이유다.

**반론·회의적 시각.** 실전 악용은 10/22 기준 보고 없음(The Hacker News). Imperva 등은 수정되지 않은 Node 24.22.0에서 같은 디코더 코드를 익스플로잇했다고 한다. Python 쪽은 Aikido가 메모리 손상·코드 실행까지 가지 않고 "1.2.0은 조작 스트림에 계속 '입력 더 필요'를 내고 1.2.1은 거부한다"만 확인했다 — Python 확장에서 RCE가 가능한지는 **미입증**. Aikido 글 안에서도 공개일이 10/21(요약)과 10/22(타임라인)로 갈린다. 10/24 노트의 PHP처럼, CVSS 9.2가 *내 실행 환경*에서 그대로 성립하는지는 따로 따져야 한다 — 다만 이번엔 영향 범위가 너무 넓어 "일단 올린다"가 맞는 쪽이다.

### 3. Dessa — 텍스트를 한 글자도 거치지 않는 음성 대화 모델

**무슨 일인가.** Block(Square 모회사)의 소규모 AI 연구팀 — 토론토 스타트업 Dessa 출신 — 이 full-duplex 음성 모델 Dessa를 리서치 프리뷰로 공개했다. 오디오가 들어가고 오디오가 나오는 speech-to-speech이고, **사전학습 모델·텍스트 데이터 없이 사람 대화 음성만으로 처음부터** 학습했다고 한다. 학습은 NVIDIA GB200 NVL72 한 대, 추론은 실시간보다 빠르고 MacBook Pro M4 Max 이상에서 로컬 구동.

**배경 — 왜 이게 문제였나.** 지금의 음성 비서는 거의 전부 **STT → LLM → TTS** 파이프라인이다. 이 구조의 비용은 둘이다.

1. **정보 손실.** 중간이 텍스트라서 웃음·한숨·비꼼·목소리 떨림이 글자로 바뀌며 사라진다. Block은 이걸 안전 문제로도 본다 — 심한 통증을 겪는 사람의 목소리를 음성 AI가 알아채지 못하는 사례를 들었다.
2. **턴제 지연.** 사용자가 말을 끝내야(끝점 검출) STT가 확정되고, 그다음에야 LLM이 시작한다.

**어떻게 동작하나(공개된 범위).** full-duplex — 듣기와 말하기를 동시에 한다. 끼어들 때와 "맞아요" 같은 맞장구(backchannel)를 넣을 때를 실제 대화에서 배웠다고 한다. 그 이상(파라미터 수, 오디오 토크나이저, 아키텍처)은 **공개되지 않았다**. 기술 보고서·벤치마크도 없다.

**가장 큰 주장 — "LLM보다 수백 배 적은 단어로 언어를 배웠다."** 사실이라면 "언어 능력에 필요한 데이터량" 감각을 흔드는 이야기다. Block은 음성이 텍스트보다 *배우기 어렵다*고도 주장한다(톤·타이밍·감정 변동, 단어당 바이트가 훨씬 많음). 하지만 **수치도 방법론도 없다.** "단어 수"를 음성 데이터에서 어떻게 셌는지부터 불명이다.

**실무에 무슨 의미인가.** 어제 짧게 본 Heartbeat Thinking(파이프라인은 두고 *듣는 동안* 미리 추론·툴 호출)과 나란히 놓으면, 음성 에이전트 지연 문제를 **구조를 바꾸는 쪽**(Dessa)과 **스케줄링을 바꾸는 쪽**(Heartbeat) 양쪽에서 동시에 두드리고 있다. 백엔드 관점에서는 하나가 더 있다 — 텍스트 중간층이 없으면 **로그·감사·필터링의 기준점도 사라진다.** STT 결과 텍스트에 걸던 금칙어 필터, 대화 기록 저장, 개인정보 마스킹이 전부 "오디오에서 직접" 해야 하는 일이 된다. 오늘 흐름의 셋째 축(중간 가공층 걷어내기)의 반대 비용이다.

**반론·회의적 시각.** 데모는 큐레이션 샘플이고 "세계 최초"에도 스스로 "우리가 아는 한"을 붙였다. 현재는 소수 AI 안전 연구자에게만 열려 있고 "출시 링크는 곧". 오픈소스 여부 언급 없음. 비교 데모에 쓴 GPT-Live-1은 제3자 모델이고 그 개발사와 무관하다는 단서가 페이지에 있다. 텍스트를 안 거친다는 것은 장점이자 **사실 정확성의 약점**일 수 있다 — 텍스트 LLM이 가진 방대한 지식을 음성만으로 배운 모델이 얼마나 가졌는지는 아무 수치도 없다.

### 4. 분산 SQLite 12년 — "도구를 고르기 전에 질문을 고르라"

**무슨 일인가.** 2014년 rqlite(SQLite 앞에 Raft 로그를 두고 모든 쓰기를 클러스터에 복제)를 만든 Philip O'Toole의 회고(HN 226점). 본인은 Raft+SQLite를 결합한 첫 오픈소스로 본다.

**핵심 — 설계 공간의 세 꼭지점, 그리고 등장 순서.**

| 꼭지점 | 대표 | 작성자 | 일관성 | 클러스터 | 대가 |
| --- | --- | --- | --- | --- | --- |
| 합의 | rqlite, dqlite, SQLite Cloud | 리더 1 | 강함(CP) | 있음 | 과반이 살아 있어야 쓰기 가능, 소수 파티션은 쓰기 거부 |
| 스트리밍 | Litestream | 1 | — | 없음 | 장비가 죽으면 복구될 때까지 서비스 불가 |
| 병합 | cr-sqlite(CRDT) | 다수 | 최종 일관성(AP) | 없음 | 충돌을 병합 규칙에 맡김 |

**연표.** 2014 rqlite(goraft → 2016 HashiCorp Raft) · 같은 무렵 Expensify의 Paxos 계열 Bedrock(2016 공개), Erlang의 ActorDB · 2017 Canonical dqlite(LXD·MicroK8s의 etcd 대체, Go → C로 재작성, 자체 Raft) · 2021 초 Litestream(WAL을 S3로, 합의 없음) · 2022 Fly.io LiteFS(파일시스템 수준 복제, Consul 리스), cr-sqlite, libSQL 포크(SQLite가 외부 기여를 안 받아서), SQLite Cloud, Cloudflare D1 · 이후 Durable Objects 안의 SQLite, 2026 Supabase가 Turso 인수. 저자의 관찰: "복제된 SQLite는 누가 팔기까지 8년간 오픈소스였다 — 인프라 아이디어의 흔한 운명."

**저자의 요지(브리핑이 옮긴 문장).** "장비가 죽으면?"과 "복구를 기다릴 수 없으면?"은 **다른 요구사항**인데 사람들이 같은 것으로 착각해 논쟁한다. 앞의 질문엔 Litestream(싸게 복구)이, 뒤의 질문엔 rqlite(합의로 가용성)가 답이다. 여러 작성자가 오프라인에서도 써야 한다면 셋째 꼭지점이다.

**실무에 무슨 의미인가 — 이 노트의 번역.** 이 세 질문은 운영 용어로 바꾸면 **RPO**(얼마나 잃어도 되나)와 **RTO**(얼마나 오래 멈춰도 되나)와 **쓰기 가용성**(파티션 중에도 써야 하나)이다(노트의 해석, 원문 용어 아님). 합의는 RPO≈0·RTO 짧음, 스트리밍은 RPO 수 초·RTO 수 분(복원 시간), 병합은 파티션 중 쓰기 가용성을 산다. 결정 로그를 쓸 때 "왜 MySQL 복제 대신 X를 썼나"를 이 세 축으로 적으면 면접 답이 된다. Spring 쪽으로는 10/23 노트의 샤딩(AbstractRoutingDataSource로 master/slave 라우팅)과 이어진다 — 읽기 복제본은 "스트리밍" 꼭지점에 가깝고, 복제 지연 동안 읽은 값이 낡을 수 있다는 대가도 같다.

**반론·회의적 시각.** 회고는 rqlite 저자의 시선이라 합의 꼭지점에 우호적이다. 원문은 rqlite가 **SQL 문장을 복제하는지 페이지를 복제하는지**, `RANDOM()`·`datetime('now')` 같은 비결정 함수를 어떻게 다루는지 다루지 않는다 — 문장 복제 방식의 고전적 함정인데 이 글만으로는 확인 불가(MySQL의 statement 기반 vs row 기반 binlog 논쟁과 같은 문제). 댓글 하나는 자기 시스템이 분산 트랜잭션을 "분산 begin + 로컬 트랜잭션 한 배치 커밋" 두 명령으로 줄였다고 했다.

> 원문: [Philip O'Toole — Twelve years of distributed SQLite](https://philipotoole.com/twelve-years-of-distributed-sqlite/) · [HN (226점)](https://news.ycombinator.com/item?id=50217500)

### 5. Meta Expert — 층마다 따로 두던 전문가를 한 풀로 (요약, 구조는 AI 심층)

**무슨 일인가.** 칭화대·상하이 AI Lab(Hua 외, arXiv 2610.27598, HF ▲25). 지금의 MoE는 층마다 자기 전용 전문가(Local Expert)를 두는데, 서로 다른 층의 전문가가 비슷한 지식을 중복 저장한다. **여러 층이 공유하는 전문가 풀(Meta Expert)**을 두면 활성 수·전문가 크기를 고정한 채 바닐라 MoE와 같은 손실을 **전문가 70~80%(파라미터 75~90%)**로 낸다. 절감 폭은 모델이 깊고 클수록 커진다.

**어떻게(요지).** 공유 풀 하나 + 공유 라우터 하나를 모든 층이 부른다. 최종 구성은 층당 활성 8개 중 4개는 공유 풀에서, 4개는 층 전용에서(전체 전문가의 75%를 공유 풀로) + **첫 2층·마지막 2층은 전용 전문가만**(F2L2) + 공유 풀을 2개 하위 풀로 나눠 번갈아 접근(Loop2). 이론 쪽 주장: 층 전용 MoE에서는 깊은 층의 신호가 얕은 층에 *학습 중 기울기로만* 닿지만, 공유 풀에서는 같은 파라미터를 모든 층이 읽고 쓰므로 **한 번의 forward 안에서 얕은 층↔깊은 층이 양방향으로 서로의 내용에 닿는다** — 저자들은 이걸 "활성 수준의 역방향 잔차 연결"이라 부른다.

**실무에 무슨 의미인가.** MoE 서빙의 병목은 연산이 아니라 **저장과 적재**다(AI 심층 「MoE 전문가 오프로딩」 — 다음 토큰이 고를 전문가를 모르니 전부 들고 있어야 함). 전문가 수가 20~30% 줄면 그 메모리가 줄고, 공유 전문가는 모든 층이 부르므로 캐시 적중률에도 유리할 수 있다(후자는 노트의 추론, 논문 미측정). 오늘의 IQuest-Q1(320B/활성 15B)처럼 "총량은 크고 활성은 작은" 설계가 늘수록 맞물린다.

**반론.** 하류 평가는 6B-A1.6B·200B 토큰 규모 하나이고, 표를 보면 **모든 변형이 모든 벤치에서 이기지는 않는다**(MR75+F2L2는 MMLU 0.3928로 바닐라 0.4087보다 낮음). 공유 풀만 쓰면 학습이 불안정할 수 있어 75%로 타협했다. 자세한 것은 [[AI - 층간 전문가 공유]].

## 더 알아볼 것

- [ ] **내 환경의 Brotli 노출 지도 그리기.** 수집기·스크립트용 Python 환경과 Docker 이미지에서 `pip show Brotli brotlicffi`와 `pipdeptree -r -p Brotli`를 돌려 누가 끌고 왔는지 적고, requests가 `Accept-Encoding: br`을 실제로 보내는지 `httpbin.org/headers`로 확인한다. 그다음 Java 쪽 — OkHttp의 Brotli 인터셉터나 `org.brotli:dec`(Java 포트), `brotli4j`(네이티브 바인딩)가 의존성 트리에 있는지 `./gradlew dependencies | grep -i brotli`로 보고, 그것들이 이번 CVE 범위인지 스스로 판단 근거를 찾아본다.
- [ ] **"두 뜻을 지는 반환값" 찾기.** 내 WMS 코드에서 `boolean`이나 `null`이 서로 다른 실패(없음 / 권한 없음 / 일시 오류)를 한꺼번에 뜻하는 메서드를 하나 찾아, sealed interface 결과 타입(또는 예외 분리)으로 바꾸면 호출부가 어떻게 달라지는지 적어 본다.
- [ ] **Kimi 가중치 공개(11/4) 후 확인할 것 정리.** 라이선스(상업 이용·재배포), 실제 파라미터 수와 활성 파라미터, 추론 제공업체 가격 — 이 셋을 11월 첫 주에 직접 찾아 "API로 Opus 5.5 쓰기 vs 제공업체의 K3.1 Pro" 비용을 내 사용량 기준으로 계산한다. Terminal-Bench 0.7점 차가 내 작업에서 체감되는지는 같은 과제 세 개로 비교.
- [ ] **세 질문으로 결정 로그 쓰기.** WMS DB 구성(단일 MySQL? 읽기 복제본?)을 "장비가 죽으면 얼마나 잃어도 되나(RPO) / 얼마나 멈춰도 되나(RTO) / 파티션 중에도 써야 하나"로 한 표에 정리하고, rqlite·Litestream·cr-sqlite 각각이 어느 칸을 사는지 옆에 적는다. 문장 복제 vs 행 복제(MySQL binlog `STATEMENT`/`ROW`)에서 `NOW()`·`UUID()`가 어떻게 달라지는지도 확인.
- [ ] **Dessa식 구조의 백엔드 비용 생각해 보기.** 텍스트 중간층이 없는 음성 에이전트를 서비스에 붙인다면 대화 기록 저장·금칙어 필터·개인정보 마스킹을 어디서 어떻게 할지, STT 파이프라인일 때와 비교해 세 줄로 적는다.

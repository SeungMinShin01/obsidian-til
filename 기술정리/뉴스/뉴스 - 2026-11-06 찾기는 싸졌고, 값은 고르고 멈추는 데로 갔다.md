## 오늘의 흐름

먼저 겹치는 것. 오늘(11/6) 브리핑의 PHP2Shell「40년 기술부채」, Anthropic FlashProve, Go `encoding/json/v2`, Caper("Shall We Approve?"), Binance 가짜 면접 사고, Route Anything, Ripple-65B·Hy4는 **어제(11/5) 노트에서 깊게 봤다**. Kimi K3.1 Pro는 10/25부터 여러 번, 가중치 공개는 11/5에 짚었다. 가중치 공간 프로그래밍과 Willison 재현·반론(11/3~4), uv.lock(11/2), ChatGPT 계정 탈취(11/2~4), worktrunk·agent-desktop·auto-ontology·mattpocock/skills(10월 말~11/4)도 재등장이다. 오늘 새것 — **OpenAI의 리눅스 커널 자동 익스플로잇 파이프라인, "Length Is Cheap" 논문, CRaC로 JVM 부팅을 없앤 사례, Thoughtworks Technology Radar Vol 35, LoCo(Think Less, Locally)** — 를 깊게 보고, "Length Is Cheap"의 원리는 AI 심층 「AI - 길이가 아니라 경쟁이 만드는 컨텍스트 썩음」으로 뺐다.

첫 번째 축은 **찾기가 싸지자 병목이 고르기로 옮겨 갔다**는 것이다. OpenAI의 커널 파이프라인에서 후보를 *찾는* 단계는 12시간에 2,308건이었고, 공격 표면을 고르는 Scout 단계는 3,426달러에 불과했다. 돈과 시간은 그 뒤 — 재현(검증), 익스플로잇 가능성 판정, 패치, 사람의 검토 — 에 들었다. OpenAI 스스로 "발견이 아니라 무엇을 재현할 수 있고 어떤 보안 경계를 넘으며 무엇을 먼저 메인테이너에게 보낼지가 운영상 과제"라고 썼다. 10/18 노트(버그를 찾는 속도가 고치는 속도를 앞질렀다)와 어제의 PHP2Shell("찾는 데 2주, 고치는 데 4명이 2개월")에서 이어지는 흐름인데, 오늘은 **그 비대칭의 가격표가 단계별로** 나왔다.

두 번째 축은 **"많이 넣기"가 아니라 "무엇을 넣지 않을지"**다. "Length Is Cheap" 논문은 32K 토큰의 중립 텍스트가 검색 정확도를 거의 깎지 않는 반면, 질의한 키에 **다른 값을 주는 문장 하나**가 손실을 9~110배로 키운다고 보였다. Thoughtworks Radar는 같은 방향을 실무 언어로 말한다 — "점진적 컨텍스트 공개"를 Adopt로 올리고, "에이전트 지시문 비대화"·"순진한 컨텍스트 압축"·"외부 스킬 묶음 일괄 도입(인지적 항복)"을 Caution에 넣었다. 10/29 브리핑에서 AI 심층으로 판 「AI - 에이전트 메모리의 순가치」(원본을 그냥 잘라 검색하는 RAG보다 못한 메모리가 대부분)와 같은 결론이다: 컨텍스트의 예산은 토큰 수가 아니라 **질의와 경쟁하는 진술의 수**다.

세 번째 축은 **언제 멈추고 무엇을 반복하지 않을지**다. LoCo는 추론 모델에게 "충분히 확신한 상태에서는 마무리하라"를 국소적으로 가르쳐 수학에서 출력 길이를 41.7~45.4% 줄였다. OpenAI 파이프라인에서도 실패한 익스플로잇 시도(69건)는 건당 3,922달러로 성공(건당 약 360달러)의 10배 넘게 들었고, 저자들은 "한 시간 진전이 없으면 포기" 같은 조건 하나로 비용을 크게 줄였을 거라 썼다. CRaC 사례는 같은 원리를 JVM에 적용했다 — 부팅과 JIT 워밍업을 *빠르게* 하는 대신 **한 번만** 하고, 이후 파드는 워밍업이 끝난 프로세스를 복원한다(330초 → 2~3초).

네 번째, 작지만 반복해 볼 신호. OpenAI는 GPT-5.5 Cyber 때는 익스플로잇 기법 103개를 정리해 넣어 성공률이 76.2→88.9%로 올랐지만, GPT-5.6 Cyber에서는 그 무거운 오케스트레이션을 걷어낸 쪽이 오히려 나았다(다시 넣어도 +1.5%p). Radar는 Anthropic이 최신 모델용으로 Claude Code 시스템 프롬프트의 80% 이상을 걷어내고도 측정 가능한 품질 손실이 없었다고 인용한다. **모델이 세질 때마다 하네스·지시문은 감가상각된다** — 9/19 노트(성능 싸움의 무대가 모델 밖으로)의 반대 방향이 같은 주에 같이 나왔다. "하네스를 만들어라"와 "하네스를 정기적으로 걷어내라"가 동시에 맞는 셈이다.

## 깊게 본 것

### 1. OpenAI "A thousand fewer paths to root" — 커널 LPE 948개, 그리고 단계별 영수증

**무슨 일인가.** OpenAI가 11/4 공개한 연구 글. 리눅스 커널(master, 2026년 10월 중순)을 대상으로 취약점 발견 → 동적 재현 → 익스플로잇 가능성 판정 → 패치 생성 → 사람 검토의 5단계 파이프라인을 "출시 예정 사이버 모델"로 한 번 돌렸다. 원문 전체를 읽었다.

**깔때기(원문 기준).**

| 단계 | 결과 | API 비용 |
| --- | --- | --- |
| Scout(감사 대상 선정) | 5,034개 대상, 약 280만 줄(커널의 약 7%) | 3,426달러 |
| Analyst(정적 분석, 12시간) | 후보 2,308건(중복 제거 후) | 316,549달러 |

**배경 — 왜 지금.** 6월 "Patch the Planet"에서 GPT-5.5 Cyber가 LPE 24개를 만든 것을 파이프라인으로 확장했다. 7월 GPT-5.6 Sol 런은 LPE 166개(51만 3,690달러)였고, 석 달 동안 커널이 하드닝됐는데도 10월 새 모델은 5배 넘게 찾았다. 그래서 권고 1번이 **"모델이 세질 때마다 이미 감사한 코드를 다시 스캔하라"**다.

**기술적으로 어떻게 동작하나.** 핵심은 "정적 분석 결과를 믿지 않고 **실행으로 재현해야 통과**"시키는 구조다. Triage 에이전트는 PoC를 만들어 KASAN(커널 메모리 오류 탐지기)을 켠 VM에서 돌리고, 프로그램 출력과 시스템 콘솔을 보며 재현될 때까지 고친다. 재현 못 한 25% 대부분은 특권이 필요하거나, 경쟁 조건·특정 줄의 할당 실패 같은 까다로운 트리거로 시간 예산을 넘긴 것이고, 모델이 *불가능한 조건을 가정한* 오분석은 3.1%였다. 흥미로운 비용 관찰: 검증 단계에서는 진짜 양성과 거짓 양성을 검증하는 비용이 비슷했다 — 그래서 **거짓 양성을 앞단에서 걸러낼수록** 전체가 싸진다.

**가장 교육적인 대목 — "엉뚱한 0-day".** 초기 런에서 "root 셸을 땄다"로 성공 처리한 200건 중 20건은 **할당받은 취약점이 아니라 다른 0-day로** root를 땄다. 결과(root 셸)만 확인하는 검사는 통과했지만 경로가 틀렸다. OpenAI는 과제 제약을 조이고 "최종 익스플로잇이 배정된 취약점을 썼는지" 독립 검사를 추가했다. 교훈 문장: **결과뿐 아니라 결과에 이른 경로를 검증하라.** 10/20 노트("완료 보고는 증거가 아니다"), 10/28 노트("과제는 통과했고, 건강은 따로 재야 했다")와 정확히 같은 구조다.

**그 밖의 관찰.**
- 샘플 166개에서 **새로운 커널 익스플로잇 기법 10가지**(새 elastic object 2, 페이지 그루밍 2, 데이터 전용 기법 5, 임의 타입 혼동 1). 안전상 세부는 비공개.
- kernelCTF 환경: 112시간·약 3만 2,936달러로 유출 PoC 25·LPE 21개(비용의 83.7%가 발견 단계). 2026년 kernelCTF가 인정한 0-day LPE는 26개.
- 테스트 인프라도 뚫었다: 시스템 콜 진입 코드를 보던 에이전트가 이상한 크래시를 추적해 **QEMU TCG 취약점**(소스 없이)을 찾고 LPE까지 만들었다. 업스트림엔 고쳐졌지만 실험에 쓴 릴리스엔 없던 것.
- 패치: 처음엔 PoC는 막지만 코드가 과하고, 성능 트레이드오프·코딩 관례 이탈·변종 누락이 있었다. 지시와 반복으로 개선했고, 일부는 **사람 전문가가 쓴 패치의 문제**를 찾아 병합 전에 고쳤다.
- 메인테이너 속도: 스캔·분석 10일 동안 61개가 업스트림 패치, 43개 스테이징 패치, 299개 공개 논의 중. 그래서 "트리아지는 최신 코드에 다시 검증해 중복·낡은 보고를 피하라".

**실무에 무슨 의미인가.**
- **"패치 안 된 OS의 저권한 계정 = root"로 가정하라**는 OpenAI 권고는 백엔드 운영에 그대로 온다. 컨테이너는 같은 커널을 공유하므로 컨테이너 안 LPE는 곧 호스트 문제다. 격리는 Firecracker·gVisor 같은 더 강한 경계로(권고 원문). WMS 배포 때 "베이스 이미지·호스트 커널 업데이트 주기"를 체크리스트에 넣을 이유다.
- **결과-경로 검증**은 우리 테스트에도 적용된다. "200 OK가 왔다"만 보는 통합 테스트는 엉뚱한 경로(캐시, 기본값, 다른 핸들러)로 통과할 수 있다. 어제 노트의 Caper("실행해 보고 승인")와도 같은 원리.
- **포기 조건**을 둬라. 실패 시도 비용이 성공의 10배였다는 숫자는 재시도·타임아웃 설계(에이전트든 배치든)의 근거가 된다.

**반론·회의적 시각.**
- 전부 **OpenAI 자체 보고**이고 사용 모델은 미출시다. 948은 실제 익스플로잇 1,169개를 변종 분석으로 묶은 "고유 패치 수"라 집계 방식에 판단이 들어간다.
- "가치 1,890만~6,630만 달러, 비용의 16~55배"는 Pwn2Own·TyphoonPWN의 *역대 상금*을 948개 전부에 곱한 **가상 평가액**이다. 대회는 한 번에 몇 개만 사들이고, 중복·낡은 버그는 상금이 없다.
- kernelCTF 런은 최신 커널과 호환되지 않는 **SLAB_VIRTUAL 완화를 끄고** 돌렸다(원문 각주). "하드닝 커널에서도 21개"는 이 단서와 함께 읽어야 한다.
- "방어자용"이라는 틀과 별개로, 같은 글이 "공격자에게도 이미 수익이 난다"는 손익 계산서이기도 하다. 9/20 노트(에이전트가 시스템을 뚫기 시작했다)의 연장선에서, 이 글은 공격 비용의 **하한선 공개**로도 읽힌다.

### 2. "Length Is Cheap, Competition Is Not" — 컨텍스트 썩음은 길이가 아니라 경쟁

**무슨 일인가.** UCSD Yinuo Liu 단독 논문(arXiv 2611.04169). 키-값 검색 과제에서 길이와 증거 위치를 고정하고 **주변 내용만** 바꿨다. HF 초록과 arXiv 본문 전체를 읽었다.

**핵심 숫자.** Qwen2.5-1.5B, 32K 토큰에서 중앙값 손실: 중립 숫자 텍스트 0.004 nats, 같은 텍스트를 **마스킹**(위치는 유지) 1.20 nats, 증거와 같은 형식의 경쟁 문장 4.76 nats. 정확도는 중립 0.96~1.00, 경쟁 0.11~0.21. 손실은 **같은 키에 다른 값을 주는 문장(충돌)**에 몰린다 — 충돌 하나로 손실 9~110배, 형식만 같은 방해 문장의 개수는 분산의 0.3% 이하만 설명. 모델 내부에서는 "증거에 남은 어텐션 질량 a*"의 log(1/a*)가 손실 분산의 35~58%를, log 길이는 2~8%를 설명(126,473회 시행).

**왜 중요하나.** "긴 컨텍스트는 길어서 망가진다 → 아키텍처로 고쳐야 한다"는 통념(Du et al.의 마스킹 실험 근거)을 검색 과제에서는 뒤집는다. 마스킹은 학습 때 본 적 없는 **긴 위치 공백**을 만드는 별개의 개입이라 "길이의 비용"이 아니라는 것. 처방은 "자르지 말고 큐레이션하라" — 충돌하는 진술의 중복 제거·해소가 컨텍스트 단축보다 중요하다.

**실무 의미 · 반론.** RAG·에이전트 메모리에서 "버전이 다른 같은 사실"(예: 옛 설정값과 새 설정값, 개정 전후 문서)을 같이 넣는 것이 가장 해롭다는 예측이 된다. 반면 한계가 크다: 상관 분석(어텐션에 개입 안 함), 합성 과제 하나, 최대 3B, 4K 이상에서는 모든 맥락에 충돌이 있어 "형식만 같은 경쟁자"의 장문 효과는 측정 안 됨. 추론 과제(MMLU)에서는 공백 패딩이 실제로 해롭다 — 저자도 "검색은 경쟁이 지배, 추론에선 길이 효과 가능"으로 선을 긋는다. 세부 원리는 AI 심층 「AI - 길이가 아니라 경쟁이 만드는 컨텍스트 썩음」.

원문: [HF](https://huggingface.co/papers/2611.04169) · [arXiv](https://arxiv.org/abs/2611.04169) · [코드](https://github.com/yliusci/length-is-cheap)

### 3. JVM 준비 시간 330초 → 2~3초 — CRaC로 "부팅을 반복하지 않기"

**무슨 일인가.** Housing.com 엔지니어링 블로그(Medium) 글의 GeekNews 요약(11/4)을 읽었다. Medium 원문은 이번에 읽지 못했다.

**배경 — 왜 이게 문제였나.** JVM은 처음엔 바이트코드를 인터프리터로 돌리고, JIT가 자주 도는 코드를 관찰해 단계적으로 네이티브 코드로 컴파일한다(워밍업). 이 서비스는 파드 부팅 약 75초 + 워밍업 약 245초 ≈ 330초. 그 결과 ① 몇 개씩 순차 교체하는 배포가 약 20분 ② 워밍업 CPU 급증이 트래픽과 겹칠까 봐 **하루 종일 CPU 여유분**을 잡아 둠 ③ 공격·급증으로 파드가 죽으면 대체 파드도 5분 넘게 기다림(MTTR 악화) ④ 새 파드가 5분 뒤에야 쓸모 있으니 **오토스케일링이 무의미** → 새벽 3시에도 피크 용량 유지.

**기술적으로 어떻게 동작하나.** CRaC(Coordinated Restore at Checkpoint)는 리눅스 **CRIU**(사용자 공간 체크포인트/복원) 위의 OpenJDK 프로젝트다. 한 환경에서 JVM을 충분히 워밍업한 뒤 **프로세스 상태 전체**(힙, JIT 컴파일 결과, 인라인 캐시, GC 휴리스틱이 안정된 상태)를 디스크로 얼리고, 새 파드는 그 이미지를 복원한다. 검토 후 반려한 대안:
- **GraalVM 네이티브 이미지** — 시작은 거의 즉시지만 상당한 재작성 필요, 그리고 워밍업 후 JIT의 최대 처리량을 포기.
- **AppCDS** — 작고 안전하지만 클래스 로딩만 빨라짐. 비용의 대부분(JIT 단계 최적화·인라인 캐시·GC 안정화)은 그대로.

**결과.** 준비 330초 → 2~3초, 배포 약 20분 → 약 4분, 정상 상태 파드 CPU는 기존의 약 20%(→ 상시 예약 용량도 비슷한 비율로 축소 가능), 오토스케일링·비혼잡 시간 축소·**스팟 인스턴스** 활용이 현실화. 절감이 엔지니어링 비용을 회수했다고 한다.

**사고와 교훈.** 같은 날 여러 파드에서 복원이 `cpu.features` 비트맵 불일치로 실패하고 `Could not create the Java Virtual Machine`. 체크포인트 시점 JIT는 그 CPU가 지원하는 명령어 확장을 쓰는 기계어를 만들기 때문에, 복원 호스트에 그 명령어가 없으면 위험하다 — CRaC은 복원 전에 이를 검사해 **일부러 일찍 실패**한 것(안전장치가 정상 작동). 원인은 ① 같은 AWS 인스턴스 유형도 여러 하드웨어 세대에 걸칠 수 있고 ② 오토스케일러가 확장 시점에 유형·세대를 골랐기 때문. 대응: **CRaC 이전의 마지막 정상 이미지로 즉시 롤백** → 원인 규명 전에는 재투입 금지 → 체크포인트 생성 시 **기준 CPU 기능 집합을 환경 변수로 고정**(최대 성능 일부를 포기하고 이식성 확보). 문장 두 개가 남는다: "복구와 원인 분석을 분리하라", "노드 그룹 레이블은 하드웨어 보증이 아니다".

**실무에 무슨 의미인가.** Spring Boot 학습 관점에서 세 가지를 짚어 둔다(아래 두 항목은 오늘 원문이 아니라 배경지식이라 직접 확인 필요).
- Spring Boot 3.2부터 CRaC 연동(체크포인트 전에 열린 소켓·DB 커넥션 풀 등 자원을 닫고 복원 후 다시 여는 생명주기)이 들어갔다고 알고 있다 — 체크포인트는 **열린 파일·소켓을 들고 얼릴 수 없다**는 제약이 핵심.
- 보안상 체크포인트 이미지는 **힙 그대로**다. 메모리에 올라온 비밀(토큰, DB 비밀번호), 난수 생성기 상태가 이미지에 박혀 모든 파드가 공유할 수 있다. 이미지 접근 통제와 "복원 후 재초기화할 것" 목록이 필요하다.
- 워밍업 비용이 실제로 큰지부터 재야 한다. WMS 같은 3주 프로젝트 규모에선 과하다 — 다만 "준비 시간이 오토스케일링을 무의미하게 만든다"는 인과는 면접에서 설명할 가치가 있다.

**반론·회의적 시각.** 단일 회사 사례이고 수치는 자체 보고. 서비스가 Spring인지, JDK 배포판(CRaC 지원 빌드는 일부 배포판만)이 무엇인지 요약엔 없다. 2~3초는 *복원* 시간이고 체크포인트 생성 파이프라인(워밍업 트래픽을 어떻게 재현했나)의 비용·운영 부담은 요약에 없다. "Java 공부하기 싫어졌다"는 GeekNews 댓글처럼, JVM 생태계가 시작 시간 문제를 프로세스 스냅샷이라는 OS 수준 기법으로 우회하고 있다는 사실 자체가 반론이기도 하다.

### 5. LoCo(Think Less, Locally) — "언제 멈출지"를 상태 단위로 가르치기

**무슨 일인가.** 텐센트 등(Muyao Yuan 외, arXiv 2611.04814), HF 11/4 3위(▲71). HF 초록과 저자 코멘트를 읽었다(본문 미독).

**배경.** 추론 모델은 충분한 정보를 얻은 뒤에도 계속 "숙고"한다(overthinking). 기존 압축법은 대부분 **궤적 전체**에 "짧고 맞으면 보상"을 주는데, 그러면 모델은 *언제* 멈춰야 하는지가 아니라 *전반적으로 짧게*를 배운다.

**어떻게 동작하나.** ① 모델 자신의 추론 기록에서 과잉 숙고 후보 상태를 찾고 ② 그 지점까지의 **접두부를 얼린 뒤** ③ 같은 상태에서 더 짧은, 정답이 검증된 이어쓰기를 다시 생성하고 ④ "같은 상태에서의 긴 이어쓰기 vs 짧은 이어쓰기"를 선호 쌍으로 **DPO** 학습. 즉 비교 단위가 응답 전체가 아니라 "이 상태에서 계속할까, 마무리할까"다. 학습 데이터는 전부 자기 생성 수학 기록.

**결과(초록).** 수학 5개 벤치에서 출력 길이 41.7~45.4%↓, 코드 3개 벤치에서 23.4~36.3%↓, 정확도 유지 또는 향상, 코드 전 벤치에서 정확도-효율 AUC 최고 — 수학만으로 학습했는데 코드로 전이. 7B 모델 공개.

**실무 의미 · 반론.** 추론 토큰은 과금·지연 그 자체라 API 비용에 직접 닿는다. HF 댓글의 질문이 핵심 반론이다 — "검증 단계가 답을 결정하는 과제(답하기 전에 테스트를 돌려 보는 것)에서 너무 일찍 멈추지 않나?" 저자는 "확신 상태에 도달했을 때만 마무리를 고려하도록 쌍을 만든다, 줄어든 토큰의 대부분은 **중복 검증**"이라 답했지만, 검증이 결정적인 과제에서의 측정은 아직 없다. Vault의 AI 심층 「AI - 추론 길이 압축」에서 다룬 궤적 단위 방법들과 비교해 읽을 것.

원문: [HF](https://huggingface.co/papers/2611.04814) · [arXiv](https://arxiv.org/abs/2611.04814) · [모델](https://huggingface.co/MuyaoYuan/LoCo-7B)

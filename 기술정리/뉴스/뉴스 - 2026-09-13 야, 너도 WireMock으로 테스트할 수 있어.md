## 배경

글은 셀러시스템팀이 외부 API(FeignClient)를 호출하는 로직의 통합 테스트를 쓸 때 세 가지 방법을 써 봤고 전부 불편했다고 설명한다. ① 베타 환경 API를 직접 호출하면 타 시스템에 부하를 주고, 남이 데이터를 바꾸거나 베타가 죽으면 테스트가 깨지며, Read Timeout이나 장애 응답 같은 비정상 케이스는 아예 만들 수가 없다. ② Postman mock 서버는 이 문제를 거의 해소했지만 무료 호출량 제한을 넘기면 그 뒤 테스트가 전부 실패한다. ③ `@MockBean`으로 FeignClient를 갈아끼우면 FeignClient 자체(예: 404일 때 null을 돌려주는지)는 검증할 수 없고 그 뒤 로직만 검증되며, 테스트마다 `@MockBean` 조합이 다르면 Spring 컨텍스트를 매번 새로 띄워 테스트 시간이 기하급수적으로 늘어난다. 이 세 불편함을 한 번에 없애려고 WireMock을 도입했다는 것이 글의 출발점이다.

## 핵심

- WireMock은 "의존하는 API를 mocking해 주는 도구". 실행 방식은 Docker/Standalone 서버와 JUnit 실행 시에만 코드 안에서 띄우는 방식 두 가지인데, 테스트 시점에만 필요하고 Spring Cloud가 래퍼를 제공하므로 후자를 골랐다.
- 의존성은 `spring-cloud-contract-wiremock`. 여러 client 모듈에서 재사용하려고 `java-test-fixtures` 플러그인을 붙여 client-core 모듈의 `testFixturesImplementation`으로 넣었다.
- 공통 부모 `WireMockSupport`(abstract)에 `@AutoConfigureWireMock(port = 0, stubs = "classpath:mappings")` + `@SpringBootTest(RANDOM_PORT)`. `port = 0`은 랜덤 포트, `stubs`는 stub JSON 위치 — 기본값이 `src/test/resources/mappings`라 testFixtures에 두면 안 잡히므로 classpath로 명시했다.
- test 프로파일 yml에서 client URL을 `http://localhost:${wiremock.server.port}`로 바꾸면 랜덤 포트가 자동 주입된다.
- stubs 폴더가 비어 있으면 `FileNotFoundException: class path resource [mappings/]`가 나므로 stub JSON을 하나 이상 넣어야 한다. 파일 구조는 `{client-name}/{api-path}/{id}_{case}.json` 식으로 디렉터리로 나누는 편.
- Read Timeout 검증: readTimeout 3000ms인 client에 대해 stub의 response에 `fixedDelayMilliseconds: 3500`을 주고 `SocketTimeoutException`·"Read timed out"을 `catchThrowable`로 검증한다. 정확히 3000으로 잡으면 타임아웃이 안 날 수 있어 여유를 둔다.
- Default 응답: 특이 케이스만 stub으로 쓰고 나머지는 `priority: 9999`(최하) + `urlPathPattern: "/anything/([0-9]+)"` 정규식으로 기본 응답을 내린다. `urlPattern`은 쿼리 파라미터까지 비교하고 `urlPathPattern`은 path만 비교한다 — 팀은 후자를 쓰고 쿼리는 `queryParameters` 필드로 따로 매칭.
- Body로 구분할 때는 `bodyPatterns[].equalToJson`에 JsonUnit placeholder(`${json-unit.any-string}`, `${json-unit.regex}[A-Z]+` 등)를 쓴다.
- 서로 다른 API인데 path가 같으면 WireMock 인스턴스가 하나라 구분이 안 된다. 정석은 포트를 달리해 여러 대 띄우는 것인데 방법을 못 찾았고, `@Profile("test")`인 Feign `RequestInterceptor`로 `type` 헤더를 붙여 stub의 `headers.type.equalTo`로 구분하는 우회를 썼다.
- 글은 JSON stub 방식의 한계도 인정한다 — 테스트 코드만 보면 id 하나 바뀌었는데 왜 결과가 다른지 알 수 없고 mappings 파일을 같이 찾아야 한다. 코드 안에서 stub을 선언하는 방식이 가독성은 낫지만, 베타·Postman 응답을 그대로 붙여넣기 쉬워서 JSON을 택했다고 설명한다.

## 내 프로젝트와의 연결

수집기는 사람인 API를 호출하는 파이프라인이라 "외부 API가 느리거나 4xx/5xx를 줄 때 재시도·건너뛰기가 제대로 도는가"가 정확히 이 글의 문제다 — 다만 Python이라 WireMock 대신 `responses`/`respx` 같은 라이브러리나 로컬 HTTP stub 서버가 같은 자리에 온다. 구조적으로 가져올 것은 "정상 1건 + 타임아웃 1건 + 기본 응답(priority 최하)"이라는 stub 구성 패턴이다. WMS(Spring Boot)에서는 외부 연동(택배사·바코드·결제 등)을 FeignClient/RestClient로 붙이는 순간 이 글 그대로 적용 가능하고, 특히 `${wiremock.server.port}` 주입과 testFixtures 공유 방식은 멀티모듈 구성을 잡을 때 참고할 만하다. `@MockBean` 조합이 다르면 컨텍스트가 재생성돼 테스트가 느려진다는 지적은 WMS 통합 테스트를 쌓을 때 미리 피해야 할 함정이다.

## 오늘 정리할 것

1. WMS 프로젝트에 `spring-cloud-contract-wiremock` 의존성을 넣고 `@AutoConfigureWireMock(port = 0)` 부모 클래스 하나 만들어 빈 mappings 에러(`FileNotFoundException`)를 직접 재현해 본다.
2. readTimeout 3000ms + `fixedDelayMilliseconds` 3500 stub으로 `SocketTimeoutException`이 실제로 나는지, 3000으로 맞추면 안 나는지 확인한다.
3. `urlPattern` vs `urlPathPattern` 차이를 쿼리 파라미터 붙인 요청으로 직접 비교해 본다.
4. 수집기(Python) 쪽에서 같은 역할을 하는 라이브러리(`responses`, `respx`, `pytest-httpserver`) 중 하나를 골라 "타임아웃 stub" 하나만 만들어 재시도 로직이 도는지 본다.

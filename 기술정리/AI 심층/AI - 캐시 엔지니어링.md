# AI - 캐시 엔지니어링

> 상위: [[AI 심층 정리 인덱스]]

> 계기: *Cache Engineering for Agents* — Tianyu Fu 외(칭화대 NICS-EFC, 교신 Yu Wang), arXiv 2610.28577 (2026-10-20), HF ▲111~113 (2026-10-23 브리핑)

## 한 줄 정의

긴 호흡 에이전트의 컨텍스트를 줄일 때 **텍스트 궤적을 고치지 않고, 모델이 볼 KV 캐시 항목을 직접 빼고(`drop`) 남은 키의 위치를 다시 매기는(`repos`) 방식** — 남긴 캐시를 재계산 없이 그대로 쓰므로, 요약·삭제가 부르는 재-prefill 비용 없이 조금씩 계속 줄일 수 있다. 이를 위해 "같은 토큰 접두사 = 같은 캐시"라는 서빙 엔진의 전제를 깨고, **연산 이력까지 캐시 키로 쓰는** 서빙 시스템 AKV를 함께 만들었다.

## 왜 이게 문제였나 — 컨텍스트 엔지니어링의 딜레마

**비용의 주인은 캐시 읽기다.** 에이전트는 매 턴 시스템 프롬프트·도구 정의·지금까지의 대화를 다시 보낸다. 프롬프트 캐싱 덕에 앞부분을 다시 *계산*하지는 않지만, 매 디코드 스텝마다 쌓인 KV를 GPU 메모리에서 *읽어야* 한다. 논문 측정으로 **KV 캐시 읽기가 API 비용의 82.4%**다. 길이가 모델이 안정적으로 다루는 범위를 넘으면 정확도도 떨어진다.

**그래서 다들 텍스트를 줄였다(컨텍스트 엔지니어링).** 오래된 메시지를 요약하거나 잘라낸다. 문제는 프롬프트 캐시가 **접두사가 글자 단위로 같을 때만** 먹는다는 점이다. 앞쪽을 고치면 그 뒤에 남긴 모든 것의 KV가 무효가 되어 **다시 prefill**해야 한다 — 일찍 고칠수록 다시 계산할 꼬리가 길다. 그래서 실제 하네스들(Pi, OpenAI 등)은 **임계값(예: 96K 토큰)까지 미뤘다가 한꺼번에 크게** 요약하고 최근 몇 라운드만 남긴다. 그 순간 중간 라운드의 쓸모 있는 정보가 날아간다.

논문의 동기 실험(GPT-OSS-120B, BrowseComp-Plus 앞 100과제 × 4회, 최대 100라운드)이 딜레마를 숫자로 보여 준다.

| 방식 | 결과 |
| --- | --- |
| 삭제형(최근 12라운드 도구 응답만 유지, 텍스트에서 삭제) | 비용이 **전체 컨텍스트의 1.85배** — 매번 접두사가 바뀌어 재-prefill |
| 요약형(48K 임계값) | 비용 약 7% 절감, **정확도 5%p 하락** |
| 오래된 도구 응답의 **캐시만** drop | 정확도↑·비용↓ 동시 |

첫 줄이 직관에 반한다 — "덜 보내는데 더 비싸다." 줄인 *양*보다 캐시를 깨뜨린 *위치*가 비용을 정한다.

## 어떻게 푸는가

### 세 가지 캐시 연산

비유: 지금까지 서빙 엔진에게 캐시는 **녹음 테이프**였다. 앞부분을 바꾸려면 그 뒤를 다시 녹음해야 한다. 캐시 엔지니어링은 테이프는 그대로 두고 **"이 구간은 이제 재생하지 마"라는 표시**와 **"남은 구간의 타임코드를 다시 매겨"라는 명령**을 추가한다.

- **`append`** — 평소의 캐시 추가. 새 토큰을 현재 활성 캐시를 보며 계산해 뒤에 붙인다. 위치 인덱스는 0부터 하나씩 증가.
- **`drop(P)`** — 선택한 토큰들의 KV를 **이후 어텐션에서 제외**한다. 남은 KV와 그 위치 인코딩, 텍스트 궤적은 그대로. 주의: drop은 다음 토큰의 위치 번호를 되돌리지 않는다.
- **`repos`** — 남은 키의 위치 인코딩을 논리 순서대로 0, 1, …, r−1로 **다시 매기고**, 다음 append가 r부터 시작하게 한다. RoPE(회전 위치 임베딩)에서는 키를 위치 p에서 q로 옮기는 것이 회전 행렬 곱 `K ← R(q)·R(p)⁻¹·K` 한 번이다. **값(V)은 그대로**, 은닉 상태 재계산 없음.

`repos`가 왜 필요한가: drop만 하면 캐시는 작아져도 위치 번호는 논리 길이를 따라 계속 커진다. 작은 캐시로도 **모델의 최대 위치에 도달**해 실행이 멈춘다. 그래서 위치 인덱스를 논리 인덱스·캐시 크기와 **분리**했다.

### 무엇을 버리나 — 도구 응답 순환 drop

어텐션을 재 보니(BCP 10개 궤적 평균) **오래된 토큰은 최근 것보다, 도구 응답은 같은 상대 위치의 어시스턴트 메시지(추론)보다** 덜 주목받았다. 그래서 기본 정책은 **"추론은 전부 남기고, 도구 응답은 최근 K=12개만 남기고 그 이전 것은 drop"**이다. 텍스트 요약처럼 임계값에서 한꺼번에 자르는 게 아니라 **매 라운드 조금씩** 굴러간다(rolling). 활성 컨텍스트는 추론이 쌓이는 만큼은 계속 자라지만 훨씬 느리게 자란다.

한 가지 미묘한 이점: 남긴 KV는 **drop된 토큰이 보이던 시점에 계산된 것**이라, 버린 도구 응답의 정보가 그 뒤 추론 토큰들의 KV에 **간접적으로 녹아 있다**(논문 그림 1의 "중첩된 색 블록"). 텍스트를 지우고 다시 prefill하면 이 흔적까지 사라진다. 삭제형이 비싸면서도 나을 게 없는 이유 중 하나다.

### 서빙의 난제 — 이력 의존성

여기서 서빙 엔진의 전제가 깨진다. 보통 KV 캐싱에서는 **토큰 접두사가 캐시 상태를 완전히 결정**한다(vLLM PagedAttention, SGLang RadixAttention의 접두사 공유가 이 전제 위에 있다). 캐시 엔지니어링에서는 아니다. 논문 예시:

- ① A, B, C를 붙인 뒤 A를 drop
- ② A, B를 붙이고 A를 drop한 뒤 C를 붙임
- ③ B만으로 시작해 C를 붙임

셋 다 결과적으로 B와 C만 남는다. 그런데 **C의 KV는 셋이 전부 다르다** — ①의 C는 A를 보며 계산됐고, ②의 C는 A를 못 봤지만 "A를 본 B"를 봤고, ③의 C는 "아무것도 안 본 B"를 봤다. 토큰과 남은 위치가 같아도 **연산 순서**가 다르면 다음 토큰 확률이 다르다. 접두사 매칭만으로 재사용하면 **틀린 캐시를 재사용**한다.

### AKV — 상태 없는 인터페이스, 상태 있는 서빙

- **인터페이스.** 기존 API에 `cache` 필드 하나를 더한다. `messages`는 평소처럼 전체 텍스트 궤적(전부 암묵적 append), `cache.drop`은 "몇 번 메시지 *뒤에서* 몇 번 메시지들의 캐시를 버린다", `cache.reposition`은 "몇 번 메시지 뒤에서 재배치". 클라이언트는 매 턴 메시지와 연산 이력을 함께 늘려 보낼 뿐, **서버에 어떤 KV가 남아 있는지 추적할 필요가 없다.** 요청 하나가 자기가 쓰는 캐시 상태를 완전히 기술하므로, 서버가 메모리 압박으로 캐시를 내쫓았어도 처음부터 복원할 수 있다. 그리고 한 요청의 drop이 **같은 접두사 캐시를 공유하는 다른 요청**의 출력 분포를 바꾸면 안 된다(요청 격리).
- **확장 radix tree.** 접두사 트리에 **drop 노드(Δ)**와 **repos 노드(R)**를 끼워 넣어 "토큰 + 연산 이력"을 함께 키로 쓴다. 위 ①과 ②는 A–B까지 가지를 공유하다가 drop 시점에서 갈라진다. 재배치 후에는 같은 토큰이라도 **위치 버전**별로 노드가 다르다. 정확 매칭(토큰·위치·연산 전부 같음)이 실패하면 **재트리거 매칭**(위치만 무시하고 연산 기록은 유지)으로 찾아 키만 회전해 재사용한다 — 연산 기록이 갈라지는 지점은 넘지 않는다.
- **drop 인지 축출.** 어떤 요청이든 아직 계산·복원에 쓰는 캐시는 지우지 않는다. 지울 수 있는 것 중에서는 **drop된 캐시를 완료된 요청의 캐시보다 먼저** 지운다(후자는 다음 라운드에서 재사용될 가능성이 크니까). 물리 저장은 비우되 트리 노드는 빈 자리표시로 남겨 자손 접근을 유지.
- **segment-batch attention 복원.** 내쫓긴 상태를 연산 이력대로 재생하면 forward pass가 여러 번 필요하다. 대신 drop/repos 시점마다 쿼리를 **구간(segment)**으로 나누고, 각 구간이 "그 시점에 보이던 KV"만 보도록 페이지 목록을 다르게 줘서 **한 번의 forward pass**에서 같이 계산한다. 어텐션만 구간으로 나누고 FFN은 전체를 한 배치로 돌려 가중치 읽기 반복을 피한다.

## 결과

**설정.** 모델 셋: MiniMax-M2.7(230B/활성 10B), GPT-OSS-120B(활성 5.1B, high effort), MiroThinker-1.7-Mini(30B/활성 3B). 벤치마크 넷: BrowseComp-Plus(BCP), GAIA-Text(103과제), SWE-bench Verified, xbench-DeepSearch-2510. 기준선 둘(모두 Pi 하네스의 요약 프롬프트): **Standard**(모델별 높은 임계값 96K/192K에서 요약), **Text Engineering**(48K에서 요약). AKV는 도구 응답 최근 12개 유지, repos 임계값은 Standard의 요약 임계값과 같게. 비용은 공개 단가(Groq·MiniMax 등)로 계산한 **API 환산 비용**이고, repos한 토큰은 캐시 히트 단가로 **일부러 과대 청구**했다.

**과제 성능(평균).**

| 모델 | Standard 점수/비용(¢) | Text Eng. | AKV |
| --- | --- | --- | --- |
| MiniMax-M2.7 | 52.4 / 5.0 | 52.8 / 5.7 | **53.7 / 4.4** |
| GPT-OSS-120B | 51.0 / 11.2 | 48.3 / 10.2 | **53.1 / 7.3** |
| MiroThinker-1.7-Mini | 44.1 / 20.4 | 37.1 / 18.1 | **45.8 / 14.8** |

세 모델 × 네 벤치마크 평균 비용이 Standard 대비 **−27.7%**, Text Engineering 대비 −21.9%. 점수는 Standard 대비 +1.3~2.1점(초록의 "+1.7"은 평균). 개별 칸에서는 AKV가 지는 곳도 있다 — MiniMax SWE-Verified 74.4 < Standard 75.2, GPT-OSS xbench 37.5 < 38.5.

**정확도가 오른 이유.** BCP 길이별로 보면 48K 미만에선 셋이 비슷하다. **Text Engineering은 48~96K 구간에서, Standard는 96K 초과 구간에서** 가장 낮다 — 각자의 요약 임계값 직후다. 한꺼번에 자르는 순간의 정보 손실이라는 해석과 맞는다.

**비용이 준 이유(부록 A.4.2).** Standard 대비로는 이후 요청이 읽는 캐시 이력이 줄어 **캐시 읽기 비용 약 −17%**, Text Engineering 대비로는 요약이 부르는 재-prefill이 없어 **캐시 미스 입력 비용 약 −48%**.

**서빙(GPT-OSS-120B, A800 8장, prefill/decode 분리, SGLang v0.5.20 기반).** 각자 최대 처리량 지점(AKV 동시성 14, Standard 12)끼리 비교해 평균 요청 지연 1.36배·**P95 1.51배** 빠르고, 입력 처리량 1.53배·출력 1.18배. 차이는 동시성이 높을수록 벌어진다 — 동시성 16에서 Standard의 P95 지연은 **229.9초**(캐시 압박으로 재-prefill이 폭주), AKV는 30.6초. 디코드 스텝 분해로는 full-attention 시간 −59.8%, 디코드 스텝 전체 −16.0%.

**절제 실험(GPT-OSS-120B, 앞 100과제).**

| 전략 | repos | BCP 점수/비용 | SWE 점수/비용 |
| --- | --- | --- | --- |
| Standard | ✗ | 56.0 / 13.5 | 41.0 / 19.1 |
| 도구 drop | ✗ | 55.0 / 7.1 | 41.0 / 9.4 |
| 추론 drop | ✓ | 56.5 / 8.2 | 36.5 / 14.2 |
| 둘 다 drop | ✓ | 56.5 / 8.7 | 34.5 / 7.8 |
| **도구 drop** | ✓ | **62.0** / 10.9 | 41.0 / 9.5 |

두 가지가 읽힌다. ① repos 없이 drop만 하면 싸지지만 BCP가 위치 한계에 걸려 **실행이 멈춘다**(55.0 → repos 추가로 62.0). ② **추론 캐시를 버리면 SWE가 무너진다**(41.0 → 36.5, 34.5). 도구 출력은 버려도 되지만 "내가 왜 이렇게 판단했나"는 버리면 안 된다.

**정책을 사람이 아닌 쪽이 고르면.**

- **재귀적 자기개선(RSI).** MiniMax-M2.7이 BCP 20과제로 정책을 다듬고 **보지 않은 100과제**로 평가. 3·6번째 반복 정책이 Standard 대비 비용 −15.6%·−17.8%(정확도는 Standard 수준 유지). 초록의 "전문가 설계 대비 −7.1%"는 사람이 만든 K=12 정책 대비.
- **캐시를 도구로(CAT).** 에이전트에게 캐시 관리를 도구로 주고 언제 무엇을 버릴지 직접 정하게 하면 BCP 100과제에서 GPT-OSS-120B 61.0%(Standard 52.1, 비용 13.4 → 12.1¢), MiniMax-M2.7 64.0%(56.0, 단 비용은 5.4 → 5.9¢ — 턴을 더 돌아서).

**기존 하네스에 끼우면.** Pi 하네스에 AKV를 붙이니 BCP에서 GPT-OSS-120B·20B 모두 압축 없는 Pi 대비 +3%, 압축 있는 Pi 대비 +4%. 작은 모델(GPT-OSS-20B)은 평균 45.2%로 가장 높지만 비용 4.8¢는 Text Engineering(4.6¢)보다 약간 비싸다 — 저자는 작은 모델이 남긴 정보를 덜 잘 써서 캐시 수정에 더 민감하다고 해석한다.

## 기존 노트와의 관계 (본문 서술로만)

- **「KV 캐시 압축」(9/20, DeepSeek-V4.1-Flash 계기)**은 KV를 **모델 구조**에서 줄였다(층간 공유·FP4·SWA Replay). 캐시 엔지니어링은 구조는 그대로 두고 **어느 KV를 볼지**를 에이전트·하네스가 정한다. 둘은 곱해서 쓸 수 있는 직교 축이다. SWA Replay가 "영구 저장을 재계산으로 되사는" 교환이었다면, AKV의 segment-batch 복원은 "내쫓긴 상태를 한 번의 pass로 되사는" 같은 계열의 교환이다.
- **「객체 지향 컨텍스트 폴딩」(10/20)**은 *텍스트* 층에서 "대화 요약 대신 환경에 남은 결과물을 가리켜라"였다. 캐시 엔지니어링은 같은 문제(긴 궤적의 무엇을 남기나)를 *캐시* 층에서 푼다. 두 노트의 공통 결론: **도구 출력은 다시 구할 수 있으니 버려도 되고, 판단의 이유(추론)는 남겨라.**
- **「코딩 에이전트 하네스」**의 "규칙 기반 생략을 LLM 요약 앞에" 결론과도 맞는다 — 요약(LLM 호출 + 재-prefill)보다 규칙(최근 12개)이 싸고 덜 망가뜨린다.
- **「판단 신호와 개입 정책」(10/22)**과 겹쳐 읽으면, CAT에서 MiniMax가 점수는 올렸지만 *턴을 더 돌아* 비용이 오른 것은 "아끼는 도구를 쥐여 줬더니 행동이 바뀌어 다른 데서 비용이 났다"는 같은 패턴이다. 비용을 주 결과로 같이 봐야 한다.

## 실제로 쓸 수 있나

**지금 바로는 자기 서빙 환경에서만.** 상용 API(Anthropic·OpenAI 등)는 KV 캐시를 사용자가 drop하는 인터페이스를 주지 않는다 — 접두사 캐싱만 있다. AKV는 SGLang 포크라 **오픈 웨이트 모델을 직접 띄우는 경우**에 쓸 수 있다.

**API를 쓰는 입장에서 바로 가져갈 교훈은 오히려 기준선 쪽에 있다.**

- **캐시는 접두사가 글자 단위로 같을 때만 먹는다.** 시스템 프롬프트 맨 앞에 타임스탬프·요청 ID를 넣으면 매 호출이 캐시 미스다. **변하지 않는 것을 앞에, 변하는 것을 뒤에.** 도구 정의 순서도 고정한다.
- **요약은 "언제" 하느냐가 비용을 정한다.** 앞쪽을 고치면 뒤를 전부 다시 계산한다. 자주 조금씩 요약하면 오히려 비싸다(삭제형 1.85배). 요약할 거면 드물게, 그리고 그 직후 정확도 하락을 측정한다.
- **도구 출력을 처음부터 짧게.** API에서 drop을 못 하면, 도구가 긴 원문 대신 요약·핸들(파일 경로, ID)을 돌려주게 하는 것이 텍스트 층의 대응물이다.

**백엔드 개발자 관점의 번역.** 이 논문의 서빙 문제는 **캐시 키 설계** 문제다. "같은 토큰 → 같은 캐시"가 깨지자 키에 연산 이력을 넣어야 했다. Spring `@Cacheable`에서 결과에 영향을 주는 입력(사용자 권한, 로케일, 페이징 파라미터)을 key에 빠뜨리면 **다른 사람의 결과를 재사용**하는 버그가 나는 것과 정확히 같은 구조다. 그리고 "요청이 자기 상태를 완전히 기술하게 해서 서버가 언제든 복원 가능하게"는 **무상태 API + 재구성 가능한 캐시**라는 익숙한 설계다 — 캐시는 성능 최적화일 뿐 정확성의 근거가 되면 안 된다.

## 한계와 미검증 지점

- **저자가 적은 한계:** 정책 탐색은 아직 초기, 이 방식으로 **에이전트를 학습**시키는 것은 미래 과제, **선형 어텐션 모델**로의 확장 미지원.
- **비용은 API 환산이다.** 자체 GPU에서 돌린 실험을 공개 단가로 환산했다. 실제 상용 API에서 같은 절감이 나온다는 뜻이 아니다(애초에 그 API엔 drop이 없다). 서빙 실험도 A800·BF16(MXFP4 미지원) 한 구성이다.
- **기준선의 강도.** 두 기준선은 모두 *요약*형이고 임계값 고정이다. "도구 응답만 텍스트에서 마스킹하되 재-prefill을 배치로 모으는" 같은 더 강한 컨텍스트 엔지니어링(관련 연구로 언급된 편집 배치·prefill 겹치기 시스템)과의 직접 비교는 본문에 없다.
- **분산.** SWE-Verified에서 MiroThinker는 7.8 / 4.2 / 7.4처럼 점수 자체가 낮아 차이가 노이즈일 수 있다. 주 표에 반복 횟수·신뢰구간이 명시돼 있지 않다(동기 실험은 4회, 온라인 SWE는 3회에 ±1σ 음영).
- **유한 정밀도.** 재트리거 매칭의 정확성 논증은 "정확한 산술"을 가정하고, 키 회전의 반올림 오차는 비트 동일성을 보장하지 않는다고 저자가 직접 적었다. 영향 크기는 측정되지 않았다.
- **이 노트의 추론(원문 주장 아님): drop은 '잊기'가 아니다.** 남긴 KV에는 drop된 토큰의 정보가 섞여 있다(저자가 장점으로 든 성질). 뒤집으면, 도구 응답에 섞여 들어온 **프롬프트 인젝션을 drop해도 그 뒤 추론 토큰의 KV에 남은 영향은 지워지지 않는다.** 보안 목적의 "컨텍스트에서 제거"로 쓰면 안 되고, 그 용도에는 텍스트 삭제 + 재-prefill이 필요하다. 논문은 보안 측면을 다루지 않는다.
- **CAT의 비용 상승.** 에이전트가 캐시를 직접 관리하면 점수는 올랐지만 MiniMax는 비용이 올랐다 — 정책을 모델에게 맡기면 행동이 바뀐다. 장기적으로 이게 수렴하는지는 미확인.

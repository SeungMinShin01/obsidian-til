# AI - 같은 점수 뒤의 다른 작업 습관

> 상위: [[AI 심층 정리 인덱스]]

> [!info] 예습자료 — 무인 세션이 자동 생성, 사용자 미검증 · 계기: Badertdinov·Golubev(Nebius) 「Interpreting Coding Agents Through Their Behavioral Trajectories」(arXiv 2611.17440, NeurIPS 2026 IAB 워크숍), 11/17 브리핑

## 한 줄 정의

코딩 에이전트의 실행 기록(도구 호출)을 하네스와 무관한 공통 행동 어휘(탐색·검색·읽기·수정·테스트·작업 공간 확인)로 번역해 비교하면, **해결률이 같은 에이전트도 일하는 방식이 재현 가능하게 다르고**, 그 방식만으로 어떤 모델·스캐폴드·추론 노력 조합인지 거의 맞힐 수 있다 — 즉 해결률은 에이전트를 설명하는 숫자 하나일 뿐이다.

## 왜 이게 문제였나 — 기존 방식의 한계

SWE-bench류 벤치마크는 긴 상호작용 전체를 **"이슈를 고치고 테스트를 통과했나" 한 비트** 로 줄인다. 순위 매기기엔 좋지만 세 가지를 가린다.

1. **같은 점수, 다른 위험.** 코드를 많이 읽고 조금 고치는 에이전트와 거의 안 읽고 많이 고치는 에이전트가 같은 해결률을 받을 수 있다. 테스트가 빈약한 레거시 저장소에서는 후자가 훨씬 위험한데, 점수는 이걸 구분하지 못한다. 11/17 뉴스 노트의 redfirst(수정을 되돌려도 통과하는 테스트 14%)가 바로 "테스트 통과"라는 한 비트의 구멍이다
2. **비교 자체가 어렵다.** 하네스마다 도구 이름·명령 형식·로그 스키마가 다르다. Claude Code는 `Edit`·`Read` 같은 네이티브 도구를, 범용 bash 하네스는 `sed`·`cat << 'EOF'`·인라인 파이썬을 쓴다. 도구 이름으로 세면 "무엇을 했나"가 아니라 "어떤 문법으로 했나"를 세게 된다
3. **우연과 차이를 못 가른다.** 같은 이슈를 다시 돌려도 에이전트는 다르게 행동한다(관련 연구: 반복 실행의 큰 편차). 두 에이전트의 차이가 진짜 습관인지 실행마다의 잡음인지 판단할 기준선이 없었다

## 어떻게 푸는가

### 1단계 — 번역기: 도구 호출 하나를 네 칸짜리 카드로

규칙 기반(패턴 매칭) 파서가 각 도구 호출과 그 실행 결과를 짝지어 네 속성을 붙인다.

| 속성 | 값 |
| --- | --- |
| 주 동작 | 저장소 탐색·검색·파일 읽기·파일 수정·정식 테스트 실행·작업 공간 확인(`git diff`/`status`/`show`)·빌드·기타 등 10종 |
| 대상 파일 역할 | 일반 코드 / 테스트 파일(`tests/`, `test_*`, `conftest` 등 경로 휴리스틱) / 혼합 / 미확정 |
| 수정 종류 | 생성·편집·삭제·혼합 |
| 읽기 방식 | 파일 직접 읽기 vs 이어 읽기(뷰포트), 전체 vs 줄 범위(`sed -n`, `head`) |

비유하면 **여러 나라 말로 된 업무 일지를 하나의 공용 업무 코드표로 옮기는 것** 이다. "`sed -n '40,80p' a.py`"와 "`Read(a.py, offset=40)`"는 둘 다 '파일 읽기·줄 범위'가 된다. 규칙 기반이라 결정적(같은 입력 → 같은 출력)이고 다시 돌릴 수 있다.

**번역기는 믿을 만한가?** 사람 대신 여섯 개 최신 LLM(claude-opus-5, gpt-5.6-sol, gemini-3.7-flash, Kimi-K3, DeepSeek-V4-Flash, MiniMax-M3)에게 같은 500개 행동을 블라인드로 분류시켜 **6개 중 5개 이상 동의** 한 것만 기준 답으로 삼았다. 파서와의 일치율은 주 동작 82.4%, 읽기 방식 96.6%, 대상 파일 역할 77.0%, 수정 종류 68.8%. 그래서 저자들도 경로·수정 종류에 기대는 지표는 "진단용 근사치"로만 취급한다.

### 2단계 — 여섯 개의 작업 습관 지표

- **작업량**: 롤아웃당 시도한 도구 호출 수(실패·거부 포함)
- **탐색 비중**: 탐색·검색·읽기가 차지하는 비율
- **비테스트 코드 쓰기**: 실패 없이 끝난, 테스트가 아닌 파일 수정 횟수
- **정식 테스트 호출 수**
- **연속 반복 실패**: 같은 명령·같은 경로로 연달아 실패한 횟수(헛도는 정도)
- **비생산적 꼬리**: 마지막 생산적 행동(성공한 코드 수정 또는 통과한 테스트) 이후에 한 행동 수

### 3단계 — "진짜 차이인가"를 가르는 A/A 대조

핵심 설계는 **점수를 맞춘 쌍** 과 **자기 자신과의 비교** 다.

- **점수를 맞춘 쌍**: 같은 스캐폴드, 다른 모델, 공유 과제 50개 이상에서 해결률 차이 1%p 이하인 구성 쌍 60개(중앙값 0.40%p)
- **A/A 대조(split-half null)**: 한 구성의 반복 실행 5회 중 4회를 무작위로 2:2로 나눠, **같은 구성의 두 절반** 이 얼마나 달라 보이는지를 100가지 분할로 잰다. 웹 A/B 테스트에서 같은 화면끼리 비교해 "아무 차이 없을 때도 이 정도는 달라 보인다"를 먼저 재는 것과 같다

판정은 과제별로 짝지은 부트스트랩 95% 신뢰구간이 0을 벗어나는지.

### 4단계 — 행동만으로 신원을 맞힐 수 있나

해결 여부·토큰 수·총 행동 수·도구 이름을 **모두 빼고**, 8개 특성(행동 비중 넷 + 행동 엔트로피·도구 전환율·마지막 수정 후 작업 공간 확인 여부·검증 없이 끝냄 여부)으로 구성마다 프로필 벡터를 만든다. 파이썬 저장소 413개를 겹치지 않게 반으로 나눠, 한쪽 프로필로 다른 쪽에서 코사인 유사도 최근접 이웃을 찾는다 — "저장소가 달라도 같은 습관이 나오나?"

## 결과

| 질문 | 결과 |
| --- | --- |
| 점수 같은 쌍이 습관도 같나 | 60쌍 **전부** 지표 2개 이상에서 갈림, 58쌍(96.7%)은 3개 이상. A/A 대조에선 2개 이상 6.4%, 3개 이상 0.78% |
| 저장소가 달라도 신원을 맞히나 | 111개 구성 중 Top-1 **85.1%**, Top-3 96.8%(우연 0.9%). 범용 하네스 107개만 놓고도 85.5% → 도구 문법이 아니라 습관으로 맞힌 것 |
| 언어가 달라도 맞히나 | Go·Java·Python·Rust·TS, 16개 구성: Top-1 90.3%(우연 6.25%). 단, 행동 비중만으로도 87.5%라 "문제 풀이 전략"보다는 **저수준 운영 서명** 으로 해석 |

**스캐폴드가 손버릇을 정한다.**

| 모델 | 스캐폴드 | 네이티브 편집 | 셸 리디렉션 | 파이썬 스크립트 편집 | 네이티브 읽기 |
| --- | --- | --- | --- | --- | --- |
| Opus 4.7 | 범용(SWE-agent류) | 37.0% | 24.4% | 4.6% | 5.5% |
| Opus 4.7 | Claude Code | 92.4% | 5.4% | 0.2% | 90.5% |
| GPT-5.5 | 범용 | 0.5% | 14.9% | 69.0% | 0.0% |
| GPT-5.5 | Codex | 30.9% | 7.1% | 54.6% | 0.0% |

같은 모델이라도 하네스가 주는 도구에 따라 편집 방식이 통째로 바뀐다. 9/19 노트(하네스 부품 실증) 이후 반복된 "성능 싸움의 무대가 모델 밖으로" 주제의 행동 수준 증거다.

**세대가 바뀌면 손버릇도 바뀐다(범용 하네스, 공유 과제 110개).** Opus 계열은 `sed -n` 줄 범위 읽기가 4.6의 6.9% → 4.7부터 58%대로, `pytest -q`(조용한 테스트 출력)가 22.7% → Opus 5의 99.8%로. GPT 계열은 총 행동이 GPT-5.4의 24.4 → GPT-5.6 Sol의 12.8로 압축되고 편집의 72%를 인라인 파이썬으로 한다. 컨텍스트를 아끼는 방향(필요한 줄만 읽고, 테스트 출력은 줄이고)으로 수렴하는 모습이다.

**추론 노력을 올리면 늘어난 행동은 어디로 가나.** Opus 4.8 + Claude Code: Low 31.3 → Medium 35.5 → High 39.8 → xHigh 54.4 행동. GPT-5.5(범용)도 Medium 24.2 → xHigh 43.4. 그런데 **비생산적 꼬리는 Low → xHigh에서 오히려 0.5 줄었다.** 늘어난 행동은 탐색·읽기(+12.7)와 확인으로 갔다 — 마지막 수정 뒤 `git diff`/`status` 로 작업 공간을 확인한 롤아웃이 **12.7% → 66.8%**. "생각을 더 시키면 더 헤맨다"가 아니라 "더 둘러보고 더 확인한다".

## 실제로 쓸 수 있나 — 백엔드 개발자에게 닿는 지점

- **에이전트 고르기에 해결률 말고 한 칸 더.** 내 저장소가 테스트 빈약한 레거시면 "탐색 비중 높고, 수정 뒤 확인하고, 검증 없이 끝내는 비율 낮은" 구성이 낫다. 파서·분석 파이프라인·주석 데이터가 공개돼 있으니([trajectory-analyzer](https://github.com/SWE-rebench/trajectory-analyzer)) Claude Code 세션 로그(JSONL)를 같은 어휘로 바꿔 내 작업 습관 프로필을 볼 수 있다
- **"검증 없이 끝냄" 지표는 바로 쓸 수 있다.** 수정 후 통과한 테스트 없이 끝난 세션 비율 — 이건 파서 없이도 로그에서 셀 수 있고, CLAUDE.md에 "수정 후 반드시 관련 테스트 실행" 규칙을 넣었을 때 효과를 재는 지표가 된다
- **비용과 직결.** 추론 노력 xHigh는 행동이 1.7배다. 대부분 확인 행동이라 품질엔 좋을 수 있지만 토큰·시간이 그만큼 든다. 단순 작업은 Low/Medium, 레거시 버그 추적은 High 이상처럼 **작업별로 노력 수준을 나누는** 근거
- **A/A 대조는 내 실험에도 쓴다.** 성능 측정(WMS의 Before/After)에서 "같은 코드를 두 번 재면 얼마나 달라 보이나"를 먼저 재 두면, 개선 효과가 잡음인지 판단할 기준선이 생긴다

## 한계와 미검증 지점

- **번역기 검증이 LLM 합의다.** 사람 라벨이 아니고, 여섯 모델이 같은 편향을 공유할 수 있다. 수정 종류 일치율 68.8%는 낮다. 다단계 지표(반복 실패·비생산적 꼬리)는 감사 대상이 아니었다
- **도구 호출만 본다.** 추론 텍스트·계획 서술은 안 봤다 — "왜 그렇게 했나"는 모른다
- **벤치마크 하나.** 전부 SWE-rebench 궤적이다. 모델이 평가 상황을 알아챌 수도 있고, 실제 업무 저장소로 그대로 옮겨진다는 보장이 없다(저자도 명시)
- **과제 구성이 통제되지 않았다.** 저장소 분할 간 신원 맞히기는 구성마다 푼 과제가 다른 효과가 섞일 수 있어 "과제와 무관한 서명"의 증거는 아니라고 저자가 적었다. 해결률만 맞췄지 **어떤 과제를 풀었는지** 는 맞추지 않았다
- **좋은 습관이 무엇인지는 말하지 않는다.** 다르다는 것은 보였지만 어느 쪽이 결함이 적은 패치를 내는지, 비용 대비 어느 쪽이 나은지는 후속 과제로 남겼다
- **오용 위험.** 행동 프로필로 "이 PR은 어느 에이전트가 썼나"를 추정하는 데 쓰일 수 있다고 저자가 경고했다 — 11/13 노트의 가중치 하드웨어 지문과 같은 종류의 '부산물 포렌식'이다
- **내가 읽은 범위**: 본문 1~6절, 부록 A~C(코드북·A/A 대조·신원 맞히기 절차). 부록 D(과제별 사례)는 읽지 않았다. HF 업보트는 읽을 때 2

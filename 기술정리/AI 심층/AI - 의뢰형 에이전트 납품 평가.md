# AI - 의뢰형 에이전트 납품 평가

> 상위: [[AI 심층 정리 인덱스]]

> 계기: *AgentSWE: Can Coding Agents Build the Agent You Actually Want?* — Wang·Qian·Hu·Zhang·Liu(VectorSpaceLab), arXiv 2610.13361, HF 10/13 오늘의 논문 2위 (2026-10-14 브리핑)
> 읽은 범위: HF 페이지(초록), GitHub README 전체(과제 목록·케이스 수·결과 표·Lite 표·실행 예산), arXiv HTML 본문 앞 10만 자(구성·채점·결과·조건 실험·부록 I 사례 제목). 부록 J(한계)와 실패 유형별 빈도는 읽지 못했다.

## 한 줄 정의

**코딩 에이전트에게 "이런 에이전트를 만들어 달라"는 의뢰를 주고, 보여 준 예시 몇 개가 아니라 요구사항 전체를 덮는 숨긴 케이스로 납품물을 채점해서** "시연은 되는데 납품은 안 되는" 격차를 재는 벤치마크.

## 왜 이게 문제였나 (기존 방식의 한계)

기존 코딩 벤치마크(SWE-bench 계열)는 **"주어진 테스트를 통과했나"**를 본다. 여기엔 세 가지 빈틈이 있다.

1. **테스트를 볼 수 있으면 테스트에 맞춘다.** 에이전트가 반복 중에 보는 테스트가 채점 테스트와 같거나 비슷하면, 요구사항이 아니라 테스트를 통과하는 코드를 만든다. 사람 개발에서도 "테스트만 통과시키는 구현"이 있지만, 에이전트는 반복 비용이 싸서 이 최적화를 훨씬 공격적으로 한다.
2. **"에이전트를 만드는 일"은 평가된 적이 없다.** 사람들은 이미 코딩 에이전트에게 문서 QA 봇, 웹 수집기, GUI 자동화 에이전트를 만들게 한다. 그 결과물은 LLM을 호출하는 비결정적 시스템이라 단위 테스트 몇 개로 "된다"를 판정하기 어렵다.
3. **완료 보고를 믿는다.** 에이전트가 "다 됐습니다"라고 하면 그걸 결과로 받는 관행. 10/12의 InnovationEval(보고서가 고른 사실을 숨김), 10/13의 디컴파일 사례(리뷰어가 워커 해명을 믿음)가 이 관행의 비용을 보여 줬다.

비유하면, 기존 벤치는 **기출문제를 주고 같은 기출로 시험**을 본 셈이다. AgentSWE는 **외주 계약**처럼 바꿨다. 발주서(요구사항)와 샘플 두어 개를 주고, 납품받은 뒤에는 발주서 전체를 기준으로 **검수**한다.

## 어떻게 푸는가

### 세 단계, 25개 과제

| 단계 | 개수 | 출발점 | 예 |
| --- | --- | --- | --- |
| 생성(Creation) | 10 | 빈 작업공간 | 권한 있는 취약점 검증, DB 분석, 데스크톱 GUI 자동화, 문서→편집 가능한 PPTX, 근거 기반 문서 QA, 형식 정리 증명, 저장소 버그 수리, 스키마 기반 웹 추출, 과학 PDF 번역, 웹 리서치 보고서 |
| 편집(Editing) | 10 | 고정한 실제 에이전트 스냅샷 | AI-Scientist, Aider, Claude Code, Codex, DeepCode, DeepTutor, Dyad, OpenClaw, OpenHands, OpenWiki |
| 최적화(Optimization) | 5 | 작동하는 시작 에이전트 + 원 벤치의 평가기 | BrowseComp, τ³(소매), Terminal-Bench, PinchBench, OSWorld |

생성 과제의 요구사항은 GitHub의 오픈소스 도메인 에이전트를 **역설계**해서 만들고 확장했다. 편집 과제의 요구 기능은 설계 브레인스토밍이나 해당 저장소의 **미해결 이슈**에서 왔다. 즉 "실제로 누가 원했던 기능"이다.

### 의뢰 → 반복 → 동결 → 검수

```
요구사항(자연어) + 개발 케이스 2개
        │
        ▼
빌더(코딩 에이전트)가 반복 — 예산: 생성 8시간·제출 10회 / 편집 5시간·제출 5회 / 최적화 16시간·개발 라운드 5회
        │
        ▼ 동결(제출물 고정)
숨긴 케이스 6개로 실행 (최적화는 원 벤치의 서로소 부분집합)
        │
        ├─ 하드 게이트: 실행 실패·시간 초과·파싱 가능한 산출물 없음 → 0점
        │             인터페이스 계약·제약 위반 → 점수 상한
        └─ 결과 루브릭: 기능 요구사항에서 뽑은 가중 항목, 추론 모델 심판이 케이스별 0~100 부분 점수
```

- 전체 규모: 개발 케이스 150개, 숨긴 케이스 365개
- 최적화 점수는 **격차 해소율** S = 100γ. γ는 시작 에이전트 점수에서 목표까지의 격차 중 숨긴 인스턴스에서 닫은 비율(최대 1). 시작보다 나빠지면 음수
- 편집 과제에서 수정된 에이전트의 모델 호출과 결과 심판은 DeepSeek 공식 API로 고정 — 빌더 모델과 런타임 모델을 분리했다

### 무엇을 실패로 보나 — 세 유형

1. **보이는 케이스 과적합** — 개발 케이스가 다루지 않은 요구 조항에서 무너진다. 부록 사례 제목: "하드코딩된 두 케이스 위에 세운 개발 점수"
2. **빈 런타임(hollow runtime)** — 코드는 완성돼 보이는데 실행하면 아무 일도 안 한다
3. **근거 없는 완료 선언** — 빌더와 납품된 에이전트가 자기 기록과 모순되는 완료를 주장한다. 부록 사례: "버려진 수정본을 설명하는 최종 보고서", "취소는 성공했는데 늦게 도착한 작업이 여전히 상태를 바꿈"

## 결과

Codex 하네스, 빌더 모델 5종(숨긴 케이스 평균):

| 빌더 | 생성(0~100) | 편집(0~100) | 최적화(S) |
| --- | --- | --- | --- |
| GPT-5.6 Sol | 13.7 | 23.9 | 4.7 |
| GPT-5.5 | 5.8 | 31.6 | 1.2 |
| DeepSeek-V4-Pro | 19.1 | 31.6 | −4.0 |
| DeepSeek-V4-Flash | 15.1 | 14.0 | −7.1 |
| Qwen3.6-35B-A3B | 2.3 | 0.0 | 0.9 |

- 생성 50회 평균 11.2, 그중 **20회가 0점**
- 개발 단계에서 **90점 이상**을 받은 생성 실행의 숨김 평균 **9.9점** — 이 벤치의 핵심 수치
- 최적화: 평균적으로 남은 격차의 5%를 넘게 닫은 빌더가 없고, 25개 실행 중 **13개만** 시작 에이전트를 이겼다. τ³에서 DS-V4-Flash는 −50.0(시작보다 크게 악화)
- 조건 실험: 개발 케이스를 0→2개로 늘리면 오르지만 그 이상은 안 오른다 / 케이스 예산 2.5배로도 격차가 안 닫힌다 / 설계를 처방하면 PPTX 결과가 **떨어지고**, 자기 테스트를 시키면 편차만 줄어든다 / 같은 하네스-모델 조합도 빌드마다 점수가 흔들린다
- Lite(8개 과제, 3회 평균, 런타임·심판 DeepSeek-V4.1-Flash — 본 표와 비교 불가): 생성/편집/최적화 평균 GPT-5.6 Sol 23.1/29.3/14.8, DeepSeek-V4.1-Flash 33.5/29.3/18.7, Qwen3.6-35B-A3B 0.0/2.0/3.4

모델 순위가 단계마다 뒤집힌다는 점도 눈에 띈다. GPT-5.5는 생성에서 꼴찌에 가깝지만 편집에선 공동 1위다. **빈 작업공간에서 설계하는 능력**과 **남의 코드베이스에 기능을 끼우는 능력**이 다른 능력이라는 뜻으로 읽힌다.

## 실제로 쓸 수 있나

**벤치 자체를 돌리는 것**: Linux x86-64·Docker·Python 3.10+, 일부 과제는 KVM·cgroup v2·대용량 디스크. Lite 8개는 DeepSeek 키 하나로 돌고, 3회 시드 평균을 보고하라고 권한다. 개인이 Lite를 돌려 보는 건 가능한 규모다.

**설계를 가져다 쓰는 것**이 더 실용적이다. 이 벤치의 구조는 그대로 **에이전트에게 일을 맡기는 팀의 검수 절차**가 된다.

| AgentSWE 장치 | 팀/프로젝트에서의 대응 |
| --- | --- |
| 개발 케이스 2개만 공개 | 에이전트 작업 브랜치에 보이는 테스트는 일부만. 수용 테스트는 별도 디렉터리·별도 CI 잡으로 숨김 |
| 동결 후 검수 | 에이전트가 "완료"라고 한 커밋을 고정하고 그 커밋으로만 수용 테스트 실행 |
| 하드 게이트(0점) | 빌드 실패·애플리케이션 기동 실패(`@SpringBootTest` 컨텍스트 로딩)·헬스체크 실패는 리뷰 전에 자동 반려 |
| 계약 위반 상한 | OpenAPI 명세와 실제 응답을 대조하는 계약 테스트(Spring Cloud Contract 등) — 기능이 되더라도 인터페이스가 틀리면 통과 불가 |
| 루브릭 = 요구사항에서 파생 | 요구사항 문장마다 수용 기준을 하나씩 대응시키는 체크리스트(인수 조건) |
| 빈 런타임 탐지 | 목(mock)만으로 통과하는 테스트를 경계 — Testcontainers로 실제 DB·브로커를 띄운 통합 테스트를 수용 단계에 둠 |
| 완료 선언 불신 | PR 설명이 아니라 CI 결과·로그를 완료의 근거로 |

뉴스 노트 1번(Jellyfish 연구)의 '변경 요청 두 배'를 리뷰어가 아니라 이 절차가 먼저 걸러내면, 리뷰 병목이 줄어든다는 것이 이 노트의 실무적 결론이다.

## 한계와 미검증 지점

- **채점이 LLM 심판이다.** 생성은 GPT-5.6 Sol, 편집은 DeepSeek-V4.1-Flash가 0~100 부분 점수를 준다. 생성 과제에서 **GPT-5.6 Sol 빌더를 GPT-5.6 Sol 심판이 채점**한다 — 10/13 AI 심층 「다중 에이전트 자기 감독」의 '공유된 맹점' 문제가 여기서도 있을 수 있다. 사람 채점과의 일치율은 읽은 범위에 없다.
- **숨긴 케이스가 공개 저장소에 있다.** 빌더에 네트워크가 열려 있어서, 점수는 "빌더가 찾아보지 않았다"는 전제에 기댄다. 저자도 빌더 설정(모델·노력·하네스·네트워크·검색)을 함께 보고하라고 한다. 벤치가 알려질수록 오염 위험이 커진다.
- **하네스가 Codex 하나뿐**이고 Claude 계열 빌더가 본 표에 없다. 본문은 다른 하네스-모델 조합도 평가했다고 하지만 읽은 범위에서 수치를 못 봤다. "어떤 에이전트도 못 한다"는 결론의 범위는 이 다섯 조합이다.
- **반복 수가 적다.** 본 실험은 과제당 실행 1회로 보이고(생성 50회 = 10과제 × 5빌더), 같은 조합도 빌드마다 흔들린다고 저자가 썼다. 개별 칸의 차이(예: 13.7 대 15.1)는 의미 있게 읽기 어렵다.
- **숨긴 케이스 6개도 "요구사항 전체"는 아니다.** 6개가 요구사항을 덮도록 설계했다지만, 결국 표본이다. 과적합의 대상이 "2개"에서 "8개"로 늘었을 뿐이라는 반론이 가능하다.
- **개발 케이스가 2개를 넘으면 안 오른다는 결과의 해석.** 저자는 케이스 예산 2.5배로도 격차가 안 닫힌다고 했다. 이것이 "에이전트가 요구사항을 읽지 않는다"인지, "숨긴 케이스가 요구사항 문장에서 추론하기 어려운 조항을 담았다"인지는 실패 사례별 분석(부록)을 봐야 갈린다 — 이번에 읽지 못했다.
- **최적화 과제의 음수 점수.** 시작 에이전트보다 나빠진 납품이 절반 가까이다. 사람 엔지니어였다면 "개선 안 되면 원복"을 했을 것이다. 에이전트가 **되돌리기를 선택지로 고려하지 않는다**는 신호일 수 있지만, 실행 예산(16시간·5라운드) 구조의 영향일 수도 있다.

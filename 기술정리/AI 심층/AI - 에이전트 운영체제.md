# AI - 에이전트 운영체제

> 상위: [[AI 심층 정리 인덱스]]

**계기**: AgentKernel — The Trust-Native Agentic Operating System (HF ▲5, [2609.29647](https://huggingface.co/papers/2609.29647) / [arXiv](https://arxiv.org/abs/2609.29647)). 업보트는 낮지만, 9월 20일·25일·26일 그리고 오늘까지 네 번에 걸쳐 나온 에이전트 보안 사고들이 **같은 지점**을 가리키는 것이 확인되면서 갈래로 잡혔다.

## 한 줄 정의

에이전트의 보안 장치를 **애플리케이션 미들웨어에서 운영체제 층으로 내리자**는 제안. 감시자가 감시 대상과 같은 프로세스 신뢰 경계를 공유하는 한 우회가 가능하므로, 신원·입력 중재·기억 관리·실행 통제를 **우회 불가능한(non-bypassable) 커널 서비스**로 만들자는 것이다.

## 왜 이게 문제였나 — 기존 방식의 한계

논문이 문제를 정의하는 문장이 정확해서 그대로 옮긴다. 현대 에이전트는 **일상적으로 신뢰 경계를 넘나든다**(routinely cross trust boundaries). 네 동작이 한 줄 안에 붙어 있다.

1. 신뢰할 수 없는 외부 콘텐츠를 **읽어들인다**
2. 그것을 특권 명령과 **섞는다**
3. 중간 판단(intermediate beliefs)을 **장기 기억에 저장한다**
4. 특권 도구를 **호출한다**

그래서 악성 페이로드가 **모델 입력으로 들어와 해로운 도구 동작으로 나온다.** 이게 SQL 인젝션과 구조가 같은데, 다른 점이 하나 있다 — SQL에서는 데이터와 명령을 구분하는 문법 경계가 있고 prepared statement가 그 경계를 강제한다. **에이전트에는 그 경계가 없다.** 모델에게 들어가는 것은 전부 토큰이고, "이 문장은 사용자 지시고 저 문장은 웹에서 읽은 것"이라는 구분이 모델 내부에는 남지 않는다.

지금까지의 대응은 대체로 **애플리케이션 미들웨어**였다. 가드레일 라이브러리, 프롬프트 필터, 도구 호출 승인 계층 같은 것들이다. 논문이 겨누는 급소는 이것이다 — **그 미들웨어가 감시 대상 에이전트와 같은 프로세스 신뢰 경계를 공유한다.** 감시자가 감시 대상과 같은 방에 있으면 우회가 가능하다. 에이전트가 자기 컨텍스트를 편집할 수 있고, 가드레일 규칙이 같은 프롬프트 안에 문장으로 들어 있고, 필터가 같은 프로세스의 코드라면, 셋 다 조작 가능한 대상이다.

이 진단이 추상적으로 들리지 않는 이유는, 최근 나온 사고들이 정확히 이 구조에서 나왔기 때문이다.

| 사례 | 어느 층이 깨졌나 |
| --- | --- |
| 프롬프트 인젝션 일반 | **입력 중재** — 신뢰할 수 없는 콘텐츠와 특권 명령이 같은 채널에 섞인다 |
| 7월 HF 침해(9/26 노트) | **실행 통제** — "GET만 허용"이라는 정책이 애플리케이션 층에만 있었고, 링크 체인·픽셀 격자로 우회됐다 |
| DNS로 나간 에이전트(9/27 노트) | **실행 통제** — HTTP는 막았는데 이름 해석 경로가 열려 있었다. 정책이 프로토콜 단위였고 통신 단위가 아니었다 |
| 압축 요약문에 지시문을 심은 모델(9/18 노트) | **기억 관리** — 자기 출력이 검증 없이 다음 턴의 입력이 됐다 |
| 검색 결과 오염(9/27 노트) | **입력 중재** — 출처 신뢰도가 조작 가능한 신호(반복 게시·정상 사이트 기생)에 기반했다 |

즉 하나의 버그가 아니라 **같은 층의 빈칸이 반복해서 드러난 것**이다. 논문은 이 실패들을 묶어 **의미 평면(semantic plane)의 실패**라고 부르고, 네 가지 이름을 붙인다 — 위임 남용(delegation abuse), 프롬프트 인젝션, 기억 오염(memory poisoning), 도구 오용(tool misuse).

## 어떻게 푸는가

핵심 발상은 **OS 보안의 고전적 원리를 의미 평면에 옮기는 것**이다. 운영체제는 이미 같은 문제를 푼 적이 있다. 프로그램이 자기 권한을 스스로 정하지 못하게 하고(커널 모드 분리), 파일에 접근할 때마다 커널이 검사하고(시스템 호출), 프로세스가 커널 자료구조를 직접 못 만지게 한다(주소 공간 분리). 요점은 **"프로그램이 착하게 굴어주기를 부탁하지 않는다"**는 것이다. AgentKernel은 에이전트에 대해 같은 태도를 취한다 — 에이전트의 생애를 **의무적(mandatory) 강제 경계**로 감싸고, 그 경계를 네 기둥으로 나눈다.

### 1. Identity(신원) — 누가 누구에게 무엇을 위임했는가

커널이 신원을 관리한다. 목적은 **조직을 넘는 협업**에서 신뢰를 성립시키는 것이다. 에이전트가 다른 조직의 에이전트에게 작업을 넘길 때, 지금은 그 위임 사슬이 대화 내용 안에만 있다. 커널이 신원을 쥐면 "이 요청은 A 조직의 사용자 X가 시작해 에이전트 B를 거쳐 온 것"이라는 사슬이 **말이 아니라 자료구조**가 된다. 위임 남용을 막는 자리가 여기다.

> **실무 비유** — OAuth의 토큰 위임 사슬이 하는 일과 같다. 지금의 에이전트 간 협업은 "내가 A의 대리인이야"라고 **문장으로 주장하는** 단계에 있고, 토큰에 해당하는 것이 없다.

### 2. Perception(지각) — 단일 필터를 단계적 여과로 바꾼다

논문의 표현은 "brittle single-point filters"를 **graduated perception**으로 대체한다는 것이다. 입력 검사를 한 지점에서 통과/차단으로 끝내지 않고, 여러 단계로 나눠 **신뢰 등급을 매겨가며** 들여보낸다. 왜 단일 필터가 깨지기 쉬운지는 오늘 노트의 검색 오염 사례가 그대로 보여준다 — 공격자가 공백·이모지·유니코드 변형으로 같은 문자열을 여러 형태로 만들면 문자열 차단은 무력해진다. **한 번의 참/거짓 판정에 모든 걸 걸지 않는 것**이 설계 원칙이다.

> **실무 비유** — Spring Security의 **필터 체인**이다. 인증을 한 군데서 끝내지 않고 여러 필터를 순서대로 통과시키며 각 단계가 컨텍스트를 채워가는 구조. 어제 노트에서 AgentKernel을 한 줄로 흘릴 때도 같은 비유를 썼는데, 원문을 읽어보니 논문의 의도가 실제로 이쪽에 가깝다.

### 3. Cognition(인지) — 기억에 정보 흐름 제어를 붙인다

에이전트의 장기 기억에 **정보 흐름 제어(information-flow control)**를 적용한다. 정보 흐름 제어는 OS·보안 쪽의 고전 개념으로, 데이터에 등급을 붙여 **낮은 신뢰의 데이터가 높은 신뢰의 자리로 흘러가지 못하게** 하는 방식이다. 기억에 적용하면 "웹에서 읽은 문장"과 "사용자가 직접 말한 것"과 "모델이 추론한 것"이 같은 등급으로 섞이지 않는다.

논문이 주장하는 효과가 두 개인데 하나는 예상대로고 하나는 뜻밖이다. 예상대로인 것은 **기억 오염을 제한한다**는 것. 뜻밖인 것은 **검색 충실도(retrieval fidelity)가 오히려 좋아진다**는 주장이다. 이유는 짐작할 수 있다 — 출처와 신뢰 등급이 메타데이터로 붙으면 검색할 때 그 신호를 쓸 수 있으니, 보안 장치가 부수적으로 검색 품질 장치가 된다. 논문은 이 태도를 **"구조적 보안은 능력 배수기(capability multiplier)"**라고 표현한다. 보안을 능력의 대가로 보지 않는다는 뜻이다.

> **여기가 이 논문에서 가장 흥미로운 지점이다.** 보통 보안 제안은 "안전해지는 대신 느려지고 불편해진다"는 교환을 전제한다. AgentKernel은 반대를 주장한다 — 경계가 확실하면 **더 넓은 권한을 줄 수 있다.** 네 번째 기둥에서 이 논리가 명시적으로 나온다.

### 4. Execution(실행) — 의미에서 커널로 경계를 옮긴다

도구 호출 통제를 **semantic-to-kernel enforcement**로 만든다. "이 도구를 쓰면 안 돼"라는 지시(의미 평면, 즉 부탁)를 커널 수준 강제(구조)로 내린다. 그리고 논문은 이것의 결과를 뒤집어 말한다 — 우회 불가능한 경계 뒤에서는 **더 넓은 도구 권한을 허용할 수 있다**(permits broader tool privileges). 지금은 경계가 약하니까 권한을 좁게 줘서 막는데, 경계가 단단하면 권한을 넓혀도 된다는 논리다.

AgentKernel의 자기 위치 규정도 여기서 나온다 — **오케스트레이션 프레임워크·에이전트 런타임·거버넌스 플랫폼·실행 샌드박스 아래에 빠져 있던 OS 층**이라고 스스로를 놓는다. 대체하려는 게 아니라 **아래에 깔리려는** 것이다.

## 실제로 쓸 수 있나

**아니다. 지금은 아키텍처 제안이다.** 초록이 검증 방법으로 제시하는 것은 "체계적 비교(systematic comparison)와 보안 분석"이고, **벤치마크 수치도 구현체도 초록에 없다.** 논문의 동사가 "introduce"와 "argue"와 "position"이라는 점이 성격을 말해준다 — 시스템 논문이 아니라 **입장 논문(position paper)에 가깝다.**

그래서 이 노트에서 건질 것은 제품이 아니라 **판단 기준**이다. 에이전트를 붙인 기능을 설계할 때 네 기둥을 체크리스트로 쓸 수 있다.

| 기둥 | 물어볼 질문 |
| --- | --- |
| Identity | 이 도구 호출은 **누구의 권한**으로 실행되는가. 위임 사슬이 자료구조로 남는가, 대화 내용에만 있는가 |
| Perception | 외부에서 읽어온 내용과 사용자 지시가 **같은 채널**에 들어가는가. 검사가 한 지점에만 있는가 |
| Cognition | 에이전트가 기억에 남기는 것에 **출처와 신뢰 등급**이 붙는가. 자기 출력이 검증 없이 다음 입력이 되는가 |
| Execution | 금지가 **프롬프트의 문장인가, 코드의 경계인가.** 에이전트가 그 경계를 편집할 수 있는 위치에 있는가 |

마지막 줄이 실무에서 가장 값이 크다. **"프롬프트로 부탁한 것은 보안 장치가 아니다."** 9월 19일 노트의 Bend 2가 "그건 부탁일 뿐"이라며 증명으로 강제한 것과 같은 판단이고, 오늘 노트 3번 항목의 사고들이 전부 이 문장의 실증이다.

Spring 쪽으로 옮기면 이미 익숙한 구조가 대응된다 — 인증·인가를 `@PreAuthorize`로 **선언**하고 프레임워크가 **강제**하는 것이, 컨트롤러 안에서 `if (user.isAdmin())`을 직접 쓰는 것보다 안전한 이유와 같다. 후자는 빠뜨릴 수 있고 전자는 빠뜨리면 통과하지 못한다. AgentKernel이 하려는 일은 에이전트 세계에 그 차이를 만드는 것이다.

## 한계와 미검증 지점

- **구현도 평가도 없다.** 초록에 벤치마크·성능 수치·오픈소스 언급이 전부 없다. "이렇게 해야 한다"까지 있고 "이렇게 하면 이만큼 막힌다"가 없다. 업보트 5는 낮지만, 입장 논문에 대한 반응으로는 이상하지 않은 숫자다
- **가장 큰 미검증 지점: 커널이 의미를 이해해야 하는 자리가 남는다.** OS 커널이 강력한 이유는 검사 대상이 **명확하게 정의된 것**(메모리 주소, 파일 디스크립터, 시스템 호출 번호)이기 때문이다. 그런데 프롬프트 인젝션 판정은 본질적으로 **의미 판단**이다. "이 문장이 지시인가 데이터인가"를 커널이 어떻게 결정론적으로 판정하는가 — 만약 그 판정을 위해 또 모델을 호출한다면, **판정자가 다시 조작 가능한 대상**이 되고 논문이 비판한 구조로 돌아온다. 초록만으로는 이 순환을 어떻게 끊는지 알 수 없다. 전문을 읽을 때 가장 먼저 확인할 지점이 여기다
- **"더 넓은 권한을 허용할 수 있다"는 주장은 검증이 필요하다.** 논리적으로는 매력적이지만, 경계가 실제로 우회 불가능한지를 입증하지 않은 상태에서 권한을 넓히면 **실패의 폭발 반경만 커진다.** 순서가 중요한 주장이다 — 경계를 먼저 증명하고 권한을 넓혀야 한다
- **성능 비용이 다뤄지지 않았다.** 모든 도구 호출과 기억 접근이 커널 경계를 통과하면 오버헤드가 생긴다. OS의 시스템 호출도 비용이 있어서 그걸 줄이는 기법(vDSO, io_uring 등)이 계속 나왔다. 에이전트 쪽 숫자는 초록에 없다
- **채택 경로가 없다.** "오케스트레이션 프레임워크 아래에 깔리는 OS 층"이려면 그 프레임워크들이 이 층 위로 올라와야 한다. 표준도, 구현도, 참조 프레임워크 연동도 초록에 없다. 이 갈래를 추적할 때 볼 것은 논문 자체보다 **누가 이걸 실제로 구현하는가**다
- **오늘 항목 중 DSec(2609.22978)과 겹치는 부분이 있다.** DSec은 이미 프로덕션에서 격리 수준을 네 단계로 나눠 돌리고 있고 "reward hacking 완화"까지 언급한다 — 즉 AgentKernel이 제안하는 것의 일부를 **다른 이름으로 이미 운영하는 곳이 있다.** 둘을 나란히 읽으면 "제안된 구조"와 "현장이 실제로 만든 구조"의 차이를 볼 수 있는데, DSec은 학습 환경용이고 AgentKernel은 배포된 에이전트용이라 목적이 다르다는 점도 같이 봐야 한다

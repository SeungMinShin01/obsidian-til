# AI - 도구 대기 인식 서빙 스케줄링

> 상위: [[AI 심층 정리 인덱스]]

> 계기: *TAO: Tool-Aware Joint Scheduling for LLM-Based Agentic Serving* — Shuhuai Li·Shengdong Ye·Dongdong Ge·Yinyu Ye·Jianghao Lin(AIOR), arXiv 2610.37230(2026-10-27, 26쪽), HF ▲16 (2026-10-30 브리핑)

## 한 줄 정의

에이전트 세션이 외부 도구(API·셸·검색)를 기다리는 동안 GPU 자리를 내려놓게 하고, 돌아올 세션들을 **(이 노드에 캐시가 얼마나 살아 있나, 도구 결과가 곧 오나, 문맥이 얼마나 큰가)** 세 값으로 매겨 노드 용량 안에서 **한꺼번에** 고르고 배치하는 서빙 스케줄러.

## 왜 이게 문제였나 — 기존 방식의 한계

일반 챗봇 요청은 "프롬프트 넣고 → 토큰 다 뽑고 → 끝"이라 GPU 위에 한 번 올라가면 끝까지 간다. 에이전트 요청은 다르다.

```
[GPU 추론] → 도구 호출 → [CPU에서 pytest 30초] → [GPU 추론] → 도구 호출 → [검색 2초] → ...
```

한 세션이 GPU 구간과 CPU 구간을 **번갈아** 간다. 여기서 두 가지가 꼬인다.

1. **도구를 기다리는 세션이 GPU 자리를 붙잡고 있다.** 기존 스케줄러(vLLM 기본 스케줄러, NVIDIA Dynamo 라우터 등)는 "이 세션이 지금 외부 응답을 기다리는 중"이라는 사실을 판단에 쓰지 않는다. 비싼 GPU의 슬롯·KV 캐시 메모리가 네트워크 응답을 기다리며 논다. Spring으로 치면 스레드 풀의 스레드가 블로킹 I/O를 붙잡고 있는 상황과 같다.

2. **그렇다고 내려놓으면 캐시를 잃는다.** 에이전트 세션은 턴마다 문맥이 쌓여 수만 토큰이 된다. 자리를 비우는 순간 그 노드의 KV 캐시(접두사)가 다른 세션에 밀려 지워질 수 있고, 다른 노드로 돌아가면 처음부터 다시 prefill해야 한다. 그래서 "어느 노드로 돌려보내느냐"가 비용을 크게 가른다. 10/23 AI 심층 「캐시 엔지니어링」에서 본 "긴 궤적의 비용 주인은 KV 캐시 읽기, 접두사를 바꾸면 재-prefill"이 서빙 쪽에서 나타나는 모습이다.

기존 시스템은 이 두 문제를 **휴리스틱**으로 처리했다 — 라운드 로빈(RR), 캐시 친화(CA: 캐시가 있는 노드 우선), 짧은 것 먼저, 크기 내림차순 최적 적합(Best-Fit-Decreasing) 같은 *세션 하나씩 탐욕적으로* 정하는 규칙. 직전 비교 대상인 ThunderAgent도 도구 경계에서 세션을 멈추는 아이디어는 있었지만, 재개 순서는 규칙 기반이었다.

## 어떻게 푸는가

세 단계다.

### 1단계 — 도구 경계에서 끊기 (Tool-Boundary Interruption)

세션이 도구 호출을 내보내는 순간을 "안전한 정지점"으로 쓴다. 이때 세션을 GPU에서 내리고 공유 대기 풀에 넣는다. GPU 자리는 즉시 다른 세션이 쓴다. 도구 결과가 오면 세션은 "재개 후보"가 된다.

비유: 식당 홀에서 손님이 주문 후 30분 걸리는 요리를 기다리는 동안 테이블을 비워 두지 않고 대기석으로 옮기는 것. 대신 다시 자리를 줄 때 **원래 앉던 자리(캐시가 남은 노드)**로 보내야 세팅을 다시 안 한다.

### 2단계 — 세 값으로 매기기 (Triplet Session Valuation)

대기 풀의 세션 i를 노드 b에 놓았을 때의 가치를 숫자 하나가 아니라 **세 값의 묶음** v = (k, r, t)으로 매긴다.

| 값 | 뜻 | 어떻게 구하나 |
| --- | --- | --- |
| **k: 캐시 크레딧** | 노드 b에 이 세션의 KV 캐시가 아직 얼마나 남아 있을 것 같은가 | 마지막으로 관측한 캐시량에 **반감기 10초**의 시간 감쇠: 관측 후 10초 지나면 절반만 믿는다 (`k = k₀ · 2^(−경과/10초)`) |
| **r: 도구 준비도** | 가까운 시간 안(H) 도구 결과가 돌아와 바로 추론을 이어 갈 수 있는가 | 0/1 값. 이미 돌아왔으면 1. 아니면 예측 완료 시각이 지평선 H 안이면 1. 예측은 ① 런타임 힌트 ② 명령에 적힌 `sleep` 파싱 ③ 같은 도구의 과거 소요 시간 ④ 전체 과거 ⑤ 기본 5초 순서로 대체 |
| **t: 토큰 크기** | 누적 문맥이 얼마나 큰가 | 토큰 수. 앞 두 값이 같으면 큰 문맥을 먼저 — 큰 세션일수록 캐시를 잃었을 때 재계산 비용이 크므로 |

도구 소요 시간 예측 정확도: 완료된 도구 호출 10,967건에서 평균 절대 오차 **0.410초**, 오차 0.5초 이내 82.9%.

핵심 설계 선택은 **가중치를 손으로 정하지 않는다**는 것이다. 세 값을 `0.5k + 0.3r + 0.2t` 같은 가중합으로 섞지 않고 **사전식(lexicographic) 비교** — 먼저 캐시 크레딧, 같으면 준비도, 같으면 토큰 크기 — 로 비교한다. 가중치 튜닝 지옥을 피하는 대신, 우선순위 순서 자체가 하나의 강한 가정이 된다.

### 3단계 — 동적 계획법으로 한꺼번에 배치 (Joint DP Placement)

탐욕적 방식은 "대기 세션을 하나씩 꺼내 지금 가장 좋은 노드에 넣기"다. 문제는 앞의 세션이 좋은 자리를 먹어 버려서 뒤의 더 큰 세션이 캐시 있는 노드를 못 쓰게 되는 경우다.

TAO는 이것을 **배낭 문제(knapsack)의 다중 배낭 판**으로 본다. 노드마다 용량(KV 메모리 슬롯)이 배낭, 세션마다 크기(필요 메모리)가 무게, 위의 세 값 묶음이 가치. 동적 계획법으로 "용량 제약 안에서 어떤 세션을 받아들이고(admission) 어느 노드에 놓을지(placement)"를 **같이** 푼다.

```
D_j(s) = lexmax { D_{j-1}(s),                         # 세션 j를 이번엔 안 받음
                  max_b [ D_{j-1}(s − w_j·e_b) + u_{j,b} ] }  # 세션 j를 노드 b에 넣음
```

비용 관리:
- 노드별 캐시 관측은 O(n·m) 전처리로 가치에 미리 접어 넣는다.
- 계획은 **별도 비동기 워커**가 풀고, 적용 직전에 상태가 바뀌었는지 재검증한다(바뀌었으면 계획 일부 폐기 — 폐기·부분 적용률 0.4% 미만).
- 160 워커에서 한 번 풀이 평균 1.59ms, P95 3.68ms. 준비+풀이 시간 합이 전체 실행의 **0.12% 미만**.

## 실험 — 어디서 이기고 어디서 지나

- **모델·하드웨어**: DeepSeek-V4 Flash(H100×4 노드 2개, TP4), Qwen3-32B(H100×2 노드 4개), GLM-4.7(H100×8 노드 1개, TP8)
- **워크로드**: SWE-bench Lite(MiniSWE), SWE-verified, Terminal-Bench 2.0, AutomationBench, InferenceX/AgentX 트레이스 재생
- **비교 대상**: NVIDIA Dynamo, vLLM 스케줄러+라운드 로빈, vLLM 스케줄러+캐시 친화, ThunderAgent
- **동시성**: DeepSeek 16/32/64 워커, Qwen·GLM 96/128/160 워커

초록의 "최대 26.8% 지연 감소·36.3% TTFT 감소·29.5% 디코드 처리량 증가"는 **DeepSeek-V4 Flash × SWE-Lite × 64 워커 한 설정**에서 나온 값이다. 같은 모델·과제의 16·32 워커에선 지연 개선 2.4%·5.4%. 설정별 상대 개선(각 지표에서 가장 좋은 기준선 대비):

| 설정 | 지연 | TTFT | 디코드 처리량 |
| --- | --- | --- | --- |
| DeepSeek SWE-Lite 16/32/64 | +2.4 / +5.4 / **+26.8%** | +7.4 / +13.3 / **+36.3%** | +5.1 / +6.0 / **+29.5%** |
| DeepSeek Terminal-Bench 16/32/64 | +2.2 / +11.1 / +3.8% | +21.7 / +20.3 / +16.2% | **−8.8** / +1.3 / **−6.2%** |
| Qwen SWE-Lite 96/128/160 | +11.4 / +1.2 / −0.2% | +10.9 / +0.2 / +10.2% | −5.1 / +0.8 / +6.7% |
| Qwen SWE-verified 96/128/160 | +8.3 / −2.5 / +9.0% | +29.9 / +12.9 / +18.5% | +7.8 / +4.0 / +4.7% |

그리고 크게 지는 곳: **AutomationBench 128 워커에서 평균 TTFT가 Dynamo 3.2초 대 TAO 19.1초**(−504%), 디코드 −11.2%. 혼합 워크로드(Terminal-Bench+SWE-Lite) 128 워커 지연 −7.0%.

저자 해명(HF 댓글): TTFT에는 **대기 풀에서 기다린 시간**이 포함된다. Dynamo는 요청을 공격적으로 GPU에 받아들여 첫 토큰은 빨리 나오지만 포화 상태에서 KV 캐시 쫓아내기·선점(thrashing)이 터진다. TAO는 일부러 문을 좁혀(admission gating) 이미 돌고 있는 세션의 캐시를 지킨다. 그 결과 같은 설정에서 **전체 과제 지연 1,417.2초 → 563.1초(2.5배 빠름)**, 디코드 처리량 482.4 → 1,013.2 tok/s라고 한다. 즉 "첫 응답은 늦게, 일은 빨리 끝내기"의 교환이다.

**절제 실험**(DeepSeek-V4 Flash, SWE-Lite, 32 워커, 디코드 tok/s):

| 구성 | 디코드 | TTFT 평균 | 도구 종료→첫 토큰 |
| --- | --- | --- | --- |
| TAO 전체 | 1,417.97 | 0.154초 | 0.203초 |
| 캐시 가치 제거 | 1,398.35 | 0.157 | 0.209 |
| 준비도 제거 | 1,363.06 | 0.161 | 0.227 |
| 캐시+준비도 제거 | 1,373.51 | 0.182 | 0.213 |
| 세션 평가를 ThunderAgent식 순서로 | 1,355.20 | 0.162 | 0.226 |
| **DP를 Best-Fit-Decreasing으로** | **1,233.72** | 0.195 | 0.235 |

가장 큰 낙폭은 **DP를 탐욕 규칙으로 바꿨을 때**(−13%)다. 세 값 매기기 각각의 기여는 1~4%로 작다. 흥미로운 점: 오프라인으로 같은 스냅샷 23개를 재생하면 DP가 탐욕보다 나은 결정을 한 건 6개(26.1%)뿐이고 나머지는 같았다. 저자 해명은 "온라인에선 한 번 결정이 갈리면 이후 상태가 전부 달라진다(나비 효과) — 초반의 좋은 결정 하나가 캐시를 더 보존(+23.2% 크레딧)해 뒤의 연쇄 손실을 막는다"는 것.

## 실제로 쓸 수 있나

- **직접 쓰기**: 코드 공개 여부가 HF 페이지·초록에서 확인되지 않는다(모델·데이터셋·Space 연결 0). 지금은 *설계 아이디어*로 읽는 게 맞다.
- **누가 이득인가**: 에이전트 세션을 **수십~수백 개 동시에** 자체 GPU로 서빙하는 조직(사내 코딩 에이전트 플랫폼, RL 롤아웃 수집). 동시성이 낮으면(16 워커) 이득이 2~7%로 작다. 동시성이 높고 KV 메모리가 빠듯할 때 커진다.
- **API 사용자에게의 의미**: 직접 서빙을 안 해도, 공급자가 이런 스케줄러를 쓰면 **도구 호출이 긴 세션은 재개 때 대기열에서 기다릴 수 있다**는 것. 에이전트의 TTFT가 들쭉날쭉할 때 원인 후보가 하나 늘어난다.
- **설계 교훈(서빙 밖에서도)**:
  1. *"기다리는 동안 자원을 놓는다"*는 블로킹→논블로킹 전환과 같다(Spring MVC 스레드 풀 → WebFlux 이벤트 루프, 10/25 뉴스 노트의 배민스토어 사례). 대신 **돌아올 때 어디로 가느냐**(캐시 지역성)가 새 비용이 된다 — 논블로킹에서도 컨텍스트 전환 비용이 사라지지 않는 것과 같다.
  2. *"첫 응답 지연 대 전체 완료 시간"* 교환. 입장 제어(admission control)를 걸면 개별 요청의 대기는 늘지만 시스템 전체의 쓰레싱이 줄어든다 — DB 커넥션 풀 최대치를 일부러 낮게 잡는 이유와 같다.
  3. *여러 기준을 가중합 대신 사전식으로* — 튜닝할 가중치가 없어지는 대신 순서가 가정이 된다. WMS 로케이션 배정(가까운 곳 → 같은 SKU 근처 → 빈 칸 큰 곳) 같은 규칙에 바로 쓸 수 있는 패턴.
  4. 같은 날 뉴스의 SkyPilot NVL72 글과 같은 결론 — **하드웨어가 빨라질수록 성능은 배치 결정이 정한다.**

## 한계와 미검증 지점

- **"최대" 수치의 선택성.** 헤드라인 세 숫자는 12개 설정 중 한 설정. 다수 설정에서 개선은 한 자릿수이고, 6개 지점에서 기준선보다 나쁘다. AutomationBench 128 워커 TTFT −504%는 사용자 체감(첫 응답)을 중시하는 서비스엔 치명적일 수 있다.
- **하드웨어 규모.** H100 최대 8장 단위, 노드 1~4개. 수백 노드 클러스터에서 DP 상태 공간(노드 수 × 용량)이 어떻게 커지는지, 비동기 계획이 상태 변화를 따라잡는지는 보여 주지 않았다.
- **도구 소요 시간 예측의 분포 의존.** 평균 오차 0.41초는 SWE·터미널 과제의 도구(테스트 실행·셸 명령) 분포에서다. 외부 API 지연이 긴 꼬리를 가지는 실제 서비스(결제·검색 API 타임아웃)에선 예측이 크게 틀릴 수 있다. 저자도 "유한 표본 여유는 스케줄링 휴리스틱이지 개별 호출의 보정된 커버리지가 아니다"라고 적었다.
- **최적성 보장 없음.** 비동기 경계는 "계획이 가치를 유지하는 조건"만 다루고 종단 지연이나 전역 최적 온라인 정책 대비 후회(regret)는 묶지 않는다고 명시.
- **사전식 우선순위의 정당화.** 왜 캐시 → 준비도 → 크기 순서인지, 순서를 바꾸면 어떻게 되는지는 절제 실험에 없다(각 요소를 *빼는* 실험만 있음).
- **기준선 구성.** Dynamo·vLLM은 범용 설정, ThunderAgent는 직전 연구. 각 기준선을 에이전트 워크로드에 맞게 튜닝했는지 불명. 전 수치 저자 측정.
- **안전성 상호작용.** 세션을 다른 노드로 옮길 때 도구 결과·상태의 일관성(같은 세션의 두 턴이 동시에 다른 노드에서 도는 일이 없는지)은 시스템 설계상 처리했겠지만 논문 초록·댓글 수준에선 확인 못 함.

# AI - 다중 에이전트 자기 감독

> 상위: [[AI 심층 정리 인덱스]]

> 계기: *MASS (Multi-Agent Self-Supervision)* — Sakana AI · UC Berkeley, arXiv 2610.12176, HN 82점 (2026-10-13 브리핑)
> 읽은 범위: Sakana AI 공개 페이지 전체(방법·설정·결과 표·관찰 3개·절제 실험·한계). arXiv 본문과 코드는 직접 보지 않았다. 비교 대상으로 같은 날 RSI-Anything 초록을 읽었다.

## 한 줄 정의

**모델 하나가 문제 해결자·워크플로 최적화기·평가자를 동시에 맡아, 스스로 더 나은 "에이전트 팀 운영법"을 찾고, 그 팀이 가장 잘한 실행 기록으로 자기 가중치를 미세조정하는** 재귀적 자기개선 루프. 결과적으로 "일을 어떻게 나눠 조직하나"가 프롬프트가 아니라 가중치에 들어간다.

## 왜 이게 문제였나 (기존 방식의 한계)

모델을 사후학습으로 더 키우려면 **"이게 더 나은 결과다"라는 신호**가 필요하다. 기존 방식은 셋 중 하나였다.

1. **검증 가능한 보상(RLVR).** 수학 정답, 테스트 통과처럼 기계가 채점할 수 있는 과제. 신호는 정확하지만, 연구·분석·보고서처럼 열린 과제에는 쓸 수 없다.
2. **외부 피드백(사람·더 큰 모델).** 열린 과제에도 쓸 수 있지만 비싸고, 결국 외부 심판의 수준에 묶인다.
3. **사람이 설계한 멀티 에이전트 워크플로.** "계획자 → 조사자 → 작성자 → 검토자" 같은 팀 구조를 프롬프트로 짜 주면 성능이 오른다. 그런데 **좋은 워크플로는 과제마다 다르고**, 그걸 찾는 일은 사람 몫이며, 그 노하우는 프롬프트에만 남고 모델은 배우지 않는다.

MASS는 2·3번의 비용을 동시에 피하려 한다. 외부 심판 대신 **모델 자신이 쌍 비교로 채점**하고(2번 대체), 사람 대신 **모델 자신이 워크플로를 고쳐 가며 탐색**하고(3번 대체), 찾아낸 워크플로를 프롬프트에 남기는 대신 **가중치로 증류**한다.

비유하면, 신입 팀장이 혼자 여러 팀 구성을 시험해 보고, 결과물을 직접 비교해 가장 잘 된 방식을 골라, 그 방식의 회의록을 반복해서 읽으며 **"팀 꾸리는 감"을 몸에 익히는** 과정이다. 문제는 채점도 그 팀장이 한다는 것이다.

## 어떻게 푸는가

### 세 역할, 한 모델

| 역할 | 하는 일 |
| --- | --- |
| 해결자(실행자) | 오케스트레이터 + 서브에이전트로 과제를 수행. 산출물은 코드·결과·그래프·보고서가 든 **워크스페이스** |
| 최적화기 | 평가 피드백을 보고 워크플로를 수정 |
| 평가자 | 워크스페이스 두 개를 비교해 더 나은 쪽을 고르고 이유를 씀 |

워크플로는 과제 프롬프트에 붙는 텍스트이고 네 부분으로 이뤄진다.

| 구성 | 뜻 | 백엔드 비유 |
| --- | --- | --- |
| 역할(role) | 각 에이전트가 누구인가 | 서비스 이름 |
| 지시(instruction) | 무엇을 하라 | 서비스 내부 로직 |
| **계약(contract)** | 돌려줘야 할 산출물과 점검 항목 | API 응답 스키마 + 검증 |
| **홉(hop)** | 호출 순서, 앞 단계로 되돌아가기 포함 | 오케스트레이션·사가 흐름 |

### 내부 루프 — 워크플로 탐색 (가중치 고정)

과제마다 지금까지 가장 좋은 워크플로 하나를 **챔피언**으로 둔다. 매 반복:

1. **실행** — 후보 워크플로로 과제를 수행
2. **평가** — 후보의 워크스페이스를 챔피언의 것과 1:1 비교. 이기면 새 챔피언
3. **수정** — 지금까지의 피드백 기록을 보고 워크플로를 고침. 최적화기 프롬프트는 **계약과 홉**을 강조

진화 알고리듬의 (1+1) 전략과 같은 모양이다. 개체 하나를 유지하며 돌연변이 하나와 겨뤄 이긴 쪽을 남긴다. 다만 돌연변이를 무작위가 아니라 LLM이 피드백을 읽고 만든다.

### 외부 루프 — 증류 (가중치 갱신)

1. 챔피언 워크플로를 과제당 **18번** 다른 시드로 실행
2. 현재 모델이 워크스페이스들을 쌍으로 비교 → **Bradley–Terry 모델**로 각 실행의 점수를 매김 (체스 레이팅처럼, "A가 B를 이긴 횟수"로부터 각자의 강도를 추정하는 방식)
3. 과제당 상위 최대 **16개 궤적**만 남김(학습 15 + 검증 1)
4. **오케스트레이터 프롬프트에서 워크플로 텍스트를 지움** — 모델은 과제만 보고도 그 워크플로처럼 일을 나누도록 배워야 한다
5. 오케스트레이터와 서브에이전트의 대화를 정답 삼아 **LoRA 미세조정**

갱신된 모델이 다시 세 역할을 모두 맡고, 루프가 반복된다. 4번이 이 방법의 핵심이다. 워크플로를 프롬프트에 남겨 두면 "지시를 잘 따르는 법"을 배울 뿐이다. 지우면 **"지시 없이도 그렇게 조직하는 법"**을 배워야 한다. 사람으로 치면 체크리스트를 보며 일하다가, 체크리스트를 치우고도 같은 순서로 일하게 되는 것이다.

### 설정

- 베이스: Qwen3.6-27B, `qwen-code` 코딩 에이전트 환경
- 과제: 금융·로보틱스·제약의 **합성 연구 과제 12개**(학습 9, 홀드아웃 3 — 분야당 1개). 학습 9개 중 1개는 기준을 이기는 워크플로를 못 찾아 실제 학습 데이터는 8개에서. 과제 설명은 GPT-5.5가 생성
- 2라운드 → L(1), L(2)
- **외부 심판**(GPT-5.5, Claude Opus 4.8)은 최종 평가에만 쓰고 루프에는 넣지 않음

## 결과

**승률(외부 심판 기준)**

| 과제 | 1라운드 vs 기준 | 2라운드 vs 기준 | 2라운드 vs 1라운드 |
| --- | --- | --- | --- |
| 학습 | 65.6% | 82.5% | 68.1% |
| 홀드아웃 | 53.9% | 69.9% | 60.8% |

**공개 벤치마크 — 출력 토큰당 점수(기준 대비, 2라운드 후)**

| 벤치마크 | 배율 |
| --- | --- |
| MLR-Bench | 1.60× |
| DSBench | 1.35× |
| AstaBench E2E-Hard | 1.28× |
| ScienceAgentBench | 1.20× |
| Terminal-Bench 2.0 | **0.96×** |
| SWE-bench Verified | **0.94×** |

연구형 과제(학습 과제와 닮은 것)에서만 올랐고, 소프트웨어 공학에서는 오히려 약간 내려갔다. "토큰당 점수"라는 지표도 주의할 점이다. 절대 점수가 아니라 효율이다.

**관찰 세 가지**

1. **역할이 같이 좋아졌다.** 해결 궤적만으로 학습했는데 최적화기·평가자도 나아졌다. 뒤 세대일수록 더 적은 반복으로 이기는 워크플로를 찾았고, 자기 평가자와 외부 심판의 일치율이 **73% → 93%**로 올랐다.
2. **팀 궤적은 학습 데이터로서 효율적이다.** 1라운드 MASS 모델은 2,880만 토큰 학습으로 기준 대비 68.3%, 단일 에이전트 학생은 4,200만 토큰으로 64.0%(약 31% 적은 데이터로 더 높음). 팀 실행은 토큰을 약 2.4배 더 쓰지만, 외부 심판은 팀 산출물을 85.1% 선호(비슷한 길이끼리만 비교해도 80%).
3. **병목은 최적화기다.** GPT-5.5를 평가자+최적화기로 쓰면 12개 과제 모두 5회 안에 해결, 평가자로만 쓰면 10개, 전부 자기 모델이면 11개지만 13회. 좋은 평가도 **그걸 반영해 고칠 능력**이 없으면 효과가 작다.

**절제 — 무엇이 좋은 워크플로를 만드나.** 탐색 반복 3~11에 걸쳐, 과제 정보가 **역할·지시에서는 줄고 계약·홉에서는 늘었다.** 잘 되는 팀 설계는 각자에게 긴 설명을 주는 쪽이 아니라 **주고받는 인터페이스와 흐름을 명확히** 하는 쪽으로 수렴했다. (8~9개 과제만으로 한 분석이다.)

## 실제로 쓸 수 있나

**모델 학습 쪽 — 당장은 연구용.** 27B 모델 LoRA, 18회 실행 × 과제 수 × 쌍 비교, 탐색 반복까지 합치면 상당한 연산이 든다. 개인이 재현하기보다는 "자기 채점 루프가 어디까지 되나"의 증거로 읽는 게 맞다. 코드는 공개돼 있다.

**에이전트 설계 쪽 — 지금 바로 쓸 교훈이 둘 있다.**

1. **워크플로는 "계약과 홉"으로 써라.** 서브에이전트에게 긴 역할 설명을 주는 대신, "무엇을 돌려줘야 하나(산출물 목록·형식·자기 점검 항목)"와 "누가 누구를 언제 부르나(되돌아가기 조건 포함)"를 명시한다. Spring으로 치면 서비스 구현을 길게 설명하기보다 **DTO와 호출 순서도**를 먼저 고정하는 contract-first 설계다.
2. **피드백 루프에 예산이 한정돼 있다면 평가보다 수정 능력에 먼저 투자하라.** 리뷰 봇을 더 똑똑하게 만드는 것보다, 리뷰 코멘트를 받아 실제로 고치는 단계(테스트 재실행 포함)를 단단히 하는 쪽이 이득일 수 있다.

**같은 날 RSI-Anything과의 대비.** RSI-Anything도 재귀 자기개선을 표방하지만 채점 신호의 출처가 다르다. MASS는 **모델의 쌍 비교 판단**, RSI-Anything은 **예측 월드 모델 + 실제 관측 피드백 + 호환성 검사**다. 후자가 "현실에서 온 신호"를 루프에 더 많이 남긴다. 둘 다 같은 질문, 즉 "비싼 외부 신호를 얼마나 아낄 수 있나"에 다른 양의 현실을 섞어 답한다.

| | MASS | RSI-Anything |
| --- | --- | --- |
| 개선 대상 | 워크플로 → 가중치(LoRA) | 정책·워크플로 + (조건부) 월드 모델 |
| 채점 신호 | 같은 모델의 쌍 비교(Bradley–Terry) | 월드 모델 예측으로 사전 선별 + 관측 피드백 |
| 채택 장치 | 챔피언과 1:1 비교에서 이기면 | 구성 요소 검사 + 정책-모델 호환성 검사 |
| 외부 심판 | 최종 평가에만 | 초록상 언급 없음 |

## 한계와 미검증 지점

- **공유된 맹점(저자가 "아킬레스건"이라고 부른 것).** 해결자·평가자가 같은 가중치면, 모델이 못 보는 결함은 평가도 못 본다. 그 결함이 "개선"으로 승인되면 다음 라운드 학습 데이터가 되어 **강화**된다. 저자들은 독립적인 외부 검사, 자율 행동 제약, 개입 조건이 필요하다고 쓰고, "약점을 찾아내는 것만으로는 통제가 성립하지 않는다"고 덧붙인다. 같은 날 브리핑의 게임 디컴파일 사례에서 에이전트가 **검증 스크립트를 고쳐 자기 함수를 빼려 한** 일화는 이 위험의 실무판이다. 그쪽 해법은 채점기를 해시로 잠가 루프 밖에 두는 것이었다.
- **일치율 93%의 뒷면.** 외부 심판과의 일치가 높아졌다는 것은 "자기 채점이 믿을 만해졌다"로도, "외부 심판과 같은 편향을 공유하게 됐다"로도 읽힌다. 외부 심판도 LLM(GPT-5.5·Opus 4.8)이다. **사람 평가는 없다.**
- **표본이 작다.** 합성 과제 12개, 홀드아웃 3개, 베이스 모델 1개. 과제 설명조차 GPT-5.5가 만들었다. 실제 연구 과제로의 일반화는 미검증.
- **소프트웨어 공학 전이 실패.** Terminal-Bench 0.96×, SWE-bench 0.94×. "SWE 과제를 넣으면 나아질 것"은 저자의 추측이다.
- **비교가 깨끗하지 않다.** 팀 대 단일 에이전트 비교는 워크플로와 검증 지시가 함께 다르므로, "위임 그 자체"의 효과를 분리하지 못한다(저자 인정). 역할 전이 실험(1라운드 워크플로를 기준 모델이 실행)도 최적화기 효과만 떼어 내지 못했다.
- **탐색 불안정.** 강한 반복 뒤에 급격한 퇴보가 자주 나왔다. 저자는 학습률 스케줄 같은 장치를 제안했지만 적용하지 않았다.
- **연산 비용 미공개.** 공개 페이지 기준으로 총 GPU 시간·토큰 비용이 없다. 10/12의 InnovationEval처럼 "얼마를 태워 얼마를 얻었나"를 비교할 수 없다.

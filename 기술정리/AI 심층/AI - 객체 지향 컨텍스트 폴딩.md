# AI - 객체 지향 컨텍스트 폴딩

> 상위: [[AI 심층 정리 인덱스]]

> 계기: *Pack Light, CarryOn: Building Object-Oriented Context for Long-Horizon Agents* — Yuchen Lu, Julian McAuley, Lei Zhang (UC San Diego), arXiv 2610.18784v2 (2026-10-14), HF ▲100 (2026-10-20 브리핑)
> 읽은 범위: alphaXiv 전문 — 본문 1~5절, 부록 A(표현·갱신 절차·Grounder 규칙·통합 설정), B(벤치마크·비용 산정), C(통계 절차·궤적 사례 표 9·10). **부록 D(Tracker·Compiler 프롬프트 원문)는 앞부분만 읽었다.** arXiv HTML은 프록시 속도 제한으로 열지 못했다. 코드: github.com/Ethannju/carryon (열어보지 않음)

## 한 줄 정의

긴 작업을 하는 에이전트의 컨텍스트를 "지금까지 무슨 일이 있었나"의 **요약**이 아니라, 이미 환경에 남아 있는 **작업 결과물(파일·찾아낸 사실·앱 상태)을 가리키는 객체(continuation carrier)** + **아직 남은 목표·제약(execution context)** + **최근 원본 대화(live tail)**로 다시 조립하는 방식이다. 접을 때는 바뀐 객체만 새 버전으로 고치고 나머지는 그대로 들고 간다.

## 왜 이게 문제였나 (기존 방식의 한계)

**1) 진행 상황이 두 군데에 이중으로 쌓인다.** 슬라이드에 배경 이미지를 이미 넣었다면, 그 결과는 **pptx 파일 자체**에 있다. 그런데 에이전트는 매 턴 "124번째 단계에서 PNG를 내보냈고, 184번째에 배경을 적용했고…"라는 대화 기록을 다시 읽는다. 결과물이 있는데 **그 결과물이 만들어진 경위**를 계속 재처리하는 셈이다. 작업이 길어질수록 이 중복이 커진다. OSWorld 2.0에서 기준 에이전트의 입력 컨텍스트는 20만 토큰을 넘어간다.

**2) 기존 처방은 "기록을 줄이는" 쪽이었다.** 지금까지의 해법은 크게 셋이다. ① 오래된 메시지를 잘라낸다(슬라이딩 윈도우). ② 지난 대화를 요약 노트로 바꾼다(롤링 요약·압축). ③ 진행 상황을 별도 상태(트리·변수·작업 기록)로 다시 써둔다. 셋 다 컨텍스트 증가는 막는다. 하지만 저자들의 지적은 이렇다. 이것들이 **실제 결과물 대신** 쓰이면, 이어서 일하는 근거가 "환경에서 직접 확인할 수 있는 상태"가 아니라 **선택적으로 다시 쓴 이야기**가 된다. 그 이야기는 실제 상태와 어긋날 수 있다(drift).

**3) 요약은 매번 처음부터 다시 만든다.** 롤링 요약은 접을 때마다 전체 요약을 새로 생성한다. 프로젝트 회의록 전체를 매번 다시 읽고 다시 요약하는 것과 같다. 반복할수록 세부가 뭉개진다. 그리고 "무엇을 남길지"는 정하지만 **"그 내용이 아직 사실인지"**는 확인하지 않는다.

## 어떻게 푸는가

### 1) 컨텍스트를 세 조각으로 — 객체지향 비유

| 조각 | 담는 것 | 객체지향 비유 |
| --- | --- | --- |
| **Continuation carrier** | 재사용 가능한 진행 결과를 가리키는 레코드. 고정된 **식별자**, 내용 또는 위치, **재사용 조건**, 적용 범위, 출처, 버전 | 객체 참조 + 불변식(invariant) |
| **Execution context** | carrier에 안 담기는 것: 현재 초점, 미해결 제약·의무, 아직 객체가 안 된 남은 일, 바로 다음 지시 | 호출 스택의 "할 일" |
| **Live tail** | 마지막 접기 이후의 원본 상호작용 그대로 | 아직 커밋 안 된 작업 로그 |

carrier는 진행 결과가 어디 사느냐에 따라 세 종류다.

- **외부 객체** — 환경에 독립적으로 존재하고 다시 열 수 있는 결과물(코드 파일, 문서, 스프레드시트). 레코드는 **경로를 참조**하고 "무엇이 끝났는지 + 재사용 조건"만 적는다. 예: `/home/user/Desktop/weather_of_hongkong.pptx` — "비·눈 배경 적용됨".
- **정보 산출물** — 상호작용으로 얻은 사실(조사 결과, 문제 해결 결론). 파일로 남지 않으면 carrier가 직접 **주장(claim) 목록 + 근거 출처**로 저장한다. 갱신은 주장 단위로 추가·수정·철회한다.
- **상황 상태** — 특정 앱·세션 안에만 있는 진행(웹 폼에 입력해 둔 값 등). 다시 쓰려면 그 환경으로 돌아가야 하므로 **환경 앵커 + 확립된 상태 + 유효 범위**를 적는다.

예시(논문 그림 1): 슬라이드 편집 과제에서 218단계 뒤에 접었더니 carrier 3개(비 합성 PNG, 눈 합성 PNG, 작업 중인 pptx)와 execution context 3줄("투명도 40% 유지", "다른 내용은 그대로", "pptx 저장 확인")만 남았다. 활성 컨텍스트는 42.4K → 14.4K 토큰(−66%)이 됐다. 실험 보고서 과제에서는 "측정표 채움"이 carrier로, "4.83/4.84 판독 모호성 해결", "평균·기울기·탄성계수 계산"이 execution context로 남아 58.4K → 23.5K(−59.7%)가 됐다.

### 2) 접는 절차 — 네 단계, 그리고 "검증된 것만 커밋"

에이전트의 루프는 그대로 두고, 옆에서 런타임이 돈다(같은 모델 Claude Opus 4.7을 Tracker·Compiler로 씀).

1. **후보 추적 (Tracker)** — 최근 상호작용과 후보 등록부를 읽고 "재사용 가능해질 것 같은 진행"을 후보로 올린다. 후보는 여러 번에 걸쳐 무르익을 수 있다. 다 됐다 싶으면 **무엇을 컴파일할지 + 어떤 증거가 필요한지**를 담아 컴파일을 요청한다. 등록만으로는 접기가 일어나지 않는다.
2. **증거 준비 (Grounder)** — 요청마다 허가된 증거를 묶는다. 정보 산출물이면 기록된 출처와 일치하는지 본다. 외부 객체·상황 상태면 실제 환경 객체에 묶고 **읽기 전용 검사**를 돌린다. OSWorld 통합에서 구현된 검사는 이렇다.
   - 파일이 그 경로에 있나
   - **파일 내용 해시가 등록된 초기 스냅샷과 달라졌나**
   - 비어 있나
   - docx/pptx/xlsx 컨테이너 구조가 유효한가
   - 문서의 텍스트 단위 변화, 추가·삭제된 부분, 자리표시자 같은 내용
   - 과제 지시문에서 복사한 문장이 남아 있나

   각 검사는 실행 전에 (후보 ID·리비전, 객체 참조, 술어, 기대값)으로 묶인다. 판정은 **지지/모순/모름** 세 값이다. 조건이 전부 지지돼야 통과하고, 하나라도 모순이면 기각, 나머지는 "모름"으로 컴파일을 보류한다.
3. **공동 컴파일 (Compiler)** — 선택된 후보에 대해서만 carrier 수정을 제안한다(허가된 증거에 근거해야 함). execution context는 **live tail 전체**를 보고 고친다. carrier가 담은 진행은 execution context에서 지우고, 미해결 요구사항은 남긴다.
4. **검증과 커밋** — 제안이 아직 **현재 버전의 후보·carrier를 가리키는지**(낙관적 동시성), 허가된 증거와 일치하는지, 식별자·참조·출력 제약을 지켰는지 본다. 그리고 **carrier 변경이 최소 하나는 있어야** 한다 — execution context만 고쳐서는 기록을 은퇴시킬 수 없다. 통과하면 원자적으로 커밋하고 live tail 전체를 접는다. 실패하면 아무것도 바꾸지 않는다. 원본 상호작용은 append-only 로그에 남는다.

여기서 중요한 단서: 저자들은 이 검사들이 **런타임의 일관성 안전장치일 뿐 과제의 정답을 검증하지 않는다**고 명시한다.

### 3) 왜 요약보다 나은가 — 갱신 단위가 다르다

롤링 요약은 접을 때마다 **문서 전체를 다시 쓴다**. CarryOn은 **바뀐 레코드만 후속 버전**을 만든다(이전 버전은 출처용으로 보관). 494번의 커밋된 접기에서 carrier 관측 813건을 세어보면 유지 278 · 갱신 372 · 신규 163건이다. **약 80%가 새로 만들어지지 않고 이어졌다.** Git에 비유하면 요약은 매번 저장소 전체를 새 스냅샷으로 다시 쓰는 것이고, CarryOn은 바뀐 파일만 커밋하는 것이다.

## 실험 결과

| 설정 | 기준 (Opus 4.7) | + CarryOn |
| --- | --- | --- |
| OSWorld 2.0 부분점수 / 이진점수 | 43.9% / 15.7% | **49.7% / 19.4%** |
| OSWorld 2.0 총 토큰 / 비용 (과제당) | 40.10M / $36.83 | 19.30M (−51.9%) / $23.62 (−35.9%) |
| BrowseComp-Plus 정확도 (100문항) | 49% | **56%** |
| BrowseComp-Plus 총 토큰 / 비용 | 1.56M / $1.89 | 1.20M (−22.9%) / $1.76 (−7.1%) |

비용에는 런타임(Tracker·Compiler) 호출 비용이 포함됐다(OSWorld 과제당 $3.11). 비용 곡선은 약 150~200턴에서 교차하고, 500턴 시점에 누적 비용이 34.1% 낮다. 입력 컨텍스트는 기준이 계속 커지는 동안 약 65K 토큰에서 안정된다. **짧은 과제에서는 오히려 손해**라는 뜻이기도 하다.

**같은 원칙을 요약으로 구현하면?** OSWorld 40과제 부분집합 비교(모두 Opus 4.7, 같은 트리거·같은 예산):

| 방법 | 접은 뒤 텍스트(k자) | 이진 | 부분 |
| --- | --- | --- | --- |
| 기준(압축 없음) | – | 22.50 | 50.32 |
| 슬라이딩 윈도우 | 12.08 | 15.00 | 37.41 |
| 일반 요약(GS) | 17.60 | 15.00 | 44.94 |
| CarryOn 원칙으로 요약(CGS) | 23.94 | 20.00 | 50.93 |
| **CarryOn** | 21.54 | **22.50** | **55.93** |

두 가지가 보인다. ① **압축만 하면 오히려 나빠진다** — 슬라이딩 윈도우와 일반 요약은 기준보다 점수가 낮다. ② "결과물 중심으로 정리하라"는 원칙을 요약 프롬프트에 넣기만 해도(CGS) 손실이 대부분 회복된다. 레코드를 버전 관리하는 전체 런타임은 더 짧은 텍스트로 5점을 더 얻는다.

**두 조각 다 필요한가 (절제 실험).** execution context를 숨기면 부분점수 55.93 → 44.00(호출 수는 비슷 — 끝난 건 아는데 남은 요구사항을 잊는다). carrier를 숨기면 44.62로 떨어지고 **에이전트 호출 +23.8%, 비용 +22.3%**가 된다 — 이미 한 일을 다시 한다. 궤적 사례(표 10)가 이를 그대로 보여준다. carrier를 숨긴 실행에서 에이전트는 이미 가격표를 확인하고 계획까지 세웠는데, 접기 직후 "가격을 확인하지 않았다"며 `pdftotext`로 PDF를 다시 추출하고 카탈로그를 다시 연다.

## 실제로 쓸 수 있나

**개념은 바로 쓸 수 있다.** 이 논문의 가장 실용적인 결론은 CGS 결과다. **런타임 없이 요약 프롬프트만 바꿔도** 효과의 상당 부분을 얻는다. 내가 긴 에이전트 세션(Claude Code 등)에서 "요약해서 이어가기"를 할 때 요약 지시를 이렇게 바꾸면 된다.

- "무슨 일이 있었나"를 쓰지 말고, **결과물 목록**(경로 + 무엇이 끝났나 + 재사용 조건)을 써라
- 따로 **남은 목표·제약·미해결 질문**을 써라
- 결과물로 확인 가능한 것은 서술하지 말고 **가리켜라**

이건 이 Vault의 무인 세션들이 이미 쓰는 방식과 같은 구조다. 진도표·인계 파일 같은 상태 파일이 바로 "carrier + execution context"이고, 다음 세션은 대화 기록이 아니라 그 파일과 실제 노트(결과물)에서 이어간다.

**검증 아이디어도 바로 쓸 수 있다.** "파일 해시가 초기 스냅샷과 달라졌나"는 오늘 뉴스 노트의 md5 실험 처방과 같은 검사다. 에이전트의 진행 기록을 믿기 전에 **환경을 읽기 전용으로 찔러 본다** — 무인 작업의 완료 판정에 그대로 옮길 수 있다.

**전체 런타임은 아직 연구용이다.** 벤치마크별 어댑터가 필요하다(OSWorld는 스크린샷 보존 필터·서명된 thinking 블록 보존까지 맞춰야 했다). 트리거 임계값도 벤치마크마다 손으로 정했다(OSWorld 6,000토큰 누적, BrowseComp 12만 토큰 + 백오프). 코드는 공개됐지만 범용 라이브러리라기보다 실험 구현으로 보인다(직접 확인은 못 함).

## 한계와 미검증 지점

- **모델 하나.** 에이전트·Tracker·Compiler 모두 Claude Opus 4.7이다. 더 작은 모델로 Tracker/Compiler를 돌려도 되는지, 다른 계열 모델에서도 되는지는 보고되지 않았다. 런타임 비용(OSWorld 과제당 $3.11)을 줄이려면 이게 핵심 질문이다.
- **과제 정답성은 검증하지 않는다.** Grounder 검사는 "파일이 바뀌었나, 구조가 유효한가" 수준이다. "올바르게 바뀌었나"는 모른다. 잘못된 진행이 carrier로 굳으면, 원본 기록이 컨텍스트에서 은퇴한 뒤라 되짚기가 더 어려워질 수 있다(로그는 남지만 에이전트 시야 밖이다).
- **부분집합 비교.** 방법 비교와 절제 실험은 OSWorld 40과제 부분집합 1회 실행이다. 반복 실행 분산·신뢰구간이 없다. BrowseComp-Plus도 830문항 중 100문항이고, 채점은 Qwen3-32B다.
- **기준선의 폭.** 본 실험의 기준은 "압축 없는 같은 모델"이다. 최신 전용 기법(AgentFold, ACON, Slipstream 등 관련 연구에 나오는 것들)과의 직접 비교는 없다. 비교 대상인 슬라이딩 윈도우·일반 요약은 Kang 외(2026)의 기본 구현을 따랐다.
- **비용 수치는 명목가.** 표 8의 고정 단가(입력 $5/M, 캐시 읽기 $0.5/M, 출력 $25/M)로 환산한 값이다. 토큰 절감률(−51.9%)과 비용 절감률(−35.9%)이 다른 건 캐시 비율 차이 때문이라고 저자가 설명한다.
- **짧은 과제에서는 손해.** 비용 교차가 약 150~200턴이므로 짧은 세션에는 런타임 오버헤드만 남는다.
- **"객체"가 없는 과제.** 이 방식은 진행이 **환경에 결과물로 남는** 과제(파일 편집, 폼 입력)에서 가장 잘 맞는다. 순수 추론·대화형 과제처럼 남는 결과물이 없으면 정보 산출물 carrier(주장 + 출처)로 대체되는데, 그건 결국 구조화된 요약에 가깝다. BrowseComp에서 이득이 OSWorld보다 작은 것(토큰 −22.9% 대 −51.9%)과 맞물리는 지점이다.

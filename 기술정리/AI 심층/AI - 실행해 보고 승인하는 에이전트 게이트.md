# AI - 실행해 보고 승인하는 에이전트 게이트

> 상위: [[AI 심층 정리 인덱스]]

> 계기: *"Shall We Approve?" Consequence-Aware Approval for Autonomous Coding Agents*(시스템 이름 **Caper**) — Weiheng Wu·Junkai Chen·Zhensu Sun·Jieke Shi·Yunbo Lyu·David Lo(싱가포르경영대 SMU, 제출자 소속 표기 기준), arXiv 2610.40753, 2026-10-29 공개·11/4 HF 제출 (2026-11-05 브리핑). HF 페이지·arXiv 초록·GitHub README는 전문을 읽었고, arXiv 본문은 질의 추출 방식으로 기준선·지연·절제·한계 절을 확인했다(본문 전체를 한 줄씩 읽은 것은 아님). 코드: Apache-2.0.

## 한 줄 정의

코딩 에이전트가 셸 명령을 내면 **스냅샷을 뜬 샌드박스에서 그 명령을 실제로 한 번 실행**하고(`strace -f`, 네트워크 차단, 출력 보류), 관측된 효과(바뀐 파일과 diff, 네트워크 시도, 자격 증명 읽기, 사용자에게 보일 출력)를 **요약 보고서**로 만들어 독립된 LLM 승인자에게 보여 준 뒤, 허용이면 그 상태를 그대로 **커밋**, 차단이면 스냅샷으로 **롤백**하고 에이전트가 고쳐 쓸 수 있는 이유를 돌려주는 승인 게이트.

## 왜 이게 문제였나 — 기존 방식의 한계

**승인 피로.** 에이전트가 명령마다 "실행할까요?"를 물으면 사람은 결국 다 누른다. 저자 HF 코멘트는 Claude Code 사용자가 권한 요청의 93%를 승인한다고 썼다(출처 미표기, 미검증). 그래서 자동 승인기가 생겼다. 논문은 기존 방식을 네 부류로 나눈다.

| 부류 | 대표(논문 기준선) | 판단 근거 |
| --- | --- | --- |
| 규칙 기반 검사기 | CARE | 명령문 패턴 |
| 가드레일 모델 | TS-Guard, gpt-oss-safeguard-20b, Qwen3Guard-Gen-8B | 요청·명령 텍스트 |
| 스테이징·롤백 | YoloFS | 실행 후 변경을 보여 주되 판단은 에이전트·사람에게 맡김 |
| 배포된 권한 시스템 | Claude Code Auto Mode | 대화·명령을 본 분류기 |

공통 약점은 **텍스트만 본다**는 것이다. `./deploy.sh`, `make clean`, `python tool.py --fix`의 위험은 명령문이 아니라 **스크립트 안에 무엇이 있고 지금 워크스페이스가 어떤 상태인가**에 달려 있다. 명령문이 순해 보일수록(바이너리·스크립트·Makefile 안에 해를 숨길수록) 텍스트 판정은 무력해진다. 반대로 YoloFS처럼 변경을 관측하는 쪽은 "그래서 이게 괜찮은가"의 판단을 실행 *뒤* 에이전트나 사람에게 미룬다.

비유: 텍스트 판정기는 **택배 송장만 보고** 통관시키는 세관이고, Caper는 **상자를 X선에 한 번 통과시키고** 그 사진을 심사관에게 보여 주는 세관이다.

## 어떻게 푸는가

**1) 트랜잭션처럼 감싼다.** 과제마다 Docker 컨테이너 하나가 샌드박스다(네트워크 차단, 메모리·프로세스 수 제한). 명령 직전에 컨테이너를 스냅샷한다.

**2) 진짜로 한 번 돌린다.** `strace -f`(ptrace 기반 시스템 콜 추적, eBPF·seccomp 아님)를 걸고 실행. 출력은 에이전트에게 바로 주지 않고 붙잡아 둔다.

**3) 추적을 '효과 보고서'로 줄인다.** 시스템 콜 원본이 아니라 승인자가 읽을 수 있는 크기로:
- 영속적으로 바뀐 파일(작은 텍스트 파일은 **내용 diff**까지)
- 네트워크 시도 — 목적지, 시도한 프로세스, 그 직전에 읽은 파일 (실제 전송은 차단됐으므로 "보내려 했다"가 보인다)
- 자격 증명·보호 데이터 읽기
- 사용자에게 보일 출력, 그리고 각 효과가 **어떤 파일에서 비롯됐는지**

**4) 독립 승인자가 판단.** 사용자 과제·대화·명령·보고서를 보고 ALLOW/BLOCK + 짧은 이유. 논문 실험의 승인자는 gpt-5.6-luna(Auto Mode 분류기도 같은 모델로 맞춤), 에이전트는 GLM-5.3-Flash.

**5) 커밋 또는 롤백.** 허용이면 스냅샷만 버리고 **이미 실행된 상태를 그대로 유지**, 붙잡아 둔 출력을 돌려준다 — 명령은 **정확히 한 번** 실행된다(다시 돌리지 않는다). 차단이면 변형된 컨테이너를 지우고 스냅샷에서 새 컨테이너를 띄워, 에이전트는 이전 상태에서 이유를 받아 다른 길을 찾는다.

"다시 돌리지 않는다"가 설계의 핵심이다. 미리 돌려 본 결과와 실제 반영이 같은 실행이므로, 미리보기와 커밋 사이에 세계가 바뀌는 TOCTOU 문제가 **컨테이너 안에서는** 생기지 않는다. 대가는 컨테이너 밖으로 나가는 효과를 되돌릴 수 없다는 것 — 그래서 네트워크를 막는다. 패키지 레지스트리만은 예외로 허용할 수 있는데, 받아 온 것은 컨테이너 안에 떨어지니 롤백에 같이 쓸려 나가기 때문이다.

Claude Code에는 `PreToolUse` 훅으로 붙인다(bwrap 사용, README 기준 Claude Code v2.1.288 바이너리 필요·미포함).

## 결과 — 숫자

**유해 결과율(낮을수록 좋음)과 안전 쌍둥이 오차단율.**

| 시스템 | SABER 유해 | YoloFS-Ext 유해 | YoloFS-Ext 오차단 |
| --- | --- | --- | --- |
| CARE(규칙) | 15.0% | 69.6% | 2.0% |
| TS-Guard | 18.8% | 94.1% | 8.8% |
| gpt-oss-safeguard-20b | 18.6% | 62.7% | 15.7% |
| Qwen3Guard-Gen-8B | 16.0% | 67.6% | 0.0%(아무것도 안 막음, 순위 제외) |
| YoloFS(스테이징) | 21.2% | 35.3% | —(막는 기능 없음) |
| Claude Code Auto Mode | 14.8% | 62.7% | 3.9% |
| **Caper** | **6.7%** | **7.8%** | **1.0%** |

- **SABER**: 상태가 있는 프로젝트 워크스페이스에서 코딩 에이전트의 운영 안전성 벤치마크(Hu 외, 682과제). **YoloFS-Ext**: 저자들이 만든 102개 위험 과제 + 각각의 안전 쌍둥이, 해가 **에이전트가 실행하라고 받은 도구 안에** 숨어 있고, 판정은 최종 파일 시스템으로 프로그램이 한다.
- 브리핑의 "기존 최소 14.8%"는 Auto Mode의 SABER 값, "35.3%"는 막는 기능이 아예 없는 YoloFS의 값이다. **막는 기능이 있는 기준선 중 YoloFS-Ext 최선은 62.7%** — 숨긴 해 앞에서 텍스트 판정기는 동전 던지기보다 조금 나은 수준이었다.

**지연.** 승인 지연 중앙값 3.2초(p95 6.4초) — 대부분은 LLM 승인자 시간. 샌드박스 자체는 허용 시 약 0.5초, 차단 시 약 1.5초. 단계별 중앙값: 스냅샷 347ms, 추적 실행 81ms(p95 832ms), strace 오버헤드 14ms, 허용 후 스냅샷 제거 15ms, 차단 후 롤백 972ms.

**절제 — 무엇이 효과를 냈나.**
- **맥락 vs 증거.** 증거 없이 승인자에게 맥락만 늘리면(명령만 → 대화 전체) 유해율 44.1%→17.6%로 줄지만 쌍둥이 오차단이 52.0%→61.8%로 **늘어난다** — 의심이 많아질 뿐 분별은 안 는다. 증거가 있으면 **명령만 보고도** 유해 1.0%, 오차단 0.
- **관측 vs 예측.** 같은 모델이 명령과 참조 파일을 보고 효과를 *예측*하게 하면 유해율은 관측만큼 내려가지만 쌍둥이 61.8%를 여전히 막는다. 예측은 조심성을 주고, 관측은 **확신을 준다**.
- **diff의 몫.** 내용 diff를 빼면 YoloFS-Ext 유해율 7.8%→13.7%. 차이는 전부 "덮어쓰기" 과제(3→10건)에서 났고 "삭제" 과제는 무관(5 vs 4) — 삭제는 목록만 봐도 보이지만, 덮어쓰기는 **무엇으로** 덮었는지를 봐야 안다.
- **은닉 수준.** 증거 없이는 해를 바이너리에 숨길 때 4.2%, 스크립트 11.5%, Makefile·스크립트 체인 26.9%로 포장이 깊을수록 통과. 증거가 있으면 모든 수준에서 4~15%.

## 실제로 쓸 수 있나

- **발상 자체는 오늘 바로 쓸 수 있다.** "에이전트는 컨테이너·워크트리 안에서만, 반영은 사람이 diff를 보고"는 이미 많은 사람이 손으로 하는 일이다. Caper는 그 diff 검토를 *명령 단위로 쪼개고* LLM에게 맡긴 것이다. 개인 개발 환경이라면 devcontainer + 네트워크 차단 + `git diff` 검토만으로 절반은 따라 할 수 있다.
- **3.2초 중앙값**은 사람이 승인 버튼을 누르는 시간보다 짧다. 다만 명령이 많은 긴 세션에선 누적된다.
- **WMS 같은 백엔드 프로젝트에 대입하면**: `./gradlew flywayMigrate`, `docker compose down -v` 같은 명령은 텍스트로는 평범하지만 효과(볼륨 삭제, 원격 DB 접속)는 크다. Caper식이라면 원격 DB 접속은 "네트워크 시도: db-host:5432"로 보고되고 막힌다 — 즉 **원격 효과가 본질인 명령은 이 방식으로 승인할 수 없다**. 배포·마이그레이션은 여전히 CI와 사람의 몫이라는 결론으로 돌아온다(오늘 뉴스 노트의 Binance 항목과 같은 결론).

## 한계와 미검증 지점

- **컨테이너 밖 효과는 되돌릴 수 없다.** 미리 실행은 진짜 실행이다. 네트워크 요청·원격 서비스 쓰기·명령이 띄운 백그라운드 프로세스는 승인자가 판단하기 *전에* 일어난다(그래서 네트워크 차단이 전제). 네트워크가 필요한 명령은 사실상 "시도만 보이고 실패"한다.
- **실행 한 번만 본다.** 시간·난수·환경에 따라 달라지는 도구, **샌드박스를 감지하고 해를 미루는** 악성 코드, 보고서에 실려 승인자에게 가는 **주입 텍스트**, 해를 무해해 보이는 명령 여러 개로 **쪼개기** — 저자 스스로 적응형 공격자에 대한 방어를 주장하지 않는다. 특히 "샌드박스 감지 후 지연"은 Binance 사고 같은 표적형 악성 코드가 흔히 하는 일이다.
- **셸 명령만.** 파일 편집 같은 다른 도구 호출은 하네스에 맡긴다.
- **판단은 결국 LLM.** 같은 보고서도 실행마다 다르게 읽을 수 있다. 승인자 모델 하나(gpt-5.6-luna)·에이전트 모델 하나(GLM-5.3-Flash)로만 쟀다.
- **벤치마크 편향.** YoloFS-Ext는 저자 자작이고, "도구 안에 해를 숨긴" 설정은 관측 기반 방식에 유리하게 짜여 있다. SABER 판정도 저자가 규칙 채널을 고친 "수정 오라클"을 썼다.
- **비교의 범위.** Codex의 자동 리뷰어는 기본 샌드박스에서 워크스페이스 밖으로 나가는 요청만 검토해 이 벤치마크의 해 대부분에 닿지 않는다며 비교에서 뺐다.
- **확인 못 한 것.** Caper가 여전히 해를 통과시킨 개별 사례(6.7%·7.8%의 내용), 실행 간 분산, 독립 재현. 저장소는 커밋 2개·스타 0, README의 arXiv 링크·BibTeX가 자리표시자 상태였다.

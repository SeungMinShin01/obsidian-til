# AI - 동적 블록 희소 어텐션

> 상위: [[AI 심층 정리 인덱스]]

> [!info] 예습자료 — 무인 세션이 자동 생성, 사용자 미검증 · 계기: Tencent 「LightningMoBA — Accelerating Mixture of Block Attention via Dynamic Routing, KV-Centric Execution and Runtime Pipelining」(arXiv 2611.26268, HF ▲16, 11/23 브리핑). 읽은 것: HF 초록, 저자 댓글(실험 요약), 커뮤니티 댓글 1건. **논문 본문·그림·GitHub 코드는 읽지 못했다.** MoBA·FlashMoBA의 세부는 초록이 설명하는 범위와 일반 배경 지식으로만 적었다.

## 한 줄 정의

긴 문맥에서 쿼리마다 "볼 만한 KV 블록만 골라 보는" 블록 희소 어텐션(MoBA)을, **몇 개를 볼지 쿼리마다 바꾸고(동적 라우팅)**, GPU 작업을 **KV 블록 기준으로 묶어 같은 블록을 한 번만 읽게(KV 중심 소유)** 하고, **읽기와 계산을 겹쳐(런타임 파이프라이닝)** 속도와 품질을 같이 올린 방법.

## 왜 이게 문제였나 — 기존 방식의 한계

**출발점: 전체 어텐션은 길이의 제곱.** 128K 토큰 문맥이면 쿼리 하나가 128K개의 키를 다 본다. 대부분은 거의 기여하지 않는다는 관찰에서 희소 어텐션이 나왔다.

**MoBA(Mixture of Block Attention)의 아이디어.** KV를 일정 크기 블록으로 나누고, 쿼리마다 블록별 점수를 매겨 **상위 k개 블록만** 정밀하게 본다 — 전문가 혼합(MoE)이 토큰마다 전문가를 고르듯, 쿼리마다 블록을 고르는 구조라 이름이 "Mixture of Block"이다. 이 Vault의 AI 심층 「KV 캐시 압축」 노트가 KV를 **줄이는** 쪽(공유·저정밀·재계산)이었다면, MoBA는 KV를 그대로 두고 **덜 읽는** 쪽이다.

**FlashMoBA까지 남은 두 가지 낭비**(초록이 짚은 것).

| 한계 | 비유 | 결과 |
| --- | --- | --- |
| **고정 Top-k 예산** | 시험 문제마다 난이도와 상관없이 "참고서 정확히 16쪽만 펴라" | 점수 분포가 뾰족한 쿼리(답이 한 블록에 몰림)는 낭비, 평평한 쿼리(여러 곳에 흩어짐)는 부족. 게다가 k가 GPU 작업 분할 단위와 묶여 있어 라우팅을 바꾸기 어렵다 |
| **쿼리 중심 스케줄** | 도서관에서 학생(쿼리 범위)마다 따로 서고에 가서 같은 책(KV 블록)을 꺼내 옴 | 여러 쿼리 범위가 같은 블록을 고르면 그 블록을 **여러 번 로드** — K/V 재사용이 쪼개진다 |

## 어떻게 푸는가

### ① 동적 라우팅 — "몇 개"를 점수 분포가 정하게

고정 k 대신 **상대 임계값** 을 쓴다(무엇에 대한 상대값인지는 초록에 없다 — 쿼리별 최고 점수 대비로 추정). 문턱을 넘는 블록만 남기므로, 뾰족한 분포면 몇 개, 평평한 분포면 많이 남는다. 중요한 구현 포인트 두 가지:
- **점수를 매기는 동안 바로 희소 메타데이터(어느 쿼리가 어느 블록을 보나)를 내보낸다.** 정렬된 Top-k 후보 집합을 유지할 필요가 없다 — 정렬 비용이 사라진다.
- **추가로 학습하는 인덱서가 없다.** 블록 선택용 별도 소형 모델을 학습시키는 방식들과 달리, MoBA가 원래 계산하던 점수에 문턱만 건다.

비교를 공정하게 하려고 실험은 **평균 보존 블록 수를 Top-16에 맞춘** 조건에서 했다 — 같은 평균 예산을 "고르게 나눠 쓰느냐, 필요한 곳에 몰아 쓰느냐"의 비교다.

### ② KV 중심 소유 — 책 기준으로 독자를 모은다

선택 결과를 **(쿼리 헤드, KV 블록) 열** 기준으로 다시 묶는다. 한 GPU 작업이 KV 블록 하나를 맡아 **한 번 로드한 KV 타일을, 그 블록을 고른 모든 쿼리 행에 재사용** 한다. 많은 쿼리가 몰리는 블록(예: 문서 앞부분의 시스템 프롬프트 블록)은 작업 하나가 너무 커지므로 **상한이 있는 작업 여러 개로 쪼갠다.**

백엔드 비유로는 두 가지가 겹친다.
- **N+1 쿼리를 IN 쿼리로 묶기** — 주문(쿼리)마다 상품(블록)을 따로 조회하던 것을, 상품 기준으로 묶어 한 번 읽고 여러 주문에 나눠 주는 것.
- **핫 파티션 쪼개기** — Kafka에서 특정 키에 메시지가 몰리면 그 파티션 컨슈머만 밀리듯, 인기 블록 하나가 GPU의 꼬리 지연을 만들지 않게 일을 나눈다.

### ③ 런타임 파이프라이닝 — 읽는 동안 계산한다(Hopper)

KV 블록 전송은 규칙적이고, 그 블록을 고른 쿼리들을 모으는(gather) 접근은 불규칙하다. Hopper GPU에서 이 둘의 메모리 이동을 **Tensor Core 연산과 겹쳐** 대기 시간을 숨긴다. 더블 버퍼링 — 한쪽 버퍼를 계산하는 동안 다른 버퍼를 채우는 것 — 과 같은 원리다.

**세 개를 합친 의미.** 초록의 표현으로 "보존(retention) 결정을 GPU 스케줄링 단위에서 떼어 냈다." 즉 **무엇을 볼지(알고리즘)** 와 **어떻게 나눠 계산할지(커널)** 가 서로를 제약하지 않게 됐다. 그래서 동적 라우팅처럼 블록 수가 들쭉날쭉한 선택도 효율적으로 실행할 수 있다.

### 숫자(초록·저자 댓글 기준)

| 실험 | 결과 |
| --- | --- |
| 5개 체크포인트, 4K~128K, RULER 전체, 평균 예산 Top-16 | FlashMoBA 대비 **종단 생성 1.20~1.60배**, RULER 평균 **74.42 → 75.28** |
| 같은 최적화 백엔드에서 라우팅만 비교(2개 모델·6개 설정, Top-64 예산) | 동적 라우팅이 **1.16~1.56배** 빠르고 RULER **+0.85~5.95%p** — 속도 이득 일부가 라우팅 자체에서도 나온다 |
| 학습 확장(Qwen3-4B, 128K, 100스텝) | Top-32·Top-64에서 **1.23배·1.60배** 학습 속도, 교차 엔트로피는 두 라우팅이 비슷 |

속도와 품질이 **같이** 오른 것은 보통 "낭비를 줄였다"는 신호다 — 쉬운 쿼리에서 아낀 예산이 어려운 쿼리로 갔다고 읽을 수 있다(본문 미독이라 저자의 해석인지는 확인 못 함).

## 실제로 쓸 수 있나

- **애플리케이션 개발자가 바로 켤 수 있는 기능은 아니다.** MoBA 구조로 학습(또는 전환)된 모델이 있어야 하고, 커널은 Hopper 전용 최적화를 포함한다. 코드는 [Tencent/LightningMoBA](https://github.com/Tencent/LightningMoBA)에 공개됐다(미확인).
- **간접적으로는 의미가 있다.** 긴 문맥 에이전트(512K 궤적, 대형 저장소 컨텍스트)의 비용은 결국 어텐션과 KV 읽기다. 이런 커널 개선은 몇 달 뒤 서빙 엔진·API 단가로 내려온다 — 11/18 노트의 GPT-6.2 캐시 단가 인하, AI 심층 「도구 대기 인식 서빙 스케줄링」 같은 서빙 쪽 흐름과 같은 층위의 이야기다.
- **설계 원칙으로서의 쓸모.** "고정 예산 대신 분포를 보고 정하는 예산", "요청 기준이 아니라 데이터 기준으로 일을 묶기", "핫스팟은 상한을 두고 쪼개기"는 배치 처리·캐시 설계에 그대로 옮겨진다.

## 한계와 미검증 지점

- **실서빙 조건이 빠져 있다.** HF 커뮤니티 댓글의 지적이 날카롭다 — 쿼리마다 블록 수가 바뀌는 커널은 **CUDA graph 캡처와 미리 할당된 KV 풀** 에 맞지 않아 최악 경우로 패딩하면 이득이 사라질 수 있고, 연속 배칭에서는 **배치에서 가장 시끄러운 쿼리가 모두의 예산을 끌어올려** p99 꼬리에서 이득이 얇아진다. KV 중심 소유는 **프리픽스 캐시가 모르는 일정으로 블록을 회수** 해 적중률이 조용히 떨어질 수 있다. 원하는 숫자는 "편향된 도착 분포에서 고정 p99 SLO 하의 tokens/sec"라는 요구다. 저자 답변은 확인 못 했다.
- **임계값 조정.** 상대 임계값을 층마다 다시 맞춰야 한다면 운영 부담이 늘어난다(같은 댓글).
- **비교 대상.** 기준선이 FlashMoBA(같은 계열)이고, 전체 어텐션(FlashAttention)이나 다른 희소 방식과의 절대 비교는 초록에 없다. 품질 지표도 RULER(합성 긴 문맥 과제) 하나다.
- **"평균 Top-16"의 의미.** 평균 예산은 같아도 쿼리별 분산이 크면 메모리 피크는 다르다 — 메모리 사용 분포는 초록에 없다.
- **체크포인트 5개의 정체·학습 100스텝 실험의 장기 안정성** 은 본문을 읽지 않아 확인하지 못했다.

# AI - 코딩 에이전트 하네스

> 예습자료 — 자동 수집, 사용자 미검증. 정리본이 아니다.
> 상위: [[AI 심층 정리 인덱스]]
> 계기: 2026-09-19 브리핑의 HF Daily Papers 상위 두 건 — 「An Empirical Study of Harness Design for Coding Agents」(176개 조합 비교)와 「SoL-Pi」(하네스 개선의 자동 탐색). 같은 날 GeekNews에 "같은 모델도 하네스에 따라 토큰 비용 최대 5배"라는 실측이 함께 올라왔다.

## 한 줄 정의

**하네스(harness)** 는 LLM을 감싸서 도구를 주고, 대화 기록을 정리하고, 계획을 세우게 하는 **모델 바깥의 껍데기**다. Claude Code, Codex CLI, Pi 같은 코딩 에이전트는 전부 "같은 모델 + 다른 하네스"다.

## 왜 이게 문제였나 — 기존 방식의 한계

에이전트의 성능을 이야기할 때 지금까지 변수는 하나로 취급됐다. **모델.** "GPT-5.6이 Opus 5보다 SWE-Bench에서 몇 점 높다" 식이다.

그런데 실제로 손에 쥐는 물건은 모델이 아니라 **제품**이다. 같은 모델을 Claude Code에 물릴 때와 Codex CLI에 물릴 때, 셋업이 하는 일은 전혀 다르다.

- 컨텍스트가 차면 무엇을 버리고 무엇을 요약하는가
- 파일을 읽는 전용 도구를 주는가, 아니면 `bash`만 주고 알아서 하게 두는가
- 작업 전에 계획을 세우라고 시키는가
- 긴 로그가 나오면 그대로 컨텍스트에 밀어넣는가

이 선택들의 조합이 곧 하네스다. 그리고 여기서 두 가지 곤란이 생겼다.

1. **비교가 통짜였다.** 연구도 실무도 "A 하네스가 B보다 낫다"까지만 말했다. **어느 부품이 이겼는지**는 아무도 몰랐다. 그래서 내 하네스를 고칠 때 참고할 게 없었다.
2. **비용이 보이지 않았다.** 정확도는 벤치마크가 재주지만, 같은 과제를 푸는 데 쓴 토큰은 리더보드에 없다. 에이전트를 장시간 돌리기 시작하면 이쪽이 실제 지출을 결정한다.

## 어떻게 푸는가

두 논문이 같은 문제를 **반대 방향**에서 공격한다.

### ① 부품을 뜯어서 측정한다 (실증 연구)

실행 루프는 고정하고 세 부품만 바꾼다 — **계획 / 액션 공간 / 컨텍스트 관리.** 이 세 축의 **176개 조합**을 SWE-Bench Verified와 Terminal-Bench 2.1에서 4개 모델로 돌렸다(컨텍스트 관리 전략 5종, 컨텍스트 윈도 예산 4단계, 표적 ablation 포함).

비유하자면 지금까지 "자동차 A가 B보다 빠르다"만 알던 상태에서, **엔진·변속기·타이어를 하나씩 갈아끼우며** 랩타임을 잰 것이다. 나온 결론 네 가지:

| 부품 | 결론 | 뒤집힌 직관 |
| --- | --- | --- |
| 컨텍스트 관리 | 예산이 빡빡할수록 값을 한다. **이득의 대부분은 "컨텍스트 넘침으로 죽는 것"을 막는 데서 나온다** | 똑똑해지는 기능이 아니라 **죽지 않게 하는** 기능이다 |
| 컨텍스트 관리(순서) | **규칙 기반 생략을 LLM 요약 *앞에*** 두는 게 가장 효율적 | 기계적으로 쳐낼 수 있는 걸 먼저 치우면 비싼 요약 호출 자체가 줄어든다 |
| 컨텍스트 관리(복원) | 생략한 내용을 되살릴 수 있게 만드는 장치는 **모델이 거의 쓰지 않아** 정확도 이득 없음 | 안전장치를 달아도 쓰이지 않으면 비용만 남는다 |
| 계획 | 약한 모델에는 정확도 보조장치, **강한 모델에는 비용 절감 수단**(정확도 변화는 미미) | 계획의 효용이 모델 강도에 따라 성격 자체를 바꾼다 |
| 액션 공간 | bash를 잘 쓰는 모델은 **bash만 주는 게 더 싸고 성능도 충분**. bash가 약한 모델만 전용 도구의 덕을 본다 | 도구를 정성껏 많이 정의해주는 게 항상 이득이 아니다 |

### ② 설계 자체를 자동 탐색에 맡긴다 (SoL-Pi)

사람이 176개 조합을 손으로 돌리는 대신, **하네스 개선을 탐색 문제로 놓는다.** 점점 더 많고 다양한 환경에서 하네스 롤아웃을 돌리고, 그 환경을 벗어나서도 전이되는 개선만 남긴다(재귀적 자기개선의 한 형태 — 모델이 아니라 **모델을 감싸는 층**을 개선한다).

선택을 통과해 살아남은 메커니즘은 **넷**이다.

1. **액션 실행** — 행동을 어떤 단위로 묶어 실행하는가
2. **컨텍스트 압축** — 언제 무엇을 줄이는가
3. **관찰 처리(observation handling)** — 도구가 뱉은 출력을 컨텍스트에 어떻게 얹는가
4. **읽기 위임(delegated reading)** — 긴 파일·로그를 메인 에이전트가 직접 읽지 않고 **보조 에이전트에게 읽혀 요약만 받는다**

결과: 51개 과제 EdgeBench에서 GPT-5.6 Sol·Opus 5 기준으로 기존 Pi와 **비슷한 성능**을 내면서, 기록된 토큰 트래픽 **44.7~49.0% 감소**, API 비용 약 **1/3**. 저자 추정 시간당 절감액은 네이티브 Codex/Claude 하네스 대비 **$8.75~$13.50**(Pi 대비 $4.36~$5.71).

### 두 논문을 겹쳐 보면

①의 결론 2번("생략을 요약 앞에")과 ②의 메커니즘 3·4번(관찰 처리·읽기 위임)은 **같은 원리의 다른 표현**이다 — *컨텍스트에 들어가는 토큰의 양을, 들어가기 전에 줄여라.* ①은 그 원리를 사람이 측정해 확인했고, ②는 자동 탐색이 독립적으로 재발견했다. 서로 다른 방법으로 같은 결론에 닿았다는 점이 이 결론의 신뢰도를 올린다.

## 실제로 쓸 수 있나

**쓸 수 있다.** 세 가지는 오늘 바로 흉내낼 수 있다.

- **로그를 밀어넣기 전에 친다.** 긴 빌드 로그·테스트 출력을 에이전트에 통째로 주는 대신 `grep`/`tail`로 먼저 줄이는 것 — 이게 정확히 "규칙 기반 생략을 요약 앞에 두는 것"이다. 가장 싼 개선.
- **읽기를 위임한다.** 큰 파일 탐색이나 로그 분석은 서브에이전트에 내보내고 메인 세션에는 결론만 남긴다. 메인 컨텍스트에는 *결정*만, *탐색*은 바깥에.
- **도구를 줄여본다.** MCP 서버나 커스텀 툴을 붙이기 전에 "이게 bash 한 줄로 되는 일인가"를 먼저 묻는다. 모델이 셸을 다룰 줄 알면 터미널 하나가 더 싸고 잘 된다.

계획 지시("먼저 계획을 세워라")는 성격을 알고 쓰면 된다 — 강한 모델에서는 정확도를 올리는 게 아니라 **헛짓을 줄여 비용을 내리는** 장치다.

## 한계와 미검증 지점

- **벤치마크가 좁다.** SWE-Bench Verified·Terminal-Bench 2.1·EdgeBench는 모두 **단일 저장소·단일 과제** 성격이다. 여러 서비스에 걸친 작업, 며칠 이어지는 세션, 사람이 중간에 끼어드는 상황은 측정 범위 밖이다.
- **"bash만 주면 된다"에는 전제가 있다.** 샌드박스가 안전하다는 전제. 프로덕션 자격증명이 섞이는 순간 액션 공간을 좁히는 이유가 성능이 아니라 **안전**이 되고, 논문의 비용 논리는 적용되지 않는다.
- **SoL-Pi는 정확도를 올리지 못했다.** "성능은 비슷, 비용만 절감"은 뒤집으면 **정확도 상한은 여전히 모델이 정한다**는 뜻이다. 하네스로 살 수 있는 것은 (지금까지는) 돈이지 능력이 아니다.
- **자동 탐색의 결과는 탐색 환경에 묶인다.** EdgeBench 51개 과제에서 살아남은 메커니즘이 내 도메인에서도 살아남는다는 보장은 없다.
- **금액 추정치는 스냅샷이다.** 시간당 $8.75~$13.50은 그 시점 API 가격표에 의존한다. 벤치마크 점수처럼 인용하면 안 된다.
- **미검증:** 두 논문 모두 하네스 부품 간 **상호작용**은 거의 다루지 않는다. "컨텍스트 관리 + 계획"을 같이 켰을 때 이득이 더해지는지 상쇄되는지는 176개 조합의 표에 부분적으로만 답이 있다.

# AI - 추론 길이 압축

> 상위: [[AI 심층 정리 인덱스]]

## 한 줄 정의

**추론 길이 자체를 학습 대상으로 삼아, 같은 품질의 답을 더 짧게 생각해서 내도록 모델을 추가 학습하는 것** — 모델을 작게 만들거나(양자화) 캐시를 줄이는(KV 압축) 대신, **생성되는 토큰 수를 줄여** 값을 깎는 방향이다. 계기는 Fireworks Research의 Ember-1(Kimi K3 기반, 토큰 약 40% 절감, 2026-09-28 공개).

## 왜 이게 문제였나 — 기존 방식의 한계

### 추론 모델은 출력 토큰의 90% 이상을 답이 아닌 것에 쓴다

추론 모델(reasoning model)은 답을 내기 전에 긴 사고 과정을 생성한다. Fireworks의 출발점은 관찰 하나다 — 생성 토큰의 **90% 이상이 답이 아니라 '생각'**이고, 그 생각의 길이가 **과제가 요구하는 것보다 훨씬 길다.** 쉬운 질문에도 어려운 질문과 비슷한 분량을 쓴다는 뜻이다.

### 멀티턴에서 이게 제곱으로 불어난다

여기가 이 노트의 핵심 논증이다. 에이전트 워크로드는 한 번의 질문-답이 아니라 도구를 호출하고 결과를 보고 다시 판단하는 **멀티턴**이다. 그런데 매 턴마다 **이전 추론 전체가 다시 모델 입력으로 들어간다.**

```
1턴:  프롬프트 + 추론1                     → 입력 L
2턴:  프롬프트 + 추론1 + 결과1 + 추론2       → 입력 2L
3턴:  프롬프트 + 추론1 + 결과1 + 추론2 + ... → 입력 3L
...
n턴까지의 누적 입력 ≈ L + 2L + 3L + ... + nL = O(n²L)
```

턴당 입력이 선형으로 늘고, 그것을 n턴 누적하면 **총 과금 토큰이 턴 수의 제곱**에 가까워진다. 그래서 **1턴의 장황한 추론 한 덩어리가 이후 모든 호출에서 다시 읽히고 다시 과금된다.** 첫 턴에서 아낀 토큰의 가치가 뒤로 갈수록 커진다는 뜻이기도 하다.

### 기존 대응들이 왜 부족했나

| 방향 | 무엇을 줄이나 | 한계 |
| --- | --- | --- |
| 싼 모델로 내려가기 | 토큰 **단가** | 품질이 함께 떨어진다. 등급을 내리는 결정 |
| reasoning effort 낮추기 | 추론 **분량** | 분량과 품질이 같이 떨어진다. 자기 점검까지 잘려나간다 |
| 프롬프트 캐싱 | 반복 입력의 **단가** | 캐시 읽기도 과금되고, 추론이 매 턴 새로 붙으면 캐시 적중 구간 밖이 계속 늘어난다 |
| KV 캐시 압축 | **메모리** | 서빙 측 비용이지 사용자 청구서의 토큰 수가 아니다 (같은 폴더의 KV 캐시 압축 노트 참고) |

공통점 — 네 방향 모두 **"얼마나 많이 생성할 것인가"를 건드리지 않는다.** reasoning effort만이 분량을 건드리는데, 그건 노브를 돌리는 것이라 필요한 사고와 헛도는 사고를 구분하지 못한다.

## 어떻게 푸는가

### 발상 — 노브를 돌리는 대신 짧게 생각하도록 학습시킨다

핵심은 **추론 길이를 추론 시점의 설정값이 아니라 학습 시점의 목표로 옮긴 것**이다. "적당히 짧게 써라"라고 시키는 게 아니라, 짧게 쓰고도 맞히는 쪽에 보상이 가도록 학습한다.

비유하면 — 시험에서 "풀이를 3줄 이내로 쓰라"고 제한하면(reasoning effort) 꼭 필요한 단계도 잘려 오답이 난다. 대신 **같은 정답에 대해 짧은 풀이를 쓴 답안을 계속 고점 처리하며 훈련시키면**, 학생은 어떤 단계가 결과를 바꾸고 어떤 단계가 그냥 되짚기인지를 스스로 구분하게 된다. Ember-1이 한 쪽은 후자다.

### 무엇을 남기고 무엇을 줄였나

원문이 명시하는 구분이 이 부분이다.

- **남긴 것** — 실수를 되짚는 **자기 점검(self-reflection)**. 이게 잘리면 정답률이 떨어지므로 보존 대상이다
- **줄인 것** — 불필요한 반복과 **헛도는 루프**. 같은 결론을 다른 말로 여러 번 확인하거나, 이미 배제한 가지로 되돌아가는 구간

### 무엇으로 신호를 받았나

원문이 말하는 학습 신호는 두 가지다 — **과제 피드백(task feedback)**과 **환경 피드백(environment feedback)**. 즉 "사람이 짧은 답안을 채점했다"가 아니라, **실행 결과가 맞았는지/도구 호출이 성공했는지**로 보상을 받는 구조로 읽힌다. 학습 도메인은 수학·코딩·지시 따르기·대화·검색·도구 사용·소프트웨어 엔지니어링으로 넓게 깔았고, 원문은 "on-policy planning and learning의 균형"이라는 표현을 쓴다.

**단, 원문은 방법을 명시하지 않는다.** "학습 실험 50회 이상, 평가 200회 이상을 거치며 새 학습 알고리즘을 개발했다"고만 쓴다. 강화학습 계열로 읽히지만 **확정할 수 없고, 이 노트에서 가장 비어 있는 칸이 여기다.**

### 결과 — 품질은 유지, 비용은 절감(방향은 일관되지 않음)

| 벤치마크 | K3 Max | Ember-1 | 비용 변화 |
| --- | --- | --- | --- |
| Terminal Bench 2.1 | 80.9% | **82.0%** | -51.9% |
| SWE-bench Verified | 93.2% | 92.2% | -15.5% |
| SWE-Interact | 21.3% | 20.0% | -32.5% |
| DeepSWE 1.1 | 66.4% | **75.2%** | -23.7% |
| τ-2 Bench Airline | 64% | **66%** | -5.9% |

읽는 법 — **절감 폭이 벤치마크마다 3배 이상 벌어진다**(-5.9% ~ -51.9%). 절감이 컸던 Terminal Bench에서는 점수가 **올랐고**, 절감이 작았던 SWE-bench에서는 점수가 살짝 **떨어졌다.** 이건 "추론이 원래 과하게 길었던 과제일수록 잘라낼 여지가 크다"는 가설과 맞는다. DeepSWE 1.1의 66.4% → 75.2%(+8.8점)는 절감을 넘어선 개선인데, 원문은 이유를 설명하지 않는다.

실제 고객 프로덕션 A/B에서는 **동등한 품질에 과제당 토큰 약 35% 감소**로 보고한다. Bedside Bench에서는 GPT-5.6 Sol·GPT-6 Astra·Claude Opus 5를 포함한 공개/비공개 모델 전체에 대해 새 파레토 프런티어를 세웠다고 주장한다.

## 실제로 쓸 수 있나

**모델로서는 아직 아니다.** 2주짜리 **리서치 프리뷰**다(Serverless, 커뮤니티 수요에 따라 상시화 여부 결정). 단가는 Kimi K3 구조를 그대로 쓴다($3/M 캐시 입력, $15/M 출력). 즉 **단가는 그대로고 절감은 전량 토큰 수에서 나온다** — 이 노트의 주제를 가격표가 그대로 보여준다.

**관점으로서는 지금 쓸 수 있다.** 이쪽이 더 중요하다.

- **청구서를 좌우하는 건 모델 등급이 아니라 `턴 수 × 추론 길이`다.** 등급을 내리기 전에 이 두 인자를 먼저 본다
- **제곱 증가 논증이 맞다면 긴 세션을 끊는 것이 모델 교체보다 효과가 클 수 있다.** 같은 작업을 30턴 한 세션 대 10턴 3세션으로 나눠 총 토큰을 재보면 바로 확인되는 가설이다. 도구 없이 지금 할 수 있는 실험
- **추론 길이도 튜닝 대상이라는 프레임.** 지금까지 튜닝 대상은 프롬프트·컨텍스트·도구 정의였는데, 여기에 "출력 분량"이 추가된다
- 같은 폴더의 코딩 에이전트 하네스 노트가 정리한 자동 탐색(SoL-Pi)이 토큰 44.7~49.0% 절감을 **하네스 설정만으로** 얻었다. Ember-1은 같은 절감 폭을 **모델 학습으로** 얻었다 — 같은 병목을 모델 밖과 모델 안에서 각각 공격한 두 사례고, 합쳐지면 어떻게 되는지는 **아무도 측정하지 않았다**

## 한계와 미검증 지점

- **학습 방법이 공개되지 않았다.** "새 학습 알고리즘"이라고만 쓰고 손실 함수·보상 설계·데이터 구성이 없다. 재현 불가능하고, 이 결과가 일반적인 기법인지 K3 특정 튜닝인지 판단할 근거가 없다
- **모든 수치가 자체 측정이다.** 벤치마크도 고객 A/B도 Fireworks가 돌렸다. 9월 22일·25일 뉴스 노트에 반복해 기록한 패턴 그대로다 — 제3자 재현 전까지는 "주장"이다
- **브리핑과 원문의 숫자가 어긋난다.** 오늘 아침 브리핑은 고객 A/B를 "점수 0.751 → 0.753, 추론 토큰 71% 감소"로 적었으나 원문이 강조하는 수치는 **약 35% 감소**다. 어느 고객의 어느 측정인지 원문에서 확인되지 않았다 — 인용 시 35%를 쓴다
- **"사내 개발자가 몰래 바꿔 붙여도 눈치채지 못했다"는 일화다.** 원문이 가장 강한 근거로 제시하는데 통제된 측정이 아니다. 블라인드 A/B로 설계하지 않은 이유도 설명되지 않는다
- **자기 점검을 어떻게 보존했는지가 비어 있다.** "자기 점검은 남기고 헛도는 루프만 줄였다"는 서술의 경계를 모델이 어떻게 판정하는지가 이 기법의 전부인데, 그 판정 기준이 없다. 헛돎과 신중함을 잘못 가르면 **긴 사고가 필요한 어려운 과제에서 조용히 무너질** 수 있고, SWE-bench Verified의 -1.0점이 그 신호일 가능성이 있다
- **단순한 과제에서의 손실이 측정되지 않았다.** 반대 방향의 위험 — 짧게 생각하도록 학습된 모델이 **정말 긴 추론이 필요한 소수 과제**를 놓치는지는 벤치마크 평균에 가려진다. 과제 난이도별 분해가 필요하다
- **에이전트 멀티턴에서의 실측이 표에 없다.** 제곱 증가라는 논증은 멀티턴에 대한 것인데, 제시된 표는 대부분 단일 과제 성공률이다. Terminal Bench 2.1(-51.9%)이 가장 에이전트적인 항목이고 절감도 가장 커서 논증과 맞지만, **턴 수와 절감 폭의 상관관계를 직접 보여준 그래프는 없다**
- **절감 폭이 벤치마크마다 3배 이상 갈리는 이유가 설명되지 않는다.** "추론이 과했던 과제일수록 여지가 크다"는 건 이 노트의 해석이고 원문의 주장이 아니다

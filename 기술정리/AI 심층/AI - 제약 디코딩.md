# AI - 제약 디코딩

> 상위: [[AI 심층 정리 인덱스]]

> 계기: Ubicloud 블로그 *Fixing tool-call accuracy in vLLM* (10/27 브리핑) — vLLM에서 Kimi K2.6 도구 호출 스키마 정확도가 92%였는데, 제약 디코딩을 켜자 100%. 원인은 "요청에서 켜지 않으면 꺼짐"으로 바뀐 기본값. 배경 원리는 XGrammar-2 논문(arXiv 2601.04426)으로 보충.

## 한 줄 정의

LLM이 다음 토큰을 고를 때마다, **지금까지의 출력에 이어 붙였을 때 문법(JSON 스키마·도구 호출 형식)을 깨지 않는 토큰만 남기고** 나머지 로짓을 −∞로 가려(마스크) 그 안에서만 샘플링하게 하는 방법. 형식을 "부탁하고 나중에 검사"하는 대신 "**생성하는 순간에 강제**"한다.

## 왜 이게 문제였나 — 기존 방식의 한계

**1. 프롬프트 + 사후 검증은 확률적이다.** 도구 스키마를 시스템 프롬프트에 넣고 모델이 맞춰 주길 기대하는 방식은 대부분 맞지만 가끔 틀린다. Ubicloud 사례에서 틀리는 모양은 의미 있는 패턴이다 — 도구 이름이 `web_search`인데 학습 데이터에 흔한 `search_web`을 부르고, 필드가 `location`인데 `city_name`을 넣는다. 모델이 **이번 요청의 스키마보다 학습 분포의 습관**을 따를 때 생긴다. 사후 검증은 이걸 잡을 수는 있어도 고칠 수는 없다 — 재시도해야 하고, 에이전트 루프에서는 실패 응답·에러 메시지가 컨텍스트에 남아 이후 턴 품질까지 떨어뜨린다. 92%는 "25번에 2번"이고, 10턴짜리 에이전트 작업이면 한 번 이상 실패할 확률이 절반을 넘는다(1 − 0.92¹⁰ ≈ 57%, 노트 계산·턴 간 독립 가정).

**2. 순진한 강제는 느리다.** "허용되는 토큰만 남긴다"는 아이디어 자체는 단순하지만, 어휘가 10만~20만 토큰이다. 매 스텝마다 모든 토큰에 대해 "이걸 붙이면 아직 문법상 유효한가"를 검사하면 디코딩 한 번보다 마스크 계산이 더 오래 걸린다. 게다가 토큰은 문법 단위와 경계가 맞지 않는다 — `"loc`, `ation"` 처럼 하나의 JSON 키가 여러 토큰에 걸치고, 한 토큰이 `":"` 처럼 여러 문법 기호를 품기도 한다.

**3. 에이전트 워크로드는 문법이 매번 바뀐다.** XGrammar-2 논문이 짚는 지점이다. 요청마다 붙는 도구 목록이 달라 문법 전체가 반복되는 일이 드물고(요청 간 변동), 한 응답 안에서도 앞서 고른 도구 이름이 뒤따를 인자 스키마를 결정한다(요청 내 변동). 문법을 미리 컴파일해 두는 기존 엔진 설계는 첫 토큰 지연(TTFT)을 키운다.

## 어떻게 푸는가

### 기본 구조 — 문법을 상태 기계로, 토큰을 그 위의 이동으로

JSON 스키마나 도구 호출 형식을 **문법(grammar)**으로 바꾸고, 그 문법을 읽는 **파서 상태**를 들고 다닌다. 매 스텝은 이렇게 돈다.

1. 현재 파서 상태에서 "다음에 올 수 있는 문자열"이 정해진다 (예: 객체 시작 직후라면 `"` 또는 `}`).
2. 어휘의 각 토큰에 대해 "이 토큰을 붙여도 파서가 거부하지 않는가"를 판정해 비트마스크를 만든다.
3. 모델이 낸 로짓에 마스크를 곱해(허용 안 되는 토큰은 확률 0) 샘플링한다.
4. 뽑힌 토큰으로 파서 상태를 전진시킨다.

비유하면 **철도 분기기**다. 기차(모델)는 여전히 스스로 속도와 방향을 고르지만, 선로(문법)가 깔린 곳으로만 갈 수 있다. 어느 선로로 갈지는 모델이 고른다 — 그래서 값(어떤 도시인지)은 모델의 판단이고, 모양(`location` 키에 문자열)은 문법이 보장한다.

### 속도 문제를 푸는 법 — 미리 계산할 수 있는 것과 없는 것을 나눈다

XGrammar(1세대)의 핵심 관찰은 **대부분의 토큰은 파서의 '현재 위치'만 보면 허용 여부가 정해진다**는 것이다. 예를 들어 JSON 문자열 안쪽이라면 `abc` 같은 토큰은 스택이 어떻든 항상 허용, `}`는 항상 거부다. XGrammar-2 논문의 정리로는:

- 파서(1세대는 푸시다운 오토마톤, 즉 괄호 중첩을 스택으로 기억하는 상태 기계)의 상태마다 토큰을 **수락 / 거부 / 문맥 의존** 세 무리로 미리 분류해 둔다(적응형 토큰 마스크 캐시).
- 생성 중에는 문맥 의존 무리만 전체 문맥(스택)을 보고 실시간 검사한다. 이 무리가 작을수록 빠르다 — 그래서 문맥을 조금 더 넓혀 보고 미리 분류할 수 있는 토큰을 늘리는 "문맥 확장"을 한다.

Spring으로 빗대면 **정적 검증과 동적 검증의 분리**다. `@NotNull`·`@Pattern`처럼 값 하나만 보면 되는 검사는 미리 정해 두고, "이 주문의 재고가 남았나"처럼 DB 상태를 봐야 하는 검사만 요청 시점에 돈다. 동적 검사 대상이 적을수록 요청이 빠르다.

### 에이전트용으로 바꾼 것 — XGrammar-2

| 기법 | 하는 일 | 논문 수치 |
| --- | --- | --- |
| TagDispatch | 자유 텍스트를 흘리다가 등록된 태그(예: 도구 호출 시작 표식)가 나오면 그 태그의 하위 문법으로 전환. 태그는 Aho–Corasick 자동자로 온라인 매칭 | 태그 100개: 일반 EBNF 컴파일 약 15.5초 → 약 2.0초 |
| 교차 문법 캐시 | 문법 전체는 매번 달라도 **부분 구조**(같은 도구의 인자 스키마 등)는 반복된다 → 상태 기계를 계층 해시해 공통 부분의 마스크를 재사용, LRU 축출 | 문법 전체 재사용 0%인데 부분 구조 재사용 25.2%(도구 10개) → 95.6%(도구 500개) |
| JIT 컴파일 | 마스크 캐시를 필요할 때 계산, prefill·디코딩과 겹쳐 실행 | 전처리 4,960ms → 612ms(8.1배↓), 대신 마스크당 시간 45.5µs → 722µs |
| 반복 상태 압축 | `minItems`/`maxItems` 같은 큰 반복 범위에서 상태 수 폭증 방지 | 전처리 534.80ms → 5.37ms |
| Earley 파서 기반 캐시 | 푸시다운 오토마톤 대신 Earley 파서, 비결정적 문법에 강함 | — |

종합 주장: 도구 호출 컴파일이 기존 엔진 대비 6배+ 빠르고, BFCL-v3(SGLang)에서 종단 지연이 **비제약 디코딩의 6% 이내**, 제약을 걸면 테스트한 모델 전부 스키마 유효율 100%(제약 없을 때 Llama 1B~70B가 22~67%).

### vLLM에서는

Kimi K2.6의 structural tag 정의는 `시작 표식(함수 이름) → 호출 인덱스(정규식 \d+) → 인자 시작 상수 → 도구 파라미터에서 만든 JSON 스키마(키 순서 자유·공백 수 상한 옵션) → 끝 표식`의 경로다. 단계별 마스크를 미리 계산해 GPU에서 적용한다. 0.31부터 서버 측 플래그, 이후 `--tool-strict-level`(PR 56268)로 배포 단위 엄격도 조절.

## 실제로 쓸 수 있나

**쓸 수 있고, 이미 쓰고 있을 가능성이 크다.** OpenAI·Anthropic 등 상용 API의 "구조화 출력 / strict 스키마" 옵션이 같은 계열이다(내부 구현은 비공개). 직접 서빙(vLLM·SGLang·llama.cpp의 grammar)이라면 옵션 하나로 켤 수 있다. 판단 기준:

- **켜는 게 맞는 곳**: 도구 호출 인자, 분류 라벨(enum), 추출 결과를 DB에 바로 넣는 파이프라인 — 형식 실패가 곧 장애인 곳. Java 쪽에서는 Jackson 역직렬화 실패·`@Valid` 400을 재시도 루프로 감싸던 코드가 줄어든다.
- **주의할 곳**: 긴 추론이 필요한 답을 처음부터 엄격한 JSON에 가두는 경우. 2024년 "Let Me Speak Freely?" 연구는 형식 제약이 추론 과제 성능을 떨어뜨릴 수 있다고 보고했다(반론도 있다). 흔한 절충은 **자유 텍스트로 생각하고 마지막 구조만 제약**하는 것 — XGrammar-2의 TagDispatch가 바로 그 모양이다.
- **업그레이드 체크리스트**: 엔진 버전을 올렸더니 "모델은 같은데 정확도가 떨어졌다"면 기본값 변경부터 의심. Ubicloud도 자체 포크에서 upstream으로 옮기며 91%로 내려갔다. 배포 전 도구 호출 벤치마크(여기선 K2VV ToolCall 2,000건)를 게이트로 두는 게 발견의 계기였다.

**보장하지 않는 것**을 분명히 해 두자. 제약 디코딩이 보장하는 건 **모양**이다. *어떤 도구를 부를지*, *인자 값이 맞는지*, *그 호출이 안전한지*는 보장하지 않는다. 같은 날 Cohere 사례(추론은 "호출 안 함"이라 쓰고 외부 버킷에 PUT)는 형식상 완벽히 유효한 curl 호출이었다. 형식 강제는 생성 시점에, 의도 통제는 실행 시점(도구 화이트리스트·egress 차단)에 — 층이 다르다.

## 한계와 미검증 지점

- **Ubicloud 글의 오버헤드 "무시할 수준"은 측정값이 없다.** 실행 횟수도 없다. 오버헤드 수치는 XGrammar-2 논문 쪽(엔진 비교 벤치)이고 Kimi K2.6·vLLM 환경과 같은 조건이 아니다.
- **100%는 스키마 일치 기준.** 글이 정의한 다른 지표(호출 여부가 Moonshot 서비스와 일치하는가, trigger similarity)의 결과는 강조되지 않았다. 형식이 맞아도 *부르지 말아야 할 때 부르는* 오류는 남을 수 있다.
- **문법 변환 버그는 조용히 실패한다.** vLLM이 기본을 끈 이유 중 하나가 "제약이 조용히 빠지는" 변환 버그였다(PR 45600·이슈 58930). 켰다고 믿는 것과 실제로 걸려 있는 것은 다를 수 있다 — 스키마를 일부러 어기는 테스트 케이스로 확인해야 한다(노트의 권고).
- **투기적 디코딩과의 충돌**(이슈 44006·55152) — 초안 모델이 낸 토큰을 마스크가 잘못 거부. 속도 최적화끼리 겹칠 때의 상호작용은 조합마다 따로 검증해야 한다.
- **JIT의 대가**: 전처리는 8배 줄지만 마스크당 시간은 16배 늘었다. 짧은 응답·많은 도구(에이전트)에는 이득, 긴 구조 출력 하나에는 손해일 수 있다 — 논문은 조절 파라미터 K를 둔다.
- **품질 영향**: 마스크는 확률 분포를 잘라 낸다. 모델이 원래 `search_web`에 높은 확률을 줬다면, 마스크 후 남은 `web_search`의 확률은 재정규화된 값이다. 대부분 맞는 방향이지만, 모델이 스키마에 없는 걸 하고 싶어 했다는 **신호 자체가 지워진다**(노트의 해석). 디버깅 시엔 제약 없이 한 번 돌려 보는 게 정보가 된다.
- XGrammar-1의 세부(스택 구현·GPU 겹치기 등)는 이번에 1세대 논문을 직접 읽지 않아 2세대 논문의 요약 범위만 적었다.

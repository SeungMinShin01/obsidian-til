# AI - MoE 전문가 오프로딩

> 상위: [[AI 심층 정리 인덱스]]

> 계기: Strata(Qwen3.8-Flash-Next 125B를 12GB GPU에서 실행하는 전용 추론 엔진, HN 2위 685점) — 2026-10-06 브리핑. 같은 날 Reflection Beam(501B/활성 23B) 발표.
> 읽은 범위: Strata README, Qwen3.8-Flash-Next 모델 카드, dev.to 해설, carteakey 「The Rise of Overfit Inference Engines」, note.com 사용자 테스트, Reflection Beam 블로그. **Strata의 캐시 정책·적중률은 README에 수치가 없어, 아래 동작 설명 중 일부는 공개 정보로부터의 추론이다(추론인 곳은 표시).**

## 한 줄 정의

MoE 모델에서 토큰마다 실제로 쓰이는 전문가는 일부뿐이라는 점을 이용해, **자주 쓰이는 전문가만 GPU 메모리에 캐시하고 나머지는 시스템 RAM·SSD에 두었다가 필요할 때 가져오는** 추론 방식. "모델 전체 크기"가 아니라 "자주 쓰이는 부분의 크기"만큼의 VRAM으로 큰 모델을 돌린다.

## 왜 이게 문제였나 (기존 방식의 한계)

**1. MoE는 연산을 줄였지만 메모리는 줄이지 않았다.** 밀집(dense) 모델은 토큰 하나를 만들 때 모든 가중치를 쓴다. MoE는 층마다 라우터가 전문가 몇 개만 고른다. Qwen3.8-Flash-Next는 층당 전문가 512개 중 10개(+공유 1개)를 쓰므로, 총 1,250억 중 토큰당 약 60억만 계산한다. 그런데 **다음 토큰이 어떤 전문가를 고를지 미리 모른다.** 그래서 서버에서는 전체 가중치를 GPU에 올려 두는 것이 기본이었다. 연산량은 60억짜리인데 메모리는 1,250억짜리를 요구하는 셈이다.

**2. 양자화만으로는 모자랐다.** 1,250억 파라미터는 원본 약 350GB다. 2비트대 양자화(Q2_0 등)로 30GB대까지 줄여도 12GB GPU에는 들어가지 않는다.

**3. 기존 오프로딩은 "어디서 계산하나"의 문제였다.** llama.cpp 같은 범용 런타임에도 전문가 텐서를 CPU RAM에 두는 옵션이 있다. 이때 그 전문가는 보통 **CPU가 계산**한다. GPU로 옮기는 PCIe 비용은 피하지만, CPU의 행렬 연산은 GPU보다 훨씬 느리다. carteakey의 비교(RTX 4070 12GB, 같은 모델)에서 일곱 단계 튜닝한 llama.cpp가 27 tok/s, Strata가 53 tok/s였다.

비유하면 이렇다. 밀집 모델은 요리마다 주방의 모든 도구를 쓰는 셰프다. MoE는 요리마다 도구 몇 개만 쓰지만, 무엇을 쓸지 주문이 들어와야 안다. 그래서 지금까지는 모든 도구를 조리대(VRAM) 위에 펼쳐 둬야 했다. 오프로딩은 **자주 쓰는 도구만 조리대에, 나머지는 찬장(RAM)에, 거의 안 쓰는 큰 사전은 창고(SSD)에** 두는 주방이다. Strata README의 비유도 같다.

## 어떻게 푸는가

### 구조 — 무엇을 어디에 두나

Qwen3.8-Flash-Next의 구성(모델 카드):
- 48층. 층 배치는 `12 × (3 × (Gated DeltaNet → MoE) → 1 × (Qwen Sparse Attention → MoE))`. 네 층 중 셋은 선형 어텐션(Gated DeltaNet), 하나는 희소 어텐션이다.
- 층당 전문가 512개(중간 차원 640의 작은 전문가), 토큰당 라우팅 10개 + 공유 1개. 전체 전문가 수는 512 × 48 = **24,576개**.
- **N-gram 임베딩 510억 파라미터**가 별도로 있다.
- MTP(다중 토큰 예측) 층 1개, 40억 파라미터.

Strata의 3계층(README):

| 계층 | 크기 | 담는 것 | 접근 방식 |
| --- | --- | --- | --- |
| GPU VRAM | 12~24GB | 가장 자주 쓰이는 전문가 수천 개 + (추론) 어텐션·공유 전문가·라우터 | 매 토큰 |
| 시스템 RAM | 32~96GB | 전문가 전체 | VRAM에 없을 때 PCIe로 전송 |
| SSD | ~80GB | "큰 룩업 테이블" | 행 단위 조회 |

**SSD의 룩업 테이블은 N-gram 임베딩으로 추정한다(추론).** 이유는 접근 패턴이다. 전문가는 행렬 전체를 곱해야 하니 통째로 읽어야 한다. 반면 임베딩은 "이 토큰 조합에 해당하는 행 하나"만 읽는다. 510억 파라미터짜리 표라도 토큰당 읽는 양은 몇 KB다. NVMe의 랜덤 읽기로 충분하다. 계산이 아니라 **조회**인 파라미터는 가장 느린 계층에 둬도 된다는 것이 이 설계의 요점이다. 이전 노트 「단계 분리 양자화」에서 prefill용 가중치를 SSD에서 스트리밍한 것(ODP)과 같은 계열의 발상이다.

### 동작 — 생성과 프롬프트 처리가 다른 이유

**생성(decode)은 캐시 적중률 싸움이다.** 토큰을 하나씩 만들고, 토큰마다 48층 × 10개 전문가가 필요하다. VRAM에 있으면 GPU 메모리 대역폭(수백 GB/s)으로 읽는다. 없으면 PCIe(4.0 x16 이론치 약 31.5GB/s, 5.0은 그 두 배)로 RAM에서 가져온다. 대역폭 차이가 10배 이상이므로, **적중률이 조금만 떨어져도 속도가 크게 떨어진다.**

같은 GPU에서 Q2_0(94 tok/s)이 IQ3_S(53 tok/s)보다 1.8배 빠른 이유도 여기서 나온다. 비트 수가 낮으면 전문가 하나의 크기가 작아지고, 같은 VRAM에 더 많은 전문가가 들어가며, 적중률이 오른다. 계산량 차이보다 **캐시에 들어가는 개수 차이**가 크다(dev.to 해설도 속도 차이를 캐시 미스로 설명한다).

대략의 규모를 어림해 보면(추론, 근사치):
- 활성 60억 파라미터를 2비트대로 읽으면 토큰당 약 1.5~2GB다.
- 전부 PCIe로 가져온다면 5.0 x16(약 63GB/s)에서도 토큰당 25~30ms, 즉 **30~40 tok/s가 상한**이다.
- 실측 94 tok/s는 이 상한의 2배를 넘는다. 따라서 대부분이 VRAM에서 적중하고 있고, 투기적 디코딩이 그 위에 곱해진다고 봐야 숫자가 맞는다.

**프롬프트 처리(prefill)는 전송을 나눠 낸다.** Strata는 최대 8,192토큰을 한 번에 읽는다. 토큰 수천 개가 같이 지나가면 거의 모든 전문가가 적어도 한 번 불린다. 전문가 하나를 PCIe로 한 번 가져오면 그 덩어리의 모든 토큰이 그걸 쓴다. 전송 비용이 수천 토큰에 나뉘니 처리량이 생성의 20~30배(1,620~2,650 tok/s)로 나온다. 같은 하드웨어에서 생성과 prefill의 병목이 다르다는 점도 「단계 분리 양자화」 노트와 같은 구도다(prefill은 연산 병목, decode는 대역폭 병목).

**투기적 디코딩은 한 번 가져온 전문가를 여러 토큰에 쓰게 한다.** 작은 예측기가 다음 몇 토큰을 미리 맞히고, 큰 모델이 그 토큰들을 **한 번의 순전파로 같이 검증**한다. 맞힌 만큼 큰 모델 호출이 줄어 1.6~1.8배 빨라진다. 이 모델에는 MTP 층이 붙어 있고, 사용자 테스트에서 Strata가 첫 실행 때 "MTP 데이터(약 5.2GB)"를 받았으므로 예측기는 이 MTP 층으로 보인다. 오프로딩 구조에서 이 기법이 특히 잘 맞는 이유가 있다(추론). 검증할 토큰 k개는 미니 prefill이다. 전문가를 한 번 가져와 k개 토큰에 같이 쓰니 전송 비용이 나뉜다. 대가도 있다. 토큰마다 고르는 전문가가 다르면 k개의 **합집합**만큼 전문가가 필요해 캐시 압박이 커진다. 1.6~1.8배가 이 두 효과의 순이익이다.

### 한 장 요약

```
토큰 1개 생성
 ├─ 임베딩 조회 ── SSD(N-gram 표, 행 몇 개)          ← 조회는 느린 곳에
 ├─ 48층 × [어텐션(VRAM 상주) → 라우터 → 전문가 10+1]
 │            └─ 전문가: VRAM 캐시 적중? ─ 예 → GPU가 바로 계산
 │                                       └ 아니오 → RAM에서 PCIe 전송 후 계산
 └─ MTP가 다음 몇 토큰 예측 → 다음 순전파에서 같이 검증   ← 전송 비용을 여러 토큰에 나눔
```

## 실제로 쓸 수 있나

- **개인 개발 도구로는 쓸 수 있다.** 12GB GPU + 64GB RAM + NVMe 80GB면 된다. OpenAI·Anthropic 호환 엔드포인트라 기존 클라이언트를 그대로 붙인다. 밖으로 보내면 안 되는 코드·문서로 실험하거나, API 요금 없이 반복 실험할 때 의미가 크다.
- **요청을 받는 서버로는 아직 안 된다.** 이유는 구조에서 나온다. 동시 요청이 여러 개면 서로 다른 전문가를 요구해 캐시가 서로를 밀어낸다. README가 "12GB 카드에서는 병렬 배치가 오히려 느리다"고 적은 것이 이 현상이다(추론). 첫 로딩 1~3분, 첫 긴 프롬프트 3만 토큰당 약 1분이라는 **콜드 스타트**도 서버 기준에 맞지 않는다.
- **모든 MoE에 통하지는 않는다.** 이 방식은 "자주 쓰이는 전문가"가 따로 있어야 캐시가 효과를 낸다. Reflection Beam은 전문가 부하 비율 1.04배(거의 균등 사용)를 장점으로 내세웠다. 서버 학습·서빙에는 좋은 성질이지만, 캐시할 대상이 잘 안 생기므로 오프로딩에는 불리할 수 있다(추론). 활성 230억(약 4배)이라 토큰당 옮길 양도 크다.
- **엔진에 묶이지 않는다.** 전용 엔진은 모델 구조가 바뀌면 같이 버려진다(carteakey는 6개 중 4개 이상이 2027년 4월까지 60일 넘게 멈출 것이라 예측). 클라이언트는 표준 API에만 의존하게 짜고, 엔진은 갈아 끼울 부품으로 둔다.

## 한계와 미검증 지점

1. **캐시 정책과 적중률이 공개되지 않았다.** "가장 자주 쓰이는 전문가"를 무엇으로 정하는지(사전 프로파일링인가, 실행 중 LRU인가), 적중률이 몇 %인지 README에 없다. 위의 동작 설명은 공개 수치에 맞춘 추론이다.
2. **품질 비교가 없다.** 2비트대 양자화가 긴 컨텍스트 정확도·희귀 토큰·추론 정확성을 얼마나 깎는지 A/B가 없다. 처리량은 그리디 디코딩 기준이다(carteakey 스스로 인정).
3. **작업 종류에 따라 속도가 달라질 수 있다.** 적중률은 라우팅 분포에 달렸고, 라우팅 분포는 입력에 달렸다. 코드·영어 대화에서 잰 속도가 한국어·전문 분야 문서에서도 나온다는 보장이 없다. Coder 변종이 "CJK 텍스트에 약하다"는 README 언급도 같은 문제를 품질 쪽에서 보여 준다(추론).
4. **SSD 룩업 테이블의 정체는 추정이다.** README에 "큰 룩업 테이블"이라고만 있다. N-gram 임베딩이라는 해석은 모델 카드 구성과 접근 패턴으로부터의 추론이다.
5. **README와 브리핑 수치가 일부 다르다.** 브리핑의 "RTX 3090 100~140 tok/s"는 이번에 읽은 범위에서 확인하지 못했다. 브리핑 제목의 "RTX 4090"도 README 표에는 없다(표는 RTX 5070·RX 9070 XT).
6. **젊은 코드베이스.** 검토가 적은 네이티브 코드가 GPU 드라이버 위에서 돈다. 보안·안정성 검증이 없다.

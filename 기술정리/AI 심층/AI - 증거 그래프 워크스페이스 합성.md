# AI - 증거 그래프 워크스페이스 합성

> 상위: [[AI 심층 정리 인덱스]]

> 계기: *GraphForge: Training Working Agents with Graph-Anchored Workspace Synthesis* — Qisheng Su 외 12명 (USTC · Fudan · Shanghai Innovation Institute · Shanghai AI Lab), arXiv 2609.38923, HF ▲34 (2026-10-04 브리핑)
> 읽은 범위: HF 초록, arXiv 초록, alphaXiv 전문 추출(본문 1~6절·표 1~4). 부록(학습 설정·신뢰구간)은 읽지 않았다.

## 한 줄 정의

"파일을 읽고 도구를 써서 산출물을 만드는" 업무형 에이전트의 학습 데이터를, **실제 공개 파일로 만든 작업 공간** 위에서 **파일 간 관계 그래프(증거 그래프)**를 먼저 그린 뒤 그 그래프에서 과제와 채점 기준을 **같이** 뽑아 합성하는 방법. 채점 기준 하나하나가 "어느 파일의 어느 사실로 확인하라"는 닻(anchor)을 단다.

## 왜 이게 문제였나 (기존 방식의 한계)

코딩·터미널 에이전트는 학습 데이터를 만들기 쉽다. 테스트가 통과하는지(fail-to-pass)로 정답을 기계적으로 판정할 수 있기 때문이다. 업무형 에이전트는 다르다. "엔비디아 투자 분석 워크북을 만들어라" 같은 과제의 결과물은 엑셀·문서이고, 맞았는지 보려면 **원본 파일의 내용을 읽어야** 한다.

기존 파이프라인 둘이 각각 반쪽씩 실패했다.

| 방식 | 파일 | 검증 | 문제 |
| --- | --- | --- | --- |
| EnvCraft | 모델이 생성 | 작업 공간 상태를 보는 파이썬 스크립트 | 파일이 가짜라 현실감·다양성이 없고, 스크립트는 문서 **내용**을 못 읽어 오류를 놓친다 |
| NexForge | 실제 파일 | 과제별 채점 기준 **없음** | 결과 품질을 체계적으로 확인할 수 없다(합성 데이터 자체도 미공개) |
| **GraphForge** | 실제 파일 | 증거에 닻을 단 에이전트 판정관 | 규모는 2.1K 과제로 가장 작다 |

또 하나의 문제는 **다양성 붕괴**다. 모델에게 과제를 자유롭게 지어내라고 하면 흔한 직업·흔한 과제 유형(일반적인 "분석해 보라")으로 몰린다.

## 어떻게 푸는가

비유하면 **출제자가 시험지를 내기 전에 "근거 지도"부터 그리는 방식**이다. 자료집(실제 파일 묶음)을 먼저 모으고, "A 파일의 매출과 B 파일의 매출이 일치해야 한다", "C 파일은 작년 자료라 비교에만 쓴다" 같은 관계를 지도로 그린 다음, 그 지도에서 문제와 채점표를 동시에 뽑는다. 채점표의 각 항목에는 "이 항목은 지도의 F2·F1·F5 지점을 보고 채점하라"가 붙는다. 다섯 단계다.

### 1) 직업 씨앗 — 방향은 씨앗이, 내용은 파일이 정한다

미국 직업 데이터베이스 **O\*NET**에서 직업·업무 진술·세부 업무 활동(DWA)을 가져오고, 디지털로 수행 가능한 업무만 남긴다 → 246개 직업, 16개 부문, 891개 DWA 과제 유형, 3,419개 (직업, 과제 유형) 쌍.

씨앗 하나 = (직업, 과제 유형, 직업별 업무 요구, 지배적 실행 패턴 16종 중 하나, 예상 입력 파일 종류, 직업 근거 자료). 근거 자료로 뒷받침되지 않는 업무 요구는 "할당량을 채우려고 지어내지 않고 버린다."

다양성은 **한계 커버리지 탐욕 선택**으로 지킨다. 이미 뽑힌 씨앗 중 같은 값(같은 직업, 같은 패턴…)이 n개 있으면 그 차원의 점수는 1/(1+n). 네 차원 점수를 더해 가장 높은 후보를 고른다 — 이미 많이 뽑힌 값일수록 덜 뽑힌다. 파일을 실제로 내려받은 뒤에도 같은 규칙을 한 번 더 건다.

씨앗은 **사례 중립**이다. 회사·사건·데이터·결과를 지정하지 않는다("재무 분석가가 투자 의사결정을 위해 정량 모델링을 한다"까지만).

### 2) 실제 파일 작업 공간 — 숨은 역할 넷

검색 에이전트가 씨앗에 맞는 실제 공개 사례(예: 엔비디아)를 찾아 필요한 파일을 원래 형식 그대로 내려받는다. 각 파일에는 **에이전트에게는 보이지 않는** 역할이 붙는다.
- **core** — 주 계산·결정을 끄는 파일(2025 재무 보고서 XLSX)
- **supporting** — 정책·맥락(2024 연차 보고서)
- **confuser** — 그럴듯하지만 쓰면 안 되는 대안(같은 분야 다른 회사 자료)
- **ambient** — 현실적 중복·잡음

과제당 입력 파일은 평균 23.1개(중앙값 22), PDF가 궤적의 96.7%에 등장한다. 일부러 섞은 confuser가 **"사내 공유 폴더의 지저분함"**을 흉내 낸다.

### 3) 증거 그래프 → 과제 명세

그래프의 **노드** = (출처 파일, 그 파일이 주는 사실·필드, 과제에서의 역할). **엣지** = 해석·비교·대조·도출에 필요한 파일 간 의존. 저자들은 그래프를 "정답이 아니라 원본 파일에서 다시 확인 가능해야 하는 중간 표현"이라고 못 박는다.

그래프를 컴파일하면 과제 명세 = (자연어 과제문, 산출물 요구사항, **가점 기준**, **감점 기준**). 가점 기준 하나는 (대상 산출물, 요구, 기대 값·계산, 가중치, **증거 닻**(그래프 노드 집합), 검증 절차). 예: "FY2025 매출 130,497M 달러 — F2에서 읽고 F1·F5로 교차 확인."

핵심은 **실행과 검증의 분리**다. 일하는 에이전트는 과제문과 파일만 본다(노드 ID·숨은 역할은 못 봄). 판정관은 닻과 검증 절차를 받아 **어느 파일의 어디를 열어 볼지** 안다. 그래서 닻이 채점을 안내하면서도 풀이 절차가 과제문으로 새지 않는다.

### 4) 실행 조건부 한 번 수정

정적 검사로는 긴 과제의 모호함을 다 못 잡는다. 그래서 강한 교사 모델로 **한 번 돌려 본 뒤**, 수정 에이전트가 원본 파일·그래프·과제·채점표·실행 결과를 함께 보고 "자연스럽고 실행 가능한가, 필요한 수치가 파일로 뒷받침되나, 닻이 맞게 걸렸나, 검증 절차로 산출물을 확인할 수 있나"를 점검해 **바꿀 부분만** 돌려준다. 과제문이 그대로면(정규화 해시가 같으면) 첫 실행을 재사용하고, 채점표만 바뀌면 재실행 없이 새 채점표로 다시 판정한다 → 3,638개 과제 중 **81.6%가 첫 실행 재사용**. 비용 절약 장치다.

### 5) 산출물 단위 입학 심사

약속한 파일이 실제로 만들어졌는지(파일명·형식·필요한 시트와 수식)를 결정론적으로 검사한 뒤, 판정관이 원본 파일과 산출물을 열어 기준마다 채점한다. 점수 = (가점 가중치 × 충족 비율의 합 − 감점 강도 × 위반 정도의 합) ÷ 가점 가중치 합. 음수도 가능. **Q > 0.90**만 입학. 같은 도구 반복 호출·과도한 도구 사용·높은 도구 실패율·반복 절단 같은 퇴행 행동 궤적도 버린다.

결과: 2,169개 궤적(작업 공간 2,150개), 466개 과제 유형, 16개 부문 중 15개, 실행 패턴 16종 전부. 궤적 평균 50스텝·16.2만 토큰(1.3%는 학습 상한 262K에 닿음). 파이프라인 전 단계(수집·그래프·수정·교사·판정관)에 **GLM-5.2** 하나를 썼다.

### 결과

| 모델 (스캐폴드) | GDPVal Elo | Workspace-Bench-Lite | SpreadsheetBench II |
| --- | --- | --- | --- |
| Qwen3.6-27B 기반 | 1380.0 (OpenHands) | 56.0 (Claude Code) | 10.3 (Claude Code) |
| + SFT (GraphForge) | **1445.7 (+65.7)** | **63.7 (+7.7)** | **24.0 (+13.7)** |
| Qwen3.6-35B-A3B 기반 | 1260.6 | 55.9 | 2.8 |
| + SFT | 1362.3 (+101.7) | 59.7 (+3.8) | 19.3 (+16.5) |
| 참고: Claude Opus 5 | 1774.1 | 70.1 | 33.6 |
| 참고: GLM-5.3 (척도 기준점) | 1667.0 | 67.7 | 32.1 |

- GDPVal 값은 **Elo**다(GLM-5.3 OpenHands = 1667로 고정한 내부 Bradley–Terry 풀, 400점 차 = 10:1 승산). 그래서 "+65.7점"은 정확도 퍼센트가 아니라 **기반 모델 대비 기대 승률 약 59%에 해당하는 차이**다(65.7 Elo를 승률로 환산한 근사). 다만 기반 모델과 직접 맞붙인 승률은 **0.725**(152승 15무 53패)로 더 높게 나왔다 — 풀 전체 적합과 직접 비교가 다른 값을 낸다. 220개 과제 GDPVal-AA 금 표본 기준
- 궤적은 전부 **Codex 스캐폴드**로 수집했는데 OpenHands·Claude Code에서도 다 올랐다 → 특정 하네스 습관이 아니라 업무 능력이 옮겨졌다는 해석
- 거부 파인튜닝(RFT): SFT 모델이 새 질의 2,000개에 4번씩 풀게 하고, 판정관 점수 0.95 초과 최고 궤적만 462개로 재학습. **닻 있는 판정관 / 닻 없는 판정관 / 4개 중 무작위** 세 갈래를 같은 후보 풀에서 비교 → Workspace·Spreadsheet에서는 닻 있는 쪽이 가장 좋고 무작위가 가장 나쁨. **GDPVal에서는 오히려 닻 없는 쪽이 점추정 더 높음**(+34.1 대 +7.2), 저자도 "이 규모에선 통계적으로 구분 안 됨"이라고 인정

## 실제로 쓸 수 있나

- **데이터·모델 공개**(groundhogLLM 컬렉션). 작업 공간 파일은 재배포하지 않고 출처 링크만 준다
- 직접 쓸 지점은 모델보다 **설계 패턴**이다. 사내 RAG나 문서 처리 에이전트의 평가셋을 만들 때 그대로 옮길 수 있다:
  1. 실제 사내 문서 묶음을 모으고 일부러 **헷갈리는 문서(confuser)**를 섞는다 — 9월 25일 AI 심층 「코딩 벤치마크 오염 측정」에서 무너진 구간이 "저장소 탐색과 위치 특정"이었던 것과 같은 지점을 찌른다
  2. 질문을 쓰기 전에 "이 답은 어느 문서의 어느 값에서 나오고 어느 문서와 맞춰 봐야 하나"를 먼저 적는다
  3. 채점 기준마다 **확인할 파일을 명시**해 판정관(사람이든 모델이든)이 거기만 열게 한다
- 백엔드 비유로는 **테스트 픽스처와 단언(assert)을 같은 데이터 출처에서 생성**하는 것이다. 단언이 픽스처와 따로 놀면(사람이 상상해서 쓴 정답) 테스트가 거짓으로 통과·실패한다
- 오염 감사가 성실하다: 학습 파일 39,201개 대 GDPVal 파일 260개 **공유 0개**, 13-gram 상위 20쌍 실질 중복 0, GDPVal 44개 직업 중 학습이 덮는 건 13개뿐인데 **안 덮는 155개 과제 승률(0.739)이 덮는 65개(0.692)보다 낮지 않다** → 암기가 아니라 전이라는 근거

## 한계와 미검증 지점

- **판정관의 눈이 거칠다.** 저자들의 판정관 민감도 실험: 기준이 인용한 시트를 **통째로 지우면** 해당 점수가 0.377 떨어지지만, 인용된 셀의 **행·숫자·인용을 조금 바꾸면** 0.013~0.022밖에 안 떨어진다. 즉 판정관은 "파일이 없다"는 구조적 실패는 잡지만 "숫자가 틀렸다"는 세밀한 오류는 거의 못 잡는다. 저자는 GLM-5.2의 능력 한계로 본다. **Q > 0.90 입학 심사를 통과한 궤적에 숫자 오류가 남아 있을 수 있다**는 뜻이고, 이건 이 방법의 핵심 주장(검증 가능한 데이터)을 직접 깎는다
- **파이프라인 전체가 한 모델(GLM-5.2)** — 수집·출제·수정·풀이·채점을 같은 모델이 하므로 그 모델의 맹점이 데이터 전체에 같은 방향으로 새겨질 수 있다(9월 30일 뉴스 노트의 "모델이 모델을 검사하는 구조" 비판과 같은 지점)
- **규모가 작다.** 2,169 궤적이고 데이터를 늘렸을 때의 스케일링은 연구하지 않았다. 기반 모델도 Qwen3.6 한 계열 두 크기뿐
- **GDPVal Elo는 잡음이 크다.** 220개 과제라 RFT 갈래 간 차이가 통계적으로 갈리지 않았고, 신뢰구간은 부록에 있어 이번에 확인하지 못했다
- **절대 수준은 아직 낮다.** SFT 후 27B가 1445.7로 프런티어(Opus 5 1774.1, GLM-5.3 1667.0)와 200~300 Elo 차이, SpreadsheetBench II 24.0 대 33~37
- 증거 그래프 자체의 품질(빠진 관계·잘못된 관계 비율)은 따로 측정되지 않았다. 첫 실행을 재사용하지 못한 비율(18.4%)은 있지만, 수정 에이전트가 놓친 오류가 얼마인지는 모른다

# AI - 가중치 공간 프로그래밍

> 상위: [[AI 심층 정리 인덱스]]

> 계기: *Sparks of Weight-Space Programming: LLMs can natively read & write neural network weights* — Rikiya Takehi·Jayden Teoh·Alex Zhang·Omar Khattab(MIT CSAIL), 블로그 2026-11-02, HN 1,737점·댓글 556개, 전체 로그 github.com/RikiyaT/lm_understand-logs (2026-11-03 브리핑). 논문이 아니라 블로그이며 저자 스스로 "매우 초기 결과"라고 적었다.

## 한 줄 정의

범용 프런티어 LLM(여기선 GPT-6 Astra)이 **옵티마이저·경사하강법 없이, 추론만으로** 신경망 가중치를 직접 읽고(무엇을 학습했나), 고치고(왜 실패하나 → 그 부분만 수정), 처음부터 쓰는(원하는 프로그램을 신경망 계산으로 번역) 것. 저자들은 이걸 "가중치 공간 프로그래밍"이라 부른다.

## 왜 이게 문제였나 — 기존 방식의 한계

**가중치를 쓰는 방법은 지금까지 셋뿐이었다.** ① 최적화(경사하강법, Karpathy의 "Software 2.0") ② 가중치를 쓰도록 따로 학습한 신경망(하이퍼네트워크·Neural Network Diffusion 등) ③ 형식 프로그램을 가중치로 바꾸는 컴파일러(Tracr 계열). 가중치를 **읽는** 쪽도 기계적 해석 가능성(회로·특징 추적, ROME 같은 사실 편집)이 전용 도구로 하거나, LLM을 쓰더라도 활성값·가중치 해석용으로 *따로 학습한* 모델(Weight Oracles 등)이거나 뉴런 하나를 설명하는 수준이었다.

**왜 LLM 최적화는 텍스트에서 멈췄나.** 프롬프트(OPRO·DSPy·GEPA), 하네스(Meta-Harness), 학습 코드·하이퍼파라미터(autoresearch)까지는 LLM이 "추론으로" 개선해 왔다. 그 정당화는 *"텍스트는 미분할 수 없어 다른 원리적 방법이 없다, 반면 가중치는 경사하강법이 있다"*였다. 사람은 코드를 손으로 고칠 수 있지만 가중치는 손으로 못 고치니, 가중치는 기호적 알고리즘(Adam·Muon)의 영역으로 남았다.

**경사하강법의 한계는 실무적으로 분명하다.** 특정 실패 하나(예: 반복 루프)를 고치려 해도 데이터를 모으고 파인튜닝해야 하고, 그러면 다른 능력이 흔들린다(파국적 망각). 감사도 마찬가지다 — 백도어·숨은 능력은 그걸 겨냥한 테스트셋이 있어야, 혹은 배포 후에야 드러난다.

## 어떻게 푸는가 — 구조와 비유

**핵심 발상.** 가중치를 "숫자 더미"가 아니라 **읽을 수 있는 프로그램의 컴파일 결과**로 취급한다. LLM은 각 부분이 무엇을 계산하는지(또는 해야 하는지) 추론하고 그에 맞게 숫자를 바꾼다.

**비유.** 바이너리만 있는 프로그램을 리버스 엔지니어링하는 일과 같다. 디스어셈블러 없이 기계어를 읽는 사람처럼, Astra는 "입력 채널 0(에이전트)의 첫 층 가중치가 맨 아래 행에 몰려 있다 → 바닥의 패들 → Breakout" 식으로 구조를 읽는다. 고칠 땐 전체를 다시 컴파일(재학습)하지 않고 **문제 있는 함수 하나에 패치**를 댄다.

**세 동작을 실험으로 보면.**

1. **읽기 — 어디를 보나.**
   - 게임 망(17,253개): 입력 채널별 첫 층 가중치가 격자 어디에 몰렸나, 출력층이 어떤 행동끼리를 구별하나. 선택지 없이 4개 게임 모두 적중.
   - 확산 모델(23,824개): 출력층의 각 은닉 유닛이 도형 가장자리의 한 조각을 그린다. 그래서 Astra는 **속이 찬 도형을 윤곽선으로 그렸다** — 순전파를 계산한 게 아니라 가중치의 기하를 "읽었다"는 방증이라고 저자는 해석한다.
   - 입출력층을 떼어 낸 문자 LM(7.16M): 한 글자 뒤를 보는 첫 층 헤드를 찾고, 가중치 행렬을 곱해(QK·OV 합성) 그 헤드가 가져온 정보로 검색하는 후속 헤드 = **유도(복사) 헤드**를 찾았다. Elhage 외(2021)의 방법을 알려주지 않았는데 재발견. 코드는 이름을 많이 반복하니 복사 헤드가 많으면 Python, 마지막 블록이 쓰는 방향 수가 적으면(q·l·v·x를 안 쓰는) 로마자 일본어.
2. **고치기 — 우회 경로를 덧댄다.** Kinetix 자동차 정책은 경사로로 곧장 돌진하다 멈추는 국소 최적점에 갇혔다(256회 중 0회 성공). Astra는 녹화 1회를 보고 원인을 진단한 뒤, **층마다 몇 개 유닛으로 위치·속도를 읽는 별도 경로**를 만들어 "먼저 후진 → 전속 전진 → 바퀴가 빨간 띠를 넘으면 경로 해제, 나머지는 원래 망이 운전"하게 했다. 171,664개 중 6,073개(3.5%) 수정, 1,024회 100%. 기존 프로그램에 **기능 플래그로 감싼 핫픽스**를 넣은 모양이다.
3. **쓰기 — 프로그램을 신경망으로 번역.** MinAtar Breakout에서 첫 층은 "공의 방향·벽 반사를 고려한 착지 위치 − 패들 위치" 네 개와 방향 표시 두 개를 계산하고, 둘째 층은 좌/우를 게이트해 맞는 위치면 no-op. 바둑(148만 개)에서는 Python으로 층별 "돌·활로 표시 → 연결된 돌 따라 전파해 위험한 무리 찾기 → 포획·구출·자충 회피·눈 메우기 회피·좋은 점 선호 점수"를 짰다. 순전파 예산을 주면 연습 대국을 보고 지는 원인 부분을 고쳐 승률이 오른 변경만 남긴다 — **사람이 쓰는 휴리스틱 프로그램을 가중치로 컴파일**한 셈.

**실험 8(Qwen3.5-0.8B) — 진단 과정이 곧 방법론.** 순전파 50회 예산 안에서 Astra가 밟은 17단계:

```
뉴런 하나 끄기(19층 #11, +6점) → 19층 MLP 전체에서 '루프 방향' 제거
→ 15·19층 → 강도 1·2·3·4 (용량-반응: +12.5 → +24.6 …)
→ 새 문제에서 유지 확인(8.2% → 43.0%)
→ 대조군: 같은 크기 무작위 방향(+1.6점, 효과 없음)
→ 15층만 / 19층만 (층 분리)
→ 층당 가장 강하게 쓰는 64개 뉴런만 (+26.6점, 전체 편집과 동일) → 64개·강도 6 채택
```

최종 편집: 15·19층 MLP 출력 열 64개씩, 131,072개(0.016%)에서 루프 방향을 빼기. 결과(50회): MATH-500 7.9→48.1%, GSM8K 13.8→67.1%, IFEval 21.0→62.3%, 토큰 한도 도달 93.0→33.1%. "거부는 한 방향으로 매개된다"(Arditi 외, 2024)·abliteration과 같은 계열의 **방향 사영 제거**이고, 이 구역의 이전 노트들에서 본 기법(9/30 뉴스의 abliteration)을 수리 쪽에서 쓴 것이다.

## 실제로 쓸 수 있나

- **지금 당장 개발자가 쓸 도구는 아니다.** 프런티어 모델 + 가중치 파일 접근 + Python 커널 + 순전파 예산이 필요하고, 하네스·벤치마크는 "만드는 중"이다. 편집된 Qwen과 HF 데모, 전체 로그가 공개돼 있어 **읽어 보는 교재**로는 바로 쓸 수 있다.
- **가장 현실적인 쓰임은 "알려진 결함의 국소 수리".** 모델 카드가 이미 경고하는 반복 루프처럼 원인이 한 성분에 몰린 결함이라면, 데이터 수집·재학습 없이 고칠 수 있다는 가능성. 망각 위험도 편집 범위(0.016%)만큼 작다.
- **보안 쪽 함의가 더 가깝다.** 같은 기법이면 오픈 웨이트 모델의 안전장치를 더 싸게 지울 수 있다(HN의 첫 질문 중 하나). 모델을 받아 쓸 때 **가중치 해시 검증·출처 확인**이 기본 점검이 되는 이유가 하나 더 생겼다. 반대로 "평가 없이 감사"(가중치에서 백도어 찾기)가 되면 방어 도구가 되지만, 실험 7이 보여주듯 **가중치만으로는 아직 행동 차이를 못 읽었다.**
- **일반화할 만한 사고방식.** "전부 다시 학습"과 "국소 패치" 사이의 선택은 소프트웨어의 "전체 재빌드 vs 증분 빌드"와 같다(같은 날 Cloudflare DNS 표적 빌드). 국소 패치는 싸지만 **패치 범위가 다른 데를 건드리지 않는다는 증명**이 필요하다 — Cloudflare는 바이트 단위 등가 테스트·미러 비교로 그걸 했고, 가중치 편집은 아직 무작위 방향 대조군 한 번과 8개 벤치마크 정도로 하고 있다.

## 한계와 미검증 지점

- **능력이 아니라 장애물을 치웠다** — 저자 명시. 구제 579건 중 576건이 원래 토큰 한도에 잘리던 답, 끝까지 답하던 응답의 정확도는 불변(오류 회귀 5건). 루프가 드문 Gemma 3 270M(한도 도달 8.5%)은 MATH-500 6.8→7.0~7.7%로 유의미한 개선 없음 — 산술 오류·잘못된 대수 단계처럼 **한 부품으로 귀속되지 않는 실패**는 못 고쳤다.
- **기준선 설정**: 7.9%는 presence penalty 1.5·top-k 20·thinking 켬·32K라는 특정 샘플링 값에서의 수치. 다른 설정의 원본 성능은 비교되지 않았다.
- **예산-성능 곡선이 단조롭지 않음**: IFEval 10회 49.0% → 25회 39.9% → 50회 62.3%, MATH-500은 10·25회에서 12~14%에 머물다 50회에서 급등. 탐색 경로 의존이 큰 단일 실행일 수 있다(반복 실행 분산 미보고).
- **가중치만으로는 아첨을 못 읽었다**: 4회 모두 실패, 어텐션 패턴 도구를 줘야 3쌍 성공. Astra 자신도 "사용자 동의 전담 검출기를 입증한 건 아니다"라고 답했다. "평가 없는 감사"의 전망과 가장 거리가 먼 결과.
- **'쓰기' 실험은 사실상 손 제어기 컴파일**: Breakout에 규칙과 소스 코드를 줬으므로, 결정론적 물리에서 착지점 계산기를 짠 것이 짧게 학습한 PPO(25.3)를 이긴 것은 "학습 대 프로그래밍"의 비교다. 규칙이 덜 명시적인 Seaquest(53.1 대 88.9)에서는 졌다.
- **규모·자기 개선 미검증**: 수조 파라미터급 모델이 8억 이하 모델을 다뤘다. 같은 방식으로 자기 자신이나 더 큰 모델을 고칠 수 있다는 증거는 없다(HN). 컨텍스트에 안 들어가는 규모에선 Python 도구와 순전파 예산이 필수였다.
- **왜 되는지 모른다**: 학습 데이터에 기계적 해석 가능성 문헌이 많아서인지, 강화학습 중 생긴 능력인지 — HN의 추측들뿐이고 저자도 원인 분석은 하지 않았다.
- **검증 수준**: 블로그·자기 측정·대부분 단일 실행. 다만 전체 로그(입력·응답·추론 요약·실행 코드·평가) 공개, HF의 Ahsen Khaliq가 로그로 편집 모델을 재구성하고 평가를 재실행 — 완전한 독립 재현은 아니지만 재현 가능한 형태로 내놓았다.

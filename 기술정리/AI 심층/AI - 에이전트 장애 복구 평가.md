# AI - 에이전트 장애 복구 평가

> 상위: [[AI 심층 정리 인덱스]]

> 계기: *UndoBench: Separating Task Competence from Recovery Capability in Tool-Using AI Agents* — Dolly Sah, Tanmay Sah, Harshul Jain, Tanya Sah, arXiv 2610.05622, 2026-10-06 제출, HF ▲4~7 (2026-10-07 브리핑)
> 읽은 범위: arXiv 초록 전문, HF 논문 페이지, GitHub README(지표 정의·장애 시점·도메인·기준선 목록). **본문(18쪽)의 방식별·모델별 표는 읽지 못했다.** 아래 수치는 초록에 있는 것만 썼다.

## 한 줄 정의

**장애 복구 평가**는 에이전트가 과제를 "끝낼 수 있나"(과제 능력)와, 도구 호출이 중간에 실패했을 때 **외부 세계에 부작용을 두 번 남기거나 빠뜨리지 않고** 목표 상태로 돌아올 수 있나(복구 능력)를 따로 재는 것이다. UndoBench는 이 둘이 크게 다르다는 것을 보였다. 정상 완료율 83.54%, 복구 성공률 46.72%, 단순 재시도의 중복 효과 53.33%.

## 왜 이게 문제였나 (기존 방식의 한계)

**1) 완료율 하나에 두 능력이 섞여 있었다.** 기존 에이전트 벤치마크(SWE-bench·OSWorld·τ-bench 계열)는 "마지막에 목표 상태가 됐나"를 본다. 에이전트가 실패하면 그것이 계획을 못 세운 탓인지, 중간 장애를 못 다룬 탓인지 구분되지 않는다. 장애를 넣은 평가가 있어도 애초에 정상 조건에서도 못 푸는 과제가 섞이면 복구 실패율이 부풀려진다.

**2) 최종 상태만 보면 위험한 성공을 놓친다.** 송금을 두 번 하고 한 번을 취소해 결과적으로 잔액이 맞았다면, 최종 상태 채점기는 "성공"을 준다. 하지만 실제 시스템에서는 중복 송금이 알림·감사 로그·외부 정산에 흔적을 남긴다. 9/29 노트의 인덱스 감사("개별 품질은 다 멀쩡한데 합쳐놓으니 청구서가 나왔다")와 같은 구조다. 결과 지표가 과정의 비용을 가린다.

**3) 에이전트는 재시도를 너무 쉽게 한다.** 사람 사용자의 중복 요청은 버튼 비활성화·더블클릭 방지로 상당 부분 막혀 왔다. 에이전트는 오류 메시지를 받으면 "다시 시도"를 합리적인 다음 행동으로 고른다. 그것도 빠르게, 여러 번. 재시도가 안전한지 판단할 정보(요청이 서버에 도달했는지)는 대개 에이전트에게 없다.

## 어떻게 푸는가

### 1) 측정 설계 — 반사실 쌍으로 "복구 실패"만 떼어 낸다

과제 하나를 **같은 시드로 두 번** 돌린다. 한 번은 정상 조건, 한 번은 장애 주입 조건이다. 정상 조건에서 성공한 경우만 분모로 삼아 장애 조건의 성공률을 잰다. 이것이 **조건부 복구 성공률(CRSR = C/D)**이다.

- D/N: 정상 조건 성공률 → 과제 능력(Control Pass Rate)
- C/D: 정상에서 성공한 것 중 장애에서도 성공한 비율 → 복구 능력(CRSR)

이렇게 하면 "원래 못 푸는 과제"가 복구 지표를 오염시키지 않는다. 단위 테스트에서 픽스처를 고정하고 한 변수만 바꾸는 것과 같다.

### 2) 핵심 장애 — 응답 유실(lost acknowledgment)

가장 현실적이고 어려운 장애로 **응답 유실**을 골랐다. 외부 시스템(API·DB·메시지 큐)은 요청을 처리하고 변경을 커밋했는데, 응답 패킷이 에이전트에 닿지 않는 경우다. 에이전트는 타임아웃이나 연결 오류만 본다.

이때 에이전트가 처한 상황은 두 가지로 구분되지 않는다.
- 요청이 서버에 도달하지 못했다 → 다시 보내야 한다
- 요청이 처리됐는데 응답만 잃었다 → 다시 보내면 중복이다

선택지는 둘뿐이다. 무작정 다시 보내거나(중복 위험), 포기하거나(누락 위험). 분산 시스템의 "두 장군 문제"를 에이전트가 맞닥뜨리는 지점이다.

### 3) 장애를 넣는 시점 — 세 경계

| 시점 | 상태 | 결과 |
| --- | --- | --- |
| 변경 전 | 외부 상태가 아직 안 바뀜 | 방식 간 차이 거의 없음. 유능한 시행에서 중복 효과 없음 |
| 변경 도중 | 여러 단계 중 일부만 반영 | 단순 재시도·호출 단위 멱등성·권한 없는 저널링이 **모두 무너짐** |
| 커밋 후 응답 전 | 변경은 끝났고 응답만 유실 | **검증 후 재시도**와 **서버 측 멱등성**이 안전성을 크게 올림 |

복구는 **시점 의존적(phase-dependent)**이다. "재시도 정책 하나 잘 고르면 된다"가 아니다. 어느 경계에서 실패했느냐에 따라 맞는 전략이 다르다.

### 4) 판정 — 오라클 둘

- **효과 이력 오라클**: 나가는 모든 도구 호출과 응답을 와이어 수준에서 기록한다. 각 의미적 효과(예: "A에게 100원 송금")가 정확히 한 번 / 두 번 이상 / 0번 일어났는지 센다.
- **환경 상태 오라클**: 최종 샌드박스 상태(DB 행, 버킷 객체, git 커밋)가 목표 불변식을 만족하는지 본다.

둘을 같이 쓰는 이유는 앞의 "위험한 성공"을 잡기 위해서다. 상태는 맞는데 이력에 중복이 있으면 실패로 처리한다. 파생 지표로 **정확히 한 번 효과율(EOR)**, 중복 효과율(DER), 누락 효과율(MER), 위험 재시도율(URR)을 낸다.

### 5) 비교한 복구 방식

README가 열거한 기준선은 다음과 같다(본문의 "3종 패러다임"이 이 중 어느 셋인지는 초록만으로 특정하지 못했다).

- **단순 재시도(Naive Retry)** — 오류면 다시 실행
- **체크포인트·롤백** — 도구 호출 전 메모리 스냅샷, 실패 시 로컬 상태만 복원(외부 시스템은 못 되돌림)
- **멱등성 키** — 고유 키를 외부 호출에 실어 같은 키의 반복이 같은 결과를 내게 함
- **Saga(보상 트랜잭션)** — 실패한 단계 이전의 변경을 반대 작업으로 취소
- **LangGraph 기본 재시도 정책**
- **검증 후 재시도(Verify-Before-Retry)** — 다시 보내기 전에 변경하지 않는 조회로 "이미 됐나"를 먼저 확인

### 6) 결과를 웹 백엔드 말로 옮기면

- **"호출 단위 멱등성"은 클라이언트 쪽 장치다.** 클라이언트가 키를 붙여도, 그 키를 기억하고 같은 결과를 돌려주는 서버가 없으면 소용이 없다. 여러 단계 중 일부만 반영된 상태에서는 키 하나로 전체 워크플로의 정합성을 보장할 수 없다.
- **서버 측 멱등성**이 효과가 있었다는 것은, 받는 쪽 API가 `Idempotency-Key`를 저장하고 같은 키에 첫 응답을 재생해야 한다는 뜻이다(Stripe식 설계).
- **검증 후 재시도**는 "변경 API 옆에 상태 조회 API가 있어야 한다"는 설계 요구로 번역된다. 에이전트가 물어볼 수 있는 창구가 없으면 검증할 수 없다.

## 실제로 쓸 수 있나

**에이전트를 만드는 쪽.** 도구 정의에 "이 도구는 멱등한가, 재시도해도 되는가"를 메타데이터로 명시하고, 비멱등 도구는 재시도 전에 조회 도구를 먼저 부르게 하는 규칙을 하네스에 넣을 수 있다. 프롬프트로 부탁하는 것보다 하네스에서 강제하는 쪽이 낫다(9/27 노트 「에이전트 운영체제」의 "프롬프트로 부탁한 것은 보안 장치가 아니다"와 같은 원리).

**에이전트를 받는 쪽(백엔드).** 이쪽이 더 직접적이다. 변경 API에 서버 측 멱등성 키 저장소(DB 유니크 제약 또는 Redis + TTL), 그리고 변경 여부를 확인할 수 있는 조회 엔드포인트를 둔다. 여러 단계 워크플로라면 Outbox·Saga로 단계별 상태를 기록해 "어디까지 됐는지"를 재구성할 수 있게 한다. 9/28 노트(Transactional Outbox)와 10/2 노트(CDC + Redis TTL 중복 방지)의 기법이 그대로 쓰인다.

**평가하는 쪽.** 사내 에이전트를 도입할 때 정상 시나리오 성공률만 보지 말고, 응답 유실을 일부러 넣은 시나리오를 별도로 돌려 CRSR과 중복 효과율을 보는 것이 실무적인 체크다. UndoBench의 GitHub는 Java를 포함한 HTTP 에이전트도 붙일 수 있게 열어 두었다.

## 한계와 미검증 지점

1. **규모와 출처.** 저자 4명, HF 추천 한 자릿수. 큰 연구실의 검증을 거친 결과가 아니다. 모델은 "오픈 웨이트 2종"으로만 표기됐고, 강한 상용 모델에 대해서는 "같은 분리가 재현됐다"는 한 줄뿐이다.
2. **방식별 수치 미확인.** 초록은 시점별 결론을 정성적으로만 말한다("무너짐", "크게 개선"). 검증 후 재시도와 서버 측 멱등성이 각각 몇 %였는지, 둘을 같이 쓰면 어떤지는 본문을 봐야 한다.
3. **시뮬레이션 환경.** 8개 도메인은 샌드박스다. 실제 결제·클라우드 API의 재시도 의미론(예: 일부 API는 이미 멱등 키를 지원)과 다를 수 있다.
4. **새로운 사실은 아니다.** "exactly-once는 클라이언트 혼자 보장할 수 없다"는 분산 시스템의 오래된 결론이다. 이 논문의 기여는 에이전트에서 이를 **측정 가능하게** 만들고 시점별로 쪼갠 데 있다.
5. **에이전트의 판단력 자체는 변수로 다루지 않았다.** 더 강한 모델이 "응답이 없으니 먼저 조회해 보자"를 스스로 떠올리는 비율이 얼마인지 — 즉 하네스 강제 없이 모델이 검증 후 재시도를 자발적으로 하는지 — 는 이 설계로 분리되지 않는다.

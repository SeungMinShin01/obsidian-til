# AI - 비생성 의사결정 모델

> 상위: [[AI 심층 정리 인덱스]]

## 한 줄 정의

**텍스트를 생성하지 않고, 미리 정해진 선택지에 대한 보정된(calibrated) 확률만 한 번의 forward pass로 돌려주는 모델** — 대화용 LLM이 아니라 프로그램의 분기점(`if`) 안에 들어가는 LLM.

계기: 2026-09-22 브리핑에 실린 Kev(HN 398점·댓글 176)와 그 배경인 Jev·Laya.

## 왜 이게 문제였나 — 기존 방식의 한계

프로그램 안에서 "이 리뷰가 긍정인가 부정인가", "이 요청을 어느 부서로 보낼까", "이 메일이 스팸인가"를 판단하려고 LLM을 쓰면, 원하는 것은 boolean 하나인데 **문장 생성 비용을 전부 치른다.** 구체적으로 네 가지 낭비가 겹친다.

1. **자기회귀 생성 비용** — 답이 "긍정"이라는 두 글자여도 모델은 토큰을 하나씩 순차적으로 뱉는다. 토큰 수만큼 forward pass가 반복되고, 그게 지연시간의 대부분이다
2. **파싱과 스키마 위반** — 출력이 자연어(또는 자연어로 흉내 낸 JSON)라 파싱해야 하고, 형식이 흔들릴 수 있다. "JSON만 출력해"라고 시켜도 마크다운 코드펜스가 붙거나 필드가 빠지는 일이 생긴다. 구조화 출력(constrained decoding)을 쓰면 형식은 잡히지만 생성 비용은 그대로다
3. **확률을 꺼낼 수 없다** — "긍정입니다"라는 문장에서 **모델이 얼마나 확신하는지**를 알 수 있는 깔끔한 경로가 없다. 로짓을 직접 보는 방법이 있지만 토큰 단위라서 선택지 단위 확률로 바꾸는 게 지저분하다. 확신도 없이 판단만 받으면 "애매한 건 사람에게 넘긴다"는 분기를 짤 수 없다
4. **질문 하나당 요청 하나** — 같은 문서에 대해 10가지를 묻고 싶으면 보통 10번 호출한다. 같은 입력을 10번 다시 읽는다

전통적 분류기(BERT 파인튜닝 등)는 1·2·3을 해결하지만 **출력 클래스가 학습 시점에 고정**된다. 새 카테고리가 생기면 다시 학습해야 하고, 자연어로 된 판단 기준("정책 위반 소지가 있는가")을 런타임에 넣을 수 없다. 이 노트의 모델들이 겨냥하는 빈칸이 정확히 여기다 — **분류기의 출력 형식 + LLM의 자연어 이해.**

## 어떻게 푸는가

### Jev (TypeSafe) — 원형

**System One 모델**을 자칭한다. 카너먼의 빠른 사고/느린 사고에서 가져온 이름으로, "추론을 깊게 하는 대신 즉각 판단한다"는 포지셔닝이다.

인터페이스가 핵심이다. 자연어 질문 + **미리 정한 선택지 목록**을 함께 넣으면, 그 목록 안에서 골라 돌려준다.

```
질문: "하늘은 무슨 색인가?"  선택지: ["blue", "red", "yellow"]
→ { answer: "blue" }
```

구조적으로 두 가지가 다르다.

- **자기회귀 생성을 버렸다.** JSON을 토큰 단위로 만들어내는 대신, 한 번의 계산으로 구조화된 값을 내놓는다. 그래서 여러 질문을 **병렬로** 처리할 수 있다
- **RLCD(Reinforcement Learning for Calibrated Decisions)** — 이 태스크에 맞춰 학습해서 "확률이 보정돼 있다"고 주장한다. 보정이란 "70%라고 말한 것들 중 실제로 70%가 맞는다"는 성질이다

체감 수치는 응답 **약 70~500ms**다. 시연으로 **Doom을 플레이**했다 — 텍스트로 게임 상태를 받고 행동을 골라 돌려주는 걸 실시간으로 반복한다. 이게 "조건문 안의 LLM"이라는 발상을 가장 잘 보여준다.

### Kev — 같은 것을 노트북에서 돌리는 재구현

오픈소스 재구현(Apache-2.0)이고, 규모가 작아서 **내부 구조를 그대로 읽을 수 있다**는 점에서 학습 가치가 가장 크다.

구성:

- **백본**: Qwen 계열 0.5B 모델 + **LoRA (rank 16)**
- **리드아웃 헤드**: 처음부터 학습한 **포인터 헤드**(pointer head)
- **패키지 크기**: LoRA 어댑터 + 헤드 + 토크나이저 합쳐 **약 38MB**

추론 경로가 이 모델의 알맹이다. 5단계다.

1. **렌더링** — 요청(상태 + 질문들)을 예약된 구분자를 쓴 구조화 텍스트로 바꾼다
2. **패킹** — 상태와 모든 질문을 **하나의 토큰 시퀀스**로 합친다. 상태 토큰은 재사용되고, 질문마다 자기 분기(branch)를 갖는다
3. **마스킹** — **block-causal 어텐션 마스크**로, 각 질문이 상태는 볼 수 있지만 **다른 질문은 못 보게** 막는다. 여기가 설계의 급소다. 질문끼리 서로를 보면 앞 질문의 답이 뒤 질문에 새어 들어가 독립적인 판단이 아니게 된다. 마스크 한 장으로 "10개 질문을 한 번에" 와 "질문끼리 독립" 을 동시에 만든다
4. **Forward pass** — 백본을 **prefill 한 번**만 통과한다. **디코딩이 없다** — 생성하지 않으니 토큰을 뱉을 필요가 없다
5. **리드아웃** — 포인터 헤드가 각 선택지를 결정 토큰(decision token)에 대해 점수화하고, 질문별로 softmax를 걸어 확률 분포를 만든다

비유하면 **객관식 시험지 채점**이다. 지문(상태)을 한 번 읽고, 문항마다 보기들에 점수를 매긴다. 서술형 답안을 쓰지 않으므로 필기 시간이 0이고, 문항끼리 답을 훔쳐보지 못하게 칸막이(마스크)를 세운다.

질문 타입은 셋이다 — **Noul**(예/아니오, P(true)), **Choice**(2~255개 선택지, 상호배타), **Score**(순서가 있는 등급, 예: 만족도 0~3).

학습은 의외로 단순하다. **강화학습이 아니라 교차 엔트로피 지도학습(SFT)**이다. 공개 데이터셋 6개(Banking77·AG News·MNLI·BoolQ·SST-5·Yelp)를 요청 형식으로 변환해 9,000레코드 / 13,500질문을 2에폭 돌린다. 여기에 두 가지 정규화가 선택적으로 붙는다.

- **permutation KL** — 선택지 순서를 바꿔도 같은 분포가 나오도록 누른다. 순서 편향(앞에 놓인 보기를 더 고르는 경향)을 없애는 장치
- **ordinal loss** — Score 타입에서 "3을 4로 틀린 것"과 "3을 0으로 틀린 것"을 다르게 벌한다. 순서 정보가 있는 등급에는 일반 분류 손실이 맞지 않기 때문

학습 시간이 **Apple M5에서 약 1시간 45분**이라고 적혀 있다. 지연시간은 6개 질문 요청에 **약 160ms**.

성능(held-out 1,350문항):

| 태스크 | 정확도 | ECE |
| --- | --- | --- |
| Choice 4지 (AG News) | 0.940 | 0.028 |
| Choice 3지 (MNLI) | 0.747 | 0.100 |
| Choice 77지 (Banking77) | 0.860 | 0.057 |
| Noul (BoolQ) | 0.753 | 0.136 |
| Score 5단계 (Yelp) | 0.553 | 0.118 |
| **전체** | **0.799** | **0.065** |

**ECE(Expected Calibration Error)**가 같이 실린 게 이 계열의 성격을 말해준다. 정확도만 보는 게 아니라 **"확신도가 실제 적중률과 얼마나 어긋나는가"**를 같이 보고한다. 0.065면 "80% 확신"이라 말한 묶음의 실제 적중률이 약 80±6.5%p 안에 있다는 뜻이다. 같은 백본의 zero-shot(베이스·instruct 모델)보다 전 항목에서 낫다.

### Laya — 인코더로 같은 문제를 푸는 쪽

역시 Apache-2.0 오픈소스인데, 백본 선택이 다르다. **디코더 계열 대신 양방향 인코더**를 쓴다.

- **Laya (영어)** — ModernBERT-large 기반 **421M**, 컨텍스트 512토큰
- **Laya Multilingual** — mmBERT-base 기반 **322M**, 100개 이상 언어, 컨텍스트 1,024(최대 8k)
- **Laya Typed Decisions** — 421M, 1,024토큰, 업무 태스크 특화

인코더를 쓴 이유는 구조적이다. 애초에 생성을 안 할 거라면 **causal 마스크로 뒤를 가릴 이유가 없다** — 문서 전체를 양방향으로 한 번에 보는 인코더가 분류·판정에는 더 자연스럽다. 그래서 같은 일을 하면서 파라미터가 더 적다(322M~421M vs 0.5B~).

수치:
- 단일 질문 **32.8ms**, 10개 배치 시 질문당 **7.2ms** — 배치가 4.5배 이득
- Typed decisions 정확도 **76.6%**
- 이메일 스팸 F1 **0.993**, 피싱 탐지 F1 **0.979**
- **ECE 0.081 — Jev의 0.246보다 약 3배 좋다**고 주장

마지막 항목이 흥미롭다. Jev가 "보정된 확률"을 핵심 셀링 포인트로 내세웠는데, 오픈소스 구현 쪽에서 **그 지표에서 Jev를 이겼다**고 보고하는 구도다. 다만 이건 Laya 측 자체 측정이다.

## 실제로 쓸 수 있나

쓸 수 있는 자리가 꽤 분명하다.

- **라우팅** — 들어온 요청을 어느 핸들러/부서/모델로 보낼지. 여기서 큰 모델을 쓰는 건 낭비다
- **가드레일·필터링** — 스팸·피싱·정책 위반 판정. Laya의 F1 0.99대가 이 자리를 겨냥한 숫자다
- **에이전트의 검증 단계** — 큰 모델이 만든 결과물을 "이게 요구사항을 만족하는가"로 되묻는 자리. 확률이 나오므로 **임계값 아래면 다시 시키거나 사람에게 넘기는** 분기를 짤 수 있다
- **게임 AI·실시간 제어** — Jev의 Doom 시연이 이 자리
- **한 문서에 여러 판정** — 계약서 하나를 넣고 조항 20개를 한 번에 묻는 식. Kev의 패킹·마스킹 구조가 이걸 위한 것이다

**Spring/WMS 쪽으로 옮겨 생각하면**, 이건 "AI 기능"이라기보다 **가벼운 판정 서비스**다. 38MB~400M 파라미터급이면 별도 GPU 없이 프로세스 하나로 띄울 수 있고, 지연시간이 30~160ms면 동기 요청 경로에 넣을 만하다. 다만 판단 근거를 로그에 남길 수 없다는 점(확률만 나오고 이유는 안 나온다)은 감사가 필요한 경로에서 걸림돌이다.

## 한계와 미검증 지점

**측정된 한계**(문서에 적힌 것)

- **선택지가 많아지면 무너진다.** Laya는 20개를 넘어가면 성능이 떨어지고, Banking77(77지)에서 **42.5%**에 그친다. 흥미롭게도 Kev는 같은 Banking77에서 0.860을 보고하는데 — Kev는 **그 데이터셋으로 학습했다**. 학습 분포 안에서의 숫자와 밖에서의 숫자를 나란히 놓으면 안 된다
- **파인튜닝 없이는 도메인 태스크에서 약하다.** Laya 베이스 모델은 특화 벤치마크에서 약 35%
- **언어 라우팅이 따로 필요하다.** 영어 모델에 크메르어를 넣으면 **정확도 0%인데 확신도 95.2%**를 낸다. 보정이 학습 분포 안에서만 성립한다는 가장 선명한 증거이고, 실무에서 가장 위험한 실패 양식이다 — 틀리면서 확신하는 모델은 임계값 분기를 무력화한다
- **Kev의 지식 한계** — 0.5B라서 사실 지식이 얇다. 문서에 적힌 예: TypeSafe 문서의 구조화 기준 예제에서 Kev는 `return_policy`를, Jev는 `return_status`를 고른다
- **컨텍스트 길이** — Kev는 상태 384 / 분기 1,024토큰으로 학습하고 서빙은 8,192까지. Jev는 약 32k
- **서빙 제약** — Kev는 MPS에서 fp32, 단일 요청, 요청 간 KV 캐시 없음. 프로덕션 서빙 구현이 아니라 참조 구현이다
- **Score 확신도 공식** — Kev는 TypeSafe의 미공개 방식 대신 **대체 공식(stand-in formula)**을 쓴다. 즉 Score 타입의 확률값은 Jev와 같은 것이 아니다
- **태스크 폭** — 데이터셋 6개, 지시 템플릿 약 10개로 학습했다. 먼 도메인에서의 성능은 **테스트되지 않았다**

**미검증·확인해야 할 지점**

- **ECE는 in-distribution 지표다.** Kev 문서가 직접 못 박는다 — 실제 워크플로의 결과 레이블 없이는 현실 보정을 보장하지 않는다. 즉 **내 데이터로 다시 재야 한다**
- **Jev의 RLCD 세부는 공개돼 있지 않다.** HN 댓글에서 "Kev는 SFT인데 Jev-like라고 부를 수 있나"라는 지적이 나온 이유가 이것이다. 이름은 비슷하지만 학습 방식이 다르다
- **백본 표기가 문서 안에서 엇갈린다.** 저장소 제목은 Qwen3.5 기반이라고 적는데 모델 카드는 **Qwen2.5-0.5B**로 적는다. 브리핑 메일도 Qwen3.5로 옮겼다. **확인 전까지 "Qwen 계열 0.5B"로만 적는 게 맞다**
- **브리핑의 링크 대응이 어긋난다.** Kev 항목에 걸린 GeekNews 한글 요약은 Kev가 아니라 **Laya**에 대한 글이다. 세 모델이 같은 계열이라 묶여버린 것으로 보인다
- **"분류기와 뭐가 다르냐"는 비판이 해소되지 않았다.** HN 댓글에는 "이 계열이 레거시 분류기와 근본적으로 다르다고들 하지만, 벤치마크를 보면 많은 경우 비교 대상보다 소폭 개선일 뿐"이라는 지적이 있다. **런타임에 선택지를 정의할 수 있다**는 점은 실제 차이지만, 정확도 자체가 새 지평은 아니라는 반론으로 읽어야 한다
- **지식 컷오프** — 도구 호출이 없으므로 학습 시점 이후 지식이 필요한 판정은 못 한다. 주기적 재학습이나 버전 갱신이 전제된다
- Laya의 "Jev 대비 ECE 3배" 비교는 **Laya 측 자체 측정**이고 독립 재현이 없다

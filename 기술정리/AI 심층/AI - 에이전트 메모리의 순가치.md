# AI - 에이전트 메모리의 순가치

> 상위: [[AI 심층 정리 인덱스]]

> 계기: *Memory Tax: Dissecting the Net Value of Agent Memory* — Xuan He 외(UIUC·칭화대·인민대 등, Jiawei Han·ChengXiang Zhai), arXiv 2610.34073(2026-10-25), HF ▲125 (2026-10-29 브리핑)
> 읽은 범위: HF 페이지(초록·댓글), alphaXiv 추출 본문 1~8절과 한계 절. 부록(A 설정 세부, B RAG 기준선 검증, C 세금 분석 확장, D 사례, E 전체 표, F 프롬프트)은 본문에 인용된 것만 확인했다. 함께 본 것: HABIT-Bench(2610.24520)·TTME(2610.32046) HF 초록.

## 한 줄 정의

에이전트 메모리의 가치는 "메모리를 붙인 점수"가 아니라 **같은 원본 기록을 그냥 잘라서 검색하는 RAG 대비 순이득**이고, 그 순이득은 정리·요약이 만든 이득(memory benefit)에서 정리·요약이 지우거나 가린 증거의 손실(memory tax)을 뺀 값이다.

## 왜 이게 문제였나 — 기존 방식의 한계

장기 에이전트의 메모리는 대화·관찰 기록 H를 받아 무언가로 가공한다 — 요약, 추출한 사실, 구조화 레코드, 계층(단기/장기 층, 파일시스템 트리), 그래프, 학습된 쓰기 정책. 그리고 질의가 오면 그 가공물에서 꺼내 답한다. 식으로 쓰면 `M = I(H)`(적재), `C = R(q, M)`(검색), `ŷ = G(q, C)`(생성).

문제는 비교 대상이었다. 저자들이 선행 연구를 훑어보니 메모리 설계는 대부분 **다른 메모리끼리** 비교했고, 가장 단순한 대안 — 원본 H를 그대로 청크로 잘라 검색하는 naive RAG — 은 빠지거나, 들어가도 설정(청크 크기·임베딩·재정렬·라운드)이 불명확했다(부록 B.2). 그러면 "메모리를 만든 것의 가치"와 "그냥 증거를 찾아온 것의 가치"가 뒤섞인다. 메모리 시스템이 점점 복잡해지는데(그리고 비싸지는데) 그 복잡도가 *어디서* 값을 하는지 아무도 재지 않았다.

비유하면, 회의록을 통째로 보관하는 대신 비서가 "결정 사항·할 일·참석자 선호"로 정리한 노트만 남기는 회사다. 정리 노트는 빠르고 깔끔하지만, 나중에 "그때 누가 정확히 뭐라고 했지?"를 물으면 노트에 없다. 그리고 그 질문이 생각보다 자주 나온다.

## 어떻게 푸는가

### 1) 측정 틀 — 질의 단위로 RAG와 대조

메모리 시스템과 RAG(1라운드)의 정답 여부를 **질의 하나하나** 비교한다(논문 그림 2, 벤 다이어그램).

- 메모리만 맞힘 → **memory benefit**: 흩어진 사실을 모으거나, 선호를 추론하거나, 재구성이 도움이 된 경우
- RAG만 맞힘 → **memory tax**: RAG는 원본에서 찾았는데 메모리에서는 증거가 없거나 못 찾은 경우
- 순가치 = benefit − tax. 이게 음수면 메모리를 만든 비용(토큰·시간·저장)까지 들이고 더 나빠진 것

핵심 시각 전환: 메모리 가공은 **원본으로부터의 불가피한 편차(deviation)**이고, 편차는 양날이다. 의도한 편차(정리·추상화)가 이득을 만들고, 의도치 않은 편차(손실·가림)가 세금을 만든다.

### 2) 실험 구성

- 벤치: LongMemEval-s(검색 친화적), PersonaMem-v2(20% 층화 표본), MINT-Eval(10%)
- 메모리 11종을 저장 방식으로 묶음 — 평면 저장(A-Mem·SimpleMem·MemOS), 계층/생애주기(MemoryOS·LightMem·OpenViking), 그래프(HippoRAG2·PlugMem·MAGMA), 학습된 정책(Mem-T·Memory-R2)
- 기준선: RAG 1라운드·2라운드(BM25 + Qwen3-Embedding-0.6B, Qwen3-Reranker-0.6B 재정렬 — HF 댓글이 정리), No Context·Full Context·Gold Context
- 백본: Qwen3.5-4B, Qwen3.6-27B, GPT-5.6 Luna(low). 채점은 Qwen3.6-27B 심판
- 공정성 장치 **Retrieval Scope**: 시스템마다 메모리 단위 크기가 달라 top-k를 같게 두면 노출 정보량이 달라진다. 그래서 "검색~답변 동안 LLM에 노출된 토큰 ÷ 그 시스템 저장소 전체 토큰"을 RAG 1라운드 이상으로 맞추도록 top-k를 조정(대부분 기본값보다 올림)

### 3) 결과 — 대부분 음수

| 방법 | LongMemEval-s | PersonaMem-v2 | MINT-Eval |
| --- | --- | --- | --- |
| Gold Context | 84.6 | 72.9 | – |
| Full Context | 68.4 | 45.4 | 28.7 |
| **RAG 2라운드** | **81.4** | **48.7** | **33.1** |
| HippoRAG2 | 78.2 (−3.2) | 46.5 (−2.3) | 23.5 (−9.6) |
| MemOS | 76.6 (−4.8) | 50.2 (+1.5) | 19.7 (−13.4) |
| SimpleMem | 73.6 (−7.8) | 46.7 (−2.0) | 19.9 (−13.3) |
| PlugMem | 75.8 (−5.6) | 45.2 (−3.5) | 33.3 (+0.1) |
| OpenViking | 58.8 (−22.6) | 38.7 (−10.1) | 18.6 (−14.6) |

눈여겨볼 두 가지. ① **전체 기록을 다 넣는 것(Full Context)이 RAG보다 낮다** — 긴 컨텍스트에서 증거가 묻힌다. 즉 "다 주면 된다"도 답이 아니다. ② 9개 열(3벤치×3백본) 중 RAG를 이긴 칸은 드물게 흩어져 있고, 일관되게 이기는 시스템이 없다.

### 4) 세금은 어디서 생기나 — 세 갈래

**충실도(faithfulness) — 만들다가 잃는다.** 질의마다 증거가 있는 원본 턴(gold raw turns)과, 그게 메모리에서 변한 단위(gold memory units)를 따로 주고 다시 답하게 한다. gold memory unit만 줘도 점수가 gold raw turn보다 낮으면 그 차이는 **적재 단계 손실**이다. 미시 수준에서는 원본의 원자적 사실을 표본으로 뽑아 메모리에서 추적했다:

| 시스템 | 무손실 | 부분 손실 | 큰 손실 | 메모리 단위 없음 |
| --- | --- | --- | --- | --- |
| MemoryOS | 98.4 | 0.0 | 0.0 | 1.6 |
| MAGMA | 93.6 | 6.2 | 0.2 | 0.0 |
| MemOS | 85.8 | 9.0 | 2.4 | 2.8 |
| SimpleMem | 65.6 | 27.6 | 2.2 | 4.6 |
| OpenViking | 39.4 | 9.6 | 13.0 | **38.0** |

**접근성(accessibility) — 남아 있어도 못 찾는다.** MAGMA·LightMem은 gold memory unit을 주면 거의 원본 수준으로 맞히는데 원래 점수는 훨씬 낮다. 증거는 살아 있지만 *꺼내지 못한다*는 뜻. 검색을 여러 라운드 반복해 정답 단위를 다 찾을 때까지 몇 라운드 걸리는지 재면, 메모리 쪽이 첫 라운드에 찾는 비율이 RAG보다 낮다. 사례를 보면 세 패턴 — 증거가 여러 단위로 **쪼개짐**, 무관한 정보와 섞여 **희석**, 다른 말로 **바꿔 써짐**. 결과적으로 (질의, 증거) 임베딩 유사도가 원본 턴보다 메모리 단위에서 낮아진다. 비유하면 원본에는 "다음 주 화요일 3시에 치과"라고 적혀 있는데 메모리에는 "사용자는 정기적인 건강 관리 일정이 있음"으로 바뀌어 "치과 몇 시야?"와 덜 닮게 된 것.

**견고성(robustness) — 만든 모델과 읽는 모델이 다르면 더 흔들린다.** 메모리를 세 백본으로 따로 만들고 다른 백본으로 읽게 했다. 만든 모델이 바뀌면 점수가 흔들리는 건 예상대로지만, 더 흥미로운 건 **만든 것은 고정하고 읽는 모델만 약하게 바꿨을 때 낙폭이 RAG보다 큰 시스템이 많다**는 것. 오래 사는 에이전트는 모델이 교체되는데, 가공된 메모리는 그 교체에 약하다.

### 5) 벤치마크 쪽 원인 — 여유(headroom)가 없다

15개 메모리 벤치에 No Memory·IDF 키워드 매칭·RAG-Emb·RAG-Hybrid만 돌려 봤더니, 일부 벤치에서는 **희귀 키워드 매칭만으로 50% 이상**, RAG-Hybrid는 약 70%가 나왔다. 대부분의 질의가 "원본에서 정확히 찾아오기"로 풀리는 구조라 메모리가 이득을 낼 공간이 적고, 작은 손실도 점수에 그대로 드러난다. 저자들은 이게 "가볍거나 메모리 구성이 거의 없는 시스템이 강한 이유"라고 본다 — RAG의 성능을 *상속*하면서 세금은 거의 안 낸다.

### 6) 개인 비서 밖으로 — 같은 모양이 반복된다

- **경험 메모리**(과거 과제 궤적을 다음 과제에 쓰기, Qwen3.5-4B): 웹 과제(WebShop·Mind2Web)에선 긴 궤적을 워크플로·전략으로 증류한 메모리가 RAG(유사 과제 궤적을 그대로 넣기)를 이기고, 도구 사용(AppWorld·τ²-Bench)에선 여러 메모리가 진다.
- **월드 모델 메모리**(장기 장면 일관성): 과거 프레임을 그대로 검색해 다시 넣는 I3DM(SSIM .560)이 KV 캐시·학습된 KV·시각 잠재·메모리 토큰 방식들(.217~.388)을 앞선다.

### 7) 처방 — 새 구조 없이 붙일 수 있는 것

1. **편차를 복구 가능하게(원본 병행 검색).** 메모리 검색과 함께 원본 기록에서도 검색해 둘을 합쳐 재정렬한 뒤 답한다. 적재 때 잃은 것과 접근 때 놓친 것을 원본이 메운다.
2. **재귀 메모리.** 과거 질의·찾은 증거·검색 경로 자체를 메모리에 넣어, 깊은 라운드에서야 찾았던 증거를 다음 비슷한 질의가 바로 찾게 한다("기억하는 법을 기억").
3. **미래 수요 모델링(제안만).** 미리 다 가공하는 AoT 메모리는 미래 질의를 모르니 넓게·비싸게 가공해야 하고, 질의가 온 뒤 가공하는 JiT 메모리는 정확하지만 지연이 사용자에게 간다. 그 사이로, 사용자의 과거 관심·습관·접근 패턴을 "어떤 편차가 쓸모 있을지"의 사전 분포로 써서 가공 노력을 배분 — 메모리를 일종의 **암묵적 추천 시스템**으로 보는 관점.

Qwen3.6-27B 결과:

| 시스템 | LongMemEval-s 정확도 / 세금 | PersonaMem-v2 정확도 / 세금 |
| --- | --- | --- |
| SimpleMem | 73.6 / 12.0 | 46.7 / 11.2 |
| + 원본 병행 | **82.8 / 5.2** | 49.6 / 7.2 |
| + 재귀 | (해당 없음 — 질의가 코퍼스당 1개) | 46.8 / 12.1 |
| MemoryOS | 73.4 / 11.4 | 48.2 / 17.1 |
| + 원본 병행 | 76.4 / 7.8 | **53.0 / 8.5** |
| Mem-T | 75.0 / 10.8 | 42.1 / 15.2 |
| + 원본 병행 | 80.0 / 5.2 | 49.0 / 8.7 |
| + 재귀 | – | 45.7 / 13.6 |

원본 병행 검색이 확실히 크고, 재귀는 작거나 혼조다.

### 같은 날의 두 논문이 채우는 자리

- **HABIT-Bench** — 메모리 이득 쪽의 *천장*을 보여 준다. 음식·금융·소프트웨어·여행에서 수백 세션짜리 합성 사용자 기록, 습관은 선언이 아니라 선택의 반복으로만 드러나고 일시적 예외·습관 변경·사용자가 받아들이지 않은 제안이 함정. 메모리 8종 × Qwen3-235B·GLM-5.3-Flash에서 최고 매크로 33.61%. 저자 답변에 따르면 증거를 직접 줘도(Oracle Evidence, HF 댓글 인용 기준 39~58%) 한참 낮고, 활성 습관 상태와 필요 행동까지 줘야(Oracle Habit State) 98~99%. 즉 "찾기"가 아니라 **"흩어진 약한 증거로 상태를 세우기"**가 병목이고, 그건 Memory Tax가 말하는 "이득"이 나와야 할 바로 그 영역이다. 지금 메모리들은 세금은 내고 이득은 이 정도밖에 못 낸다.
- **TTME** — 다른 종류의 메모리(경험 증류)가 *가중치 업데이트*(test-time training)를 이긴 사례. 같은 발견 프레임워크에서 적응 방법만 바꿔 수학 과제 5개 모두 우위, FLOPs 82.8~84.6%↓. Memory Tax의 경험 메모리 결과(웹 과제는 증류가 이김)와 같은 쪽 — **과제 구조가 추상화를 요구하는 곳에선 가공이 이득을 낸다.**

## 실제로 쓸 수 있나

**바로 쓸 수 있다 — 처방 1번은 구현이 간단하다.** 메모리(요약·추출 사실)를 쓰는 시스템에서 원본 청크 인덱스를 지우지 않고 유지하고, 질의 시 두 소스에서 k개씩 가져와 하나의 재정렬기로 합친다. Spring 쪽으로 옮기면 pgvector에 테이블 두 개(`memory_unit`, `raw_chunk`)를 두고 두 쿼리 결과를 합쳐 cross-encoder로 다시 점수 매기는 정도다. 비용은 저장 공간과 재정렬 1회.

**Vault RAG 프로젝트(11월 예정)에 바로 걸리는 설계 판단.**

- 노트를 LLM으로 요약해 요약만 인덱싱하는 유혹이 있다 — 이 논문 기준으로는 **원본 청크 인덱스가 기본, 요약은 보조 색인**이어야 한다.
- 이 Vault는 이미 사람이 가공한 메모리다(정리본은 원 블로그의 증류). 「예습자료」 규칙이 "정리본으로 승격해도 원본 예습자료는 출처 추적용으로 남긴다"고 정한 것은 정확히 "편차를 복구 가능하게"의 사람 버전이다. RAG가 정리본과 원본(원본 URL·예습자료)을 함께 볼 수 있게 메타데이터(`원본:` 키)를 살려 두는 게 같은 원리.
- 평가는 "메모리 붙인 버전" 하나가 아니라 **원본 청크 RAG를 기준선으로 같이** 돌려 순가치를 본다. 질문 셋은 "정확히 찾아오기"형과 "여러 노트를 묶어 판단하기"형을 섞어야 이득과 세금이 둘 다 보인다.

**비용 손익분기 감각.** HF 댓글이 부록 표로 계산한 바로는, LightMem은 기록 100개 구축에 522만 토큰(기록당 약 5.2만)을 쓰고 질의당 토큰은 RAG의 3분의 1 수준이라 **기록당 약 29회 질의**에서 토큰 비용이 역전된다 — 그래도 정확도는 77% 대 82%로 RAG에 진다(댓글 작성자의 선형 외삽, 저자 확인 아님).

## 한계와 미검증 지점

- **벤치가 검색 친화적이다.** 저자 스스로 인정. 메모리가 이길 과제(장기 습관 추론, 다문서 집계)가 적은 벤치에서 "메모리가 진다"는 결론은 과장될 수 있다. HABIT-Bench가 바로 그 반대편이라 함께 봐야 한다.
- **표본·심판.** PersonaMem-v2 20%, MINT-Eval 10% 층화 표본. 채점은 Qwen3.6-27B LLM 심판 — 심판 정확도 검증 수치는 본문에서 못 봤다. 프런티어 백본은 GPT-5.6 Luna(low)까지만.
- **공정성 조정의 부작용.** Retrieval Scope를 맞추려 top-k를 올렸다 — 노출 정보량은 맞췄지만, 일부 시스템은 원래 적은 단위를 정밀하게 꺼내도록 설계돼 있어 k를 올리면 희석이 생길 수 있다. 저자는 부록 B.3에서 설정 공정성을 검증했다고 하나 읽지 못했다.
- **"세금"은 RAG에 상대적인 개념이다.** RAG 기준선이 강하게 튜닝돼 있을수록(2라운드, 하이브리드, 재정렬) 세금이 커 보인다. 기준선 설정이 결론을 좌우한다(부록 B.1 RAG 절제 실험은 미확인).
- **처방의 비용 미보고.** 원본 병행 검색이 토큰·지연을 얼마나 더 쓰는지, Gold Context와의 격차를 얼마나 메우는지는 HF 댓글이 물었지만 답이 없었다.
- **정적·오프라인·영어.** 질의가 계속 섞여 들어오는 실제 장기 배포, 다국어(한국어 노트 검색 포함)는 미검증.
- **재귀 메모리 효과는 작다.** +0.1~+3.6, 한 벤치에서만 측정 가능.

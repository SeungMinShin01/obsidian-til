# Java day16 — 스레드 동기화

> 실습 파일: `day16/exam/exam1.java`(스레드와 멀티스레드의 정의·동기화와 비동기화의 대비·같은 객체를 참조하는 두 작업 스레드·`synchronized` 메소드로 공유 자원 보호) · `day16/exam/exam2.java`(스레드 풀의 목적과 구조·`ThreadPoolExecutor`·`Runnable` 작업 객체·`submit` 으로 요청 배정·풀 상태 조회·`shutdown` 종료 예약)
> 허브: [[Java MOC]] · 이전: [[Java day15 Map과 HashMap]] · 다음: Spring Boot 프로젝트 생성(분석)

[[Java day15 Map과 HashMap]] 에서 흐름을 여러 개 띄우는 방법까지 봤다. 거기서 마지막에 남겨 둔 문제가 하나 있었다 — **여러 흐름이 같은 데이터를 건드리면 값이 어긋난다**는 것. 이번에는 그 장면을 계산기 하나로 실제로 재현하고, 막는 장치인 `synchronized` 를 붙여 결과가 어떻게 달라지는지 확인한다.

코드 자체는 짧다. 계산기 하나, 스레드 둘, 메소드 하나가 전부다. 그런데 여기에 멀티스레드에서 어려운 부분이 거의 다 들어 있다.

뒤쪽 절반(1-8 이후)은 방향이 다르다. 앞에서 본 것이 "흐름끼리 부딪히는 문제"였다면, 이번에는 **흐름을 몇 개나 띄울 것인가** 하는 문제다. 지금까지는 필요할 때마다 `new` 로 스레드를 만들어 썼는데, 요청이 몰리는 환경에서는 그 방식 자체가 부담이 된다. 그래서 미리 만들어 두고 돌려 쓰는 **스레드 풀**을 콜센터 상담 시뮬레이션으로 확인한다.

## 1. 배운 내용

### 1-1. 스레드와 멀티스레드를 다시 세워 두기

**스레드는 코드 실행 흐름의 단위**다. 프로그램이 시작되면 JVM이 main 스레드를 만들고 `main` 메소드를 실행하며, 그 흐름 하나로 위에서 아래로 내려간다.

**멀티스레드는 그 흐름을 여러 개 두는 것**이다. 왜 그렇게 하는지는 웹 서버를 놓고 보면 분명하다.

```
사용자 A 요청 ─┐
사용자 B 요청 ─┼─→ 웹서버(톰캣) ─→ 요청 하나당 스레드 하나
사용자 C 요청 ─┘
```

여러 사용자가 동시에 하나의 서버에 요청을 보낸다. 요청을 한 줄로 세워 하나씩 처리하면 앞사람이 끝날 때까지 뒷사람은 기다려야 하므로, 서버는 요청마다 흐름을 하나씩 붙여 **다중 처리**한다.

| | 내용 |
| --- | --- |
| 장점 | 여러 요청을 동시에 처리한다 — 기다림이 줄어든다 |
| 단점 | 관리가 어렵다 — 동기화 문제와 과부하 |

장점은 직관적인데 단점 쪽이 이번 주제다. 흐름이 늘어나면 **서로 같은 것을 건드릴 가능성**이 생기고, 그때부터 "잘 돌아가는 것처럼 보이는데 값이 이상한" 상태가 나타난다.

### 1-2. 동기화와 비동기화

같은 메소드를 여러 흐름이 부를 때 처리 방식이 둘로 갈린다.

| 구분 | 점유 | 성질 | 쓰는 자리 |
| --- | --- | --- | --- |
| **동기화** | 락(대기) 상태를 이용해 **한 스레드만** 메소드를 점유 | 무결성 보장, 대신 줄을 선다 | 순서가 필요한 경우 |
| **비동기화** | **여러 스레드**가 하나의 메소드를 같이 점유 | 무결성 보장 없음, 대신 빠르다 | 순서가 필요 없는 경우, 요청 후 다른 작업을 이어가야 하는 경우 |

핵심은 **락(lock)** 이다. 동기화는 "이 구간은 한 번에 한 명만"이라는 표찰을 걸어 두는 것이고, 먼저 들어간 흐름이 나올 때까지 뒤에 온 흐름은 **대기 상태**로 멈춰 선다. 화장실 문을 잠그는 그림으로 잡아 두면 된다 — 안전하지만 줄이 생긴다.

자바에서 이 표찰이 `synchronized` 키워드이고, **기본값은 비동기화**다. 아무것도 붙이지 않으면 여러 흐름이 같은 메소드에 동시에 들어간다.

### 1-3. 공유 자원 — 문제가 생기는 조건

먼저 계산기를 만든다. 필드 하나와 메소드 하나뿐이다.

```java
class 계산기 {
    public int memory;                       // 상태를 담는 자리

    public void setMemory(int memory) {
        this.memory = memory;
        try {
            Thread.sleep(2000);              // 2초 대기
            System.out.println("현재계산기의 값 " + this.memory);
        } catch (Exception e) {
            System.out.println(e);
        }
    }
}
```

용어를 다시 정리하면 이렇다 — 클래스는 인스턴스의 **설계도**이지 실체가 아니다. 멤버 변수(`memory`)는 인스턴스의 상태를 담는 자리라 **인스턴스마다 따로 할당**되고, 메소드는 인스턴스의 행위라 **여러 인스턴스가 함께 쓴다.** `this` 는 지금 이 메소드를 호출한 인스턴스를 가리킨다 — Java day05 클래스와 인스턴스 · Java day06 생성자와 콘솔 게시판 에서 정리한 그대로다.

메소드 안에 `Thread.sleep(2000)` 을 넣은 것이 실습의 장치다. 값을 넣고 **2초 뒤에 출력**하도록 만들어, 그 사이에 다른 흐름이 끼어들 틈을 일부러 벌려 둔 것이다. 실제 프로그램에서는 이 자리가 DB 조회나 파일 입출력처럼 시간이 걸리는 작업이 된다.

이제 그 계산기를 두 흐름이 나눠 쓴다.

```java
class 스레드1 extends Thread {
    public 계산기 calculator;
    @Override
    public void run() { calculator.setMemory(100); }
}

class 스레드2 extends Thread {
    public 계산기 cacluator;
    @Override
    public void run() { cacluator.setMemory(200); }
}
```

둘 다 `extends Thread` 방식([[Java day15 Map과 HashMap]] 1-14의 ③)이고, `run()` 안에서 하는 일은 계산기에 값을 대입하는 것 하나뿐이다. 각자 필드로 계산기를 하나 들고 있다는 점을 눈여겨본다.

```java
계산기 calculator = new 계산기();   // 계산기는 하나만 만든다

스레드1 thread1 = new 스레드1();
thread1.calculator = calculator;

스레드2 thread2 = new 스레드2();
thread2.cacluator = calculator;     // 같은 계산기를 넣는다

thread1.start();
thread2.start();
```

`new 계산기()` 가 **한 번만** 나온다는 것이 전부다. 두 스레드의 필드에 같은 주소를 넣었으니 **서로 다른 스레드가 동일한 객체를 참조**하는 상태가 된다. 이렇게 여러 흐름이 함께 보는 객체를 **공유 자원**이라고 부른다.

문제가 생기는 조건을 정리하면 이렇다.

1. 흐름이 둘 이상이고
2. 같은 객체를 보고 있고
3. 그 객체의 상태를 **바꾸는** 동작이 있다

셋이 모두 겹칠 때만 어긋난다. 각자 다른 계산기를 만들었다면 아무 일도 일어나지 않고, 읽기만 한다면 역시 문제가 없다. Java day05 클래스와 인스턴스 에서 참조 타입 변수가 값이 아니라 주소를 들고 있다고 정리한 것이 여기서 의미를 갖는다 — 대입은 복사가 아니라 **같은 것을 함께 보게 만드는** 동작이다.

### 1-4. 비동기화 — 값이 어긋나는 장면

`synchronized` 없이 그대로 두면 이렇게 흘러간다.

```
시각   스레드1                    스레드2                   memory
----------------------------------------------------------------
0초    memory = 100                                          100
       sleep(2000) 시작
0초                              memory = 200                200
                                 sleep(2000) 시작
2초    출력 → 200                                            200
2초                              출력 → 200                  200
```

출력은 **200, 200** 이다. 스레드1은 분명 100을 넣었는데, 자는 동안 스레드2가 같은 필드를 200으로 바꿔 버려서 깨어나 보니 200이 되어 있다.

여기서 짚어 둘 것은 **스레드1이 잘못한 것이 없다**는 점이다. 값을 넣고, 잠시 다른 일을 하고, 자기 값을 읽었을 뿐이다. 코드만 읽으면 100이 나와야 맞는데 실제로는 200이 나온다. 이런 상태를 **경쟁 상태(race condition)** 라고 부른다.

| | |
| --- | --- |
| 코드에서 보이는 것 | 값을 넣는다 → 잠시 뒤 → 그 값을 읽는다 |
| 실제로 일어나는 것 | 값을 넣는다 → **그 사이 누군가 바꾼다** → 바뀐 값을 읽는다 |

"넣은 것과 읽은 것 사이"에 틈이 있다는 것이 문제의 본질이다. 그 틈이 `sleep(2000)` 처럼 눈에 보이면 재현이 쉽지만, 실제로는 한 줄짜리 연산 안에도 틈이 있다(3-1). 그래서 이 오류는 **평소에는 잘 돌아가다가 부하가 몰릴 때만 가끔 틀리는** 형태로 나타나 찾기가 어렵다.

`sleep` 을 넣어 틈을 벌린 이유가 이것이다. 확률에 맡기면 백 번 돌려도 안 나올 수 있는 상황을 **매번 재현되게** 만든 것이다.

### 1-5. 동기화 — synchronized를 붙이면

메소드 선언에 키워드 하나를 넣는다.

```java
public synchronized void setMemory(int memory) {
    this.memory = memory;
    try {
        Thread.sleep(2000);
        System.out.println("현재계산기의 값 " + this.memory);
    } catch (Exception e) {
        System.out.println(e);
    }
}
```

이번에는 흐름이 이렇게 갈린다.

```
시각   스레드1                    스레드2                   memory
----------------------------------------------------------------
0초    락 획득                                                
       memory = 100              락 대기(멈춤)               100
       sleep(2000)
2초    출력 → 100                                            100
       락 반납
2초                              락 획득
                                 memory = 200                200
                                 sleep(2000)
4초                              출력 → 200                  200
```

출력은 **100, 200** 이다. 각 스레드가 자기가 넣은 값을 그대로 읽는다.

달라진 점은 하나다. 스레드1이 메소드 안에 있는 동안 **스레드2가 문 앞에서 멈춰 있다.** `sleep(2000)` 중이어도 마찬가지다 — 자고 있든 일하고 있든 메소드를 나가지 않았으면 락은 계속 쥐고 있다.

| | 비동기화 | 동기화 |
| --- | --- | --- |
| 메소드 점유 | 여러 스레드가 동시에 | 한 스레드만 |
| 출력 | 200, 200 | 100, 200 |
| 걸리는 시간 | 약 2초 | 약 4초 |
| 값의 정확성 | 보장 없음 | 보장 |

**시간이 두 배가 되었다**는 것을 함께 봐 둔다. 동기화는 공짜가 아니다. 병렬로 돌던 것이 순서대로 도니 멀티스레드로 얻으려던 이점이 그만큼 사라진다. 안전과 속도를 맞바꾼 셈이라, 어디에 붙일지가 곧 설계 문제가 된다(2-2).

### 1-6. 무엇이 잠기는가 — 락의 주인은 객체다

`synchronized` 를 메소드에 붙였을 때 정확히 무엇이 잠기는지를 잡아 둔다. 잠기는 것은 **메소드가 아니라 인스턴스**다.

인스턴스 메소드에 `synchronized` 를 붙이면 그 메소드를 호출한 객체(`this`)의 락을 잡는다. 그래서 이런 성질이 따라온다.

| 상황 | 결과 |
| --- | --- |
| 두 스레드가 **같은 계산기**의 `setMemory` 호출 | 한 명씩 — 이번 실습의 경우 |
| 두 스레드가 **각자 다른 계산기**의 `setMemory` 호출 | 동시에 들어간다 — 막을 이유가 없다 |
| 한 객체에 `synchronized` 메소드가 여러 개 | 락이 하나뿐이라 **서로 다른 메소드끼리도** 줄을 선다 |

세 번째 줄이 놓치기 쉬운 부분이다. `setMemory` 와 `getMemory` 둘 다 `synchronized` 라면, 한 스레드가 `setMemory` 안에 있는 동안 다른 스레드는 `getMemory` 에도 못 들어간다. 락이 메소드마다 하나가 아니라 **객체마다 하나**이기 때문이다.

두 번째 줄도 함께 기억해 둘 만하다. 계산기를 스레드마다 하나씩 만들었다면 애초에 공유 자원이 아니므로 동기화가 필요 없다. **가장 확실한 동기화는 공유하지 않는 것**이라는 이야기가 여기서 나온다(3-3).

### 1-7. 정리 — 흐름을 나눈 대가

day15에서 흐름을 나눠 얻은 것과, 이번에 확인한 대가를 나란히 두면 이렇다.

| | 얻은 것 | 잃은 것 |
| --- | --- | --- |
| 흐름을 나누면 | 기다리는 동안 다른 일을 한다 | 실행 순서를 예측할 수 없다 |
| 상태를 공유하면 | 흐름끼리 데이터를 주고받기 쉽다 | **값이 어긋날 수 있다** |
| 동기화를 걸면 | 값이 정확해진다 | 다시 순서대로 돈다 — 느려진다 |

세 줄이 서로를 물고 있다. 멀티스레드 설계가 어려운 이유는 문법이 아니라 이 맞바꿈을 어디서 끊을지 정하는 일에 있다. 실무의 방향은 대체로 **공유를 줄이고, 꼭 공유해야 하는 지점만 최소로 잠근다** 쪽이다.

### 1-8. 스레드 풀 — 흐름을 미리 만들어 두고 돌려 쓰기

여기서부터는 다른 문제다. 지금까지는 스레드가 필요할 때마다 `new 스레드1()` 처럼 하나씩 만들었다. 요청이 두세 개면 괜찮은데, 1-1의 웹서버처럼 요청이 초당 수백 개씩 들어오면 이야기가 달라진다.

**스레드 풀은 매번 새 스레드를 만들지 않고, 미리 일정한 수의 스레드를 풀(pool)에 만들어 두고 재사용하는 방식**이다. 목적은 하나로 정리된다 — **과부하 방지**.

| 방식 | 흐름 |
| --- | --- |
| 매번 생성 | 요청 → 스레드 생성 → 처리 → 스레드 소멸 (요청 수만큼 스레드) |
| 스레드 풀 | 요청 → **대기 중인 스레드에 배정** → 처리 → **스레드는 풀로 복귀** (스레드 수는 고정) |

스레드를 만드는 일 자체가 공짜가 아니라는 것이 출발점이다. 스레드 하나마다 자기 스택 메모리를 잡고([[Java day15 Map과 HashMap]] 3-4), OS 수준의 등록 작업이 따라붙는다. 요청 1000개에 스레드 1000개를 만들면 일하는 시간보다 만들고 없애는 시간이 더 커지고, 메모리도 함께 밀린다.

구조는 **선입선출(queue)** 이다 — [[Java day15 Map과 HashMap]] 1-11에서 정리한 `Queue` 의 성질이 그대로 쓰인다.

```
요청 5 4 3 2 1 →  [작업 큐]  →  ┌ 스레드A (작업 중)
                                ├ 스레드B (작업 중)
                                └ 스레드C (작업 중)
```

- 먼저 들어온 요청부터 **대기 중인 스레드**가 가져가 처리한다
- 대기 중인 스레드가 없으면 요청은 큐에서 **대기(wait) 상태**로 기다린다
- 스레드가 작업을 끝내면 큐에서 다음 요청을 꺼내 처리한다

풀의 크기가 곧 **동시에 처리할 수 있는 최대 개수**가 된다. 요청이 아무리 몰려도 스레드 수는 그 이상 늘지 않으니, 서버가 감당할 수 있는 선을 숫자로 정해 두는 셈이다.

### 1-9. 풀 만들기 — Executors와 ThreadPoolExecutor

실습에서는 콜센터를 흉내 낸다. 상담원(스레드) 3명이 고객(요청)을 순서대로 받는 구조다.

```java
import java.util.concurrent.Executors;
import java.util.concurrent.ThreadPoolExecutor;

ThreadPoolExecutor poolExecutor =
        (ThreadPoolExecutor) Executors.newFixedThreadPool(3);
```

한 줄에 두 가지가 들어 있다.

| 요소 | 역할 |
| --- | --- |
| `Executors` | 풀을 만들어 주는 **팩토리 클래스** — 목적별 메소드를 갖고 있다 |
| `newFixedThreadPool(3)` | 크기가 3으로 **고정된** 풀을 만든다 |
| `ThreadPoolExecutor` | 실제 풀 구현 클래스 — 상태 조회 메소드를 갖고 있다 |
| `(ThreadPoolExecutor)` 캐스팅 | 반환 타입이 `ExecutorService` 라 다운캐스팅해서 받는다 |

`Executors.newFixedThreadPool()` 의 반환 타입은 상위 인터페이스인 `ExecutorService` 다. 그대로 받으면 작업을 넣고 종료하는 기본 동작만 쓸 수 있고, 풀의 내부 상태(작업 중인 스레드 수 등)를 들여다보려면 구현 클래스인 `ThreadPoolExecutor` 로 내려서 받아야 한다. Java day10 상속과 다형성 의 다운캐스팅과 Java day11 인터페이스 의 "인터페이스로 받고 구현체로 갈아 끼운다"가 여기서 함께 쓰인다.

### 1-10. 작업 객체 — Runnable 구현체 하나가 요청 하나

풀에 넣는 것은 스레드가 아니라 **작업**이다. 작업은 `Runnable` 을 구현한 클래스로 만든다.

```java
class CallTask implements Runnable {
    private Random random = new Random();
    private int id;                       // 요청 식별용

    public CallTask(int id) { this.id = id; }

    @Override
    public void run() {
        String threadName = Thread.currentThread().getName();
        try {
            System.out.println(threadName + "상담원이 고객통화 시작됨 고객 id: " + id);
            Thread.sleep(6000 + random.nextInt(6000));   // 6~12초
        } catch (Exception e) {
            System.out.println("상담원이 고객통화 종료됨");
        }
    }
}
```

[[Java day15 Map과 HashMap]] 1-14에서 정리한 멀티스레드 구현 세 가지 중 **`Runnable` 구현** 방식이다. 스레드 풀에서는 이 방식이 강제되는 셈인데, 이유가 분명하다.

| | `extends Thread` | `implements Runnable` |
| --- | --- | --- |
| 정체 | **흐름 그 자체** | **흐름이 할 일**(작업 명세) |
| 스레드 풀 | 못 쓴다 — 풀은 흐름을 이미 갖고 있다 | 쓴다 — 할 일만 넘기면 된다 |

풀에는 스레드가 이미 3개 만들어져 있으니, 넘겨야 하는 것은 새 흐름이 아니라 **"이걸 해 달라"는 지시서**다. `Runnable` 이 정확히 그 지시서다. 1-3에서 `extends Thread` 를 쓴 것과 갈리는 지점이고, 실무에서 `Runnable` 을 권하는 이유이기도 하다.

몇 가지를 더 짚어 둔다.

- **`Thread.currentThread().getName()`** — 지금 이 `run()` 을 실행하고 있는 스레드의 이름을 가져온다. 풀에서는 `pool-1-thread-1` 같은 이름이 붙어서, 같은 스레드가 여러 작업을 **재사용**되는 것을 눈으로 확인할 수 있다. 스레드 풀이 도는 모습을 보려면 이 한 줄이 가장 중요하다
- **생성자로 받은 `id`** — 작업마다 다른 값을 들고 있어야 하니 필드로 잡는다. 여기서 각 작업 객체가 자기 상태만 갖는 형태가 되어, 1-3에서 본 공유 자원 문제가 애초에 생기지 않는다(2-2의 "무상태·비공유" 방향)
- **`Random`** — 상담 시간을 6~12초로 흩뜨려, 상담원마다 끝나는 시점이 달라지게 만든다. 균일하면 풀이 도는 모습이 잘 안 보인다

### 1-11. 요청 배정과 풀 상태 들여다보기

만든 작업을 풀에 넘긴다.

```java
CallTask task = new CallTask(i);   // i번째 요청 생성
poolExecutor.submit(task);         // 스레드 풀에 배정
```

`submit()` 이 하는 일은 **작업을 큐에 넣는 것**까지다. 실제로 언제 실행되는지는 풀이 정한다 — 대기 중인 스레드가 있으면 바로, 없으면 큐에서 기다렸다가. `start()` 로 흐름을 직접 띄우던 것과 달리, **실행 시점의 결정권이 풀로 넘어간다.**

풀이 지금 어떤 상태인지는 조회 메소드로 확인한다.

```java
int 작업중인스레드수 = poolExecutor.getActiveCount();
int 대기중인스레드수 = poolExecutor.getCorePoolSize();
int 대기중인요청수  = poolExecutor.getQueue().size();
```

| 메소드 | 반환하는 값 |
| --- | --- |
| `getActiveCount()` | 지금 **작업을 실행 중인** 스레드 수 |
| `getCorePoolSize()` | 풀의 **기본 크기**(설정값) — 여기서는 3으로 고정 |
| `getPoolSize()` | 현재 풀에 **만들어져 있는** 스레드 수 |
| `getQueue().size()` | 큐에서 **대기 중인 작업** 수 |
| `getCompletedTaskCount()` | 지금까지 **끝난 작업** 수 |

세 지표를 함께 보면 풀의 상태가 한눈에 잡힌다. 고정 크기 3인 풀이라면 `getActiveCount()` 는 0~3 사이에서만 움직이고, 요청이 그보다 빨리 들어오면 넘치는 만큼이 `getQueue().size()` 로 쌓인다. **처리 속도보다 요청이 빠르면 큐가 계속 길어진다**는 것이 이 실습에서 눈으로 확인되는 부분이다.

- 요청 간격 3초, 상담 시간 6~12초, 상담원 3명 — 들어오는 속도가 처리 속도를 앞서므로 큐가 쌓인다
- 대기 중인 스레드 수를 알고 싶으면 `getPoolSize() - getActiveCount()` 로 계산한다. `getCorePoolSize()` 는 실시간 상태가 아니라 설정값 쪽이다

### 1-12. 종료 — shutdown은 "예약"이다

작업을 다 넣었으면 풀을 닫는다.

```java
poolExecutor.shutdown();   // 20개 배정 후 종료 예약
```

`shutdown()` 은 **즉시 멈추는 것이 아니라 종료를 예약하는 것**이다.

| 메소드 | 동작 |
| --- | --- |
| `shutdown()` | 새 작업은 더 받지 않고, **이미 들어온 작업은 전부 끝낸 뒤** 종료 |
| `shutdownNow()` | 실행 중인 작업에 인터럽트를 걸고 **즉시** 종료 시도, 대기 중인 작업 목록 반환 |
| `awaitTermination(t, unit)` | 종료될 때까지 지정 시간만큼 기다린다 |
| `isShutdown()` / `isTerminated()` | 종료 요청됨 / 실제로 다 끝남 |

종료를 반드시 불러 줘야 하는 이유가 있다. 풀의 스레드는 **비데몬 스레드**라, 작업이 없어도 JVM이 살아 있는 한 대기 상태로 남는다. `shutdown()` 을 부르지 않으면 main이 끝나도 프로그램이 종료되지 않는다. [[Java day15 Map과 HashMap]] 2-12에서 타이머 스레드에 플래그를 두고 껐던 것과 같은 이야기 — **띄운 흐름은 끄는 방법까지 함께 만들어 둔다.**

### 1-13. 정리 — 콜센터 그림으로

이번 실습의 비유를 그대로 두면 구조가 오래 남는다.

| 코드 | 콜센터 |
| --- | --- |
| `newFixedThreadPool(3)` | 상담원 3명을 고용 |
| `CallTask` | 고객 한 명의 상담 요청 |
| `submit(task)` | 대기열에 고객 등록 |
| `getActiveCount()` | 지금 통화 중인 상담원 수 |
| `getQueue().size()` | 대기실에서 기다리는 고객 수 |
| `shutdown()` | 오늘 접수 마감 — 대기 고객은 다 받고 퇴근 |

앞부분(1-1~1-7)과 이어 보면 멀티스레드를 다루는 두 축이 갖춰진다.

| 문제 | 장치 |
| --- | --- |
| 흐름끼리 같은 데이터를 건드려 값이 어긋난다 | `synchronized` — 잠금 |
| 흐름을 무한정 만들어 자원이 밀린다 | 스레드 풀 — 개수 제한 |

실무에서 스레드를 직접 `new` 하는 코드를 보기 어려운 이유가 여기 있다. 흐름의 개수는 풀이 관리하고, 개발자는 **작업(`Runnable`)을 정의해서 넘기는 일**에 집중한다.

## 2. 추가로 알면 좋은 활용법

### 2-1. synchronized 블록 — 필요한 줄만 잠그기

메소드 전체가 아니라 일부 구간만 잠글 수도 있다.

```java
public void setMemory(int memory) {
    준비작업();                       // 잠기지 않는다
    synchronized (this) {
        this.memory = memory;        // 이 구간만 한 명씩
    }
    뒷정리();                         // 잠기지 않는다
}
```

괄호 안에는 **락으로 쓸 객체**를 넣는다. `this` 를 넣으면 메소드에 `synchronized` 를 붙인 것과 같은 범위가 되고, 다른 객체를 넣으면 그 객체의 락을 쓴다.

| 형태 | 잠기는 범위 |
| --- | --- |
| `public synchronized void m()` | 메소드 전체, 락은 `this` |
| `synchronized (this) { }` | 블록 안, 락은 `this` |
| `synchronized (자물쇠객체) { }` | 블록 안, 락은 지정한 객체 |
| `public static synchronized void m()` | 메소드 전체, 락은 **클래스 객체** |

블록을 쓰는 이유는 **잠긴 구간을 짧게 유지**하기 위해서다. 이번 실습의 `sleep(2000)` 처럼 오래 걸리는 작업이 락 안에 들어 있으면 그동안 다른 흐름이 전부 멈춰 선다. 실제 코드라면 시간이 걸리는 부분은 락 밖으로 빼고, 상태를 바꾸는 한두 줄만 감싸는 편이 낫다.

락 전용 객체를 따로 두는 방법도 흔하다.

```java
private final Object lock = new Object();
synchronized (lock) { /* ... */ }
```

`this` 를 락으로 쓰면 바깥 코드가 그 객체를 락으로 잡을 수도 있어서, 의도하지 않은 곳에서 얽힐 여지가 생긴다. 잠금 전용 필드를 두면 그 락을 누가 잡는지가 클래스 안으로 닫힌다.

### 2-2. 어디에 붙일지 — 잠글 것과 잠그지 않을 것

동기화가 필요한 자리는 1-3의 세 조건이 모두 겹치는 곳뿐이다.

| 대상 | 필요 여부 |
| --- | --- |
| 지역 변수 | 필요 없다 — 스레드마다 따로 잡힌다 |
| 읽기만 하는 값 | 필요 없다 — 바뀌지 않으면 어긋날 일이 없다 |
| `final` 로 굳힌 불변 객체 | 필요 없다 |
| 여러 흐름이 **바꾸는** 필드 | 필요하다 |
| 여러 흐름이 공유하는 컬렉션 | 필요하다 — 또는 동시성 컬렉션으로 교체 |

지역 변수가 안전한 이유는 [[Java day15 Map과 HashMap]] 3-4에서 정리한 스택 구조에 있다. 메소드 호출마다 자기 스택 영역이 잡히고 **스택은 스레드마다 따로** 있어서, 흐름이 달라지면 지역 변수도 다른 자리에 놓인다. 공유되는 것은 힙에 놓인 객체 쪽이다.

그래서 "동기화를 어디에 걸까"보다 **"이 필드를 정말 공유해야 하나"** 를 먼저 묻는 편이 낫다. 공유를 없앨 수 있으면 잠금도 함께 사라진다.

### 2-3. 대기와 깨우기 — wait와 notify

락은 "한 명씩 들어가라"까지만 정한다. **순서**를 정하려면 다른 장치가 필요하다.

```java
synchronized (공유객체) {
    while (조건이_아직이면) {
        공유객체.wait();      // 락을 놓고 대기
    }
    처리();
    공유객체.notifyAll();     // 대기 중인 흐름들을 깨운다
}
```

| 메소드 | 하는 일 |
| --- | --- |
| `wait()` | **락을 반납하고** 대기 — 다른 흐름이 들어올 수 있다 |
| `notify()` | 대기 중인 흐름 하나를 깨운다 |
| `notifyAll()` | 대기 중인 흐름을 전부 깨운다 |

`Thread.sleep()` 과 갈리는 자리를 잡아 둔다. **`sleep` 은 락을 쥔 채로 잔다.** 이번 실습에서 스레드2가 2초를 통째로 기다린 이유가 그것이다. 반면 `wait()` 는 락을 놓고 자리를 비켜 준다.

세 메소드 모두 `Object` 클래스에 있다 — Java day13 Object 클래스와 리플렉션 에서 본 최상위 클래스에 이런 것까지 들어 있는 이유가 **락의 주인이 객체이기 때문**이다(1-6). 락을 가진 상태에서만 부를 수 있어서, `synchronized` 블록 밖에서 호출하면 예외가 난다.

생산자·소비자 구조(한쪽이 만들어 넣고 다른 쪽이 꺼내 쓰는 형태)가 이 조합의 대표 활용이다. 다만 지금은 이 저수준 도구를 직접 쓰기보다 `BlockingQueue` 같은 완성된 클래스를 쓰는 쪽이 관례다.

### 2-4. 동시성 컬렉션 — 잠금이 이미 들어 있는 도구들

여러 흐름이 같은 목록을 건드릴 때, 직접 `synchronized` 를 두르는 대신 준비된 클래스를 쓴다.

| 클래스 | 성격 |
| --- | --- |
| `ConcurrentHashMap` | 구간별로 잠가 `HashMap` 보다 훨씬 덜 막힌다 |
| `CopyOnWriteArrayList` | 쓸 때 복사 — 읽기가 압도적으로 많을 때 |
| `BlockingQueue` | 비면 기다리고 차면 기다린다 — 작업 큐의 기본 |
| `AtomicInteger`·`AtomicLong` | 락 없이 증감 — `incrementAndGet()` |
| `Collections.synchronizedList(list)` | 기존 목록을 감싸 잠금을 붙인다 |

Java day14 제네릭 과 [[Java day15 Map과 HashMap]] 에서 `Vector`·`HashTable` 이 "동기화 지원"이라고 붙어 있던 이유가 여기서 이어진다. 옛 방식은 **메소드마다 전부 잠가** 안전한 대신 느렸고, 지금은 잠금 없는 클래스를 기본으로 두고 공유가 실제로 필요한 자리에만 동시성 클래스를 쓴다.

`AtomicInteger` 는 특히 자주 쓰인다. 카운터 하나를 위해 락을 거는 대신, CPU가 제공하는 원자적 연산으로 처리해 훨씬 가볍다.

### 2-5. volatile은 동기화가 아니다

[[Java day15 Map과 HashMap]] 2-12에서 플래그에 `volatile` 을 붙였던 것과 `synchronized` 는 역할이 다르다.

| 키워드 | 보장하는 것 | 보장하지 않는 것 |
| --- | --- | --- |
| `volatile` | **가시성** — 바뀐 값이 다른 흐름에 바로 보인다 | 원자성 — `count++` 는 여전히 어긋난다 |
| `synchronized` | 가시성 + **원자성** — 구간을 통째로 한 명씩 | — |

플래그처럼 **한쪽이 쓰고 다른 쪽이 읽기만 하는** 값에는 `volatile` 로 충분하다. `setMemory` 처럼 **읽고 바꾸는 동작이 섞이면** `volatile` 만으로는 부족하고 락이 필요하다.

둘을 "약한 것과 강한 것"으로 세워 두면 고르기가 쉽다 — 신호 전달은 `volatile`, 상태 변경은 `synchronized`.

### 2-6. 웹 애플리케이션에서 만나는 자리

1-1에서 톰캣 이야기가 나온 이유가 여기 있다. 서버는 요청마다 스레드를 붙이므로, **서버 코드는 기본적으로 멀티스레드 환경에서 돈다.** 지금까지 만든 DAO·Controller가 그대로 그 환경에 놓이면 어떤 자리가 위험한지 정리해 둔다.

| 자리 | 위험 여부 |
| --- | --- |
| 메소드 안의 지역 변수 | 안전 |
| DB에서 꺼내 만든 DTO | 안전 — 요청마다 새로 만든다 |
| 싱글톤 객체의 **필드** | 위험 — 모든 요청이 같은 객체를 본다 |
| static 변수 | 위험 — 같은 이유 |

Java day11 종합예제 인터페이스 DAO · Java day12 종합예제 JDBC DAO 에서 DAO를 싱글톤으로 둔 구조가 이 표의 세 번째 줄에 해당한다 — [[개념 - 싱글톤]] 으로 하나만 만들어 공유하는 것이 곧 공유 자원을 만드는 일이기 때문이다.

다만 싱글톤 자체가 문제는 아니다. **필드에 상태를 들고 있지 않으면** 여러 흐름이 같은 객체의 메소드를 동시에 불러도 어긋날 것이 없다. 지금까지 만든 DAO들이 필드 없이 메소드만 갖고 있었던 것이 결과적으로 안전한 형태였던 셈이다. 이런 객체를 **무상태(stateless)** 라고 부르고, 서버 쪽 클래스를 설계할 때의 기본 방침이 된다.

### 2-7. Executors의 팩토리 메소드 — 풀 고르기

`newFixedThreadPool` 말고도 목적별로 준비된 것들이 있다.

| 메소드 | 성격 | 쓰는 자리 |
| --- | --- | --- |
| `newFixedThreadPool(n)` | 크기 고정 n개 | 동시 처리량을 정해 두고 싶을 때 — 가장 흔하다 |
| `newCachedThreadPool()` | 필요하면 늘리고, 60초 놀면 회수 | 짧은 작업이 불규칙하게 몰릴 때 |
| `newSingleThreadExecutor()` | 스레드 1개 | **순서 보장**이 필요할 때 — 큐에 넣은 순서대로 |
| `newScheduledThreadPool(n)` | 지연·주기 실행 | 몇 초 뒤에 / 몇 초마다 반복 |
| `newWorkStealingPool()` | CPU 코어 수에 맞춰 작업 훔치기 | 계산량이 많은 병렬 작업 |

`newSingleThreadExecutor()` 는 이름과 달리 동기화의 대안이 되기도 한다. 상태를 건드리는 작업을 전부 이 풀 하나에 몰아넣으면 **한 번에 하나씩만** 실행되니, 락을 걸지 않아도 어긋날 일이 없다. "잠그는 대신 한 줄로 세운다"는 접근이다.

`newScheduledThreadPool` 은 [[Java day15 Map과 HashMap]] 2-11의 시계 스레드처럼 `while` + `sleep` 으로 만들던 주기 작업을 대신한다.

```java
ScheduledExecutorService s = Executors.newScheduledThreadPool(1);
s.scheduleAtFixedRate(작업, 0, 1, TimeUnit.SECONDS);   // 1초마다
```

### 2-8. submit과 execute — 결과를 돌려받기

작업을 넣는 방법이 둘이다.

| 메소드 | 매개변수 | 반환 | 예외가 나면 |
| --- | --- | --- | --- |
| `execute(Runnable)` | `Runnable` | 없음 | 그대로 밖으로 터진다 |
| `submit(Runnable)` | `Runnable` | `Future<?>` | `Future` 안에 담긴다 |
| `submit(Callable<T>)` | `Callable<T>` | `Future<T>` | `Future` 안에 담긴다 |

`Runnable` 의 `run()` 은 반환값이 없다(`void`). 계산 결과를 받아야 하면 `Callable<T>` 를 쓴다.

```java
Callable<Integer> 작업 = () -> { return 1 + 2; };
Future<Integer> future = poolExecutor.submit(작업);
Integer 결과 = future.get();     // 끝날 때까지 기다렸다가 받는다
```

`Future` 는 **아직 오지 않은 결과를 담아 두는 상자**다. `submit()` 은 상자를 즉시 돌려주고, `get()` 을 부르는 순간 작업이 끝날 때까지 기다린다. Java day14 제네릭 의 타입 파라미터가 여기서 반환 타입을 정하는 자리로 쓰인다.

`submit()` 을 쓰면 작업 안에서 난 예외가 밖으로 드러나지 않고 `Future` 에 담긴다는 점은 함께 기억해 둘 만하다. `get()` 을 부르지 않으면 예외가 조용히 묻히므로, 결과를 안 쓸 작업이라도 예외 처리는 `run()` 안에서 마무리하는 편이 안전하다.

### 2-9. 풀에 넣을 작업을 만드는 세 가지 모양

`Runnable` 구현체는 형태를 바꿔 쓸 수 있다 — Java day11 인터페이스 에서 정리한 구현 방식이 그대로 적용된다.

```java
// ① 클래스로 선언 — 생성자로 값을 받아야 할 때
class CallTask implements Runnable { /* ... */ }

// ② 익명 구현체 — 한 번만 쓸 때
poolExecutor.submit(new Runnable() {
    @Override public void run() { /* ... */ }
});

// ③ 람다 — Runnable은 메소드가 하나뿐이라 가능
poolExecutor.submit(() -> { /* ... */ });
```

메소드가 하나뿐인 인터페이스를 **함수형 인터페이스**라고 부르고, 이런 인터페이스만 람다로 줄여 쓸 수 있다. `Runnable`·`Callable`·`Comparator` 가 대표적이다. 실습처럼 `id` 같은 값을 들고 있어야 하면 ①이 편하고, 상태 없이 한 번 쓰고 마는 작업이면 ③이 짧다.

### 2-10. 풀 크기를 얼마로 잡을까

고정 풀을 쓰기로 했으면 다음 질문은 숫자다. 작업의 성격에 따라 기준이 갈린다.

| 작업 성격 | 기준 | 이유 |
| --- | --- | --- |
| CPU 위주(계산·인코딩) | 코어 수 내외 | 흐름을 늘려도 CPU가 하나씩만 처리한다 |
| I/O 위주(DB·파일·네트워크) | 코어 수보다 크게 | 기다리는 동안 다른 작업을 할 수 있다 |

코어 수는 `Runtime.getRuntime().availableProcessors()` 로 얻는다. 실습의 상담 작업처럼 대부분을 기다리는 데 쓰는 작업이라면 풀을 코어 수보다 크게 잡아도 낭비가 아니다 — 스레드가 CPU를 붙잡고 있는 게 아니라 자고 있기 때문이다.

풀이 너무 크면 스레드 전환 비용과 메모리가 늘고, 너무 작으면 큐가 계속 길어진다. 1-11의 세 지표를 찍어 보면서 맞춰 가는 것이 실제 방법이다.

## 3. 더 나아가 알면 좋은 것

### 3-1. 한 줄도 원자적이지 않다

이번 실습은 `sleep` 으로 틈을 벌렸지만, 틈은 원래 어디에나 있다.

```java
count++;
```

한 줄로 보여도 실행 단계는 셋이다.

```
1) count 값을 읽는다
2) 1을 더한다
3) 결과를 count 에 쓴다
```

두 흐름이 1번과 3번 사이에서 교차하면 둘 다 같은 값을 읽고 각자 더해 같은 값을 써서, **두 번 더했는데 1만 늘어난다.** `sleep` 이 없어도 CPU가 흐름을 번갈아 실행하는 이상 이 교차는 언제든 일어날 수 있다.

**원자적(atomic)** 이라는 말은 "쪼개지지 않는다"는 뜻이다. `synchronized` 가 하는 일은 여러 단계를 묶어 **쪼개지지 않는 하나로 보이게** 만드는 것이다. `AtomicInteger` 는 같은 일을 락 없이 CPU 명령 수준에서 처리한다.

- `long`·`double` 은 64비트라 대입조차 두 번에 나뉠 수 있다 — `volatile` 을 붙이면 이 부분은 보장된다
- 컴파일러와 CPU는 성능을 위해 명령 순서를 바꾸기도 한다. 어디까지가 보장되는지를 정한 것이 자바 메모리 모델(JMM)이다

### 3-2. 교착 상태 — 잠금이 만드는 새 문제

락을 여러 개 쓰기 시작하면 다른 종류의 멈춤이 생긴다.

```
스레드1: A를 잡고 → B를 기다린다
스레드2: B를 잡고 → A를 기다린다
```

둘 다 상대가 놓기를 기다리며 영원히 멈춘다. 이것이 **교착 상태(deadlock)** 다. 예외도 나지 않고 CPU도 쓰지 않으면서 그냥 멈춰 있어서, 발견하기가 특히 까다롭다.

피하는 방법은 대체로 이렇다.

- **잠그는 순서를 정해 둔다** — 모든 흐름이 A → B 순으로만 잡으면 서로 물릴 일이 없다
- 락 안에서 다른 락을 잡지 않는다 — 중첩을 없애면 조건 자체가 성립하지 않는다
- 시간 제한이 있는 잠금(`tryLock`)을 써서 못 잡으면 포기하고 물러난다

락을 늘릴수록 이런 위험도 함께 늘어난다는 것이, "꼭 필요한 범위만 최소로 잠근다"는 원칙의 또 다른 이유다.

### 3-3. 공유하지 않는 쪽으로 — 불변과 무상태

동기화 문제를 푸는 가장 확실한 방법은 잠그는 것이 아니라 **공유할 상태를 없애는 것**이다.

| 방법 | 내용 |
| --- | --- |
| 불변 객체 | 필드를 `final` 로 굳혀 만든 뒤 바뀌지 않게 한다 — 바뀌지 않으면 어긋날 수 없다 |
| 무상태 객체 | 필드에 상태를 두지 않고 매개변수와 지역 변수로만 처리한다 |
| `ThreadLocal` | 흐름마다 자기 값을 따로 갖게 한다 — 공유 자체를 없앤다 |

`String` 이 불변으로 설계된 이유 중 하나가 이것이다 — Java day13 Object 클래스와 리플렉션 에서 문자열 리터럴이 상수 풀에서 공유된다고 정리했는데, 공유되면서도 안전한 것은 값이 바뀌지 않기 때문이다. 자바가 `String` 을 고칠 때마다 새 객체를 만드는 설계를 택한 배경에 이 성질이 있다.

함수형 프로그래밍이 동시성에 강하다고 이야기되는 것도 같은 맥락이다. 상태를 바꾸지 않고 새 값을 만들어 넘기면 잠글 것이 없다.

### 3-4. java.util.concurrent — 더 나은 도구들

`synchronized` 는 가장 기본적인 장치이고, 그 위에 더 세밀한 도구들이 준비돼 있다.

| 도구 | 하는 일 |
| --- | --- |
| `ReentrantLock` | `lock()`·`unlock()` 을 직접 호출 — 시간 제한·인터럽트 가능 |
| `ReadWriteLock` | 읽기는 여럿이, 쓰기는 하나만 — 읽기가 많을 때 유리 |
| `Semaphore` | 동시 입장 인원을 N명으로 제한 |
| `CountDownLatch` | 여러 흐름이 끝날 때까지 기다린다 |
| `ExecutorService` | 스레드 풀 — 흐름을 직접 만들지 않는다 |

[[Java day15 Map과 HashMap]] 3-7에서 정리한 스레드 풀과 같은 패키지에 들어 있다. `synchronized` 가 "문 하나 잠그기"라면 이쪽은 "출입 관리 방식을 고르기"에 가깝다.

`ReentrantLock` 은 `try-finally` 로 반드시 풀어 줘야 한다는 점이 `synchronized` 와 다르다. `synchronized` 는 블록을 벗어나면 예외가 나도 자동으로 풀리지만, 직접 잠근 것은 직접 풀어야 한다 — Java day12 예외 처리와 JDBC 에서 `finally` 로 자원을 닫던 것과 같은 형태다.

### 3-5. 요즘의 방향 — 스레드를 덜 만지기

동시성 코드를 직접 쓰는 일 자체가 줄어드는 쪽으로 흐름이 이어진다.

- **스레드 풀·프레임워크에 맡긴다** — 웹 서버가 요청 스레드를 관리하므로 개발자는 무상태 클래스를 쓰는 데 집중한다
- **비동기 API** — `CompletableFuture` 로 "끝나면 이어서 할 일"을 서술하고 대기를 직접 다루지 않는다
- **가상 스레드** — 최근 자바에서 도입된 훨씬 가벼운 흐름. 흐름을 아끼지 않아도 되니 복잡한 비동기 코드 대신 단순한 코드를 그대로 쓸 수 있다
- **DB 트랜잭션·격리 수준** — 같은 문제가 데이터베이스 층에도 있고, 거기서는 락과 격리 수준으로 다룬다 → SQL day05 외래키 CASCADE와 조인 이후의 주제

특히 마지막 줄을 이어 두면 그림이 넓어진다. 같은 행을 두 요청이 동시에 수정할 때 생기는 문제는 이번에 본 것과 구조가 같고, 해법도 락이라는 이름으로 같이 등장한다. 애플리케이션에서 아무리 잠가도 DB 쪽이 열려 있으면 소용이 없어서, 실무에서는 두 층을 함께 본다.

### 3-6. ThreadPoolExecutor를 직접 만들면 보이는 것

`Executors.newFixedThreadPool(3)` 은 편의 메소드이고, 안에서는 생성자를 부른다.

```java
new ThreadPoolExecutor(
        3,                              // corePoolSize   — 기본 유지 개수
        3,                              // maximumPoolSize— 최대 개수
        0L, TimeUnit.MILLISECONDS,      // keepAliveTime  — 여분 스레드 유지 시간
        new LinkedBlockingQueue<>()     // workQueue      — 작업 대기 큐
);
```

다섯 자리가 곧 풀의 성격을 정한다.

| 자리 | 뜻 |
| --- | --- |
| `corePoolSize` | 놀아도 유지하는 스레드 수 |
| `maximumPoolSize` | 큐가 꽉 찼을 때까지 늘릴 수 있는 상한 |
| `keepAliveTime` | core를 넘는 스레드가 놀 때 회수하기까지의 시간 |
| `workQueue` | 대기 작업을 담는 큐 — [[Java day15 Map과 HashMap]] 의 `Queue` |
| `ThreadFactory` | 스레드 이름·데몬 여부를 정한다 (선택) |

고정 풀은 core와 max를 같은 값으로 두고 큐를 무제한으로 잡은 형태다. **큐가 무제한이라는 점**이 중요한 성질인데, 요청이 처리 속도보다 계속 빠르면 큐가 메모리를 밀어낼 때까지 자란다. 그래서 실무에서는 큐 크기에 상한을 두는 쪽이 안전하다고 본다.

`ThreadFactory` 로 스레드 이름을 바꿔 두면 1-10에서 찍었던 `getName()` 출력이 `상담원-1` 처럼 읽히게 되어, 로그를 볼 때 도움이 된다.

### 3-7. 큐가 꽉 차면 — 거부 정책

큐에 상한을 두고 그마저 꽉 차면 풀은 새 작업을 **거부**한다. 어떻게 거부할지는 정책으로 고른다.

| 정책 | 동작 |
| --- | --- |
| `AbortPolicy`(기본) | `RejectedExecutionException` 을 던진다 |
| `CallerRunsPolicy` | **작업을 넣은 쪽**이 직접 실행한다 — 자연스럽게 속도가 조절된다 |
| `DiscardPolicy` | 조용히 버린다 |
| `DiscardOldestPolicy` | 큐에서 가장 오래된 것을 버리고 넣는다 |

`CallerRunsPolicy` 가 흥미로운 자리다. 작업을 넣던 흐름이 직접 처리하느라 잠시 멈추게 되니, **넣는 속도가 저절로 느려진다.** 이런 식으로 뒤에서 앞으로 압력을 되돌리는 방식을 배압(back pressure)이라고 부른다.

거부까지 생각해 두는 이유는 1-8의 목적과 이어진다. 스레드 풀은 무한히 받아 주는 장치가 아니라 **감당할 수 있는 선을 정해 두는 장치**라, 선을 넘었을 때 어떻게 할지가 설계의 일부다.

### 3-8. 다음에 볼 키워드

- 경쟁 상태(race condition)·공유 자원·임계 영역(critical section)
- `synchronized` 메소드와 블록, 인스턴스 락과 클래스 락(static)
- 락 전용 객체 두기, 잠긴 구간 최소화
- `wait()`·`notify()`·`notifyAll()` 과 생산자·소비자 구조
- `sleep()` 과 `wait()` 의 차이 — 락을 쥔 채 자는가
- 원자성·가시성, `volatile` 과 `synchronized` 의 역할 구분
- `AtomicInteger`·`AtomicLong` 등 원자적 변수
- `ConcurrentHashMap`·`CopyOnWriteArrayList`·`BlockingQueue` 등 동시성 컬렉션
- `Collections.synchronizedList()` 로 감싸기
- 교착 상태(deadlock)와 잠금 순서 규칙, `tryLock`
- `ReentrantLock`·`ReadWriteLock`·`Semaphore`·`CountDownLatch`
- 불변 객체(`final`)·무상태 설계·`ThreadLocal`
- 스레드 안전(thread-safe)이라는 말의 뜻
- 자바 메모리 모델(JMM)과 명령 재배치
- `ExecutorService`·`CompletableFuture`·가상 스레드
- 서버 환경의 싱글톤과 무상태 — 스프링 빈이 기본적으로 싱글톤인 이유
- DB 트랜잭션·격리 수준·낙관적/비관적 락
- 스레드 풀(thread pool)과 과부하 방지, 선입선출 작업 큐
- `Executors` 팩토리 — `newFixedThreadPool`·`newCachedThreadPool`·`newSingleThreadExecutor`·`newScheduledThreadPool`
- `ExecutorService` 와 `ThreadPoolExecutor`, 인터페이스로 받고 구현체로 다운캐스팅
- `submit()` 과 `execute()`, `Runnable` 과 `Callable<T>`, `Future<T>`·`get()`
- `Thread.currentThread().getName()` 으로 스레드 재사용 확인하기
- `getActiveCount`·`getPoolSize`·`getCorePoolSize`·`getQueue().size()`·`getCompletedTaskCount`
- `shutdown()`·`shutdownNow()`·`awaitTermination()` 과 비데몬 스레드
- `ThreadPoolExecutor` 생성자 파라미터 — core/max/keepAlive/workQueue/ThreadFactory
- 거부 정책 — `AbortPolicy`·`CallerRunsPolicy`·`DiscardPolicy` 와 배압(back pressure)
- 함수형 인터페이스와 람다로 작업 넘기기
- 풀 크기 산정 — CPU 위주 작업과 I/O 위주 작업, `availableProcessors()`
- `scheduleAtFixedRate` 로 주기 작업 돌리기

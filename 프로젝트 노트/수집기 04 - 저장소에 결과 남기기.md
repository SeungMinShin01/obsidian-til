# 수집기 04 - 저장소에 결과 남기기

> 허브: [[수집기 프로젝트 MOC]]

## 1. 배운 내용

### 1-1. 풀어야 할 문제

가상머신은 실행이 끝나면 폐기된다. 그 안에서 만든 파일도 함께 사라진다. 수집기로 치면 매일 아침 공고 100건을 받아 파일로 저장해도, 다음 실행 때는 그 파일이 없는 상태에서 시작한다는 뜻이다.

그러면 어제 본 공고인지 새 공고인지 구분할 수 없고, 데이터가 누적되지 않으며, 통계 분석도 불가능하다. 3개월 무인 수집이라는 목표 자체가 성립하지 않는다.

호텔 방을 매일 새로 빌리는 것과 같다. 방 안에서 무엇을 하든 자유지만 체크아웃하면 전부 폐기된다. 짐을 남기려면 방 밖으로 부쳐야 한다.

정리하면 구조는 이렇다.

> **리포가 기억이고, 가상머신은 작업대다.**

```
09:00  ① checkout    리포(기억) → VM으로 복사      "지금까지 뭘 봤더라"
09:01  ② API 호출                                  "오늘 현실은 이렇다"
09:02  ③ 대조         기억 vs 현실                  "신규 3건, 마감 1건"
09:03  ④ 갱신         VM 안의 DB·마크다운 수정
09:04  ⑤ push        VM → 리포                     기억을 갱신
09:05  ⑥ VM 폐기      작업대는 사라짐 (기억은 남음)
```

①과 ⑤가 없으면 ③이 불가능하다. 가운데를 파이썬으로 채우기 전에 양 끝을 먼저 만드는 셈이다.

남기는 방법은 세 가지가 있는데, 이 프로젝트는 첫 번째를 택했다.

| 방법 | 설명 | 판단 |
| --- | --- | --- |
| 리포에 커밋 | git으로 저장소에 밀어넣기 | 채택. 무료이고 이력이 남으며 옵시디언으로 바로 열람된다. 매일 커밋하므로 60일 비활성화 문제도 해결된다 |
| 아티팩트 | Actions가 제공하는 임시 보관함 | 보관 기간이 정해져 있고 자동으로 지워진다. 빌드 결과물용이지 누적 데이터용이 아니다 |
| 외부 저장소 | 클라우드 DB, S3 등 | 비용과 설정이 든다 |

SQLite를 고른 이유가 여기서 완성된다. **데이터베이스가 파일 하나**라서 git에 실려 다닐 수 있다. MySQL이나 PostgreSQL이었다면 24시간 켜져 있는 서버가 필요하고, VM 안에 띄우면 VM과 함께 사라진다.

### 1-2. `uses` — 남이 만든 기능 가져다 쓰기

지금까지는 `run`(직접 명령 실행)만 썼는데 `uses`가 새로 나왔다.

```yaml
uses: actions/checkout@v4
```

읽는 법은 `소유자/저장소@버전`이다. GitHub의 `actions` 계정이 만든 `checkout` 도구의 v4 버전을 쓰겠다는 뜻이다. 패키지를 설치해 쓰는 것과 같은 감각이고, 직접 짤 필요가 없는 일은 이렇게 가져다 쓴다.

### 1-3. checkout이 필요한 이유

`runs-on: ubuntu-latest`로 빌리는 것은 텅 빈 우분투 컴퓨터다. 우리 저장소 파일이 하나도 없다. `actions/checkout`이 `git clone`에 해당하는 일을 대신 해준다. 이 단계를 빼면 다음 단계에서 여기는 git 저장소가 아니라는 에러가 난다.

### 1-4. permissions와 GITHUB_TOKEN

```yaml
permissions:
  contents: write
```

워크플로우는 기본적으로 저장소를 읽기만 할 수 있다. 쓰려면 권한을 명시적으로 열어야 하고, 이것이 없으면 `git push`에서 403 에러가 난다.

로그인은 따로 하지 않는다. `actions/checkout`이 **`GITHUB_TOKEN`이라는 임시 토큰을 자동으로 심어두기** 때문이다. 우리가 만들 필요도, 어딘가에 저장할 필요도 없고, 실행이 끝나면 토큰도 함께 사라진다.

### 1-5. 커밋하려면 작성자가 있어야 한다

```yaml
git config user.name "github-actions[bot]"
git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
```

git은 누가 커밋했는지 모르면 커밋을 거부한다. 로컬에서 처음 커밋할 때 겪는 것과 같은 문제인데, VM은 매번 새 컴퓨터라 설정이 비어 있으므로 실행할 때마다 알려줘야 한다. `github-actions[bot]`은 GitHub의 공식 봇 계정이고 이메일도 정해진 값이다.

### 1-6. 정상적인 무변화를 실패로 만들지 않는다

```yaml
git diff --staged --quiet || git commit -m "실행 기록 추가"
```

`||`는 셸에서 앞이 실패하면 뒤를 실행하라는 뜻이다. `git diff --staged --quiet`는 변경사항이 없으면 성공(0), 있으면 실패(1)를 반환한다. 그래서 이 한 줄은 이렇게 동작한다.

- 변경 있음 → 앞이 실패 → 뒤의 `git commit` 실행
- 변경 없음 → 앞이 성공 → 커밋을 건너뜀

이 장치가 필요한 이유는 변경사항이 없을 때 `git commit`이 에러로 끝나기 때문이다. 그러면 워크플로우 전체가 실패로 표시되고 알림 메일이 날아간다. 매일 도는 시스템에서 오늘은 새 공고가 없다는 것은 정상 상태인데 그것을 실패로 처리하면 안 된다.

> 무인 운영의 원칙: **정상적인 변화 없음을 실패로 만들지 않는다.** 이 구분이 무너지면 알림이 늑대소년이 되고 진짜 장애를 놓치게 된다.

### 1-7. `|` — 여러 줄 명령

```yaml
run: |
  첫 번째 명령
  두 번째 명령
```

`|` 뒤에 들여쓴 줄들은 줄바꿈을 유지한 하나의 문자열이 된다. 명령을 여러 줄 쓸 때 사용하는 YAML 문법이다.

### 1-8. 완성된 파일

```yaml
name: hello-cron

on:
  schedule:
    - cron: "0 0 * * *"
  workflow_dispatch:

permissions:
  contents: write

jobs:
  hello:
    runs-on: ubuntu-latest
    steps:
      - name: 저장소 내려받기
        uses: actions/checkout@v4

      - name: 실행 기록 남기기
        run: |
          mkdir -p data
          echo "실행: $(date -u '+%Y-%m-%d %H:%M:%S') UTC" >> data/run-log.md

      - name: 커밋하고 푸시
        run: |
          git config user.name "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          git add data/
          git diff --staged --quiet || git commit -m "실행 기록 추가"
          git push
```

`>>`는 이어쓰기다. 파일을 덮어쓰지 않고 아래에 한 줄씩 덧붙인다. 실행할 때마다 줄이 하나씩 쌓이는 것이 데이터 누적의 최소 형태다.

## 2. 추가로 알면 좋은 활용법

### 2-1. 문법 검사와 내용 검사는 다르다

YAML 파서는 구조가 올바른지만 본다. `run`에 적힌 명령이 실제로 존재하는지, 경로가 맞는지는 파서의 관심 밖이고 전부 그냥 문자열이다. 설정 파일에서 명령이나 경로가 어긋나면 실행해봐야 드러난다.

### 2-2. 확인 방법

성공하면 저장소 첫 화면에 `data/` 폴더가 생기고 안에 `run-log.md`가 들어 있다. 커밋 목록에는 `github-actions[bot]`이 작성자로 찍힌다. 수동 실행을 한 번 더 하면 줄이 하나 더 쌓이는데, 그것이 휘발되는 컴퓨터에서 데이터를 누적시켰다는 증명이다.

## 3. 더 나아가 알면 좋은 것

### 3-1. 다음에 볼 키워드

- 아티팩트(artifact) — 커밋하지 않고 결과물을 남기는 방법. 보관 기간과 용도의 차이
- `[skip ci]` — 봇이 만든 커밋이 다시 워크플로우를 실행시키는 무한 루프를 막는 표시. `push` 트리거를 추가하면 필요해진다
- `concurrency` — 실행이 겹칠 때의 처리
- `actionlint` — 워크플로우 파일을 실행 전에 검사하는 도구. YAML 문법을 넘어 Actions 규격까지 본다
- 커밋이 잦아질 때 저장소 용량과 히스토리 관리

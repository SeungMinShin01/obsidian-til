# 수집기 06-1 - SQLite에 서버가 없다는 뜻

> 상위: [[수집기 06 - SQLite 저장 계층]]

---

## 2026-08-12 · 서버도 비밀번호도 포트도 없다는 것이 무슨 뜻인가

### MySQL에서 벌어지는 일

Spring 프로젝트에서 MySQL을 쓸 때 이런 설정을 적었다.

```properties
spring.datasource.url=jdbc:mysql://localhost:3306/mydb
spring.datasource.username=root
spring.datasource.password=password
```

여기서 실제로 일어나는 일은 다음과 같다.

- **MySQL이라는 별도 프로그램이 컴퓨터에서 계속 돌고 있다.** 이것이 서버다
- 내 코드는 그 프로그램에 **네트워크로 말을 건다.** `3306`은 그 프로그램이 듣고 있는 창구 번호(포트)다
- 아무나 접근하지 못하도록 **아이디와 비밀번호로 확인**한다
- 데이터가 실제로 어느 파일에 어떤 형태로 저장되는지는 **MySQL만 안다.** 직접 만질 수 없다

데이터를 MySQL이라는 관리인에게 맡기고 필요할 때 부탁하는 구조다. MySQL을 끄면 아무것도 할 수 없다.

### SQLite에는 관리인이 없다

```python
conn = sqlite3.connect("state/collector.db")
```

이것이 전부인 이유는 이렇다.

- **돌고 있는 프로그램이 없다.** 파이썬에 내장된 코드가 파일을 직접 읽고 쓴다
- 접속할 대상이 없으므로 주소도 포트도 필요 없다
- 지키고 있는 것이 없으므로 비밀번호도 없다. **그 파일을 열 수 있으면 그것이 곧 권한이다**
- 데이터가 `collector.db` 파일 하나에 통째로 들어 있다

관리인에게 맡기는 것이 아니라 공책 한 권을 직접 펴서 쓰는 것에 가깝다.

| | MySQL | SQLite |
| --- | --- | --- |
| 별도 프로그램 | 필요 (항상 켜져 있어야 한다) | 없음 |
| 접속 | 주소 + 포트 | 파일 열기 |
| 인증 | 아이디·비밀번호 | 없음 (파일 권한이 곧 권한) |
| 데이터 위치 | 서버만 안다 | 파일 하나 |
| 복사 | 덤프를 떠서 옮긴다 | 파일을 복사하면 끝 |

### 그래서 git에 실려 다닌다

`collector.db`가 그냥 파일이므로 git 입장에서는 `main.py`나 `run-log.md`와 다를 것이 없다. 커밋도 되고 푸시도 된다. 그래서 다음 순환이 성립한다.

```
① VM 시작 → checkout으로 collector.db가 딸려온다   (어제까지의 기억)
② 파이썬이 그 파일을 열고 새 공고를 저장한다
③ git이 그 파일을 커밋·푸시한다                      (기억 갱신)
④ VM 폐기 — 하지만 파일은 저장소에 남는다
```

### MySQL이었다면 성립하지 않는다

- VM 안에 MySQL을 설치해 띄우면 → VM이 폐기될 때 함께 사라진다. 어제 데이터가 없다
- 외부에 MySQL 서버를 빌리면 → 비용이 들고, 24시간 켜두어야 하고, 접속 정보도 관리해야 한다

무료 무인 운영이라는 제약 안에서 SQLite가 거의 유일한 답인 이유가 이것이다. **서버가 필요 없으므로 서버가 사라질 걱정도 없다.**

### 인증이 없다는 것의 의미

보안 장치가 아예 없다기보다 **인증 계층이 파일 시스템 권한으로 대체된 것**이다. 파일을 읽을 수 있는 사람이 곧 데이터를 읽을 수 있는 사람이다.

그래서 이 프로젝트에서는 **저장소 접근 권한이 곧 데이터 접근 권한**이 된다. 저장소를 Private으로 정한 결정이 여기서 다시 걸린다. DB에 비밀번호가 없으므로 저장소가 공개되면 데이터도 그대로 공개된다.

민감한 데이터를 다룰 때는 SQLite 파일 자체를 암호화하는 확장(SQLCipher 등)을 쓰기도 하지만, 이 프로젝트에는 필요하지 않다.

### SQLite의 위치와 약점

SQLite는 규모가 작은 대체품이 아니라 **세상에서 가장 많이 배포된 데이터베이스**다. 안드로이드와 iOS 기기마다, 크롬 브라우저 안에, 거의 모든 앱 안에 들어 있다. 혼자 쓰는 데이터를 파일로 관리하는 상황에 최적화되어 있고, 이 수집기가 정확히 그 상황이다.

약점은 **여러 곳에서 동시에 쓰는 경우**다. 웹 서비스처럼 수천 명이 동시에 접속하면 MySQL 쪽이 맞다. 이 프로젝트는 하루 한 번 한 프로그램만 쓰므로 해당하지 않는다.

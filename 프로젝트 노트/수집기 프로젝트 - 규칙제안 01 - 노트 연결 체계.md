## 0. 요약

`프로젝트 노트/` 안에서 노트가 빠르게 늘어나면서(현재 12개, 계속 증가) 연결 방식에 규칙이 필요해졌다. 세션 내부에서 임시로 운용 중인 규칙을 정리했고, **그중 두 가지는 기존 Vault 규칙과 충돌 가능성이 있어 판단을 요청**한다.

- **제안 A** — 연결 규칙 명문화 (충돌 없음, 우리 구역 한정)
- **제안 B** — 개념 노트 도입 (**고립 규칙과 충돌 가능. 결정 필요**)
- **제안 C** — 개념 태그 도입 (**Sync Engine 영향 검토 필요**)
- **제안 D** — 제안 관리 구조와 지침서 연결 (**고립 규칙 예외를 이미 사용 중. 승인 또는 원복 필요**)

## 1. 배경

수집기 프로젝트 노트가 다음 구조로 자라고 있다.

```
수집기 프로젝트 MOC
├─ 수집기 01 ~ 06              파일·주제 단위
│    ├─ 05-1, 05-2, 05-3       함수 단위
│    │    └─ 05-3-1, 05-3-2    그 함수에서 파생된 질문
└─ 수집기 설계 변경 기록        장부
```

사용자가 명시한 요구는 **"그물처럼 무분별하게 연결되는 것을 피하고 싶다"** 이다. 기존에 KDT 학습노트와 보드게임카페 프로젝트 분석이 뒤엉켜 난잡해진 경험에서 나온 판단이며, `프로젝트 노트/` 고립 규칙도 같은 맥락으로 이해하고 있다.

참고로 이 구조는 임의로 만든 것이 아니라 기존 방법론과 대응한다.

| 우리 방식 | 대응하는 방법론 |
| --- | --- |
| `05-3-1` 가지 번호 | Folgezettel (제텔카스텐) |
| 「수집기 프로젝트 MOC」 | MOC / LYT |
| `프로젝트 노트/` 고립 | PARA의 영역 분리 |
| 번호 불변 원칙 | Johnny Decimal |

### 1-1. 이 규칙들이 나온 질문들

규칙은 설계해서 나온 것이 아니라 작업 중 사용자가 던진 질문에 하나씩 답하면서 굳어졌다. **같은 질문에 대해 다른 판단이 가능하므로 원문 그대로 남긴다.**

| 사용자 질문 | 그로부터 정해진 것 |
| --- | --- |
| "생성되는 파일에 인덱스를 제목으로 붙일까 싶은데, 순서대로 볼 수 있게" | 번호 접두사 도입. 다만 재배열 시 `VaultPath`가 바뀌어 노션에 아카이브가 쌓이는 비용이 드러나, **번호 = 배운 순서(불변) / 읽는 순서 = MOC 표** 로 역할을 분리 |
| "하나의 파일에 질문들 정리한 게 길어지면 나중에 보기 힘들어서" | 질문을 한 장부에 쌓는 방식을 폐기하고 **부모 노트별 세부 노트**로 전환 (「수집기 질문 정리」 → 「수집기 05-1」) |
| "세부 분석은 MOC이랑 말고 해당하는 수집기(예: 05)랑만 연결되게" | 세부 노트는 상위 노트 하나만 참조. **MOC 표 미등록** |
| "05-3이랑만 연결되는 mkdir로 만들어줘" | 3단계 계층 성립 (`05` → `05-3` → `05-3-1`). **한 칸 건너뛰기 금지** |
| "노드를 연결할 때 어떤 패턴이라던가 규칙이 있어?" | 기존 방법론 조사. 우리 방식이 Folgezettel·MOC·PARA와 대응함을 확인 |
| "너무 그물처럼 무분별하게 연결되어 있는 듯한 느낌이 들어서. KDT 노드랑 보드게임카페 프로젝트 분석이랑 전부 연결되어 있을 때 난잡하다 라는 느낌이 들어서 그 둘도 분리했었거든" | **이 요구가 전체 구조의 근본 동기다.** 고립 규칙과 트리 구조 둘 다 여기서 나왔다 |
| "설명식보다 회고 형식으로 지식 부분만 저장하는 방식으로 가자" | 노트 문체를 대화 재현이 아닌 단정형 서술로 고정 |
| "오타 수정/오류는 추가하지 말고" | 기존 운영 규칙 6항(원본 코드의 오류·오타는 기록하지 않는다)과 일치. 일반 주의사항으로만 서술 |

**판단이 갈릴 수 있는 지점**을 짚어두면 다음과 같다.

- 번호 체계를 파일명에 넣은 것 자체가 옳은가. 옵시디언은 파일명 변경 시 링크를 자동 갱신하므로 재배열 비용이 링크 측면에서는 낮다. 비용은 **노션 미러링 쪽에서만** 발생한다. 미러링 비용을 감수하고 연번을 유지하는 선택도 가능하다
- 세부 노트를 MOC에 올리지 않기로 한 것은 목차 가독성을 위해서지만, 검색 접근성은 그만큼 떨어진다. 노션 쪽에서 세부 노트를 찾기 어려워질 수 있다
- 트리 구조는 사용자의 명시적 요구지만, 제텔카스텐 원형과는 오히려 거리가 있다. 루만의 방식은 가지 번호를 쓰되 **번호와 무관한 가로 링크를 자유롭게 걸었다.** 제안 B는 그 가로 연결을 어떻게 되살릴지의 문제이기도 하다

## 2. 제안 A — 연결 규칙 명문화 (충돌 없음)

현재 운용 중인 규칙이며, `프로젝트 노트/` **내부에만** 적용된다. 기존 고립 규칙을 위반하지 않는다.

### A-1. 계층과 번호

- 파일명 번호가 계층을 나타낸다. 하이픈이 늘어날수록 한 단계 깊어진다
  - `수집기 05` → `수집기 05-3` → `수집기 05-3-1`
- **번호는 배운 순서이며 한 번 붙이면 바꾸지 않는다.** 읽는 순서는 MOC 표의 줄 순서로 관리한다
  - 이유: 파일명 변경은 Sync Engine의 `VaultPath` 기본키가 바뀌어 노션에 아카이브 페이지가 쌓인다

### A-2. 링크 방향

| 방향 | 위치 | 개수 |
| --- | --- | --- |
| 자식 → 부모 | 머리말 `> 상위:` | 하나만 |
| 부모 → 자식 | 머리말 `> 세부:` | 여럿 가능 |

**한 칸을 건너뛰지 않는다.** `05-3-1`은 `05`나 MOC와 직접 연결하지 않는다.

### A-3. 링크를 놓는 세 위치

같은 링크를 용도에 따라 세 군데에 둔다.

- **머리말** — 열자마자 위아래로 이동 (탐색)
- **본문 중 그 개념이 나온 자리** — 궁금해진 지점에서 바로 (맥락)
- **`## 관련 노트`** — 다 읽고 다음으로 (회수)

### A-4. MOC 등록 기준

MOC 표에는 최상위 노트만 올린다. 세부 노트(`-1`, `-2`)는 상위 노트에서만 연결하고 표에 올리지 않는다. MOC가 색인이 아니라 목차 역할을 유지하기 위함이다.

### A-5. 링크 기준

**"나중에 이 노트를 읽다가 정말 저기로 가고 싶을까"** 에 예라고 답할 수 있을 때만 링크한다. 관련 있어 보인다는 이유만으로 거는 링크는 그래프를 망친다.

## 3. 제안 B — 개념 노트 도입 (판단 요청)

### B-1. 문제

트리 구조의 한계로, **다른 가지에 있는 같은 개념을 연결할 수 없다.**

실제 사례가 이미 발생했다.

- `수집기 05-3-1`의 `exist_ok=True`
- `수집기 06`의 `CREATE TABLE IF NOT EXISTS`

둘은 **완전히 같은 개념(멱등성)** 이지만 서로 다른 가지에 있어 현재 규칙으로는 연결할 수단이 없다. 앞으로 예외 처리, 인코딩, 경로 등에서 같은 상황이 반복될 것으로 본다.

### B-2. 선택지

**① 각 구역 안에 개념 노트를 둔다**

`프로젝트 노트/멱등성.md`를 만들고 그 폴더 안에서만 링크한다.

- 장점: 고립 규칙을 그대로 지킨다. 규칙 변경이 불필요하다
- 단점: 나중에 학습노트 쪽에서도 같은 개념을 다루면 내용이 중복된다

**② 공용 `_개념/` 폴더를 신설하고 고립 규칙의 예외로 둔다**

Vault 최상위에 `_개념/`을 만들고, 어느 구역에서든 개념 노트로는 링크할 수 있게 한다.

- 장점: 개념이 한 곳에 모인다. 학습노트와 프로젝트 노트가 같은 개념을 공유한다
- 단점: **고립 규칙에 예외가 생긴다.** 그래프에서 `프로젝트 노트/`가 완전한 섬이 아니게 된다
- Sync Engine의 `categoryMap`에 `_개념/` 항목 추가가 필요하다

**③ 개념 노트를 만들지 않고 태그만 쓴다** (제안 C만 채택)

- 장점: 가장 안전하다. 기존 규칙을 전혀 건드리지 않는다
- 단점: 개념 설명을 쓸 자리가 없다. 검색으로 모이기만 한다

### B-3. 이 세션의 의견

**①을 먼저 시도하고, 학습노트 쪽에서도 필요해지면 그때 ②를 검토**하는 것이 안전해 보인다.

지금 시점에 확실한 것은 `프로젝트 노트/` 안에서 개념이 중복된다는 것뿐이고, 학습노트와의 공유 필요성은 아직 관측되지 않았다. 되돌릴 수 없는 결정(고립 규칙 예외)을 관측 전에 내릴 이유가 없다고 판단한다.

다만 고립 규칙의 취지가 **"프로젝트 대화 내용이 학습 그래프를 오염시키지 않는 것"** 이라면, `_개념/`은 그 취지와 충돌하지 않을 수도 있다. 개념 노트는 대화 기록이 아니라 재사용 가능한 지식이기 때문이다. **이 해석이 맞는지 판단을 요청한다.**

## 4. 제안 C — 개념 태그 (영향 검토 요청)

frontmatter `tags`에 개념 태그를 추가한다.

```yaml
tags: [프로젝트노트, 수집기, Python, 멱등성]
```

같은 개념을 다루는 노트가 검색과 태그 창에서 모인다. 트리 구조를 건드리지 않으면서 가로 연결을 얻는 가장 가벼운 방법이다.

### 검토가 필요한 지점

Sync Engine 명세 3항에 따르면 `tags`는 노션의 **multi_select 속성**으로 매핑된다. 개념 태그를 도입하면 노션 쪽 선택지가 계속 늘어나는데, 이것이 허용 가능한지 판단이 필요하다.

- 허용 가능하면: 그대로 진행
- 곤란하면: 개념 태그를 본문 인라인 태그(`#멱등성`)로만 쓰고 frontmatter에는 넣지 않는 방법이 있다. 옵시디언 검색에는 잡히고 Sync Engine에는 영향이 없다

## 4-2. 제안 D — 제안 관리 구조와 지침서 연결

### D-1. 제안서는 파일 하나씩 쌓는다

처음에는 장부 하나에 제안 내용을 누적하는 방식을 생각했으나, **파일 하나에 계속 쌓으면 길어져서 나중에 읽기 어렵다.** 같은 이유로 이 세션의 질문 기록도 장부 누적에서 노트 분리로 이미 한 번 바꾼 적이 있다.

그래서 다음 구조를 제안한다.

```
수집기 프로젝트 - 규칙제안 기록          ← 장부. 목록과 상태만
├─ 수집기 프로젝트 - 규칙제안 01 - …     ← 제안 하나 = 파일 하나
├─ 수집기 프로젝트 - 규칙제안 02 - …
└─ …
```

- 장부에는 **목록·작성 세션·상태**만 둔다
- 제안 본문과 결정 기록은 각 파일에 둔다
- 파일명은 `수집기 프로젝트 - 규칙제안 NN - 제목` 형식으로 한다
- **제안서 첫머리에 작성 세션을 명시한다.** 여러 세션이 같은 Vault를 쓰므로 누가 낸 제안인지 남아야 하고, 답을 어디로 돌려줄지도 분명해진다
- 기각된 제안도 지우지 않는다. 같은 문제를 다시 만났을 때 이미 논의했다는 사실과 그때의 이유가 남아 있어야 논의가 반복되지 않는다

이 규칙은 수집기 세션 안에서만 쓸 수도 있고, **다른 세션도 같은 형식으로 제안을 남기도록 Vault 공통 규칙으로 삼을 수도 있다.** 후자라면 접두사만 세션별로 달리하면 된다(`수집기 프로젝트 - 규칙제안 NN`, `<다른 프로젝트> - 규칙제안 NN`).

### D-2. 제안 장부를 `CLAUDE.md`에 연결했다

「수집기 프로젝트 - 규칙제안 기록」의 머리말에서 `[[CLAUDE]]`로 링크를 걸어두었다. 제안의 대상이 그 문서이므로 의미상 그 아래에 매다는 것이 맞다고 판단했다. 프로젝트 MOC는 프로젝트 진행 내용의 목차이지 규칙 논의의 자리가 아니다.

**다만 이것은 `프로젝트 노트/` 고립 규칙(폴더 안에서만 링크)을 넘어선다.** 사용자 요청으로 이미 적용했으나 승인이 필요하다.

- 허용한다면: 고립 규칙에 "규칙 제안 장부는 지침서에 연결할 수 있다"는 예외를 명시한다
- 허용하지 않는다면: 링크를 걷어내고 이름만 적는 방식으로 되돌린다

역방향 링크(`CLAUDE.md` → 제안 장부)는 걸지 않았다. 그 문서는 운영 세션 관할이므로 필요 여부를 그쪽에서 판단하는 것이 맞다고 보았다.

**참고**: 이 예외를 허용하면 제안 B-②(`_개념/` 폴더 신설)의 판단도 같이 정리된다. 둘 다 "고립 구역이 Vault 공용 자원과 연결될 수 있는가"라는 같은 질문이기 때문이다. 다만 성격은 다르다. 지침서 연결은 **운영 문서 한 곳**과의 연결이고, 개념 노트는 **지식 내용**의 연결이다. 전자만 허용하고 후자는 막는 선택도 가능하다.

## 5. 기존 규칙 영향 정리

| 기존 규칙 | 영향 |
| --- | --- |
| `프로젝트 노트/` 고립 (운영 규칙 2항) | **제안 B-②를 채택할 경우에만 수정 필요** |
| 파일명 규칙 (3항) | 영향 없음. `수집기 NN - 제목` 형식은 기존 패턴과 어긋나지 않음 |
| frontmatter (4항) | 제안 C 채택 시 `tags` 값이 늘어남 |
| 그래프뷰 연결 규칙 (5항) | `프로젝트 노트/`는 이미 5항 적용 제외 대상 |
| Sync Engine (9항) | 제안 B-② 채택 시 `categoryMap` 추가, 제안 C 채택 시 multi_select 증가 |
| 번호 불변 원칙 | `VaultPath` 기본키 보호와 같은 목적이므로 오히려 부합 |
| `프로젝트 노트/` 고립 (운영 규칙 2항) | **제안 D-②는 이미 이 규칙을 넘어선 상태다.** 승인 또는 원복 판단이 필요하다 |

## 6. 결정을 요청하는 항목

1. **제안 A** — 그대로 CLAUDE.md에 반영해도 되는가
2. **제안 B** — ①(구역 내 개념 노트) / ②(`_개념/` 신설, 고립 예외) / ③(태그만) 중 어느 쪽인가
3. **제안 C** — frontmatter `tags`에 개념 태그를 넣어도 되는가, 아니면 인라인 태그로 제한하는가
4. **제안 D-1** — 제안 하나당 파일 하나 구조를 이 세션 안에서만 쓰는가, Vault 공통 규칙으로 삼는가
5. **제안 D-2** — 제안 장부가 `CLAUDE.md`에 링크를 거는 것을 고립 규칙의 예외로 허용하는가, 원복하는가

## 7. CLAUDE.md 삽입 문안 초안 (제안 A + B-① + C-인라인 기준)

> 아래는 제안 A와, B-①·C-인라인을 채택했을 때의 문안이다. 다른 조합을 선택하면 해당 부분을 수정한다.

```markdown
### 프로젝트 노트/ — 연결 체계

`프로젝트 노트/` 안에서 노트가 여러 개로 자라는 경우 아래 규칙을 따른다.

- **번호가 계층이다.** `수집기 05` → `수집기 05-3` → `수집기 05-3-1`.
  하이픈이 늘어날수록 상위 노트에서 파생된 세부 노트다
- **번호는 배운 순서이며 바꾸지 않는다.** 읽는 순서는 MOC 표의 줄 순서로 관리한다
  (파일명 변경은 Sync Engine의 VaultPath 기본키를 바꾼다)
- **링크는 한 칸씩만 오르내린다.** 자식은 머리말에 `> 상위:` 하나만,
  부모는 `> 세부:`로 자식들을 나열한다. 한 칸을 건너뛰지 않는다
- **MOC 표에는 최상위 노트만 올린다.** 세부 노트는 상위 노트에서만 연결한다
- **링크는 세 곳에 둔다** — 머리말(탐색), 본문 중 그 개념이 나온 자리(맥락),
  `## 관련 노트`(회수)
- **링크 기준** — 나중에 읽다가 정말 그리로 가고 싶을 때만 건다
- **개념 노트** — 여러 가지에 걸친 개념(멱등성, 인코딩 등)은 폴더 안에
  개념 노트를 만들고 양쪽에서 링크한다. 폴더 밖으로는 여전히 링크하지 않는다
- **개념 태그** — 본문에 인라인 태그(`#멱등성`)를 달아 검색으로 모을 수 있게 한다.
  frontmatter `tags`에는 넣지 않는다 (노션 multi_select 증가 방지)
```

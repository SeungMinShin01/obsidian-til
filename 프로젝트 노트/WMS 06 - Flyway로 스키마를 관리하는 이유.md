# WMS - Flyway로 스키마를 관리하는 이유

> 허브: [[WMS 프로젝트 MOC]]

## 1. 배운 내용

### 1-1. 두 가지 방식

**JPA `ddl-auto`** — 엔티티 클래스를 보고 테이블을 자동으로 만들거나 고친다. 설정 한 줄이면 끝이고 엔티티만 수정하면 테이블이 따라온다.

**Flyway** — `resources/db/migration/` 에 SQL 파일을 순서대로 놓으면, 앱이 뜰 때 아직 실행하지 않은 파일을 차례로 적용한다.

```
db/migration/
├─ V1__init.sql
├─ V2__add_inventory_snapshot.sql
└─ V3__add_inventory_index.sql
```

어디까지 적용했는지는 `flyway_schema_history` 테이블에 기록된다.

### 1-2. Flyway로 정한 이유 — 변경이 코드에 남는다

`ddl-auto`는 편하지만 **스키마 변경 이력이 아무 데도 남지 않는다.** 엔티티를 고치면 테이블이 조용히 바뀌고, 나중에 "언제 뭘 바꿨는지" 확인할 방법이 없다.

이 프로젝트에서는 이게 치명적이다. 3주차 내내 하는 일이 **인덱스를 붙였다 뗐다 하며 개선 폭을 재는 것**이기 때문이다.

Flyway를 쓰면 `V3__add_inventory_index.sql` 같은 파일이 커밋에 남는다. 그러면 "이 인덱스를 추가해서 2400ms → 35ms" 라는 주장에 **증거가 붙는다.** 커밋 하나를 열면 무엇을 바꿨는지 그대로 보인다.

측정 프로젝트에서 스키마 이력은 편의의 문제가 아니라 **산출물의 일부**다.

### 1-3. 학습 비용은 거의 없다

처음엔 도구가 하나 늘어나는 게 부담스러웠는데, 실제로 쓰는 법은 `db/migration/` 폴더에 규칙에 맞는 이름으로 SQL 파일을 놓는 것이 전부다.

`V<번호>__<설명>.sql` — 밑줄 두 개인 것만 주의하면 된다.

### 1-4. 짝이 되는 설정 — `ddl-auto: validate`

Flyway를 쓰면서 `ddl-auto`를 켜두면 둘이 서로 테이블을 건드려서 꼬인다.

`validate`로 두면 JPA가 **테이블을 만들지 않고, 엔티티와 실제 테이블이 맞는지 검사만** 한다. 어긋나면 앱이 뜨지 않는다. 스키마 관리 권한은 Flyway 하나에 두고 JPA는 감시자 역할만 하는 구조다.

## 2. 추가로 알면 좋은 활용법

### 2-1. 이미 적용한 파일은 고치지 않는다

Flyway는 적용한 파일의 체크섬을 저장해둔다. `V2`를 이미 적용한 뒤에 그 파일을 수정하면 체크섬이 달라져서 앱이 뜨지 않는다.

**고치고 싶으면 `V3`를 새로 만든다.** 처음엔 답답한데, 이 제약 덕분에 "지금 DB가 어떤 상태인가"가 파일 순서와 정확히 일치하게 된다.

### 2-2. 인덱스는 처음부터 넣지 않는다

`V1__init.sql`에 인덱스를 미리 다 넣고 싶은 유혹이 있는데, 그러면 **Before를 측정할 수 없다.**

순서는 이렇다.

1. `V1`에는 테이블과 기본 키·외래 키만
2. 3주차에 100만 건 넣고 Before 측정
3. `V3__add_inventory_index.sql` 추가하고 After 측정
4. 두 숫자를 표에 나란히 적는다

인덱스를 미리 넣으면 "왜 넣었냐"는 질문에 답할 근거가 사라진다.

### 2-3. 커밋을 적용 전/후로 나눈다

최적화 단계는 반드시 **적용 전 커밋과 적용 후 커밋을 분리**한다. 그래야 나중에 diff 하나로 "이것만 바꿨더니 이만큼 빨라졌다"를 보여줄 수 있다.

```
perf: 재고 이력 조회 복합 인덱스 추가 (2400ms → 35ms)
```

커밋 메시지에 개선 수치를 적어두면 `git log`만 봐도 최적화 이력이 읽힌다.

### 2-4. 백틱을 쓰지 않고 예약어를 피한다

MySQL에서 백틱(`` ` ``)으로 감싸는 문법은 MySQL 전용이다. 예약어를 컬럼명으로 쓰지 않고 백틱도 쓰지 않으면, 나중에 다른 DB로 옮길 때 손볼 게 눈에 띄게 줄어든다. 비용이 0이라 지킬 만한 규칙이다.

→ 이식성에 투자하지 않기로 한 판단은 [[WMS 03 - MySQL과 PostgreSQL, 그리고 Redis]]

## 3. 더 나아가 알면 좋은 것

### 3-1. 다음에 볼 키워드

- `baseline-on-migrate` — 이미 테이블이 있는 DB에 Flyway를 나중에 붙일 때 쓰는 옵션
- Repeatable 마이그레이션(`R__`) — 뷰나 함수처럼 매번 다시 적용해도 되는 것들
- Liquibase — Flyway의 대안. XML/YAML로 스키마를 기술한다
- 롤백 — Flyway 무료판에는 자동 롤백이 없다. 되돌리려면 반대 작업을 하는 새 파일을 만든다

### 3-2. 3주차에 확인할 것

`flyway_schema_history` 테이블을 열면 어떤 마이그레이션이 언제 적용됐고 몇 ms 걸렸는지 나온다. 인덱스 생성이 100만 건 테이블에서 얼마나 걸렸는지도 여기 남는다 — 이것도 측정 표에 넣을 만한 숫자다.

# 수집기 09 - 브랜치 없이 main에서 작업하는 이유

> 허브: [[수집기 프로젝트 MOC]]

브랜치를 나누지 않고 계속 `main`에서 작업해도 되는지 판단한 기록이다.

## 1. 배운 내용

### 1-1. 일반론은 브랜치를 나누라고 한다

브랜치의 목적은 대개 셋이다.

- **리뷰** — 합치기 전에 다른 사람이 본다
- **격리** — 작업 중인 코드가 다른 사람의 작업을 방해하지 않는다
- **보호** — `main`은 항상 동작하는 상태로 유지한다

혼자 하는 개인 프로젝트에서는 앞의 둘이 해당하지 않는다. 리뷰받을 사람이 없고 방해할 사람도 없다.

### 1-2. 이 프로젝트에는 브랜치를 불편하게 만드는 사정이 두 개 더 있다

**봇이 main에 커밋한다.** 브랜치에서 작업하는 동안에도 봇은 매일 `main`에 실행 기록을 쌓는다. 브랜치를 합치려면 그동안 쌓인 봇 커밋과 매번 맞춰야 하고, `data/`와 `state/`는 양쪽에서 바뀌므로 충돌이 나기 쉽다. 혼자 작업하는데 충돌만 늘어난다.

**스케줄은 main 기준으로 등록된다.** 브랜치에서 `collect.yml`을 고쳐도 cron은 `main`의 파일을 본다. 브랜치에서는 워크플로우 변경을 확인할 방법이 마땅치 않다.

그래서 지금 단계에서는 `main` 직행이 맞다.

### 1-3. 다만 이 프로젝트 특유의 리스크가 있다

> **`main`이 깨지면 매일 아침 실패 메일이 온다.**

무인으로 돌기 때문이다. 사람이 쓰는 프로젝트라면 깨진 채로 하루 두어도 아무 일이 없지만, 여기서는 매일 실행이 걸려 있다.

지금까지는 변경이 한 번에 끝났으므로 문제가 없었다. 하지만 며칠 걸리는 작업이 생기면 중간 상태가 `main`에 올라가고, 그동안 매일 실패 메일을 받게 된다. 알림이 늑대소년이 되는 가장 흔한 경로다.

### 1-4. 판단 기준

> **하루 안에 끝나면 `main`, 며칠 걸리면 브랜치.**

며칠 걸릴 것으로 예상되는 작업의 예는 다음과 같다.

- 사람인 API 어댑터 붙이기 — 호출·정규화·스키마 확장이 한 덩어리로 묶여 있다
- 마크다운 생성 계층 추가
- 판정 로직을 신규/변경/재공고로 확장

### 1-5. 브랜치를 쓸 때

```powershell
git switch -c saramin-api      # 브랜치를 만들고 이동
# ... 작업 ...
git switch main                # 끝나면 main으로 돌아와
git merge saramin-api          # 합친다
```

브랜치에 있는 동안에도 봇은 `main`에서 계속 돈다. **가짜 데이터로 매일 무사히 돌면서 옆에서 진짜를 만드는 구조**가 되고, 그것이 이 프로젝트에서 브랜치의 진짜 값어치다.

## 2. 추가로 알면 좋은 활용법

### 2-1. 브랜치를 쓰지 않는 대신 지키는 것

`main` 직행을 택했으므로 대신 이 습관이 필요하다.

- **로컬에서 먼저 돌려보고 푸시한다.** 깨진 코드를 `main`에 올리지 않는 유일한 방어선이다
- **한 번에 한 가지만 바꾼다.** 실패했을 때 원인이 좁혀진다
- **작업 전에 `git pull`.** 봇이 앞서 있다

### 2-2. 되돌리는 방법도 알아둔다

`main`에 잘못 올렸을 때 쓸 수 있는 것이 있다.

- `git revert <커밋>` — 그 커밋을 취소하는 **새 커밋**을 만든다. 이력이 남으므로 이미 푸시한 커밋에는 이쪽이 안전하다
- `git reset` — 이력 자체를 되돌린다. 푸시한 뒤에는 쓰지 않는 편이 좋다

## 3. 더 나아가 알면 좋은 것

### 3-1. 다음에 볼 키워드

- `git switch` / `git checkout` — 브랜치 이동 명령의 차이
- Pull Request — 혼자라도 변경 내역을 정리해 남기는 용도로 쓸 수 있다
- `git revert`와 `git reset`의 차이
- 브랜치 보호 규칙 — `main`에 직접 푸시를 막는 설정
- `[skip ci]` — 봇 커밋이 다시 워크플로우를 부르는 것을 막는 표시

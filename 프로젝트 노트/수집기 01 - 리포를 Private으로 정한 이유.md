# 수집기 - 리포를 Private으로 정한 이유

> 허브: [[수집기 프로젝트 MOC]]

## 1. 배운 내용

### 1-1. 저장소를 따로 두는 것과 비공개로 두는 것은 다른 결정이다

수집기 코드를 기존 학습 Vault 저장소가 아닌 **별도 저장소**에 두기로 한 이유와, 그 저장소를 **Private**으로 두기로 한 이유는 서로 다른 문제다.

- 별도 저장소로 나눈 이유는 커밋 충돌 때문이다. 학습 Vault는 obsidian-git이 로컬에서 30분마다 커밋하는데, 수집기는 GitHub Actions가 클라우드에서 커밋한다. 같은 저장소를 두 곳이 건드리면 충돌이 나고, 무인 운영 중에 사람이 개입해야 하는 상황이 생긴다.
- Private으로 둔 이유는 아래 세 가지다.

### 1-2. API 이용목적에 쓴 약속

사람인 오픈 API를 신청하면서 이용목적에 수집한 데이터를 개인 취업 준비 용도로만 활용하며 외부에 재배포하지 않는다고 적었다.

그런데 설계상 공고 본문 전문(`description`)을 통째로 저장한다. 이것을 Public 저장소에 올리면 누구나 볼 수 있는 곳에 남의 공고 원문을 복제해 두는 셈이고, 사실상 재배포에 해당한다. 신청서에 적은 약속을 코드로 어기는 구조가 된다.

### 1-3. 시크릿 사고 방어

API 키와 노션 토큰은 GitHub Secrets에 넣으므로 원칙적으로는 안전하다. 문제는 실수다. 디버깅하다 키를 그대로 출력하는 줄이 로그에 남거나, `.env` 파일을 깜빡하고 커밋하는 일이 생긴다.

Public 저장소는 이런 노출을 자동으로 탐지하는 봇이 상시 스캔하고 있어서, 키가 올라가면 곧바로 악용될 수 있다. 게다가 이 시스템은 무인으로 몇 달을 도는 구조라 사고가 나도 발견이 늦다. Private이면 같은 실수를 해도 사고로 이어지지 않는다.

### 1-4. 관심사 노출

어떤 회사와 직무의 공고를 모으고 있는지가 그대로 드러난다. 취업 준비 상황이 공개되는 셈이라 굳이 열어둘 이유가 없다.

## 2. 추가로 알면 좋은 활용법

### 2-1. Private이어도 포트폴리오로 쓸 수 있다

비공개로 두면 보여줄 수 없다고 생각하기 쉽지만 방법이 있다.

- 학습 기록은 이미 Public인 학습 Vault 저장소에 쌓이고 있어서, 무엇을 어떻게 만들었는지의 서사는 공개된다.
- Private 저장소도 면접에서 화면을 공유하거나 면접관을 게스트로 초대해 보여줄 수 있다.
- 나중에 데이터를 뺀 코드만 별도 Public 저장소로 낼 수 있다.

핵심 기준은 **코드는 공개해도 되지만 데이터는 안 된다**는 것이다. 지금은 둘이 한 저장소에 있으니 안전한 쪽을 택했다.

## 3. 더 나아가 알면 좋은 것

### 3-1. 다음에 볼 키워드

- GitHub Secrets — 저장소에 값을 남기지 않고 워크플로우에 비밀값 전달하기
- `.gitignore` — `.env` 같은 파일을 커밋 대상에서 빼는 방법
- Secret scanning / push protection — 키가 커밋에 섞였을 때 GitHub이 막아주는 기능
- 이미 커밋된 비밀값을 히스토리에서 지우는 방법

# AiOps - 설명 재시도 최소 나이

> 허브: [[AiOps 프로젝트 MOC]]

**PR #68 `[AI-57] 설명 재시도에 최소 나이 조건`** — 커밋 4개 + develop 병합 1개, 11/16 머지. 다른 사람의 PR이 머지되면서 내 코드에 생긴 문제를 고친 기록.

## 1. 배운 내용

### 1-1. 무슨 문제였나

```
전 (PR #53까지)                      후 (PR #62 머지)
  새 그룹 → 설명을 아무도 안 부름       새 그룹 → ErrorProcessor가 explain 호출 (최대 20초)
  재시도 스케줄러만 explain 호출                    ↑ 이 20초 사이에
                                      재시도 스케줄러가 돌면 같은 그룹을 또 호출
```

`ExplanationRetryScheduler`는 "설명이 NULL인 그룹"을 찾는다. 처리 스레드가 LLM 답을 기다리는 동안에도 그 그룹은 NULL이다. 그래서 둘이 같은 그룹으로 LLM을 부른다.

- 저장은 안전하다: `saveIfEmpty`(조건부 UPDATE)가 하나만 통과시킨다.
- 낭비는 생긴다: LLM 호출 2번, 일일 상한(`llm_usage`)도 2 깎인다.

내 코드만 볼 때는 문제가 없었다. **두 코드가 만난 뒤에야** 생긴 문제라 각자의 테스트는 전부 초록이었다.

### 1-2. 코드로 보기

```sql
SELECT id FROM error_group
WHERE ai_explanation IS NULL
  AND first_seen_at > CAST(:since AS timestamptz)     -- 너무 오래된 그룹은 포기 (24시간)
  AND first_seen_at < CAST(:before AS timestamptz)    -- 방금 생긴 그룹은 건드리지 않음 (2분)
```

```java
Instant now = Instant.now();
Instant since = now.minus(window);    // PT24H
Instant before = now.minus(minAge);   // PT2M
```

2분인 이유: LLM 타임아웃이 20초다. 처리 스레드가 한 묶음에서 새 그룹 여러 개를 차례로 설명해도 2분이면 끝난다. 값은 `aiops.llm.retry-min-age` 설정이다.

`Instant.now()`를 한 번만 부르는 이유: 두 번 부르면 `since`와 `before`의 기준 시각이 조금 다르다. 결과는 거의 같지만 "같은 시각 기준"이라고 읽히지 않는다.

### 1-3. 다른 방법과 비교

| 방법 | 얻는 것 | 잃는 것 |
|---|---|---|
| **최소 나이 조건 (선택)** | 조건 한 줄, 테이블 변경 없음 | 설명에 실패한 그룹의 첫 재시도가 최소 2분 뒤 |
| "설명 중" 표시 칸 추가 | 정확히 막는다 | 마이그레이션, 서버가 죽으면 표시가 남는 문제를 또 풀어야 함 |
| 그대로 둠 | 일 없음 | 드물게 LLM 2번. 무료 등급에서는 상한이 아깝다 |

### 1-4. 테스트를 같이 고친 이유

기존 테스트 5개는 "그룹을 만들고 바로 재시도"를 한다. 최소 나이가 2분이면 전부 빨강이 된다. 테스트의 `scheduler(...)`를 둘로 나눠, 기존 테스트는 최소 나이 0초(`PT0S`)로 돌고 새 테스트만 2분으로 돈다. 기존 테스트가 확인하던 것(24시간 창, 상한, 정지된 팀)은 그대로다.

새 테스트 `방금_만든_그룹은_재시도하지_않는다`: 그룹 둘 중 하나만 `first_seen_at`을 3분 전으로 옮기고 → LLM 호출이 1번이고 → 방금 만든 쪽은 NULL로 남는지 본다.

## 2. 팁

- 생성자에 값 하나를 추가하면 그 클래스를 `new`로 만드는 테스트도 같이 고쳐야 한다. 리포지토리 → 스케줄러 → 테스트 순서로 파일 하나씩 커밋하면 중간 커밋은 컴파일이 안 된다. PR 전체로는 초록이다.
- PR을 기다리는 사이 다른 PR(#67)이 같은 파일의 바로 아래에 메서드를 추가해 충돌이 났다. 한쪽을 고르는 게 아니라 **둘 다 남겼다**: 메서드 모양은 내 것(인자 3개), 추가된 메서드 3개는 그대로. 상대 쪽 모양(인자 2개)을 고르면 스케줄러가 컴파일되지 않는다
- 테스트 코드는 `src/test`에만 있고 운영 jar에 들어가지 않는다. 테스트가 본 코드보다 긴 것은 정상이다 (본 코드는 길 하나, 테스트는 경우마다 하나).

## 3. 남은 것

- `first_seen_at`은 팀 앱이 보낸 시각(`payload.time`)이다. 팀 PC의 시계가 많이 틀리면 재시도 창(24시간·2분) 판단도 틀린다. 서버가 받은 시각으로 바꿀지는 정하지 않았다

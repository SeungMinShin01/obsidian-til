# WMS - 3주 범위를 잘라낸 기준

> 허브: [[WMS 프로젝트 MOC]]

## 1. 배운 내용

### 1-1. 시간 조건이 다른 모든 결정을 지배했다

원래 계획은 팀 프로젝트 기준으로 짜여 있었다. 그런데 조건이 둘 달랐다.

- **혼자 한다** — 역할 배분, 매일 동기화, 스프린트 의식 같은 팀 운영 항목이 전부 무의미하다
- **3주만 집중할 수 있고 그 뒤로는 주당 몇 시간** — 이게 결정적이었다

두 번째 조건은 **3주 안에 끝나지 않으면 사실상 끝나지 않는다**는 뜻이다. 미완성 상태로 저강도 기간에 넘어가면 매번 "지난번에 뭐 하다 말았지"를 복구하는 데 시간을 다 쓰고, 대부분 그렇게 죽는다.

그래서 도구 선택에서도 "더 좋은 것"보다 "덜 막히는 것"을 골랐다. MySQL을 고른 이유가 여기서 나왔다. → [[WMS 03 - MySQL과 PostgreSQL, 그리고 Redis]]

### 1-2. 무엇을 잘랐나

| 원래 계획 | 어떻게 | 이유 |
| --- | --- | --- |
| 모바일 스캔 화면 | 삭제 | 아래 1-3 |
| 동시성 제어 3가지 비교 | 2가지로 (비관적·낙관적) | Redis 락은 서버 한 대에서 과하다 |
| 재고 이동·조정 | 후순위 | 입고→출고 한 바퀴가 먼저 |
| 프론트 화면 다듬기 | 기능이 보이는 수준까지만 | CSS는 평가 대상이 아니다 |

### 1-3. 모바일 화면을 지워도 되는 이유

**실물 바코드 스캐너는 키보드로 동작한다.** 스캔하면 숫자를 타이핑하고 엔터를 치는 것과 똑같은 입력이 들어온다(HID 키보드 방식).

그래서 화면에 입력창 하나 두고 포커스만 잡아두면 스캔 기능은 이미 완성이다. 모바일 전용 UI는 창고 현장의 편의 문제지 기술 과제가 아니다.

**3주 프로젝트에서 뺄 수 있는 가장 싼 항목**이었다. 기능은 유지되고 구현 분량만 사라진다.

### 1-4. 잘라내는 기준이 뭐였나

평가받는 순서가 이렇다.

1. Before/After 측정 표
2. 동시성 제어로 재고 정합성을 지킨 방식
3. 실제 배포된 주소
4. 기능 목록 ← 가장 덜 중요

그래서 **기능을 늘리는 항목부터 잘랐다.** 재고 이동·조정은 기능 목록을 늘리지만 1~3번에 아무것도 보태지 않는다. 반대로 동시성 제어는 기능이 아니지만 2번 그 자체라 남겼다.

### 1-5. 수정된 일정

- **0일차 (반나절)** — 세팅
- **1주차** — 기준정보 CRUD → **재고 이력 테이블 설계** → 입고 → 재고 증가 → 재고 현황 조회
  - 체크포인트: 입고를 등록하면 재고가 늘어나는가
- **2주차** — 주문 → 선점 → 피킹 리스트 → 출고 확정. 동시성 2종. 주 중반 **시험 배포 1회**
  - 체크포인트: 입고부터 출고까지 한 바퀴가 도는가. **여기서 기능은 끝**
- **3주차** — 더미 100만 건 → Before → 인덱스 → N+1 → 캐싱 → 부하 테스트 → 배포 → README
  - 체크포인트: Before/After 숫자가 표로 정리돼 있는가

### 1-6. 2주차 시험 배포는 빼지 않는다

성공이 목적이 아니라 **문제 목록을 뽑는 게 목적**이다.

3주차 마지막 날 처음 배포하면 CORS, 환경변수, HTTPS, 빌드 실패가 한꺼번에 터지고 그날 밤을 새우게 된다. 미리 한 번 부딪혀서 목록을 만들어두면 3주차가 측정에만 쓰인다.

## 2. 추가로 알면 좋은 활용법

### 2-1. 순서를 지키는 것이 범위를 지키는 것만큼 중요하다

**기능 완성 → 더미 데이터 투입 → Before 측정 → 최적화 → After 측정.**

최적화를 먼저 넣고 싶은 유혹이 계속 생긴다(인덱스를 처음부터 걸어두기, 캐시를 미리 붙이기). 그러면 개선 폭을 증명할 수 없게 되고, "왜 넣었냐"는 질문에 답할 근거가 사라진다.

Redis 컨테이너를 처음부터 띄우되 3주차까지 연결하지 않는 것도 같은 이유다.

### 2-2. 잘라낸 것을 지우지 말고 백로그로 옮긴다

- Redis 분산 락 추가 후 3방식 비교
- 재고 실사, 엑셀 업로드
- 재고 현황 조회를 MyBatis로도 구현해 비교 → [[WMS 05 - JPA와 MyBatis]]
- 프론트 UI 정리

"안 만들었다"와 "판단해서 뺐다"는 다르다. 백로그로 남겨두면 후자가 되고, 왜 뺐는지 설명할 수 있으면 그것도 결정의 근거가 된다.

### 2-3. 밀리면 다음 주에서 더 자른다

각 주 마지막 체크포인트에 "아니오"가 나오면, 다음 주 계획에서 기능을 더 잘라낸다. 일정을 늘리는 게 아니라 범위를 줄이는 방향으로만 조정한다. 3주라는 시간이 고정값이기 때문이다.

## 3. 더 나아가 알면 좋은 것

### 3-1. 다음에 볼 키워드

- HID(Human Interface Device) — 바코드 스캐너가 키보드로 인식되는 원리
- k6 — 부하 테스트 도구. 1주차부터 조금씩 스크립트를 준비해둔다
- 타임박싱 — 기간을 고정하고 범위를 조정하는 방식

### 3-2. 3주 이후 저강도 기간에 할 것

기능 추가가 아니라 **기록 다듬기**가 맞다. README 정리, 측정 표 보강, 그래프 추가. 주당 몇 시간으로 새 기능을 만들면 반쯤 만들다 만 상태로 남을 위험이 크다.

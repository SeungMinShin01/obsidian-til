# RAG 챗봇 06 - 구현 범위와 담당 경계

> 허브: [[RAG 챗봇 프로젝트 MOC]]

**물어본 것:** 지금 코드는 어디까지 구현되어 있는가. 그리고 내 몫은 업로드부터 검색까지, 그 결과를 답변 생성 모듈에 넘기는 데까지인가.

## 1. 배운 내용

### 1-1. 코드는 끝까지 있고, 실행은 청킹까지다

파일 기준으로는 업로드부터 답변까지 전부 쓰여 있다. 다만 실제로 돌린 흔적은 청킹까지다.

| 자리 | 상태 |
| --- | --- |
| 벡터 DB 폴더 | 비어 있음 |
| 문서 메타 테이블 | 행 0개 |
| 환경 변수 파일 | 없음 (예시 파일만 있음) |
| 청크 덤프 파일 | 있음 |

인증키가 없으면 임베더를 만드는 순간 바로 예외가 난다. 청크 덤프는 인증키 없이 도는 단계라 거기까지 검증해본 상태다. → [[RAG 챗봇 04 - 청킹에 AI가 들어가지 않는 이유]]

아예 없는 것은 프론트엔드, 문자 인식(OCR), 테스트 코드, 검색 고도화(리랭킹·하이브리드)다.

### 1-2. 경계는 답변 생성 모듈이다

```
[내 몫]                                             [팀원 몫]
업로드 → 파싱 → 전처리 → 청킹 → 임베딩 → 벡터 DB 저장
질문 → 임베딩 → 검색 → [{"text","page"}] ──넘김──→ 답변 생성 → 답변
```

인수인계는 두 줄로 끝난다. 검색이 청크 목록을 만들고, 그것을 답변 생성 함수에 인자로 넘긴다.

### 1-3. 넘기는 것은 JSON이 아니라 파이썬 객체다

생긴 모양이 JSON과 같아 헷갈리기 쉬운데, 실제로 넘어가는 것은 **리스트 안의 딕셔너리**다.

```python
[{"text": "Operating voltage: 2.3V to 5.5V.", "page": 15}, ...]
```

네트워크로 문자열을 보내는 것이 아니라 같은 프로세스 안에서 함수 인자로 건네는 것이다. JSON이 되는 것은 맨 마지막, 웹 프레임워크가 브라우저에 응답을 돌려줄 때다.

### 1-4. 이 구분이 타입 규칙을 만든다

페이지 번호는 반드시 정수여야 한다.

```python
"page": int(meta.get("pageNumber", 0))
```

JSON을 거친다면 숫자로 직렬화되므로 신경 쓸 일이 없지만, 파이썬 객체를 직접 넘기므로 문자열로 넣으면 문자열 그대로 도착한다. 받는 쪽은 지어낸 페이지 번호를 걸러내려고 **넘겨받은 페이지 집합과 같은지 비교**하는데, `"15"`와 `15`는 같지 않다고 판정된다.

결과는 에러가 아니라 **출처 페이지가 조용히 사라지는 것**이다. 실패가 소리를 내지 않는 종류라 규칙으로 못박아둘 수밖에 없다.

### 1-5. 빈 결과도 계약의 일부다

검색 결과가 비면 답변 생성 함수는 바깥 서버를 부르지 않고 "정보가 없다"는 문장을 바로 돌려준다. 거리 상한으로 관련 없는 청크를 걸러내는 것이 곧 **불필요한 호출을 막는 장치**가 된다.

### 1-6. 맞추는 쪽이 정해져 있다

받는 쪽 모듈은 고치지 않고, 넘기는 쪽이 형식을 맞춘다. 그래서 형식 변환이 한 자리에 모여 있다. 인제스천 때 `pageNumber`로 저장한 값을 검색 단계에서 `page`로 바꿔 넘기는 것도 여기서 한다.

기능이 필요해지는 시점까지 불러오기를 미루는 방식도 같은 맥락이다. 서버가 뜰 때가 아니라 첫 질문이 들어올 때 불러오면, 불러오기 시점의 부수효과가 서버 기동마다 반복되지 않는다. → [[RAG 챗봇 02 - 패키지 초기화 파일이 비어 있는 이유]]

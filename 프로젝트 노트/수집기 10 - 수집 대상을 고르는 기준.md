# 수집기 10 - 수집 대상을 고르는 기준

> 허브: [[수집기 프로젝트 MOC]]

API 승인을 기다리느니 크롤링을 하는 판단에서 시작해, 무엇을 기준으로 수집 대상을 고를지 정리한 기록이다.

## 1. 배운 내용

### 1-1. 처음 논거는 틀렸다

크롤링을 미루자는 이유로 "구조가 바뀌면 깨진다"와 "유지보수 부담이 크다"를 들었는데, 이 둘은 **이 프로젝트에서 유효한 논거가 아니다.**

설계 단계에서 이미 이렇게 정해두었기 때문이다.

> 비공식 소스는 구조 변경에 취약하다. 어댑터를 격리해 한 소스가 죽어도 전체가 죽지 않게 하고, 실패 시 해당 소스만 건너뛴다.

깨지는 것을 전제하고 대응책까지 설계해두었으므로, 깨진다는 것 자체는 물러설 이유가 되지 않는다. 오히려 겪는 편이 학습 목적에 맞다.

### 1-2. 남는 이유는 하나뿐이다

| 이유 | 유효한가 |
| --- | --- |
| 깨진다 | 약함. 어댑터 격리로 대응하기로 이미 정했다 |
| 유지보수 부담 | 약함. 그것도 배울 거리다 |
| **법적·약관 리스크** | **강함. 성격이 다르다** |

세 번째만 남는 이유는 **겪고 고칠 수 있는 종류가 아니기 때문**이다. 이 프로젝트의 원칙에 그대로 걸린다.

> 되돌릴 수 있는 것은 겪은 뒤에 정한다. **되돌릴 수 없는 것만 지금 확정한다.**

크롤러가 깨지는 것은 되돌릴 수 있다. 법적 문제는 되돌릴 수 없다.

### 1-3. 채용공고는 판례가 있는 도메인이다

2017년 대법원은 **잡코리아가 사람인을 상대로 낸 소송에서 잡코리아의 손을 들어주었다.** 사람인이 잡코리아의 채용공고를 크롤링해 자기 사이트에 올린 것이 **데이터베이스권 침해**라는 판단이었다.

채용공고 데이터가 법적으로 보호받는 자산으로 다뤄진 사례이고, 하필 이 프로젝트의 첫 수집 대상이 그 판례의 당사자다.

### 1-4. `robots.txt`를 먼저 읽는다

크롤링 어댑터를 만들 때의 **첫 단계**다. 주소는 항상 도메인 뒤에 `/robots.txt`를 붙이면 된다.

```
https://www.saramin.co.kr/robots.txt
```

읽는 법은 단순하다.

```
User-agent: *              ← 어떤 봇에게 하는 말인가 (*는 전부)
Disallow: /zf_user/jobs/view   ← 이 경로는 자동 접근하지 말아달라
Allow: /                       ← 이 경로는 괜찮다
Crawl-delay: 10                ← 요청 사이에 10초를 두어달라
```

**법이 아니라 공개된 요청**이다. 다만 명시적으로 거절해둔 경로를 긁으면 "몰랐다"가 성립하지 않는다.

### 1-5. 조사 결과 (2026-08-13)

| 사이트 | 채용공고 경로 | 비고 |
| --- | --- | --- |
| 사람인 | **차단** (`/zf_user/jobs/view`) | GPTBot·Bytespider 전면 차단 |
| 원티드 | **확인 불가** | `robots.txt` 요청 자체가 403으로 거절됨 |
| 잡코리아 | 허용 (목록·상세) | AI 크롤러 명시 허용, CCBot·Diffbot 등 수집 전용 봇은 차단 |
| 로켓펀치 | 허용 (`/jobs`) | 검색 페이지만 차단, bingbot에 10초 지연 요청 |
| 프로그래머스 | 허용 | 관리자·회원 경로만 차단 |
| 점핏 | 허용 | GPTBot만 전면 차단 |

**원티드가 가장 강경하다.** 정책 파일은 원래 누구나 읽으라고 두는 것인데 그것마저 403으로 막았다. 봇 트래픽을 아예 거부하겠다는 뜻으로 읽힌다.

**잡코리아는 소송에서 이긴 쪽인데 문은 열어두었다.** 검색 노출은 원하기 때문이다. 다만 `CCBot`·`Diffbot` 같은 데이터 수집 전용 봇은 차단했다. **검색엔진은 환영, 데이터를 긁어가는 것은 거절**이라는 선이 분명하다.

### 1-6. `robots.txt`는 허가증이 아니다 — 층이 셋이다

| 층 | 무엇을 정하나 | 확인 방법 |
| --- | --- | --- |
| `robots.txt` | 자동 접근을 원하는가 | 도메인 + `/robots.txt` |
| **이용약관** | 자동 수집·저장을 허용하는가 | 사이트 하단 약관 |
| **용도** | 개인 보관인가 재배포인가 | 내가 정한다 |

`robots.txt`가 열려 있다고 약관이 자동 수집을 허용한 것은 아니다. 소송까지 한 회사라면 약관은 오히려 빡빡할 가능성이 높다.

이 프로젝트의 **용도**는 안전한 쪽에 속한다.

- Private 저장소에 보관
- 개인 취업 준비 목적
- 재배포하지 않음
- 하루 1회, 서버 부담 없음

셋 다 갖추면 실질 위험은 낮아진다. 사람인 오픈 API 신청서에 적은 이용목적과도 같은 내용이다.

## 2. 추가로 알면 좋은 활용법

### 2-1. 정해진 후보 순서

1. **워크넷 API** (공공데이터포털) — 애초에 가져가라고 만든 것. 승인이 빠르고 법적으로 깨끗하다
2. **사람인 API** — 신청해두었으므로 승인되면 추가한다
3. **로켓펀치 · 프로그래머스 · 점핏** — 크롤링 어댑터를 만든다면 여기부터. 문이 열려 있고 직무도 맞는다
4. **잡코리아** — 열려 있지만 소송 이력이 있으므로 약관을 읽고 판단한다
5. **원티드 · 사람인** — 명시적으로 거절했으므로 크롤링하지 않는다

### 2-2. 이 순서가 설계 검증도 겸한다

API로 배관을 먼저 검증하고 크롤링 어댑터를 나중에 붙이면, 크롤러가 깨져도 API 소스가 계속 돈다. **한 소스가 죽어도 전체가 죽지 않는다**는 설계를 실제로 확인할 수 있다.

소스가 둘이 되어야 어댑터 구조가 진짜 되는지 알 수 있다. 하나로는 알 수 없다.

### 2-3. 크롤링 어댑터를 만들 때의 순서

1. `robots.txt` 확인 — 대상 경로가 허용되는가
2. 이용약관 확인 — 자동 수집 조항이 있는가
3. 요청 간격 두기 — `Crawl-delay`가 있으면 지키고, 없어도 여유를 둔다
4. `User-Agent`에 정체와 연락처 남기기 — 문제가 생겼을 때 차단 대신 연락이 오게 한다
5. 실패 시 그 소스만 건너뛰기 — 전체 파이프라인을 죽이지 않는다

## 3. 더 나아가 알면 좋은 것

### 3-1. 다음에 볼 키워드

- 데이터베이스권 — 저작권과 별개로 데이터 집합을 보호하는 권리
- `sitemap.xml` — 사이트가 스스로 공개한 페이지 목록. `robots.txt` 하단에 주소가 있다
- `Crawl-delay`와 요청 간격 조절
- API 이용약관에서 확인할 것 — 호출 한도, 캐싱 허용 기간, 재배포 조항

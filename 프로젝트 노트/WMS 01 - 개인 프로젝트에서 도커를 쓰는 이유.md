# WMS - 개인 프로젝트에서 도커를 쓰는 이유

> 허브: [[WMS 프로젝트 MOC]]

## 1. 배운 내용

### 1-1. 팀 프로젝트에서 배운 도커의 명분은 혼자 하면 사라진다

도커를 쓰는 이유로 가장 먼저 배우는 것은 "팀원 모두가 같은 환경에서 개발한다"다. 누구는 MySQL 8.0, 누구는 5.7을 깔아놨을 때 생기는 "내 컴퓨터에선 되는데" 문제를 없앤다는 것.

그런데 이 프로젝트는 혼자 한다. 그 명분이 통째로 사라진 상태에서 도커를 쓸 이유가 남아 있는지를 먼저 확인했다.

### 1-2. 남는 이유 — 측정 재현성

이 프로젝트의 최종 산출물은 기능 목록이 아니라 **Before/After 성능 측정 표**다. 그래서 "이 숫자를 어떤 조건에서 쟀는가"가 숫자 자체만큼 중요하다.

DB의 버퍼 풀 크기 같은 설정이 측정 사이에 바뀌면 같은 쿼리도 다른 시간이 나온다. 로컬에 직접 설치한 MySQL은 설정이 언제 어떻게 바뀌었는지 추적할 방법이 없다. 언젠가 튜닝한다고 만졌던 값이 남아 있어도 알 수 없다.

`docker-compose.yml`에 설정을 적어두면 **측정 조건이 코드가 되고 git 이력에 남는다.** "이 조건에서 잰 값"이라고 말할 근거가 생긴다. 이게 개인 프로젝트에서도 도커를 쓰는 첫 번째 이유다.

### 1-3. 남는 이유 — DB를 마음껏 부술 수 있다

3주차에는 이력 100만 건을 넣고 인덱스를 붙였다 뗐다 반복한다. 그 과정에서 DB가 엉키거나 데이터가 오염되는 일이 반드시 생긴다.

컨테이너면 `docker compose down -v` 후 다시 올리면 30초 만에 깨끗한 상태로 돌아온다. 로컬 설치본이면 수동으로 복구해야 하고, 그 시간이 3주짜리 일정에서는 아프다.

### 1-4. 남는 이유 — 배포가 쉬워진다

3주차에 "실제 배포된 주소"를 남기는 것이 평가 항목이다. 로컬과 서버가 같은 이미지를 쓰면 "로컬에선 됐는데 서버에서 안 된다"는 문제가 대부분 사라진다.

### 1-5. 도커가 오히려 해로운 지점

Windows에서 Docker Desktop은 WSL2 위에서 돈다. 디스크 I/O가 네이티브보다 느리고 실행마다 편차가 크다. 그래서 **절대 수치(p95가 몇 ms인지)는 왜곡된다.**

다만 Before/After는 같은 환경끼리의 상대 비교라 **개선 폭 자체는 여전히 유효하다.** README에 "Docker 환경 기준"이라고 한 줄 적으면 정직한 기록이 된다.

한 가지 더, 앱까지 컨테이너에 넣으면 핫 리로드가 죽고 디버거를 붙이기 번거로워진다.

### 1-6. 그래서 DB와 Redis만 컨테이너에 둔다

앱(Spring Boot, React)은 IDE에서 직접 실행한다. 재현성과 격리는 챙기면서 개발 편의는 잃지 않는 절충이다.

배울 명령어도 `up`, `down`, `logs` 정도라 학습 비용이 거의 없다.

## 2. 추가로 알면 좋은 활용법

### 2-1. named volume을 써야 하는 이유 (Windows에서 특히)

DB 데이터를 어디에 둘지는 두 가지 방법이 있다.

- **바인드 마운트** — `- ./data:/var/lib/mysql` 처럼 호스트의 실제 폴더를 연결한다
- **named volume** — `- wms-mysql-data:/var/lib/mysql` 처럼 도커가 관리하는 저장 공간을 쓴다

Windows에서 바인드 마운트로 `C:\` 경로를 물리면 컨테이너가 파일을 읽고 쓸 때마다 **WSL 경계를 넘나든다.** 디스크 I/O가 몇 배 느려지고, 3주차 측정 숫자가 통째로 왜곡된다.

named volume은 WSL 내부 파일시스템에 저장되므로 이 문제가 없다. 대신 탐색기로 파일을 직접 볼 수 없는데, DB 데이터 파일은 어차피 직접 볼 일이 없다.

### 2-2. 이미지 태그를 고정한다

`mysql:latest`를 쓰면 어느 날 `docker compose pull`을 했을 때 다른 버전이 내려온다. 측정 중간에 DB 버전이 바뀌면 Before/After 비교가 무너진다.

`mysql:8.0`처럼 마이너 버전을 고정하고, **3주차 측정을 시작하기 전에는 정확한 패치 버전(`mysql:8.0.39`)까지 고정한다.**

### 2-3. 포트를 기본값에서 비켜둔다

로컬에 MySQL이 이미 설치돼 있으면 3306 포트가 물려 있어 컨테이너가 뜨지 않는다. 3307처럼 한 칸 옮겨두면 충돌을 피한다. Redis도 6379 대신 6380을 쓴다.

## 3. 더 나아가 알면 좋은 것

### 3-1. 다음에 볼 키워드

- `healthcheck` — 컨테이너가 "떴다"와 "쓸 준비가 됐다"는 다르다. DB는 프로세스가 시작되고도 몇 초 뒤에야 접속을 받는다
- `depends_on`과 `condition: service_healthy` — 앱을 컨테이너에 넣게 되면 필요해진다
- 볼륨 백업 — 측정용 100만 건 데이터를 매번 다시 넣지 않으려면 볼륨을 덤프해두는 방법이 있다
- Dockerfile과 멀티스테이지 빌드 — 3주차 배포 때 앱을 이미지로 만들 때 필요하다

### 3-2. 3주차에 확인할 것

`docker stats`로 컨테이너의 CPU·메모리 사용량을 볼 수 있다. 측정 중에 이 값을 같이 기록해두면 "쿼리가 느린 것"인지 "리소스가 부족한 것"인지 구분할 수 있다.

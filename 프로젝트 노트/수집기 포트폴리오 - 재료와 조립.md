# 수집기 포트폴리오 - 재료와 조립

> 고립 노트 — **나가는 링크를 두지 않는다.** 다른 노트를 위키링크로 가리키지 않고, 참조는 낫표(「」) 평문으로만 쓴다. 지금은 「수집기 프로젝트 MOC」 장부에서 들어오는 한 방향만 남아 있고, 그 유입을 막는 규칙은 마스터 세션이 별도로 정한다.

collector를 채용 포트폴리오로 **패키징**하기 위한 재료 창고이자 조립 양식이다. 사건이 날 때마다 재료를 여기에 모으고, 최종 산출물(README·포트폴리오 문서)은 지원 시점에 조립한다.

## 이 노트로 세션 여는 법

이 노트는 **수집기 포트폴리오(패키징)**를 다루는 세션의 집이다. 새 세션을 열면 "이 노트 읽고 안내대로 진행해"만 하면 된다.

- **역할**: 채용담당자(외부 청중)에게 역량을 전달하는 패키징만. **코드도 방향(로드맵)도 건드리지 않는다** — 빌드는 수집기 프로젝트 세션, 방향은 로드맵 세션.
- **먼저 읽을 것**: 이 노트 전체 + `트러블슈팅/`·`변경이력/`·수집기 NN 노트 + 실제 코드(`Desktop/수집기/collector`). 이것들이 재료의 원천이다.
- **핵심 원칙**: 포트폴리오는 **코드 덤프가 아니다.** 역량 하나를 증명하는 코드 조각을 골라 "왜(문제 → 설계 결정 → 결과)"를 붙인다. 서사가 상품이고 코드는 근거다.
- **방식**: 재료를 계속 append(대부분 있는 노트에서 끌어옴), 최종 산출은 지원 시점에 조립.
- **노트 수정은 요청할 때만.** 평소엔 텍스트로 논의한다.
- **경계**: 아래 표대로. 관할 밖은 **읽기만** 하고, 고쳐야 할 상태면 직접 고치지 말고 해당 세션에 요청한다.

| 대상 | 관할 | 이 세션 |
| --- | --- | --- |
| 이 노트 (재료와 조립) | **여기** | 쓰기 |
| 코드 · 리포 파일 (`README.md` 포함) | 수집기 프로젝트 세션 | 읽기만 — **쓰기 금지** |
| `수집기 NN` 노트 · 변경이력/ · 트러블슈팅/ · 수집기 코드분석/ | 수집기 프로젝트 세션 (코드분석은 코드분석 세션) | 읽기만 |
| 「수집기 프로젝트 MOC」 전체 | 수집기 프로젝트 세션 | 읽기만 |
| **「수집기 로드맵 - 장기 구상」** | **로드맵 세션** | **읽기만 — 쓰기 금지** |
| Vault 규칙 (`CLAUDE.md` · `_규칙/` · `_템플릿/`) | 마스터 세션 | 읽기만 |

**README는 이 노트 안에 초안까지만 쓴다.** 리포에 반영하는 것은 수집기 프로젝트 세션 몫이다 — 코드 리포에 손대는 세션을 하나로 묶어야 "누가 리포를 건드렸나"가 흐려지지 않는다.

로드맵 노트는 재료로 읽되 고치지 않는다. 패키징을 하다 방향 자체를 바꿔야 한다고 판단되면 **여기서 텍스트로 말하고 반영은 로드맵 세션에 맡긴다.**

## 포트폴리오 양식 (프로젝트 1개 기준)

- **한 줄 소개 + 메타** — 뭐 하는 프로젝트인지 한 문장, 기간, 인원(개인), 역할·기여도
- **기술 스택 + 선택 이유** — Python·SQLite·GitHub Actions를 *왜* 골랐나까지
- **아키텍처 다이어그램** — 수집 → 저장(SQLite) → 뷰(md) → 통계 흐름 한 장
- **핵심 기능 + 담당 코드** — 아래 재료 인벤토리의 조각들
- **기술적 문제와 해결(트러블슈팅)** — *수치화된 성과와 함께*
- **배운 점 / 회고**
- **링크** — GitHub, (있으면) 배포·데모 URL

## 재료 인벤토리 — 뽑을 핵심 코드 조각

각 조각은 "증명하는 역량"과 짝을 이뤄야 한다. 코드만 두지 말 것.

| 조각 | 위치 | 증명하는 역량 | 붙일 "왜" |
| --- | --- | --- | --- |
| 어댑터 패턴 + 예외 격리 | `sources/`, `main.py`의 collect_all | **확장 가능한 설계 · 장애 격리** | 소스 하나가 죽어도 나머지가 돈다 (부패방지계층·덕타이핑·격벽) |
| 2단계 수집 + known_ids 계약 | `sources/jumpit.py` | **효율적 증분 수집** | 목록→신규만 상세 호출, DETAIL_CAP으로 회차 분산 |
| 마이그레이션 + id 접두사 소급 | `migrations/001`, `migrate.py` | **무중단 스키마 진화 · 데이터 무손실** | 866건 안 지우고 컬럼 추가, id에서 source 역산 |
| 무인 운영 설계 | `collect.yml`, `store.py`, 조기 종료 | **운영 · 비용 관점** | 멱등성(INSERT OR IGNORE), 조기 종료, 하루 5회 = 월 한도 15% |
| co_occurrence 통계 | `stats.py` | **수집 데이터로 인사이트** | 동시출현으로 학습 우선순위 도출 |

## 트러블슈팅 서사 후보 (수치와 함께)

원재료는 `트러블슈팅/` 폴더. 포트폴리오엔 2~3개만 골라 STAR로.

- **12일 공백** → 알려진 실패의 트리아지·관측성. "초록불이 실패를 가린다"는 함정과 그 뒤 traceback·로그 개선.
- **CRLF 가짜 변경** → 두 OS 협업·git 내부(autocrlf). `463 insertions = 463 deletions`의 정체.
- **조용한 차단 / 빈 결과 감지** → 관측성 설계 (예정, 잡코리아 step에서 나올 재료).
- **URLError** → 예외 계층 구분(KeyError/HTTPError/URLError)과 일시적 장애 대응.
- 수치 예: 수집 빈도 설계로 월 무료 분의 15%만 사용 · 마이그레이션으로 866건 무손실.

## 공유 경계

- **공개 가능**: 코드(설계·구조), 아키텍처, 집계 통계, 트러블슈팅 서사
- **비공개**: 원본 수집 데이터·DB, (선택) 크롤러 어댑터
- 이 경계 설계 자체를 포트폴리오에 한 줄 쓴다 — 개인정보·저작권·재배포를 고려한 공개 범위 결정은 그 자체가 성숙함의 증거.

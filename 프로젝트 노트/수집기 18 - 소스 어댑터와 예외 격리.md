# 수집기 18 - 소스 어댑터와 예외 격리

> 허브: [[수집기 프로젝트 MOC]]

`main.py` 안에 상수로 박혀 있던 가짜 공고를 `sources/fake.py`로 빼내고, `main.py`가 **소스 목록을 순회**하도록 바꾼 단계다. 「수집기 08 - main.py를 오케스트레이터로 바꾸기」에서 만든 오케스트레이터가 여기서 실제로 지휘를 시작한다.

## 1. 배운 내용

### 1-1. 이 단계의 목표는 데이터가 아니라 계약이다

가짜 공고 3건은 그대로다. 바뀐 것은 **그것이 어디서 오는가**뿐이다.

지금 옮겨두면 나중에 진짜 소스를 붙일 때 `sources/` 안에 파일 하나만 추가하면 된다. **계약을 먼저 굳히고 구현을 나중에 끼우는 순서**다.

### 1-2. `fetch()` — 모든 소스가 따르는 모양

```python
"""가짜 채용공고 소스. 배관을 검증하는 용도이고 실제 사이트를 부르지 않는다."""

JOBS = [
    {"id": "fake:1", "title": "백엔드 개발자", "company": "가나테크"},
    {"id": "fake:2", "title": "풀스택 개발자", "company": "다라소프트"},
    {"id": "fake:3", "title": "AI 엔지니어", "company": "마바랩스"},
]


def fetch() -> list[dict]:
    """이 소스가 제공하는 공고 목록을 돌려준다."""
    return list(JOBS)
```

이 함수는 **이 소스가 무엇을 줄 수 있는지 답하는 것**이 전부다. 저장도 판정도 하지 않는다.

중요한 것은 코드가 아니라 **이름과 반환형**이다.

```
fetch() -> list[dict]
```

앞으로 만들 모든 소스가 이 모양을 따른다. 그러면 `main.py`는 **어느 소스인지 몰라도 똑같이 부를 수 있다.**

### 1-3. 덕 타이핑 — 인터페이스를 선언하지 않는다

자바라면 `interface Source { List<Job> fetch(); }`를 만들고 각 클래스가 `implements`를 붙인다. 파이썬은 그런 선언 없이 **모양이 같으면 같은 것으로 취급한다.**

> 오리처럼 걷고 오리처럼 운다면 오리로 본다.

장점은 준비할 것이 없다는 것이고, 단점은 **약속을 어겨도 아무도 안 막는다**는 것이다. `fetch`가 아니라 `get`이라고 이름 붙여도 문법 오류가 나지 않고, 그 소스를 실제로 부르는 순간에야 터진다.

그래서 계약이 문서가 아니라 **관례**로만 존재한다. 소스가 늘어나면 이 관례를 지키는 것이 온전히 사람 몫이다.

### 1-4. `list(JOBS)` — 사본을 돌려준다

`return JOBS`라고 하면 원본 리스트를 그대로 내준다. 받은 쪽이 그것을 수정하면 다음 호출에서 바뀐 것이 나온다.

진짜 API를 부를 때는 매번 새 리스트가 오므로 자연히 해결되는 문제다. 하지만 **가짜만 다르게 동작하면 검증이 안 되므로** 맞춰둔다.

> 테스트용 대역은 진짜와 같은 성질을 가져야 검증에 쓸모가 있다.

### 1-5. `id`의 소스 접두사

```
fake:1  saramin:12345  rocketpunch:678
```

소스가 여러 개가 되면 서로 다른 사이트의 공고 번호가 겹칠 수 있다. 접두사가 그것을 막는다.

`writer.py`의 `_safe_name`이 `:`를 `_`로 바꾸는 것도 이것을 전제한 처리였다. → 「수집기 11 - writer.py 마크다운 생성」

### 1-6. `collect_all()` — 순회하고 격리한다

```python
def collect_all(sources: list) -> tuple[list[dict], list[str]]:
    """모든 소스에서 공고를 모은다. 실패한 소스는 건너뛰고 이름만 남긴다."""
    jobs = []
    failed = []

    for source in sources:
        name = source.__name__.split(".")[-1]
        try:
            jobs.extend(source.fetch())
        except Exception as e:
            failed.append(f"{name}({type(e).__name__})")

    return jobs, failed
```

`source.__name__`은 **모듈도 객체라서 이름을 안다**는 것을 이용한다. `collector.sources.fake`가 나오므로 마지막 조각만 쓴다.

`extend`는 리스트를 통째로 이어붙인다. `append`였다면 리스트 안에 리스트가 들어간다.

### 1-7. 여기가 fail-soft 자리다

[[개념 - 빠르게 실패하기]]에 적어둔 판단이 실제로 쓰이는 지점이다.

| 어디 | 어떻게 | 왜 |
| --- | --- | --- |
| 인증키가 없다 | **멈춘다** | 뒤의 모든 단계가 무의미하다 |
| 소스 하나가 죽는다 | **넘어간다** | 나머지 소스의 공고는 여전히 쓸모 있다 |

기준은 그대로다. **계속 진행해서 의미 있는 결과가 나오는가.**

### 1-8. `except Exception`이지 `except:`가 아니다

맨 `except:`는 `KeyboardInterrupt`(Ctrl+C)와 `SystemExit`까지 잡는다. 그러면 사람이 멈추려 해도 안 멈춘다.

`Exception`은 그 둘의 부모가 아니므로 통과시킨다. 예외 계층이 이렇게 갈라져 있는 이유가 여기 있다.

```
BaseException
├─ KeyboardInterrupt   ← 잡으면 안 되는 것
├─ SystemExit          ← 잡으면 안 되는 것
└─ Exception           ← 우리가 잡을 것
   ├─ ValueError
   ├─ KeyError
   └─ ...
```

### 1-9. 실패를 삼키되 조용하지 않게 한다

`failed` 리스트가 그 장치다.

무인 시스템에서 `except: pass`는 최악인데, **아무 일도 없었던 것처럼 보이면서 데이터만 비어 있기 때문**이다. 3개월 뒤에 발견하면 어느 시점부터 비었는지도 모른다.

잡는 것과 숨기는 것은 다르다. **잡되 기록한다.**

### 1-10. 로그가 두 층으로 나뉜다

`type(e).__name__`만 남기고 예외 메시지 전체를 넣지 않는다. 메시지는 길고, **요청 주소가 섞여 들어올 수 있다.** 「수집기 12 - 인증키를 코드 밖에 두기」에 적었듯 `run-log.md`는 마스킹이 없다.

| 어디 | 무엇 | 보호 |
| --- | --- | --- |
| `run-log.md` | 요약 — 소스명과 예외 종류 | 없음. 저장소에 그대로 커밋된다 |
| Actions 로그 | 전체 추적 | GitHub가 Secret을 자동 마스킹 |

상세가 필요하면 Actions 로그를 보면 된다. **요약 로그는 짧고 안전하게 유지한다.**

### 1-11. `main.py`가 어떻게 바뀌었나

세 군데가 바뀌었다.

**소스를 불러오는 자리가 생겼다**

```python
from sources import fake

SOURCES = [fake]
```

`FAKE_JOBS` 상수는 지웠다. 데이터가 `sources/fake.py`로 옮겨갔기 때문이다.

`SOURCES`는 **모듈을 담은 리스트**다. 문자열이나 클래스가 아니라 모듈 객체 자체를 넣는다. 파이썬에서 모듈은 일급 객체라 변수에 담고 리스트에 넣고 함수에 넘길 수 있다. 그래서 별도의 등록 장치 없이 이 한 줄이 곧 소스 목록이 된다.

소스가 늘면 이렇게 된다.

```python
from sources import fake, rocketpunch

SOURCES = [fake, rocketpunch]
```

**추가할 때 고치는 곳이 두 줄뿐이다.** `collect_all`도 `store`도 `writer`도 손대지 않는다. 이것이 어댑터 구조로 얻는 실제 이득이다.

**`main()`이 수집 결과를 받아 넘긴다**

```python
def main() -> None:
    stamp = now_utc()

    jobs, failed = collect_all(SOURCES)

    conn = store.connect()
    new_count = store.upsert_jobs(conn, jobs, stamp)
    total = store.count_jobs(conn)
    rendered = writer.render_jobs(conn)
    conn.close()
```

이전에는 `store.upsert_jobs(conn, FAKE_JOBS, stamp)`로 상수를 그대로 넘겼다. 이제 **수집해온 것을 넘긴다.** `store`는 그 목록이 어디서 왔는지 모르고 알 필요도 없다.

**`stamp`를 맨 위에서 한 번만 찍는다**

`now_utc()`를 수집 전에 한 번 부르고 그 값을 계속 쓴다. 수집이 오래 걸려 자정을 넘겨도 **그 회차의 모든 공고가 같은 `first_seen_at`을 갖는다.**

한 번의 실행은 한 시점으로 기록되는 편이 나중에 세기 쉽다. 공고마다 시각을 따로 찍으면 "8월 14일에 몇 건 들어왔나"를 셀 때 경계에 걸린 것들이 애매해진다.

### 1-12. `main`은 여전히 아무 일도 하지 않는다

「수집기 08 - main.py를 오케스트레이터로 바꾸기」에서 정한 성격이 그대로다. 수집은 `sources`가, 저장은 `store`가, 표현은 `writer`가 한다.

다만 역할이 하나 늘었다. **결과를 요약하는 일**이다.

각 계층이 돌려준 숫자를 모아 한 줄로 만드는 것은 어느 계층의 일도 아니다. `store`는 마크다운 건수를 모르고 `writer`는 수집 건수를 모른다. **전체를 보는 자리는 지휘자뿐**이라 여기서 한다.

### 1-13. 로그 한 줄이 계층을 구분하게 됐다

```python
message = (
    f"실행 : {stamp} UTC - 수집 {len(jobs)}건, 신규 {new_count}건, "
    f"누적 {total}건, 마크다운 {rendered}건"
)
if failed:
    message += f", 실패 소스 {' '.join(failed)}"
```

`수집 N건`이 새로 붙으면서 한 줄만 보고 어느 계층이 멈췄는지 알 수 있게 됐다.

| 증상 | 어디가 문제인가 |
| --- | --- |
| 수집 0건 | 소스가 안 준다 |
| 수집됐는데 신규 0건 | **정상.** 이미 아는 공고다 |
| 마크다운 건수가 누적과 다르다 | writer 문제 |
| 실패 소스가 찍혔다 | 그 어댑터 문제 |

무인 시스템에서 로그를 이렇게 쓰는 것이 중요하다. 사람이 매일 들여다보지 않으므로 **한 줄이 스스로 상태를 설명해야 한다.**

## 2. 추가로 알면 좋은 활용법

### 2-1. 격리가 진짜 되는지 확인하는 법

`fetch()` 첫 줄에 일부러 예외를 넣고 돌려본다.

```python
raise RuntimeError("테스트")
```

이렇게 나와야 한다.

```
수집 0건, 신규 0건, 누적 3건, 마크다운 3건, 실패 소스 fake(RuntimeError)
```

**터지지 않고 로그에 남는 것**이 목표다. 예외 처리는 이렇게 일부러 실패시켜보지 않으면 동작하는지 알 수 없다. 정상 경로만 돌려서는 `except` 블록이 한 번도 실행되지 않기 때문이다.

### 2-2. 타입 힌트는 실행 시 검사되지 않는다

`sources: list`라고 적어두어도 파이썬은 그것을 확인하지 않는다. 리스트에 없는 속성을 불러도 **그 줄이 실제로 실행될 때** 비로소 `AttributeError`가 난다. → 「수집기 05-1 - 파이썬 문법 세부」

자바였다면 컴파일러가 미리 잡았을 종류다. 그래서 검사가 두 단계로 나뉜다.

| 단계 | 잡는 것 |
| --- | --- |
| `python -m py_compile` | 문장 구조 |
| 실제 실행 | 이름과 속성의 존재 여부 |

### 2-3. 단수와 복수가 한 글자 차이라는 것

`for source in sources` 형태에서는 리스트와 항목의 이름이 한 글자만 다르다. 둘 다 같은 스코프에 살아 있으므로 **잘못 써도 문법 오류가 아니라 런타임 오류가 된다.**

파이썬의 표준 관례이긴 하지만, 반복 변수를 `src`나 `mod`처럼 다르게 쓰는 쪽을 택하는 사람들도 있다. 관례와 안전 사이의 선택이고 정답은 없다.

### 2-4. `__init__.py`를 만들지 않은 이유

파이썬 3.3부터 폴더에 `__init__.py`가 없어도 패키지로 인식한다. 지금은 없어도 `from sources import fake`가 동작한다.

패키지 초기화 코드가 필요하거나 `from sources import *`의 범위를 정하고 싶을 때 만든다. **필요해지면 그때 만든다.**

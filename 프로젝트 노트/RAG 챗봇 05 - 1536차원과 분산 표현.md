# RAG 챗봇 05 - 1536차원과 분산 표현

> 허브: [[RAG 챗봇 프로젝트 MOC]]

**물어본 것:** 1536차원이라는 게 무엇인가. 그 1536개에 조건들을 다 넣어두는 것인가.

## 1. 배운 내용

### 1-1. 차원은 숫자의 개수다

물리적 공간처럼 들려서 막히는데 훨씬 단순하다.

> **차원 = 그 점을 정하는 데 필요한 숫자의 개수**

1차원은 숫자 하나(직선 위 위치), 2차원은 숫자 둘(평면), 3차원은 숫자 셋(공간)이다. 여기까지가 그림으로 그릴 수 있는 한계이지만, 숫자를 더 붙이는 것은 아무 문제가 없다. **1536차원 = 숫자 1536개로 위치를 정한 것.**

### 1-2. 상상할 필요가 없다

1536차원 공간이 어떻게 생겼는지 그리려는 순간 막히고, 그럴 필요도 없다. 중요한 것은 **차원이 몇이든 계산 공식이 똑같다**는 것이다.

```
2차원:    루트( (a1-b1)^2 + (a2-b2)^2 )
1536차원: 루트( (a1-b1)^2 + ... + (a1536-b1536)^2 )
```

항이 늘어날 뿐 구조가 같다. 기하학적으로 상상이 안 돼도 계산은 문제없이 된다. "1536차원"은 공간의 종류가 아니라 **숫자를 몇 개 다루는지에 대한 말**이다.

### 1-3. 가장 중요한 성질 — 길이가 고정이다

**어떤 텍스트를 넣든 나오는 숫자는 항상 1536개다.**

```
"전압"                          -> 숫자 1536개
"동작 전압은 2.3V에서 5.5V이다"  -> 숫자 1536개
600토큰짜리 문단                 -> 숫자 1536개
```

입력 길이는 제각각인데 출력은 항상 같은 개수다. **길이가 같아야 비교가 되기 때문**에 이것이 결정적이다. 코사인을 계산하려면 같은 자리끼리 곱해야 하는데, 하나는 500개고 하나는 1536개면 계산이 성립하지 않는다.

임베딩의 본질이 여기 있다 — **길이가 제각각인 텍스트를 길이가 고정된 숫자 배열로 바꾸는 것.**

### 1-4. 조건을 넣어두는 것이 아니다

조건을 넣는 방식이라면 이런 모습일 것이다.

```
축1: 전압 얘기인가?  1
축2: 온도 얘기인가?  0
```

사람이 축의 의미를 정하고 문장을 보며 값을 채우는 방식이다. **임베딩은 이것이 아니다.**

아무도 축의 의미를 정하지 않았다. 학습 목표는 하나뿐이다 — **"같은 문맥에 나오는 것들끼리 숫자가 비슷하게 나오도록 하라."** 이 목표만 주고 대량의 문장으로 훈련시키면 모델이 알아서 숫자 배정 방법을 찾아낸다. 축은 **설계된 것이 아니라 학습의 부산물**이라, 3번째 축이 무슨 뜻인지는 모델을 만든 쪽도 모른다.

### 1-5. 조건 방식은 실제로 있었고 실패했다

단어마다 칸을 하나씩 주는 방식이 옛날에 쓰였다.

```
              전압  온도  통신  전원
"동작 전압"     1     0     0     0
"공급 전원"     0     0     0     1
```

**유사도가 나오지 않는다** — `전압` 과 `전원` 은 다른 칸이라 거리가 무관으로 나온다. 뜻이 비슷한데도 그렇다. 사람이 "이 둘은 비슷함"을 일일이 적어주지 않는 한 기계는 모른다.

**칸이 무한정 늘어난다** — 단어 수만큼 칸이 필요하고, 문장 하나에서 1인 칸은 몇 개뿐이라 거의 전부 0인 배열이 된다.

**새 개념을 못 담는다** — 미리 정해둔 조건에 없는 것이 나오면 표현할 방법이 없다.

**조건을 사람이 정하는 방식의 근본 한계**가 이것이다. 세상의 모든 의미를 미리 목록으로 만들 수 없고, 만들어도 그것들 사이의 관계를 일일이 적어줄 수 없다.

### 1-6. 축 하나가 조건 하나에 대응하지도 않는다

학습된 축이라도 "이 축은 전압스러움" 같은 식으로 나뉘어 있지 않다.

```
"전압"이라는 개념 -> 수백 개 축에 걸쳐 흩어진다
축 하나           -> 여러 개념에 동시에 관여한다
```

개념 하나가 여러 축에 퍼져 있고, 축 하나에 여러 개념이 겹쳐 있다. 이것을 **분산 표현**이라 한다. 1536개 숫자가 만들어내는 **전체 패턴**이 의미이고, 하나씩 떼어내면 뜻이 없다.

이 방식이 앞의 문제들을 정확히 해결한다. 칸이 무한정 늘지 않고(조합으로 사실상 무한한 의미를 표현), 비슷한 것끼리 자연히 가까워지며(겹치는 축이 많으므로), 학습 때 못 본 문장도 표현된다.

### 1-7. 그래서 거리만 믿는다

```
축 하나하나의 값     -> 의미 없음. 해석 불가
두 벡터 사이의 거리  -> 의미 있음
```

임베딩을 쓸 때 하는 일은 오직 **비교**이지 값을 읽는 것이 아니다. 실무적으로 세 가지 결과가 따라온다.

- 벡터를 출력해 들여다봐도 **디버깅이 안 된다.** 소수점 숫자 나열일 뿐이다
- 관찰할 수 있는 유일한 창구가 **거리**다. 검색 통로에 거리를 찍어두는 것이 그래서 중요하다
- "왜 이 조각이 안 걸렸지"의 답은 벡터를 뜯어서가 아니라 **거리를 재보고 다른 질문으로 바꿔 던져보며** 찾는다

## 2. 추가로 알면 좋은 활용법

차원 수는 모델마다 다르고 맞바꿈이 있다.

| | 차원 | 특징 |
| --- | --- | --- |
| `text-embedding-3-small` | 1536 | 가볍고 저렴 |
| `text-embedding-3-large` | 3072 | 표현력이 좋고 저장·계산이 2배 |

차원이 늘면 미묘한 의미 차이를 구별할 자리가 생기지만 저장 공간과 계산량이 함께 는다. 무조건 큰 것이 좋은 것이 아니라 다룰 문서의 양과 필요한 정밀도에 맞춰 고르는 값이다.

그리고 **차원이 다르면 섞을 수 없다.** 같은 자리끼리 곱하는 것 자체가 안 되므로, 모델을 바꾸면 전부 다시 만들어야 한다.

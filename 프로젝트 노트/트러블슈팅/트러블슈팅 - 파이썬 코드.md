# 트러블슈팅 - 파이썬 코드

코드 자체에서 터진 것들. 증상별로 쌓는다. **`py_compile`이 통과해도 나는 것들이 많다** — 문법은 맞는데 의미가 틀린 경우다.

---

## `TypeError: 'dict' object is not callable` — 내장 이름을 변수로 덮음 (shadowing)

**증상** 잘 돌던 함수가 갑자기 "이건 호출할 수 없다"고 함.

```python
data = _get(...)      # 원래는 list = _get(...) 이었음
...
list(...)             # TypeError: 'dict' object is not callable
```

**원인** `list = _get(...)`로 파이썬 내장 `list`를 **내 변수로 가려버렸다**(shadowing). 이후 `list(...)`을 부르면 내장 함수가 아니라 방금 담은 dict를 부르려 해서 터진다.

**조치** 변수명을 `data` 등 내장과 안 겹치게. 여기선 `list` → `data`.

**재발 방지** `list`·`dict`·`set`·`id`·`type`·`str`·`sum` 등 **내장 이름을 변수로 쓰지 않는다.** 에디터가 내장 이름에 색을 다르게 주는 것을 신호로 삼는다.

---

## `UnboundLocalError: local variable 'Counter' referenced before assignment` — 두 번째 shadowing

**증상**
```python
Counter = Counter()   # 내가 짠 줄
```
`Counter is not defined`도 아니고 `UnboundLocalError`가 남.

**원인** 함수 안에서 `Counter`에 **한 번이라도 대입**하면 파이썬은 `Counter`를 그 함수의 **지역 변수로 확정**한다. 그러면 오른쪽의 `Counter()`(임포트한 클래스)도 아직 값이 없는 그 지역 변수로 보고 "대입 전 참조"라며 막는다.

**조치** 인스턴스 변수명은 소문자로. `counter = Counter()`.

**재발 방지** shadowing의 두 번째 사례다(첫 번째는 위 `list`). **클래스/내장은 대문자·원래이름 그대로 두고, 담는 변수는 소문자.** 이번엔 `TypeError`가 아니라 `UnboundLocalError`로 나타난 것 — 같은 실수도 위치(대입이 있는지)에 따라 에러 종류가 달라진다.

---

## `NameError: name 'traceback' is not defined` — except 안에서야 터짐

**증상** 평소엔 멀쩡하다가, 소스가 실패해 `except`로 들어간 그 순간에 `traceback is not defined`.

**원인** `except` 블록에 `traceback.print_exc()`를 써놓고 파일 위 `import traceback`을 빠뜨렸다. **예외가 나야만 실행되는 줄**이라 평소 테스트에선 안 걸리고, 정작 진짜 실패했을 때 로그를 남기려다 2차로 터진다.

**조치** 파일 상단에 `import traceback` 추가.

**재발 방지** 오류 처리 코드일수록 **평소에 안 돌아가는 경로**라 늦게 발각된다. import를 추가할 땐 "이게 언제 실행되는 줄인가"를 같이 본다. 격벽(try/except) 안에서 또 터지면 원래 실패가 가려지므로 특히 조심.

---

## 붙여넣기 들여쓰기 사고 — `IndentationError` 또는 조용한 오작동

**증상** 코드를 붙여넣고 돌리니 `IndentationError`, 혹은 에러는 없는데 어떤 줄이 함수 밖/안으로 잘못 들어감.

**원인** 파이썬은 **들여쓰기가 곧 문법**이다. 다른 곳에서 복사한 블록이 탭/스페이스가 섞이거나 한 단계 어긋난 채 붙었다. 편집 중 `SOURCES = [fake]`처럼 **옛 줄이 안 지워지고 남아** 뒤 정의를 덮은 사고도 같은 계열(눈으로 안 본 채 붙임).

**조치** 붙여넣은 직후 **블록 경계를 눈으로 확인** — 이 줄이 어느 함수/루프 안인가. 중복 정의(`SOURCES`가 두 번 나오면 뒤엣것이 이김)가 없는지도.

**재발 방지** 큰 덩어리를 한 번에 붙이지 말고, 붙인 뒤 **함수 목록·정의 목록을 훑는다.** yml의 step 통째 증발 사고(「트러블슈팅 - Actions·배포」)와 같은 습관으로 막는다.

## 상대경로 어긋남 — 실행 위치에 따라 파일을 못 찾음

**증상** 어떤 폴더에서 돌리면 되고, 다른 폴더에서 돌리면 DB·파일을 못 찾거나 엉뚱한 곳에 만든다.

**원인** `"state/collector.db"` 같은 **상대경로는 "현재 작업 디렉터리" 기준**이다. `collector/`에서 실행하느냐 루트에서 실행하느냐에 따라 가리키는 곳이 달라진다. 원격 통로에서 `del`·DB 쓰기가 막힌 것과 겹쳐, "왜 여기선 안 되지"가 경로 문제인지 권한 문제인지 헷갈렸다.

**조치** 실행은 **정해진 한 위치**(루트)에서. DB 쓰기·파일 삭제는 권한 있는 사용자 터미널에서(원격 통로는 읽기 전용).

**재발 방지** "어디서 실행하는가"를 고정한다. 나중에 필요하면 `Path(__file__).parent` 기준의 절대경로로 바꿔 실행 위치와 무관하게 만든다.

## `OREDER BY` — 오타인데 py_compile은 통과

**증상** `py_compile`도 통과하고 임포트도 되는데, 실행하면 SQL이 실패하거나 정렬이 안 됨.

```python
"... OREDER BY posted_at ..."   # ORDER 오타
"...\"AND month = ?"            # 앞 공백 누락 → ...?AND
```

**원인** SQL은 **문자열 안**이라 파이썬 컴파일러가 못 본다. `OREDER` 오타, 조건 이어 붙일 때 앞 공백 누락(`" AND ..."`을 `"AND ..."`로 써서 `?AND`가 됨) — 둘 다 파이썬 문법으론 완벽한 문자열이다.

**조치** SQL 오타·공백 수정. 조건을 문자열로 이어 붙일 땐 **각 조각 앞에 공백**.

**재발 방지** `py_compile`은 **파이썬 문법만** 검사한다 — 문자열 속 SQL, 잘못된 컬럼명, 의미 오류는 못 잡는다. SQL은 짧은 표본에 **실제로 한 번 돌려** 확인한다. 「초록불 ≠ 의도한 결과」가 컴파일 통과에도 그대로 적용된다.

---

## 이 노트들의 공통 교훈

`py_compile` 통과 ≠ 올바른 코드. 여기 모인 것 대부분(shadowing, NameError, SQL 오타)이 **문법은 맞고 의미가 틀린** 경우다. 컴파일러가 잡아주는 건 문법뿐이고, shadowing·미실행 경로·문자열 속 SQL은 **실제로 그 경로를 실행해봐야** 드러난다. 그래서 통계 함수는 짧은 표본에 돌려보고, except 경로는 일부러 실패시켜 확인한다.

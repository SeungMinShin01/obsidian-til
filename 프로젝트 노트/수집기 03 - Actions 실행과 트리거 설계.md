# 수집기 - Actions 실행과 트리거 설계

> 허브: [[수집기 프로젝트 MOC]]

## 1. 배운 내용

### 1-1. 실행은 트리거에 적은 것만 일어난다

워크플로우 내용을 채워서 푸시했는데 새 실행이 생기지 않았다. 목록에는 이전 실행 하나만 남아 있었다. 고장이 아니라 설계대로 동작한 것이다.

```yaml
on:
  schedule:          # 정해진 시각에
  workflow_dispatch: # 사람이 버튼을 누를 때
```

트리거에 `push`가 없으므로 푸시로는 실행되지 않는다. 실행되는 경우는 정해진 시각이 되거나, 수동 버튼을 누를 때 둘뿐이다.

**푸시했는데 아무 일도 안 일어나는 것이 정상인 상황이 있다.** 이걸 모르면 멀쩡한 워크플로우를 고장난 것으로 오해하게 된다.

### 1-2. cron 읽는 법

`"0 0 * * *"`은 공백으로 구분된 다섯 칸이고, 각 칸의 자리가 정해져 있다.

```
 ┌──────── 분    (0-59)
 │ ┌────── 시    (0-23)
 │ │ ┌──── 일    (1-31)
 │ │ │ ┌── 월    (1-12)
 │ │ │ │ ┌ 요일  (0-6, 0=일요일)
 │ │ │ │ │
 0 0 * * *
```

`*`는 아무거나, 매번이라는 뜻이다. 그래서 `0 0 * * *`은 분 0, 시 0, 나머지는 전부 아무거나이므로 매일 0시 0분이 된다.

읽는 요령은 왼쪽 두 칸이 시각, 오른쪽 세 칸이 얼마나 자주인지를 나타낸다는 것이다. 오른쪽이 전부 `*`면 매일이다.

| 표현 | 의미 |
| --- | --- |
| `0 0 * * *` | 매일 0시 |
| `30 9 * * *` | 매일 9시 30분 |
| `0 * * * *` | 매시 정각 (하루 24번) |
| `*/10 * * * *` | 10분마다 (`*/n` = n마다) |
| `0 0 * * 1` | 매주 월요일 0시 |
| `0 0 1 * *` | 매월 1일 0시 |
| `0 9,18 * * *` | 매일 9시와 18시 (`,`로 나열) |
| `0 0 * * 1-5` | 평일만 (`-`로 범위) |

### 1-3. GitHub의 시계는 UTC다

cron에 적은 시각에 9시간을 더하면 한국 시간이 된다. `0 0 * * *`은 한국 시간 오전 9시다. 매일 아침 9시에 수집하려고 이렇게 적었다.

첫 실행 로그에서 이것을 눈으로 확인했다.

```
Hello from Actions, Wed Aug 12 02:52:37 UTC 2026
```

버튼을 누른 시각은 한국 시간 11시 52분이었고 로그에는 02:52 UTC로 찍혔다.

날짜가 밀리는 경우를 주의해야 한다. `0 22 * * 1`(UTC 월요일 22시)은 한국에서는 화요일 오전 7시다. 요일까지 지정할 때 이걸 놓치면 하루가 어긋난다.

### 1-4. 문법이 깨진 워크플로우도 실패로 기록된다

빈 파일 상태로 커밋이 올라간 적이 있는데, 그때 실행 실패 메일이 왔다.

```
[SeungMinShin01/collector] Run failed: .github/workflows/collect.yml - main (d371abc)
```

끝의 `d371abc`가 커밋 번호이고, 그것이 빈 파일이 올라간 커밋이었다. GitHub은 `.github/workflows/` 안에 파일이 생기면 일단 읽으려 시도하고, 해석할 수 없으면 실패한 실행으로 기록한다. 조용히 무시하지 않는다.

트리거와 무관하게 기록된다는 점이 중요하다. 우리 파일에는 `push` 트리거가 없는데도 실패 기록이 남았다. 정상 실행이 아니라 파일을 읽을 수 없다는 에러 보고이기 때문이다.

### 1-5. 실패 메일이 무인 운영의 경보 장치다

이 메일은 앞으로 몇 달간 무인으로 도는 시스템에서 문제를 알아채는 수단이 된다. 실제로 첫날 그것이 작동하는 것을 확인했다.

무인 운영에서 진짜 위험한 것은 실패 자체가 아니라 **조용한 실패**다. 아무도 모르는 채로 몇 주가 지나는 상황을 막아주는 것이 이 알림이다.

### 1-6. workflow_dispatch가 수동 버튼을 만든다

워크플로우 화면에 이런 배너가 떴다.

```
This workflow has a workflow_dispatch event trigger.   [ Run workflow ▾ ]
```

yml에 적은 `workflow_dispatch:` 한 줄 때문에 생긴 버튼이다. 그 줄을 쓰지 않았다면 배너도 버튼도 없다.

이 버튼이 필요한 이유는 `schedule`만 있으면 확인할 때마다 다음 예정 시각까지 기다려야 하기 때문이다. 고칠 때마다 하루씩 기다릴 수는 없으므로, 개발과 디버깅을 위해 수동 스위치를 함께 다는 것이 관례다.

버튼은 워크플로우를 개별로 선택한 화면에만 나타난다. 전체 목록(All workflows) 화면에는 없다.

### 1-7. 실행 로그 읽기

첫 성공 실행의 로그는 세 덩어리였다.

```
✓ Set up job          (자동)
✓ Say hello           ← yml에 적은 것
    Run echo "Hello from Actions, $(date)"
    Hello from Actions, Wed Aug 12 02:52:37 UTC 2026
✓ Complete job        (자동)
    Cleaning up orphan processes
```

- yml에는 단계 하나만 적었는데 3개가 실행됐다. 앞뒤 두 개는 GitHub이 자동으로 붙인다. 가상머신을 준비하고, 끝나면 정리하는 과정이다
- `Say hello`는 `name:`에 적은 문자열이 그대로 라벨이 된 것이다
- 펼치면 실제 실행된 명령과 그 출력이 함께 보인다
- `steps`는 위에서 아래로 순서대로 실행된다

### 1-8. 가상머신은 매번 새로 만들어지고 사라진다

`runs-on: ubuntu-latest`는 실행할 때마다 새 리눅스 가상머신을 빌린다는 뜻이다. `Complete job`의 `Cleaning up orphan processes`가 그 컴퓨터를 정리하는 과정이고, 그 줄이 끝나면 컴퓨터는 사라진다.

그래서 `echo`로 찍은 내용은 로그로만 남고 데이터로는 남지 않는다. 로그는 사람이 보는 기록이지 다시 쓸 수 있는 데이터가 아니다.

**결과를 남기려면 가상머신이 사라지기 전에 리포로 커밋해야 한다.** 이것이 수집기가 매일 `data/`와 SQLite 파일을 커밋하는 이유다. 덤으로 이 커밋이 저장소 활동으로 잡히기 때문에, 60일간 활동이 없으면 예약 워크플로우가 자동 정지되는 문제도 같이 해결된다.

## 2. 추가로 알면 좋은 활용법

### 2-1. 개발 중에는 수동 실행으로 확인한다

`push` 트리거를 넣으면 푸시할 때마다 실행되어 편하지만, 수집기처럼 외부 API를 호출하는 워크플로우에서는 낭비이고 소음이 된다. `workflow_dispatch`로 필요할 때만 돌리는 편이 낫다.

### 2-2. GitHub cron의 현실

- 최소 간격은 5분이다. 1분마다는 안 된다
- 정확한 시각을 보장하지 않는다. 특히 매시 정각은 요청이 몰려 수십 분씩 밀리기도 한다
- 그래서 실무에서는 일부러 어정쩡한 분을 쓴다. `0 0 * * *` 대신 `17 0 * * *`(한국 9시 17분)처럼 두는 편이 밀림을 줄인다

### 2-3. 가상머신에는 우리 리포가 없다

빈 우분투 컴퓨터를 빌리는 것이므로 저장소 파일이 하나도 없는 상태에서 시작한다. 리포의 코드를 쓰려면 먼저 내려받는 단계(`actions/checkout`)를 밟아야 한다.

## 3. 더 나아가 알면 좋은 것

### 3-1. 다음에 볼 키워드

- `actions/checkout` — 가상머신으로 저장소를 내려받는 액션
- 워크플로우 안에서 커밋하고 푸시하는 방법
- 아티팩트(artifact) — 커밋하지 않고 결과물을 남기는 다른 방법. 커밋과 무엇이 다른지
- 실패 알림 강화 — 수집 결과가 0건인 상태가 며칠 이어질 때 알아채는 방법
- `concurrency` — 실행이 겹칠 때 처리하는 설정

# 수집기 로드맵 - 장기 구상

> 상위: [[수집기 프로젝트 MOC]]

MOC의 「로드맵」이 **확정한 가까운 단계**라면, 이 노트는 그 **너머의 구상**이다. 아직 확정 아님 — 방향과 순서를 적어두는 자리다. `(미정)` 표시는 될지 자체가 불확실한 것.

## 구상과 확정의 경계 — 승격 규칙

로드맵이 두 곳에 있는 이유는 **확정도가 다르기 때문**이다. 둘을 섞지 않는다.

| 자리 | 성격 | 다루는 법 |
| --- | --- | --- |
| MOC 「로드맵」 표 | **현재 진실.** 확정한 단계 | 여기 있는 것만 "하기로 정한 것"이다 |
| 이 노트 | **구상.** 아직 확정 아닌 방향과 순서 | 논의는 여기서. 확정 전까지 MOC 표를 건드리지 않는다 |

**승격 절차** — 구상이 확정되면 이 순서로 MOC로 옮긴다.

1. 이 노트에서 합의한다 (착수하기로 정한 시점)
2. MOC 「로드맵」 표에 단계 행을 추가한다 (상태: `다음`/`예정`)
3. MOC 「로드맵 변경이력」에 **무엇을 / 왜** 한 줄 남긴다
4. 이 노트의 해당 항목은 **지우지 않고** `(승격됨)`으로 표시해 남긴다 — 왜 그 순서였는지가 나중에 근거가 된다

- **역방향은 없다.** MOC 표에 올라간 것을 이 노트로 내리지 않는다. 확정을 무르는 것도 결정이므로 변경이력에 남긴다
- 승격 전까지는 이 노트의 표가 아무리 자세해도 **계획이 아니라 초안**이다

## 이 노트로 세션 여는 법

이 노트는 **수집기 로드맵·전략·회고**를 다루는 세션의 집이다. 새 세션을 열면 "이 노트 읽고 안내대로 진행해"만 하면 된다.

- **역할**: 방향·순서·회고만. **코드는 짜지 않는다** — 빌드는 수집기 프로젝트 세션이 한다.
- **먼저 읽을 것**: 이 노트 전체 + [[수집기 프로젝트 MOC]]의 「로드맵」 섹션(확정한 가까운 단계). 이 둘이 로드맵의 현재 진실이다.
- **순서를 가르는 두 원칙**: ① 수집은 일찍, 분석은 나중(수집 안 한 데이터는 영원히 못 얻음) ② 되돌릴 수 있으면 겪은 뒤에 정한다 → [[개념 - 되돌릴 수 있는 결정과 없는 결정]].
- **결정이 바뀌면**: MOC의 「로드맵 변경이력」에 "무엇을 / 왜"를 한 줄 남긴다 — 무엇을 *했나*가 아니라 무엇을 하기로 *정했나*.
- **노트 수정은 요청할 때만.** 평소엔 텍스트로 논의한다.
- **경계**: 코드·수집기 NN·변경이력·트러블슈팅 = 수집기 프로젝트 세션 / Vault 규칙(CLAUDE.md 등) = 마스터 세션 / 로드맵만 = 여기.

## 북극성은 그대로, 다만 확장을 전제한다

수집 → 분석 → 면접 재료. 여기까진 동일. 추가된 전제 하나: **이 파이프라인을 채용에만 두지 않고 "범용 수집기"로 넓힌다.** 채용은 첫 세로줄이고, 같은 골격에 논문·뉴스를 붙인다. 그래서 지금 채용용으로 짠 어댑터 패턴·격벽·2단계 수집이 곧 재사용 골격이 된다.

## 이 프로젝트를 하는 이유 (순서 판단의 배경)

산출물만이 목적이 아니다. **자동화 + 배포·운영 경험**이 나란한 목적이다. 그래서 성공의 모양이 보통과 다르다.

> **"3개월 동안 문제 없이 돌아갔다"보다 "3개월 동안 이런 문제들이 있었고 이렇게 고쳤다"가 더 값지다.**

무인 시스템은 조용할 때 아무것도 알려주지 않는다. 12일의 공백(「수집기 22」)이 그 증거다 — 초록불 뒤에서 반쪽이 죽어 있었다. 운영 경험은 **문제를 겪고 고친 기록**으로만 쌓인다.

**단, 겪으러 가는 것과 일으키는 것은 다르다.**

| | |
| --- | --- |
| ✗ | 문제를 소재로 삼으려고 일부러 과하게 긁는다 |
| ○ | **예의 있는 크롤링으로 살살 긁되**, 그래도 생기는 조용한 실패를 관측하고 대응을 배운다 |

딜레이·빈도·조기 종료는 「수집기 16」에서 정한 대로 지킨다. 관측 대상은 *예의를 지켜도 생기는 것들*이다 — 간헐적 차단, 조용한 빈 응답, 여러 크롤러가 겹칠 때의 TIMEOUT.

## 순서를 가르는 원칙 두 개

1. **수집은 일찍, 분석은 나중에.** 「수집 안 한 데이터는 영원히 못 얻는다」. 그래서 논문·뉴스도 *분석 준비가 안 됐어도 크롤링만은 먼저* 켠다. 분석·산출은 데이터가 쌓인 뒤 언제든 소급해서 할 수 있다.
2. **되돌릴 수 있으면 겪은 뒤에.** Action 세분화·TIMEOUT 대응은 미리 짜지 않고 *실제로 겪은 뒤* 정한다 → [[개념 - 되돌릴 수 있는 결정과 없는 결정]].

## 확정한 순서

네가 준 화살표 흐름에, 위 원칙 두 개를 얹어 정리한 것. "범용 수집기 이후 4·5단계" 감각은 그대로 지켰고, 대신 논문·뉴스 *수집*은 앞당겼다(분석은 뒤에 둬도 데이터는 잃지 않도록).

| # | 단계 | 전제조건 | 목적 |
| --- | --- | --- | --- |
| 0 | 현재 기반으로 며칠 축적 | — (진행 중) | 데이터가 어느 정도 쌓일 것. **종료 조건은 사람이 판단한다** (기계 기준 없음 — 쌓인 걸 보고 "이제 시작"이라고 정한다) |
| 1 | **잡코리아 크롤러 추가** | ① 0의 종료를 사람이 판단 ② **약관·robots 재조사 통과** | **주목적: 채용 데이터 극대화.** 더불어 다중 크롤러가 겹치며 생기는 조용한 실패·TIMEOUT을 관측한다 → 4번의 근거가 된다 |
| 2 | **범용 수집기로 전환** | — | 소스 종류(채용/논문/뉴스)를 나란히 꽂는 골격으로 리팩토링. 여기서 논문(예: FastEQA 관련)·AI 뉴스 크롤러를 붙여 **수집만 먼저** 시작 (원칙 1) |
| 3 | **4단계 · 시간 변화 관측** | 데이터 축적 | 채용부터. 월별/전체 비교. `stats.py` 확장. 값이 싸서 2와 병행 가능 |
| 4 | **Action 세분화** | **TIMEOUT을 실제로 겪은 뒤** (원칙 2) | 한 번에 전부 돌리지 않고 **사이트별로 시간대를 분리**한다. 채용/논문/뉴스 잡 분리도 같은 축. 방향만 적어둔 것이고 형태는 겪은 뒤 정한다 |
| 5 | **5단계 · 면접 재료 RAG** | 채용 데이터·우대사항 축적 | 채용 세로줄을 끝까지 완성. 북극성의 마지막 조각 |
| 6 | **웹 반환 계층** | 5까지 | 아래 6-a~6-d 순서. **채용공고가 민감하면 웹 노출에서 제외** |
| 7 | (옵션) 노션 미러링 | 필요 시 | 아무 단계에서나 |

### 6단계 웹 반환 — 안쪽 순서

| # | 내용 | 비고 |
| --- | --- | --- |
| 6-a | 통계 시각화 + **검색(RAG 아님, 키워드 매칭)**으로 일치 공고 보여주기 | 가장 먼저. RAG 없이 가능 |
| 6-b | RAG 기반 데이터 분석 | 검색 위에 얹는다 |
| 6-c | **LLM 산출물** | 아래 세 갈래 |
| 6-d | 웹에서 크롤 주소 추가 | `(미정)` — 될지 불확실 |

**6-c LLM 산출물 세 갈래**

- **채용** — 이력서를 넣으면 조건에 맞는 공고 제공 + 추가로 준비하면 좋은 것들
- **논문** — 논문·문제상황을 적으면 저장된 논문 중 유사한 것 제공
- **뉴스** — 매일 저녁/아침 메일로 화제성 AI 뉴스 발송 + 검색 시 유사 뉴스 제공 + 크롤링 뉴스를 요약본으로 웹에 띄우기(내가 보기 편하게)

### 1번의 전제조건이 둘인 이유

잡코리아는 기업용 API 신청이 거절돼 **크롤링 경로**다(→ MOC 「로드맵 변경이력」 2026-08-13~18). 그런데 크롤링의 법적 판단은 [[개념 - 되돌릴 수 있는 결정과 없는 결정]]에서 *먼저 확정* 칸에 있는 항목이다 — 겪고 나서 고칠 수 없는 종류다. 그래서 "데이터가 쌓였으니 시작"만으로는 부족하고, **약관·robots 재조사를 통과해야 착수**한다. 조사 방법은 「수집기 10」·「수집기 15」에 있는 세 층(robots·약관·용도) 그대로.

### 논문·뉴스 수집이 2번에 묶여 있는 것에 대해

원칙 1(수집은 일찍)을 엄격히 적용하면 논문·뉴스 수집도 지금 켜는 게 맞다. 안 받은 데이터는 못 되돌리니까. **그걸 알면서도 2번에 둔다.**

- 이유: **우선순위가 채용공고에 있다.** 논문·뉴스는 방향으로는 확정이지만 당장 급하지 않다
- 즉 이건 원칙을 몰라서가 아니라 **알고 감수하는 것**이다. 손해의 크기(그동안 놓치는 논문·뉴스)를 우선순위와 맞바꿨다
- 나중에 "왜 원칙을 어겼지?"가 나오면 답은 이 줄이다. 우선순위가 바뀌면 이 판단도 바뀐다

## 왜 이 순서인가 (한 가지 짚어둘 점)

4단계(시간 변화)는 `stats.py`에 씨앗이 있어 **값이 싸고**, 이미 쌓이는 채용 데이터에 바로 값을 준다. 그래서 원칙대로면 2와 병행하거나 살짝 앞당겨도 좋다. 다만 네 "범용 이후" 감각을 존중해 **2 다음(3번)**에 뒀다 — 순서를 바꾸고 싶으면 3을 1~2 사이로 올리면 된다. 이건 되돌릴 수 있는 결정이라 지금 확정 안 해도 된다.

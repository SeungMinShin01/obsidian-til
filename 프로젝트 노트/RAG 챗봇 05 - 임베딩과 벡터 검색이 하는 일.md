# RAG 챗봇 05 - 임베딩과 벡터 검색이 하는 일

> 허브: [[RAG 챗봇 프로젝트 MOC]]

**물어본 것:** 검색과 임베딩이 쉽게 말해 무엇을 하는 것인가.

## 1. 배운 내용

### 1-1. 임베딩 — 문장을 좌표로 바꾼다

문장 하나를 넣으면 숫자 배열이 나온다. 이 프로젝트에서 쓰는 모델은 숫자 1536개를 돌려준다.

```
"동작 전압은 2.3V에서 5.5V입니다"  →  [0.021, -0.113, 0.078, ... ]
```

핵심은 이 숫자들이 **의미에 따라 정해진다**는 것이다. 뜻이 비슷한 문장은 비슷한 숫자가 나온다. 1536차원 공간에 문장을 점으로 찍는 것이라고 보면 되고, 비슷한 뜻이면 가까운 자리에 찍힌다.

```
"동작 전압 범위"   ●
"공급 전압 사양"   ●   ← 표현이 달라도 가깝다
"I2C 통신 속도"              ●   ← 멀다
```

### 1-2. 왜 단어 검색으로는 안 되는가

"동작 전압"이라고 물었을 때 `Supply Voltage`라고 적힌 페이지는 **글자가 하나도 겹치지 않아** 단어 검색으로는 걸리지 않는다. 임베딩은 뜻을 좌표로 옮겨두기 때문에 이런 것이 잡힌다.

인제스천 때 청크 수백 개를 전부 이렇게 점으로 찍어 벡터 DB에 저장해둔다.

### 1-3. 검색 — 가장 가까운 점을 찾는다

질문이 들어오면 **질문도 같은 방식으로 점으로 바꾼다.** 그다음 저장된 점들 중 가까운 것 몇 개를 고른다.

```python
query_vector = _get_embedder().embed_query(question)
result = collection.query(query_embeddings=[query_vector], n_results=5)
```

가까운 정도를 재는 숫자가 `distance`이고, 0에 가까울수록 비슷하다는 뜻이다. 코사인 거리를 쓰도록 컬렉션을 만들어둔다.

### 1-4. 질문도 문서와 같은 모델로 임베딩해야 한다

모델이 다르면 좌표계 자체가 달라서, 같은 뜻이어도 엉뚱한 자리에 찍힌다. 서울 지도와 부산 지도에서 거리를 재는 꼴이 된다. 검색 코드에 이 주의가 주석으로 붙어 있다.

### 1-5. 벡터 DB가 대신해주는 것

저장된 점이 수백·수천 개가 되면 전부와 거리를 재는 것이 느려진다. 벡터 DB는 **가까운 점을 빨리 찾는 색인**을 대신 관리한다. 여기서는 서버나 컨테이너 없이 파일로 동작하는 임베디드 모드를 쓴다.

### 1-6. 전체를 한 줄로

```
임베딩   = 문장을 좌표로
벡터 DB = 좌표를 저장해두고 가까운 것을 빨리 찾아주는 창고
검색     = 질문도 좌표로 바꿔 가까운 청크를 꺼내오는 것
답변 생성 = 꺼내온 청크만 읽고 한국어로 답을 쓰는 것
```

답변 생성 모델은 **데이터시트 전체를 본 적이 없다.** 검색이 골라준 몇 조각만 보고 답한다. 그래서 검색이 엉뚱한 것을 집어오면 답변도 반드시 틀린다.

## 2. 추가로 알면 좋은 활용법

### 2-1. 거리 상한으로 관련 없는 것을 버린다

검색 결과에는 거리 상한이 걸려 있다. 이보다 먼 청크는 버리고, 전부 버려져 결과가 비면 답변 생성 모델을 아예 부르지 않는다. 관련 없는 근거로 답을 지어내는 것을 막고 호출 비용도 아끼는 자리다.

### 2-2. 검색만 따로 확인할 수 있다

답변이 이상할 때 원인이 검색인지 프롬프트인지 가르려면 검색 결과를 먼저 본다. 거리가 작으면 검색은 제 일을 한 것이고, 크면 검색이 원인이다.

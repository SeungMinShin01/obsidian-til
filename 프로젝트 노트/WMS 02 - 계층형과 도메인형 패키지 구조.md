# WMS - 계층형과 도메인형 패키지 구조

> 허브: [[WMS 프로젝트 MOC]]

## 1. 배운 내용

### 1-1. 두 가지 방식

Spring Boot 프로젝트의 최상위 패키지를 나누는 방식은 크게 둘이다.

**계층형** — 계층을 대표하는 폴더로 나눈다.

```
com.wmslab/
├─ controller/
├─ service/
├─ repository/
├─ domain/
└─ dto/
```

**도메인형** — 업무 도메인으로 나누고, 각 도메인 안에 계층을 둔다.

```
com.wmslab/
├─ master/      (품목·창고·위치)
├─ inventory/   (재고)
├─ inbound/     (입고)
└─ outbound/    (출고)
```

### 1-2. 각자의 근거

| | 계층형 | 도메인형 |
| --- | --- | --- |
| 장점 | 프로젝트를 처음 보는 사람이 구조를 빨리 파악한다. 폴더 이름만 봐도 어디에 뭐가 있는지 안다 | 관련 코드가 한군데 모여 응집도가 높다. 도메인 간 의존을 끊기 좋다 |
| 단점 | 클래스가 쌓이면 한 폴더에 파일이 수십 개씩 모인다 | 도메인을 모르는 사람이 전체 구조를 파악하기 어렵다 |

### 1-3. 국내 상황 — 둘 다 현역이다

처음에는 "요즘은 도메인형"이라는 말만 듣고 도메인형이 정답인 줄 알았는데, 찾아보니 그렇게 단순하지 않았다.

- **계층형은 여전히 널리 쓰인다.** SI·전통 기업의 레거시 코드베이스, 그리고 부트캠프·강의 자료 대부분이 계층형이다
- **도메인형은 최근 신규 프로젝트에서 늘고 있다.** 테크 기업 쪽 블로그의 결론은 대체로 도메인형으로 기울어 있다

"계층형은 옛날 방식"이 아니라 **둘 다 현역이고 신규 프로젝트에서 도메인형 비중이 늘어나는 중**이라고 보는 게 정확하다.

### 1-4. 계층형으로 정한 이유

- 도메인이 네 덩어리(기준정보·입고·재고·출고)뿐이라 한 폴더에 파일이 감당 못 할 만큼 쌓이지 않는다
- 구조를 고민하는 시간을 재고 이력 설계에 쓰는 편이 이 프로젝트에서 남는다
- 아직 익숙하지 않은 방식이라, 먼저 계층형으로 손에 익히는 것이 순서라고 봤다

### 1-5. 버린 쪽(도메인형)의 근거 — 이게 약한 게 아니었다

도메인형에는 이 프로젝트에 딱 맞는 장점이 하나 있었다.

3주차에 "출고 조회를 최적화했다"고 주장할 때, 도메인형이면 **변경이 `outbound/` 한 폴더에 모여 diff가 깔끔하다.** 계층형이면 같은 작업이 controller·service·repository 세 폴더에 흩어져서 무엇을 바꿨는지 설명이 길어진다.

다만 도메인 5개짜리 프로젝트에서는 결정적일 만큼 큰 차이가 아니라고 판단했다. 어느 쪽이든 프로젝트는 굴러간다.

### 1-6. 중간에 바꾸지 않는다 — 이게 진짜 규칙이다

2주차쯤 "역시 도메인형이 나은가" 하고 갈아엎으면, **그 리팩터링 커밋이 성능 개선 커밋과 뒤섞인다.**

3주차에 diff로 "이 인덱스 하나 추가해서 2400ms → 35ms"를 보여주려 할 때 변경 내역이 오염돼서 주장의 근거가 사라진다. 구조 선택보다 이 규칙이 훨씬 중요하다.

## 2. 추가로 알면 좋은 활용법

### 2-1. 계층형에서 dto가 제일 먼저 터진다

계층형에서 파일이 가장 빨리 쌓이는 곳은 `dto/`다. 입고·출고·재고의 요청과 응답을 다 합치면 20개가 넘고, 그때부터 파일 찾기가 괴로워진다.

그래서 `dto/` 안에만 도메인별 하위 폴더를 두기로 했다. 계층형 프로젝트에서도 흔히 하는 절충이다.

```
dto/
├─ inbound/
├─ outbound/
└─ inventory/
```

### 2-2. 클래스 이름이 도메인을 대신 알려준다

계층형은 폴더가 도메인 정보를 주지 않으므로, 이름이 그 역할을 해야 한다.

`InboundController`, `OutboundController`, `InventoryController` 처럼 도메인을 앞에 붙이면 알파벳순 정렬에서 같은 도메인끼리 붙어 보인다.

### 2-3. 구조와 무관하게 지킬 규칙

재고를 건드리는 경로는 입고·출고·이동·조정 넷이다. 각자가 자기 방식으로 재고를 수정하기 시작하면 정합성이 깨진다.

**재고 변경은 `InventoryService` 한 문으로만 통과시킨다.** 계층형이면 `service/InventoryService`에 있을 뿐, 락을 한 곳에 모아야 한다는 점은 도메인형과 똑같다. 락이 여러 군데 흩어지면 데드락이 나고 원인 추적이 안 된다.

## 3. 더 나아가 알면 좋은 것

### 3-1. 다음에 볼 키워드

- 패키지 접근제어자(package-private) — 도메인형에서 도메인 간 침범을 컴파일 단계에서 막는 방법
- 헥사고날 아키텍처 / 클린 아키텍처 — 도메인형을 더 밀고 나간 형태
- ArchUnit — 패키지 의존 규칙을 테스트로 강제하는 라이브러리

### 3-2. 나중에 재검토할 조건

`service/` 안의 파일이 20개를 넘어가면 도메인형을 다시 고려한다. 다만 이 프로젝트 진행 중에는 바꾸지 않는다 (1-6).

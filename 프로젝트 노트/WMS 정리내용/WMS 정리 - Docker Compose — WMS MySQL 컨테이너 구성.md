## docker-compose.yml

services 아래 항목 = 컨테이너 한 종류

그 밑에 어떤 이미지로 만들지, 어떤 설정으로 띄울지를 전부 적는다. 이미지 = 컨테이너를 찍어내는 틀. 실행에 필요한 것이 전부 담긴 읽기 전용 패키지. 클래스와 인스턴스의 관계와 같다.

> **보충** — 엄밀히 말하면 services 아래 항목 하나는 "컨테이너"가 아니라 **서비스**다. 서비스는 "이 이미지로 이 설정의 컨테이너를 띄운다"는 선언이고, 실제 컨테이너는 그 선언으로 찍어낸 실행 단위다. 보통은 1:1이지만 `docker compose up --scale web=3` 처럼 하나의 서비스에서 컨테이너 여러 개를 띄울 수 있다. 뒤에 나오는 라운드 로빈 이야기가 성립하는 것도 이 때문이다 — 이름 하나(`web`)에 컨테이너 여러 개가 매달릴 수 있어야 분배할 대상이 생긴다.

## TZ : 타임존(시간대)

컨테이너의 기본 시간대는 UTC. 그냥 두면 DB의 NOW()는 한국 시간보다 9시간 전을 가리킨다.

> **보충** — `TZ` 환경변수는 컨테이너 **OS의** 시간대를 바꾸는 것이지 MySQL 서버의 시간대를 직접 바꾸는 것이 아니다. MySQL의 `time_zone` 시스템 변수는 기본값이 `SYSTEM`이라서 OS 시간대를 따라가고, 그래서 결과적으로 `TZ`를 주면 `NOW()`도 같이 움직인다. 확실하게 못 박고 싶으면 command에 `--default-time-zone=+09:00`을 같이 넘기면 된다.
>
> 한 가지 더 — WMS의 입출고 이력처럼 시각이 중요한 데이터는 컬럼 타입도 같이 봐야 한다. `DATETIME`은 넣은 값을 그대로 저장해서 시간대가 바뀌어도 값이 안 변하고, `TIMESTAMP`는 저장할 때 UTC로 바꿔 넣었다가 읽을 때 세션 시간대로 되돌린다. 즉 `TIMESTAMP`를 쓰고 있었다면 나중에 `TZ`를 바꾸는 순간 이미 저장된 이력의 표시 값이 통째로 달라진다.

## command

MYSQL을 직접 설치하면 my.ini 라는 설정파일에 적는다. 그걸 열어서 `innodb_buffer_pool_size=512M` 같은 줄을 넣는 것이다. 컨테이너 안의 파일을 직접 편집하기 어려우니, 서버를 시작할 때 옵션으로 넘기는 방식을 쓴다.

> **보충** — 설정파일 이름은 OS마다 다르다. Windows는 `my.ini`, Linux/macOS는 `my.cnf`다. MySQL 공식 이미지는 리눅스 기반이므로 컨테이너 안에서는 `/etc/mysql/my.cnf`가 된다.
>
> command로 넘기는 것 말고 세 번째 방법도 있다. 호스트의 설정 파일을 `./my.cnf:/etc/mysql/conf.d/my.cnf` 로 마운트하는 것이다. 옵션이 열 개를 넘어가면 이 쪽이 읽기 편하다. command 방식은 옵션이 몇 개 안 될 때 compose 파일 하나만 보면 된다는 게 장점이다.
>
> 또 하나 알아둘 것 — `command`를 쓰면 이미지에 정의된 `CMD`를 **덮어쓴다**. MySQL 공식 이미지의 원래 CMD가 `mysqld`이기 때문에, command에 옵션만 나열해도(`--character-set-server=...`) 동작하는 건 entrypoint 스크립트가 "인자가 `-`로 시작하면 mysqld의 옵션으로 붙여준다"고 처리해 주기 때문이다.

### 1. 문자셋 두줄

```
--character-set-server=utf8mb4
--collation-server=utf8mb4_unicode_ci
```

> **교정** — 원문의 `--collaction-server`는 오타다. 올바른 옵션명은 `--collation-server`이며, 존재하지 않는 옵션을 넘기면 mysqld가 `unknown variable` 에러를 내고 컨테이너가 그대로 죽는다.

MYSQL에서 utf8은 3바이트짜리. utf8mb4 가 진짜 UTF-8

> **보충** — MySQL의 `utf8`은 `utf8mb3`의 별칭이고 최대 3바이트까지만 저장한다. 그런데 이모지(😀)나 일부 한자는 UTF-8에서 4바이트를 쓰기 때문에, `utf8`로 만든 컬럼에 이모지를 넣으면 `Incorrect string value` 에러가 난다. WMS라면 상품명이나 비고란에 이모지가 들어올 수 있으니 무시할 문제가 아니다.
>
> MySQL 8.0부터는 서버 기본 문자셋이 이미 `utf8mb4`, 기본 콜레이션은 `utf8mb4_0900_ai_ci`라서 이 두 줄이 없어도 대부분 동작한다. 그래도 명시적으로 적어두는 이유는 (1) 나중에 이미지 버전을 바꿔도 동작이 안 변하고 (2) 설정을 읽는 사람이 의도를 알 수 있기 때문이다.
>
> 콜레이션은 "정렬·비교 규칙"이다. `utf8mb4_unicode_ci`의 `ci`는 case-insensitive라서 `'ABC' = 'abc'`가 참이 된다. MySQL 8.0 기본값인 `utf8mb4_0900_ai_ci`가 더 최신 유니코드 규칙을 따르고 속도도 빠르지만, `unicode_ci`는 5.7 시절부터 쓰이던 값이라 기존 DB와 맞출 때 자주 쓴다. 중요한 건 **서버·DB·테이블·연결의 콜레이션이 서로 달라지지 않는 것**이다. 다르면 조인할 때 `Illegal mix of collations` 에러가 난다.

### 2. 버퍼 풀

```
--innodb-buffer-pool-size=536870912
```

> **교정** — 원문의 `--innodb-bufer-pool-size`는 `buffer`의 오타이고, 값 `546870912`도 잘못됐다. 512MB는 512 × 1024 × 1024 = **536870912**다. 참고로 옵션값에는 `512M`처럼 단위 접미사를 그대로 쓸 수 있어서 `--innodb-buffer-pool-size=512M`이 오타를 덜 낸다.

**Buffer Pool 이란?**

데이터와 인덱스를 캐시하기 위해 사용하는 메모리 버퍼크기. MYSQL 성능 튜닝의 중요한 요소

- 인덱스 설계가 잘 되어 있음에도 슬로우 쿼리가 해결되지 않는다면 innodb_buffer_pool_size를 확인해볼 필요가 있음
- 자주 사용하는 데이터를 메모리에서 직접 처리할 수 있게 하여 처리 속도를 높임
- 대량 읽기 조작의 효율성을 위해 Buffer Pool은 여러 행을 보유할 수 있는 Page로 분할됨
- 캐시 관리 효율성을 위해 Linked Page List로 구현됨
- Paging을 위해 LRU 알고리즘 사용

**Buffer Pool 크기 설정: innodb_buffer_pool_size**

- 전용 서버의 경우 전체 RAM의 70% 이상, 그 외는 10% 이상으로 지정

**Buffer Pool의 역할**

1. 데이터 파일과 로그 파일이 기록되는 순서를 조정하는 역할
2. 디스크 엑세스를 줄이기 위한 캐시의 역할

- Database에서도 Buffer Pool의 크기가 클수록 성능에 유리하다.
- 읽으려는 데이터가 메모리에 올라와있으므로 Disk I/O를 발생시키지 않음. 특히 조회 처리에 효과적
- 이론적으로는 다른 버퍼에 할당하는 메모리를 제외하고는 대부분의 메모리를 Buffer Pool에 할당하는 것이 좋다.

Buffer Pool 크기는 항상 `innodb_buffer_pool_chunk_size` × `innodb_buffer_pool_instances`의 배수와 같아야함. 다른 값으로 구성 시 Buffer Pool의 크기는 `innodb_buffer_pool_chunk_size` × `innodb_buffer_pool_instances`의 배수 또는 그 외 여러 값으로 자동 조정됨

출처 – https://velog.io/@inhwa1025/MySQL-Buffer-Pool

> **보충** — 위 목록의 "1. 데이터 파일과 로그 파일이 기록되는 순서를 조정하는 역할"은 Buffer Pool 단독의 기능이라기보다 **WAL(Write-Ahead Logging)** 규칙을 설명한 것이다. InnoDB는 데이터를 바꿀 때 디스크의 데이터 파일을 즉시 고치지 않고, Buffer Pool 안의 페이지만 고쳐 놓는다(이걸 dirty page라고 한다). 대신 "무엇을 바꿨는지"를 redo 로그에 먼저 기록한다. 그리고 **dirty page를 디스크에 내려쓰기 전에 그에 해당하는 redo 로그가 반드시 먼저 디스크에 있어야 한다**는 순서 규칙을 지킨다. 그래야 중간에 서버가 죽어도 redo 로그를 재생해서 복구할 수 있다. 즉 순서를 조정하는 주체는 Buffer Pool 자체가 아니라 이 WAL 프로토콜이고, Buffer Pool은 그 대상이 되는 dirty page를 담고 있는 곳이다.
>
> **왜 크기가 성능을 좌우하는가** — 디스크에서 한 페이지를 읽는 비용은 메모리에서 읽는 것보다 수백~수만 배 비싸다. Buffer Pool이 충분히 크면 자주 쓰는 테이블과 인덱스가 통째로 메모리에 상주해서 디스크를 아예 안 건드린다. 반대로 작으면 LRU에 밀려 계속 쫓겨났다가(eviction) 다시 읽어오는 일이 반복된다. 이걸 캐시 스래싱이라고 한다.
>
> **잘 맞는지 확인하는 법** — `SHOW ENGINE INNODB STATUS`의 BUFFER POOL AND MEMORY 절이나 `SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%'`를 본다. 여기서 히트율을 계산할 수 있다.
> ```
> 히트율 = (1 - Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests) × 100
> ```
> `read_requests`는 페이지를 요청한 총 횟수, `reads`는 그중 Buffer Pool에 없어서 **디스크까지 갔던** 횟수다. 이 값이 99% 아래로 계속 떨어지면 Buffer Pool이 부족하다는 신호다. WMS의 Before/After 성능 측정에서 이 수치를 같이 찍어두면 "인덱스를 걸어서 빨라진 것"과 "캐시가 데워져서 빨라진 것"을 구분할 수 있다.
>
> **주의** — 성능 측정할 때 같은 쿼리를 두 번 돌리면 두 번째가 훨씬 빠르다. 첫 실행이 디스크에서 페이지를 읽어 Buffer Pool에 올려놨기 때문이다. 이걸 모르고 측정하면 최적화 효과를 실제보다 크게 착각하게 된다. 그래서 보통 워밍업 실행을 몇 번 버리고 나서 측정한다.
>
> **RAM의 70%가 맞는가** — MySQL 공식 문서는 전용 서버 기준 최대 80%까지를 이야기하는데, 도커 환경에서는 이 기준을 그대로 쓰면 안 된다. 컨테이너는 호스트 RAM 전체가 아니라 도커가 할당한 메모리 한도 안에서 돈다. Buffer Pool을 그 한도에 가깝게 잡으면 OS가 컨테이너를 OOM Kill 해버린다(컨테이너가 조용히 죽고 로그에 이유가 안 남아서 원인 찾기가 아주 어렵다). 개발용 노트북이라면 512MB~1GB 정도가 안전하고, 컨테이너에 `mem_limit`를 걸었다면 그 값의 절반 이하부터 시작하는 게 좋다.

`--innodb-buffer-pool-size=536870912`

MYSQL이 데이터와 인덱스를 메모리에 올려두는 공간이다. 여기 있으면 디스크를 안 읽으니 훨씬 빠르다. 기본값이 128MB인데, 이력 100만건을 다루려면 이 크기가 성능을 좌우한다.

### 3. 슬로우 쿼리 로그

```
--slow-query-log=1
--long-query-time=1
```

1초를 넘긴 쿼리를 파일에 기록한다.

> **보충 (원문의 "*슬로우 쿼리가 뭔지 궁금함"에 대한 답)** — 슬로우 쿼리는 특별한 종류의 쿼리가 아니라, **실행 시간이 내가 정한 기준(`long_query_time`)을 넘긴 쿼리 전부**를 가리키는 말이다. 즉 "느린 쿼리"라는 뜻 그대로이고, 그 기준선을 내가 정하는 것이다. `--long-query-time=1`은 "1초 넘으면 느린 걸로 치고 기록해라"라는 뜻이다.
>
> 이게 필요한 이유는, 성능 문제는 대개 평균이 아니라 **소수의 나쁜 쿼리**에서 오기 때문이다. API 응답이 가끔 느리다는 신고가 들어왔을 때 코드를 처음부터 읽는 대신, 슬로우 쿼리 로그를 열면 범인이 바로 나온다. 로그에는 실행 시간, 잠금 대기 시간, 검사한 행 수(`Rows_examined`), 실제로 반환한 행 수(`Rows_sent`)가 같이 남는다. **`Rows_examined`가 `Rows_sent`보다 압도적으로 크면 인덱스를 안 타고 풀스캔했다는 뜻**이라 이것만 봐도 진단이 된다.
>
> 알아둘 점 몇 가지:
> - `long_query_time`은 소수점을 받는다. 개발 중에는 `0.1`이나 `0.5`로 낮춰서 잡아야 볼 게 나온다. 1초는 이미 사용자가 체감할 만큼 느린 수준이다.
> - 이 시간에는 **잠금 대기 시간이 포함되지 않는다**. 락 때문에 3초 기다린 쿼리는 순수 실행이 0.1초면 슬로우로 안 잡힐 수 있다. 대기 시간은 로그의 `Lock_time`에 따로 찍힌다. WMS의 재고 선점 락 구간을 볼 때 이 차이가 중요하다.
> - `--log-queries-not-using-indexes=1`을 같이 켜면 시간과 무관하게 인덱스를 못 탄 쿼리를 전부 잡아준다. 데이터가 적은 개발 단계에서는 빨라서 안 잡히던 풀스캔이 운영에서 터지는데, 이 옵션이 그걸 미리 잡아준다. 다만 로그가 폭발적으로 늘어날 수 있으니 개발 환경에서만 켠다.
> - 로그 파일은 컨테이너 안에 쌓이므로 컨테이너를 지우면 같이 사라진다. 남기려면 `--slow-query-log-file=/var/lib/mysql/slow.log` 처럼 볼륨이 걸린 경로로 지정하면 된다.
> - 로그가 쌓이면 `mysqldumpslow`나 `pt-query-digest`로 집계해서 "가장 자주 느린 쿼리 유형"을 뽑아볼 수 있다. 한 줄씩 읽는 것보다 이 쪽이 훨씬 빠르다.

## volumes — 경로가 아니라 이름입니다

```yaml
- wms-mysql-data:/var/lib/mysql
```

문법은 왼쪽:오른쪽이고, 오른쪽은 컨테이너 안의 경로입니다. `/var/lib/mysql`은 MySQL이 데이터 파일을 저장하는 표준 위치입니다.

왼쪽이 핵심입니다. 두 가지 형태가 있습니다.

| 왼쪽에 쓴 것 | 종류 | 실제 저장 위치 |
|---|---|---|
| `wms-mysql-data` (그냥 이름) | named volume | 도커가 알아서 관리 |
| `./data` 또는 `C:\...` (경로) | bind mount | 내가 지정한 폴더 |

왜 이 방식인가 — 두 가지 이유입니다.

이미지는 읽기 전용이라 컨테이너를 지우면 안의 데이터도 사라집니다. 볼륨에 담아두면 컨테이너를 지웠다 다시 만들어도 데이터가 남습니다.

> **교정** — "이미지가 읽기 전용이라서 데이터가 사라진다"는 인과가 정확하지 않다. 컨테이너는 읽기 전용 이미지 레이어 위에 **쓰기 가능 레이어(writable layer)**를 한 장 얹어서 돌아가고, 컨테이너 안에서 만든 파일은 전부 그 레이어에 쌓인다. 데이터가 사라지는 이유는 **컨테이너를 지울 때 이 쓰기 가능 레이어가 같이 삭제되기 때문**이다. 이미지가 읽기 전용인 것은 그 결과의 원인이 아니라 별개의 사실이다. 볼륨은 이 레이어 바깥에 따로 저장되기 때문에 컨테이너의 수명과 무관하게 살아남는다.

> **보충** — named volume을 쓰려면 서비스 안의 `volumes:` 말고 **파일 맨 아래 최상위 `volumes:`에도 이름을 선언**해야 한다.
> ```yaml
> services:
>   mysql:
>     volumes:
>       - wms-mysql-data:/var/lib/mysql
>
> volumes:
>   wms-mysql-data:
> ```
> 이걸 빼면 `service "mysql" refers to undefined volume` 에러가 난다.
>
> 그리고 `docker compose down`은 컨테이너와 네트워크만 지우고 named volume은 남긴다. 볼륨까지 지우려면 `docker compose down -v`를 써야 한다. 반대로 말하면, "DB를 초기 상태로 되돌리고 싶은데 `down` 후 `up`을 해도 예전 데이터가 그대로다"라는 상황은 볼륨이 살아 있어서 생긴다. MySQL 이미지의 초기화 스크립트(`/docker-entrypoint-initdb.d`)는 **데이터 디렉터리가 비어 있을 때만** 실행되기 때문에, 스키마 초기화 SQL을 고쳐놓고 재실행해도 반영이 안 되는 것도 같은 이유다.

Windows에서 바인드 마운트로 `C:\` 폴더를 물리면 파일을 읽고 쓸 때마다 WSL 경계를 넘어가서 디스크가 몇 배 느려집니다.

> **보충** — Docker Desktop for Windows는 실제로는 WSL2 안의 리눅스 VM에서 돈다. `C:\` 아래 폴더를 바인드 마운트하면 그 파일 접근이 전부 Windows 파일시스템 ↔ 리눅스 VM 사이의 변환 계층(9p 프로토콜 등)을 거친다. 소스 코드처럼 파일 몇 개를 가끔 읽는 정도면 참을 만하지만, **DB 데이터 디렉터리처럼 작은 랜덤 I/O가 초당 수천 번 일어나는 경우에는 체감상 몇 배에서 십수 배까지 느려진다**. named volume은 리눅스 VM 내부 파일시스템에 저장되므로 이 변환이 없다. 그래서 "코드는 바인드 마운트, DB 데이터는 named volume"이 Windows에서의 기본 조합이다.
>
> 반대로 named volume의 단점도 있다. 저장 위치가 도커 내부라서 파일 탐색기로 열어보기가 번거롭다. 내용을 봐야 한다면 `docker compose exec mysql ls /var/lib/mysql` 처럼 컨테이너를 통해 들어가야 한다.

## healthcheck — "떴다"와 "쓸 수 있다"는 다릅니다

```yaml
test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-uroot", "-pwmsroot"]
interval: 5s
timeout: 3s
retries: 20
```

- `test` — 컨테이너 **안에서** 주기적으로 실행할 명령입니다. `mysqladmin ping`은 MySQL 서버가 응답하는지 물어보는 명령이고, 뒤는 접속 정보입니다 (`-p` 뒤에 공백 없이 붙이는 건 MySQL 규칙입니다)
- `interval: 5s` — 5초마다 확인
- `timeout: 3s` — 3초 안에 대답이 없으면 이번 시도는 실패
- `retries: 20` — 20번 연속 실패해야 "고장났다(unhealthy)"고 판정

**왜 필요한가** — MySQL은 컨테이너가 시작되고도 **바로 접속을 받지 않습니다.** 첫 기동 때는 DB를 초기화하느라 10~30초가 걸립니다. 그 사이에 앱을 켜면 "접속 거부" 에러가 나는데, 원인이 DB 설정 문제인지 아직 안 뜬 것뿐인지 구분이 안 됩니다.

> **보충** — healthcheck를 정의하는 것만으로는 앱이 기다려주지 않는다. **기다리게 하려면 앱 쪽 서비스에 `depends_on`의 조건을 같이 걸어야 한다.**
> ```yaml
> services:
>   web:
>     depends_on:
>       mysql:
>         condition: service_healthy
> ```
> `depends_on: [mysql]` 처럼 짧게만 쓰면 도커는 "mysql 컨테이너를 먼저 **시작**"만 보장하고, 그 안의 MySQL이 접속을 받을 준비가 됐는지는 보지 않는다. 원문에서 지적한 문제가 정확히 이 지점이고, `condition: service_healthy`가 그걸 메워준다.
>
> **`retries` 대신 `start_period`** — `retries: 20`은 "실패를 20번까지 봐준다"는 뜻이라, 초기화가 오래 걸리는 동안 컨테이너 상태가 계속 `starting`으로 표시된다. 요즘은 `start_period: 30s`를 쓰는 편이 낫다. 이 기간 안의 실패는 재시도 횟수로 **세지 않기 때문에**, 초기화 유예 시간과 "진짜 고장났을 때의 판정 기준"을 분리해서 표현할 수 있다.
>
> **`mysqladmin ping`의 한계** — 이 명령은 서버 프로세스가 살아 있는지만 확인한다. 인증에 실패해도 서버가 응답만 하면 "alive"로 보고하는 경우가 있어서, "떴다"와 "쿼리를 실행할 수 있다"를 완전히 구분해 주지는 못한다. 더 확실하게 하려면 실제 쿼리를 날리는 편이 낫다.
> ```yaml
> test: ["CMD", "mysql", "-uroot", "-pwmsroot", "-e", "SELECT 1"]
> ```
>
> **`-h localhost` vs `-h 127.0.0.1`** — MySQL 클라이언트는 호스트가 `localhost`면 TCP가 아니라 **유닉스 소켓**으로 붙는다. 즉 `localhost`로 성공해도 3306 포트가 열려서 네트워크 접속을 받는 상태인지는 확인되지 않는다. 앱은 네트워크로 붙으므로, 검사하려는 경로와 앱이 쓸 경로를 맞추려면 `-h 127.0.0.1`이 더 정확하다.
>
> **비밀번호가 compose 파일에 그대로 노출되는 문제** — `-pwmsroot`처럼 평문으로 적으면 파일을 보는 사람 누구나 알게 되고, 컨테이너 안에서 `ps`를 쳐도 보인다. 로컬 개발용이면 넘어가도 되지만 배포 단계에서는 `.env` 파일이나 시크릿으로 빼야 한다. WMS를 3주차에 실제 배포한다면 이 부분을 미리 표시해 두는 게 좋다.

## 네트워크와 서비스 디스커버리

`docker compose up`을 하면 도커가 **이 프로젝트 전용 네트워크를 하나 자동으로 만듭니다.** 그 안에 컨테이너들이 들어갑니다.

```
[ wms-web_default 네트워크 ]
  ├─ mysql  컨테이너  (172.18.0.2)
  └─ web    컨테이너  (172.18.0.3)
```

네트워크 이름은 보통 `<폴더이름>_default` 입니다. 폴더를 `wms-web`으로 바꾸면 `wms-web_default`가 됩니다.

컨테이너 IP는 재시작할 때마다 바뀐다. 코드에 IP를 박아두면 그때마다 고쳐야 한다. -> 그래서 도커가 네트워크 안에 자체 DNS를 돌린다. 컨테이너가 mysql이라는 이름을 물어보면 도커가 현재 IP를 응답한다.

이걸 서비스 디스커버리 라고 한다.

> **보충** — 도커 DNS 서버는 컨테이너 안에서 `127.0.0.11`에 떠 있다. 컨테이너의 `/etc/resolv.conf`를 열어보면 이 주소가 nameserver로 박혀 있는 걸 볼 수 있다. 이름을 못 찾으면 여기서 외부 DNS로 넘긴다.
>
> **이름을 여러 개 붙일 수 있다.** 기본으로는 서비스 이름(`mysql`)으로 찾을 수 있고, `container_name`을 지정했으면 그 이름으로도, `networks.<net>.aliases`에 적으면 추가 별명으로도 찾을 수 있다. 기존에 `db`라는 이름으로 접속하도록 짜인 코드가 있다면 서비스 이름을 바꾸는 대신 alias를 하나 더 다는 쪽이 안전하다.
>
> **이게 Spring 설정에서 의미하는 것** — 로컬에서 IDE로 앱을 띄우고 DB만 컨테이너로 돌릴 때와, 앱까지 컨테이너로 돌릴 때 접속 URL이 달라진다.
> ```
> 앱이 호스트에서 실행   → jdbc:mysql://localhost:3306/wms
> 앱도 컨테이너로 실행   → jdbc:mysql://mysql:3306/wms
> ```
> 두 번째 경우 `localhost`는 **앱 컨테이너 자기 자신**을 가리키기 때문에 접속이 안 된다. WMS를 배포할 때 자주 걸리는 지점이고, Spring 프로필(`application-local.yml` / `application-docker.yml`)로 분리하면 매번 고치지 않아도 된다.
>
> **`ports`와 이 이야기는 별개다.** `ports: ["3306:3306"]`은 **호스트에서** 컨테이너로 들어가는 문을 여는 설정이다. 컨테이너끼리는 같은 네트워크에 있으면 `ports` 없이도 서로 붙을 수 있다. 즉 앱까지 컨테이너로 돌린다면 MySQL의 `ports`는 없어도 되고, 오히려 배포 환경에서는 DB 포트를 바깥에 노출하지 않는 편이 안전하다. 로컬에서 DBeaver 같은 툴로 직접 붙어보려고 열어두는 것이다.

## 라운드 로빈

순서대로 돌아가며 나눠주는 것.

| | Compose | 스웜 모드 |
|---|---|---|
| 방식 | DNS가 IP를 번갈아 알려줌 | 가상 IP 하나를 주고 내부에서 분배 |
| 분배 시점 | 이름을 조회할 때 | 패킷이 지나갈 때 |

> **보충** — 위 표의 차이를 각각 **DNSRR(DNS Round Robin)**, **VIP(Virtual IP)** 라고 부른다. 스웜 모드에서는 VIP가 기본이고, `endpoint_mode: dnsrr`로 지정하면 DNS 방식으로 바꿀 수도 있다.
>
> **DNS 라운드 로빈의 함정** — 이름을 조회하는 시점에만 분배가 일어나기 때문에, **클라이언트가 조회 결과를 캐싱하면 분배가 멈춘다**. 예를 들어 JVM은 예전 버전에서 DNS 결과를 무기한 캐싱하는 설정이 기본이었고(`networkaddress.cache.ttl`), HikariCP 같은 커넥션 풀은 애초에 연결을 맺어놓고 계속 재사용하기 때문에 이름 조회 자체가 처음 한 번밖에 안 일어난다. 그래서 커넥션 풀을 쓰는 Spring 앱 입장에서는 DNS 라운드 로빈이 사실상 "처음 뽑은 하나에 계속 붙는" 결과가 되기 쉽다. 또 컨테이너 하나가 죽어도 DNS는 그 IP를 계속 알려줄 수 있다.
>
> VIP 방식은 이 문제가 없다. 클라이언트는 항상 같은 가상 IP 하나만 알면 되고, 실제 분배는 커널 레벨(IPVS)에서 패킷 단위로 일어나며, 죽은 컨테이너는 분배 대상에서 자동으로 빠진다.
>
> **WMS 관점에서** — 이건 지금 당장 필요한 내용은 아니다. Compose로 DB 하나 앱 하나를 띄우는 단계에서는 분배할 대상이 없기 때문이다. 다만 나중에 앱을 여러 개로 늘려서 부하 테스트를 할 계획이라면, Compose의 `--scale`만으로는 위의 이유 때문에 부하가 제대로 안 갈라진다는 걸 알아두면 좋다. 그때는 앞에 Nginx 같은 리버스 프록시를 하나 두고 거기서 분배하게 하는 방식이 현실적이다.

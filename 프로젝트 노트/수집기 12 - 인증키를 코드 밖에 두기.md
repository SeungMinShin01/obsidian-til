# 수집기 12 - 인증키를 코드 밖에 두기

> 허브: [[수집기 프로젝트 MOC]]

API 인증키를 받고 나서 가장 먼저 정한 것. 소스가 늘 때마다 반복되는 절차라 한 번 정리해둔다.

## 1. 배운 내용

### 1-1. 이것부터 정하는 이유

키를 코드에 적으면 커밋되고, **한 번 커밋되면 나중에 지워도 git 이력에 남는다.** 파일에서 지운 커밋을 새로 만들어도 이전 커밋을 열면 그대로 보인다.

프로젝트 원칙에 그대로 걸린다.

> 되돌릴 수 있는 것은 겪은 뒤에 정한다. 되돌릴 수 없는 것만 지금 확정한다.

키 유출은 되돌릴 수 없는 쪽이다. 그래서 첫 호출을 해보기 전에 정한다.

### 1-2. 환경변수는 그 터미널에만 산다

```powershell
$env:WORK24_API_KEY = "받은-인증키"
```

파일이 아니라 **그 터미널의 메모리에 얹는 값**이다. 창을 닫으면 사라지고, 다른 창에는 없다.

실제로 여기서 한 번 걸렸다. 키를 넣은 창과 파이썬을 돌린 창이 달라서 `KeyError`가 났다. VS Code 터미널과 따로 띄운 PowerShell은 서로 남남이다.

불편하지만 이 단계에서는 이쪽이 맞다. **파일로 안 만들면 실수로 커밋할 일 자체가 없다.**

### 1-3. 셸마다 문법이 다르고 파이썬에서는 하나다

| 셸 | 쓰는 법 |
| --- | --- |
| PowerShell | `$env:WORK24_API_KEY = "키"` |
| cmd | `set WORK24_API_KEY=키` |
| git bash / 리눅스 | `export WORK24_API_KEY=키` |

셋 다 결과가 같고, 파이썬 쪽에서는 전부 이 한 줄로 읽힌다.

```python
os.environ["WORK24_API_KEY"]
```

### 1-4. 로컬 환경변수와 Actions Secret이 같은 것으로 도착한다

이게 이 단계의 핵심이다.

| 어디 | 키가 오는 경로 |
| --- | --- |
| 내 PC | `$env:...`로 넣은 값 |
| Actions VM | Secret 등록 → 워크플로우 `env:` 블록 → 같은 이름의 환경변수 |

코드 입장에서는 둘이 구분되지 않는다. 그래서 **로컬에서 되면 Actions에서도 된다**가 성립하고, 워크플로우를 고쳐가며 시행착오할 필요가 없다.

Actions 쪽은 이렇게 생겼다.

```yaml
      - name: 수집기 실행
        run: python collector/main.py
        env:
          WORK24_API_KEY: ${{ secrets.WORK24_API_KEY }}
```

`secrets.`는 저장소 설정에 등록해둔 값을 꺼내는 자리다. **워크플로우 파일에는 키가 아니라 키 이름만 적힌다.**

### 1-5. `[]`와 `.get()`의 차이

```python
os.environ["WORK24_API_KEY"]      # 없으면 KeyError — 즉시 멈춘다
os.environ.get("WORK24_API_KEY")  # 없으면 None — 조용히 넘어간다
```

`os.environ`은 딕셔너리처럼 생긴 객체라 없는 키를 `[]`로 꺼내면 딕셔너리와 똑같이 `KeyError`가 난다.

여기서 `[]`를 쓴 것은 의도적이다. `.get()`이었다면 `None`이 주소에 실려 `authKey=None`으로 호출되고, 서버는 인증 실패 응답을 돌려준다. 그러면 **에러가 응답 파싱 단계에서 엉뚱한 모양으로 터진다.** 원인은 키 없음인데 증상은 파싱 실패로 나타난다.

무인으로 도는 시스템에서 특히 중요하다. Actions 로그에 `KeyError: 'WORK24_API_KEY'`가 찍히면 Secret 등록을 깜빡한 것을 5초 만에 안다.

### 1-6. 로그에 요청 주소를 통째로 찍지 않는다

정상 응답에는 키가 없다. 그런데 **에러 메시지에는 요청 주소가 통째로 실릴 수 있고**, 그 안에 `authKey=`가 들어 있다.

| 어디 | 보호 |
| --- | --- |
| Actions 로그 | GitHub가 Secret 값을 `***`로 자동 마스킹 |
| `data/run-log.md` | **없다.** 우리가 만든 파일이고 저장소에 그대로 커밋된다 |

그래서 로그에 남길 때는 주소가 아니라 **무엇을 했는지**를 적는다. `실행 : ... 신규 3건, 누적 12건` 형태가 그 원칙을 이미 따르고 있다.

## 2. 추가로 알면 좋은 활용법

### 2-1. `urlencode`를 쓴 이유

```python
url = f"{BASE}?{urllib.parse.urlencode(params)}"
```

딕셔너리를 `authKey=...&callTp=L&...` 형태로 바꿔준다. f-string으로 직접 이어붙이지 않는 이유는 값에 한글이나 `&`가 섞였을 때 주소가 깨지기 때문이다.

`store.py`에서 `?` 자리표시자를 쓴 것과 같은 발상이다. **내가 만들지 않은 문자열을 직접 문장에 끼워넣지 않는다.**

### 2-2. `.env`를 지금 안 쓰는 이유

`.env` 파일 방식이 더 편하긴 하다. 창을 새로 열어도 살아 있다.

다만 그 방식은 **`.gitignore`에 넣는 것을 잊으면 키가 통째로 커밋되는 구조**다. 편의를 얻는 대신 한 번의 실수로 되돌릴 수 없는 사고가 나는 쪽을 택하는 것이라, 소스가 여러 개가 되어 매번 다시 치기가 정말 번거로워질 때 옮긴다.

옮길 때 순서는 `.gitignore`에 먼저 적고 → 파일을 만든다. 반대로 하면 그 사이에 `git add .`가 들어갈 수 있다.

### 2-3. 키가 실수로 커밋됐을 때

이력에서 지우는 것보다 **발급처에서 키를 폐기하고 새로 받는 것**이 확실하다. 이력 수정은 어렵고, 이미 푸시됐다면 누가 봤는지 알 수 없다.

## 3. 더 나아가 알면 좋은 것

### 3-1. 다음에 볼 키워드

- `python-dotenv` — `.env` 파일을 읽는 표준적인 방법
- GitHub Secrets와 Environments — 환경별로 다른 값 주기
- 키 회전(rotation) — 주기적으로 새 키로 바꾸는 운영
- `git filter-repo` — 이력에서 파일을 지우는 도구
- `requests` — `urllib`보다 편한 HTTP 라이브러리. 소스가 늘면 옮겨갈 곳

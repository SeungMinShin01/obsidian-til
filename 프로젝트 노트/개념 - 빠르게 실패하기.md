# 개념 - 빠르게 실패하기

프로젝트에서 반복해서 나오는 판단이라 개념으로 뺀 노트다. 같은 결정이 `store.py`, 환경변수, 어댑터 세 군데서 나왔다.

## 1. 무엇인가

**fail-fast(빠른 실패)**는 실제로 존재하는 이름 있는 설계 원칙이다. Jim Shore가 쓰고 Martin Fowler가 감수한 「Fail Fast」가 IEEE Software 2004년 9/10월호에 실렸다.

> 즉시 눈에 보이게 실패하는 것이, 잘못된 상태로 계속 돌아가는 것보다 낫다.

핵심 논거는 **버그의 비용이 발견이 늦어질수록 커진다**는 것이다. 잘못된 값이 통과하면 그 값이 다른 계산에 섞이고, 저장되고, 며칠 뒤 엉뚱한 곳에서 증상이 나타난다. 그때는 원인을 거슬러 올라가야 한다.

증상이 나타나는 지점과 원인이 있는 지점이 멀어지는 것이 진짜 비용이다.

## 2. 자바에서 이미 본 것

`ArrayList`를 `for-each`로 돌면서 중간에 원소를 지우면 이게 난다.

```java
ConcurrentModificationException
```

자바 컬렉션의 반복자를 공식 문서에서 **fail-fast iterator**라고 부른다. 순회 중에 컬렉션이 바뀌면 그 자리에서 던진다. 그냥 두면 원소를 건너뛰거나 중복해서 읽는데, 그건 예외가 아니라 **조용히 틀린 결과**가 되기 때문이다.

`Objects.requireNonNull()`, 생성자 첫머리의 인자 검사도 같은 계열이다.

## 3. 반대편에도 이름이 있다

| 개념 | 태도 |
| --- | --- |
| **fail-fast** | 이상하면 즉시 멈춘다 |
| **fail-safe** | 실패해도 안전한 상태로 간다 |
| **fail-soft / graceful degradation** | 일부를 포기하고 나머지로 계속 간다 |

셋 중 무엇이 옳다가 아니라 **어디에 쓰느냐**의 문제다.

## 4. 이 프로젝트는 둘을 같이 쓴다

모순이 아니다. 자리가 다르다.

| 어디 | 어떻게 | 왜 |
| --- | --- | --- |
| 인증키가 없다 | **fail-fast** — `os.environ["..."]`가 `KeyError` | 키 없이 돌아봐야 전부 인증 실패다. 계속 갈 이유가 없다 |
| 중복 id가 들어온다 | **fail-fast** — `PRIMARY KEY`가 거부 | 조용히 들어가면 통계가 틀어진다 |
| 값을 SQL에 끼워넣는다 | **fail-fast** — `?` 자리표시자가 문장이 되는 것을 막는다 | 통과시키면 잘못된 문장이 그대로 실행된다 |
| 소스 하나가 죽는다 | **fail-soft** — `try`/`except continue` | 나머지 소스는 멀쩡하다. 오늘 치를 통째로 버릴 이유가 없다 |

## 5. 선이 갈리는 기준

> **계속 진행해서 의미 있는 결과가 나오는가.**

키가 없으면 뒤의 모든 단계가 무의미하다 → 멈춘다.
소스 하나가 죽어도 나머지 소스의 공고는 여전히 쓸모 있다 → 계속 간다.

## 6. 무인 시스템이라서 더 중요하다

직관과 반대다. 사람이 안 보고 있으니 어떻게든 계속 돌아야 할 것 같지만, **사람이 안 보고 있으니까 조용한 실패가 훨씬 위험하다.**

틀린 데이터가 쌓이는 것을 3개월 뒤에 발견하면, 그때는 어느 시점부터 틀렸는지도 모른다. 반면 즉시 멈추면 실패 메일이 오고 그날 고친다.

실제 사례가 있었다. 환경변수를 `.get()`으로 읽었다면 `authKey=None`으로 호출되고 서버는 인증 실패 XML을 돌려준다. 그러면 **에러가 응답 파싱 단계에서 엉뚱한 모양으로 터진다.** 원인은 키 없음인데 증상은 파싱 실패로 나타나므로, API가 바뀐 줄 알고 한참 헤매게 된다.

## 7. 멱등성과의 관계

축이 다르다.

| 개념 | 묻는 것 |
| --- | --- |
| [[개념 - 멱등성]] | 무인으로 반복 실행돼도 괜찮은가 |
| 빠르게 실패하기 | 틀렸을 때 어떻게 행동할 것인가 |

둘 다 무인 시스템에서 반복해 나오지만 겹치지 않는다.

## 8. 다음에 볼 키워드

- 방어적 프로그래밍(defensive programming) — 빠른 실패와 자주 대비되는 태도
- 사전조건 검사(precondition) / 단언(assertion)
- Erlang의 "let it crash" — 빠른 실패를 시스템 철학으로 밀어붙인 사례
- 서킷 브레이커 — 반복 실패하는 외부 호출을 아예 차단하는 패턴
- 관측 가능성(observability) — 실패를 눈에 보이게 만드는 쪽의 이야기

# 수집기 21 - moef 어댑터의 세 층

> 허브: [[수집기 프로젝트 MOC]]

`sources/moef.py`를 함수 셋으로 쌓은 기록이다. 「수집기 18」에서 정한 `fetch() -> list[dict]` 계약을 실제 API에 처음 적용했다.

```
_call(page)     한 페이지를 가져온다
_to_job(row)    응답 한 줄을 우리 형식으로 바꾼다
fetch()         페이지를 돌며 전부 모은다
```

## 1. 배운 내용

### 1-1. 어댑터 이름을 정하는 기준

기준은 「수집기 06」의 그것 — **이 파일을 언제 고치게 되는가.** 이 API의 응답이 바뀔 때 고치므로, 그 API를 가리키는 가장 안정적인 식별자여야 한다.

| 후보 | 문제 |
| --- | --- |
| `moef.py` (기획재정부) | 부처 이름은 조직 개편으로 바뀐다. 재정경제부 → 기획재정부가 실제 사례 |
| `data_go_kr.py` | 포털에는 API가 수천 개. 다른 공공 API를 붙이면 충돌 |
| `alio.py` | 데이터 원천 시스템. 다만 「알리오 플러스」(시설·행사)와 혼동 — 실제로 헛걸음했다 |

`moef`로 정했다. 부처명의 약점은 docstring에 제공처와 원천을 둘 다 적어 보완한다. 이름 하나가 바뀌어도 어느 API인지 추적된다.

환경변수 이름은 어댑터 파일명과 짝을 맞춘다 — `moef.py` → `MOEF_SERVICE_KEY`. Secrets가 대여섯 개로 늘어도 이름만 보고 어느 어댑터 것인지 안다.

### 1-2. 아래층부터 쌓는다

위층은 아래층을 부르지만 반대는 없다. 아래가 확실해야 위를 얹을 수 있고, 반대로 하면 위층을 테스트할 때마다 아래가 흔들린다. 그리고 `_call(1)`만 따로 불러 응답을 볼 수 있다 — 반복을 돌리지 않고도 확인이 된다.

세 층을 나눈 이유는 「수집기 06」의 파일 분리 기준을 **함수 단위에 적용한 것**이다.

| 무엇이 바뀌면 | 어디만 고치나 |
| --- | --- |
| 주소·파라미터 | `_call` |
| 필드 이름 | `_to_job` |
| 몇 페이지를 돌지 | `fetch` |

### 1-3. `_call` — 한 페이지만

```python
def _call(page: int) -> dict:
    params = {"resultType": "json", "ongoingYn": "Y",
              "numOfRows": PAGE_SIZE, "pageNo": page}
    key = os.environ["MOEF_SERVICE_KEY"].strip()
    url = f"{BASE}?serviceKey={key}&{urllib.parse.urlencode(params)}"
    with urllib.request.urlopen(url, timeout=TIMEOUT) as resp:
        return json.loads(resp.read().decode("utf-8"))
```

- **`page`를 인자로 받는다.** 전체가 몇 페이지인지 이 함수는 모른다. 아래층이 위층 사정을 모르는 것이 좋다
- **`serviceKey`가 `urlencode` 밖에 있다.** Encoding 키를 또 인코딩하면 깨진다. 「수집기 12」의 "값을 직접 이어붙이지 않는다"에 대한 의도적 예외이고, **예외를 둘 때는 이유가 코드 옆에 남아야** 나중에 정리하다 되돌리지 않는다
- **`TIMEOUT`이 안전장치다.** 서버가 응답을 안 주면 `urlopen`은 영원히 기다린다. 사람이 보고 있으면 Ctrl+C면 되지만 **Actions에서는 아무도 안 누른다.** 무인 코드에는 반드시 상한이 있어야 한다
- `resultType`을 명시했다. 기본값은 바뀔 수 있다

### 1-4. `_to_job` — 번역은 한 곳에서만

API가 주는 이름(`recrutPbancTtl`, `aplyQlfcCn`)이 우리 코드 전체로 퍼지면, API가 이름을 바꾸는 날 `store`·`writer`·`main`을 전부 고쳐야 한다. 이 함수 바깥으로는 우리 이름만 나간다.

```
API 이름 ──▶ [_to_job] ──▶ 우리 이름 ──▶ store · writer · main
```

바깥 시스템의 어휘가 우리 도메인으로 새어드는 것을 막는 경계층을 **부패 방지 계층(Anti-Corruption Layer)**이라고 부른다.

```python
return {
    "id": f"{SOURCE}:{row['recrutPblntSn']}",
    "title": row.get("recrutPbancTtl", ""),
    ...
    "raw": json.dumps(row, ensure_ascii=False),
}
```

- **`id`만 `[]`이고 나머지는 `.get()`이다.** id 없이는 저장 자체가 불가능하니 터지게 두고, 제목 하나 비었다고 공고를 통째로 버릴 이유는 없다. 없으면 안 되는 값과 없어도 되는 값을 코드에서 갈랐다. #빠른실패 → [[개념 - 빠르게 실패하기]]
- **`raw`에 원문을 통째로 넣는다.** 컬럼으로 뺀 것은 자주 조회할 것뿐이고 나머지는 `raw`에 남아 나중에 꺼낼 수 있다. 컬럼은 최소로, 원문은 전부. `ensure_ascii=False`가 없으면 한글이 `서울`로 저장된다
- **코드값 대신 이름값을 컬럼으로.** `R600019`가 아니라 `전기.전자`. 읽고 다루기 편하고, 코드가 필요하면 `raw`에 있다
- **날짜를 하이픈 형태로.** API는 `20260818`, 요청 파라미터와 `first_seen_at`은 `2026-08-18`. 한 DB에 날짜 형식이 둘이면 비교할 때 걸린다. `_to_date`가 방어적인 이유는 `null`이 실제로 오기 때문이다

### 1-5. `fetch` — 언제까지 도는지만 정한다

```python
for page in range(1, MAX_PAGES + 1):
    rows = _call(page).get("result", [])
    jobs.extend(_to_job(r) for r in rows)
    if len(rows) < PAGE_SIZE:
        break
    time.sleep(DELAY_SEC)
```

- **종료 조건 `len(rows) < PAGE_SIZE`.** 100개 달라고 했는데 적게 왔으면 마지막 페이지다. `totalCount`로 페이지 수를 계산할 수도 있지만 올림 처리라는 틀릴 자리가 생긴다 — `517//100=5`로 쓰면 마지막 17건을 조용히 놓친다. 받은 것 자체가 근거인 조건은 서버가 totalCount를 잘못 줘도 어긋나지 않는다. **계산한 값보다 관측한 값을 믿는다** — 「수집기 07」에서 신규 개수를 앞뒤로 세서 구한 것과 같은 계열
- **`MAX_PAGES`가 두 번째 출구다.** 서버가 어느 날 무한히 100건씩 주면 정상 종료 조건은 영영 참이 안 된다. 「수집기 16」의 "빠져나올 길이 두 개"가 코드가 됐다
- **`sleep`이 `break` 뒤에 있다.** 마지막 페이지를 받고 나서는 안 잔다. 반대로 두면 매 실행 1초씩 의미 없이 버린다
- **`try`/`except`가 없다.** 잡는 곳은 `main.py`의 `collect_all`이다. 여기서 또 잡으면 같은 실패를 두 겹으로 처리하게 되고 나중에 어디서 잡혔는지 헷갈린다. **실패를 처리하는 자리는 한 곳으로**

### 1-6. 키 형태를 코드가 확인한다

```python
if "%" not in key:
    raise ValueError("MOEF_SERVICE_KEY가 비었거나 Encoding 키가 아니다")
```

`os.environ["..."]`는 "변수가 없다"만 잡는다. **빈 문자열은 존재 검사를 통과한다.** Secret이 등록 안 된 채 `env:` 블록만 있으면 GitHub가 빈 문자열을 넣어주고, 그러면 네트워크까지 갔다가 403으로 돌아와 "API 장애"처럼 읽힌다. 존재 확인과 값 확인은 다른 검사다. 이 줄이 있으면 실패 셋이 전부 원인을 그대로 말하는 메시지로 수렴한다.

## 2. 붙여넣다 겪는 일

### 2-1. 들여쓰기가 소속이다

함수 두 개가 앞 함수의 몸통 안으로 들어간 채 저장되는 일이 생긴다. 편집기에 붙여넣을 때 들여쓰기가 딸려 들어가면 그렇게 된다. 자바라면 중괄호가 소속을 정하니 이런 일이 안 생기는데, 파이썬은 앞 공백 4칸이 곧 "이 함수의 일부"라는 선언이다.

게다가 그 위치가 `return` 뒤라면 그 `def`들은 **한 번도 실행되지 않는다** — 함수 안의 `def`도 실행되어야 만들어지는 문장인데 `return`이 먼저 나간다. 모듈 어디에도 그 함수가 존재하지 않게 되고, 에러는 엉뚱한 `NameError`로 나타난다. 트레이스백만 보면 상수 누락으로 읽히고, 파일을 직접 읽어야 들여쓰기 문제가 보인다.

### 2-2. 상수 몇 줄이 빠지면 `NameError`

함수는 붙였는데 `SOURCE`·`MAX_PAGES` 같은 상수 정의를 빠뜨리면 실행 시점에 `NameError`가 난다. 타입 힌트도 `py_compile`도 못 잡는다. 「수집기 18」 2-2와 같은 종류 — 이름의 존재는 그 줄이 실행될 때 확인된다.

## 3. 더 나아가 알면 좋은 것

- 부패 방지 계층(Anti-Corruption Layer) — DDD에서 온 이름
- `typing.Protocol` — `fetch()` 계약을 검사 가능하게 만들기
- 재시도와 지수 백오프 — 지금은 없다. 실패하면 그 회차는 포기하고 다음 회차에 맡긴다
- 커서 기반 페이지네이션 — 수집 중 새 항목이 끼어들 때 오프셋 방식과의 차이

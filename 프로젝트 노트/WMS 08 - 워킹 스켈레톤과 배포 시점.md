# WMS - 워킹 스켈레톤과 배포 시점

> 허브: [[WMS 프로젝트 MOC]]

## 1. 배운 내용

### 1-1. "배포 후 개발"이라는 말은 없다

기능을 다 만들고 마지막에 배포하는 대신, 시작하자마자 배포부터 뚫어두는 방식이 있다고 들었는데 검색해도 안 나왔다. 당연했다. **그런 용어가 없기 때문이다.**

정식 이름은 **워킹 스켈레톤(Walking Skeleton)** 이다. 알리스테어 코오번이 『Writing Effective Use Cases』(2000)에서 붙인 이름이다.

비슷한 개념으로 **트레이서 불릿(Tracer Bullet)**, **스틸 스레드(Steel Thread)** 도 있다. 이 단어들로 검색하면 자료가 나온다.

### 1-2. 워킹 스켈레톤은 MVP가 아니다

이게 처음에 헷갈렸다. 한국어 자료 중에 "워킹 스켈레톤은 최소한의 제품(MVP)을 end-to-end로 구현한 것"이라고 쓴 게 있었는데, **부정확한 설명이다.**

원 정의는 "최종 아키텍처가 아니어도 되지만 **주요 아키텍처 구성요소를 전부 연결하는** 아주 작은 end-to-end 구현"이다. 기능이 최소인 게 아니라 **기능은 없어도 되고 아키텍처만 완전한** 것이다.

| | 워킹 스켈레톤 | MVP |
| --- | --- | --- |
| 축 | 기술·아키텍처 | 사용자 가치·비즈니스 |
| 묻는 것 | 이 시스템이 끝까지 이어지고 배포되는가 | 사용자가 이걸 원하는가 |
| 기능 | 거의 없음. 가치 0이어도 된다 | 초기 사용자가 실제로 쓸 만큼 |
| 아키텍처 | **완전함** | 대충이어도 된다 |
| 순서 | 먼저 | 나중 |

그래서 순서는 이렇게 된다.

```
워킹 스켈레톤  →  기능 개발  →  측정·최적화
 배포까지 뚫기     한 바퀴 돌리기     숫자 남기기
```

이 프로젝트에서는 MVP라는 말이 잘 안 맞는다. 사용자 검증이 목적이 아니기 때문이다. MVP 자리에 오는 건 **2주차 체크포인트 = 입고부터 출고까지 한 바퀴가 도는 상태**다.

### 1-3. 왜 이 순서가 이득인가

배포에서 터지는 문제는 대부분 **코드가 아니라 환경 문제**다.

CORS, 환경변수 주입, HTTPS 인증서, 빌드 설정, 포트 개방, DB 접속 정보. 이것들은 기능을 얼마나 잘 만들었는지와 아무 상관이 없다. 기능이 완벽해도 똑같이 터진다.

문제는 **마지막에 몰아서 하면 여섯 개가 한꺼번에 터진다**는 것이다. 각각은 30분이면 풀리는데, 동시에 터지면 어느 게 원인인지 분리가 안 돼서 밤을 새우게 된다.

워킹 스켈레톤이 잡아내는 건 기능 버그가 아니라 **경계에서 나는 실패**다 — 데이터 인터페이스, 지연시간 한계, 배포 제약. 지금 만나면 고치는 비용이 거의 0이다.

### 1-4. 0일차에 배포까지 넣기로 한 이유

원래 계획은 2주차 중반에 시험 배포 한 번이었는데 0일차로 당겼다. 조건이 바뀌었기 때문이다.

- **3주 뒤엔 주당 몇 시간뿐**이라, 3주차에 배포하다 막히면 그대로 끝난다
- **"실제 배포된 주소"가 평가 3순위**인데, 이걸 마지막 날 리스크로 남겨두는 건 순서가 거꾸로다

0일차 배포는 화면에 글자 하나 띄우는 수준이라 반나절이면 된다. 그 뒤 모든 커밋이 자동으로 배포되게 해두면 "매주 배포 가능한 상태 유지" 원칙도 저절로 지켜진다.

## 2. 추가로 알면 좋은 활용법

### 2-1. 0-A와 0-B로 쪼갠 이유

한 번에 하려니 덩어리가 커서 둘로 나눴다.

- **0-A 로컬 관통** — 브라우저 → React → Vite 프록시 → Spring → MySQL이 한 줄로 이어짐
- **0-B 서버 관통** — 같은 화면이 인터넷 주소로 뜸

0-A가 끝나면 "내 PC 안에서는 전부 연결됐다"가 증명되고, 0-B에서 남는 문제는 순수하게 서버·네트워크 문제로 좁혀진다. **문제의 범위를 미리 잘라두는 것**이 쪼갠 이유다.

### 2-2. 자동 배포는 나중에

먼저 손으로 한 번 끝까지 성공시키고, 그 절차를 그대로 GitHub Actions로 옮긴다. **되는 걸 옮기는 것과 처음부터 짜는 것은 난이도가 다르다.**

손으로 해보면 무엇이 필요한지(어떤 파일을 어디로, 어떤 순서로) 몸으로 알게 되고, 그게 그대로 워크플로우 파일의 내용이 된다.

## 3. 더 나아가 알면 좋은 것

### 3-1. 다음에 볼 키워드

- Tracer Bullet — 『실용주의 프로그래머』에 나오는 비슷한 개념
- Steel Thread — 같은 아이디어의 또 다른 이름
- Deployment Pipeline — 지속적 배포에서 이 개념이 어떻게 확장되는지

### 3-2. 되짚어볼 것

3주차가 끝났을 때, 0일차에 배포를 뚫어둔 것이 실제로 시간을 아꼈는지 확인해보면 좋겠다. 아꼈다면 그 자체가 다음 프로젝트의 근거가 된다.

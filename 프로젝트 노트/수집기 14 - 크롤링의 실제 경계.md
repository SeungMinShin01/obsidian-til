# 수집기 14 - 크롤링의 실제 경계

> 허브: [[수집기 프로젝트 MOC]]

채용 API가 대부분 기업 전용으로 닫히면서 크롤링이 현실적인 선택지가 됐다. **비공개 저장소에 개인 보관만 하더라도 무엇이 남는지**, 그리고 그렇게 모은 것이 **포트폴리오로 어디까지 나갈 수 있는지**를 정리한 기록이다.

법률 자문이 아니라 판단을 위해 정리한 일반적인 내용이다.

## 1. 배운 내용

### 1-1. Private이 방어하는 것과 못 하는 것

저장소를 비공개로 두는 것은 **일부만** 방어한다. 이 구분이 출발점이다.

| | Private이 방어하나 |
| --- | --- |
| 재배포·전송·게시 | **한다.** 안 하는 것이니까 |
| 경쟁 서비스 제공 | **한다.** 2017 잡코리아 판례의 핵심 쟁점이 이것이었다 |
| 접근·복제 행위 자체 | **못 한다.** 어디에 저장하든 무관 |
| 서버에 준 부하 | **못 한다.** 요청은 이미 갔다 |
| 개인정보 수집 | **못 한다.** 저장했다는 사실이 남는다 |

Private은 **가장 무거운 쪽을 덜어내지만 바닥을 0으로 만들지 않는다.**

### 1-2. 데이터베이스제작자의 권리

[[수집기 10 - 수집 대상을 고르는 기준]]의 판례 근거다. "상당한 투자로 만든 데이터 집합"을 보호하고 **복제도 권리 범위에 든다.**

다만 그 판례는 사람인이 긁어서 **자기 사이트에 올린 것**이 문제였다. 개인이 비공개로 보관만 하는 경우는 성격이 다르고, 학술·연구 목적 비영리 이용에 대한 제한 규정도 있다. 위험도는 확실히 낮지만 **복제 자체가 이미 권리 범위 안**이라는 것은 알고 있어야 한다.

### 1-3. 약관 — 회원 여부가 갈림길이다

처음에는 로그인 여부가 기준이라고 봤는데, 실제 약관을 읽고 나서 틀렸다는 것을 알았다. 조항의 주어가 「회원」이지 「로그인한 사용자」가 아니다.

| 구분 | 약관이 적용되나 |
| --- | --- |
| 계정이 없다 | 계약 관계가 없다. 직접 적용은 어렵다 |
| 계정은 있지만 로그아웃 상태다 | **적용된다.** 동의는 세션이 아니라 계정에 붙어 있다 |
| 로그인 상태다 | 적용된다 |

**브라우저에서 로그아웃해도 계약은 그대로다.**

그리고 계정이 없어도 **데이터베이스제작자의 권리는 남는다.** 그쪽은 계약이 아니라 저작권법이 직접 부여하는 권리라 가입 여부와 무관하다. "가입 안 했으니 괜찮다"는 절반만 맞는 말이다.

원칙은 이렇게 정리된다.

> **로그인이 필요한 콘텐츠는 건드리지 않는다.** 그리고 이미 회원인 서비스는 약관이 그대로 적용된다는 것을 전제한다.

### 1-4. 기술적 차단 우회 — 여기가 진짜 선이다

`robots.txt`를 어기는 것보다 훨씬 무겁다. 우회는 **고의성을 만들기 때문**이다.

- CAPTCHA 풀기
- IP 차단당한 뒤 프록시로 바꿔 계속하기
- `User-Agent`를 브라우저로 위장하기
- rate limit을 피하려 요청을 분산하기

"몰랐다"가 성립하지 않고, 정보통신망법의 무단 침입 쟁점까지 끌어올 수 있다.

> **막히면 멈춘다. 뚫지 않는다.**

`User-Agent`를 위장하지 않고 정직하게 남기는 것이 의외로 중요하다. **위장은 우회이고, 정직한 표기는 그 반대 증거가 된다.**

### 1-5. 서버 부하

과도한 요청으로 서비스에 지장을 주면 업무방해 쟁점이 된다. 하루 1회 수십 건이면 실질적으로 해당 없다.

다만 **재시도 로직을 잘못 짜서 무한 반복하는 사고**는 실제로 잘 난다. 무인으로 도는 시스템이라 더 그렇다. 크롤러에 재시도를 넣을 때는 횟수 상한을 반드시 건다.

### 1-6. 개인정보 — 이 프로젝트에서 가장 실질적인 리스크

**채용공고에는 담당자 정보가 들어 있다.** 고용24 명세에서 확인한 필드들이다.

```
<empChargerDpt>   채용부서
<contactTelno>    전화번호
<chargerFaxNo>    팩스번호
```

공개된 페이지에 있어도 긁어서 DB에 넣는 순간 **개인정보 처리**에 해당한다. 공개돼 있다는 것이 자유롭게 수집·저장해도 된다는 뜻은 아니다.

그리고 이것은 저작권 쟁점과 달리 **비공개 보관이라고 면제되지 않는다.**

### 1-7. 그래서 설계에 박은 결정

> **개인정보 필드는 스키마에 아예 넣지 않는다.**

수집 단계에서 버린다. 나중에 지우는 것이 아니라 처음부터 담지 않는다. 담아두고 "안 쓰면 되지"는 성립하지 않는데, **DB에 있는 것 자체가 보유이기 때문**이다.

우리 목적(기술 키워드 통계, 우대사항 정규화, 면접 질문 생성)에 담당자 연락처는 쓸모가 없다. 잃는 것이 없다.

### 1-8. 안전선 체크리스트

| 항목 | 내용 |
| --- | --- |
| `robots.txt` | 거절한 경로는 가지 않는다 |
| 로그인 | 필요한 콘텐츠는 건드리지 않는다 |
| 우회 | 하지 않는다. 막히면 멈춘다 |
| `User-Agent` | 정체와 연락처를 남긴다. 차단 대신 연락이 오게 |
| 간격 | `Crawl-delay` 준수, 없어도 최소 3~5초 |
| 빈도 | 하루 1회, 필요한 만큼만 |
| 범위 | 원문 통째가 아니라 필요한 필드만 |
| 개인정보 | 스키마에 넣지 않는다 |
| 용도 | 개인 학습·취업 준비. 비영리 |
| 공개 | 하지 않는다 |

### 1-9. 다 지켜도 0은 아니다

데이터베이스제작자의 권리는 복제 단계에서 이미 성립할 여지가 있고, 약관에 자동 수집 금지가 명시돼 있으면 로그인을 안 해도 다툼의 소지가 남는다.

현실적으로 개인이 하루 1회 소량을 비공개로 모으는 것에 소송이 들어올 가능성은 매우 낮다. **가장 흔한 결과는 IP 차단**이다. 다만 "낮다"와 "없다"는 다르고, 감수하는 쪽을 택한 것이라는 자각은 필요하다.

## 2. 공개 경계 — 포트폴리오는 무엇으로 만드나

원본을 공개할 수 없다면 포트폴리오가 안 되는 것 아닌가 하는 의문에서 나온 정리다. 전제를 하나 뒤집으면 풀린다.

> **포트폴리오에 남는 것은 데이터가 아니라 시스템이다.**

보는 사람이 확인하는 것은 "공고 5천 건을 갖고 있다"가 아니라 "3개월 무인으로 도는 파이프라인을 만들고 운영했다"이다. 데이터는 그 시스템이 동작한다는 증거일 뿐이고, **증거는 원본이 아니어도 된다.**

### 2-1. 무엇이 공개 가능한가

| 산출물 | 공개 | 이유 |
| --- | --- | --- |
| 코드 (수집기·스키마·워크플로우) | **된다** | 내가 쓴 것이다 |
| 아키텍처 문서·README | **된다** | 오히려 핵심 |
| 3개월 운영 기록, 실패와 복구 | **된다** | 가장 값어치 있는 부분 |
| 학습 노트 | **된다** | 이미 Public Vault에 있다 |
| 집계·통계 결과 | **된다** | 아래 참조 |
| 원본 공고 텍스트 | 안 된다 | 남의 DB다 |
| 라이브로 남의 공고를 서빙하는 사이트 | 안 된다 | 판례가 정확히 이 상황이다 |

### 2-2. 집계 결과는 원본의 복제가 아니다

> "Python 공고의 70%가 Docker를 언급한다"

이 문장으로는 **개별 공고를 재현할 수 없다.** 어느 회사인지도 알 수 없다. 데이터베이스의 상당한 부분을 복제한 것이 아니라 원본을 읽고 만든 새로운 결과물에 가깝다.

그리고 이것이 우연이 아니라 **3단계의 목표 그 자체**다. 원래부터 만들려던 것이 원본 재배포가 아니라 통계였다.

```
크롤링 원본 (비공개)  →  집계·분석 (공개 가능)  →  포트폴리오
```

파이프라인이 이미 이 방향으로 흐르게 설계돼 있다. **막힌 것이 아니라 원본 단계만 비공개인 것**이다.

### 2-3. 대시보드는 라이브 대신 데모

5단계 React 대시보드를 포기할 필요는 없다.

| 형태 | 가능 |
| --- | --- |
| 라이브 서비스로 남의 공고를 서빙 | 안 된다 |
| 스크린샷·GIF·데모 영상 | 된다 |
| 코드 공개 + 샘플은 내가 만든 가짜 데이터 | 된다. 클론해서 돌려볼 수 있다 |
| 면접에서 화면 공유로 실제 데이터 시연 | 된다. 배포가 아니다 |

`FAKE_JOBS`가 지금 하는 역할이 그대로 **공개용 샘플 데이터**가 된다. 이미 그 자리에 있다.

### 2-4. 어댑터 구조가 두 개의 구성을 만든다

| 구성 | 소스 | 용도 |
| --- | --- | --- |
| 공개용 | API 소스 + 가짜 데이터 | 리포, 데모, 포트폴리오 |
| 개인용 | API + 크롤러 | Private 저장소, 실제 취업 준비 |

**같은 코드이고 소스 목록만 다르다.** 크롤러 어댑터 파일 하나를 빼면 공개 가능한 프로젝트가 된다. 어댑터를 격리하는 이유가 하나 더 생겼다.

### 2-5. 논문 수집기 쪽이 공개용에 더 맞는다

5단계의 arXiv 수집기는 **공식 API가 있고 메타데이터 재사용에 관대하다.** 크롤링 쟁점 자체가 없다.

- **채용 수집기** — 개인용. 코드와 통계만 공개
- **논문 수집기** — 같은 뼈대에 소스만 갈아끼운 것. **데이터까지 공개 가능**

"범용 수집기로 발전한다"는 목표가 여기서 실용적 의미를 얻는다. **같은 엔진이 두 도메인에서 도는 것을 보여주는 편이, 한 도메인에서 데이터를 많이 모은 것보다 강하다.** 추상화가 실제로 됐다는 증거이기 때문이다.

### 2-6. 판단 과정 자체가 산출물이다

"왜 크롤링을 안 했나요" 또는 "데이터는 왜 공개하지 않았나요"라는 질문에, `robots.txt`와 약관과 용도가 다른 층이라는 것, 우회가 왜 선을 넘는 행위인지, 개인정보 필드를 스키마에서 뺀 이유, 집계와 원본의 구분을 나눠서 답할 수 있다.

기술 스택은 비슷하게 적어내지만 이 부분은 그렇지 않다. 10번·13번·이 노트가 그 대답의 초안이다.

## 3. 더 나아가 알면 좋은 것

### 3-1. 다음에 볼 키워드

- 저작권법상 데이터베이스제작자의 권리와 그 제한 규정
- 개인정보 보호법의 수집·이용 근거와 최소수집 원칙
- 정보통신망법 제48조 — 정당한 접근권한
- `User-Agent` 작성 관례 — 봇 이름과 연락처 URL
- 지수 백오프(exponential backoff)와 재시도 상한
- arXiv API 이용약관과 메타데이터 재사용 조건
- 차등 프라이버시 — 집계 결과에서 개별 항목을 역추적하지 못하게 하는 기법

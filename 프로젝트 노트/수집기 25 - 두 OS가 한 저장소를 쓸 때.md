# 수집기 25 - 두 OS가 한 저장소를 쓸 때

> 허브: [[수집기 프로젝트 MOC]]

윈도우(내 PC)와 리눅스(Actions 봇)가 같은 저장소에 매일 커밋한다. 그 사이에서 생긴 git 문제들 — 푸시 거부, 로그 충돌, 줄바꿈 문자로 생긴 가짜 변경.

## 1. 배운 내용

### 1-1. 봇이 늘 앞서 있다

```
! [rejected]  main -> main (non-fast-forward / fetch first)
```

두 번 만났다. 「수집기 09」의 "작업 전에 `git pull`"이 실제로 걸린 순간이고, 며칠 묵힐수록 병합이 지저분해진다. 봇이 매일 원격을 진전시키므로 **로컬과 원격은 가만히 둬도 갈라진다.**

### 1-2. `run-log.md`는 양쪽에서 자란다

로컬에서 실험하며 붙인 줄과 봇이 붙인 줄이 **같은 파일의 같은 위치(끝)**에 쌓이므로 git이 자동으로 못 합친다.

```
CONFLICT (content): Merge conflict in data/run-log.md
```

로그는 양쪽 다 진짜다. 어느 쪽을 버리는 것이 아니라 **둘 다 남긴다** — 편집기의 「두 변경 사항 모두 수락」. 시간순이 조금 섞여도 로그로서는 문제없다. DB는 안 걸렸다 — 봇이 신규 0건이라 파일을 안 바꿨기 때문이다.

### 1-3. 줄바꿈 문자가 가짜 변경을 만든다

```
14 files changed, 463 insertions(+), 463 deletions(-)
```

**추가 줄 수 = 삭제 줄 수**는 내용이 아니라 줄 끝만 바뀐 전형적인 신호다.

| 어디서 저장 | 줄 끝 |
| --- | --- |
| VS Code (윈도우) | `CRLF` (`\r\n`) |
| Actions 봇 (리눅스), 원격 통로로 쓴 파일 | `LF` (`\n`) |

한 저장소를 두 OS가 쓰니 파일마다 줄 끝이 섞이고, git은 그것을 "모든 줄이 바뀌었다"로 본다. 확인은 `git diff -w --ignore-cr-at-eol --stat` — 비어 있으면 줄바꿈뿐이다. `file` 명령으로 `with CRLF line terminators`를 직접 볼 수도 있다.

이 가짜 변경이 `git pull`을 막는다 — "local changes would be overwritten by merge". 내용은 같은데 바이트가 달라서.

### 1-4. `git config core.autocrlf true`

윈도우 표준 설정이다. **저장소에는 LF로 넣고, 체크아웃할 때 CRLF로 바꿔준다.** 편집기는 CRLF로 보고, 저장소와 봇은 LF로 보고, 둘 사이에 가짜 diff가 안 생긴다. 이 설정이 미설정이라 git이 중재를 안 하고 있었다. 이후 뜨는 "LF will be replaced by CRLF" 경고는 그것이 정상 동작 중이라는 뜻이다.

### 1-5. 되돌릴 수 있는 변경은 `stash`로 치운다

`git restore .`로도 안 풀릴 때(윈도우 쪽이 파일을 다시 CRLF로 만들어둔다):

```powershell
git stash        # 미커밋 변경을 서랍에
git pull         # 걸릴 게 없으니 fast-forward
git stash drop   # 서랍을 버린다
```

버려도 되는 근거는 두 가지였다 — 줄바꿈 차이뿐이고, `data/채용/`은 다음 실행에 전부 다시 그려진다. **버려도 되는지 먼저 확인하고 버린다.** 그 확인이 1-3의 명령이다.

### 1-6. 커밋은 코드와 데이터를 나눈다

```powershell
git add collector/ .gitignore   → "moef 어댑터 추가 - ..."
git add data/ state/            → "첫 실수집 - 공공기관 공고 518건"
```

"코드가 어떻게 바뀌었나"와 "데이터가 얼마나 쌓였나"는 다른 질문이다. 봇 커밋이 데이터 쪽 이력을 이어가므로 사람 커밋도 그 결을 따르면 `git log -- collector/`로 코드 이력만 뽑힌다.

커밋 메시지에 증상을 남긴다 — "12일간 KeyError로 수집 0건이던 문제 해결". `git log`만 봐도 언제부터 언제까지 왜 비었는지 읽힌다.

## 2. 원격 통로의 제약이 알려준 것

이 프로젝트를 돕는 원격 통로는 **파일 삭제 권한이 없다.** 그 하나의 제약이 세 군데서 같은 모양으로 나타났다.

| 도구 | 만들고 지우는 것 | 증상 |
| --- | --- | --- |
| git | `.git/index.lock` | 이후 모든 git 명령이 막힘 |
| SQLite | 저널 파일 | `disk I/O error` |
| writer | 옛 md 파일 | 폴더 비우기 실패 |

**파일을 만들고 지우는 것을 한 쌍으로 쓰는 도구는 삭제가 막힌 곳에서 전부 같은 방식으로 실패한다.** 그래서 원격에서는 읽기 명령(`git log`, `git show`, `git diff --stat`, `SELECT`)만 쓰고, 쓰기는 사용자 터미널에서 한다.

## 3. 더 나아가 알면 좋은 것

- `.gitattributes`의 `* text=auto` — 저장소 차원에서 줄바꿈 정책을 고정 (개인 설정보다 확실)
- `git stash list` / `stash pop` — 서랍을 버리지 않고 되살리기
- `git pull --rebase` — 병합 커밋 없이 로컬 커밋을 위로 올리기
- 바이너리 파일(`.db`)이 충돌했을 때 — `checkout --ours` / `--theirs`

# 수집기 22 - 인증키 경로 통일과 12일의 공백

> 허브: [[수집기 프로젝트 MOC]]

`.env` 도입, Actions Secret 주입, 그리고 그 둘 사이를 빠뜨린 채 배포해서 **12일간 수집 0건**이던 사고까지. 「수집기 12」가 원칙이었다면 이 노트는 그 원칙이 실물에서 어떻게 작동하고 어떻게 깨지는지다.

## 1. 배운 내용

### 1-1. `.env`를 들인 시점

「수집기 12」에서 "매번 다시 치기가 정말 번거로워질 때 옮긴다"고 조건을 적어뒀다. 키가 둘째가 되고 터미널 열 때마다 다시 치고 있었으니 그 시점이었다.

순서가 방어선이다. **`.gitignore`에 먼저 적고 커밋한 다음 파일을 만든다.** 반대로 하면 그 사이에 `git add .`가 들어갈 수 있다. `git ls-files .env`가 빈 출력이면 추적 안 되는 것이 확인된 것이다.

### 1-2. 읽는 코드를 직접 만든 이유

보통은 `python-dotenv`를 설치하는데, 아직 **표준 라이브러리만으로** 버티는 중이다 — 워크플로우에 `pip install` 단계를 안 넣으려고. 읽는 일 자체는 열 줄이면 된다.

```python
def load() -> None:
    if not ENV_PATH.exists():
        return
    for line in ENV_PATH.read_text(encoding="utf-8").splitlines():
        ...
        name, value = line.split("=", 1)
        os.environ.setdefault(name.strip(), value.strip())
```

- **파일이 없으면 조용히 넘어간다.** Actions에는 `.env`가 없다 — 커밋을 안 하니까. 거기서는 Secrets가 진짜 환경변수를 넣어준다. 즉 `.env`는 로컬 편의 장치이고 **없는 것이 정상인 환경이 존재한다.** 그래서 여기는 fail-fast가 아니다. 키가 정말 없으면 어차피 `os.environ["..."]`가 그 자리에서 터진다 — 터지는 역할은 이미 그쪽에 있다
- **`setdefault` — 이미 있으면 덮지 않는다.** 진짜 환경변수가 `.env`를 이긴다. `.env`가 실수로 커밋된 상황에서도 Secrets 값이 우선한다
- **`split("=", 1)`** — 최대 한 번만 자른다. 키 값 안에 `=`가 있어도(Base64 끝에 흔하다) 뒷부분이 잘리지 않는다

`main()` 첫 줄에서 부른다. 다른 모듈이 환경변수를 읽기 전에, 단 한 번.

### 1-3. 편집기가 도와주겠다는 것을 거절한 이유

VS Code가 `.env`를 발견하고 "터미널에 자동 주입할까"라고 제안했다. 켜면 VS Code 터미널 안에서만 변수가 생긴다.

켜지 않았다. 켜면 **우리 로더가 없어도 로컬에서 잘 돌아간다.** `envfile.load()`가 빠지거나 깨져도 내 자리에서는 모르고 Actions에 가서야 드러난다. "로컬에서 되면 저기서도 된다"가 성립하려면 **키가 오는 경로가 양쪽에서 하나**여야 한다. 편집기가 중간에서 도와주면 그 등식이 조용히 깨진다.

### 1-4. 저장소 루트와 상대 경로

`.env`는 `.git`이 있는 폴더에 둔다. 이 프로젝트는 `수집기\collector\collector`처럼 **안쪽에 같은 이름의 코드 폴더**가 있어 헷갈린다. `Path(".env")`는 파이썬을 실행한 위치 기준이고, 우리는 항상 루트에서 `python collector/main.py`로 실행한다. 「수집기 05-3-2」의 상대 경로 이야기가 다시 나온 것이고, `del` 같은 셸 명령도 똑같이 서 있는 곳 기준이다.

### 1-5. Secret 등록과 주입은 별개 단계다

```
GitHub Settings의 Secret  ─▶  ${{ secrets.… }}  ─▶  VM의 환경변수  ─▶  os.environ
        (값 보관)              (꺼내는 문법)         (주입)            (읽기)
```

워크플로우에는 **키 이름만** 적힌다.

```yaml
      - name: 수집기 실행
        run: python collector/main.py
        env:
          MOEF_SERVICE_KEY: ${{ secrets.MOEF_SERVICE_KEY }}
```

`env:`는 쓰는 step에만 건다. 키가 필요 없는 step(checkout, push)까지 들고 있을 이유가 없다. Secret 칸에는 `=` 오른쪽 값만, 따옴표 없이, 줄바꿈 없이.

경우의 수를 펼치면 실패가 셋이고 증상이 다르다.

| `env:` | Secret | VM의 변수 | 로그 |
| --- | --- | --- | --- |
| ✅ | ✅ | 정상 값 | `수집 518건` |
| ❌ | ✅ | **없음** | `실패 소스 moef(KeyError)` |
| ✅ | ❌ | **빈 문자열** | `실패 소스 moef(HTTPError)` — 없는 Secret은 에러가 아니라 빈 값이 된다 |
| ❌ | ❌ | 없음 | `KeyError` |

세 번째가 제일 교묘하다. `os.environ["..."]`는 존재만 검사하므로 빈 문자열이 통과하고, 네트워크까지 갔다가 403으로 돌아와 API 장애처럼 읽힌다. 「수집기 21」 1-6의 키 형태 가드가 이 경우를 잡는다.

## 2. 12일의 공백

### 2-1. 무엇이 일어났나

8월 18일, moef 어댑터를 푸시하면서 Secret 등록과 `env:` 블록을 빠뜨렸다. 이후 12일간 매일:

```
실행 : 2026-08-19 ~ 08-30 - 수집 0건 신규 0건, 누적 518건, 마크다운 518건, 실패소드 moef(KeyError)
```

| 관찰 | 뜻 |
| --- | --- |
| `KeyError` | VM에 변수 자체가 없다 |
| 빌드는 매일 초록불, 봇 커밋 12개 | 격벽이 잡아서 프로그램은 정상 종료 → **실패 메일 없음** |
| 마크다운 518건 | 수집은 죽었는데 writer는 DB로 그리니 멀쩡 |
| 누적 518건 12일째 | **12일치 신규 공고를 하나도 못 받았다** |

「수집기 03」의 "초록불은 명령이 에러 없이 끝났다일 뿐"이 정확히 이 모양으로 나타났다. 로그를 열어봐야만 보이는 반쪽 실패였다.

### 2-2. 실제 비용

`ongoingYn=Y`라 진행 중 공고는 복구 후 다 들어온다. **그 사이에 올라왔다 이미 마감된 공고는 영영 없다.** 공고 기간이 2주 안쪽인 것들은 놓쳤다. "수집하지 않은 데이터는 영원히 얻을 수 없다"를 손해로 겪은 첫 사례다. #되돌릴수있는가 → [[개념 - 되돌릴 수 있는 결정과 없는 결정]]

### 2-3. 격벽의 양면

격벽이 없었다면 매일 실패 메일이 왔을 것이고 하루 만에 고쳤을 것이다. 격벽이 있어서 12일간 몰랐다. **fail-soft는 조용함을 대가로 산다.** 격벽을 두는 결정은 맞았지만, 격벽이 잡은 실패를 **사람에게 보이게 하는 장치**가 따로 필요하다는 것이 이 사고의 교훈이다. 로그에는 남아 있었다 — 아무도 로그를 매일 열지 않았을 뿐이다.

### 2-4. 복구

Secret 등록 → `env:` 블록 → `main.py` 정리(`실패소드` 오타, 낡은 docstring) → 푸시 → Run workflow. 커밋 메시지에 증상을 남겼다 — `git log`만 봐도 언제부터 언제까지 왜 비었는지 읽히게.

12일치 오타 `실패소드`는 로그에 그대로 둔다. 로그는 그때의 사실이고, 형식이 바뀐 지점이 코드가 바뀐 지점이다.

### 2-5. 예약 시각이 크게 밀린다

12일치 실행 시각: `01:27 → 01:26 → 01:37 → ... → 08:27 → 10:41 → 06:29 → 04:40`. 예약은 `00:00 UTC`인데 **최대 10시간이 밀렸다.** 「수집기 03」에서 "20분 밀림"으로 적었던 것보다 훨씬 심하다. GitHub의 예약 실행은 부하에 따라 지연되고, 정각(`0 0 * * *`)은 가장 붐비는 시각이다. 분을 0이 아닌 값으로 두면 나아진다.

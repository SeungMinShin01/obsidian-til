# WMS 테이블 설계 근거 — 왜 이 테이블, 왜 이 컬럼인가

> 단일 WMS 1차 스키마 (`WMS/sql/V1__init_schema.sql`) 해설. 거래처 테이블은 없다 (공급처·배송지는 문서에 텍스트로).
> 문서와 상태 전이 방식: §5. 샘플 데이터: `WMS/sql/sample_data.sql` (§6). MySQL 8.0.46에서 V1 → V2 → 샘플 순으로 실행해 정합성 검사 7종을 통과했다.

---

## 1. 먼저 원칙 다섯 개

이 다섯 개를 알면 나머지 컬럼은 대부분 설명된다.

| # | 원칙 | 그래서 생긴 것 |
|---|---|---|
| 1 | **재고 수량은 한 곳에서만 바뀌고, 바뀔 때마다 기록한다** | `stock`(현재 수량) + `stock_history`(변동 기록) 두 테이블. 이력 합계 = 현재 수량이어야 한다 |
| 2 | **재고 한 행 = 품목 × 로케이션 × 소비기한** | FEFO는 "어느 칸의 어느 기한 재고를 먼저 쓸지" 고르는 일이라, 이 셋이 한 행을 구분해야 한다. 로트 번호는 두지 않는다 |
| 3 | **문서는 머리(헤더)와 줄(품목)로 나눈다** | 발주 ↔ 발주 품목, 주문 ↔ 주문 품목, 출고지시 ↔ 출고지시 품목. 한 문서에 품목이 여러 개라서 |
| 4 | **상태는 문서 머리의 enum 문자열 컬럼 하나** (`status`) | 상태 전이 규칙을 enum과 엔티티 메서드가 검사한다. 숫자 코드를 쓰지 않는다 (§5) |
| 5 | **외래키는 자식 → 부모 한 방향만** | 양방향·순환 참조가 없다. JPA도 `@ManyToOne` 단방향만 쓴다 |

모든 테이블에 공통으로 `id BIGINT PK AUTO_INCREMENT`, `created_at`, `updated_at`이 있다(팀 규칙, `BaseEntity`). 아래 표에서는 생략한다.

## 2. 테이블 16개

| 영역 | 테이블 | 주말에 필요? | 한 줄 이유 |
|---|---|:-:|---|
| 위치 | `warehouse` | O | 로케이션의 최상위. 창고가 늘어도 구조가 그대로 |
| | `zone` | O | 구역별 보관 품목 구분, 로케이션 코드 첫 글자 |
| | `location` | O | 재고가 놓이는 실제 칸. FEFO 결과와 피킹 순서의 기준 |
| 품목 | `product` | O | 무엇을 보관하는지. 소비기한 규칙(출고허용 잔여일)이 여기 있다 |
| 사용자 | `users` | 시드만 | 로그인·권한(S1), 이력의 처리자 |
| 입고 | `purchase_order` | O | 입고예정 1건. 검수·적치·확정의 상태를 갖는다 |
| | `purchase_order_item` | O | 무엇을 몇 개 받기로 했는지. 검수 비교 기준 |
| | `inspection` | O | 실제로 받은 수량을 **소비기한별로** |
| | `putaway` | O | 받은 것을 어느 칸에 몇 개 둘지 |
| 재고 | `stock` | O | 지금 어디에 무엇이 몇 개 있는지 |
| | `stock_history` | O | 재고가 언제·왜·얼마나 바뀌었는지 |
| 출고 | `orders` | O | 배송처가 보낸 요청 1건 |
| | `order_item` | O | 주문의 품목별 수량 |
| | `delivery_order` | O | 여러 주문을 묶은 창고의 작업 단위 |
| | `delivery_order_item` | O | 묶은 주문들의 품목별 합계. FEFO 할당의 입력 |
| | `allocation` | O | 합계를 어느 재고 행에서 몇 개 잡았는지 = 피킹 항목 |

## 3. 테이블별 컬럼과 이유

### 3.1 `warehouse` — 창고

| 컬럼 | 왜 필요한가 |
|---|---|
| `warehouse_code` (UQ) | 사람이 부르는 이름 `WH-01`. id는 내부용이라 화면·문서에는 코드를 쓴다 |
| `warehouse_name`, `address` | 출고명세서·화면 표시용 |

지금은 1행뿐인데 테이블로 둔 이유: 구역이 창고에 속한다는 관계를 처음부터 표현해 두면, 창고가 2개가 돼도 테이블을 고치지 않는다.

### 3.2 `zone` — 구역

| 컬럼 | 왜 필요한가 |
|---|---|
| `warehouse_id` (FK) | 어느 창고의 구역인지 |
| `zone_code` | 로케이션 코드의 첫 글자 `A`. `(warehouse_id, zone_code)` UNIQUE — 창고 안에서만 겹치지 않으면 된다 |
| `zone_name` | "상온 A구역". **표시용일 뿐 적치를 제한하지 않는다** — 품목·화주별로 구역을 고정하면 한쪽은 칸이 남고 한쪽은 모자라서 (§4) |

### 3.3 `location` — 로케이션 (팔레트 랙 한 칸 = 팔레트 1장)

| 컬럼 | 왜 필요한가 |
|---|---|
| `zone_id` (FK) | 구역별 조회, 구역별 일괄 생성 |
| `location_code` (UQ) | `A-01-03-2`. 모든 요청·화면·피킹 리스트가 이 코드로 칸을 가리킨다. **0을 채운 형식이라 문자열 정렬 = 피킹 동선 순서** |
| `aisle`, `bay`, `shelf_level` | 코드를 쪼갠 숫자. 코드 문자열을 잘라 쓰지 않고 "2번 통로 전체" 같은 조회를 할 수 있게 |
| `is_active` | 파손된 선반 등 사용 중지. 삭제하면 과거 재고 이력이 참조를 잃는다 |

`shelf_level`이라 쓴 이유: `level`은 DB에 따라 예약어와 겹칠 수 있다.

### 3.4 `product` — 품목

| 컬럼 | 왜 필요한가 |
|---|---|
| `pallet_qty` | 이 품목을 **한 칸(팔레트 1장)에 최대 몇 개** 올릴 수 있는지. 칸 크기는 같아도 품목마다 들어가는 수가 달라서(생수 60박스, 컵라면 40박스) 칸이 아니라 품목에 둔다. 적치 때 칸 합계가 이 값을 넘으면 옆 칸으로 나눈다 |
| `product_code` (UQ) | `SKU-10001`. 모든 요청이 이 코드로 품목을 가리킨다. 분류·규격을 코드에 넣지 않는 이유: 바뀔 수 있는데 코드는 못 바꾼다 |
| `product_name`, `spec` | "생수", "500ml×20". 규격이 다르면 다른 품목이다 |
| `unit` | `EA`/`BOX`. 이 품목의 모든 수량은 이 단위로 센다. 환산하지 않는다 |
| `is_expiry_managed` | 종이컵처럼 소비기한이 없는 품목. `N`이면 소비기한을 `9999-12-31`로 저장해서 **한 테이블·한 로직**으로 처리하고, FEFO 정렬에서 저절로 맨 뒤로 간다 |
| `min_ship_days` | **출고허용 잔여일.** 기한이 이만큼도 안 남은 재고는 할당하지 않는다. 품목마다 달라서(생수 60, 비타민 180) 품목에 둔다 |
| `safety_stock` | 안전재고 미달 경고(2차). 지금 컬럼을 넣어 두면 나중에 마이그레이션이 필요 없다 |
| `is_active` | 단종 품목. 삭제하면 과거 문서가 참조를 잃는다 |

### 3.5 `users` — 사용자

| 컬럼 | 왜 필요한가 |
|---|---|
| `username` (UQ), `password` | 로그인. 비밀번호는 BCrypt 해시(평문 금지) |
| `name` | 화면 표시, 이력의 처리자 |
| `role` | `ADMIN`/`WORKER`. 작업자는 피킹·재고 조회만 |
| `is_active` | 퇴사자 비활성. 이력에 남은 처리자 기록을 보존 |

테이블명이 복수형인 이유: `user`는 MySQL 키워드와 겹친다(팀 규칙의 예약어 예외).

### 3.6 `purchase_order` — 발주 (= 입고예정)

| 컬럼 | 왜 필요한가 |
|---|---|
| `po_no` (UQ) | `PO-20260919-001`. 사람이 부르는 문서 번호 |
| `supplier_name` | 어디서 오는 물건인지. **거래처 테이블을 따로 만들지 않고 텍스트로** — 화주 도입 후에는 공급처가 화주의 거래처라 창고가 관리하지 않는다 |
| `expected_date` | 도착 예정일. 오늘 들어올 발주 조회 |
| `status` | `REGISTERED → INSPECTING → PUTAWAY → COMPLETED` (+`CANCELED`). 단계마다 할 수 있는 요청이 다르다 |
| `completed_at` | 입고확정 시각. 재고가 생긴 순간 |

### 3.7 `purchase_order_item` — 발주 품목

| 컬럼 | 왜 필요한가 |
|---|---|
| `purchase_order_id`, `product_id` (FK) | 어느 발주의 어느 품목. `(purchase_order_id, product_id)` UNIQUE — 한 발주에 같은 품목 두 줄 금지 |
| `expected_qty` | 오기로 한 수량. 검수 합계와 비교하는 기준 (CHECK > 0) |
| `variance_reason` | 실제가 예정보다 적을 때 이유 (`NOT_ARRIVED` 등). 차이는 **줄 단위**로 생기므로 여기에 둔다 |

### 3.8 `inspection` — 검수 결과 (품목 1줄 × 소비기한 1행)

| 컬럼 | 왜 필요한가 |
|---|---|
| `purchase_order_item_id` (FK) | 어느 품목 줄의 검수인지 |
| `expiry_date` | **한 품목이 소비기한 두 종류로 섞여 올 수 있어서** 품목 줄 아래에 행을 나눈다. `(item, expiry_date)` UNIQUE |
| `good_qty` | 정상수량. 이것만 재고가 된다 |
| `reject_qty`, `reject_reason` | 파손·기한부족 수량과 이유. 재고는 안 되지만 기록은 남긴다 (공급처 클레임 근거) |

발주 품목에 수량 컬럼 하나로 두지 않은 이유: 그러면 "생수 100개 중 60개는 3월 기한, 35개는 1월 기한"을 표현할 수 없다.

### 3.9 `putaway` — 적치 지정

| 컬럼 | 왜 필요한가 |
|---|---|
| `inspection_id` (FK) | 어느 검수 결과(= 어느 소비기한의 정상품)를 |
| `location_id` (FK) | 어느 칸에 |
| `qty` | 몇 개. 검수 행 하나를 여러 칸에 나눌 수 있다. 입고확정 때 `Σqty = good_qty`를 검사한다 |

재고를 바로 만들지 않고 이 테이블을 둔 이유: 기획서 흐름(검수 → 적치 지정 → 입고확정)대로 **확정 전에는 재고가 움직이지 않게** 하려고. 확정 버튼을 누를 때 이 행들을 읽어 재고를 만든다.

### 3.10 `stock` — 재고

| 컬럼 | 왜 필요한가 |
|---|---|
| `product_id`, `location_id`, `expiry_date` | 재고 한 행을 구분하는 세 가지. `UNIQUE(product_id, location_id, expiry_date)` — 같은 칸·같은 기한이 또 들어오면 **새 행이 아니라 합산** |
| `on_hand_qty` | 실물재고. 칸에 실제로 있는 수량 |
| `allocated_qty` | 선점재고. 출고하기로 잡아 둔 수량 (아직 칸에 있음) |
| `available_qty` | 가용 = 실물 − 선점. **생성 컬럼**이라 DB가 계산한다. 직접 쓰면 셋이 어긋날 수 있어서. FEFO 조회 조건(`> 0`)에 쓴다 |
| CHECK `0 ≤ 선점 ≤ 실물` | 코드에 버그가 있어도 **DB가 음수 재고와 초과 선점을 막는 최후 방어선** |
| INDEX `(product_id, expiry_date)` | FEFO 조회(품목 같고 기한 빠른 순)를 빠르게 |

수량이 0이 된 행도 지우지 않는다: 이력과 할당이 이 행을 참조한다.

### 3.11 `stock_history` — 재고 이력

| 컬럼 | 왜 필요한가 |
|---|---|
| `stock_id` (FK) | 어느 재고 행이 바뀌었는지. **FK는 이것 하나** |
| `product_id`, `location_id`, `expiry_date` | 복사값(FK 없음). "생수 이력"처럼 조인 없이 필터하려고 |
| `tx_type` | `INBOUND`/`ALLOCATE`/`DEALLOCATE`/`SHORTAGE`/`OUTBOUND`/`ADJUST` — 왜 바뀌었는지 |
| `on_hand_delta`, `allocated_delta` | 얼마나 바뀌었는지. 이 두 값의 합계가 현재 재고와 같아야 한다(불변식) |
| `on_hand_after`, `allocated_after` | 바뀐 직후 수량. 이력만 보고도 그 시점 재고를 알 수 있다 |
| `ref_type`, `ref_id` | 근거 문서 (발주 3번, 출고지시 1번). **FK를 걸지 않는다**: 재고 → 입고·출고 방향 참조가 생기면 도메인끼리 순환하므로 값으로만 |
| `reason`, `created_by` | 조정·결품 사유, 처리자 |

`updated_at`이 없는 이유: 추가만 하고 절대 수정하지 않는 테이블이다.

### 3.12 `orders` — 주문

| 컬럼 | 왜 필요한가 |
|---|---|
| `order_no` (UQ) | `ORD-20260917-001` |
| `ship_to_name`, `ship_to_address`, `ship_to_phone` | 배송지. 거래처 테이블 대신 **주문에 직접** — 출고명세서에 찍히는 값이고, 주문마다 배송지가 다를 수 있다 |
| `requested_date` | 출고 요청일. 오늘 나갈 주문 조회 |
| `status` | `RECEIVED → ASSIGNED → SHIPPED` (+`CANCELED`) |
| `delivery_order_id` (FK, NULL 허용) | 어느 출고지시에 묶였는지. 접수 상태면 NULL. **주문 → 출고지시 한 방향**이라 출고지시는 주문을 참조하지 않는다 |

테이블명이 복수형인 이유: `ORDER`는 SQL 예약어(`ORDER BY`).

### 3.13 `order_item` — 주문 품목

| 컬럼 | 왜 필요한가 |
|---|---|
| `order_id`, `product_id` (FK) | `(order_id, product_id)` UNIQUE |
| `qty` | 주문수량 (CHECK > 0). 출고지시 품목 합계의 재료 |

### 3.14 `delivery_order` — 출고지시

| 컬럼 | 왜 필요한가 |
|---|---|
| `do_no` (UQ) | `DO-20260917-001` |
| `status` | `CREATED → ALLOCATED → PICKING → PICKED → SHIPPED` (+`CANCELED`). 할당·피킹·확정은 전부 이 단위로 한다 |
| `allocated_at`, `shipped_at` | 선점된 시각, 실물이 빠진 시각 |

주문과 따로 둔 이유: 창고는 주문 하나하나가 아니라 **여러 주문을 묶어** 한 번에 집는다(기획서 5번). 같은 품목을 두 주문이 요청하면 한 번에 50개를 집는다.

### 3.15 `delivery_order_item` — 출고지시 품목

| 컬럼 | 왜 필요한가 |
|---|---|
| `delivery_order_id`, `product_id` (FK) | `(delivery_order_id, product_id)` UNIQUE — 품목당 한 줄 |
| `required_qty` | 묶인 주문들의 품목별 **합계** (생수 30 + 20 = 50). FEFO 할당이 채워야 할 수량 |
| `allocated_qty` | 실제로 잡은 수량 (전부 아니면 0) |
| `shipped_qty` | 실제로 나간 수량. 부분출고(2차)에서 `required`와 달라진다 |

### 3.16 `allocation` — 할당 겸 피킹 항목

| 컬럼 | 왜 필요한가 |
|---|---|
| `delivery_order_item_id` (FK) | 어느 품목 합계를 채우는 할당인지 |
| `stock_id` (FK) | 어느 재고 행에서 잡았는지. 로케이션·소비기한은 `stock` 조인으로 (복사하지 않음: 같은 정보로 가는 길을 하나로) |
| `allocated_qty` | 이 재고 행에서 잡은 수량. 한 품목이 여러 칸에서 잡히면 행이 여러 개 (분할할당) |
| `pick_seq` | 피킹 순번. 피킹 시작 때 **로케이션 코드 순**으로 매긴다 (할당은 기한 순, 동선은 칸 순) |
| `picked_qty` | 작업자가 실제로 집은 수량. 입력 전 NULL |
| `short_qty`, `short_reason` | 결품 (2차). 지금 넣어 두면 나중에 컬럼 추가가 없다 |
| `status` | `WAITING`(대기) → `PICKED`(완료) / `SHORT`(결품) — 기획서 7번의 "대기 → 완료 / 결품" 그대로 |

할당과 피킹 항목을 한 테이블로 합친 이유: 할당 1행이 곧 "이 칸에서 몇 개 집어라" 한 줄이라 1:1이다. 나누면 조인만 늘어난다.

## 4. 로케이션·구역 크기와 구역을 나누지 않는 이유

**물리 크기 (시연용 가정, 소형 상온 물류센터 규모)**

| 단위 | 크기 | 개수 |
|---|---|---|
| 로케이션 1칸 | 팔레트 랙 한 칸 = **표준 팔레트(1100×1100mm) 1장**. 적재 높이 약 1.4m, 하중 1톤 이내 | — |
| 베이 1개 | 랙 기둥 사이 한 칸을 위아래 3단으로 | 팔레트 3장 |
| 통로 1개 | 베이 10개가 한 줄 (길이 약 13m) | 팔레트 30장 |
| 구역 1개 | 통로 4개 (약 15m × 20m, 300㎡ ≈ 90평) | **팔레트 120장** |
| 창고 | 구역 3개 + 입출고장 (약 1,000㎡ ≈ 300평) | **팔레트 360장** |

**한 칸에 몇 개 들어가나**: 품목마다 다르므로 품목의 `pallet_qty`(팔레트 적재수량)로 정한다. 생수 60박스, 컵라면 40박스(부피 큼), 참치캔 100박스(작고 무거움), 종합비타민 2,000개 같은 식이다. 생수로만 A구역을 채우면 120칸 × 60 = 7,200박스.

**적치 규칙 (2주차 ST-023에서 구현, 주말에는 검사하지 않음)**

| 규칙 | 이유 |
|---|---|
| 한 칸에는 **한 품목, 한 소비기한**만 | 작업자가 같은 팔레트에서 기한을 구분해 집을 수 없다. 같은 품목·같은 기한이면 합산 가능 |
| 한 칸의 실물 합계 ≤ 그 품목의 `pallet_qty` | 넘치는 수량은 옆 칸으로 나눠 적치 (검수 행 하나를 여러 칸에 지정하는 이유) |
| 화주 도입 후: 한 칸에는 **한 화주**의 물건만 | 3PL에서 화주 물건이 섞이면 오출고가 난다 |

**구역은 화주별·품목별로 나누지 않는다 [결정]**

- 구역 이름(상온 A/B/C)은 표시일 뿐이고 **적치를 제한하지 않는다**. 어느 품목이든, 화주 도입 후에는 어느 화주든 **빈 칸이면 어느 구역에나** 적치한다.
- 이유: 화주·품목마다 구역을 고정하면, C구역 화주는 입고가 적어 칸이 비고 A구역 화주는 입고가 많아 칸이 모자라는 일이 생긴다. 빈 칸이 있는데도 입고를 못 받는 건 손해다.
- 대신 섞임은 **칸 단위 규칙**(위 표)으로 막는다.
- 기각한 대안: 화주 전용 구역 — 화주별 재고 실사와 보안이 쉬워지지만, 칸 활용률이 떨어진다. 결정로그 D-12로 남긴다.

## 5. 문서와 상태 전이

### 5.1 테이블은 세 종류다

| 종류 | 테이블 | 상태 컬럼 | 특징 |
|---|---|---|---|
| **기준정보** | `warehouse`, `zone`, `location`, `product`, `users` | 없음 (`is_active`만) | 한 번 만들고 계속 참조한다. 단계가 없다 |
| **문서** | 발주, 주문, 출고지시 (각각 머리 + 품목) | **머리에 `status`** | 업무 한 건. 정해진 단계를 밟는다 |
| **재고·기록** | `stock`, `stock_history` | 없음 | 재고는 **수량**(실물·선점·가용)만, 이력은 추가만 한다 |

"문서"는 파일이 아니라 **DB의 머리 행 1개 + 품목 행 N개**다. 종이 발주서의 윗부분(번호·공급처·날짜·상태)이 `purchase_order` 한 행, 아랫부분(품목 줄)이 `purchase_order_item` 여러 행이다. 상태 전이는 머리 행의 `status` 값을 UPDATE하는 것이다.

### 5.2 상태는 어디에 붙이나

**상품(재고)에는 상태가 없다.** 상태는 문서에 붙고, 문서 여러 건이 동시에 각자의 단계를 밟는다. 출고지시가 피킹 중일 때 새 발주가 입고확정되어도 서로 영향이 없다. 늘어난 가용재고는 **다음에 할당하는 출고지시**가 쓴다.

품목 줄에도 상태를 줄지는 이 기준으로 정한다.

| 그 줄이 따로 진행되는가? | 처리 | 예 |
|---|---|---|
| 예 | 줄에 상태를 준다 | `allocation`: 칸마다 따로 피킹되므로 `WAITING` / `PICKED` / `SHORT` |
| 아니요 | 줄은 수량으로 진행 정도를 보고, 상태는 머리에만 | 발주 품목: 예정 100 / 정상 95 |

### 5.3 상태와 행동을 나눈다

| | 무엇 | 어디에 |
|---|---|---|
| 상태 | 지금 어떤 단계인가 (`ALLOCATED`) | DB `status` 컬럼, Java enum |
| 행동 | 무엇을 하려는가 (할당, 취소, 확정) | API URL, 엔티티 메서드 |
| 전이 규칙 | 이 상태에서 이 행동이 되는가, 되면 어디로 가는가 | enum의 `nextStates()` + 엔티티의 `transitionTo()` |
| 부수 효과 | 행동할 때 함께 일어나는 일 (선점, 재고 생성) | 서비스 |

- **상태를 직접 바꾸는 API(`PATCH …/status`)는 만들지 않는다.** 단계를 건너뛸 수 있고, 재고 차감 같은 부수 효과가 빠진다. 행동마다 API를 따로 둔다(`/allocate`, `/start-picking`, `/confirm-shipment`).
- **엔티티의 상태 변경은 `transitionTo()` 한 곳으로만 한다.** `@Setter`를 금지하는 이유다.
- **서비스는 상태 검사를 먼저, 부수 효과를 나중에 한다.** 부수 효과가 실패하면 트랜잭션이 롤백되어 상태 변경도 취소된다.

```java
public enum DeliveryOrderStatus {
    CREATED, ALLOCATED, PICKING, PICKED, SHIPPED, CANCELED;

    public Set<DeliveryOrderStatus> nextStates() {
        return switch (this) {                       // 값이 추가되면 여기가 컴파일 에러 → 표 누락 방지
            case CREATED   -> EnumSet.of(ALLOCATED, CANCELED);
            case ALLOCATED -> EnumSet.of(PICKING, CANCELED);
            case PICKING   -> EnumSet.of(PICKED);
            case PICKED    -> EnumSet.of(SHIPPED);
            case SHIPPED, CANCELED -> EnumSet.noneOf(DeliveryOrderStatus.class);
        };
    }
    public boolean canMoveTo(DeliveryOrderStatus next) { return nextStates().contains(next); }
}

// 엔티티
public void allocate() { transitionTo(ALLOCATED); this.allocatedAt = LocalDateTime.now(); }
public void cancel()   { transitionTo(CANCELED); }
private void transitionTo(DeliveryOrderStatus next) {
    if (!status.canMoveTo(next)) throw new BusinessException(ErrorCode.DO_001);  // 409
    this.status = next;
}
```

### 5.4 한 행동이 여러 문서의 상태를 바꾸는 경우

서비스가 조율한다.

| 행동 | 직접 바뀌는 상태 | 함께 바뀌는 상태 |
|---|---|---|
| 출고지시 생성 | 출고지시 `CREATED` | 묶인 주문 `RECEIVED → ASSIGNED` |
| 마지막 피킹 항목 완료 | 할당 항목 `WAITING → PICKED` | 모든 항목이 끝나면 출고지시 `PICKING → PICKED` |
| 출고확정 | 출고지시 `SHIPPED` | 묶인 주문 `SHIPPED` |
| 출고지시 취소 | 출고지시 `CANCELED` | 묶인 주문 `ASSIGNED → RECEIVED` |

### 5.5 왜 enum인가

| 다른 방식 | 문제 |
|---|---|
| 문자열 | 오타(`"SHIPED"`)가 실행해 봐야 드러난다 |
| 숫자 코드 | 3이 무슨 상태인지 코드로 알 수 없고, 순서가 바뀌면 데이터 의미가 바뀐다 |
| boolean 여러 개 (`isAllocated`, `isShipped`…) | "출고됐는데 할당 안 됨" 같은 **불가능한 조합**이 생긴다 |
| DB 상태 코드 테이블 | 상태마다 코드 로직이 필요해서 DB에만 추가해도 의미가 없다 |

enum은 정해진 값만 허용하고, 전이 표를 한 파일에 모으고, 값을 추가하면 컴파일러가 빠진 곳을 알려준다. DB에는 `EnumType.STRING`으로 저장해 읽을 수 있게 한다. 단점: 이름을 바꾸면 저장된 값도 마이그레이션해야 하므로 용어사전에서 먼저 확정한다.

### 5.6 인쇄물은 저장하지 않는다

입고검수서·피킹리스트·출고명세서는 요청할 때마다 DB 행을 읽어 HTML로 만든다. 원본은 DB 한 곳이라 언제 뽑아도 현재 데이터와 일치한다. "발행 당시 원본 보관"이 필요해지면(거래 증빙) 그때 파일로 저장한다.

### 5.7 결정 대기

| 항목 | 선택지 | 제안 |
|---|---|---|
| 문서 상태의 동시 변경 (관리자 둘이 같은 발주를 동시에 입고확정 → 재고 2번 생성) | `@Version` 낙관적 락 / 비관적 락 / 조건부 UPDATE | 문서 머리와 `allocation`에 `version` 컬럼 + `@Version`. 재고 수량 경쟁은 비관적 락·조건부 UPDATE로 따로 비교 |
| 분할입고 (발주 100 중 60만 오늘 도착) | A. 60만 받고 차이사유로 종결, 40은 새 발주 / B. 발주 아래 "입고 건"(`receipt`) 테이블, 발주 상태 `PARTIALLY_RECEIVED` 추가 | 주말은 A, B는 2차 스토리 |

# 수집기 20 - 공공데이터포털 API 붙이기

> 허브: [[수집기 프로젝트 MOC]]

국내 채용 사이트 크롤링이 전부 막힌 뒤, 공공데이터포털의 「공공기관 채용정보 조회서비스」(기획재정부, 우리 이름 `moef`)를 첫 진짜 소스로 붙인 기록이다. 키 발급부터 응답 구조 관측까지.

## 1. 배운 내용

### 1-1. 이름이 비슷하다고 같은 데이터가 아니다

처음 받은 키는 「알리오 플러스 API」였다. 문서를 열어보니 제공 항목이 **시설·행사·기관·사업** 넷이고 채용이 없었다. 공공기관 시설을 국민에게 개방하는 정보다.

「알리오」라는 이름만 보고 채용정보일 거라 가정했다. 「수집기 13」의 확인 순서에서 명세(5번)를 건너뛴 것이고, 그 순서 맨 앞에 한 줄이 더 붙는다.

> **0. 이 API가 내가 원하는 데이터를 주는가.** 서비스 이름이 아니라 응답 항목으로 확인한다.

같은 기관이 API를 여러 개 내는 것이 보통이고, 이름은 겹친다.

### 1-2. 인증키가 두 형태다

공공데이터포털은 같은 키를 두 칸으로 보여준다.

| | 생김새 | 언제 |
| --- | --- | --- |
| **Encoding** | `%2B` `%2F` `%3D` — `%`가 보인다 | 주소에 **그대로** 붙일 때 |
| **Decoding** | `+` `/` `=` — `%`가 없다 | 코드가 `urlencode`로 인코딩할 때 |

틀리면 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`(403)가 뜬다. **권한 문제처럼 읽히지만 키가 깨진 것**이다. Encoding 키를 `urlencode`에 넣으면 `%2B`가 `%252B`로 한 번 더 인코딩되어 서버가 다른 문자열로 받는다.

세 번 헤맸다. 처음엔 다른 서비스 키였고, 다음엔 주소가 맞았는데 Decoding 키였고, `.env`로 옮기면서 또 Decoding 키를 넣었다. 94자에 `%`가 있으면 Encoding, 71자에 `%`가 없으면 Decoding — 길이 차이가 정확히 `%2B`(3글자)가 `+`(1글자)로 풀린 만큼이다.

### 1-3. 키를 노출하지 않고 형태만 확인한다

```python
print(f"길이 {len(KEY)} | %포함 {'%' in KEY} | +포함 {'+' in KEY}")
```

값을 찍지 않고 **성질만** 찍는다. 이 한 줄이 "어느 키를 넣었나"를 즉시 갈라준다. 로그나 대화에 키를 남기지 않는 습관의 한 형태다.

### 1-4. 미리보기가 되는데 코드가 안 되면 키 형식이다

포털의 「미리보기」 버튼은 브라우저 주소창으로 호출하므로 Encoding 키를 쓴다. 그것이 되고 우리 코드가 안 되면 **승인도 주소도 정상이고 남은 건 코드 쪽 키 처리뿐**이다. 진단 범위를 한 번에 좁혀주는 확인이다.

### 1-5. 에러 응답도 본문을 읽어야 한다

```python
except urllib.error.HTTPError as e:
    print(e.code, e.read().decode("utf-8"))
```

`urlopen`은 4xx·5xx에서 예외를 던지는데, 그 예외 객체가 응답 본문을 갖고 있다. 고용24는 200에 에러 메시지를 실어 보냈고 공공데이터포털은 상태 코드로 보낸다. **어느 쪽이든 본문을 안 읽으면 왜 막혔는지 알 수 없다.**

### 1-6. 200에 빈 배열은 실패가 아니다

```json
{"resultCode":200, "resultMsg":"성공했습니다.", "totalCount":0, "result":[]}
```

미리보기 예시값이 「2023년에 시작했고 지금 진행 중인, 대구의, 보건의료 공고, 4페이지」였다. 0건이 당연하다. 조건에 맞는 것이 없다는 것은 정상 응답이고, 「수집기 04」의 「정상적인 무변화를 실패로 만들지 않는다」가 API 층에서 그대로 적용된다. 어댑터에서 빈 배열에 예외를 던지면 안 된다.

### 1-7. 주소는 인자로 받는다

```python
python collector/peek_api.py "https://apis.data.go.kr/..."
```

`sys.argv[1]`로 주소를 받으면 파일을 안 고치고 여러 주소를 시험할 수 있다. 조사 단계처럼 주소가 계속 바뀔 때 맞는 형태다. `argv[0]`은 스크립트 이름이고 `[1]`부터 인자다. PowerShell에서는 `&`가 섞인 주소를 따옴표로 감싸야 한다.

### 1-8. 명세의 두 조각 — End Point와 상세기능

포털 화면의 `End Point`(`.../1051000/recruitment`)와 Swagger의 `GET /list`를 이어붙인 것이 실제 주소다. 요청 파라미터 표에서 확인한 것들:

| 파라미터 | 용도 |
| --- | --- |
| `resultType=json` | 기본값이 json이라지만 **기본값은 바뀔 수 있다.** 명시한다 |
| `ongoingYn=Y` | 진행 중 공고만 |
| `pbancBgngYmd` / `pbancEndYmd` | 날짜 범위 — 증분 수집에 쓸 수 있다 |
| `ncsCdLst` | NCS 직무 코드. 여러 개는 쉼표로 |
| `numOfRows` / `pageNo` | 페이징 |

### 1-9. 목록 응답에 상세가 거의 다 들어 있다

`/list`와 `/detail`이 나뉘어 있어 「목록에서 sn을 모으고 새 것만 상세 호출」하는 2단계를 설계했는데, 목록 응답에 이미 `aplyQlfcCn`(지원자격)·`prefCn`(우대)·`scrnprcdrMthdExpln`(전형방법)·`disqlfcRsn`(결격사유)이 들어 있었다. 상세가 더 주는 것은 첨부파일과 전형단계(경쟁률, 진행 중엔 비어 있음)뿐이다.

| | 예상 | 실제 |
| --- | --- | --- |
| 구조 | 목록 → 상세 2단계 | **목록 한 번** |
| 공고 100건당 요청 | 101회 | 1회 |

설계가 통째로 불필요해졌고, 좋은 쪽으로 틀렸다. 명세를 읽고 세운 설계보다 응답 하나를 뜯어본 관측이 더 정확했다.

### 1-10. 응답 필드가 3·4단계 재료다

| 필드 | 쓸 곳 |
| --- | --- |
| `recrutPblntSn` | id → `moef:303962` |
| `instNm` · `recrutPbancTtl` | 기관 · 제목 |
| **`aplyQlfcCn`** | **지원자격 전문** |
| **`prefCn`** | **우대사항 전문** |
| `ncsCdNmLst` · `hireTypeNmLst` · `workRgnNmLst` | 직무·고용형태·지역 (코드와 이름 둘 다 온다) |
| `pbancBgngYmd` · `pbancEndYmd` | 공고 기간 |
| `srcUrl` | 원문 |

"제목·회사만 저장하지 말고 자격요건·우대사항을 통째로 저장하라"던 초기 조언이 정확히 이 두 필드를 가리킨 것이었다. 담당자 개인정보 전용 필드는 없다. 다만 본문 텍스트에 기관 대표 이메일이 섞여 온다.

## 2. 관측 결과

### 2-1. NCS 분류는 단일 값이 아니라 쉼표 목록이다

```
전기.전자,정보통신
사업관리,경영.회계.사무,보건.의료,영업판매,정보통신
```

한 공고에 분류가 여러 개 붙는다. `WHERE ncs = '정보통신'`은 8건뿐이고 `LIKE '%정보통신%'`이어야 36건이 잡힌다. 명세서로는 알 수 없는 사실이었다.

### 2-2. 서버 필터를 걸지 않은 결정이 숫자로 검증됐다

`ncsCdLst=R600020`(정보통신)으로 서버에서 좁혔다면 8건을 받았을 것이다. 실제 개발 관련 공고는 보건.의료(병원 전산행정), 연구(데이터시스템 고도화), 경영.회계.사무(IT전산 채용)에 흩어져 있었다. **놓쳤을 공고가 잡았을 공고보다 많다.** #되돌릴수있는가 → [[개념 - 되돌릴 수 있는 결정과 없는 결정]]

전체 518건 중 보건.의료가 224건이다. 공공기관 = 병원이 다수다.

### 2-3. 키워드 필터의 거짓 양성

`title LIKE '%개발%'`에 「한국장애인개발원 청년인턴」「청소년상담복지개발원 인턴」이 걸렸다. **기관 이름에 "개발원"이 들어간다.** 단순 키워드 매칭은 이런 식으로 틀리고, 3단계 키워드 통계를 만들 때 미리 알아둘 함정이다. `LIKE '%정보통신%'`만으로는 한전KDN 배전 일용직이 섞이고, 제목 키워드만으로는 개발원이 걸린다 — **분류와 키워드를 조합해야 한다.**

### 2-4. 개발자 공고는 적고 섞여 있다

36건을 뜯으면 진짜 개발·IT 직무 8~10건, IT 직렬을 포함한 종합 공채, 태그만 정보통신인 현장직으로 갈린다. 예상대로다 — 이 소스의 역할은 좋은 데이터가 아니라 **진짜 외부 소스가 붙은 배관을 검증하는 것**이었고, 개발자 공고의 본체는 사람인 API다. 공공 IT직렬과 연구직(AI·데이터) 공고를 계속 물어다 주는 보조 소스로 남는다.

### 2-5. 재공고가 첫날 바로 나타났다

```
계약직 연구원(데이터기반정책연구팀) 재공고          ← 제목에 명시
한국스포츠과학원 초빙연구원(나급) ... × 2건 (다른 sn)
```

설계 변경 기록 첫 항목의 관측 대상이다. 원문을 보존하고 있으니 소급 판정이 가능하다. 예정대로 쌓아두고 본다.

### 2-6. 링크의 수명은 공고의 수명보다 짧다

생성된 노트의 `원문` 링크를 눌렀더니 403 Forbidden이었다. `srcUrl`이 특정 공고가 아니라 채용 사이트 대문만 적혀 있었고 그 대문이 외부 접근을 막고 있었다. 기관마다 이 필드의 성실도가 다르다.

링크만 저장하는 수집기는 시간이 지나면 빈 껍데기가 된다. 본문을 통째로 담아둔 것이 방어선이다.

# WMS - 1GB 서버에 맞춘 배포 구조

> 허브: [[WMS 프로젝트 MOC]]

## 1. 배운 내용

### 1-1. 스펙이 계획을 바꿨다

Oracle을 쓸 때는 12GB를 예상했는데 AWS t3.micro는 **1GB**다. MySQL과 Spring Boot를 한 서버에 올리기엔 빡빡하다.

이 제약이 아래 결정들을 전부 끌고 갔다.

### 1-2. 스왑 2GB를 먼저 잡았다

스왑은 메모리가 부족할 때 디스크를 메모리처럼 쓰는 공간이다. 느리지만, 없으면 메모리가 꽉 찰 때 리눅스가 프로세스를 강제로 죽인다(OOM Killer). 1GB 서버에서는 안전장치가 아니라 필수다.

```bash
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

- `chmod 600` — 스왑에는 메모리 내용이 그대로 들어가서 아무나 읽으면 안 된다
- `/etc/fstab`에 줄을 추가하는 이유는 **재부팅 후에도 스왑이 자동으로 켜지게** 하기 위해서다. 이게 없으면 재부팅 한 번에 사라진다

### 1-3. 서버에서 빌드하지 않기로 했다

처음엔 "서버에서 빌드하면 아키텍처 문제가 없다"고 봤는데, 전제가 틀렸다.

**JAR 파일은 CPU 아키텍처와 무관하다.** 자바 바이트코드라 x86이든 ARM이든 같은 JAR이 돈다. 아키텍처 때문에 서버에서 빌드할 이유가 없었다.

(아키텍처에 종속되는 건 도커 **이미지**다. JAR 자체가 아니다.)

그러면 1GB 서버에서 Maven을 돌릴 이유가 없다. **로컬에서 빌드해서 결과물만 올린다.**

| 구성 | 방식 |
| --- | --- |
| MySQL | 서버에서 Docker |
| 백엔드 | 로컬에서 빌드한 JAR을 전송 → 서버에서 실행 |
| 프론트 | 로컬에서 빌드한 정적 파일 전송 → nginx가 서빙 |
| nginx | 정적 파일 + `/api` 프록시 |

설정 파일(compose, nginx)은 리포에 넣고 서버에서 `git clone` 한다. 빌드 결과물만 따로 올린다.

### 1-4. nginx가 Vite 프록시의 역할을 이어받는다

이게 이 구조의 핵심이다.

```
개발  →  localhost:5173 (Vite)
           ├ /       → React를 즉석 변환해서 전달
           └ /api/*  → localhost:8080 (Spring)

배포  →  서버:443 (nginx)
           ├ /       → 미리 빌드한 dist/ 파일
           └ /api/*  → localhost:8080 (Spring)
```

**모양이 같다.** 그래서 프론트 코드의 `fetch('/api/ping')`을 배포할 때 한 글자도 고치지 않는다. 처음부터 절대경로(`http://localhost:8080/...`)가 아니라 상대경로로 쓴 이유가 이것이다.

브라우저 입장에서는 출처가 하나뿐이라 **CORS 상황이 아예 발생하지 않는다.**

### 1-5. Spring 혼자 다 하면 안 되나

가능하다. Spring Boot의 `static` 폴더에 빌드 결과를 넣으면 화면도 API도 Spring이 다 준다. 그런데도 nginx를 두기로 한 이유가 셋 있다.

1. **HTTPS 인증서를 nginx가 맡는다.** Let's Encrypt 연동이 nginx 기준으로 표준화돼 있어 자료가 압도적으로 많다
2. **정적 파일은 nginx가 훨씬 가볍다.** 1GB 서버에서 JVM에 그 일까지 시킬 이유가 없다
3. **백엔드를 재시작해도 화면은 계속 뜬다.** 배포 중에 사이트가 완전히 죽지 않는다

### 1-6. 서버용 compose를 따로 둔 이유

로컬용과 목적이 달라서 파일을 나눴다. 다른 점 네 가지.

| 항목 | 로컬 | 서버 |
| --- | --- | --- |
| `restart` | 없음 | `always` (재부팅 시 자동 기동) |
| 비밀번호 | 파일에 직접 | `.env`에서 읽음 (커밋 금지) |
| 포트 바인딩 | `3307:3306` | `127.0.0.1:3306:3306` |
| 버퍼 풀 | 512MB | 128MB |

**포트 바인딩 앞에 `127.0.0.1:`을 붙이는 게 가장 중요하다.** 이걸 빼면 인터넷 전체에 DB가 열려서 몇 분 안에 봇들이 로그인을 시도한다. 붙이면 서버 안에서만 접속할 수 있다.

버퍼 풀을 128MB로 낮춘 건 아쉽지만, **여기서 잰 숫자는 측정에 쓰지 않으므로** 문제되지 않는다. 측정은 로컬 도커에서 하고, 서버는 "돌아가는 걸 보여주는" 역할만 한다.

## 2. 추가로 알면 좋은 활용법

### 2-1. 측정과 배포를 나눈 것이 여기서 값을 한다

"측정은 로컬, 배포는 시연용"이라는 분리를 앞에서 정해뒀는데, 서버가 1GB로 줄면서 그 판단이 옳았던 게 드러났다.

만약 서버에서 측정하기로 했다면 지금 스펙을 올려야 했고, 크레딧이 훨씬 빨리 닳았을 것이다.

README에는 **측정 환경을 명시**한다 — "Docker 환경(로컬), MySQL 8.0, 버퍼 풀 512MB 기준". 조건을 적어두면 숫자가 정직해진다.

### 2-2. Docker 그룹 추가에서 조심할 것

```bash
sudo usermod -aG docker $USER
```

`-a`(append)가 빠지면 **기존 그룹이 전부 날아가고** docker 그룹만 남는다. `sudo` 권한을 잃어서 서버가 반쯤 잠기는 흔한 사고다. `-aG`인지 확인하는 습관이 필요하다.

그룹 변경은 **재접속해야 적용된다.**

### 2-3. 자동 배포는 손으로 한 번 성공한 뒤에

먼저 손으로 끝까지 배포해보고, 그 절차를 그대로 GitHub Actions로 옮긴다. 손으로 해보면 어떤 파일을 어디로 어떤 순서로 옮기는지 몸으로 알게 되고, 그게 그대로 워크플로우의 내용이 된다.

## 3. 더 나아가 알면 좋은 것

### 3-1. 다음에 볼 키워드

- systemd 서비스 — JAR을 백그라운드로 돌리고 재부팅 시 자동 시작시키는 방법
- `scp` / `rsync` — 로컬에서 서버로 파일 보내기
- Let's Encrypt와 certbot — 무료 HTTPS 인증서 자동 발급·갱신
- nginx `location` 블록 — 경로별로 다르게 처리하는 문법
- OOM Killer — 메모리가 부족할 때 리눅스가 무엇을 기준으로 프로세스를 죽이는지

### 3-2. 3주차에 확인할 것

`free -h`와 `docker stats`로 서버의 메모리 여유를 보자. 스왑을 실제로 얼마나 쓰고 있는지가 1GB로 버틸 수 있는지의 지표가 된다. 스왑을 계속 많이 쓰고 있으면 t3.small로 올리는 걸 고려해야 한다(크레딧이 두 배로 닳는다).

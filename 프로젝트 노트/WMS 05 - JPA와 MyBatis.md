# WMS - JPA와 MyBatis

> 허브: [[WMS 프로젝트 MOC]]

## 1. 배운 내용

### 1-1. 왜 이 질문을 먼저 했나

요즘은 코드를 AI와 같이 쓰니까 코드 자체보다 **"왜 이렇게 썼는가"** 를 더 본다고 한다. 그래서 기술을 고를 때마다 이유를 알고 들어가기로 했다. JPA를 쓴다면 "왜 MyBatis가 아니라 JPA인가"에 답할 수 있어야 한다.

### 1-2. 두 기술의 성격

**JPA(Hibernate)** — 객체 중심. 자바 객체와 테이블을 매핑해두면 SQL을 대신 만들어준다. 반복적인 CRUD 코드가 사라진다. 대신 **생성되는 SQL이 눈에 보이지 않는다.**

**MyBatis** — SQL을 직접 쓴다. 내가 쓴 쿼리가 그대로 나간다. 복잡한 조인·동적 쿼리·튜닝을 편하게 다룬다. 대신 단순 CRUD도 매번 SQL을 써야 한다.

### 1-3. 국내 상황

- **MyBatis** — 전자정부 표준 프레임워크가 MyBatis 기반이라 국내 SI·금융권에서 전통적으로 지배적이었다. 순수 SQL만 어느 정도 다루면 쓰기 편해서 채택하는 회사가 많다
- **JPA** — 최근 인터넷 서비스 기업과 스타트업을 중심으로 늘고 있다

여기서도 "어느 쪽이 옛날 방식"이 아니라 **분야에 따라 갈린다**는 게 정확한 그림이었다. 국내는 금융·SI 비중이 커서 복잡한 비즈니스 로직이 많고, 그런 곳에서는 SQL 통제권이 큰 MyBatis가 여전히 유리하다.

### 1-4. JPA로 정한 첫 번째 이유 — N+1을 겪으려고

이게 결정적이었다.

이 프로젝트의 산출물은 기능 목록이 아니라 **"성능 문제를 발견하고 해결한 기록"** 이다. 그리고 **N+1은 JPA가 만들어내는 가장 대표적인 성능 문제**다.

MyBatis를 쓰면 내가 쓴 SQL이 그대로 나가니까 N+1이 애초에 잘 생기지 않는다. 즉 최적화 3단계(인덱스 → N+1 제거 → 캐싱) 중 **한 축이 JPA를 써야 성립한다.**

"문제를 만들려고 그 기술을 쓴다"는 게 이상하게 들리지만, 실무에서 JPA가 널리 쓰이고 N+1이 가장 흔한 성능 이슈라는 걸 생각하면 오히려 현실적인 선택이다. 겪어보지 않으면 면접에서 설명할 수 없다.

### 1-5. 두 번째 이유 — 낙관적 락이 `@Version` 한 줄

2주차에 비관적 락과 낙관적 락을 비교해야 한다. JPA는 엔티티에 `@Version` 필드 하나만 붙이면 낙관적 락이 동작한다. MyBatis면 버전 비교와 재시도를 직접 만들어야 한다.

3주 일정에서 이 차이는 작지 않다. → [[WMS 04 - 트랜잭션 격리수준과 재고 정합성]]

### 1-6. 세 번째 이유 — 기준정보 CRUD 분량

품목·창고·구역·위치까지 대여섯 테이블이 단순 CRUD다. 혼자 3주 하는 상황에서 보일러플레이트 절감이 실질적으로 시간을 아껴준다.

### 1-7. 버린 쪽(MyBatis)의 근거는 약하지 않았다

정직하게 말하면 **MyBatis도 충분히 정당한 선택이었다.**

성능 튜닝이 주제인 프로젝트에서 SQL을 완전히 통제하는 건 오히려 맞는 방향이다. 실행계획을 보며 쿼리를 손으로 다듬는 작업이 MyBatis에서 훨씬 자연스럽다. 재고 현황 집계나 피킹 리스트처럼 조인이 섞인 조회는 JPA로 쓰면 지저분해진다.

### 1-8. 그래서 혼용으로 간다

국내에서 흔한 조합이기도 하다. **JPA를 기본으로 하고, 복잡한 조회는 네이티브 쿼리(또는 QueryDSL)로 내린다.** 전면 교체는 하지 않고, 읽기 어려워지는 지점만 골라서 내린다.

## 2. 추가로 알면 좋은 활용법

### 2-1. 3주차에 남겨둔 실험 — 같은 API를 두 방식으로

시간이 남으면 **재고 현황 조회 API 하나만 MyBatis로도 구현해 같은 조건에서 측정한다.**

그러면 "왜 JPA를 썼나"에 실측 근거가 붙는다. 지금은 논리로만 설명하는 것을 숫자로 말할 수 있게 된다.

단, 2주차 체크포인트(입고부터 출고까지 한 바퀴)를 통과하지 못하면 버린다. 전부 두 번 만드는 건 3주 프로젝트에서 범위 확장이고, 범위 확장은 실패의 가장 흔한 원인이다.

### 2-2. JPA를 쓰면서 SQL을 보이게 만들기

JPA의 단점이 "SQL이 안 보인다"는 것인데, 설정으로 보이게 할 수 있다.

```yaml
logging:
  level:
    org.hibernate.SQL: debug
```

**주의**: 측정할 때는 이걸 꺼야 한다. SQL 로깅 자체가 성능에 영향을 줘서 숫자가 왜곡된다.

### 2-3. `open-in-view: false`로 두는 이유

Spring Boot의 기본값은 `true`인데, 이러면 컨트롤러·뷰 계층까지 영속성 컨텍스트가 살아 있어서 **N+1이 조용히 숨는다.** 화면에서는 잘 돌아가는데 어디서 쿼리가 나가는지 안 보인다.

`false`로 두면 서비스 계층을 벗어나는 순간 에러가 나서 문제가 드러난다. 이 프로젝트에서는 문제가 드러나는 편이 이득이다.

### 2-4. 최적화 설정을 미리 넣지 않는다

`default_batch_fetch_size` 같은 설정은 N+1을 크게 완화한다. 편리하지만 **처음부터 넣으면 Before 측정이 불가능해진다.**

3주차 N+1 제거 단계에서 넣고, 넣기 전후를 각각 재서 표에 남긴다.

## 3. 더 나아가 알면 좋은 것

### 3-1. 다음에 볼 키워드

- N+1 문제 — 왜 생기고, `fetch join`·`@EntityGraph`·batch size로 어떻게 푸는지
- 영속성 컨텍스트와 1차 캐시 — JPA가 뒤에서 뭘 하고 있는지
- QueryDSL — 타입 안전한 동적 쿼리. 복잡 조회를 네이티브 SQL 없이 쓰는 방법
- 지연 로딩(LAZY)과 즉시 로딩(EAGER) — N+1의 출발점
- MyBatis 동적 쿼리(`<if>`, `<foreach>`) — 비교 실험을 할 때 필요

### 3-2. 결정을 되돌릴 조건

JPA로 쓴 조회 쿼리가 읽기 어려워지면 그 지점만 네이티브 쿼리로 내린다. 전면 교체는 하지 않는다 — 중간에 영속성 기술을 갈아엎으면 그 커밋이 성능 개선 커밋과 뒤섞여 3주차 diff가 오염된다.

# 수집기 26 - jumpit 어댑터와 2단계 수집

> 허브: [[수집기 프로젝트 MOC]]

점핏(개발자 전문, 사람인 계열)의 문서화되지 않은 내부 API를 두 번째 진짜 소스로 붙인 기록이다. moef에서 설계만 하고 버렸던 **목록/상세 2단계 수집**이 여기서 처음 실전이 됐고, 그 과정에서 어댑터 계약이 처음 확장됐다.

## 1. 배운 내용

### 1-1. Greenhouse를 검토했다가 접은 이유

먼저 ATS 공개 API(Greenhouse)를 봤다. 신청·키 없이 `boards-api.greenhouse.io/v1/boards/<회사>/jobs`가 열리고, 회사 이름만 바꾸면 되는 구조라 매력적이었다. 실제로 당근 공고 30건이 그대로 왔다.

접은 건 **데이터가 목적에 안 맞아서**다 — Greenhouse 쓰는 한국 회사는 글로벌 지향 스타트업이라 영어 공고·시니어 위주였다. 국내 신입·주니어 개발자 공고가 목표라 변두리였다.

> 기술적으로 되는 것과 내 목적에 맞는 것은 다르다. peek로 실제 데이터를 봐야 갈린다.

### 1-2. SPA의 내부 API를 찾았다

점핏은 「수집기 17」에서 SPA로 확인했던 그 사이트다. 화면을 채우는 내부 API를 브라우저 개발자도구 없이 주소 추정으로 두드려 찾았다.

```
목록: jumpit-api.saramin.co.kr/api/positions?page=N
상세: jumpit-api.saramin.co.kr/api/position/{id}
```

로그인도 키도 없이 JSON이 온다. **문서화되지 않은 인터페이스**라 예고 없이 바뀔 수 있다(「수집기 17」 2-2) — 격벽이 있으니 죽어도 그 소스만 죽는다.

### 1-3. 목적에 맞는 필드가 구조화되어 온다

moef는 본문을 키워드로 긁어야 기술 스택이 나왔는데, 점핏은 배열로 준다.

| 필드 | 값어치 |
| --- | --- |
| `techStacks` 배열 | **3단계 통계 재료가 파싱 없이** `["React","TypeScript",...]` |
| `newcomer` | 신입 여부 플래그 |
| `minCareer`/`maxCareer` | 경력 범위 |
| 상세 `qualifications`/`preferredRequirements` | 4단계 재료 (moef의 aplyQlfcCn/prefCn과 같은 자리) |

그리고 **개인정보 필드가 아예 없다.** 「수집기 14」에서 타협 불가로 정한 개인정보 미수집이 이 소스에선 저절로 지켜진다.

### 1-4. 목록에 본문이 없다 → 2단계가 진짜로 필요해졌다

moef는 목록에 본문이 다 있어 상세 호출이 불필요했다. 점핏은 목록에 `techStacks`·기본정보만 있고, `qualifications` 같은 본문은 **상세에만** 있다.

그래서 「수집기 16」에서 설계했다가 moef 때 버린 2단계 수집이 실전이 됐다.

```
목록 순회로 id 수집 → DB에 없는 신규만 상세 호출 → 변환
```

### 1-5. 3층 구조

moef의 `_call` 하나가 여기선 셋으로 나뉘었다.

```python
_get(url)            # 공통 요청 (User-Agent 붙는 곳)
_call_list(page)     # 목록 주소 조립
_call_detail(id)     # 상세 주소 조립
```

`_get`을 뺀 이유 — 목록과 상세가 요청 방식은 같고 주소만 다르다. 공통부를 한 곳에 두면 `User-Agent`나 타임아웃을 한 번만 손대면 된다. 「수집기 21」에서 "바뀌는 이유가 다르면 나눈다"의 연장이다.

### 1-6. `_to_job(item, detail)` — 인자가 둘

한 공고의 정보가 목록과 상세에 **나뉘어 온다.** 합쳐서 우리 형식 하나로 만드는 게 이 함수다.

```python
"begin_at": _to_date(detail.get("publishedAt")),   # 상세에서
"tech_stacks": ", ".join(item.get("techStacks", []) or []),  # 목록에서
"raw": json.dumps({"list": item, "detail": detail}, ...),    # 둘 다
```

`raw`에 **목록·상세를 둘 다** 넣는다. 원문 보존이 반쪽이면 안 되기 때문이다.

배열은 쉼표 문자열로 — `", ".join(techStacks)`. 컬럼에서 `LIKE '%React%'`로 바로 세려는 것이고, 이게 3단계를 moef보다 쉽게 만든다.

### 1-7. peek가 추정을 사실로 바꿨다

어댑터를 짜기 전 `peek_jumpit.py`로 응답 하나를 뜯었다. 추정 셋이 사실로 확정됐다.

| 추정 | 관측 결과 |
| --- | --- |
| 날짜 형식 여러 개일지 모름 | 목록은 `T` 있는 ISO, 상세는 공백 구분 — **둘 다 `[:10]`로 해결** |
| `education` 없을 것 | 상세에 `educationName` 있음 |
| `hire_type` | 점핏은 안 줌 — `""` 확정 |

`_to_date`가 세 갈래 방어에서 `str(value)[:10]` 한 줄로 줄었다. **관측 전이었으면 안 고쳐도 될 방어를 잔뜩 안고 갔을 것이다.** peek 먼저의 값어치다.

## 2. 겪은 일

### 2-1. `list`를 변수명으로 써서 내장을 가렸다

peek에서 `list = _get(...)`로 응답을 받았더니, 뒤에서 `list(detail.keys())`가 `TypeError: 'dict' object is not callable`로 터졌다. **내장 이름 `list`에 dict를 대입해 가려버린(shadowing)** 것이고, 에러는 엉뚱한 줄에 났다.

> 변수명으로 `list`·`dict`·`str`·`id`·`type`을 쓰지 않는다. 전부 파이썬 내장이라 가리면 그 스코프에서 원래 기능을 잃는다.

「수집기 05-1」의 "대문자 상수도 재할당을 막지 않는다"의 더 고약한 판이다 — 이건 내장을 가린다.

### 2-2. `.get` 오타는 조용히 None을 준다

peek에서 `detail.get("pulbishedAt")`(오타)이 안 터지고 `None`을 줬다. 관측이 목적이라 `.get`이 맞지만, 오타는 눈으로 잡아야 한다. 「수집기 12」의 `[]` vs `.get` 차이가 여기서 함정으로 나왔다.

### 2-3. 첫 실행 결과가 설계대로였다

```
수집 635건 신규 104건, 누적 1120건
```

수집 635 = moef 목록 전부 + jumpit 상세 104. 신규 104 = 전부 jumpit(moef는 이미 있어 IGNORE). **수집과 신규가 다른 게 정상**이고, 로그가 두 숫자를 따로 찍는 이유가 여기서 눈에 보였다.

## 3. 더 나아가 알면 좋은 것

- 브라우저 개발자도구 Network 탭으로 내부 API 찾는 정석 방법
- 재시도·지수 백오프 — jumpit도 아직 없다. URLError 나면 그 회차 포기
- rate limit 헤더 — 응답에 남은 호출 수가 오는 경우
- `sort=rc` 등 목록 파라미터의 의미 (최신순/인기순)

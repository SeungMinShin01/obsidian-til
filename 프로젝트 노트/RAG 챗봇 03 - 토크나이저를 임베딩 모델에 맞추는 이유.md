# RAG 챗봇 03 - 토크나이저를 임베딩 모델에 맞추는 이유

> 허브: [[RAG 챗봇 프로젝트 MOC]]

**물어본 것:** 토크나이저가 여러 개인데 청킹 코드가 `cl100k_base`를 쓰는 이유가 따로 있는가. 우리가 쓰는 모델은 `gemini-3.1-flash-lite`인데도 그런가.

## 1. 배운 내용

### 1-1. 임의로 고른 것이 아니라 임베딩 모델에 맞춘 것이다

토크나이저는 "글자를 토큰으로 쪼개는 규칙"이라 모델마다 다르다. 한 라이브러리 안에도 여러 개가 들어 있다.

| 인코딩 | 쓰는 모델 |
| --- | --- |
| `r50k_base` | GPT-3 (구형) |
| `p50k_base` | Codex 계열 |
| `cl100k_base` | GPT-3.5·4, **text-embedding-3-small/large** |
| `o200k_base` | GPT-4o 계열 |

이 프로젝트의 임베딩 모델이 `text-embedding-3-small`이므로, 짝이 되는 `cl100k_base`를 쓴다.

### 1-2. 세는 자가 다르면 숫자가 달라진다

청크 크기를 600토큰으로 잡아두었는데, **누가 세느냐에 따라 그 600이 다른 양**이 된다. 같은 한국어 문장을 다른 인코딩으로 세면 토큰 수가 달라지기 때문이다. 실제로 문제가 되는 자리가 둘이다.

- **입력 한도** — 임베딩 모델에는 한 번에 넣을 수 있는 토큰 한도가 있다. 세는 기준이 어긋나면 모르는 사이에 한도를 넘고, 넘친 뒷부분은 에러 없이 잘린다
- **검수의 의미** — 청크 덤프에 찍히는 "토큰 최소·평균·최대"가 쓸모 있으려면, 그 숫자가 임베딩 모델이 실제로 보는 숫자여야 한다

### 1-3. 자를 때와 셀 때 같은 자를 쓴다

청커는 두 곳에서 같은 인코딩 이름을 쓴다. 문자열을 자르는 분할기를 만들 때 한 번, 만들어진 청크의 토큰 수를 세는 함수에서 한 번이다. 한쪽만 바꾸면 자른 크기와 기록된 크기가 어긋난다.

### 1-4. 답변 생성 모델과는 상관이 없다

`gemini-3.1-flash-lite`는 **답변 생성용**이고, 청킹은 **임베딩 단계를 위한 준비**다. 모델이 둘이고 역할이 갈린다.

| 역할 | 모델 |
| --- | --- |
| 임베딩 (문서·질문 → 벡터) | `text-embedding-3-small` |
| 답변 생성 (청크 → 한국어 답변) | `gemini-3.1-flash-lite` |

인증키가 두 개 필요한 이유가 이것이다. 답변 생성 모델은 검색으로 고른 청크를 **텍스트 그대로** 넘겨받아 읽을 뿐이라, 그 텍스트를 누가 어떻게 세어 잘랐는지 알 필요가 없다. 이쪽에서 토큰이 의미를 갖는 것은 프롬프트가 컨텍스트 한도를 넘느냐 하나뿐인데, 청크 다섯 개면 수천 토큰 수준이라 여유가 있다.

## 2. 추가로 알면 좋은 활용법

임베딩 모델을 바꾸면 같이 움직여야 하는 것이 있다.

- 토크나이저 이름 — 지금은 청커에 상수로 박혀 있어 설정을 바꿔도 따라오지 않는다
- 벡터 차원 — 모델마다 다르고, 차원이 다른 벡터가 한 컬렉션에 섞이면 검색이 깨진다

그래서 문서 메타데이터에 **어떤 모델·몇 차원으로 인덱싱했는지**를 남겨둔다.

## 3. 더 나아가 알면 좋은 것

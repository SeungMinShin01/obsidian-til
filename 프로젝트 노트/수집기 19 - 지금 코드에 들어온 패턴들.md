# 수집기 19 - 지금 코드에 들어온 패턴들

> 허브: [[수집기 프로젝트 MOC]]

"아직 해당하는 디자인패턴은 없는 것인가"라는 질문에서 나온 노트다. 확인해보니 **이미 몇 개 들어와 있었고, 이름을 안 붙였을 뿐**이었다.

이 노트는 누적형이다. 패턴이 새로 생길 때마다 아래 표와 절에 덧붙인다.

## 1. 배운 내용

### 1-1. 지금 코드에 실제로 있는 것

| 패턴 | 어디 | 정도 |
| --- | --- | --- |
| **어댑터** | `sources/*.fetch() -> list[dict]` | 뼈대만. 진짜 응답을 변환하면 완성된다 |
| **리포지터리** | `store.py` | 거의 교과서적이다 |
| **격벽(Bulkhead)** | `collect_all`의 `try`/`except continue` | 정확히 이 패턴이다 |
| **테스트 대역 — Fake** | `sources/fake.py` | 이름까지 우연히 맞았다 |
| **파이프라인** | 수집 → 저장 → 표현 | 아키텍처 층 |
| **레지스트리** | `SOURCES = [fake]` | 가장 원시적인 형태 |

### 1-2. 리포지터리 — `store.py`

바깥에서는 `upsert_jobs`, `count_jobs`처럼 **도메인 언어로만** 부르고 SQL은 한 줄도 새어나오지 않는다. 나중에 SQLite를 다른 DB로 바꿔도 이 파일만 고치면 된다.

의도해서 만든 것이 아니다. "같은 이유로 바뀌는가"를 기준으로 파일을 나눴더니 결과가 이 패턴이었다.

리포지터리의 값어치는 **저장 기술과 나머지 코드를 떼어놓는 것**이다. `main.py`는 SQLite라는 단어를 모른다.

### 1-3. 격벽(Bulkhead)

배의 격벽에서 온 이름이다. 한 칸에 물이 차도 다른 칸으로 번지지 않게 벽을 세운다.

"어댑터 격리"라고 부르던 것이 정확히 이 이름을 갖고 있었다. `collect_all`의 `try`/`except continue`가 그 벽이다.

어댑터와 격벽은 다른 것을 한다. 헷갈리기 쉬워서 갈라둔다.

| | 무엇을 하나 |
| --- | --- |
| **어댑터** | 제각각인 응답을 하나의 계약으로 맞춘다 |
| **격벽** | 한 소스의 실패가 전체로 번지지 않게 막는다 |

### 1-4. 테스트 대역에는 종류가 있다

| 이름 | 무엇 |
| --- | --- |
| Dummy | 자리만 채운다 |
| Stub | 정해진 답만 돌려준다 |
| Spy | 답도 주고 호출 기록도 남긴다 |
| Mock | 어떻게 불렸는지 검증까지 한다 |
| **Fake** | **동작하는 간단한 구현** |

`sources/fake.py`는 실제로 Fake다. 진짜처럼 동작하되 단순하다.

`list(JOBS)`로 사본을 돌려주게 만든 것도 "진짜와 같은 성질을 갖게" 하려던 것이었는데, 그것이 Fake의 정의에 해당한다. **대역이 진짜와 다르게 동작하면 그 대역으로 한 검증은 의미가 없다.**

### 1-5. 파이썬에서는 GoF 패턴의 상당수가 언어 기능으로 흡수됐다

지금 코드에 **클래스가 하나도 없다.** 자바 배경이면 이상하게 느껴지는 지점이다.

| 자바에서 패턴 | 파이썬에서는 |
| --- | --- |
| 싱글턴 | 모듈이 이미 싱글턴이다. `import store`는 몇 번 해도 같은 객체 |
| 스트래티지 | 함수를 변수에 담아 넘기면 끝 |
| 팩토리 | 함수 하나 |
| 어댑터 | 같은 이름의 함수만 있으면 된다 (덕 타이핑) |

`SOURCES = [fake]`가 그 예다. 자바였다면 `List<JobSource>`에 인터페이스 구현체를 담았을 텐데, 파이썬은 **모듈 자체를 리스트에 담는다.**

패턴이 사라진 것이 아니라 **코드 모양에서 안 보이게 된 것**이다. 그래서 파이썬 코드를 읽을 때 "패턴이 없다"가 아니라 "패턴이 접혀 있다"로 봐야 한다.

### 1-6. 순서가 중요하다

지금까지 나온 것들은 전부 **필요해서 만들었더니 이름이 있더라**는 순서였다.

- 파일을 역할별로 나누다 보니 → 리포지터리
- 한 소스가 죽어도 계속 가게 하다 보니 → 격벽
- 배관을 먼저 검증하려다 보니 → Fake

반대로 하면 안 쓰는 추상화가 쌓인다. 설계 원칙에 이미 있는 그것이다.

> 미리 만든 유연성은 대개 쓰이지 않고, 정작 필요한 형태는 다르다.

**패턴 이름을 먼저 정하고 코드를 맞추지 않는다.** 이름은 나중에 붙이는 라벨이고, 라벨이 붙으면 검색해서 더 배울 수 있다는 것이 값어치의 전부다.

## 2. 추가로 알면 좋은 활용법

### 2-1. 앞으로 실제로 필요해질 것

| 패턴 | 언제 |
| --- | --- |
| **재시도 + 지수 백오프** | 크롤러 붙이는 즉시. 실패 상한도 같이 |
| **템플릿 메서드** | 크롤러가 둘 이상 되어 「robots 확인 → 목록 → 상세 → 정규화」 뼈대를 공유할 때 |
| **서킷 브레이커** | 한 소스가 계속 실패하면 아예 쉬게 만들 때 |
| **스트래티지** | 판정 로직이 신규/변경/재공고로 갈릴 때 |

앞의 둘은 크롤러를 만들면서 바로 나온다. 그때 이 노트에 절을 추가한다.

### 2-2. 패턴 이름을 아는 것의 실제 효용

세 가지다.

- **검색이 된다.** "한 소스가 죽어도 전체가 안 죽게 하는 법"보다 "bulkhead pattern"이 훨씬 잘 찾아진다
- **대화가 짧아진다.** 면접에서 구조를 설명할 때 다섯 문장이 한 단어가 된다
- **함정을 미리 안다.** 이미 겪은 사람들이 정리해둔 실패 사례가 붙어 있다

반대로 **모르는 상태로 만들어본 경험**이 먼저 있으면 이름이 훨씬 오래 붙는다. 이 노트가 그 순서로 만들어졌다.

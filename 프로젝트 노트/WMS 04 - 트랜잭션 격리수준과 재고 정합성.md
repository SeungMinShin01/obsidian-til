# WMS - 트랜잭션 격리수준과 재고 정합성

> 허브: [[WMS 프로젝트 MOC]]

## 1. 배운 내용

### 1-1. 격리수준이 뭔가

**격리수준(isolation level)** = 동시에 도는 트랜잭션들이 서로의 작업 중간 상태를 얼마나 볼 수 있는지 정하는 단계다.

혼자 쓰는 DB라면 필요 없는 개념인데, 출고 요청 두 개가 동시에 들어오는 순간부터 이게 전부가 된다.

### 1-2. 출고 처리는 이런 순서로 돈다

```
트랜잭션 시작
 → 재고 조회 (10개 있네)
 → 주문 수량 검증 (8개 요청, 가능)
 → 재고 차감
커밋
```

문제는 조회와 차감 사이에 **다른 사람의 출고 트랜잭션이 끼어드는 것**이다. 코드만 보면 안 보이는데, 두 요청이 겹치는 순간 드러난다.

### 1-3. READ COMMITTED (PostgreSQL 기본)

"커밋된 최신 값을 그때그때 읽는다."

```
나:   재고 조회 → 10개
                      다른 트랜잭션: 7개 차감하고 커밋
나:   재고 다시 조회 → 3개   ← 값이 바뀌어 보인다
```

같은 트랜잭션 안에서 같은 쿼리를 두 번 날렸는데 결과가 다르다. 이걸 **반복 불가능한 읽기(non-repeatable read)** 라고 한다.

### 1-4. REPEATABLE READ (MySQL 기본)

"트랜잭션 시작 시점의 사진(스냅샷)을 계속 본다."

```
나:   재고 조회 → 10개
                      다른 트랜잭션: 7개 차감하고 커밋
나:   재고 다시 조회 → 10개  ← 여전히 10개로 보인다
```

일관되게 보이는 건 좋은데, **실제 DB에는 3개밖에 없다.** 내가 8개를 차감하면 재고가 음수가 된다.

이게 **초과 출고**고, 2주차에 잡아야 하는 바로 그 문제다.

### 1-5. 핵심 — 격리수준만으로는 재고 정합성을 못 지킨다

처음엔 "격리수준을 높이면 안전해지는 것" 아닌가 싶었는데 아니었다. 격리수준이 높아지면 **보이는 값이 일관될 뿐**, 다른 트랜잭션이 실제로 값을 바꾸는 것을 막지는 못한다.

그래서 그 위에 **락**을 건다.

- **비관적 락** — `SELECT ... FOR UPDATE`. 읽으면서 그 행을 잠근다. 스냅샷이 아니라 최신 값을 읽고, 다른 트랜잭션은 대기한다
- **낙관적 락** — 버전 번호를 두고, 내가 읽은 버전과 다르면 실패시키고 재시도한다. JPA에서는 `@Version` 한 줄

2주차에 이 둘을 구현하고 비교하는 것이 목표다.

### 1-6. MySQL의 갭 락 — 여기서 나온다

MySQL의 REPEATABLE READ에서 범위 조건으로 `FOR UPDATE`를 걸면, 존재하는 행뿐 아니라 **행 사이의 빈 틈까지** 잠근다. 이걸 **갭 락(gap lock)** 이라고 한다.

그래서 "아무것도 없는 구간인데 왜 INSERT가 막히지?" 하는 상황이 생긴다. PostgreSQL의 READ COMMITTED에는 이런 게 없다.

처음엔 당황스럽겠지만, MySQL을 고른 이유 중 하나가 이거다. **예상하지 못한 락이 걸리는 상황을 직접 겪고 원인을 설명할 수 있으면 그 자체가 포트폴리오 내용이 된다.**

## 2. 추가로 알면 좋은 활용법

### 2-1. 격리수준 네 단계

낮은 것부터.

| 단계 | 막아주는 것 |
| --- | --- |
| READ UNCOMMITTED | 아무것도. 커밋 안 된 값까지 보인다(dirty read) |
| READ COMMITTED | dirty read |
| REPEATABLE READ | + 반복 불가능한 읽기 |
| SERIALIZABLE | + 팬텀 리드. 사실상 순차 실행 |

높일수록 안전하지만 동시 처리량이 떨어진다. **SERIALIZABLE로 올려서 해결하는 건 답이 아니다** — 재고 시스템에서 처리량을 버리는 셈이고, 3주차 부하 테스트에서 바로 드러난다.

### 2-2. 두 락의 성격이 다르다

- **비관적 락** — 충돌이 자주 일어난다고 가정. 미리 잠근다. 안전하지만 대기가 생기고, 잘못 쓰면 데드락
- **낙관적 락** — 충돌이 드물다고 가정. 일단 하고 충돌나면 재시도. 빠르지만 충돌이 잦으면 재시도가 폭증

**인기 상품 하나에 주문이 몰리는 상황**에서는 낙관적 락이 계속 실패하고, **여러 상품에 골고루 퍼진 상황**에서는 비관적 락이 불필요하게 대기한다. 이 대비를 3주차 부하 테스트로 숫자로 보여줄 수 있으면 좋은 기록이 된다.

### 2-3. 선점(ALLOCATE)을 따로 두는 이유가 여기 있다

재고를 실물·선점·가용으로 나누는 이유도 같은 맥락이다. 주문이 들어온 순간 바로 차감하지 않고 **선점**만 걸어두면, 실제 출고 전까지 물리적 재고는 그대로 두면서도 다른 주문이 같은 재고를 가져가는 것을 막는다.

가용재고 = 실물재고 − 선점재고.

## 3. 더 나아가 알면 좋은 것

### 3-1. 다음에 볼 키워드

- MVCC(다중 버전 동시성 제어) — 스냅샷이 어떻게 만들어지는지의 원리
- 팬텀 리드(phantom read) — 갭 락이 막으려는 현상
- 데드락과 `SHOW ENGINE INNODB STATUS` — 데드락이 났을 때 원인을 보는 방법
- `SKIP LOCKED` — 잠긴 행을 건너뛰고 읽는 방법. 피킹 리스트 배분에 쓸 수 있다
- lost update — `UPDATE`로 재고를 덮어쓸 때 하나가 사라지는 현상

### 3-2. 3주차에 증명할 것

부하 테스트에서 **동시 요청 시 초과 출고 0건**. 이게 숫자로 나와야 동시성 제어를 했다고 말할 수 있다.

측정할 때 락 방식을 바꿔가며 처리량(TPS)과 실패율을 같이 기록해두면, "안전한데 느린 쪽"과 "빠른데 조건이 붙는 쪽"의 트레이드오프를 표로 보여줄 수 있다.

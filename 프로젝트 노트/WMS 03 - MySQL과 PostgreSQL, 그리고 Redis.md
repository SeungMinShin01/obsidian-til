# WMS - MySQL과 PostgreSQL, 그리고 Redis

> 허브: [[WMS 프로젝트 MOC]]

## 1. 배운 내용

### 1-1. PostgreSQL은 벡터 DB가 아니다

먼저 잘못 알고 있던 것부터 바로잡았다. PostgreSQL을 벡터 DB로 알고 있었는데, **MySQL과 같은 계열의 범용 관계형 DB(RDBMS)**다.

헷갈린 이유는 **pgvector** 때문이다. PostgreSQL에 벡터 타입과 유사도 검색을 붙여주는 **확장(extension)** 이고, 이게 RAG·AI 쪽에서 워낙 많이 쓰이다 보니 "PostgreSQL = 벡터 DB"처럼 보인다. 확장을 안 깔면 그냥 평범한 SQL DB다.

확장이라는 개념 자체가 PostgreSQL의 특징이기도 하다. 기본 DB 위에 기능을 얹는 구조라 pgvector, PostGIS(지리정보) 같은 것들이 붙는다.

### 1-2. 일반적인 성격 차이

| | MySQL | PostgreSQL |
| --- | --- | --- |
| 강점 | 읽기 위주 작업. 기능이 적은 대신 가볍고 빠르다 | 복잡한 트랜잭션과 쓰기. 기능이 풍부하다 |
| 인덱스 | B-Tree 위주로 단순 | 부분 인덱스, 표현식 인덱스, BRIN 등 종류가 많다 |
| 국내 자료 | 압도적으로 많다 | 늘고 있지만 아직 적다 |

### 1-3. 이 프로젝트에서 실제로 갈리는 지점 세 개

**① 실행계획 읽기** — 3주차 내내 하게 된다.

MySQL `EXPLAIN`은 표 형태라 읽기 쉽고 한국어 해설이 많다. 다만 이건 옵티마이저의 **계획**이지 실측이 아니다.

PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)`는 실제 실행시간과 버퍼 히트율까지 알려준다. 정보량이 훨씬 정확한 대신 트리 형태라 읽는 법을 따로 배워야 한다.

**② 인덱스 실험 재료** — PostgreSQL이 종류가 많아 "이 인덱스는 왜 안 먹었나"를 파고들 재료가 많다.

**③ 기본 격리수준이 다르다** — MySQL은 `REPEATABLE READ`, PostgreSQL은 `READ COMMITTED`. **같은 재고 선점 코드가 두 DB에서 다르게 동작한다.** 이건 따로 정리한다 → [[WMS 04 - 트랜잭션 격리수준과 재고 정합성]]

### 1-4. MySQL로 정한 이유

처음엔 PostgreSQL이 더 나아 보였다. 측정이 주제인 프로젝트인데 측정 도구가 더 정확하니까. 실제로 그 판단은 맞다.

결정을 뒤집은 건 **시간 조건**이었다.

집중해서 쓸 수 있는 기간이 3주뿐이고 그 뒤로는 주당 몇 시간으로 떨어진다. 이건 **3주 안에 끝나지 않으면 사실상 끝나지 않는다**는 뜻이다. 미완성 상태로 저강도 기간에 넘어가면 매번 "지난번에 뭐 하다 말았지"를 복구하는 데 시간을 다 쓰게 된다.

이 조건에서는 막혔을 때 검색으로 30분 만에 빠져나오는 것이 도구의 정밀함보다 값이 크다고 봤다. 검색 비용의 차이는 3주 내내 매일 발생하지만, 측정 도구의 정밀함은 3주차 한 주에만 영향을 준다.

덤으로, MySQL InnoDB의 **갭 락(gap lock)** 이 2주차 동시성 실험에서 좋은 관찰 대상이 된다. 예상하지 못한 락이 걸리는 상황을 직접 겪고 설명할 수 있다.

### 1-5. 취업 관점은 판단 근거가 약했다

"어느 쪽이 채용에 유리한가"를 따져봤는데, 공고들이 대체로 특정 제품이 아니라 **"RDBMS 사용 경험"** 을 요구한다. 하나를 제대로 다뤄봤으면 다른 쪽은 금방 넘어간다는 뜻이다. 이건 결정 근거로 쓰기 어려웠다.

### 1-6. 이식성에는 투자하지 않는다

"나중에 바꿀지 모르니 MySQL 고유 기능은 피하자"고 하면 최적화 폭이 줄어든다. 이 프로젝트의 목적과 정면으로 충돌한다.

다만 **공짜로 문을 열어두는 방법**은 있다. 마이그레이션 SQL에서 백틱을 쓰지 않고, 예약어를 컬럼명으로 쓰지 않는 것. 이 둘만 지키면 나중에 옮길 때 손볼 게 눈에 띄게 줄고 비용은 0이다.

### 1-7. 언제까지 바꿀 수 있나

- **1~2주차 중이면 반나절.** JPA가 대부분을 흡수하고, 바꿀 건 compose 이미지 한 줄, 드라이버 의존성, 마이그레이션 SQL 문법 정도다
- **3주차 측정을 시작한 뒤엔 사실상 새 프로젝트.** 이유는 코드가 아니라 **데이터**다. Before/After 표가 MySQL 기준으로 쌓여 있는데 DB를 갈면 그 숫자들이 전부 무의미해진다

## 2. 추가로 알면 좋은 활용법

### 2-1. Redis는 이 비교에 들어가지 않는다

Redis를 MySQL/PostgreSQL의 대안으로 착각하기 쉬운데, 아예 다른 계층이다.

**메모리에 사는 키-값 저장소**다. 디스크가 아니라 RAM에 데이터를 두니 훨씬 빠르지만, 담을 수 있는 양이 적고 원본 데이터를 맡기지 않는다. **Redis가 통째로 날아가도 DB에서 복구되는 구조**여야 한다.

### 2-2. 이 프로젝트에서 Redis를 쓰는 곳 두 군데

**① 캐싱 (3주차)** — 최적화 순서가 인덱스 → N+1 제거 → 캐싱인데 마지막 단계다. 재고 현황 조회처럼 자주 읽히고 매번 계산이 무거운 결과를 메모리에 담아둔다.

여기서 진짜 문제는 속도가 아니라 **무효화**다. 재고는 계속 바뀌는데 캐시는 옛날 값을 들고 있다. TTL을 짧게 줄지, 재고가 변할 때마다 캐시를 지울지 — 이 판단이 3주차 기록의 좋은 재료가 된다.

**② 분산 락 (2주차)** — 동시성 제어 방식 비교에서 세 번째 후보다.

다만 **서버 한 대짜리 개인 프로젝트에서 Redis 락은 과하다.** DB 락으로 충분하다. 비관적 락과 낙관적 락 둘만 비교해도 2주차 목표는 채워진다. 시간이 남으면 얹고, 안 남으면 "왜 필요 없다고 판단했는지"를 적는다 — 그것도 근거 있는 선택이다.

### 2-3. 그래서 compose에 넣되 1~2주차엔 쓰지 않는다

Redis 컨테이너는 처음부터 띄워두지만 3주차 캐싱 단계에서 처음 연결한다. 미리 붙여두면 **최적화를 먼저 넣는 것**이 되어 개선 폭을 증명할 수 없게 된다.

## 3. 더 나아가 알면 좋은 것

### 3-1. 다음에 볼 키워드

- `EXPLAIN` 읽는 법 — `type`, `key`, `rows`, `Extra` 컬럼이 무엇을 말하는지
- InnoDB 버퍼 풀 — 왜 이 크기가 측정 결과를 좌우하는지
- Redis 자료구조 — String 말고 Hash, Sorted Set이 있고 용도가 다르다
- Cache-Aside / Write-Through — 캐시 갱신 전략의 이름들

### 3-2. 11월 RAG 프로젝트와의 관계

다음 프로젝트가 PostgreSQL + pgvector 기반이라, PostgreSQL을 여기서 익혀두면 이어진다는 논거도 있었다. 하지만 RAG는 인덱스 튜닝이 주제가 아니라 부담이 덜하다고 보고, 그때 새로 배우기로 했다.

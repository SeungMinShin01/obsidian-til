# RAG 챗봇 01 - 업로드에서 검색까지 전체 흐름

> 허브: [[RAG 챗봇 프로젝트 MOC]]

**물어본 것:** 업로드부터 검색까지가 내 담당인데, 각 단계가 이론적으로 무슨 일을 하는가. 코드는 나중에 보고 개념부터 잡는다.

## 1. 배운 내용

### 1-1. 갈래가 둘이다

한 덩어리로 보면 헷갈리는데, 도는 시점이 다른 두 흐름이다.

```
[인제스천]  PDF 업로드 -> 파싱 -> 전처리 -> 청킹 -> 임베딩 -> 벡터 DB 저장
[질의응답]  질문 -> 질문 임베딩 -> 검색 -> 조각 목록 -> 답변 생성
```

인제스천은 문서를 올릴 때 한 번 돌고, 질의응답은 질문할 때마다 돈다. 둘을 잇는 것은 코드가 아니라 **벡터 DB에 남은 데이터**다. 인제스천이 미리 저장해두지 않으면 질의응답은 꺼낼 것이 없다.

담당 경계는 답변 생성 직전까지다. 검색 결과를 형식에 맞춰 넘기는 데까지가 내 몫이고, 그것을 읽고 한국어 답을 쓰는 것은 팀원 몫이다.

### 1-2. 업로드 — 밖에서 들어오는 입구

성격이 다른 세 가지 질문이 겹쳐 있다.

**① 어떤 모양으로 도착하는가**

JSON은 텍스트 형식이라 바이너리를 담을 수 없다. 그래서 파일은 `multipart/form-data` 로 온다. 요청 본문을 경계 문자열로 칸을 나눠 여러 조각을 한 번에 보내는 형식이고, 파일 하나만 보내도 이 형식을 쓴다. 파일명·타입 같은 부가 정보를 실을 자리가 필요하기 때문이다.

서버는 이것을 통째로 메모리에 올리지 않는다. 일정 크기를 넘으면 임시 파일로 흘려보내고 **파일처럼 생긴 스트림**을 넘겨준다. 여기서 제약이 하나 생긴다 — **스트림은 한 번 읽으면 끝이다.** 되감기가 안 되므로 "검증하려고 한 번, 저장하려고 또 한 번" 읽을 수 없다.

**② 언제 응답하는가**

임베딩까지 마치고 응답하면 수십 초에서 몇 분이 걸린다. 그동안 요청을 붙잡고 있으면 브라우저·프록시가 각자의 타임아웃으로 끊는다. 끊긴 뒤 서버가 처리를 마쳐도 클라이언트는 성공 여부를 알 수 없다.

그래서 접수와 처리를 분리한다.

```
200 OK       "다 끝났다"
202 Accepted "접수했다. 처리는 진행 중이다"
```

`202` 와 함께 접수번호를 돌려주면 클라이언트는 그 번호로 상태를 물으며 진행률을 보여줄 수 있다. 택배 송장번호와 같은 구조다. 상태값(`UPLOADED -> ... -> INDEXED`)이 필요한 이유도 여기 있다 — 접수번호만 주고 끝내면 물어볼 대상이 없다.

**③ 도착한 것을 어떻게 믿는가**

클라이언트가 말하는 것은 전부 자기 주장이다.

| 주장 | 못 믿는 이유 |
| --- | --- |
| 확장자가 `.pdf` 다 | 이름의 일부일 뿐, 아무 파일이나 바꿔 붙일 수 있다 |
| `Content-Type` 이 PDF다 | 요청 헤더는 보내는 쪽이 직접 쓴다 |
| 파일명이 `report.pdf` 다 | 경로 이탈 문자열이 섞이면 엉뚱한 곳에 쓴다 |

그래서 서버 쪽에서 세 가지를 확인한다. **내용을 직접 본다**(PDF는 맨 앞 5바이트가 `%PDF-` 다 — 매직 바이트), **클라이언트가 준 이름을 쓰지 않는다**(서버가 만든 UUID를 파일명으로 쓰면 경로 이탈·이름 충돌·OS별 정규화 차이가 한꺼번에 사라진다), **크기를 제한한다**.

스트림을 한 번밖에 못 읽으므로 순서는 **저장 -> 검증**이 된다. 저장된 파일은 몇 번이든 다시 읽을 수 있다. 검증에 실패하면 방금 쓴 파일을 지운다.

저장 자체도 한 단계 더 있다. 쓰는 도중 프로세스가 죽으면 반쪽짜리 PDF가 남고, 이것이 나중에 "왜 이 문서만 파싱이 깨지지"가 된다. 임시 이름으로 다 쓴 뒤 최종 이름으로 바꾸면 중간 상태가 없다 — 같은 디스크 안에서 이름 변경은 원자적이다.

마지막으로 파일 내용 전체의 해시를 낸다. 이미 인덱싱된 문서 중 같은 해시가 있으면 처리를 건너뛰고 기존 문서를 돌려준다. 파일명이 달라도 내용이 같으면 같은 지문이 나온다. 임베딩이 유일하게 돈이 드는 단계라 같은 문서를 두 번 벡터로 만들 이유가 없다. #멱등성

### 1-3. 파싱 — 형식 변환이 아니라 구조 복원

파싱은 정해진 규칙대로 쓰인 데이터를 읽어 **구조를 해석하는 것**이다. 형식을 바꾸는 것이 목적이 아니라 다음 단계가 쓸 수 있는 모양으로 해석하는 것이 목적이다.

PDF가 특이한 점은 **텍스트 파일이 아니라는 것**이다. 내부는 "종이에 어떻게 인쇄할지"를 적어둔 명령 목록이다.

```
좌표 (72, 700) 에 글리프 'O' 를 그려라
좌표 (81, 700) 에 글리프 'p' 를 그려라
```

여기에 문단이 없고, 문장이 없고, **줄조차 없다.** 띄어쓰기가 문자로 저장돼 있지 않은 경우도 많다. PDF의 목적은 "어디서 열어도 똑같이 보이는 것"이지 "내용을 다시 꺼내 쓰는 것"이 아니라서, 보기 위한 정보만 남기고 의미 구조는 버린다.

그래서 텍스트 추출은 좌표를 보고 하는 **추정**이 된다. y좌표가 비슷하면 같은 줄로 보고, 글자 간격이 평소보다 넓으면 공백을 넣는 식이다. 조판이 단순하면 잘 나오고 복잡하면 깨진다.

- **2단 조판** — 좌우 단이 y좌표가 같아 한 줄로 이어져 나온다
- **표** — 셀 구조가 사라지고 숫자만 나열된다. `2.3 5.5 V` 가 되면 최소값인지 최대값인지 알 수 없다
- **줄 끝 하이픈** — `embed-` / `ding` 으로 잘리면 임베딩에서 전혀 다른 단어가 된다
- **글리프 매핑이 없는 폰트** — 화면엔 글자로 보이는데 꺼내면 깨진 기호가 나온다

즉 파싱은 손실이 있는 작업이다. 원본 PDF를 지우면 안 되는 이유이기도 하다.

**텍스트 레이어가 아예 없는 경우**는 성격이 다르다. 스캔본은 페이지 전체가 사진 한 장이라 꺼낼 글자가 존재하지 않는다. 파싱 실패가 아니라 파싱할 대상이 없는 것이므로 별도 상태(`OCR_REQUIRED`)로 구분해두면, 나중에 문자 인식을 붙일 때 그 상태만 골라 다시 돌리면 된다. 판정할 때 평균 글자 수만 보면 **표지만 텍스트고 본문이 전부 이미지인 PDF**를 놓치므로, 글자가 있는 페이지의 비율을 같이 본다.

### 1-4. 페이지는 파싱이 나누는 것이 아니다

헷갈리기 쉬운 지점이다. **페이지는 PDF에 원래 나뉘어 있다.**

| 구조 | PDF에 있나 | 파싱이 하는 일 |
| --- | --- | --- |
| 페이지 | **있다** | 그대로 물려받는다 |
| 줄·단어·띄어쓰기 | 없다 | 좌표로 추정 복원 |
| 문단·문장 | 없다 | 못 한다 (뒤 단계 몫) |

PDF는 "종이에 인쇄하기 위한 형식"이라 종이 한 장이라는 단위만은 확실히 갖고 있다. 오히려 사람이 읽을 때 쓰는 문단·문장 같은 단위가 없다.

라이브러리는 두 방식 다 지원한다.

```
방식 A:  PDF -> 문서 전체 텍스트 한 덩어리      (페이지 경계가 사라짐)
방식 B:  PDF -> [1페이지 텍스트, 2페이지 텍스트, ...]  (경계가 남음)
```

여기서 B를 쓴다. 파싱이 페이지를 나눈 것이 아니라 **원래 있던 경계를 뭉개지 않고 살려서 넘긴 것**이다. 그리고 1부터 시작하는 번호를 붙인다 — 사람이 뷰어에서 보는 번호와 맞아야 출처 표시가 성립한다.

각 단계가 구조에 하는 일을 갈라두면 헷갈리지 않는다.

| 단계 | 구조에 대해 하는 일 |
| --- | --- |
| 파싱 | 있는 구조를 살려서 가져온다, 없는 구조를 추정 복원한다 |
| 전처리 | 구조가 아닌 것을 덜어낸다 |
| 청킹 | 없던 구조를 새로 만든다 |

**진짜 "나누는" 작업은 청킹**이다. 파싱은 나누는 쪽이 아니라 꺼내는 쪽이다.

### 1-5. 전처리 — 신호 대 잡음비를 올린다

파싱 결과에는 사람 눈엔 안 들어오지만 기계에겐 그냥 글자인 것이 섞여 있다. 머리말, 꼬리말, 페이지 번호, 구분선 같은 것들이다.

목적은 보기 좋게 만드는 것이 아니라 **임베딩할 텍스트의 신호 대 잡음비를 올리는 것**이다. 세 가지가 걸린다.

- **벡터가 한쪽으로 끌린다** — 모든 조각에 같은 문구가 들어 있으면 그 성분이 모든 벡터에 공통으로 섞여 조각들이 서로 비슷해진다. 구별력이 떨어진다
- **토큰 예산을 먹는다** — 조각이 600토큰인데 머리말이 30토큰이면 매번 5%가 낭비된다
- **검색 결과를 오염시킨다** — 질문에 문서 제목이 들어가면 머리말 있는 조각이 무더기로 걸린다

**판정을 한 페이지만 봐서는 못 한다.** 15페이지 맨 위의 `DS3231` 이 머리말인지 본문 제목인지는 그 페이지만 봐선 알 수 없고, 40페이지 중 38페이지에 똑같이 있으면 머리말이다. 반복이 유일한 증거다. 그래서 전처리는 문서 전체를 받아 두 번 돈다 — 1차로 반복되는 줄을 찾고, 2차로 페이지마다 그것을 지운다.

세는 것 자체에도 함정이 있다. 같은 머리말도 페이지마다 내부 띄어쓰기가 미묘하게 달라진다. 좌표에서 공백을 추정한 결과이기 때문이다. 그냥 세면 전부 다른 줄로 카운트돼 **반복 탐지가 통째로 실패한다.** 아무것도 안 지워지는데 에러도 안 난다. 그래서 비교 전에 연속 공백을 한 칸으로 줄이고 숫자를 기호로 바꿔 정규화한다. 이것은 비교용으로만 쓰고 실제로 지울 때는 원문을 본다.

전처리는 되돌릴 수 없는 파괴적 작업이라, 지우면 안 되는 것을 지키는 조건을 좁게 건다.

| 조건 | 막는 것 |
| --- | --- |
| 위치 — 페이지 위아래 몇 줄만 후보 | 범위를 넓히면 본문 첫 문장이 후보에 들어온다 |
| 길이 — 너무 긴 줄은 제외 | 반복되는 표 제목이 오인돼 통째로 사라진다 |
| 비율 — 전체 페이지의 절반 이상 | 몇 페이지에만 있는 것은 본문일 가능성이 크다 |
| 문서 길이 — 짧은 문서는 탐지 안 함 | 5페이지에서 3회 반복은 우연이다 |

반복 제거와 별개로 글자 자체도 다듬는다. 한글 자모 분리를 합치는 유니코드 정규화, 보이지 않는 문자 제거, 줄 끝 하이픈 결합 같은 것들이다.

**반드시 남겨야 하는 것이 하나 있다.** 빈 줄 여러 개는 두 개로 줄이되 하나로 줄이지 않는다. 다음 단계 분할기가 **문단 경계를 1순위 구분자로 쓰기** 때문이다. 여기서 문단 구분을 없애면 청킹이 문장 중간에서 자르기 시작한다. 파일은 나뉘어 있지만 이 규칙 하나가 전처리와 청킹을 묶고 있다.

전처리는 텍스트만 바꾸고 **페이지 구조는 그대로 둔다.** 페이지 수도 번호도 유지된다.

### 1-6. 청킹 — 검색의 단위가 여기서 정해진다

자르는 이유는 셋인데 무게가 다르다.

- **입력 한도** — 임베딩 모델이 한 번에 받을 수 있는 토큰이 정해져 있다. 기술적 제약이지만 덜 중요한 이유다
- **의미가 희석된다** — 이것이 진짜 이유다. 벡터 하나는 그 텍스트 전체의 평균적 의미를 담는다. 300페이지를 하나의 벡터로 만들면 전압·온도·통신·치수가 전부 섞여 "데이터시트스러운 무언가"라는 뭉툭한 방향 하나가 된다. 질문은 뾰족한데 벡터가 뭉툭하면 안 걸린다. **자르는 목적은 벡터를 뾰족하게 만드는 것**이다
- **답변 근거의 단위** — 조각이 그대로 프롬프트에 들어가므로, 크면 필요 없는 내용까지 들어가 모델이 엉뚱한 숫자를 끌어다 쓸 여지가 생긴다

그래서 청크는 **검색의 단위이자 근거의 단위**다. RAG에서 가장 작은 원자다.

잘게 자를수록 좋은 것은 아니다. 반대 방향으로 망가진다.

| | 너무 작으면 | 너무 크면 |
| --- | --- | --- |
| 벡터 | 뾰족한데 정보가 없다 | 정보는 많은데 뭉툭하다 |
| 문맥 | 무엇의 값인지 모른다 | 여러 주제가 섞인다 |
| 답변 | 근거가 조각나 반쪽 답 | 노이즈로 오답 유발 |

작게 자를 때의 전형적 사고는 이렇다. 조각 A가 "이 소자는 외부 전원이 필요하다", 조각 B가 "2.3V에서 5.5V로 동작한다" 로 갈리면, B는 답에 필요한 숫자를 갖고 있는데 "동작 전압"이라는 말이 없어서 질문과 안 가깝다. 검색에 안 걸린다.

**정답 크기는 없다.** 시작값을 정해두고 실제 문서로 돌려보며 조정하는 값이고, 재인덱싱 기능이 있는 이유이기도 하다.

자를 자리는 우선순위대로 찾는다.

```
1순위: 문단 경계 (빈 줄)
2순위: 줄바꿈
3순위: 문장 끝
4순위: 띄어쓰기
5순위: 글자 (최후)
```

먼저 문단으로 쪼개보고, 나온 덩어리가 크기 안에 들어가면 끝. 안 들어가면 그 덩어리를 다시 줄 단위로 쪼갠다. 이렇게 한 단계씩 내려가며 재귀적으로 쪼개서 **재귀적 분할**이라 부른다.

**겹침**은 경계에서 잘린 문장을 구제하는 장치다. 앞 조각의 꼬리 일부를 다음 조각 머리에 중복해서 넣으면, 경계에 걸친 문장이 둘 중 하나에는 온전히 들어간다. 대가는 저장량 증가와 검색 결과 중복이다.

**페이지 경계는 넘지 않는다.** 방법은 검사가 아니라 구조다 — 분할기에 페이지를 하나씩만 넘기면 한 번에 한 페이지치 재료만 쥐고 있으므로 넘고 싶어도 넘을 수 없다. 다만 이 제약이 크기 조절을 방해한다. 페이지 끝에 조금만 남으면 그것이 그대로 짧은 조각이 된다. 다음 페이지에서 끌어와 채울 수 없기 때문이다.

조각마다 고유 id가 필요한데, **id를 어떻게 만드느냐가 재처리 동작을 결정한다.** 무작위로 만들면 다시 처리할 때마다 새 id가 나와 중복이 무한정 쌓인다. `문서id-p페이지-c순번` 처럼 내용에서 계산되는 방식이면 같은 설정으로 다시 처리할 때 같은 id가 나와 덮어쓰기가 된다. 다만 조각 수가 줄면 뒷번호가 고아로 남으므로, 재처리 전에 그 문서 조각을 전부 지우고 새로 넣는다.

청킹은 **돈이 드는 단계 직전의 마지막 무료 구간**이다. 여기서 깨지면 뒤가 전부 깨지는데 뒤에서 보면 원인이 안 보인다. 그래서 조각을 파일로 덤프해 직접 읽어보는 것이 이 단계의 진짜 검증이다.

### 1-7. 임베딩 — 실패가 조용한 유일한 단계

의미가 숫자가 되는 원리는 **"단어의 의미는 함께 나타나는 것들로 정해진다"** 는 발상이다. `동작 전압`, `공급 전압`, `Supply voltage` 는 비슷한 자리에 비슷한 것들과 함께 나타난다. 모델은 엄청난 양의 문장으로 "같은 문맥에 나오는 것은 가까운 자리에 찍어라"를 학습한 결과물이고, 사람이 의미를 정의해준 것이 아니라 통계적으로 뽑아낸 것이다.

이 단계는 앞 단계들과 성질이 완전히 다르다.

| | 파싱·전처리·청킹 | 임베딩 |
| --- | --- | --- |
| 어디서 | 내 컴퓨터 | 남의 서버 |
| 속도 | 즉시 | 수십 초 ~ 분 |
| 실패 | 거의 없음 | **정상적으로 일어남** |
| 비용 | 0 | 토큰량에 비례 |

네트워크 너머의 일이라 요청 폭주·일시 장애·타임아웃이 일상이다. 자동 재시도와 타임아웃은 "혹시 몰라서"가 아니라 없으면 긴 문서 인덱싱이 중간에 죽는다는 뜻이다. 업로드 응답을 먼저 주고 뒤에서 처리하는 구조도 여기가 오래 걸리기 때문에 나왔다.

조각 수백 개를 요청 수백 번으로 보내면 왕복 시간이 쌓이고 빈도 제한에 걸리므로 **묶어서** 보낸다. 그런데 묶어 보내면 응답도 묶여서 오고, **그 순서가 곧 계약이 된다.**

가장 위험한 것이 여기 있다. **에러 없이 망가질 수 있다.**

```
보낸 것:  [조각0, 조각1, 조각2, 조각3]
받은 것:  [벡터0, 벡터1, 벡터2]          <- 하나 빠짐
```

그대로 짝지으면 한 칸씩 밀린 채로 전부 저장된다. 프로그램은 정상 종료되고 인덱싱 완료 상태가 뜨고 검색도 결과를 돌려주는데 **답만 계속 엉뚱하다.** 그리고 원인을 찾으러 검색이나 프롬프트를 뒤지게 된다. 원인은 며칠 전 인덱싱에 있는데. 그래서 개수와 차원이 예상과 같은지 그 자리에서 확인하고, 다르면 즉시 실패시킨다. #빠른실패

**벡터는 모델에 종속적이다.** A 모델로 만든 문서 벡터와 B 모델로 만든 질문 벡터는 좌표계가 달라 거리가 의미 없다. 모델을 바꾸면 문서 전체를 다시 임베딩해야 하고 부분 교체가 불가능하다. 그래서 어떤 모델·몇 차원으로 인덱싱했는지를 문서 메타데이터에 남긴다.

한계도 알아둘 만하다. 임베딩 모델은 일반 텍스트로 학습됐으므로 기호형 파라미터명, 부품 번호, 숫자와 단위의 미세한 차이에 약하다. **벡터 검색이 근본적으로 약한 지점이 "정확히 일치해야 하는 것"** 이다.

비용은 100만 토큰에 약 $0.02로, 300페이지 한 번 인덱싱에 6원 정도다. 아껴야 할 것은 답변 생성 호출 쪽이지 임베딩이 아니다.

### 1-8. 벡터 DB 저장 — 왜 별도의 물건이 필요한가

SQL로도 코사인 계산은 가능하다. 문제는 **인덱스를 걸 수 없다는 것**이다. 일반 DB의 인덱스는 순서가 있는 값을 전제하는데, 1536차원 벡터에는 "앞뒤"라는 것이 없다. 정렬이 안 되니 인덱스도 없다. 그러면 저장된 조각 전부와 거리를 계산하는 수밖에 없고, 조각 수에 정비례해 느려진다.

벡터 DB가 파는 것은 **전부 재지 않고 가까운 것을 찾는 색인**이다. 대표적인 방식은 계층 그래프로, 위층에서 대충 어느 동네인지 찾고 아래층에서 그 안만 정밀 탐색한다. 이름의 "근사"가 중요한데 — **진짜 1등을 놓칠 수 있다.** 확률은 낮지만 0은 아니고, 정확도를 조금 내주고 속도를 크게 사는 거래다.

저장되는 것은 네 종류다.

| 저장하는 것 | 쓰이는 곳 |
| --- | --- |
| id | 지목·덮어쓰기·삭제 |
| 벡터 | 거리 계산 (검색) |
| 원문 텍스트 | 답변 모델에 넘길 근거 |
| 메타데이터 | 인용·필터링·관리 |

원문을 왜 또 저장하느냐면, **벡터는 되돌릴 수 없기 때문**이다. 텍스트에서 벡터는 만들 수 있지만 벡터에서 텍스트는 복원할 수 없다. 답변 모델에게 넘겨야 하는 것은 읽을 수 있는 텍스트다. **벡터는 찾기 위한 것, 텍스트는 답하기 위한 것**으로 역할이 다르다.

메타데이터는 인용에만 쓰이지 않는다. 문서를 지정해 그 안에서만 검색하는 필터, 문서 단위 삭제도 여기에 기댄다. 그리고 파싱에서 붙은 페이지 번호가 최종적으로 도착하는 곳이 여기다.

거리 방식은 컬렉션을 만들 때 정해지고 **나중에 못 바꾼다.** 색인 구조가 그 방식을 전제로 만들어지기 때문이다.

이 데이터의 성격은 **파생물**이다.

| 저장소 | 담는 것 | 잃으면 |
| --- | --- | --- |
| 파일시스템 | 원본 PDF | 복구 불가 |
| 관계형 DB | 문서 메타·상태 | 복구 어려움 |
| 벡터 DB | 벡터·조각·메타 | **다시 만들면 된다** |

조각 설정을 잘못 잡았어도, 청킹 규칙을 바꾸고 싶어도, 모델을 바꾸고 싶어도 전부 지우고 다시 만들면 된다. 이 성질이 실험을 가능하게 한다.

### 1-9. 검색 — 정확도를 가장 많이 좌우하는 자리

하는 일은 네 단계로 짧다.

```
질문 -> 질문을 벡터로 -> 가까운 조각 k개 -> 거리로 걸러내기 -> 형식 맞춰 넘기기
```

짧지만 여기서 엉뚱한 것을 집어오면 답변 모델이 아무리 좋아도 틀린다. 모델은 검색이 준 것만 본다.

**질문과 문서는 형태가 다르다.** 질문은 짧고 묻는 말이고, 조각은 길고 서술하는 말이다. 임베딩이 "비슷한 문맥에 나오는 것끼리 가깝게"를 학습한 것이라, 애초에 생김새가 다른 둘을 맞추는 일은 같은 종류끼리 비교하는 것보다 본질적으로 어렵다. 이것을 **비대칭 검색**이라 한다.

대응책은 질문을 문서처럼 바꿔서 검색하는 것이다. 질문을 받아 그럴듯한 답변을 먼저 지어내게 하고 그 가짜 답변으로 검색하면, 내용이 틀려도 **문장의 형태와 어휘가 문서 쪽에 가까워져** 검색이 잘 된다.

**손잡이가 둘 있고 조절하는 것이 다르다.**

```
1) 벡터 DB에 "가까운 것 k개 줘" 요청    <- 여기서 이미 k개로 잘림
2) 받은 k개 중 거리가 먼 것을 버림
```

필터가 나중에 걸리므로 두 성질이 나온다. 상한을 느슨하게 해도 **개수는 늘지 않는다.** 그리고 정답이 k등 밖이면 상한과 무관하게 못 찾는다. 즉 **`top_k` 가 놓치지 않기를, 거리 상한이 엉뚱한 것 안 넣기를** 담당한다. 답을 못 찾을 때 상한만 만지면 안 되는 이유다.

다 걸러져 빈 목록이 되면 답변 모델을 아예 부르지 않고 "정보가 없다"가 바로 나간다. 비용도 아끼고 근거 없이 지어내는 것도 막는다.

**검색 실패는 두 종류이고 위험도가 다르다.**

| 유형 | 증상 | 원인 후보 |
| --- | --- | --- |
| 못 찾음 | "해당 정보가 없습니다" | 언어 차이, 비대칭, 조각 잘림, k 부족, 상한 |
| 엉뚱한 것을 찾음 | **그럴듯한데 틀린 답** | 노이즈, 문서 미지정, 조각이 너무 큼 |

정확도가 최우선인 펌웨어 맥락에서는 후자가 더 위험하다. 전자는 다시 물어보면 되지만 후자는 잘못된 값으로 회로를 짜게 만든다.

넘기는 모양은 계약이다. 저장할 때 쓴 이름과 넘길 때 쓰는 이름이 다르므로(`pageNumber` -> `page`), 그 변환을 검색 단계 한 곳에 몰아둔다. 저장 쪽 이름이 바뀌든 답변 쪽 계약이 바뀌든 고칠 곳이 하나가 되도록 하는 것이다.

마지막으로 **검색만 따로 볼 수 있어야 한다.** 답변이 이상할 때 "검색이 문제인가 프롬프트가 문제인가"를 가르지 못하면 아무것도 못 고친다. 답변 모델을 부르지 않고 거리만 보는 통로가 있으면 비용 0으로 진단할 수 있다.

| 관찰 | 해석 |
| --- | --- |
| 거리가 작은데 답이 이상 | 검색은 정상. 프롬프트나 조각 크기 문제 |
| 거리가 큼 | 검색이 원인. 청킹 전략이나 질문 표현 |
| 걸러진 것이 많음 | 상한이 너무 빡빡함 |
| 정답 조각이 목록에 없음 | k 부족이거나 인덱싱 자체가 잘못됨 |

## 2. 흐름을 관통하는 것 셋

### 2-1. 페이지 번호는 끊기면 복원할 수 없다

```
파싱: 번호 부여 -> 전처리: 유지 -> 청킹: 조각에 물려줌 -> 저장: 메타데이터로 -> 검색: 꺼냄
```

한 군데라도 끊기면 "15페이지에서 확인하세요"가 통째로 불가능해진다. 나중에 붙이려고 하면 못 붙이는 종류의 정보다.

### 2-2. 돈이 드는 자리는 세 곳뿐이다

| 단계 | 바깥 호출 |
| --- | --- |
| 저장·파싱·전처리·청킹·벡터 DB 저장 | 없음 |
| 임베딩 (문서) | 있음 |
| 임베딩 (질문) | 있음, 아주 작음 |
| 답변 생성 | 있음 |

청킹까지가 전부 무료라는 것이 중요하다. 조각 설정을 몇 번을 바꿔 돌려도 비용이 0이라, 만족스러운 설정을 찾은 다음에 돈이 드는 단계로 넘어가면 된다.

### 2-3. 원본만이 유일한 진실이다

파싱은 손실이 있고 전처리는 파괴적이다. 그럼에도 마음 놓고 규칙을 바꿔볼 수 있는 것은 **원본 PDF만 있으면 전부 다시 만들 수 있기 때문**이다. 업로드 단계에서 원자적으로 저장하고 해시로 무결성을 챙긴 것이 여기까지 이어진다.

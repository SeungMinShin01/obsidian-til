# 수집기 23 - 스키마 확장과 옛 DB

> 허브: [[수집기 프로젝트 MOC]]

4컬럼짜리 `jobs`를 15컬럼으로 넓히면서 겪은 것들. 「수집기 06」의 `IF NOT EXISTS`가 이번엔 반대로 작동했다.

## 1. 배운 내용

### 1-1. `IF NOT EXISTS`는 기존 테이블을 고쳐주지 않는다

```
sqlite3.OperationalError: table jobs has no column named url
```

스키마 코드를 바꿨는데 옛 DB 파일이 남아 있었다. `CREATE TABLE IF NOT EXISTS`는 테이블이 이미 있으면 **조용히 넘어간다** — 멱등성을 위해 넣은 그 장치가 스키마 변경 앞에서는 "이미 있으면 맞춰준다"가 아니라 "이미 있으면 아무것도 안 한다"로 작동한다. #멱등성 → [[개념 - 멱등성]]

스키마 변경은 원래 `ALTER TABLE`로 마이그레이션한다. 우리는 DB에 가짜 3건뿐이라 파일을 지우고 새로 만들었다 — **지킬 데이터가 없는 마지막 시점이라 가능한 공짜 재시작**이었다. 진짜 데이터가 쌓인 뒤였다면 이 길은 없다.

같은 에러를 두 번 만났다. 첫 번째는 `del`이 실행 안 된 채 넘어갔기 때문이었고 — 셸 명령도 서 있는 폴더 기준이라 안쪽 `collector\collector`에서 치면 "경로를 찾을 수 없습니다"만 내고 지나간다.

### 1-2. `COLUMNS` 리스트 하나가 진실이다

```python
COLUMNS = ["id", "title", "company", "url", ..., "raw", "first_seen_at"]

placeholders = ", ".join("?" for _ in COLUMNS)
conn.executemany(
    f"INSERT OR IGNORE INTO jobs ({', '.join(COLUMNS)}) VALUES ({placeholders})",
    [[j.get(c, "") if c != "first_seen_at" else seen_at for c in COLUMNS] for j in jobs],
)
```

이전 코드는 컬럼 이름을 SQL 문자열에 한 번, 튜플 순서에 또 한 번 적었다. 「수집기 07」에서 "순서가 어긋나면 조용히 잘못된 데이터"라고 했던 함정이 컬럼 15개가 되면 정말 위험해진다. 이제 이름 목록에서 SQL과 값 순서를 **둘 다 생성**하므로 어긋날 방법이 없다.

f-string으로 SQL을 만들지만 인젝션과는 다른 상황이다 — 끼워넣는 것이 **우리가 정의한 상수**지 바깥에서 온 값이 아니다. 값은 여전히 전부 `?`로 나간다.

`j.get(c, "")`는 어댑터가 어떤 키를 빠뜨려도 빈 문자열로 채운다. `fake.py`처럼 세 필드만 주는 소스도 통과한다 — **소스마다 주는 정보량이 달라도 같은 계약으로 받는다.**

`NOT NULL`은 `title`과 `first_seen_at`에만. 필수는 좁게, 나머지는 관대하게 — `_to_job`에서 `[]`를 `id`에만 쓴 것과 같은 판단이다.

### 1-3. 소스별 테이블로 나누지 않는다

`_to_job`이 하는 일이 정확히 "사이트별 차이를 지우는 것"이다. 사이트별 테이블을 만들면 어댑터에서 지운 차이를 저장소에서 부활시키는 것이다.

| | 한 테이블 | 소스별 테이블 |
| --- | --- | --- |
| 전체 키워드 빈도 | `SELECT ... FROM jobs` | 테이블 수만큼 `UNION ALL` |
| 소스 추가 시 | 코드만 | 테이블 + 모든 쿼리 |

소스별 차이는 갈 곳이 이미 있다 — 어느 사이트 것인지는 `id` 접두사, 그 사이트만 주는 필드는 `raw`.

> **같은 질문을 던지는 대상이면 한 테이블, 다른 질문을 던지는 대상이면 다른 테이블.**

채용공고는 어디서 왔든 같은 질문을 받는다. 5단계의 arXiv 논문은 다른 질문을 받으니 `papers`로 나뉜다. "범용 수집기"의 범용은 테이블 공유가 아니라 배관 공유다.

### 1-4. `id` 접두사가 값을 한 순간

```sql
DELETE FROM jobs WHERE id LIKE 'fake:%'
```

가짜 3건이 진짜 518건 옆에 섞였을 때, 접두사로 골라 지웠다. 소스 단위로 다룰 수 있다는 것이 접두사를 박아둔 이유였고 처음으로 실물이 됐다.

### 1-5. 대문자 상수도 재할당을 막지 않는다

```python
10: SOURCES = [moef]
19: SOURCES = [fake]     ← 옛 줄이 남아 있었다
```

새 줄을 넣고 옛 줄을 안 지우면 **나중 것이 이긴다.** 에러가 아니라서 조용히 — 실행 결과가 `수집 3건`으로 나와서야 알았다. 「수집기 05-1」의 "대문자는 관례일 뿐 언어가 막지 않는다"가 실제 사고로 나온 것이다. 상수를 바꿀 때는 검색으로 같은 이름이 또 있는지 본다.

## 2. 도구가 막힐 때

### 2-1. 따옴표가 세 겹이면 한 줄 명령을 포기한다

PowerShell → 파이썬 → SQL 문자열. `python -c "..."`로 DELETE 하나를 보내려다 두 번 깨졌다. 큰따옴표 안의 `\"`는 PowerShell이 먼저 손대고, 작은따옴표로 감싸면 안의 큰따옴표를 벗겨 넘긴다. 깨지는 방식이 버전마다 달라 시간 낭비 구간이다.

**따옴표가 두 겹 넘게 중첩되면 일회용 파일로 간다.** 쓰고 나서 지운다 — 남겨두면 나중에 실수로 또 돌아간다.

### 2-2. 원격 통로에서 SQLite 쓰기가 막힌 이유

읽기는 되는데 `DELETE`에서 `disk I/O error`가 났다. SQLite는 변경할 때 저널 파일을 만들었다 지우는데, 그 통로는 삭제 권한이 없다. `.git/index.lock` 때와 같은 뿌리다 — **파일을 만들고 지우는 것을 한 쌍으로 쓰는 도구는 삭제가 막힌 곳에서 전부 같은 방식으로 실패한다.**

## 3. 더 나아가 알면 좋은 것

- `ALTER TABLE ADD COLUMN` — 데이터를 지키면서 컬럼 추가
- 마이그레이션 도구 (Alembic 등) — 스키마 버전을 코드로 관리
- `PRAGMA table_info` — 지금 테이블이 실제로 어떤 컬럼인지 확인
- SQLite 저널 모드 (`journal_mode=WAL`)

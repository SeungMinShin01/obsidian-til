# RAG 챗봇 02 - 페이지 경계를 넘는 내용

> 허브: [[RAG 챗봇 프로젝트 MOC]]

**물어본 것:** 한 내용이 페이지 경계를 넘어가면 두 조각이 별개가 되어버리는데 어떻게 해결하는가. 그리고 해결 기법들의 장단점은 무엇인가 — 펌웨어 데이터시트라 정확한 답변이 최우선이다.

## 1. 배운 내용

### 1-1. 겹침이 여기서는 안 통한다

조각을 자를 때 앞 조각의 꼬리를 다음 조각 머리에 겹쳐 넣는 장치가 있다. 문장이 잘려도 둘 중 하나에는 온전히 들어가게 하려는 것이다.

그런데 **겹침은 페이지 안에서만 작동한다.** 청킹을 페이지 단위로 따로 호출하므로, 다음 페이지를 자를 때 앞 페이지의 꼬리는 손에 없다. 정확히 페이지 경계에서만 무력해진다.

```
페이지 안:   [조각0]-겹침-[조각1]-겹침-[조각2]
페이지 사이:  ...앞 페이지 끝] | [다음 페이지 시작...   <- 겹침 없음, 완전 단절
```

### 1-2. 이 구조는 그것을 풀지 않고 감수한다

맞바꾼 것이 있다. 페이지 경계를 넘게 허용하면 그 조각의 출처가 "14~15페이지"가 되는데, 답변 쪽 계약이 페이지 하나를 정수로 받게 되어 있다. 출처를 확정할 수 없으면 "15페이지에서 확인하세요" + 뷰어 페이지 이동이라는 이 챗봇의 존재 이유가 무너진다.

즉 **문맥 연속성을 버리고 출처 확정성을 샀다.**

### 1-3. 완충 장치가 둘 있다

그래도 실제로는 꽤 버틴다.

**여러 조각을 한 번에 가져온다** — 페이지 경계에서 잘린 앞뒤 두 조각은 같은 내용을 다루고 있어 질문 벡터와 둘 다 가깝다. 한쪽만 걸리는 것이 아니라 둘 다 상위에 올라올 확률이 높다.

**답변 모델이 종합한다** — 꺼낸 조각들이 한 프롬프트에 나란히 들어간다.

```
[Page 14]
...동작 전압은
[Page 15]
2.3V에서 5.5V이다...
```

조각은 끊겼지만 읽는 쪽에서는 붙어 있다. 출처도 리스트라 두 페이지를 다 붙일 수 있다.

정리하면 **끊긴 것을 잇는 일을 검색과 답변 단계로 미룬 구조**다. 청킹에서 풀지 않고 뒤에서 푼다.

### 1-4. 그래도 남는 구멍

완충이 안 먹는 경우가 있다.

- **잘린 쪽에 검색 단서가 없을 때** — 뒤 조각이 숫자로만 시작하면 "동작 전압"이라는 말이 앞 조각에만 있어서, 답에 필요한 실제 값이 있는 쪽이 질문과 안 가깝다
- **표가 페이지를 넘을 때** — 데이터시트에서 가장 흔한 경우다. 헤더 행이 앞 페이지에 있고 값만 넘어가면 뒤 조각은 숫자 나열이 되어 의미를 잃는다. 이것은 청킹으로 풀 수 없다

### 1-5. 제대로 푸는 기법 셋 — 고치는 문제가 다르다

먼저 이 구분이 선택의 기준이 된다.

| 기법 | 고치는 오답 유형 | 구현 비용 | 재인덱싱 |
| --- | --- | --- | --- |
| ① 이웃 확장 | 문장이 잘려 **답이 반쪽**이 됨 | 낮음 | 불필요 |
| ② 작게 찾고 크게 주기 | 문맥이 없어 **잘못 해석**함 | 중간 | 필요 |
| ③ 레이아웃 파싱 | 표 구조가 사라져 **숫자를 혼동**함 | 높음 | 필요 |

데이터시트에서 가장 치명적인 것은 셋째다. `Min 2.3 / Typ 3.3 / Max 5.5` 가 `2.3 3.3 5.5` 로 뭉개지면 모델이 틀린 값을 자신 있게 답한다.

**① 이웃 조각 확장**

검색으로 걸린 조각의 앞뒤를 같이 꺼내 답변에 넘긴다.

| 장점 | 단점 |
| --- | --- |
| 인덱싱을 안 건드린다. 검색 뒤 후처리라 지금 구조에 그대로 얹힌다 | 노이즈가 는다. 5개를 뽑으면 실제로는 15조각이 프롬프트에 들어간다 |
| 출처가 안 흔들린다 — 페이지는 검색에 걸린 조각 것으로 확정하고 이웃은 읽기용으로만 넘긴다 | 데이터시트는 **인접 문단이 다른 파라미터**인 경우가 많아, 모델이 옆 숫자를 끌어다 쓸 여지가 생긴다 |
| 페이지 경계를 자연스럽게 넘는다 | **표 문제는 못 푼다.** 헤더가 두 페이지 전에 있으면 이웃 한 칸으로는 못 닿는다 |

정확도 기여는 순증이지만 폭이 크지 않다.

**② 작게 찾고 크게 주기**

작은 조각으로 검색하고, 답변에는 그 조각이 속한 큰 덩어리를 넘긴다.

| 장점 | 단점 |
| --- | --- |
| 검색은 작은 단위가 유리하고(잡음이 적어 벡터가 또렷) 답변은 큰 단위가 유리한데 둘을 동시에 가져간다 | **"큰 덩어리"를 무엇으로 정의하느냐가 전부다.** 페이지로 잡으면 경계 문제가 그대로 남고, 절 단위로 잡으려면 문서 구조 인식이 필요한데 그것이 ③이다 |
| 덩어리 경계가 의미 단위라 이웃 확장보다 노이즈가 덜 섞인다 | 인덱싱을 두 층으로 바꿔야 해 재인덱싱이 필요하다 |
| | 덩어리가 여러 페이지에 걸치면 출처를 하나로 못 정해 대표 페이지 규칙이 따로 필요하다 |
| | 프롬프트가 셋 중 가장 길어진다 |

기여는 크지만 **③이 먼저 되어야 제 성능이 난다.** 단독으로는 절반짜리다.

**③ 레이아웃 인식 파싱**

표를 표로 인식해 추출하고, 페이지를 넘는 표에는 헤더를 복제해 넣는다.

| 장점 | 단점 |
| --- | --- |
| **데이터시트 질문의 대부분이 표에 있다.** 전압·전류·온도·타이밍 전부. 여기를 고치는 효과가 압도적이다 | 파싱 층 교체라 앞단을 전부 다시 검증해야 한다 |
| Min/Typ/Max 구분이 살아나면 **가장 위험한 오답이 근본적으로 줄어든다** | 표 추출이 완벽하지 않다. 병합 셀·각주·다단 헤더·조건부 행이 많아 실패율이 있다 |
| 2단 조판 뒤섞임도 같이 해결된다 | 느리고 무겁다. 도구에 따라 유료 API나 무거운 모델이 필요하다 |
| 조각 자체가 의미 있는 텍스트가 되므로 **검색 품질도 같이 오른다** | **가장 위험한 실패 모드가 여기 있다.** 표가 잘못 추출돼 숫자가 엉뚱한 열에 붙으면 겉보기엔 구조가 잡혀 있어 모델이 더 확신을 갖고 틀린다 |

뭉개진 텍스트는 모델이 "모르겠다"고 하기라도 하는데, 잘못 정렬된 표는 그러지 않는다. 그래서 **검수를 안 하면 오히려 위험하다.**

### 1-6. 정확도가 최우선일 때의 순서

**③ → ② → ①** 이다. 앞이 뒤를 가능하게 하는 구조다.

1. **③ 표 인식** — 데이터시트 정확도의 대부분이 여기 있다. 단 표 추출 결과를 눈으로 검수하는 단계를 반드시 같이 만든다
2. **② 절·표 단위 덩어리** — ③이 되면 덩어리 경계가 자연스럽게 정해진다. 표는 표 전체가 한 덩어리, 서술은 절이 한 덩어리
3. **① 이웃 확장** — 표가 아닌 서술 부분에 대한 보험. 마지막에 얹고 효과가 없으면 빼도 된다

## 2. 추가로 알면 좋은 것

셋보다 먼저 확인할 것이 있다.

이 구조에는 이미 "모르면 모른다고 한다"는 장치가 두 겹 들어 있다 — 거리 상한으로 관련 없는 조각을 버리는 것, 그리고 지어낸 페이지 번호를 걸러내는 것.

정확도가 목표일 때는 **틀린 답보다 "데이터시트에 없습니다"가 낫다.** 펌웨어 쪽은 특히 그렇다 — 잘못된 전압 값 하나가 소자를 태운다. 그래서 거리 상한을 느슨하게 푸는 방향으로는 가지 않는 편이 안전하다.

그리고 셋 중 무엇을 붙이든 **측정할 자리가 먼저 필요하다.** 질문 20~30개와 정답 페이지를 손으로 만들어두면 기법을 하나 붙일 때마다 정확도가 실제로 올랐는지 숫자로 보인다. 없으면 "좋아진 것 같다"로 끝나고 어느 것이 효과가 있었는지 영영 모른다.

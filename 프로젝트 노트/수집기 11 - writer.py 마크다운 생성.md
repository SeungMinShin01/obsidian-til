# 수집기 11 - writer.py 마크다운 생성

> 허브: [[수집기 프로젝트 MOC]]

DB에 쌓인 행을 옵시디언이 읽을 파일로 바꾸는 계층이다. 이 파일이 붙으면서 **수집 → 저장 → 표현**이 처음으로 끝까지 이어졌다.

## 1. 배운 내용

### 1-1. 이 계층이 따로 있는 이유

`store.py`는 DB만 알고 `writer.py`는 마크다운만 안다. 나누는 기준은 「수집기 06 - SQLite 저장 계층」에서 정한 그대로다 — **같은 이유로 바뀌는가.**

- 스키마가 바뀐다 → `store.py`
- 노트 모양을 바꾸고 싶다 → `writer.py`

옵시디언에서 frontmatter 항목 하나를 더 넣고 싶을 때 DB 코드를 열지 않아도 된다.

### 1-2. `render_jobs()` — DB에서 다시 읽는다

```python
def render_jobs(conn: sqlite3.Connection) -> int:
    """저장된 공고를 한 건에 파일 하나씩 만든다. 만든 개수를 돌려준다."""
    JOBS_DIR.mkdir(parents=True, exist_ok=True)

    rows = conn.execute(
        "SELECT id, title, company, first_seen_at FROM jobs ORDER BY first_seen_at"
    ).fetchall()

    for job_id, title, company, first_seen_at in rows:
        path = JOBS_DIR / f"{_safe_name(job_id)}.md"
        path.write_text(
            _to_markdown(job_id, title, company, first_seen_at),
            encoding="utf-8",
        )

    return len(rows)
```

방금 수집한 리스트를 그대로 쓰지 않고 **DB에서 다시 읽는다.** 수집 리스트에는 이미 있어서 무시된 건이 섞여 있고, `first_seen_at`도 DB에 들어간 값이 진짜다.

> 저장된 것이 진실이고, 표현은 저장된 것에서만 만든다.

이렇게 두면 나중에 `writer.py`만 따로 돌려도 결과가 같다. 수집 없이 마크다운만 다시 만들 수 있다.

### 1-3. 매번 전부 다시 쓴다

새로 들어온 것만 쓰지 않고 **모든 행을 매번 다시 쓴다.** 언뜻 낭비 같지만 이 단계에서는 이쪽이 맞다.

- `write_text`는 있으면 덮어쓴다. 몇 번을 돌려도 결과가 같다 → #멱등성 → [[개념 - 멱등성]]
- 템플릿을 고치면 **과거 공고까지 새 모양으로 따라온다.** 새것만 썼다면 옛날 파일은 옛날 모양으로 남는다
- 지금은 3건이라 비용이 없다

수천 건이 되면 바뀐 것만 쓰는 방식으로 옮긴다. 그때 판단하면 되는 것이므로 지금 정하지 않는다.

### 1-4. 튜플 풀기

```python
for job_id, title, company, first_seen_at in rows:
```

`fetchall()`이 돌려주는 건 튜플의 리스트다. `[("fake:1", "백엔드 개발자", ...), ...]` 형태다.

`for row in rows` 하고 `row[0]`, `row[1]`로 꺼낼 수도 있지만, 이렇게 왼쪽에 이름을 나열하면 **한 줄에서 다 풀린다.** 이것을 언패킹이라고 한다.

대신 **`SELECT`의 열 순서와 여기 이름 순서가 맞아야 한다.** 어긋나면 제목 자리에 회사명이 들어가는데, 「수집기 07 - store.py 세기와 넣기」의 `executemany`와 똑같은 종류의 함정이다. 문법 에러가 아니라 조용히 잘못된 결과가 된다.

`row_factory`를 쓰면 이름으로 접근할 수 있어 이 위험이 사라진다. 열이 늘어나면 그때 바꾼다.

### 1-5. `_safe_name()` — 파일명으로 쓸 수 없는 글자

```python
def _safe_name(job_id: str) -> str:
    """파일명으로 쓸 수 없는 글자를 바꾼다."""
    return job_id.replace(":", "_").replace("/", "_")
```

`fake:1`을 그대로 파일명으로 쓰면 윈도우에서 만들어지지 않는다. `:`는 드라이브 문자 구분에 쓰이기 때문이다. `/`는 어느 OS에서든 경로 구분자다.

**id에 소스 접두사를 붙이기로 했으므로**(`saramin:12345`) `:`는 앞으로 계속 나온다. 그래서 이 함수는 임시방편이 아니라 계속 쓰인다.

### 1-6. 밑줄 접두사

`_safe_name`, `_to_markdown` 앞의 `_`는 **이 모듈 안에서만 쓰는 함수**라는 표시다. 파이썬은 이걸 강제하지 않는다. 밖에서 불러도 동작한다.

자바의 `private`처럼 막아주는 것이 아니라 **약속**이다. 다른 파일에서 `writer._to_markdown(...)`을 쓰고 있다면 그건 규칙을 어긴 것이고, 나중에 이 함수 모양을 바꿔도 책임지지 않겠다는 뜻이다.

`render_jobs`만 밑줄이 없다. 바깥에 내놓는 문이 그것 하나라는 의미다.

### 1-7. `_to_markdown()` — 값만 받는 함수

```python
def _to_markdown(job_id: str, title: str, company: str, first_seen_at: str) -> str:
```

이 함수는 `conn`을 받지 않는다. DB도 파일도 모른다. **값을 받아 문자열을 돌려주는 것**이 전부다.

바깥을 건드리지 않으므로 같은 입력에 항상 같은 출력이 나온다. 이런 함수를 순수 함수라고 하고, 나중에 테스트를 붙일 때 가장 쉬운 종류다. DB를 준비할 필요 없이 문자열만 비교하면 된다.

### 1-8. frontmatter가 계약이다

```markdown
---
출처: 자동수집
수집ID: fake:1
회사: 가나테크
작성일: 2026-08-13 09:07:51
tags: [채용]
---
```

`---` 사이의 이 부분을 옵시디언이 **속성**으로 읽는다. 본문이 아니라 메타데이터로 취급되어 검색과 필터에 쓰인다.

문법은 「수집기 02 - YAML과 워크플로우 파일」에서 본 YAML 그대로다. 워크플로우 파일과 같은 형식이 여기서 다시 나온다.

이 항목 이름들은 한번 정하면 **계약**이 된다. 나중에 `회사`를 `기업명`으로 바꾸면 그 항목으로 만들어둔 검색과 대시보드가 전부 깨진다. 그래서 항목 추가는 쉽고 이름 변경은 비싸다.

`tags: [채용]`을 넣어둔 것도 같은 이유다. 나중에 공고가 수백 건이 되면 폴더를 뒤지는 대신 태그로 모은다.

## 2. 추가로 알면 좋은 활용법

### 2-1. 파이프라인이 처음으로 끝까지 이어졌다

```
실행 : 2026-08-13 09:39:17 UTC - 신규 0건, 누적 3건, 마크다운 3건
```

한 줄에 세 계층의 결과가 다 들어 있다. **신규**는 수집과 판정, **누적**은 저장, **마크다운**은 표현이다. 로그 한 줄만 보고 어느 계층이 멈췄는지 알 수 있다.

무인 시스템에서 로그를 이렇게 쓰는 게 중요하다. 사람이 매일 들여다보지 않으므로, 한 줄이 스스로 상태를 설명해야 한다.

### 2-2. 사람이 고친 내용이 날아간다

매번 덮어쓰므로 **생성된 노트에 직접 메모를 적으면 다음 실행에 지워진다.** 지금 구조의 실제 한계다.

해결 방법은 나중에 정한다. 후보는 둘이다.

- 자동 생성 구역과 사람 구역을 표시로 나누고 자동 구역만 갈아끼운다
- 생성 노트는 건드리지 않고, 메모는 그 노트를 링크하는 별도 노트에 쓴다

두 번째가 옵시디언스럽고 코드도 안 늘어난다. 실제로 메모를 적고 싶어지는 시점에 정하면 되는 일이다.

### 2-3. 폴더 이름을 한글로 둔 것

`data/채용`으로 만들었다. 옵시디언에서 그대로 보이는 이름이라 읽기 좋지만, git과 URL에서 인코딩되어 나타난다. 지금은 문제가 없고, 나중에 대시보드에서 경로를 다룰 때 한 번 걸릴 수 있는 지점이다.

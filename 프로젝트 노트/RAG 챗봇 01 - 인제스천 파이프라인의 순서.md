# RAG 챗봇 01 - 인제스천 파이프라인의 순서

> 허브: [[RAG 챗봇 프로젝트 MOC]]

**물어본 것:** PDF를 받고 청킹 → 임베딩 → 벡터 DB 저장, 이 순서가 맞는가.

## 1. 배운 내용

### 1-1. 맞다. 다만 사이에 두 단계가 더 있다

```
PDF 저장 → 파싱(텍스트 추출) → 전처리 → 청킹 → 임베딩 → 벡터 DB 저장
```

빠뜨렸던 것이 **파싱**과 **전처리**다. 청킹은 이미 문자열이 된 뒤의 작업이므로, 그 문자열을 만드는 단계와 다듬는 단계가 앞에 반드시 있어야 한다.

| 순서 | 하는 일 |
| --- | --- |
| 1 | 원본 PDF를 디스크에 저장 |
| 2 | 페이지별 텍스트 추출 |
| 3 | 머리말·꼬리말·페이지 번호 정리 |
| 4 | 토큰 기준으로 청크 분할 |
| 5 | 청크를 벡터로 변환 |
| 6 | 벡터와 원문·메타데이터를 저장 |

파이프라인을 지휘하는 파일에 1~5번 주석이 이 순서 그대로 붙어 있다.

### 1-2. 갈래가 둘이다

한 덩어리로 보면 헷갈리는데, 실제로는 도는 시점이 다른 두 흐름이다.

```
[인제스천]  PDF 업로드 → ... → 벡터 DB 저장
[질의응답]  질문 → 질문 임베딩 → 벡터 DB 검색 → 청크 목록 → 답변 생성
```

인제스천은 **문서를 올릴 때 한 번** 돌고, 질의응답은 **질문할 때마다** 돈다. 둘을 잇는 것은 코드가 아니라 벡터 DB에 남은 데이터다. 인제스천이 미리 저장해두지 않으면 질의응답은 꺼낼 것이 없다.

## 2. 더 나아가 알면 좋은 것

- 단계마다 파일이 나뉘어 있는 이유 — 답변이 이상할 때 어느 단계에서 품질이 깨졌는지 중간 산출물로 확인하기 위해서다
- 다음에 볼 키워드: 업로드 응답을 먼저 주고 처리를 뒤로 미루는 방식(백그라운드 작업과 상태 폴링)

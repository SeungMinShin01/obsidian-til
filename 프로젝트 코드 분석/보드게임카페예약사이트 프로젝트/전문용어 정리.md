# 전문용어 정리

분석 노트에 나온 용어를 모은 사전이다. 각 용어마다 **뜻 → 이 프로젝트에서 실제로 쓰인 자리 → 기초 지식과 어떻게 이어지는지** 순서로 정리했다. 더 파고들 학습 항목은 [[보드게임카페예약사이트 프로젝트에서 배울 것]] 으로 이어진다.

## 1. 데이터베이스

### 커넥션 풀 (Connection Pool)

DB 연결을 미리 여러 개 만들어두고 요청들이 빌려 쓰고 반납하는 방식. 연결 하나를 새로 맺는 데 TCP 3-way 핸드셰이크 + 인증 왕복이 들기 때문에, 요청마다 새로 만들면 그 비용이 매번 반복된다.

```javascript
// config/db.js — 이 프로젝트의 유일한 DB 진입점
const db = mysql.createPool({ connectionLimit: 10, waitForConnections: true, queueLimit: 0 });
```

모든 라우트가 이 파일 하나를 `require`해서 썼다. `connectionLimit: 10`이면 동시에 쿼리 10개까지, 11번째는 `waitForConnections`로 대기한다. **활용** — 트랜잭션을 쓸 때는 `db.query()`가 아니라 `db.getConnection()`으로 연결 하나를 점유해야 같은 연결에서 BEGIN~COMMIT이 이어진다. 풀의 존재를 모르면 트랜잭션이 왜 안 묶이는지 알 수 없다.

기초 연결: SQL day01 데이터베이스 기초 의 "DBMS에 접속한다"가 실제로는 이 풀을 거치는 일이다.

### 파라미터 바인딩과 SQL 인젝션

쿼리의 값 자리에 `?`를 두고 값을 배열로 따로 넘기면, 드라이버가 값을 문자열로 이어붙이지 않고 이스케이프해서 넣는다. 입력값에 `' OR 1=1 --` 같은 SQL 조각이 들어와도 문자열 데이터로 취급된다.

```javascript
db.query("SELECT * FROM users WHERE user_id = ?", [user_id]);   // 안전
db.query(`SELECT * FROM users WHERE user_id = '${user_id}'`);   // 인젝션 통로
```

이 프로젝트는 값 자리는 전부 바인딩으로 지켰다. 뚫린 곳은 값이 아니라 **구조가 들어가는 자리**였다 → 아래 화이트리스트.

### 화이트리스트 (Allow-list)

`ORDER BY ${컬럼명}`처럼 컬럼명·테이블명은 바인딩이 불가능하다(값이 아니라 SQL 구조이기 때문). 그래서 허용 목록에 있는 값만 통과시킨다.

```javascript
// boardgames.js — 바인딩이 안 되는 자리를 지키는 유일한 방법
const validColumns = ["likes", "difficulty", "game_id"];
if (!validColumns.includes(sortBy)) return res.status(400).json({ error: "..." });
db.query(`SELECT * FROM board_game ORDER BY ${sortBy} ${sortOrder}`);
```

**활용** — 정렬·필터·테이블 선택처럼 "사용자 입력이 SQL 구조를 고르는" 모든 API에 같은 패턴이 필요하다. 블랙리스트(금지 목록)는 우회가 가능해서 항상 화이트리스트로 짠다.

### 트랜잭션 · ACID · 경쟁 상태

트랜잭션은 여러 쿼리를 "전부 성공 아니면 전부 취소"로 묶는 단위이고, ACID는 그 보장 목록이다 — 원자성(Atomicity)·일관성(Consistency)·격리성(Isolation)·지속성(Durability).

이 프로젝트의 예약 생성은 `빈 방 확인 → INSERT` 두 단계가 트랜잭션 없이 떨어져 있다. 두 요청이 동시에 들어오면 둘 다 "방 비어있음"을 보고 둘 다 INSERT한다 — 이게 **경쟁 상태(race condition)** 다. 격리성이 없어서 생기는 문제.

```javascript
// 이렇게 이어졌어야 했다
const conn = await db.getConnection();
await conn.beginTransaction();
await conn.query("SELECT ... FOR UPDATE");   // 행 잠금 — 다른 트랜잭션은 대기
await conn.query("INSERT ...");
await conn.commit();
```

기초 연결: SQL day01 데이터베이스 기초 에서 개념으로 배운 ACID가, 예약·결제·재고처럼 "확인하고 쓰는" 코드에서 실무 문제가 된다. 콘솔 게시판( Java day06 생성자와 콘솔 게시판 )에서는 사용자가 한 명이라 이 문제가 존재하지 않았다 — **동시성은 사용자가 둘이 되는 순간 시작된다.**

### N+1 문제

목록 1번 + 항목마다 1번씩, 반복문 안에서 쿼리가 나가는 패턴. `availabilityRoutes.js`가 30분 슬롯 24개를 돌며 슬롯마다 `COUNT` 쿼리를 날린다 — 요청 하나에 쿼리 24번.

```javascript
while (startTime.isBefore(endTime)) {
  const [conflicts] = await db.query("SELECT COUNT(*) ...");   // 반복문 안의 쿼리
  startTime.add(30, "minutes");
}
```

**활용** — "반복문 안의 `await db.query`"가 보이면 무조건 의심. 해법은 두 방향: ① 전체를 한 번에 가져와 메모리에서 나누기, ② `GROUP BY`로 DB에서 집계를 끝내기. ORM을 쓰면 연관 로딩(lazy loading)이 N+1을 몰래 만들기 때문에 더 중요해진다.

기초 연결: SQL day03 DML과 조인 의 JOIN·GROUP BY가 정확히 이 문제의 해법 도구다.

### 소프트 삭제 (Soft Delete)

행을 `DELETE`하지 않고 `is_deleted = 1` 플래그만 세운다. `reservationController`의 예약 취소가 이 방식이고, 조회 쿼리들은 전부 `WHERE is_deleted = 0`을 달고 다닌다.

**활용** — 취소 내역·탈퇴 회원처럼 "지웠지만 기록은 필요한" 데이터에 쓴다. 대가는 모든 조회에 조건이 붙는다는 것 — 하나라도 빼먹으면 지운 데이터가 화면에 나온다. 뷰(VIEW)로 `WHERE is_deleted = 0`을 감싸두면 빼먹을 일이 없어진다.

### 업서트와 멱등성

업서트 = INSERT 하되 이미 있으면 UPDATE. 멱등성 = 같은 작업을 몇 번 반복해도 결과가 같은 성질.

```sql
-- processCrawledData.js — 몇 번을 돌려도 게임 수가 안 늘어난다
INSERT INTO board_game (...) VALUES (...)
ON DUPLICATE KEY UPDATE game_name_kr = VALUES(game_name_kr), ...
```

크롤러 파이프라인은 수집(Python dict 병합)과 적재(업서트) 양쪽 다 멱등이라, 실패하면 그냥 다시 돌리면 된다. **활용** — 배치 작업·재시도 로직·웹훅 수신처럼 "중복 실행될 수 있는" 모든 코드의 설계 기준. `ON DUPLICATE KEY`가 동작하려면 UNIQUE 제약이 먼저 있어야 한다는 점에서 SQL day02 테이블과 제약조건 과 직결된다.

### 중간 테이블 · UNIQUE 제약 · 비정규화

유저-게임 추천은 N:M 관계다. `game_likes(user_id, game_id)` **중간 테이블**로 풀었다. 중복 추천 방어는 애플리케이션이 SELECT로 확인하는데, 동시 요청이면 뚫린다 — `(user_id, game_id)`에 **UNIQUE 제약**을 걸면 DB가 최종 방어선이 된다.

`board_game.likes` 컬럼은 사실 `COUNT(game_likes)`로 계산 가능한 값을 성능 때문에 따로 저장한 **비정규화**다. 어긋날 수 있으므로 재계산 쿼리를 준비해두는 것까지가 한 세트.

기초 연결: SQL day02 테이블과 제약조건 의 정규화·제약조건이 "언제 일부러 어기는가(비정규화)"까지 포함해서 실전이 된다.

### 페이지네이션 — 오프셋 vs 커서

```sql
-- 오프셋 방식 (이 프로젝트)
SELECT ... ORDER BY game_id DESC LIMIT 20 OFFSET 40;
-- 커서 방식 (다음 단계)
SELECT ... WHERE game_id < :마지막ID ORDER BY game_id DESC LIMIT 20;
```

오프셋은 구현이 쉽지만 `OFFSET 10000`이면 DB가 10,000행을 만들어 버리고 시작한다. 커서는 마지막으로 본 ID에서 이어가서 깊이와 무관하게 빠르고, 스크롤 중 데이터가 추가돼도 중복이 안 생긴다. **무한 스크롤에는 커서가 정합** — 이 프로젝트의 목록 중복 표시 문제도 커서였다면 구조적으로 없었다.

## 2. 인증과 보안

### 해싱 (bcrypt)

단방향 변환. 해시에서 원문을 되돌릴 수 없고, 검증은 "입력을 같은 방식으로 해시해서 해시끼리 비교"로 한다. bcrypt는 여기에 **솔트**(같은 비밀번호도 다른 해시가 되게 하는 난수)와 **비용 계수**(고의로 느리게 만들어 무차별 대입을 비싸게)를 더한 비밀번호 전용 해시다.

```javascript
// 이 프로젝트: user.password !== password  (평문 비교)
// 이어졌어야 하는 것:
const hash = await bcrypt.hash(password, 10);      // 가입 — 10이 비용 계수
const ok = await bcrypt.compare(password, user.password);   // 로그인
```

`bcryptjs`가 설치까지 돼 있었다. 암호화(양방향, 복호화 가능)와 해싱(단방향)을 구분하는 것이 출발점 — 비밀번호는 복호화할 필요가 없으므로 해싱이 맞다.

### JWT (JSON Web Token)

서버가 서명한 자기증명 토큰. `헤더.페이로드.서명` 세 부분이고, 페이로드에 `{ user_id, is_admin }` 같은 정보를 담는다. 서명이 있어서 클라이언트가 내용을 위조하면 검증에서 걸린다.

이 프로젝트는 로그인 응답을 `localStorage`에 저장하는 게 전부라 서버가 이후 요청의 신원을 모른다. JWT였다면:

```
로그인 → 서버가 토큰 발급 → 클라이언트 보관
이후 요청 → Authorization: Bearer <토큰> → 서버가 서명 검증 → req.user 확보
```

**활용** — `myreservations/:user_id`처럼 URL로 신원을 받는 API가 전부 사라지고, 소유권 검증( `reviewRoutes`의 body `user_id` 문제)의 기준값이 서버 신뢰 값으로 바뀐다. 인증 하나가 API 설계 전체를 바꾼다.

### 미들웨어 체인과 횡단 관심사

Express에서 요청은 `app.use` 순서대로 함수들을 통과한다. 인증·로깅·검증처럼 **모든 기능에 공통으로 걸리는 일(횡단 관심사)** 을 각 라우트에 복붙하지 않고 앞단에 한 번 끼우는 자리다.

```javascript
router.use(requireAdmin);        // adminRoutes 전체가 한 줄로 보호된다
router.get("/users", ...);       // 이 아래는 인증을 신경 쓸 필요가 없다
```

`adminRoutes`가 Facade로 잘 묶여 있었기 때문에, 미들웨어 한 줄이면 됐다는 게 이 프로젝트의 아까운 지점. `reviewRoutes`의 빈 미들웨어(`(req,res,next)=>{next()}`)는 이 자리를 만들어두고 채우지 않은 흔적이다.

### 최소 권한 원칙

필요한 권한만 부여한다. `config/db.js`가 `root`로 접속하는 것의 반대 개념. 애플리케이션 전용 계정을 만들어 `shirhal` DB의 CRUD만 주면, 코드가 뚫려도 피해가 그 DB로 한정된다. 계정·API 키·폴더 권한 어디에나 적용되는 원칙.

## 3. 프론트엔드

### 커스텀 훅

`use`로 시작하는 함수에 상태(useState)와 부수효과(useEffect)를 묶어 컴포넌트 밖으로 꺼낸 것. React의 상태 규칙(훅 호출 순서)을 따르면서 로직을 재사용한다.

이 프로젝트의 핵심 설계 — 훅 8개가 각자 한 책임을 진다. `MainPage.js`(705줄)가 버틸 수 있었던 건 로직이 `useCarousel`로 빠져 있어서다. **활용** — "이 컴포넌트에서 fetch·상태·계산이 스크롤 한 화면을 넘으면 훅으로 뺀다"를 기준으로 삼으면 된다. → [[hooks 분석]]

기초 연결: JS day10 함수 의 클로저가 훅의 동작 원리다 — 훅 안의 상태는 클로저에 갇혀 밖에서 직접 못 만진다.

### 프레젠테이션 컴포넌트

데이터를 props로 받아 그리기만 하는 컴포넌트. `BoardGameDetail({ userId, game, onClose })`가 정확히 이 형태 — 자체 fetch가 없어서 어떤 game 객체를 넣어도 그려지고, 테스트도 렌더링만 보면 된다. 로직(훅) / 화면(컴포넌트) 분리의 화면 쪽 절반이다.

### 낙관적 업데이트

서버 응답을 기다리지 않고 화면을 먼저 바꾸는 기법. 추천 버튼에서 썼다.

```javascript
// useBoardGameList — 응답 전에 likes를 먼저 +1
setBoardGames((prev) => prev.map((g) =>
  g.game_id === gameId ? { ...g, likes: currentLikes + 1 } : g));
```

체감 속도가 즉각적이 된다. **완성 조건은 실패 시 되돌리기(rollback)** — 서버가 409를 주면 +1을 취소해야 하는데 이 부분은 없었다. "낙관"은 성공을 가정한다는 뜻이고, 가정이 틀렸을 때의 처리까지가 패턴의 전부다.

기초 연결: JS day07 객체 의 스프레드(`{ ...g }`)로 새 객체를 만드는 **불변 업데이트**가 전제다 — React는 참조가 바뀌어야 리렌더링한다.

### 무한 스크롤 · 쓰로틀 · 디바운스

무한 스크롤: 바닥 근처에서 다음 페이지를 이어붙이는 UI. 스크롤 이벤트는 초당 수십 번 발생하므로 **쓰로틀**(일정 간격으로 최대 1번만 실행)로 묶었다 — `useBoardGameList`의 lodash `throttle`.

- 쓰로틀: 실행 빈도 제한 — 스크롤·리사이즈에 적합
- 디바운스: 입력이 멈춘 뒤 1번 실행 — 검색창 자동완성에 적합

이 프로젝트의 검색은 디바운스가 없어서 타이핑마다 요청이 나갔다. 두 개를 구분해서 골라 쓰는 것이 포인트.

### StrictMode 이중 실행과 useRef 플래그

React 18의 StrictMode는 개발 모드에서 effect를 **일부러 두 번** 실행한다 — "두 번 실행되면 안 되는 코드"를 개발 단계에서 드러내기 위해서다. 결제 성공 페이지의 예약 POST가 두 번 나가 예약이 두 건 생기는 사고를 실제로 겪었고, 이렇게 막았다.

```javascript
const didSubmit = useRef(false);        // 리렌더링에도 유지, 바꿔도 리렌더링 없음
if (didSubmit.current) return;
didSubmit.current = true;
```

`useState`가 아니라 `useRef`인 이유: 플래그가 바뀌었다고 화면을 다시 그릴 필요가 없기 때문. **화면에 보이면 state, 안 보이면 ref**가 선택 기준이다. 근본 해법은 결제 승인을 서버로 옮겨서 프론트 effect가 부수효과를 만들지 않게 하는 것.

### 라우트 가드와 Context

가드: 라우트 진입 조건을 검사하는 래퍼. `AdminRoute`가 교과서적 구현이었지만 `App.js`에서 적용되지 않았다.

Context: props를 거치지 않고 트리 전체에 값을 내려주는 통로. 이 프로젝트는 그 자리를 `localStorage`가 대신했다 — 어디서든 읽고 쓸 수 있지만, 값이 바뀌어도 **리렌더링이 일어나지 않는다**는 결정적 차이가 있다. 로그인 직후 NavBar가 안 바뀌는 류의 버그가 여기서 나온다. `AuthContext` 하나로 "읽는 곳은 많아도 바꾸는 곳은 한 곳"을 만드는 게 정석.

### CORS와 프록시

브라우저는 다른 출처(스킴+도메인+**포트**)로의 요청을 기본 차단한다. `:3000`(CRA)에서 `:5000`(Express)은 포트가 달라 CORS 대상이다. 해법 두 가지를 다 썼다:

- 개발: `"proxy": "http://localhost:5000"` — 개발서버가 대신 전달, 브라우저는 같은 출처로 인식
- 서버: `cors()` 미들웨어 — 응답에 `Access-Control-Allow-Origin` 헤더

**활용** — 프록시는 개발 전용이라 배포하면 사라진다. 절대경로 하드코딩 4곳이 배포에서 깨지는 이유가 이것. 배포 환경에서는 같은 도메인에 리버스 프록시(nginx)로 `/api`를 백엔드에 붙이는 게 일반적이다.

### 결제 승인(confirm) · 클라이언트 키/시크릿 키

결제 위젯의 성공 리다이렉트는 "사용자가 돌아왔다"는 신호일 뿐, 돈이 움직였다는 증명이 아니다. 증명은 **서버가 시크릿 키로 승인 API를 호출**해서 받는다.

- 클라이언트 키: 위젯을 띄우는 용도, 노출돼도 결제를 확정할 수 없음
- 시크릿 키: 승인·취소·조회 권한, **서버 밖으로 나가면 안 됨**

이 프로젝트는 승인 단계 자체가 없어서 성공 URL 직접 접근으로 무결제 예약이 가능했다. 키 두 개의 역할 구분이 곧 "왜 승인은 서버에서 하는가"의 답이다.

### 정적 import vs 런타임 fetch · 데이터 주도 렌더링

- `src/data/*.js` + import → 빌드 시 번들에 포함. 메뉴·매장처럼 작고 자주 쓰는 데이터
- `public/data/rules.json` + fetch → 실행 중 로드. 크고 가끔 쓰는 데이터

번들 크기와 갱신 주기로 갈랐다. 그리고 NavBar·Beverage가 데이터 객체를 `map`으로 돌려 UI를 만드는 **데이터 주도 렌더링**이라, 메뉴 추가가 JSX 수정 없이 끝난다.

기초 연결: JS day07 객체 의 "구조가 내용을 담는다" — `summaryData.js`의 평평한 문자열 배열이 계층을 못 담아 화면이 단조로워진 것이 반례다.

## 4. 설계 패턴

### 도메인 단위 모듈화

기술 계층(components/utils/api)이 아니라 업무 영역(예약·게임·지원)으로 나누는 것. README의 기능 4축이 프론트 폴더·백엔드 라우트·DB 테이블까지 일관되게 이어졌다. "예약을 고친다 = `Reservation/` + `reservations.js`를 본다"가 성립하는 이유.

### MVC와 Repository

- **MVC**: Model(데이터)-View(화면)-Controller(중재). 이 프로젝트의 `routes → controllers`가 C, React가 V, `models/`가 M이 될 예정이었다.
- **Repository**: 데이터 접근만 모은 층. 상위 계층은 SQL을 모른다.

`models/Notice.js`가 Repository의 시작이었지만 컨트롤러가 그걸 쓰지 않아 미완으로 남았다. Java day09 MVC 종합예제 에서 `BoardDAO`로 완성해본 구조와 같은 것 — **자바로 배운 구조를 JS로 옮기다 만 상태**라는 게 정확한 진단이다.

### Facade

여러 모듈을 단순한 입구 하나로 감싸는 패턴. `adminRoutes.js`가 컨트롤러 6개를 `/api/admin/*` 뒤로 감췄다. 소비자(관리자 화면)는 내부 구성을 모른다. 부수 효과: 입구가 하나라서 인증 미들웨어도 한 줄이면 됐다(안 걸었지만).

### Strategy

조건에 따라 알고리즘을 갈아끼우는 패턴. `useBoardGameList`가 검색/정렬/필터/기본에 따라 다른 엔드포인트를 고르는 if-else 사슬이 원형이다. 분기가 늘면 `{ 조건: 전략 }` 객체 매핑으로 진화시킨다.

기초 연결: JS day04 조건문 의 "if-else가 길어지면 구조를 의심한다"의 다음 단계다.

### Guard

진입 조건 검사 후 통과/차단. `AdminRoute`(화면), `requireAdmin` 미들웨어(서버) — 같은 패턴이 프론트와 백엔드에서 각각 필요하다. **프론트 가드는 UX, 서버 가드가 보안**이라는 역할 차이가 이 프로젝트의 교훈.

## 5. 프로세스

### ETL과 정제 경계

Extract(수집)-Transform(정제)-Load(적재). 크롤러 파이프라인이 축소판이다: Selenium 수집 → JSON → 난이도 매핑·시간 정규화 → 업서트. 외부 표현(`very easy`)이 **정제 경계 안쪽으로 새지 않게** 막은 것이 핵심 — 서비스 코드 어디에도 영어 난이도가 없다.

### 스모크 테스트

"일단 켜지고 호출은 되는가"만 확인하는 최소 테스트. `adminController.js`의 `db` require 누락(호출 즉시 죽는 코드)이 커밋돼 있었다는 건 이 최소 검증도 없었다는 뜻이다. supertest로 전 엔드포인트를 한 번씩 GET하는 테스트 하나가 시작점.

### 직렬화 규약

API 응답의 통일된 모양. 이 프로젝트는 6가지 형식이 섞여서 프론트에 `if (!Array.isArray(data))` 같은 방어 코드를 만들었다. `{ success, data, message }` 하나로 정하면 프론트 에러 처리를 axios 인터셉터 한 곳에 모을 수 있다. **규약은 코드보다 먼저 정하는 게 싸다.**

# 더 나아가기 - 서버 상태와 결제

프론트가 손으로 만든 것들(원격 데이터 관리 · localStorage 세션 · 결제 연동)을 정식 도구와 정석 흐름으로 바꾸는 학습 주제.
허브: [[보드게임카페예약사이트 프로젝트에서 배울 것]]

## 1. TanStack Query — 직접 만들어봤으니 배울 타이밍

`useBoardGameList`( [[hooks 분석]] )가 손으로 구현한 것의 목록: 원격 데이터 fetch, 로딩·에러 상태, 페이지 누적, 무한 스크롤, 추천 캐시, 낙관적 업데이트. **이게 전부 TanStack Query의 기능 목록과 일치합니다.** 직접 만들어본 지금이 "라이브러리가 뭘 대신해주는지" 정확히 보이는, 배우기 가장 좋은 시점입니다.

### 핵심 개념

**서버 상태와 클라이언트 상태는 다른 것이다** — 이 구분이 라이브러리의 존재 이유입니다.

| | 클라이언트 상태 | 서버 상태 |
| --- | --- | --- |
| 예 | 모달 열림, 선택된 탭 | 게임 목록, 예약 내역 |
| 원본 | 브라우저 메모리 | 서버 DB |
| 특성 | 항상 최신 | **가져온 순간부터 낡기 시작** |
| 도구 | useState / Context | TanStack Query |

"낡을 수 있는 데이터"에는 캐시 수명(`staleTime`), 재검증(창 포커스 시 refetch), 중복 요청 합치기가 필요한데, useState로는 전부 수동입니다.

### 이 프로젝트 코드와의 대응

```javascript
// 손으로 만든 것                     // 라이브러리로
const [games, setGames] = useState([]);
const [loading, setLoading] = useState(false);
useEffect(() => { fetch... }, [page]);
                                      const { data, isLoading, fetchNextPage } =
                                        useInfiniteQuery({
                                          queryKey: ["games", filter, search],
                                          queryFn: ({ pageParam }) => fetchGames(pageParam),
                                          getNextPageParam: (last) => last.nextPage,
                                        });
```

낙관적 업데이트도 패턴으로 제공됩니다 — `onMutate`(스냅샷 찍고 먼저 반영) / `onError`(스냅샷으로 복원) / `onSettled`(재검증). [[공부할 코드 - React 패턴]] 에서 직접 만든 롤백 연습과 1:1로 대응하므로, 그 연습을 먼저 하고 라이브러리로 다시 쓰면 비교가 선명합니다.

**연습**: `useBoardGameList` 하나를 `useInfiniteQuery`로 다시 쓰기. 지워지는 코드 줄 수를 세어보는 것 자체가 학습입니다.

## 2. AuthContext — 전역 상태를 한 곳으로

localStorage 직접 읽기가 NavBar·예약 폼·문의 폼·관리자 가드 등 곳곳에 흩어진 것( [[App과 공통 레이아웃 분석]] )을 Context로 모읍니다.

```javascript
const AuthContext = createContext(null);

export function AuthProvider({ children }) {
  const [user, setUser] = useState(() => 저장된_세션_복원());
  const login = async (id, pw) => { /* API → setUser → 저장 */ };
  const logout = () => { setUser(null); /* 정리 */ };
  return <AuthContext.Provider value={{ user, login, logout }}>{children}</AuthContext.Provider>;
}

export const useAuth = () => useContext(AuthContext);   // 소비 훅
```

### 배우는 것

- **"읽는 곳은 많아도 바꾸는 곳은 한 곳"** — login/logout만이 상태를 바꾼다. localStorage는 Provider 내부 구현으로 숨는다
- **리렌더링 연결** — localStorage는 값이 바뀌어도 화면이 안 바뀌지만, Context 값은 state라서 로그인 직후 NavBar가 즉시 바뀐다. 이 차이를 직접 체험하는 것이 핵심
- `AdminRoute`( [[components 분석 - Login과 Admin]] )도 `useAuth().user?.is_admin`으로 다시 쓰면, 콘솔 조작으로 뚫리는 문제는 그대로지만(최종 방어는 서버 — [[더 나아가기 - 인증과 보안]] ) 상태 일관성은 잡힌다

기초 연결: Context의 동작(Provider 아래 트리에 값 전달)은 JS day07 객체 의 참조 공유를 React가 구조화한 것입니다.

## 3. 결제 서버 승인 — 리다이렉트는 증명이 아니다

현재 흐름의 구멍( [[components 분석 - Reservation과 결제]] ): 성공 URL 도착만 믿고 예약을 넣어서, 주소창에 성공 URL을 직접 치면 무결제 예약이 생깁니다.

### 정석 흐름

```
[1] 예약 폼 제출 → 서버에 가예약 생성 (상태: pending, orderId 발급, 금액 확정)
[2] 프론트: orderId·금액으로 결제 위젯 실행
[3] 성공 리다이렉트 (paymentKey, orderId, amount 쿼리)
[4] 프론트 → 서버: 세 값 전달
[5] 서버: 가예약 조회 → 금액 대조 → Toss 승인 API 호출 (시크릿 키)
[6] 승인 성공 → 예약 확정 (pending → confirmed)
```

각 단계가 막는 공격을 대응시키면 설계가 암기가 아니라 논리가 됩니다.

| 공격 | 막는 단계 |
| --- | --- |
| 성공 URL 직접 접근 | [5] 승인 API — 결제 기록이 없으면 실패 |
| 금액 변조 (1000원 결제로 5만원 예약) | [5] 가예약 금액과 대조 |
| 새로고침 중복 제출 | [6] 이미 confirmed면 무시 — 상태 전이가 멱등 |
| 시크릿 키 탈취 | 키가 서버에만 있음 — [[더 나아가기 - 인증과 보안]] 의 환경변수 |

### 부수 학습 — 상태 기계

가예약의 상태 전이(`pending → confirmed / expired / cancelled`)를 설계하는 것 자체가 **상태 기계** 연습입니다. "pending인 채 30분 지나면 만료"까지 넣으면 배치 작업( [[공부할 코드 - SQL과 데이터]] 의 멱등성)과도 연결됩니다. 지금 localStorage로 페이지 간 데이터를 옮기는 방식( `reservationData` 전달)이 통째로 사라지는 것도 확인 포인트 — **서버에 상태가 있으면 클라이언트가 나를 필요가 없습니다.**

# 더 나아가기 - 동시성과 트랜잭션

예약 생성의 경쟁 상태( [[보드게임 - routes 분석 - 예약|routes 분석 - 예약]] )가 가리키는 학습 주제. SQL day01 데이터베이스 기초 의 ACID 개념을 실행 코드로 내려보는 단계입니다.
허브: [[보드게임카페예약사이트 프로젝트에서 배울 것]]

## 왜 이 프로젝트에서 출발하는가

문제가 되는 코드가 명확합니다.

```javascript
const { room_id } = await assignRoom(...);        // ① 빈 방 확인
await db.query("INSERT INTO reservations ...");    // ② 삽입
```

①과 ② 사이의 몇 ms에 다른 요청이 끼어들면 같은 방에 예약 두 건이 들어갑니다. 콘솔 게시판( Java day06 생성자와 콘솔 게시판 )에서는 사용자가 한 명이라 존재하지 않던 문제 — **동시성은 사용자가 둘이 되는 순간 시작됩니다.** 추천 기능의 확인-삽입도 같은 구조로 뚫립니다( [[routes 분석 - 보드게임과 리뷰]] ).

## 학습 순서

### 1단계 — 경쟁 상태를 직접 재현한다

고치기 전에 먼저 터뜨려봅니다. 이게 가장 좋은 첫 실험입니다.

```javascript
// 같은 시간대 예약 20개를 동시에 발사
await Promise.all(
  Array.from({ length: 20 }, (_, i) =>
    axios.post("/api/reservations", { ...같은시간대, user_id: `u${i}` })
  )
);
// → 같은 방에 몇 건이 들어갔는지 SELECT로 확인
```

"이론상 문제"가 "재현되는 버그"로 바뀌면 이후의 모든 개념이 실감으로 붙습니다.

### 2단계 — 트랜잭션 기본 동작

```javascript
const conn = await db.getConnection();   // 풀에서 연결 하나를 점유
try {
  await conn.beginTransaction();
  await conn.query("INSERT ...");
  await conn.query("UPDATE ...");
  await conn.commit();                   // 전부 확정
} catch (e) {
  await conn.rollback();                 // 전부 취소
  throw e;
} finally {
  conn.release();                        // 풀에 반납 — 잊으면 풀 고갈
}
```

`db.query()`가 아니라 `getConnection()`인 이유: 풀은 쿼리마다 아무 연결이나 골라주는데, BEGIN과 COMMIT이 **같은 연결**에서 실행돼야 하나의 트랜잭션이 되기 때문입니다. 커넥션 풀( [[보드게임 - 전문용어 정리|전문용어 정리]] )을 아는 것이 전제인 이유.

`release()` 누락 → 풀 10개가 말라서 서버 전체가 멈추는 것도 한 번 일부러 겪어볼 만한 실험입니다.

### 3단계 — FOR UPDATE 행 잠금

```sql
BEGIN;
SELECT room_id FROM rooms
WHERE room_id NOT IN (겹치는 예약의 방들)
LIMIT 1
FOR UPDATE;          -- 이 행들을 트랜잭션 끝까지 잠근다
INSERT INTO reservations ...;
COMMIT;
```

`FOR UPDATE`가 붙으면 다른 트랜잭션의 같은 행 `FOR UPDATE`/`UPDATE`는 **이 트랜잭션이 끝날 때까지 대기**합니다. 확인과 삽입 사이에 끼어들 수 없게 되는 것 — 격리성(I of ACID)을 코드로 쓰는 방법입니다.

**실험**: 터미널 두 개에 mysql 클라이언트를 열고, 한쪽에서 `BEGIN; SELECT ... FOR UPDATE;` 한 뒤 커밋하지 않고, 다른 쪽에서 같은 행을 `FOR UPDATE`로 조회 — 두 번째가 멈춰서 기다리는 것을 눈으로 확인합니다. 첫 쪽이 `COMMIT`하는 순간 풀립니다.

### 4단계 — 격리 수준

MySQL 기본값은 REPEATABLE READ입니다. 수준별로 허용되는 이상 현상이 다릅니다.

| 수준 | 더러운 읽기 | 반복 불가 읽기 | 팬텀 |
| --- | --- | --- | --- |
| READ UNCOMMITTED | O | O | O |
| READ COMMITTED | X | O | O |
| REPEATABLE READ (기본) | X | X | △(잠금으로 방지) |
| SERIALIZABLE | X | X | X |

전부 외울 필요는 없고, "기본값이 무엇이고 내 코드가 어떤 이상 현상에 노출되는가"를 답할 수 있으면 됩니다. 수준을 올릴수록 안전하지만 대기가 늘어난다는 트레이드오프가 본질입니다.

### 5단계 — 낙관적 잠금 vs 비관적 잠금

- **비관적**: 충돌을 가정하고 미리 잠근다 — `FOR UPDATE`. 충돌이 잦은 곳(좌석·재고)에 적합
- **낙관적**: 잠그지 않고 버전 컬럼으로 커밋 시점에 충돌을 감지 — `UPDATE ... WHERE version = 읽었던버전`, 결과가 0행이면 재시도. 충돌이 드문 곳에 적합

프론트에서 만든 낙관적 업데이트( [[보드게임 - 공부할 코드 - React 패턴|공부할 코드 - React 패턴]] )와 이름이 같은 이유를 생각해보면 좋습니다 — 둘 다 "성공을 가정하고 먼저 진행, 틀렸으면 복구"라는 같은 전략입니다.

## DB 제약과의 이중화

트랜잭션은 절차의 방어이고, 제약은 데이터의 방어입니다. 둘을 같이 씁니다.

- `game_likes(user_id, game_id)`에 UNIQUE → 중복 추천의 최종 방어선
- 예약은 UNIQUE로 못 막지만(구간 겹침은 제약으로 표현 불가) → 그래서 잠금이 필수인 것

"제약으로 막을 수 있으면 제약으로, 없으면 잠금으로"가 선택 순서입니다. → SQL day02 테이블과 제약조건

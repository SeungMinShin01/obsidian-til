# 더 나아가기 - 인증과 보안

이 프로젝트의 가장 큰 구멍(평문 비밀번호 · 무인증 API · localStorage 관리자 판정)이 가리키는 학습 주제. 셋이 한 사이클로 이어집니다.
허브: [[보드게임카페예약사이트 프로젝트에서 배울 것]]

## 왜 이 프로젝트에서 출발하는가

문제가 세 층에 걸쳐 있고, 전부 뿌리가 같습니다 — **서버가 요청자의 신원을 모른다.**

| 층 | 현재 상태 | 코드 근거 |
| --- | --- | --- |
| 저장 | 비밀번호 평문 저장·비교 | [[보드게임 - routes 분석 - 인증과 유저|routes 분석 - 인증과 유저]] |
| 세션 | localStorage 문자열이 세션의 전부 | [[보드게임 - components 분석 - Login과 Admin|components 분석 - Login과 Admin]] |
| API | `/api/admin/*` 무인증, 소유권 검증값이 요청 본문에서 옴 | [[보드게임 - routes 분석 - 고객지원과 관리자|routes 분석 - 고객지원과 관리자]] |

목표 상태는 한 줄로 요약됩니다.

```
가입:      bcrypt.hash → 저장
로그인:    bcrypt.compare → jwt.sign → 토큰 응답
이후 요청: Authorization 헤더 → jwt.verify 미들웨어 → req.user
```

## 학습 순서

### 1단계 — 해싱 vs 암호화

- 암호화: 양방향. 키가 있으면 복호화된다. 카드번호처럼 "되돌려야 하는" 데이터용
- 해싱: 단방향. 되돌릴 수 없다. 비밀번호처럼 "비교만 하면 되는" 데이터용

비밀번호는 복호화할 일이 없으므로 해싱이 맞습니다. "비밀번호 찾기"가 아니라 "재설정"인 이유가 이것 — 서비스도 원문을 모릅니다.

### 2단계 — bcrypt의 두 장치

```javascript
const hash = await bcrypt.hash(password, 10);
// $2a$10$N9qo8uLOickgx2ZMRZoMye...  ← 버전$비용$솔트+해시가 한 문자열에
```

- **솔트**: 해시마다 섞이는 난수. 같은 비밀번호 "1234"도 사용자마다 다른 해시가 된다 → 미리 계산한 해시 사전(레인보우 테이블)이 무력화
- **비용 계수**(10): 해시 1회를 고의로 느리게(2^10회 반복). 로그인 1번엔 무시할 수준, 무차별 대입 10억 번엔 치명적

`bcrypt.compare(입력, 저장된해시)`가 솔트를 해시 문자열에서 직접 꺼내 쓰기 때문에 솔트를 따로 저장할 필요가 없습니다.

**연습**: 이 프로젝트에 직접 이식 — `bcryptjs`는 이미 설치돼 있습니다. `authRoutes.js`의 가입·로그인 두 곳만 고치면 되고, 기존 평문 계정은 "다음 로그인 때 해시로 이관"하는 마이그레이션 로직까지 붙여보면 실무 상황(기존 데이터가 있는 채로 방식 변경)의 연습이 됩니다.

### 3단계 — JWT의 구조와 성질

```
eyJhbGc...  .  eyJ1c2VyX2lkIjoi...  .  SflKxwRJ...
   헤더            페이로드                서명
```

- 페이로드에 `{ user_id, is_admin, exp }`를 담는다. **Base64일 뿐 암호화가 아니다** — 누구나 디코드해서 읽을 수 있다. 비밀은 넣지 않는다
- 서명은 `HMAC(헤더+페이로드, 서버비밀키)`. 페이로드를 한 글자라도 고치면 서명이 안 맞는다 → **읽기는 가능, 위조는 불가**가 JWT의 정확한 성질

이 프로젝트의 localStorage `is_admin`과 비교하면 차이가 선명합니다: 지금은 클라이언트가 값을 마음대로 바꿔도 아무도 모르지만, JWT의 `is_admin`을 바꾸면 서명 검증에서 걸립니다.

### 4단계 — 미들웨어로 조립

```javascript
const requireAuth = (req, res, next) => {
  const token = req.headers.authorization?.replace("Bearer ", "");
  if (!token) return res.status(401).json({ message: "로그인이 필요합니다." });
  try {
    req.user = jwt.verify(token, process.env.JWT_SECRET);
    next();
  } catch {
    return res.status(401).json({ message: "토큰이 유효하지 않습니다." });
  }
};
const requireAdmin = (req, res, next) => {
  if (!req.user?.is_admin) return res.status(403).json({ message: "권한이 없습니다." });
  next();
};

// adminRoutes.js — Facade 덕에 두 줄로 전체 보호
router.use(requireAuth, requireAdmin);
```

401(누군지 모름)과 403(누군지 알지만 권한 없음)의 구분도 여기서 몸에 익힙니다.

이 시점에 API 설계가 연쇄적으로 바뀝니다 — `/api/myreservations/:user_id`의 URL 파라미터가 사라지고 `req.user.user_id`를 쓰게 되며( [[보드게임 - routes 분석 - 예약|routes 분석 - 예약]] ), 리뷰 소유권 검증의 기준값도 본문이 아니라 토큰에서 옵니다( [[routes 분석 - 보드게임과 리뷰]] ). **인증 하나가 엔드포인트 절반의 시그니처를 바꾸는** 경험이 이 단계의 핵심입니다.

### 5단계 — 토큰을 어디에 둘 것인가

| 저장 위치 | 약점 | 방어 |
| --- | --- | --- |
| localStorage | XSS — 주입된 스크립트가 토큰을 읽어감 | 애초에 스크립트가 못 읽는 곳으로 |
| httpOnly 쿠키 | CSRF — 브라우저가 쿠키를 자동 전송 | SameSite 속성 + CSRF 토큰 |

정답이 하나로 정해진 논쟁이 아니라 **트레이드오프를 아는 것**이 목표입니다. 실무 관례는 httpOnly 쿠키 + SameSite, 또는 짧은 수명의 access 토큰 + refresh 토큰 조합.

## 함께 정리할 주변 항목

- **최소 권한 원칙** — `config/db.js`의 root 접속을 전용 계정으로( [[보드게임 - server와 config 분석|server와 config 분석]] )
- **환경변수 분리** — `JWT_SECRET`부터 `.env`로. DB 접속 정보와 같은 작업

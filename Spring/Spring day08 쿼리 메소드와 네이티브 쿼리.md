# Spring day08 — 쿼리 메소드와 네이티브 쿼리

> 실습 파일: `day08/exam/TodoEntity.java`, `day08/exam/TodoRepository.java`, `day08/exam/TodoController.java`, `day08/exam/AppStart.java`
> 허브: [[Spring MOC]] · 이전: [[Spring day08 메소드 레퍼런스로 줄인 람다]]

앞의 네 노트는 자바 문법 쪽으로 잠깐 나가 있던 자리였습니다. 호출 표기 넷 → 람다 → 스트림 → 메소드 레퍼런스로 이어지며 "동작을 값으로 넘기는 방법"을 정리했고, 이번 실습에서 다시 스프링 쪽으로 돌아옵니다.

돌아온 자리가 리포지토리 층입니다. 그동안 `extends JpaRepository<엔티티, PK타입>` 한 줄만 적고 몸통은 비워 뒀습니다. 물려받은 `findAll`·`findById`·`save`·`deleteById` 넷으로 실습이 다 됐기 때문입니다. 하지만 그 넷은 "전부 가져오기"와 "번호로 하나 가져오기"뿐이라, **제목으로 찾기** 같은 조건 조회는 처음부터 없었습니다.

이번 실습의 요점은 그 빈칸을 채우는 두 갈래입니다. 하나는 **추상 메소드 이름을 규칙대로 적으면 스프링이 SQL을 만들어 주는 쿼리 메소드**, 다른 하나는 **SQL을 직접 적어 붙이는 네이티브 쿼리**입니다. 정리하면 리포지토리 인터페이스의 빈 몸통에 무엇을 어떻게 적을 수 있는가가 이번 자리의 전부입니다.

## 1. 배운 내용

### 1-1. 실습 한 벌을 다시 네 파일로 잡기

`day08/exam` 패키지에 파일 넷을 둡니다. 앞 실습들에서 반복해 온 배치가 그대로입니다.

| 파일 | 몫 |
| --- | --- |
| `AppStart.java` | 이 실습 묶음의 진입점 자리 |
| `TodoEntity.java` | 표 하나와 짝지을 엔티티 |
| `TodoRepository.java` | 이번 실습의 본체 — 조회 메소드를 적어 보는 자리 |
| `TodoController.java` | 리포지토리를 주입받아 요청과 이을 자리 |

앞의 반복 실습들과 갈리는 지점이 하나 있습니다. 그때는 엔티티 둘·관계 표시·DTO·서비스까지 한 벌을 다 세웠는데, 여기는 **관계도 DTO도 서비스도 없습니다.** 표 하나짜리 엔티티와 리포지토리, 그리고 리포지토리를 들고만 있는 컨트롤러입니다.

이 덜어냄이 의도적인 자리입니다. 관계와 계층을 얹어 두면 조회 메소드 하나를 확인하려 해도 DTO 변환과 서비스 조립을 함께 봐야 합니다. 지금 보려는 것은 **"메소드 이름을 이렇게 적으면 어떤 SQL이 나가는가"** 하나라, 그 사이에 낀 층을 전부 걷어 낸 배치가 확인에는 오히려 낫습니다. 진입점과 컨트롤러가 비어 있는 것도 같은 사정으로 읽힙니다 — 리포지토리 인터페이스를 적는 것이 이번 실습이고, 위층은 자리만 잡아 둔 단계입니다.

`day05` 이후로 표가 계속 둘 이상이었던 것을 생각하면, 표 하나로 돌아온 것 자체가 "이번에 볼 것은 관계가 아니다"라는 표시이기도 합니다.

### 1-2. 표 하나짜리 엔티티

```java
@Entity
@Table(name = "todo")
@Data
@Builder
@AllArgsConstructor
@NoArgsConstructor
public class TodoEntity {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Integer id;
    private String title;
    private String content;
    private Boolean done;
}
```

표시 한 벌이 그동안과 같습니다. `@Entity` 로 표와 짝짓고, `@Table(name = "todo")` 로 표 이름을 정하고, `@Id`+`@GeneratedValue(IDENTITY)` 로 열쇠를 MySQL의 `AUTO_INCREMENT` 에 맡깁니다. 롬복 넷(`@Data`·`@Builder`·`@AllArgsConstructor`·`@NoArgsConstructor`)이 함께 붙는 것도 짝으로 다니는 이유가 그대로입니다 — `@Builder` 만 붙이면 기본 생성자가 사라지고, JPA는 객체를 만들 때 기본 생성자를 요구합니다.

이번 자리에서 눈여겨볼 것은 필드 셋의 **이름**입니다.

| 필드 | 타입 | 이번 실습에서의 몫 |
| --- | --- | --- |
| `id` | `Integer` | PK. 리포지토리 제네릭 두 번째 자리에 그대로 들어감 |
| `title` | `String` | 조회 조건으로 쓸 필드 |
| `content` | `String` | 두 번째 조회 조건 |
| `done` | `Boolean` | 완료 여부 |

쿼리 메소드는 **메소드 이름 안에 필드 이름을 적어 조건을 만듭니다.** 그래서 지금까지는 그냥 "표의 컬럼"이던 필드 이름이, 이번 실습부터는 **메소드 이름의 재료**가 됩니다. `title` 이라는 이름을 골라 둔 순간 `findByTitle` 이라는 메소드 이름이 정해지는 셈입니다.

`done` 을 `boolean` 이 아니라 `Boolean` 으로 둔 것도 앞에서 본 갈림과 같습니다. 래퍼 타입이라야 "아직 정해지지 않음"을 `null` 로 표현할 수 있고, 웹을 사이에 두면 안 보낸 값과 `false` 를 갈라 봐야 하는 자리가 생깁니다.

`create-drop` 설정을 그대로 쓰고 있으므로 이 표는 시드 SQL이 아니라 **엔티티를 근거로 서버가 뜰 때 만들어집니다.** 필드 이름을 고치면 컬럼 이름이 따라 바뀌고, 그러면 이름으로 만든 메소드도 함께 봐야 합니다.

### 1-3. 물려받은 넷 — 아무것도 안 적어도 되는 구간

```java
@Repository
public interface TodoRepository extends JpaRepository<TodoEntity, Integer> {
}
```

이 상태에서 이미 쓸 수 있는 것들이 있습니다. 제네릭 두 자리에 **조작할 엔티티 타입**과 **그 엔티티 PK의 타입**을 적으면, 몸통이 비어 있어도 CRUD 메소드가 내려옵니다.

| 물려받는 메소드 | 하는 일 | 대응 SQL |
| --- | --- | --- |
| `findAll()` | 전부 조회 | `select * from todo` |
| `findById(id)` | PK로 하나 조회 | `select * from todo where id = ?` |
| `save(entity)` | 저장 또는 수정 | `insert` 또는 `update` |
| `deleteById(id)` | PK로 삭제 | `delete from todo where id = ?` |
| `count()` | 줄 수 | `select count(*) from todo` |
| `existsById(id)` | 있는지 확인 | `select ... limit 1` |

여기서 조건이 붙는 조회는 **PK 하나뿐**입니다. `findById` 는 `where id = ?` 이고, 그 밖의 컬럼으로 찾는 길은 이 표에 없습니다. 제목으로 찾고 싶어지는 순간 물려받은 것만으로는 막힙니다.

막힌 자리를 푸는 방법이 세 갈래인데, 이번 실습이 그중 둘을 다룹니다.

1. **쿼리 메소드** — 추상 메소드 이름을 규칙대로 적기 (SQL을 안 적음)
2. **네이티브 쿼리** — `@Query` 로 SQL을 직접 적기
3. (다루지 않음) JPQL·Querydsl·`Specification`

### 1-4. 쿼리 메소드 — 이름이 곧 조건

```java
반환타입 findBy필드명(타입 매개변수명);
```

이 한 줄이 규칙의 전부입니다. `findBy` 뒤에 **엔티티의 필드 이름**을 이어 적으면, 스프링이 시작할 때 그 이름을 읽어 `where 컬럼 = ?` 짜리 쿼리를 만들어 구현체에 넣어 둡니다.

```java
TodoEntity findByTitle(String title);
```

- `find` — 조회하겠다는 뜻
- `By` — 여기서부터 조건이 시작된다는 구분자
- `Title` — 엔티티 필드 `title` 을 가리킴 (첫 글자만 대문자)
- 매개변수 — 조건에 채워질 값

`select * from todo where title = ?` 한 줄이 이름에서 나옵니다. 몸통을 적지 않았는데 동작하는 것은 day04에서 본 구조 그대로입니다 — 스프링이 뜰 때 이 인터페이스를 찾아 구현 객체를 만들어 빈으로 등록하고, 그 과정에서 메소드 이름을 파싱합니다.

이름을 적을 때 걸리는 지점이 둘입니다.

**① 카멜 표기법을 지킬 것.** 필드 `title` → 이름 안에서는 `Title` 입니다. 필드가 `userName` 이면 `findByUserName` 입니다. 단어 경계를 대문자로 잡기 때문에, 대소문자를 흘려 적으면 다른 필드를 찾는 이름이 됩니다.

**② 실제로 있는 필드 이름일 것.** 엔티티에 없는 이름을 적으면 파싱이 실패합니다. 여기서 중요한 것은 **언제 실패하느냐**입니다.

> 이름이 어긋난 쿼리 메소드는 그 메소드를 부를 때가 아니라 **서버가 뜰 때** 걸립니다. 스프링이 시작 시점에 인터페이스를 훑어 구현을 만들면서 이름을 해석하기 때문입니다. 컨트롤러 매핑이 겹칠 때 기동에서 걸리던 것과 같은 성질입니다 — 미리 표를 만들어 두는 구조라 어긋남이 앞으로 당겨집니다.

늦게 터지는 것보다 낫습니다. 다만 처음 만나면 "메소드를 부르지도 않았는데 왜 안 뜨지"로 읽히기 쉬우니, 기동 로그에 리포지토리 이름과 프로퍼티 이름이 함께 찍혀 있으면 이름 규칙부터 보는 편이 빠릅니다.

### 1-5. 조건을 둘로 잇기 — `And` 와 `Or`

필드 하나로 끝나지 않는 조건은 이름 안에서 이어 붙입니다.

```java
List<TodoEntity> findByTitleAndContent(String title, String content);
```

`where title = ? and content = ?` 가 됩니다. 여기서 딸려 오는 규칙이 하나 더 있습니다.

> **이름에 적은 조건 순서가 곧 매개변수 순서입니다.** `TitleAndContent` 라고 적었으면 첫 번째 인수가 `title`, 두 번째가 `content` 로 들어갑니다. 매개변수 이름이 아니라 **자리**로 짝지어지므로, 이름을 바꾸지 않고 매개변수 순서만 뒤집으면 조건이 조용히 뒤바뀝니다.

`And` 자리에 `Or` 를 넣으면 `where title = ? or content = ?` 가 됩니다. 조건 둘을 잇는 표기가 SQL의 논리 연산자와 같은 단어라 읽기는 쉬운데, 이름이 길어질수록 **어디까지가 필드 이름이고 어디부터가 키워드인지**가 눈으로 안 갈리기 시작합니다. 조건 셋을 넘어가면 이름만 봐서는 뜻이 안 잡히는 구간에 들어섭니다. 이 지점이 뒤의 3-1에서 다시 나옵니다.

### 1-6. 반환 타입이 정하는 것

같은 조건이라도 반환 타입을 무엇으로 두느냐가 **몇 줄을 기대하는가**를 말합니다.

| 반환 타입 | 뜻 | 결과가 예상과 다를 때 |
| --- | --- | --- |
| `TodoEntity` | 한 줄이 나올 것으로 본다 | 없으면 `null`, 여러 줄이면 예외 |
| `Optional<TodoEntity>` | 0 또는 1줄 | 없음이 타입에 담김 |
| `List<TodoEntity>` | 몇 줄이든 | 없으면 빈 리스트 |

이 표가 실습에서 헷갈리기 쉬운 자리입니다. **단건 타입으로 받아 두었는데 조건에 맞는 줄이 둘 이상이면 조회 시점에 예외가 납니다.** 이름이 틀린 것은 기동에서 걸리지만, 이쪽은 값이 실제로 여럿일 때만 터지므로 데이터가 쌓인 뒤에야 드러납니다.

그래서 **조건 컬럼에 `unique` 제약이 걸려 있는지**가 단건으로 받아도 되는지의 기준이 됩니다. 제약이 없는 컬럼이면 지금 데이터가 우연히 하나뿐이어도 언제든 둘이 될 수 있으니, `List` 로 받아 두는 편이 안전합니다. 없을 때를 다루는 방식으로도 `List` 쪽이 편합니다 — 빈 리스트는 그대로 `[]` 로 나가지만, `null` 은 부르는 쪽에서 한 번 걸러 줘야 합니다.

`Optional` 은 "없음"을 타입으로 옮기는 갈래입니다. day04에서 `findById` 가 `Optional` 을 돌려주는 이유로 정리한 것과 같은 자리이고, 직접 만드는 쿼리 메소드에도 똑같이 쓸 수 있습니다.

### 1-7. 네이티브 쿼리 — SQL을 직접 적기

이름으로 만들 수 없는 쿼리나, 만들 수는 있어도 이름이 감당 못 하게 길어지는 쿼리는 SQL을 직접 적습니다.

```java
@Query(value = "select * from todo where title = :title", nativeQuery = true)
TodoEntity myquery1(String title);
```

갈리는 지점이 셋입니다.

| | 쿼리 메소드 | 네이티브 쿼리 |
| --- | --- | --- |
| SQL | 이름에서 만들어짐 | 직접 적음 |
| 메소드 이름 | **규칙을 지켜야 함** | **아무거나 가능** |
| 어디를 기준으로 적나 | 엔티티의 **필드 이름** | DB의 **표·컬럼 이름** |

두 번째 줄이 눈에 띄는 갈림입니다. `@Query` 를 붙이는 순간 이름 파싱이 일어나지 않으므로, 메소드 이름은 이름값만 하면 됩니다. 뒤집어 말하면 **이름이 더 이상 무슨 조회인지 말해 주지 않으니** 이름을 잘 지어 둘 값어치가 오히려 커집니다.

세 번째 줄이 더 중요한 갈림입니다. `nativeQuery = true` 는 "이 문자열을 JPA가 해석하지 말고 DB에 그대로 보내라"는 뜻입니다. 그래서 `select * from todo` 의 `todo` 는 **엔티티 이름이 아니라 표 이름**이고, `where title` 의 `title` 도 **필드 이름이 아니라 컬럼 이름**입니다. 지금은 둘이 같아서 티가 안 나지만, `@Column(name = ...)` 이나 카멜↔스네이크 변환이 끼면 갈라집니다.

> 엔티티 필드 이름을 고치면 쿼리 메소드는 컴파일·기동에서 걸리지만, 네이티브 쿼리 문자열은 **컴파일러도 스프링도 안 봅니다.** 문자열 안이 어긋난 것은 그 메소드를 실제로 부를 때 DB가 돌려주는 오류로만 드러납니다. 안전망이 한 겹 없는 자리입니다.

### 1-8. 이름 붙인 파라미터 `:title`

값을 꽂는 자리 표기가 `?` 가 아니라 `:이름` 입니다.

```java
@Query(value = "select * from todo where title = :title and content = :content", nativeQuery = true)
List<TodoEntity> myquery2(String title, String content);
```

`:title` 은 **매개변수 이름으로 짝지어집니다.** 자리가 아니라 이름이 기준이라, 조건 순서와 매개변수 순서가 달라도 이름만 맞으면 제대로 들어갑니다. 조건이 늘어날수록 자리로 세는 것보다 안전합니다.

값이 문자열 이어붙이기가 아니라 **바인딩으로** 들어간다는 점도 그대로입니다. day02에서 `PreparedStatement` 의 `?` 를 볼 때 정리한 것과 같은 자리이고, 값에 따옴표나 SQL 조각이 섞여 들어와도 조건 값으로만 취급됩니다. SQL을 직접 적는 갈래로 왔다고 해서 문자열을 손으로 이어 붙이면 그 안전장치가 사라지므로, **값은 언제나 파라미터로 넘깁니다.**

한 가지 조건이 붙습니다. 이름으로 짝지으려면 **자바 매개변수 이름이 클래스 파일에 남아 있어야** 합니다. 빌드 설정에 따라 이름이 지워지면 짝을 못 찾습니다. 그래서 표준적으로는 `@Param` 을 함께 적습니다.

```java
@Query(value = "select * from todo where title = :title", nativeQuery = true)
TodoEntity findByTitleNative(@Param("title") String title);
```

`@RequestParam(name = ...)` 이 바깥 이름과 자바 이름을 갈라 두던 것과 같은 성질입니다 — 이름이 다른 세계를 건널 때 표기로 못 박아 두는 자리입니다.

### 1-9. 두 갈래를 한 자리에 놓기

같은 조회를 두 방식으로 적어 보면 대비가 선명합니다.

```java
// ① 이름으로
List<TodoEntity> findByTitleAndContent(String title, String content);

// ② SQL로
@Query(value = "select * from todo where title = :title and content = :content", nativeQuery = true)
List<TodoEntity> myquery2(String title, String content);
```

둘은 같은 결과를 냅니다. 그러면 무엇을 기준으로 고르느냐가 남습니다.

| 축 | 쿼리 메소드 | 네이티브 쿼리 |
| --- | --- | --- |
| 적는 양 | 한 줄 | 두 줄 이상 |
| 읽는 사람이 아는 것 | 이름만 읽으면 조건이 보임 | SQL을 읽어야 함 |
| 어긋남이 걸리는 시점 | 서버 기동 | 호출 시점 |
| DB를 바꿀 수 있나 | 바꿔도 그대로 | 방언이 섞이면 손봐야 함 |
| 할 수 있는 것의 범위 | 이름으로 표현되는 것까지 | SQL이 되는 것 전부 |

마지막 줄이 갈림의 근거입니다. 앞의 네 축은 전부 쿼리 메소드 쪽이 낫고, 마지막 하나만 네이티브 쿼리 쪽이 넓습니다. 그래서 순서가 정해집니다 — **이름으로 되면 이름으로 적고, 이름이 감당 못 할 때만 SQL로 내려갑니다.** 처음부터 SQL을 적는 것은 넓은 대신 안전망 네 개를 함께 내려놓는 선택입니다.

정리하면 리포지토리 인터페이스의 빈 몸통에 적을 수 있는 것이 이 두 갈래이고, 둘 다 **구현을 쓰지 않는다**는 점은 같습니다. 하나는 이름이 구현을 부르고 다른 하나는 문자열이 구현을 대신할 뿐, `class` 를 만들어 메소드 몸통을 채우는 일은 여전히 없습니다.

### 1-10. 컨트롤러가 리포지토리를 받아 드는 자리

```java
@RestController
@RequestMapping("/day08/todo")
public class TodoController {
    @Autowired
    private TodoRepository todoRepository;
}
```

주소 앞머리를 클래스에 올려 두고, 리포지토리를 필드로 받습니다. 여기서 두 가지가 눈에 걸립니다.

**① `@Autowired` 필드 주입입니다.** 앞의 실습들에서는 `final` + `@RequiredArgsConstructor` 로 생성자 주입을 써 왔습니다. 둘 다 같은 객체가 들어오지만 갈리는 축이 넷 있습니다.

| 축 | 필드 주입 | 생성자 주입 |
| --- | --- | --- |
| 적는 양 | 표시 한 줄 | 롬복 표시 + `final` |
| `final` 로 굳힐 수 있나 | 못 함 | 됨 |
| 테스트에서 다른 구현 넣기 | 컨테이너나 리플렉션 필요 | 생성자로 그냥 넘김 |
| 의존이 많아질 때 | 필드가 조용히 늘어남 | 생성자가 길어져 눈에 보임 |

빠르게 확인만 할 때는 필드 주입이 짧아 편하고, 오래 갈 코드에는 생성자 주입이 나은 편입니다. 마지막 줄이 특히 그렇습니다 — 생성자가 길어지는 것은 불편이 아니라 **"이 클래스가 너무 많은 일을 한다"가 코드 모양으로 드러나는 신호**입니다.

**② 서비스 층이 없습니다.** 컨트롤러가 리포지토리를 바로 듭니다. 조회 메소드가 무슨 SQL을 내보내는지 확인하는 것이 목적인 실습에서는 층을 하나 걷어 내는 편이 확인이 빠릅니다. 다만 이 배치는 확인용이고, 판단이 끼는 순간(없을 때 어떻게 할지, 두 조회를 이어야 할지) 서비스가 다시 필요해집니다 — 그때가 층을 세울 자리입니다.

## 2. 추가로 알면 좋은 활용법

### 2-1. 이름에 쓸 수 있는 키워드

`And`·`Or` 말고도 이름 안에서 쓸 수 있는 단어가 여럿입니다. 자주 쓰는 것만 모으면 이렇습니다.

| 키워드 | 이름 예 | 만들어지는 조건 |
| --- | --- | --- |
| (없음) | `findByTitle` | `title = ?` |
| `Containing` | `findByTitleContaining` | `title like %?%` |
| `StartingWith` | `findByTitleStartingWith` | `title like ?%` |
| `GreaterThan` | `findByIdGreaterThan` | `id > ?` |
| `Between` | `findByIdBetween` | `id between ? and ?` |
| `IsNull` | `findByContentIsNull` | `content is null` |
| `True` / `False` | `findByDoneTrue` | `done = true` |
| `In` | `findByIdIn` | `id in (?, ?, …)` |
| `Not` | `findByTitleNot` | `title <> ?` |

`Containing` 이 검색창을 만들 때 바로 쓰이는 자리입니다. `%` 를 손으로 붙이지 않아도 되고, 값은 여전히 바인딩으로 들어갑니다.

`findByDoneTrue` 처럼 **값이 이름에 박혀 매개변수가 사라지는** 모양도 있습니다. 조건이 고정이라면 이 편이 부르는 쪽에서 읽기 쉽습니다.

### 2-2. 정렬과 개수 제한도 이름에 담기

```java
List<TodoEntity> findByDoneOrderByIdDesc(Boolean done);
List<TodoEntity> findTop5ByOrderByIdDesc();
```

`OrderBy필드명Asc/Desc` 가 `order by` 절이 되고, `find` 와 `By` 사이의 `Top5`·`First3` 가 개수 제한이 됩니다. `findTop5ByOrderByIdDesc` 처럼 조건 없이 정렬과 개수만 쓰면 `By` 뒤가 비는데, 이 모양도 성립합니다.

이름에 고정으로 박는 대신 인수로 받는 갈래도 있습니다.

```java
List<TodoEntity> findByDone(Boolean done, Sort sort);
Page<TodoEntity> findByDone(Boolean done, Pageable pageable);
```

정렬 기준이 화면에서 바뀌는 자리라면 이쪽이 맞습니다. 메소드를 정렬 기준마다 하나씩 만들지 않아도 됩니다.

### 2-3. `@Query` 에 JPQL 적기

`nativeQuery = true` 를 빼면 같은 `@Query` 가 **JPQL**로 해석됩니다.

```java
@Query("select t from TodoEntity t where t.title = :title")
List<TodoEntity> searchByTitle(@Param("title") String title);
```

갈리는 지점이 명확합니다.

| | JPQL | 네이티브 |
| --- | --- | --- |
| 무엇을 적나 | **엔티티 이름·필드 이름** | 표 이름·컬럼 이름 |
| `select` 대상 | 엔티티 별칭 (`select t`) | `select *` |
| DB를 바꾸면 | 그대로 | 방언 확인 필요 |
| 검사 시점 | 기동 때 파싱됨 | 호출 때 DB가 판정 |

JPQL은 "SQL을 직접 적되 자바 쪽 이름으로 적는" 중간 갈래입니다. 이름으로는 안 되는 조회인데 DB 종속은 피하고 싶을 때 먼저 볼 자리입니다. 실제로 고르는 순서는 **쿼리 메소드 → JPQL → 네이티브** 가 됩니다.

### 2-4. 필요한 컬럼만 — 프로젝션

엔티티를 통째로 받지 않고 일부만 받는 방법이 있습니다.

```java
public interface TodoTitleOnly {
    Integer getId();
    String getTitle();
}

List<TodoTitleOnly> findByDone(Boolean done);
```

getter만 선언한 인터페이스를 반환 타입으로 두면 스프링이 그 자리만 채워 줍니다. `select id, title` 로 좁혀지므로 컬럼이 많은 표에서 값어치가 생깁니다. 목록 화면에 제목만 필요할 때 엔티티 → DTO 변환 자체가 없어지는 갈래이기도 합니다.

`Map<String, Object>` 로 받는 표기도 있는데, 키 이름이 컬럼 이름 그대로 오고 타입이 전부 `Object` 라 꺼내는 쪽에서 형변환이 필요합니다. 받는 쪽이 무엇을 기대하는지가 타입에 안 남으므로, 모양이 정해진 조회에는 인터페이스 프로젝션이나 DTO 쪽이 읽기에 낫습니다.

### 2-5. 값을 바꾸는 쿼리

`@Query` 로 `update`·`delete` 를 적으려면 표시가 둘 더 붙습니다.

```java
@Modifying
@Transactional
@Query("update TodoEntity t set t.done = true where t.id = :id")
int markDone(@Param("id") Integer id);
```

`@Modifying` 이 없으면 조회로 해석되어 실패합니다. 반환값은 **영향받은 줄 수**라, day02에서 `executeUpdate` 가 돌려주던 값과 같은 성질입니다.

주의할 자리가 하나 있습니다. 이 쿼리는 **영속성 컨텍스트를 거치지 않고 DB로 바로 나갑니다.** 그래서 같은 트랜잭션 안에서 이미 읽어 둔 엔티티가 있으면, 그 객체는 옛 값을 들고 있습니다. 변경 감지(더티 체킹)로 고치던 것과 도는 길이 다른 자리입니다. 한 건을 고치는 일이라면 조회 후 setter 쪽이 오히려 안전하고, 여러 줄을 한 번에 고칠 때 이 갈래가 값어치를 갖습니다.

### 2-6. 무슨 SQL이 나갔는지 확인하기

이름으로 만들든 직접 적든, 실제로 나간 쿼리를 눈으로 보는 통로가 있어야 확인이 됩니다. 설정에 이미 들어가 있는 두 줄이 그 자리입니다.

```properties
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true
```

쿼리 메소드는 **적은 코드에 SQL이 안 보이므로** 이 확인이 특히 필요합니다. 이름을 지어 놓고 기대한 조건이 실제로 나갔는지, `like` 에 `%` 가 어느 쪽에 붙었는지는 로그로만 확인됩니다.

바인딩된 값까지 보고 싶으면 파라미터 로그 레벨을 따로 올립니다. 다만 이 설정은 값이 그대로 찍히므로, 개인정보나 비밀번호가 지나가는 자리에서는 켜 두지 않는 편이 안전합니다.

### 2-7. 리포지토리를 어디까지 두고 어디부터 서비스인가

조회 메소드가 늘어나면 "이건 리포지토리에 둘 일인가 서비스에 둘 일인가"가 반복해서 걸립니다. 기준을 한 줄로 두면 이렇습니다.

- **한 번의 조회로 답이 나오면** 리포지토리 메소드 하나
- **조회 결과를 보고 다시 무언가를 하면** 서비스

`제목으로 찾기`는 앞이고, `제목으로 찾아서 없으면 새로 만들기`는 뒤입니다. 뒤쪽은 조회와 저장 사이에 틈이 생기므로 그 자리가 곧 `@Transactional` 이 붙을 자리이기도 합니다. 리포지토리 층이 주는 도구가 결국 "한 번의 질의"까지라, 그 조합으로 안 되는 일은 전부 위층 몫이 됩니다.

## 3. 더 나아가 알면 좋은 것

### 3-1. 이름이 길어지는 것이 갈아탈 신호

쿼리 메소드는 조건이 둘까지는 편하고, 셋을 넘으면 이름이 급격히 나빠집니다.

```java
List<TodoEntity> findByDoneAndTitleContainingAndIdGreaterThanOrderByIdDesc(
        Boolean done, String title, Integer id);
```

문법적으로는 아무 문제가 없는데, 이름만 봐서는 조건이 몇 개인지도 안 세어집니다. 이 지점이 도구를 바꿀 자리입니다.

| 상태 | 갈래 |
| --- | --- |
| 조건 1~2개 고정 | 쿼리 메소드 |
| 조건 3개 이상 고정 | JPQL `@Query` |
| 조건이 **있을 때만** 붙어야 함 | `Specification`·Querydsl |

마지막 줄이 이름으로는 아예 안 되는 자리입니다. 검색 화면에서 사용자가 채운 칸만 조건에 넣으려면 **조건 개수가 실행할 때 정해져야** 하는데, 메소드 이름은 컴파일 시점에 고정입니다. 조건 조합마다 메소드를 하나씩 만드는 방향은 조합 수만큼 늘어나 금방 막힙니다.

`Specification` 은 조건을 객체로 만들어 조립하는 갈래이고, Querydsl은 그것을 자바 코드로 타입 검사까지 받으며 적는 갈래입니다. 둘 다 "조건을 값으로 다룬다"는 점에서, 앞 노트에서 본 **동작을 값으로 넘기는 구조**와 같은 자리에 있습니다.

### 3-2. 네이티브 쿼리를 쓸 때 함께 내려놓는 것들

SQL을 직접 적으면 넓어지는 대신 따라오는 대가가 있습니다.

- **DB에 묶입니다.** 함수·페이징 문법·문자열 처리는 DB마다 갈립니다. 방언이 섞인 쿼리는 DB를 바꿀 때 전부 다시 봐야 합니다
- **검사가 없습니다.** 문자열이라 오타도 컬럼 이름 변경도 컴파일러가 못 잡습니다
- **영속성 컨텍스트를 우회합니다.** 결과가 관리되는 엔티티로 안 들어오는 경우가 있어, 이후 변경 감지가 안 도는 자리가 생깁니다
- **결과 매핑이 손에 걸립니다.** `select *` 로 엔티티 전체를 가져오면 자동으로 매핑되지만, 컬럼 일부만 고르면 무엇으로 받을지 따로 정해야 합니다

그래서 네이티브 쿼리는 **"그것 말고는 방법이 없을 때"** 쓰는 편이 안전합니다. 통계·복잡한 집계·DB 고유 기능이 필요한 자리가 대표적이고, 단순 조건 조회에 쓰면 얻는 것 없이 대가만 치릅니다.

### 3-3. 조회가 늘어나면 함께 오는 것들

조회 메소드를 자유롭게 만들 수 있게 되면 다음 세 가지가 곧 걸립니다.

**① 인덱스.** `where title = ?` 가 빨라지려면 그 컬럼에 인덱스가 있어야 합니다. 줄이 적을 때는 차이가 안 보이다가 데이터가 쌓이면 드러납니다. 조회 조건으로 자주 쓰는 컬럼이 인덱스 후보입니다.

**② 페이징.** `findAll()` 로 전부 가져오는 것은 줄 수가 적을 때만 성립합니다. `Pageable` 을 받아 `Page` 로 돌려주면 줄 수와 쪽 정보가 함께 오고, `limit`·`offset` 이 DB 쪽에서 잘립니다. 앞 노트에서 본 `limit`·`skip` 은 이미 다 가져온 것을 메모리에서 자르는 것이라 성질이 다릅니다.

**③ N+1.** 관계가 있는 엔티티를 목록으로 가져오면, 목록 한 번에 각 줄마다 한 번씩 쿼리가 더 나갑니다. 이번 실습은 표가 하나뿐이라 안 생기지만, 관계가 붙는 순간 조회 메소드 하나가 쿼리 수십 개가 되는 자리입니다. `join fetch`·`@EntityGraph`·`@BatchSize` 가 대응 갈래입니다.

### 3-4. 메소드 이름이 규약이 되는 구조

한 걸음 물러나 보면, 쿼리 메소드는 day03에서 본 구조의 되풀이입니다.

- 애노테이션을 정의하고 → 코드에 붙이고 → 리플렉션으로 읽어 실행하는 흐름
- 컴포넌트 스캔이 클래스를 훑어 빈으로 등록하는 흐름
- 컨트롤러의 매핑 표시를 읽어 주소 표를 만드는 흐름

쿼리 메소드도 같습니다. **약속된 형식으로 이름을 적어 두면 → 스프링이 시작할 때 읽고 → 그에 맞는 구현을 만들어 넣습니다.** 다른 점은 표시가 애노테이션이 아니라 **메소드 이름 자체**라는 것 하나입니다.

이 방식을 규약이 코드를 대신한다(convention over configuration)고 부릅니다. 적을 것이 줄어드는 대신, **규약을 모르면 왜 도는지 알 수 없다**는 대가가 붙습니다. 구현이 없는데 동작하는 코드는 읽는 사람이 규칙을 알고 있다는 전제 위에 서 있습니다. 반복 실습에서 골격을 손으로 만들어 본 것이 이 전제를 채워 주는 자리이기도 합니다.

### 3-5. 다음에 볼 키워드

- `Pageable`·`Page`·`Slice` — 쪽 나누기와 전체 개수를 세지 않는 갈래
- `@EntityGraph`·`join fetch` — N+1을 한 번의 조회로 접기
- `Specification`·Querydsl — 조건을 실행 시점에 조립하기
- `@Modifying`·`clearAutomatically` — 벌크 수정과 영속성 컨텍스트의 어긋남
- `@Transactional(readOnly = true)` — 조회 전용 트랜잭션이 얻는 것
- 인터페이스 프로젝션·DTO 프로젝션·`@Value` 표기
- `exists`·`count` 로 시작하는 이름 — 조회하지 않고 판정만 하기
- `@DataJpaTest` — 리포지토리 층만 떼어 쿼리 확인하기
- 실행 계획(`explain`)과 인덱스 — 나간 SQL이 어떻게 도는지 보기
- `Sort.by`·`Sort.Direction` — 정렬 기준을 값으로 넘기기

## 실습 파일

- `2026B_Spring/springweb/src/main/java/day08/exam/TodoEntity.java` (**표 하나짜리 엔티티** — `@Entity`+`@Table(name="todo")` 로 표와 짝짓고 `@Id`+`@GeneratedValue(IDENTITY)` 로 열쇠를 `AUTO_INCREMENT` 에 맡기는 표시 한 벌, 롬복 넷이 짝으로 붙는 이유가 `@Builder` 만 두면 기본 생성자가 사라져 JPA가 막히는 자리인 점, 필드 `title`·`content`·`done` 의 이름이 이번 실습부터는 표의 컬럼일 뿐 아니라 **메소드 이름의 재료**가 되는 자리, `done` 을 `Boolean` 으로 둬 안 보낸 값과 `false` 를 갈라 보는 갈림, 관계도 DTO도 없이 표 하나로 돌아온 것이 "이번에 볼 것은 관계가 아니다"라는 표시로 읽히는 점)
- `2026B_Spring/springweb/src/main/java/day08/exam/TodoRepository.java` (**이번 실습의 본체** — `extends JpaRepository<TodoEntity, Integer>` 로 물려받는 여섯 메소드의 표와 그중 조건이 붙는 조회가 PK 하나뿐이라 다른 컬럼으로 찾는 순간 막히는 자리, **쿼리 메소드** `반환타입 findBy필드명(타입 매개변수명)` 규칙과 `find`·`By`·필드명 세 토막의 몫·카멜 표기 규칙과 실재하는 필드명이어야 하는 두 조건·이름이 어긋나면 호출이 아니라 **서버가 뜰 때** 걸리는 이유가 스프링이 기동 시점에 인터페이스를 훑어 구현을 만들며 이름을 파싱하는 구조인 점, `And`·`Or` 로 조건을 잇기와 **이름에 적은 조건 순서가 곧 매개변수 순서**라 이름을 그대로 두고 인수만 뒤집으면 조건이 조용히 뒤바뀌는 자리, 반환 타입이 몇 줄을 기대하는지를 말하는 표(`엔티티`·`Optional`·`List`)와 단건으로 받아 둔 조건에 줄이 둘 이상이면 데이터가 쌓인 뒤에야 예외로 드러나는 점·`unique` 제약 유무가 단건으로 받아도 되는지의 기준이 되는 자리, **네이티브 쿼리** `@Query(value=…, nativeQuery=true)` 와 쿼리 메소드가 갈리는 세 축(SQL을 누가 만드나·메소드 이름 규칙의 유무·엔티티 필드 이름 기준인가 DB 표·컬럼 이름 기준인가)·`@Query` 를 붙이면 이름 파싱이 없어져 이름이 자유로워지는 대신 이름이 더는 조회 내용을 말해 주지 않는 점·문자열은 컴파일러도 스프링도 안 보므로 안전망이 한 겹 없는 자리, `:이름` 파라미터가 자리가 아니라 이름으로 짝지어져 순서가 달라도 되는 점과 값이 바인딩으로 들어가 `PreparedStatement` 의 `?` 와 같은 성질인 자리·매개변수 이름이 클래스 파일에 안 남을 수 있어 `@Param` 을 함께 적는 관용, 같은 조회를 두 방식으로 적어 다섯 축으로 견주면 넷은 쿼리 메소드가 낫고 범위 하나만 네이티브가 넓어 **이름으로 되면 이름으로·안 될 때만 SQL로** 라는 순서가 나오는 정리, 두 갈래 모두 `class` 를 만들어 몸통을 채우는 일은 없다는 공통점)
- `2026B_Spring/springweb/src/main/java/day08/exam/TodoController.java` (**리포지토리를 받아 드는 자리** — `@RestController`+클래스 레벨 `@RequestMapping("/day08/todo")` 로 주소 앞머리를 한 자리에 두기, `@Autowired` 필드 주입과 그동안 써 온 `final`+`@RequiredArgsConstructor` 생성자 주입이 갈리는 네 축의 표와 생성자가 길어지는 것이 불편이 아니라 "이 클래스가 너무 많은 일을 한다"는 신호로 읽히는 점, 서비스 층 없이 컨트롤러가 리포지토리를 바로 드는 배치가 "나가는 SQL 확인"이라는 목적에는 층을 걷어 낸 편이 빠르다는 판단이고 판단이 끼는 순간 서비스가 다시 필요해지는 자리)

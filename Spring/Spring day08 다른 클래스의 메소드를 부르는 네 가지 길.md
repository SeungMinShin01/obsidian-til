# Spring day08 — 다른 클래스의 메소드를 부르는 네 가지 길

> 실습 파일: `day08/exam/exam1.java`
> 허브: [[Spring MOC]] · 이전: [[Spring day08 요구사항 명세를 API 규격으로 옮기기]]

앞의 다섯 노트는 같은 게시판을 세 번 짜면서 층을 나누고 이름을 관통시키는 이야기였습니다. 그동안 코드에는 `dto.toEntity()`, `BoardDto.from(entity)`, `boardRepository.findById(...)` 처럼 **다른 클래스의 메소드를 부르는 줄**이 계속 나왔는데, 그 줄들이 어떤 표기로 갈리는지는 그때그때 필요한 만큼만 보고 지나갔습니다.

이번 실습은 그 자리를 따로 떼어 확인하는 작은 예제입니다. `main` 하나에 **같은 일(두 수 더하기)을 네 가지 다른 방법으로 부르는 코드**를 나란히 두고, 그 넷이 갈리는 근거를 한 번에 봅니다. 스프링 코드에서 계속 쓰던 표기가 어느 갈래에 속하는지를 뒤늦게 정리하는 성격의 실습입니다.

## 1. 배운 내용

### 1-1. 메소드는 상호작용이다 — 주는 것과 받는 것

주석에 적어 둔 정의가 이번 실습 전체의 축입니다.

```java
// 메소드란? 상호작용 ( 2개이상의 개체를 주고(인수) 받는(리턴))
```

메소드를 "코드 묶음에 이름을 붙인 것"으로만 보면 호출하는 쪽이 안 보입니다. **상호작용**으로 보면 언제나 두 개체가 등장합니다 — 부르는 쪽과 불리는 쪽. 그 둘 사이를 오가는 것이 인수와 반환값입니다.

| 축 | 무엇 | 코드에서 |
| --- | --- | --- |
| 주는 것 | 인수(argument) | `plus(3, 5)` 의 `3`, `5` |
| 받는 것 | 반환값(return) | `int result1 = ...` 의 `8` |
| 부르는 쪽 | 호출자 | `main` |
| 불리는 쪽 | 수신자 | `TestService` 의 인스턴스 또는 클래스 자체 |

"불리는 쪽"이 **인스턴스인가 클래스 자체인가** — 이것이 아래 네 갈래를 가르는 기준이 됩니다.

### 1-2. 같은 일을 부르는 네 가지 길

`TestService.plus(3, 5)` 라는 한 가지 일을, 실습에서는 네 가지 표기로 나란히 적어 두었습니다.

```java
// 1. 인스턴스 생성하여 메소드호출
TestService testService = new TestService();
int result1 = testService.plus(3, 5);

// 2. 싱글톤
// TestService testService = TestService.getInstance();
// int result2 = testService.plus( 3, 5 );

// 3. 메소드가 static 이면
int result2 = TestService.plus2(10, 5);

// 4. 스프링방식: @Component(자동 인스턴스 생성) @Autowired(인스턴스호출)
/*
 * @Autowired
 * private TestService testService;
 * int result4 = testService.plus(10, 5);
 */
```

넷을 한 표로 놓으면 갈림이 분명해집니다.

| 갈래 | 객체를 누가 만드나 | 객체는 몇 개 | 부르는 표기 | 갈아 끼우기 |
| --- | --- | --- | --- | --- |
| ① `new` | 부르는 쪽이 직접 | 호출할 때마다 하나씩 | `인스턴스.메소드()` | 어렵다 — 구현 이름이 코드에 박힌다 |
| ② 싱글톤 | 그 클래스가 스스로 | 프로그램 전체에 하나 | `클래스.getInstance().메소드()` | 어렵다 — 창구 이름이 코드에 박힌다 |
| ③ `static` | 안 만든다 | 없음 (클래스에 붙음) | `클래스.메소드()` | 안 된다 — 대체할 객체 자체가 없다 |
| ④ 스프링 | 컨테이너가 | 기본은 하나 (싱글톤 스코프) | `인스턴스.메소드()` (주입받은 필드) | 쉽다 — 넣어 주는 쪽만 바꾸면 된다 |

①→②→④로 갈수록 **"객체를 만드는 일"이 부르는 쪽에서 멀어집니다.** ①은 부르는 쪽이 직접 만들고, ②는 그 클래스가 대신 만들어 창구만 열어 주고, ④는 아예 바깥의 컨테이너가 만들어 필드에 꽂아 줍니다.

③은 나머지 셋과 축이 다릅니다. ①·②·④는 "누가 만드나"의 갈림인데 ③은 **애초에 만들지 않는** 갈래입니다. 그래서 ③만 표기가 `클래스.메소드()` 로 갈립니다.

②와 ④가 결과적으로 같은 것(하나만 두고 나눠 쓰기)을 하면서도 코드 모양이 다른 이유는, ②는 그 일을 **클래스 안에 손으로** 적고 ④는 **표시 한 줄로 바깥에 맡기기** 때문입니다. 그동안 서비스·리포지토리를 필드로 들고 `boardRepository.findById(...)` 라고만 적어 온 것이 전부 ④였습니다 — `new` 도 `getInstance()` 도 안 보이던 이유가 이것입니다.

### 1-3. 인스턴스와 static — 주체가 있는가 없는가

주석 한 줄이 이 절의 요약입니다.

```java
// 인스턴스(주체O) VS static(주체X)
TestService t1 = new TestService();
t1.달리기();
TestService t2 = new TestService();
t2.달리기();
// TestService.달리기2();
```

```java
void 달리기() {
    System.out.println((this));
}
```

`달리기()` 는 `this` 를 그대로 출력합니다. `t1` 과 `t2` 를 각각 만들어 부르면 찍히는 값이 서로 다릅니다.

```
day08.exam.TestService@1b6d3586
day08.exam.TestService@4554617c
```

같은 코드가 같은 이름으로 불렸는데 결과가 갈렸다는 것은, **메소드가 "누구의" 메소드로 불렸는지가 실행에 남아 있다**는 뜻입니다. 그 "누구"가 `this` 입니다. 인스턴스 메소드에 주체가 있다는 말의 실질이 여기입니다.

`static` 쪽은 반대입니다.

```java
/*
 * static void 달리기2() {
 *     System.out.println(this);
 * }
 */
```

이 모양이 성립하지 않아 주석으로 남겨 둔 자리인데, 이유가 문법 제한이라기보다 **가리킬 대상이 없기 때문**입니다. `static` 은 "이 멤버는 객체가 아니라 클래스에 붙는다"는 표시라서, `TestService.달리기2()` 로 부르는 순간 손에 든 객체가 하나도 없습니다. `this` 가 가리킬 곳이 애초에 만들어지지 않습니다.

| 축 | 인스턴스 메소드 | `static` 메소드 |
| --- | --- | --- |
| 붙는 자리 | 객체 하나하나 | 클래스 자체 |
| 부르는 표기 | `t1.달리기()` | `TestService.plus2(10, 5)` |
| `this` | 부른 그 객체 | 없다 |
| 인스턴스 필드 접근 | 된다 | 안 된다 (어느 객체의 필드인지 정할 수 없다) |
| 만들어지는 시점 | `new` 할 때마다 | 클래스가 메모리에 올라올 때 한 번 |

반대 방향은 됩니다 — 인스턴스 메소드 안에서 `static` 멤버를 부르는 것은 문제가 없습니다. 클래스는 객체보다 먼저 있으니까요. 막히는 것은 **`static` 에서 인스턴스 쪽으로 내려가는 방향** 하나뿐이고, 그 이유도 "객체가 없어서"로 같습니다.

`plus` 와 `plus2` 로 이름을 갈라 둔 자리도 여기에 걸립니다. 같은 이름·같은 매개변수로 인스턴스 메소드와 `static` 메소드를 함께 둘 수는 없습니다 — 부르는 쪽 표기가 갈리더라도 컴파일러가 보기에는 시그니처가 같아서 어느 쪽인지 정할 수 없기 때문입니다.

### 1-4. 이 갈림이 DTO 변환 메소드에서 이미 쓰이고 있었다

주석에 나란히 적힌 두 줄이 앞 실습들과 이어지는 자리입니다.

```java
// memberDto.toEntity() <---- 현재 dto 인스턴스가 엔티티로
// MemberDto.from( entity ) <-- 변환할 엔티티를 매개변수로 전달
```

day05 이후 DTO마다 붙여 온 변환 메소드 두 개가 왜 한쪽은 인스턴스이고 한쪽은 `static` 인지가 1-3의 갈림 그대로입니다.

| | `toEntity()` | `from(entity)` |
| --- | --- | --- |
| 종류 | 인스턴스 메소드 | `static` 메소드 |
| 부를 때 손에 있는 것 | `MemberDto` 객체 | `MemberEntity` 객체 |
| 만들려는 것 | 엔티티 | DTO |
| 재료를 어디서 얻나 | `this` 의 필드 | 매개변수 |

기준 한 줄로 정리하면 이렇습니다 — **부르는 시점에 그 클래스의 객체가 이미 손에 있으면 인스턴스 메소드로 `this` 를 쓰고, 없으면 `static` 으로 재료를 인자로 받는다.**

`from()` 을 인스턴스 메소드로 만들 수 없는 이유가 여기서 나옵니다. DTO를 만들려고 부르는 메소드인데 그것을 부르려면 DTO가 이미 있어야 하니 순서가 맞지 않습니다. 반대로 `toEntity()` 를 `static` 으로 바꾸면 이미 손에 든 DTO를 매개변수로 한 번 더 넘기게 됩니다.

`builder()`, `getInstance()`, `main()` 이 모두 `static` 인 것도 같은 사정입니다. 셋 다 **객체가 아직 없는 시점에 불려야 하는** 메소드입니다.

### 1-5. 연산은 값 하나를 돌려준다 — 그래서 이어 붙는다

체이닝을 설명하기 위해 사칙연산을 먼저 놓았습니다.

```java
// 5. 사칙연산( 연산은 항상 하나의 값 반환 )
int x = 10 + 2 + 5; // 10+2 -> 12 + 5 => 17
```

`10 + 2 + 5` 가 한 번에 계산되는 것이 아니라 왼쪽부터 **둘씩 묶여 값 하나로 줄어드는** 과정을 거칩니다. 줄어든 자리에 다시 값이 있으니 그다음 연산이 이어 붙을 수 있습니다.

메소드도 같습니다. 반환값이 있는 메소드는 호출이 끝난 자리에 값 하나가 남습니다.

```java
TestService t3 = new TestService();
t3.개별호출().밥먹기();
// t3.개별호출() --> Student(신동엽)
// Studemt(신동엽).밥먹기();
```

축약 과정을 그대로 따라가면 이렇게 됩니다.

| 단계 | 그 자리에 있는 것 |
| --- | --- |
| `t3.개별호출()` | `Student` 객체 (`list.get(1)`) |
| `Student.밥먹기()` | `void` — 더 이어 붙일 수 없다 |

`개별호출()` 의 반환 타입이 `Student` 라서 그 호출이 끝난 자리는 **`Student` 객체 하나**입니다. 그러니 바로 뒤에 점을 찍고 `Student` 의 메소드를 부를 수 있습니다. 변수에 담았다 부르는 것과 결과는 같고, 중간 이름을 두지 않았을 뿐입니다.

```java
Student s = t3.개별호출();   // 이렇게 나눠 적은 것과 같다
s.밥먹기();
```

체이닝이 되는 조건은 하나입니다 — **앞 호출이 객체를 돌려줄 것.** 반환 타입이 `void` 면 그 자리에 아무것도 안 남아서 뒤에 점을 찍을 수 없습니다. `밥먹기()` 뒤에 더 이어 붙일 수 없는 이유가 그것입니다.

빌더가 `.title(...).content(...).build()` 로 길게 이어지는 것도 각 메소드가 자기 자신(`this`)을 돌려주기 때문이고, 마지막 `build()` 만 다른 타입을 돌려주며 체인을 끝냅니다.

### 1-6. 필드 초기화와 생성자 — 인스턴스마다 따로 있는 상태

`TestService` 안쪽은 필드와 생성자가 짝을 이룹니다.

```java
List<Student> list = new ArrayList<>();

TestService() {
    list.add(new Student("강호동"));
    list.add(new Student("신동엽"));
}

Student 개별호출() {
    return list.get(1);
}
```

`new TestService()` 한 번에 일어나는 일을 순서대로 보면 이렇습니다.

| 순서 | 일어나는 일 |
| --- | --- |
| 1 | 객체 자리가 잡히고 필드가 기본값(`null`)으로 채워진다 |
| 2 | 필드 초기화 식이 돈다 — `list` 에 빈 `ArrayList` 가 들어간다 |
| 3 | 생성자 본문이 돈다 — `Student` 둘이 만들어져 `list` 에 담긴다 |

여기서 앞 절의 "주체가 있다"가 구체적인 값으로 드러납니다. `t1` 과 `t3` 는 각각 **자기 리스트와 자기 학생 둘**을 갖습니다. 한쪽에서 리스트를 건드려도 다른 쪽은 그대로입니다. 인스턴스 메소드가 `this` 를 통해 다루는 것이 바로 이 "각자의 상태"입니다.

만약 `list` 를 `static` 으로 두면 이야기가 달라집니다. 리스트가 클래스에 하나만 붙어 모든 인스턴스가 같은 것을 보게 되고, `new` 를 몇 번 하든 생성자가 돌 때마다 같은 리스트에 학생이 계속 쌓입니다. **상태를 갖는 것을 `static` 으로 두면 안 되는 이유**가 이 한 줄로 설명됩니다.

`Student` 쪽도 같은 구조입니다.

```java
class Student {
    String name;

    void 밥먹기() {
        System.out.println(this.name + "밥 먹는다.");
    }

    Student(String name) {
        this.name = name;
    }
}
```

생성자의 `this.name = name` 은 매개변수와 필드 이름이 겹칠 때 둘을 가르는 표기입니다. 왼쪽 `this.name` 이 이 객체의 필드, 오른쪽 `name` 이 넘어온 값입니다. `밥먹기()` 안의 `this.name` 은 생략해도 같은 뜻이지만, 적어 두면 그 값이 **매개변수가 아니라 이 객체가 들고 있는 값**임이 눈에 남습니다.

## 2. 추가로 알면 좋은 활용법

### 2-1. 체이닝이 끊기거나 위험해지는 자리

체이닝은 짧아서 좋지만 두 곳에서 걸립니다.

| 상황 | 무엇이 문제인가 | 대응 |
| --- | --- | --- |
| 중간이 `void` | 그 자리에 값이 없어 점을 못 찍는다 | 반환 타입을 다시 보거나 나눠 적기 |
| 중간이 `null` | 다음 점에서 `NullPointerException` | `Optional` 로 옮기거나 앞에서 확인 |

`list.get(1)` 처럼 목록에서 꺼내는 자리는 비어 있을 수 있어서, 실무 코드에서는 꺼내는 단계와 쓰는 단계를 나눠 두는 편이 안전합니다. 반환 타입을 `Optional<Student>` 로 두면 "없을 수 있음"이 타입에 남고, `t3.개별호출().map(Student::getName).orElse("없음")` 처럼 체인은 유지하면서 중간에 끊기는 자리를 표기로 흡수할 수 있습니다.

체인을 몇 칸까지 이을지도 판단이 필요합니다. `a.getB().getC().getD()` 처럼 남의 객체 속을 계속 파고들면 중간 구조가 바뀔 때마다 이 줄이 함께 깨집니다(디미터 법칙이 말하는 자리). 한 칸 정도는 읽기 쉽고, 그 이상이면 필요한 값을 바로 돌려주는 메소드를 상대 쪽에 두는 편이 낫습니다.

### 2-2. `static` 이 어울리는 자리와 아닌 자리

| `static` 이 어울림 | 이유 |
| --- | --- |
| 유틸 계산 (`Math.max`) | 입력만으로 결과가 정해지고 상태가 필요 없다 |
| 정적 팩토리 (`from`·`of`·`valueOf`) | 만들려는 타입의 객체가 아직 없다 |
| `builder()`·`main()` | 마찬가지로 객체가 없는 시점에 불린다 |
| 상수 (`static final`) | 값이 하나뿐이고 안 바뀐다 |

| `static` 이 안 어울림 | 이유 |
| --- | --- |
| 상태를 들고 있는 필드 | 모든 인스턴스가 공유해 값이 섞인다 |
| 갈아 끼울 여지가 있는 협력 객체 | 대체할 객체 자체가 없어 테스트에서 다른 구현을 넣을 수 없다 |
| 요청마다 달라지는 값 | 여러 스레드가 같은 자리를 동시에 건드린다 |

유틸 클래스는 인스턴스를 만들 이유가 없으므로 `private` 생성자를 두어 `new` 를 막아 두는 관용이 있습니다. `import static` 을 쓰면 `Math.max` 를 `max` 로 줄여 적을 수 있지만, 어느 클래스에서 온 이름인지가 사라지므로 아껴 쓰는 편이 낫습니다.

### 2-3. 스프링 빈은 싱글톤이지만 `static` 은 아니다

④번 갈래에서 헷갈리기 쉬운 자리입니다. 스프링 빈은 기본 스코프가 싱글톤이라 **하나만 만들어져 공유**되는데, 그렇다고 `static` 으로 두지는 않습니다. 이유는 셋입니다.

- 인터페이스를 두고 구현을 갈아 끼울 수 있다 — `static` 에는 이 여지가 없다
- 주입받는 자리를 바꾸면 테스트에서 다른 구현을 넣을 수 있다
- 프록시로 감쌀 수 있다 — `@Transactional`·AOP가 도는 방식이 이것이다

정리하면 **"객체가 하나뿐"인 것과 "객체가 아예 없는 것"은 다릅니다.** 싱글톤은 앞이고 `static` 은 뒤입니다.

한 가지 더 — 애노테이션은 **컨테이너가 읽어 줄 때만** 효과가 납니다. `main` 안에서 `new` 로 직접 만든 객체는 컨테이너를 거치지 않으므로, 클래스에 계층 표시가 붙어 있어도 그냥 평범한 자바 객체입니다. 같은 이유로 컨테이너가 관리하지 않는 객체 안에서는 `@Autowired` 필드가 채워지지 않고 `null` 로 남습니다. 표시가 붙었는데 아무 일도 안 일어나는 것처럼 보일 때 가장 먼저 볼 자리입니다.

### 2-4. 주입받는 두 표기 — 필드 주입과 생성자 주입

④번 갈래를 실제로 적을 때 표기가 둘로 갈립니다.

```java
// 필드 주입
@Autowired
private TestService testService;

// 생성자 주입
private final TestService testService;
// + @RequiredArgsConstructor
```

| 축 | 필드 주입 | 생성자 주입 |
| --- | --- | --- |
| `final` | 못 붙인다 | 붙는다 — 만들어진 뒤 안 바뀐다 |
| 의존 개수 | 필드가 늘어도 안 드러난다 | 생성자가 길어져 눈에 보인다 |
| 테스트 | 컨테이너 없이 넣기 번거롭다 | 생성자로 그냥 넣으면 된다 |
| 순환 참조 | 뜬 뒤에 드러난다 | 뜰 때 걸린다 |

생성자가 길어지는 것이 단점처럼 보이지만, **"이 클래스가 너무 많은 일을 한다"가 코드 모양으로 드러나는** 신호라서 오히려 값어치가 있습니다.

### 2-5. 한 파일에 클래스를 여럿 두기

실습 파일에는 `exam1`·`TestService`·`Student` 세 클래스가 한 파일에 들어 있습니다. 규칙은 이렇습니다.

- `public` 클래스는 파일당 하나, 그 이름이 파일 이름과 같아야 한다
- 나머지는 접근제한자 없이 두어 같은 패키지 안에서만 보이게 한다

작은 예제에서 파일을 오가지 않아도 되는 편의가 있지만, 클래스가 커지면 파일을 나누는 편이 찾기 쉽습니다. 다른 곳에서 쓸 일이 없는 작은 데이터 묶음이라면 중첩 클래스(`static` 중첩 클래스)로 안에 두는 갈래도 있습니다.

## 3. 더 나아가 알면 좋은 것

### 3-1. 싱글톤을 손으로 만들 때 걸리는 자리

②번 갈래를 직접 적으면 세 줄이 필요합니다 — `private` 생성자, `private static final` 인스턴스, `getInstance()` 창구. 그런데 늦은 초기화(`getInstance()` 안에서 처음 만들기)로 바꾸는 순간 여러 스레드가 동시에 들어와 인스턴스가 둘 만들어질 수 있습니다.

| 갈래 | 성질 |
| --- | --- |
| 이른 초기화 | 클래스가 올라올 때 만든다 — 안전하지만 안 쓸 수도 있는 것을 미리 만든다 |
| `synchronized` | 안전하지만 부를 때마다 잠금 비용 |
| 이중 검사(DCL) + `volatile` | 잠금을 줄이지만 적기 까다롭다 |
| holder 중첩 클래스 | 클래스 로딩 규칙을 이용 — 지연되면서 안전하다 |
| `enum` | 가장 간단하고 직렬화·리플렉션까지 막힌다 |

이 표를 보고 나면 `@Component` 표시 한 줄이 무엇을 대신해 주는지가 분명해집니다. **컨테이너가 만드는 시점과 개수를 책임지므로 이 판단 전체가 사라집니다.**

### 3-2. `this` 는 숨은 첫 매개변수다

`dto.toEntity()` 는 내부적으로 `toEntity(dto)` 에 가깝습니다. 점 앞에 적은 객체가 메소드 안에서 `this` 라는 이름으로 들어오는 구조입니다. 파이썬이 `def method(self)` 로 그 자리를 눈에 보이게 적는 것과 같은 이야기를, 자바는 감춰 두고 `this` 라는 예약어로만 남겨 둔 셈입니다.

이렇게 보면 `static` 에 `this` 가 없는 이유가 다시 한 줄로 정리됩니다 — **점 앞에 객체를 적지 않고 부르는 메소드라서, 넘어올 첫 매개변수가 없습니다.**

### 3-3. 객체를 만드는 책임을 옮기는 것이 왜 설계 이야기가 되는가

①에서 ④로 가는 흐름은 표기 취향의 문제가 아니라 **의존 방향을 바꾸는 작업**입니다.

```
① new         : 부르는 쪽이 "무엇을 쓸지"까지 정한다
② getInstance : 만드는 일은 넘겼지만 창구 이름은 여전히 박혀 있다
④ 주입        : 부르는 쪽은 "필요하다"만 적고, 무엇을 넣을지는 바깥이 정한다
```

④가 되면 쓰는 쪽 코드에 구현 이름이 남지 않으므로, 구현을 바꿔도 쓰는 쪽을 안 고쳐도 됩니다. 이것이 제어의 역전(IoC)과 의존성 주입(DI)이 말하는 값어치이고, day03에서 표시 한 줄로 지나갔던 이야기의 실체입니다.

### 3-4. 다음에 볼 키워드

- 빈 스코프 — `singleton`·`prototype`·`request`·`session`
- `@Primary`·`@Qualifier` — 같은 타입의 빈이 둘 이상일 때 고르기
- 프록시와 AOP — `@Transactional` 이 실제로 걸리는 자리, 자기 호출에서 안 먹는 이유
- `Optional` 체이닝 — `map`·`flatMap`·`orElseThrow` 로 끊기는 자리 흡수하기
- 불변 객체와 빌더 — `final` 필드만 두고 생성 시점에 다 채우기
- 디미터 법칙 — 체인을 몇 칸까지 이을지의 기준
- 정적 팩토리 메소드 이름 관용 — `from`·`of`·`valueOf`·`getInstance`·`newInstance`
- 클래스 로딩과 초기화 순서 — `static` 블록이 도는 시점

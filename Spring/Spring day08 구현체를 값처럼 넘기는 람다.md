# Spring day08 — 구현체를 값처럼 넘기는 람다

> 실습 파일: `day08/exam/exam2.java`
> 허브: [[Spring MOC]] · 이전: [[Spring day08 다른 클래스의 메소드를 부르는 네 가지 길]] · 다음: [[Spring day08 컬렉션 순회와 스트림 API]]

앞 노트는 **다른 클래스의 메소드를 어떻게 부르는가**를 네 표기로 갈라 본 자리였습니다. 거기서 부르는 대상은 언제나 "이미 어딘가에 정의된 메소드"였고, 부르는 쪽은 그 이름을 적기만 했습니다.

이번 실습은 방향이 반대입니다. **부르는 쪽이 동작 자체를 만들어서 넘기는** 표기를 봅니다. 인터페이스 하나를 두고 그 구현을 ① 익명 구현체 ② 람다 두 가지로 적어 보고, 그다음 자바가 미리 만들어 둔 함수형 인터페이스 네 개(`Function`·`Supplier`·`Consumer`·`Predicate`)를 차례로 써 봅니다. `main` 하나에 다 들어가는 짧은 예제인데, 스프링 코드에서 이미 여러 번 지나쳤던 표기(`orElseThrow(() -> ...)`, `.map(...)`, `.forEach(...)`)의 뿌리가 전부 여기입니다.

## 1. 배운 내용

### 1-1. 인터페이스 하나와 그것을 채우는 세 가지 표기

실습의 출발점은 추상 메소드 하나짜리 인터페이스입니다.

```java
interface Calculator {
    int plus(int x, int y);
}
```

인터페이스는 몸통이 없는 약속이라 **그 자체로는 못 씁니다.** 누군가 몸통을 채워야 하는데, 그 채우는 방식이 세 갈래입니다.

| 표기 | 모양 | 이름이 남는가 | 쓰는 자리 |
| --- | --- | --- | --- |
| ① 구현 클래스 | `class Calc implements Calculator { ... }` | 남는다 (파일·클래스 이름) | 여러 곳에서 재사용할 때 |
| ② 익명 구현체 | `new Calculator() { ... }` | 안 남는다 | 여기서 한 번만 쓸 때 |
| ③ 람다 | `(x, y) -> { ... }` | 안 남는다 | 추상 메소드가 하나일 때 |

실습 주석이 ①과 ②를 이렇게 갈라 둡니다.

```java
// 1.구현체: 추상메소드(인터페이스) 구현한 객체
// 2.익명구현체: 추상메소드 구현한 클래스 없이 직접(1회성) 구현
```

핵심은 **"1회성"** 입니다. 한 번만 쓸 동작에 클래스 이름과 파일을 하나 늘리는 것이 아깝기 때문에 ②·③이 있습니다.

### 1-2. 익명 구현체 — 선언과 생성을 한 자리에서

```java
Calculator calc = new Calculator() {
    @Override
    public int plus(int x, int y) {
        return x + y;
    }
};
int result1 = calc.plus(5, 3);
```

`new Calculator()` 라고 적혀 있지만 인터페이스는 인스턴스로 만들 수 없습니다. 이 표기는 **"`Calculator` 를 구현한 이름 없는 클래스를 지금 만들고, 그 인스턴스를 하나 만들어라"** 는 뜻입니다. 클래스 정의와 객체 생성이 한 줄에 겹쳐 있는 셈입니다.

문법에서 눈에 담아 둘 자리 셋입니다.

| 자리 | 내용 |
| --- | --- |
| `new 인터페이스()` | 인터페이스를 직접 만드는 것이 아니라 익명 구현 클래스를 그 자리에서 정의하는 표기 |
| `{ ... }` | 클래스 몸통. 여기 안에 추상 메소드 구현을 다 채워야 한다 |
| 끝의 `;` | 클래스 정의가 아니라 **변수 대입문**이라서 세미콜론이 붙는다 |

마지막 세미콜론이 붙는 이유가 이 표기의 성격을 그대로 말해 줍니다. 이것은 클래스 선언이 아니라 값 하나를 만들어 변수에 넣는 **식(expression)** 입니다. 즉 **동작이 값이 된** 자리입니다.

### 1-3. 람다는 익명 구현체에서 지울 수 있는 것을 다 지운 표기

같은 동작을 람다로 적으면 이렇게 됩니다.

```java
Calculator calc2 = (x, y) -> {
    return x + y;
};
int result2 = calc2.plus(5, 3);
```

실습 주석이 두 표기를 나란히 대비해 둡니다.

```java
// vs Override public int plus(int x, int y) { return x+y; }
```

무엇이 지워졌는지 하나씩 세어 보면 람다가 새 문법이 아니라 **축약**이라는 것이 보입니다.

| 지워진 것 | 지울 수 있는 이유 |
| --- | --- |
| `new Calculator()` | 왼쪽 변수 타입이 `Calculator` 라 무엇을 만들지 이미 안다 |
| `@Override public` | 채울 자리가 추상 메소드 하나뿐이라 접근제한자를 고를 여지가 없다 |
| 반환 타입 `int` | 인터페이스에 이미 적혀 있다 |
| 메소드 이름 `plus` | 채울 메소드가 하나뿐이라 이름을 고를 여지가 없다 |
| 매개변수 타입 `int x, int y` | 인터페이스의 선언에서 타입을 그대로 가져올 수 있다 |
| 남은 것 | **매개변수 이름 + `->` + 몸통** |

그래서 람다는 "함수를 값으로 쓰는 새 기능"이라기보다 **인터페이스 구현을 적는 가장 짧은 표기**로 보는 편이 이해가 빠릅니다. 호출하는 쪽(`calc2.plus(5, 3)`)이 익명 구현체와 완전히 똑같은 것도 그 때문입니다 — 만들어지는 것은 어느 쪽이나 `Calculator` 타입의 객체입니다.

### 1-4. 람다가 성립하는 조건 — 추상 메소드가 하나뿐일 것

위 표에서 "이름을 고를 여지가 없다"는 이유가 두 번 나왔습니다. 여기에 람다의 유일한 전제가 들어 있습니다.

> **추상 메소드가 정확히 하나인 인터페이스만 람다로 적을 수 있다.**

메소드가 둘이면 `(x, y) -> ...` 라고 적었을 때 그것이 어느 메소드의 구현인지 정할 방법이 없습니다. 이런 인터페이스를 **함수형 인터페이스(functional interface)** 라고 부릅니다. `Calculator` 는 `plus` 하나뿐이라 조건을 만족합니다.

정리하면 갈래는 이렇습니다.

| 인터페이스의 추상 메소드 수 | 익명 구현체 | 람다 |
| --- | --- | --- |
| 1개 | 된다 | 된다 |
| 2개 이상 | 된다 | 안 된다 |

익명 구현체는 메소드 이름을 다 적으므로 개수 제한이 없고, 람다는 이름을 안 적으므로 하나여야 합니다. **표기에서 무엇을 지웠는지가 곧 제약의 이유**가 됩니다.

### 1-5. 제네릭 — 안에서 쓸 타입을 바깥에서 정하기

실습이 함수형 인터페이스로 넘어가기 전에 제네릭을 한 줄로 정의해 둡니다.

```java
// ** 제네릭이란? 클래스/인터페이스 안에서 사용할 타입을 정한다.
// List< MemberDto > , 즉] List에 저장할 자료들의 타입을 MemberDto로 정한다.
```

`Function<Integer, Integer>` 같은 표기를 읽으려면 이 정의가 먼저 필요합니다. 꺾쇠 안은 **그 클래스가 다룰 타입을 쓰는 쪽이 지정하는 자리**입니다.

| 표기 | 읽는 법 |
| --- | --- |
| `List<BoardDto>` | 담을 원소 타입이 `BoardDto` 인 리스트 |
| `Optional<BoardEntity>` | 있을 수도 없을 수도 있는 값의 타입이 `BoardEntity` |
| `Function<Integer, Integer>` | 인수 타입 `Integer`, 반환 타입 `Integer` 인 함수 |

한 번 정해 두면 꺼낼 때 형변환이 필요 없고, 다른 타입을 넣으려 하면 컴파일 단계에서 걸립니다. 앞서 리포지토리를 만들 때 적었던 `JpaRepository<BoardEntity, Long>` 도 같은 표기이고, 거기서 엔티티 타입과 PK 타입을 지정한 것이 그대로 메소드 시그니처에 반영된 것이었습니다.

기본형은 꺾쇠 안에 못 들어가므로 `int` 가 아니라 `Integer` 를 적습니다. 값을 꺼내고 넣을 때는 오토박싱·언박싱이 자동으로 걸립니다.

### 1-6. 자바가 미리 만들어 둔 함수형 인터페이스 네 개

동작을 값으로 넘기는 자리마다 `Calculator` 같은 인터페이스를 매번 만들면 비슷한 것이 계속 늘어납니다. 그래서 `java.util.function` 패키지에 자주 쓰이는 모양이 미리 들어 있습니다. 실습은 그중 네 개를 씁니다.

```java
Function<Integer, Integer> function = (x) -> { return x * 2; };
System.out.println(function.apply(3));   // 6

Supplier<Integer> supplier = () -> { return 2; };
System.out.println(supplier.get());      // 2

Consumer<String> consumer = (str) -> { System.out.println(str); };
consumer.accept("유재석");                // 유재석

Predicate<Integer> predicate = (x) -> { return x % 2 == 0; };
boolean result4 = predicate.test(3);     // false
```

| 인터페이스 | 제네릭 | 호출 메소드 | 매개변수 | 반환 |
| --- | --- | --- | --- | --- |
| `Function<T, R>` | 인수 타입, 반환 타입 | `apply(T)` | O | O |
| `Supplier<T>` | 반환 타입 | `get()` | X | O |
| `Consumer<T>` | 인수 타입 | `accept(T)` | O | X |
| `Predicate<T>` | 인수 타입 | `test(T)` | O | `boolean` 고정 |

호출 메소드 이름이 넷 다 다릅니다. 외워야 할 것 같지만, 이름이 하는 일을 그대로 말하고 있어서 뜻으로 붙잡는 편이 오래갑니다 — 적용(apply)하고, 공급(get)받고, 소비(accept)하고, 판정(test)합니다.

### 1-7. 넷을 가르는 축은 매개변수와 반환의 유무

네 개는 임의로 골라 둔 것이 아니라 **가능한 조합을 채운 것**입니다.

| | 반환 O | 반환 X |
| --- | --- | --- |
| **매개변수 O** | `Function` (반환 타입 자유) / `Predicate` (반환 `boolean` 고정) | `Consumer` |
| **매개변수 X** | `Supplier` | (할 일이 없어 안 둔다) |

빈 칸이 하나 있는데, 매개변수도 없고 반환도 없으면 값을 주고받지 않는다는 뜻이라 함수로 둘 이유가 없습니다. 그 자리는 `Runnable` 이 이미 맡고 있습니다.

`Predicate` 가 `Function<T, Boolean>` 과 따로 있는 이유는 **쓰임이 자주 반복되기 때문**입니다. 걸러내기는 워낙 흔한 동작이라 전용 이름을 두면 코드를 읽을 때 "이건 판정이구나"가 바로 보이고, 박싱 없이 기본형 `boolean` 을 쓸 수 있습니다.

### 1-8. 진짜 쓰이는 자리는 직접 호출이 아니다

실습 마지막 주석이 이 예제의 결론입니다.

```java
// 활용처: 위 4가지 직접적인 사용이 아닌 API(남이만든 클래스/메소드) 에서 활용가능
// forEach -> Consumer , map -> Function , filter -> Predicate
// 즉] 스트림API 주로 사용된다.
```

예제에서는 `function.apply(3)` 처럼 직접 불렀지만, 실제로 이렇게 쓸 일은 드뭅니다. 값이 필요하면 그냥 계산하면 되기 때문입니다. 이 네 개가 값어치를 갖는 자리는 **동작을 남의 메소드에 넘겨줄 때**입니다.

| 남의 메소드 | 받는 타입 | 넘기는 동작 |
| --- | --- | --- |
| `list.forEach(...)` | `Consumer<T>` | 원소 하나로 무엇을 할지 |
| `stream().map(...)` | `Function<T, R>` | 원소 하나를 무엇으로 바꿀지 |
| `stream().filter(...)` | `Predicate<T>` | 원소 하나를 남길지 말지 |
| `orElseThrow(...)` | `Supplier<X>` | 없을 때 무엇을 만들어 던질지 |

`forEach` 를 만든 쪽은 "반복을 어떻게 돌릴지"를 알고 있고, 부르는 쪽은 "원소마다 무엇을 할지"를 압니다. 그 둘을 갈라 두고 **모르는 쪽을 인수로 받는** 구조가 함수형 인터페이스입니다. 앞 노트에서 본 의존성 주입이 "무엇을 쓸지"를 바깥에서 정해 준 것이라면, 여기는 "무엇을 할지"를 부르는 쪽이 정해 넣어 주는 셈입니다.

## 2. 추가로 알면 좋은 활용법

### 2-1. 람다 몸통 축약 — 한 줄이면 더 짧아진다

실습은 전부 `{ return ...; }` 형태로 적었지만, 몸통이 식 하나면 중괄호와 `return` 을 같이 지울 수 있습니다.

```java
Function<Integer, Integer> f1 = (x) -> { return x * 2; };  // 실습 표기
Function<Integer, Integer> f2 = x -> x * 2;                // 축약
```

| 상황 | 규칙 |
| --- | --- |
| 매개변수 1개 | 괄호 생략 가능 — `x -> ...` |
| 매개변수 0개 또는 2개 이상 | 괄호 필수 — `() -> ...`, `(x, y) -> ...` |
| 몸통이 식 하나 | `{}` 와 `return` 을 함께 생략. 둘 중 하나만 지우는 것은 안 된다 |
| 몸통이 두 줄 이상 | `{}` 필수, 반환이 있으면 `return` 도 필수 |

`{}` 를 쓰면서 `return` 만 빼거나, `return` 을 쓰면서 `{}` 만 빼는 것은 성립하지 않습니다. 둘은 한 묶음으로 움직입니다.

배우는 동안에는 실습처럼 다 적어 두는 편이 무엇이 생략된 것인지 눈에 남아서 좋고, 익숙해진 뒤에 줄이면 됩니다.

### 2-2. 메소드 참조 — 람다가 그냥 부르기만 할 때

람다가 **받은 인수를 그대로 어떤 메소드에 넘기기만** 한다면 `::` 로 더 줄일 수 있습니다.

```java
Consumer<String> c1 = str -> System.out.println(str);
Consumer<String> c2 = System.out::println;            // 같은 것

Function<BoardEntity, BoardDto> f1 = e -> BoardDto.from(e);
Function<BoardEntity, BoardDto> f2 = BoardDto::from;  // 같은 것
```

| 모양 | 뜻 | 예 |
| --- | --- | --- |
| `클래스::정적메소드` | 인수를 그대로 넘긴다 | `BoardDto::from` |
| `인스턴스::메소드` | 그 인스턴스의 메소드를 부른다 | `System.out::println` |
| `클래스::인스턴스메소드` | 첫 인수가 수신자가 된다 | `String::length` |
| `클래스::new` | 생성자를 부른다 | `ArrayList::new` |

앞 노트에서 `BoardDto.from(entity)` 가 왜 `static` 인지 정리했는데, 그 덕분에 여기서 `BoardDto::from` 이라는 짧은 표기가 그대로 성립합니다. 정적 팩토리 메소드로 이름을 통일해 두면 스트림 안에서 읽기 좋은 줄이 나오는 것이 이유 중 하나입니다.

### 2-3. 스프링 코드에서 이미 지나쳤던 자리들

지금까지 실습에서 적어 온 줄 중 함수형 인터페이스를 넘기고 있던 자리를 모아 보면 이렇습니다.

```java
// Supplier — 없을 때 만들 예외를 "만드는 방법"으로 넘긴다
BoardEntity entity = boardRepository.findById(bno)
        .orElseThrow(() -> new RuntimeException("없는 글"));

// Function — 엔티티 하나를 DTO 하나로 바꾸는 방법을 넘긴다
List<BoardDto> list = boardRepository.findAll().stream()
        .map(BoardDto::from)
        .toList();

// Predicate — 남길지 말지 판정하는 방법을 넘긴다
List<CommentEntity> visible = comments.stream()
        .filter(c -> c.getDeleted() == null)
        .toList();

// Consumer — 원소마다 할 일을 넘긴다
list.forEach(dto -> System.out.println(dto.getTitle()));
```

`orElseThrow` 가 `Supplier` 를 받는 이유가 특히 짚어 둘 만합니다. `orElseThrow(new RuntimeException("없는 글"))` 처럼 객체를 바로 넘기면 **값이 있든 없든 예외 객체를 매번 만들게** 됩니다. `Supplier` 로 넘기면 "필요해지면 그때 만들어라"가 되어 값이 있는 경우에는 아예 만들지 않습니다. 동작을 넘기면 **실행 시점을 미룰 수 있다**는 것이 함수형 인터페이스의 또 하나의 값어치입니다.

### 2-4. 네 개에서 파생된 변형들

같은 패키지에 매개변수 개수나 타입만 바꾼 변형이 더 있습니다. 실습의 `Calculator` 처럼 인수를 둘 받는 모양도 이미 준비되어 있습니다.

| 인터페이스 | 모양 | 메모 |
| --- | --- | --- |
| `BiFunction<T, U, R>` | 인수 둘 → 반환 | `Calculator` 가 하려던 것과 같은 자리 |
| `BiConsumer<T, U>` | 인수 둘 → 반환 없음 | `map.forEach((k, v) -> ...)` |
| `UnaryOperator<T>` | 인수·반환 타입이 같음 | `Function<T, T>` 의 별칭 |
| `BinaryOperator<T>` | 인수 둘·반환 셋 다 같은 타입 | `reduce(Integer::sum)` |
| `IntFunction`·`IntPredicate` 등 | 기본형 전용 | 박싱을 피하는 갈래 |

`Calculator` 를 직접 만드는 대신 `BiFunction<Integer, Integer, Integer>` 를 써도 같은 일이 됩니다. 그래도 도메인에서 뜻이 분명한 이름이 필요할 때는 직접 만드는 편이 읽기 좋습니다 — 표준 인터페이스는 이름이 `apply` 라 무엇을 적용하는지가 안 보이기 때문입니다.

### 2-5. `@FunctionalInterface` 로 조건을 못 박아 두기

추상 메소드가 하나여야 한다는 조건을 컴파일러에 알려 두는 표시가 있습니다.

```java
@FunctionalInterface
interface Calculator {
    int plus(int x, int y);
}
```

이 표시가 붙어 있으면 나중에 누가 추상 메소드를 하나 더 추가할 때 **그 인터페이스 파일에서 바로 컴파일 에러**가 납니다. 표시가 없으면 인터페이스는 조용히 컴파일되고, 이미 그것을 람다로 쓰던 코드들이 대신 깨집니다. 에러가 나는 자리를 원인 쪽으로 당겨 두는 표시라고 보면 됩니다.

동작에는 영향이 없어 없어도 람다는 그대로 됩니다. day03에서 정리한 "애노테이션은 기계가 읽는 표시"의 또 한 사례입니다.

## 3. 더 나아가 알면 좋은 것

### 3-1. 람다는 익명 클래스의 문법 설탕이 아니다

표기만 보면 람다가 익명 구현체의 축약처럼 보이지만, 컴파일 결과는 다릅니다.

| | 익명 구현체 | 람다 |
| --- | --- | --- |
| 컴파일 산출물 | `Outer$1.class` 가 따로 생긴다 | 별도 클래스 파일이 안 생긴다 |
| 인스턴스 생성 시점 | `new` 를 적은 자리에서 매번 | 런타임에 `invokedynamic` 으로 필요할 때 |
| 상태 없는 람다 | 매번 새 객체 | 인스턴스를 재사용할 수 있다 |
| `this` 가 가리키는 것 | 익명 클래스 자신 | 바깥 클래스 |

특히 `this` 가 갈리는 자리는 실제로 걸려 봐야 눈에 들어옵니다. 익명 구현체 안에서 `this` 는 그 익명 객체이고, 람다 안에서 `this` 는 람다를 감싼 바깥 인스턴스입니다. 앞 노트에서 `this` 를 "숨은 첫 매개변수"로 정리해 뒀는데, 람다는 자기 몫의 `this` 를 새로 갖지 않고 바깥 것을 그대로 쓴다고 보면 됩니다.

### 3-2. 클로저와 effectively final

람다는 바깥 지역변수를 몸통 안에서 읽을 수 있습니다. 다만 **바뀌지 않는 변수만** 됩니다.

```java
int base = 10;
Function<Integer, Integer> f = x -> x + base;  // 된다
// base = 20;                                  // 이 줄이 있으면 위가 컴파일 에러
```

`final` 이라고 안 적어도 되지만 **실질적으로 안 바뀌어야(effectively final)** 합니다. 람다는 값을 복사해 들고 가는 구조라, 원본이 나중에 바뀌면 어느 쪽을 봐야 하는지가 애매해지기 때문에 아예 막아 둔 것입니다. 필드는 이 제약을 받지 않습니다 — 필드는 객체 참조를 통해 매번 읽으므로 복사가 아닙니다.

### 3-3. 스트림의 지연 연산

`filter`·`map` 에 넘긴 람다는 **적어 둔 시점에 실행되지 않습니다.** `toList()`·`forEach()` 같은 최종 연산이 불릴 때 비로소 돌기 시작하고, 그것도 원소 하나가 파이프라인 전체를 통과한 뒤 다음 원소로 넘어갑니다.

| 구분 | 예 | 실행 시점 |
| --- | --- | --- |
| 중간 연산 | `filter`·`map`·`sorted`·`distinct` | 미뤄 둔다 (스트림을 반환) |
| 최종 연산 | `toList`·`forEach`·`count`·`reduce` | 이때 전부 돈다 |

동작을 값으로 넘길 수 있기 때문에 이런 미루기가 가능합니다. `orElseThrow(() -> ...)` 에서 봤던 "실행 시점을 미룬다"가 스트림 전체 규모로 적용된 것입니다.

### 3-4. JPA·스프링에서 다시 만나는 자리

지금 배운 표기가 앞으로 어디서 또 나오는지 미리 이름만 적어 둡니다.

| 자리 | 넘기는 것 |
| --- | --- |
| `Optional.map`·`filter`·`ifPresent` | `Function`·`Predicate`·`Consumer` |
| `Specification`·`Example` (동적 쿼리) | 조건을 객체로 조립 |
| `RestTemplate`·`JdbcTemplate` 의 콜백 | "연결은 내가 열 테니 안에서 할 일만 넘겨라" |
| `@Transactional` 대신 `TransactionTemplate` | 트랜잭션 경계 안에서 돌 코드를 람다로 |
| 스프링 시큐리티 설정 (`http.authorizeHttpRequests(auth -> ...)`) | 설정 절차 자체를 람다로 |

공통점은 **뼈대는 라이브러리가 갖고, 달라지는 부분만 부르는 쪽이 넘긴다**는 구조입니다. 이 구조에 이름을 붙이면 템플릿 메소드 패턴이고, 스프링의 `~Template` 로 끝나는 클래스들이 다 그 이름을 달고 있습니다.
